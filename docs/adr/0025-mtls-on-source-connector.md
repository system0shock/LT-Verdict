# ADR 0025: mTLS на коннекторе онлайн-источников: клиентский сертификат на профиль

Дата: 2026-10-05.

Статус: Proposed. Решение владельца 2026-10-05 (раздел «Контекст», п. 1) фиксирует
требование, а формат профиля, коды ошибок и порядок проверки ниже предложены
автором и не приняты владельцем: вопросы с рекомендациями собраны в разделе
«Вопросы владельцу». Этот ADR ничего не меняет в коде, контрактах, схемах и
пользовательских документах. Номер 0025 выбран как следующий после 0024; перед
слиянием его нужно перепроверить по `origin/main` (на 2026-10-05 файлов с номером
0025 и выше нет ни в `docs/adr/`, ни в открытых ветках и PR).

Связь. ADR [0007](0007-opt-in-online-sources.md) (Accepted) не переписывается: он
по-прежнему требует, чтобы TLS проверялся, редиректы были отключены, а профили
читались из явного локального файла. Этот ADR добавляет к нему необязательные
настройки TLS на профиль и три кода ошибок. Основание фактов:
[отчёт сквозной проверки демо](../superpowers/plans/2026-10-05-demo-walkthrough-report.md)
(раздел «Подключение к Grafana: mTLS», дефект D18).

## Контекст

### 1. Решение владельца 2026-10-05

Источник: ответ владельца на вопрос 49 пакета вопросов (файл
`docs/superpowers/plans/2026-10-05-owner-questions.md` в основном чекауте, не в
git), передан оркестратором. Суть: анонимный просмотр Grafana на боевом стенде

модель в отдельной сессии; от этой работы нужны **только документация и mTLS на
коннекторе**.

Проверено в отчёте демо 2026-10-05 запуском: клиентский сертификат работает на
уровне процесса через `JAVA_OPTS` (`-Djavax.net.ssl.keyStore=...` и
`trustStore`): с временным TLS-прокси (`CERT_REQUIRED`) перед Grafana источник
`COMPLETE`, без свойств анализ завершается `SOURCE_ACQUISITION_FAILED` с запросами
`SOURCE_HTTP_ERROR`. Настоящий боевой mTLS-узел не проверялся.

### 3. Чего нет

1. Настройки в профиле: путей к ключу, сертификату и CA, пароля через `*_env`.
2. Изоляции: свойства JVM глобальны на процесс, `HttpClient` один на все профили,
   два источника с разными сертификатами невозможны.
3. Безопасного пароля: пароль хранилища в `JAVA_OPTS` виден в командной строке.
4. Диагностики: «нет сертификата», «CA не доверен», «имя не совпало», «срок
   истёк» неотличимы от недоступности сети.
5. Документации.

## Решение (предлагается)

### Д1. Контракт: необязательный объект `tls` в профиле, версия документа не меняется

В профиль HTTP-источника (`source_kind`: `prometheus`, `victoria_metrics`,
`influxdb`, `opensearch`; `transport`: `direct` и `grafana_proxy`) добавляется
необязательный объект `tls`:

```json
{
  "id": "grafana-prod",
  "source_kind": "prometheus",
  "transport": "grafana_proxy",
  "base_url": "https://grafana.example.internal",
  "datasource_uid": "prometheus-main",
  "tls": {
    "ca_file": "/etc/ltv/tls/ca.pem",
    "client_keystore_file": "/etc/ltv/tls/client.p12",
    "client_keystore_password_env": "LTV_GRAFANA_MTLS_PASSWORD"
  },
  "queries": []
}
```

Поля объекта `tls` (все необязательны, но объект не пуст; лишние поля отвергаются
как и везде):

| Поле | Смысл |
| --- | --- |
| `ca_file` | PEM-файл с одним или несколькими сертификатами CA, которым доверяет **этот** профиль (Д3) |
| `client_keystore_file` | файл PKCS12 с клиентским ключом и цепочкой сертификатов, которые профиль предъявляет серверу (Д2) |
| `client_keystore_password_env` | имя переменной окружения с паролем PKCS12; **обязательно** при `client_keystore_file` и допустимо только вместе с ним; значение пароля в профиле не хранится |

Правила разбора (ошибка даёт существующий `SOURCE_CONFIG_INVALID`, отказ при
чтении connections file, как для остальных ошибок формы):

1. `tls` допустим только при `base_url` со схемой `https`; `tls` при `http`
   отвергается.
2. Пути только абсолютные: `readSourceConnections` принимает `InputStream` и не
   знает каталог файла, а относительный путь от рабочего каталога процесса
   неоднозначен. «Абсолютный» означает `Path.isAbsolute` на ОС backend. На Windows
   JSON-запись такая: `C:/ltv/tls/ca.pem` или `C:\\ltv\\tls\\ca.pem` (обратные косые
   в JSON удваиваются); пути без диска (`\x`) и с диском без корня (`C:x`)
   отвергаются, UNC-пути принимаются как абсолютные. Без `~`, без подстановки
   переменных, без сегментов `.` и `..`, без схем (`file:` и подобных), не длиннее
   1024 байт, без управляющих символов.
3. Имя переменной проверяется тем же `sourceEnvironmentName`, что у `auth`.
4. Профили `postgresql` не получают `tls`: у них свой механизм `sslmode`
   (ADR [0008](0008-postgresql-pre-post-capture.md)), поле остаётся неизвестным
   и отвергается.
5. `tls` и `auth` независимы: профиль может одновременно предъявлять клиентский
   сертификат и отправлять `Authorization` (например, Grafana за mTLS-прокси с
   токеном сервисной учётной записи).

**Версия документа.** `tls` принимается **аддитивно** во всех существующих
версиях HTTP-профиля (`v1`, `v2`, `v3`); новая версия `source-connections.v4` не
вводится. Основания:

- Ни один ранее допустимый документ не может содержать `tls`: сейчас такое поле
  отвергается `rejectUnknown`, значит смысл любого действующего документа не
  меняется, а профили без `tls` разбираются и исполняются байт-в-байт как раньше.
- Старые сборки отвергают документ с `tls` (`SOURCE_CONFIG_INVALID`): отказ
  закрытый, молчаливой потери клиентского сертификата не бывает.
- `source_summary` и `source-acquisition.json` у профилей без `tls` не меняются;
  у профилей с `tls` в них тоже не появляется новых полей (Д7), поэтому identity
  анализа не затронута.
- Версии `v2` и `v3` вводились потому, что новые поля меняли **вычисление**
  (профили `postgresql`; автошаг, события, длительные правила). `tls` меняет
  только установку соединения.

Отклонённая альтернатива: `source-connections.v4` (всё из `v3` плюс `tls`) по
прецеденту ADR [0014](0014-resource-series-limits-autostep-arm-api.md)
(`source-request.v4`, «чтобы не менять смысл опубликованного `v3`»). Минусы:
флаг `allowAutoStep` связан с тремя полями про автошаг, поэтому `v4` затащил бы
в профиль с mTLS ещё и семантику `v3`; профиль `v1`, выпущенный генератором
платформенных профилей, пришлось бы переводить на `v3`-семантику только ради
сертификата; новая версия ничего не добавляет к закрытому отказу старых сборок.
Если владелец предпочитает явную версию, отличие минимально (вопрос 1).

### Д2. Формат ключевого материала: PKCS12 и PEM CA, без новых зависимостей

- **Клиентский ключ и сертификат:** PKCS12 (`client_keystore_file`),
  загружается как `KeyStore.getInstance("PKCS12")` (не автоопределение типа, чтобы
  не принять JKS и устаревшие форматы). Ровно одна запись с закрытым ключом и
  цепочкой сертификатов.
- **Доверие:** PEM-файл `ca_file`, разбирается `CertificateFactory("X.509")`
  (публичные сертификаты, не секрет), от 1 до 32 сертификатов.

Не поддерживаются: закрытый ключ в PEM (PKCS#1, SEC1, PKCS#8, зашифрованный),
JKS, `trust_all` и подобные. Причина: в JDK 21 нет публичного API для разбора
закрытого ключа из PEM; ручной разбор ASN.1 или BouncyCastle означает новую
production-зависимость и изменение `gradle.lockfile` без необходимости (правило 5
AGENTS.md). Конвертация одной командой, которую документация даст
пользователю (пароль берётся из окружения, а не из командной строки):

```text
openssl pkcs12 -export -inkey tls.key -in tls.crt -certfile ca.pem -out client.p12 -passout env:LTV_GRAFANA_MTLS_PASSWORD
```

Совместимость PKCS12, созданного OpenSSL 3, с JDK 21 нужно подтвердить на тесте
(см. «План реализации»). Что выдаёт боевой стенд (PEM или PKCS12) неизвестно:
вопрос 2.

**Пароль.** Только `client_keystore_password_env`, как у `auth` (имя переменной в
профиле, значение в окружении процесса backend), и он **обязателен** вместе с
`client_keystore_file`: PKCS12 без пароля не принимается (пароль защищает ключ,
если файл утёк, см. Д8; кроме того, открытие PKCS12 с пустым паролем у OpenSSL и
JDK ведёт себя по-разному). Пароль читается при сборке
контекста в `char[]`, после загрузки массив затирается; в профиле, `toString`,
журналах и артефактах его нет. Значения нет или оно пустое:
`SOURCE_TLS_CONFIG_INVALID` (молчаливого «пустого пароля» нет).

Сравнение способов передать пароль:

| Способ | За | Против |
| --- | --- | --- |
| Пароль в профиле | просто | секрет в файле, который копируют и коммитят: **отвергнуто** |
| `JAVA_OPTS` (`-Djavax.net.ssl.keyStorePassword=...`) | работает сегодня | виден в командной строке и списке процессов, глобален на процесс: **отвергнуто** (путь остаётся только как неподдерживаемый обход) |
| `*_password_env` | единообразно с `auth`; не в командной строке; код переиспользует `sourceEnvironmentName`; ИИ-раннер окружения не наследует (таблица раздела «Контекст», п. 2) | окружение читаемо тем же пользователем и администратором; наследуется дочерними процессами, которые запускаются без `clear()` |
| `*_password_file` | файл можно смонтировать как секрет, нет наследования потомками | второй механизм; права на файл (на Windows ACL) и правила чтения (размер, перевод строки) становятся контрактом |

Рекомендация: `*_password_env` сейчас; `*_password_file` добавляется отдельно и
аддитивно, если боевой стенд не позволит задать окружение (вопрос 3).

### Д3. Доверие серверу и проверка имени узла

1. `ca_file` задан: профиль доверяет **только** сертификатам из файла; доверие по
   умолчанию JVM (`cacerts`) для этого профиля **заменяется**, а не расширяется.
   Это сужает доверие до стенда и исключает публичные CA там, где сервер подписан
   внутренним. Если сервер подписан публичным CA, нужно положить его корень в
   `ca_file` (вопрос 4).
2. `ca_file` не задан: доверие по умолчанию JVM, как сегодня (в том числе
   глобальные `javax.net.ssl.trustStore*`: «по умолчанию JVM» означает правила
   JVM).
3. **Режима «доверять всем» нет** и не будет: ни поля `insecure_skip_verify`, ни
   `verify_hostname: false`, ни пустого `TrustManager`. Единственный способ
   выключить проверку цепочки у профиля с `tls` — не использовать `tls`
   (тогда действует прежнее поведение с проверкой по умолчанию).
4. Имя узла проверяется всегда: по `host` из `base_url` против SAN сертификата
   сервера (для IP-адреса в `base_url` нужен `iPAddress` SAN) стандартным
   механизмом `HttpClient` (`endpointIdentificationAlgorithm=HTTPS`). У JDK есть
   скрытое глобальное свойство `jdk.internal.httpclient.disableHostnameVerification`
   (проверено по исходникам JDK 21, `Utils.hostnameVerificationDisabledValue`:
   свойство, заданное без значения, считается `true`, иначе
   `Boolean.parseBoolean`). Поэтому при пустом значении или `true` (без учёта
   регистра) сборка контекста профиля с `tls` отказывает кодом
   `SOURCE_TLS_CONFIG_INVALID`: «нельзя тихо снять проверку имени».
5. Протоколы: только `TLSv1.3` и `TLSv1.2` (явно, независимо от правки
   `java.security`). Отзыв сертификатов (CRL, OCSP) не проверяется (поведение
   JSSE по умолчанию; ограничение, см. «Риски»).

### Д4. Изоляция: свой `HttpClient` на профиль с `tls`

- Для каждого профиля с `tls` создаётся **собственный** `HttpClient` со своим
  `SSLContext`: пул соединений клиента предъявляет одну идентичность, поэтому
  общий клиент разные сертификаты не обеспечит.
- Профили без `tls` продолжают пользоваться прежним общим клиентом: поведение
  (в том числе влияние глобальных `javax.net.ssl.*`, на которое могли положиться)
  не меняется. Этот обход не удаляется, но документацией не рекомендуется
  (только «один источник на процесс и только временно»).
- Профиль с `tls` **не** использует глобальные `javax.net.ssl.keyStore*` JVM: при
  отсутствии `client_keystore_file` профиль не предъявляет никакого клиентского
  сертификата (менеджер ключей строится на пустом хранилище, а не передаётся
  `null`, иначе JSSE подставил бы ключ по умолчанию из свойств JVM). Глобальное
  `trustStore` у профиля с `tls` игнорируется, когда задан `ca_file`.
- Governor остаётся **на origin**, а не на профиль: два профиля на один и тот же
  origin с разными сертификатами делят бюджет запросов (ёмкость источника не
  зависит от того, чей сертификат). `followRedirects(NEVER)`, лимит тела ответа и
  отмена остаются как есть: клиент профиля строится тем же способом, меняется
  только `sslContext` и список протоколов.
- Потоки: не более 16 профилей, клиент строится лениво, дополнительные потоки
  `HttpClient` на каждый профиль с `tls` приемлемы.

### Д5. Жизненный цикл: ленивая сборка, ротация перезапуском, срок действия

1. **Ленивая сборка.** `SSLContext` и `HttpClient` профиля с `tls` строятся при
   первом запросе профиля, а не в `SourceHttp.init`. Причина: исключение из
   `init` не перехватывается в `CommandLine.kt:198` и `:496` и обрушило бы запуск
   всего backend для **всех** профилей из-за одного пропавшего файла, а код
   ошибки не попал бы в `source_summary` (то есть в то место, где его видит
   пользователь). Ленивый отказ даёт `FAILED`-запрос с причиной у одного
   профиля; остальные источники и анализ нагрузки работают.
2. Неудачная сборка **не кэшируется** (исправленный файл подхватывается
   следующим запросом без перезапуска); успешная кэшируется на жизнь процесса.
3. **Ротация** сертификатов и CA: перезапуск backend, как и для самих профилей
   («Профили загружаются при запуске», `online-sources.md`). Перечитывание по
   отпечатку файла отложено (вопрос 7).
4. **Срок действия.** При сборке и **при каждом запросе** у кэшированной цепочки
   проверяется `notBefore`/`notAfter` каждого сертификата (`checkValidity`, без
   сети): просроченный или ещё не наступивший даёт `SOURCE_TLS_CLIENT_CERT_EXPIRED`
   **до** отправки запроса. Допуска на расхождение часов нет; неверные часы
   хоста дают ложный отказ, это записано в ограничениях. Срок CA-якорей из
   `ca_file` локально не проверяется.
5. Предупреждение «скоро истекает» в продукт сейчас не добавляется (вопрос 9):
   канала предупреждений у источников нет, а поле в `source-acquisition.json`
   зависело бы от даты. Документация даёт команды проверки срока
   (`openssl pkcs12 ... | openssl x509 -enddate`, `keytool -list -v`).

### Д6. Коды ошибок

Новые причины (поле `reason` запроса источника и код при рендере панели);
никакой текст исключения, путь, DN, имя пользователя или пароль в вывод не
попадают, `SourceHttpFailure` по-прежнему несёт только код и **не** хранит cause.

| Код | Когда | Повтор |
| --- | --- | --- |
| `SOURCE_CONFIG_INVALID` (существующий) | форма JSON: неизвестное поле, пустой `tls`, `tls` при `http`, относительный путь, `client_keystore_file` без `client_keystore_password_env` и наоборот, плохое имя переменной | при чтении файла, отказ запуска |
| `SOURCE_TLS_CONFIG_INVALID` (новый) | материал: файл отсутствует, не читается, больше предела (Д9), не PKCS12, неверный пароль, переменная не задана или пуста, нет записи с ключом или их больше одной, `ca_file` без сертификатов, отключена проверка имени глобальным свойством (Д3 п. 4) | нет |
| `SOURCE_TLS_CLIENT_CERT_EXPIRED` (новый) | сертификат клиента или цепочки вне срока (Д5 п. 4) | нет |
| `SOURCE_TLS_HANDSHAKE_FAILED` (новый) | `javax.net.ssl.SSLException` в цепочке причин ошибки запроса: сервер не доверен, имя не совпало, сервер отверг наш сертификат (alert), несовместимый протокол | нет |

Правила:

- Обнаружение: «в цепочке `cause` есть `SSLException`» (`unwrap` снимает только
  `ExecutionException` и `CompletionException`, этого мало). По тексту
  сообщения причина **не** определяется.
- Не обещано: при TLS 1.3 сервер может отвергнуть отсутствующий или неверный
  клиентский сертификат уже после завершения рукопожатия на стороне клиента, и
  ошибка тогда придёт обычным `IOException` (закрытое соединение). Такой случай
  остаётся `SOURCE_HTTP_ERROR` (с повторами, как сегодня) до проверки на
  эксперименте: это входит в тест (раздел «План реализации») и в проверку на
  стенде другой сессией. Эвристики по тексту не вводятся.
- Коды без повтора: неверный сертификат или доверие не лечатся повтором, а
  повторы тратят бюджет запросов и время. Цена: кратковременный сбой при
  рукопожатии (перезапуск сервера) тоже не повторяется; пользователь запускает
  анализ заново.
- Уточняющие причины внутри `SOURCE_TLS_HANDSHAKE_FAILED` (untrusted, hostname,
  rejected) не вводятся: надёжно их различает только текст сообщений JDK и
  alert сервера, а он зависит от серверного ПО стенда. Решение откладывается до
  опыта на стенде и принимается аддитивно (вопрос 8).
- Путь от кода до пользователя уже есть: `reason` в `source_summary`,
  `analysis_coverage.status = INCOMPLETE`, переход интерфейса по любому коду
  `SOURCE_*` на вкладку источника (`ui/src/shell/overview.ts:84`); русские тексты
  новых кодов в интерфейсе вне объёма (интерфейс не входит).

### Д7. Секреты и поверхность данных

Принцип: **профиль `tls` никогда не покидает процесс.**

- `source_summary`, `source-acquisition.json`, result, evidence для ИИ, отчёты и
  экспорт: никаких новых полей. Профиль без `tls` и профиль с `tls` дают
  одинаковые по составу полей артефакты; identity анализа (она включает хэш
  acquisition) от `tls` не зависит. Единственная новая информация в артефактах:
  строка кода в `reason`.
- `GET /api/sources` и `GET /api/grafana` не получают `tls` и пути: остаются
  идентификатор, вид, транспорт и `base_url`.
- Санитайзер ИИ: изменений не требует. Профиль в evidence не входит; код
  `SOURCE_TLS_*` не содержит слов-триггеров (`password`, `secret`, `token`,
  `authorization`, `session`, `cookie`) и проходит без изменений. Тест на
  реализации это подтверждает.
- Журналы и сообщения: JSSE и файловые исключения содержат пути и DN, поэтому
  наружу уходит только код (Д6). `data class SourceProfile` распечатывает поля;
  в нём нет значений секретов (пароль читается лишь при сборке контекста), но
  пути к файлам видны; тест на реализации проверяет, что `toString` профиля и
  текст `SourceHttpFailure` не содержат значение пароля (в профиле лежит только имя
  переменной).
- Окружение дочерних процессов: ИИ-раннер получает очищенное окружение (таблица
  раздела «Контекст», п. 2), `LTV_*` в него не попадает; тест на реализации закрепляет это для имени
  вроде `LTV_GRAFANA_MTLS_PASSWORD`.
- Закрытый ключ не покидает PKCS12: он не пишется в артефакты и временные файлы.

### Д8. Права доступа к файлам

Продукт права **не проверяет**: на Windows это ACL, в Kubernetes секреты
монтируются с `fsGroup` и группой, а connections file сам по себе доверенный
ввод оператора (он уже может направить backend на любой адрес). Требование
вынесено в документацию: PKCS12 и каталог читает только пользователь backend
(`chmod 600` / ACL), пароль PKCS12 обязателен и защищает ключ, если файл всё же утёк.
Отказ при чтении другими пользователями отклонён как непереносимый (вопрос 5).
Пути не разыменовываются иначе, чем обычным открытием файла; символические ссылки
допустимы (так монтируются секреты Kubernetes).

### Д9. Пределы

| Что | Предел |
| --- | --- |
| Профилей с `tls` | входят в существующий предел 16 профилей |
| `ca_file` | не более 1 MiB и 32 сертификатов |
| `client_keystore_file` | не более 1 MiB, одна ключевая запись, цепочка не длиннее 8 |
| Значение переменной пароля | не более 1 KiB, без управляющих символов |
| Путь | абсолютный, не длиннее 1024 байт |
| Чтение файлов | ограниченное (читается не больше предела + 1 байт), один раз при сборке контекста |

Превышение: `SOURCE_TLS_CONFIG_INVALID`.

### Д10. `grafana_proxy`, Prometheus напрямую и ссылка на панель

- `grafana_proxy` и рендер панели используют тот же `execute()` и потому тот же
  клиент профиля: отдельной работы для рендера не нужно, а коды Д6 видны и в
  `grafana-render`.
- `transport: direct` (Prometheus, VictoriaMetrics, InfluxDB, OpenSearch за
  mTLS) использует тот же объект `tls`.
- Ссылка на панель Grafana (`grafanaPanelLink`) открывается в **браузере
  пользователя**, а не backend: клиентский сертификат нужно установить в
  браузер. Продукт этого не обеспечивает, документация предупреждает.
- На боевом стенде mTLS, как правило, завершает обратный прокси или ingress
  перед Grafana; куда указывает `base_url` и какой сертификат ждёт прокси,
  уточняет отдельная сессия подгонки (вне этого ADR).

### Д11. Локальная проверка

1. **Автотест в JVM (обязателен).** Сертификаты создаются на лету: CA, серверный
   сертификат с SAN `IP:127.0.0.1` и `DNS:localhost`, клиентский сертификат
   (подписан тем же CA), клиент с неверным CA, клиент с истёкшим сроком —
   запуском `keytool` из `java.home` дочерним процессом, в каталоге `@TempDir`,
   один раз на класс тестов. Приватные ключи в репозиторий не попадают, пароли
   для PKCS12 случайные (не литералы: сканер секретов в CI). Сервер:
   `com.sun.net.httpserver.HttpsServer` с `setNeedClientAuth(true)` (тот же
   пакет `jdk.httpserver`, что и `HttpServer` в `SourceHttpTest`). Новых
   зависимостей и правок `gradle.lockfile` нет.
2. **Стенд (необязателен).** Отдельный файл `tools/demo-stand/docker-compose.mtls.yml`
   со **своим** именем проекта (`ltv-mtls-stand`) и портом
   `127.0.0.1:13443`; в `docker-compose.yml` демо-стенда профиль **не** добавляется:
   в нём зашито `name: ltv-demo-stand`, и запуск из другого worktree пересоздал бы
   контейнеры работающего стенда (предупреждение в README). Состав: одноразовый
   контейнер с закреплённым тегом образа `openssl`, который пишет CA, серверный
   сертификат, клиентский PEM и `client.p12` в `tools/demo-stand/out/mtls/`
   (каталог `out/` уже в `.gitignore`); обратный прокси `nginx` (закреплённый
   тег) с `ssl_verify_client on` перед `grafana:3000` работающего демо-стенда
   (подключается к его внешней сети, контейнеры демо не пересоздаются и не
   останавливаются). Скрипт генерации и конфиг прокси коммитятся, ключи и
   сертификаты нет. Сценарий проверки: профиль с `tls` даёт `COMPLETE`, без
   `tls` и с чужим CA получается `SOURCE_TLS_HANDSHAKE_FAILED` (или
   `SOURCE_HTTP_ERROR`, если TLS 1.3 покажет отказ после рукопожатия, см. Д6).

## Вопросы владельцу

Каждый вопрос имеет рабочую рекомендацию; ни один не блокирует слияние этого
ADR, но 1-4 нужно закрыть до реализации (ответы на 2 и 4 может дать сессия
подгонки на стенде).

1. **Версия документа.** Рекомендация: аддитивно в `v1`-`v3` (Д1). Альтернатива:
   `source-connections.v4`.
2. **Формат клиентского ключа.** Что выдаёт боевой стенд: PEM или PKCS12?
   Рекомендация: только PKCS12 сейчас, конвертация `openssl pkcs12 -export`
   описана в документации. Альтернативы: PEM PKCS#8 разбором вручную
   (не покрывает PKCS#1 и SEC1, которые выдают многие инструменты), либо
   BouncyCastle (новая production-зависимость, нужна отдельная запись).
3. **Пароль.** Рекомендация: `*_password_env` (Д2). `*_password_file` добавить,
   только если на стенде нельзя задать окружение процесса.
4. **Доверие.** Чем подписан сертификат сервера (внутренний CA или публичный)?
   Рекомендация: `ca_file` заменяет доверие профиля; для публичного CA его корень
   кладётся в `ca_file`. Альтернатива: флаг, добавляющий `cacerts` к `ca_file`.
5. **Права на файлы.** Рекомендация: документация без проверки (Д8).
   Альтернатива: отказ при чтении файла посторонними на POSIX.
6. **Локальный отказ по сроку и отдельный код.** Рекомендация: да,
   `SOURCE_TLS_CLIENT_CERT_EXPIRED` (Д5, Д6). Альтернатива: свернуть в
   `SOURCE_TLS_CONFIG_INVALID` (два кода вместо трёх) или не проверять локально.
7. **Ротация.** Рекомендация: перезапуск backend. Альтернатива: перечитывание по
   отпечатку (размер и время изменения файлов) при каждом запросе.
8. **Уточнение причин рукопожатия.** Рекомендация: не сейчас; решить после
   проверки на стенде, аддитивно.
9. **Предупреждение о скором истечении.** Рекомендация: не сейчас (Д5 п. 5);
   команды проверки срока в документации.
10. **Стенд.** Рекомендация: отдельный `docker-compose.mtls.yml` (Д11). Альтернатива:
    только автотест в JVM (стенд отдельной сессии).
11. **Генератор платформенных профилей** (`tools/platform_profiles`) не выпускает
    `tls`: рекомендация оставить как есть (профиль с mTLS правится вручную);
    расширение генератора отдельным срезом, если понадобится.

### План реализации (срезы, отдельный PR `feat/sources-mtls`, после принятия ADR)

Каждый срез идёт по TDD (красный тест до кода), коммиты атомарные.

1. **Разбор профиля.** Тесты: `tls` во всех трёх версиях, пустой `tls`, `tls` при
   `http`, относительный путь, `..`, неизвестное вложенное поле, пароль без
   keystore и keystore без пароля, `tls` у `postgresql`; профиль без `tls` равен прежнему (golden). Код:
   `SourceConfig.kt`.
2. **Материал и клиент на профиль.** Тесты на вспомогательном генераторе
   сертификатов: загрузка PKCS12 (в том числе созданного OpenSSL 3 — проверка
   совместимости на машине, где есть `openssl`, иначе помечено как не
   проверенное), неверный пароль, пустая переменная, несколько ключевых записей,
   пределы, затирание пароля. Код: `SourceTlsMaterial.kt`, `SourceHttp.kt`
   (клиент на профиль, ленивая сборка, кэш, проверка срока на каждый запрос,
   отказ при глобальном `disableHostnameVerification` (пустое значение или `true`)).
3. **Интеграция с `HttpsServer` и `needClientAuth`.** Сценарии: успех;
   клиент без сертификата; клиентский сертификат чужого CA; серверный
   сертификат без нужного SAN; профиль без `ca_file` при внутреннем CA сервера;
   истёкший клиентский сертификат (локальный отказ без запроса к серверу);
   **изоляция:** два профиля с разными клиентскими сертификатами к двум серверам,
   каждый сервер видит свой сертификат; профиль с `tls` и без ключа не
   предъявляет сертификат; профиль без `tls` не затронут; рендер панели через
   тот же клиент; наблюдаемый код для случая «сервер отверг сертификат после
   рукопожатия» фиксируется как есть (Д6). Тесты безопасности: пароль, пути и
   имя переменной не попадают в `source-acquisition.json`, evidence, ответы API и
   текст ошибок; окружение ИИ-раннера не содержит `LTV_*`; санитайзер оставляет
   коды `SOURCE_TLS_*`.
4. **Документация.** Раздел «mTLS» в `docs/user/online-sources.md`: подготовка
   PKCS12 и CA, пример профиля без секретов (в том числе `grafana_proxy` и
   `direct`), права на файлы, ротация, срок, таблица кодов и типовых причин
   (проверка `openssl s_client`), ограничение `JAVA_OPTS`, предупреждение о
   браузере и ссылке на панель; пример `mtls-connections.example.json`;
   исправление фразы «TLS verification всегда включена»; запись в `CHANGELOG.md`
   (или фрагмент `changelog.d/`, если он к тому времени влит).
5. **Стенд** (если принят вопрос 10): `docker-compose.mtls.yml`, скрипт
   генерации, конфиг прокси, абзац в README стенда. Если объём окажется
   существенным, отдельным PR (правило 10 AGENTS.md).

markdownlint, Python как в CI, поиск секретов (ни закрытых ключей, ни паролей в

контракт, целостность данных, один раунд.

### Риски и остаточные ограничения

- Отзыв сертификатов (CRL, OCSP) не проверяется.
- Проверка срока по часам хоста: неверные часы дают ложный
  `SOURCE_TLS_CLIENT_CERT_EXPIRED` или пропускают просроченный; серверная
  проверка срока остаётся.
- Ротация только перезапуском; сертификат, истёкший за время работы процесса,
  ловится проверкой срока на каждый запрос (код `SOURCE_TLS_CLIENT_CERT_EXPIRED`).
- Отказ сервера в клиентском сертификате при TLS 1.3 может прийти как
  `SOURCE_HTTP_ERROR` (Д6): не проверено, проверяется тестом и на стенде.
- PKCS12 от OpenSSL 3 с шифрованием по умолчанию читается JDK 21 по ожиданию, не
  по проверке: подтверждается тестом реализации.
- Боевой mTLS-узел не проверялся ни отчётом демо, ни этим ADR: конкретика
  прокси, формат выдаваемых файлов и CA остаются входом для сессии подгонки.
- Без `ca_file` в профиле с `tls` доверие определяют правила JVM, включая
  глобальные свойства `trustStore`; для изоляции доверия `ca_file` лучше задавать.
- Кэшированный `HttpClient` профиля живёт до конца процесса; число профилей
  ограничено 16.

### Не входит

Пользовательский интерфейс и русские тексты кодов; боевой узел и подгонка (другая
сессия); смена `auth`; PostgreSQL (`sslmode`, ADR 0008); PEM-ключи, JKS,
BouncyCastle; проверка отзыва; предупреждение о скором истечении; перечитывание
сертификатов без перезапуска; `tls` в генераторе платформенных профилей;
HTTP-прокси исходящих соединений.
