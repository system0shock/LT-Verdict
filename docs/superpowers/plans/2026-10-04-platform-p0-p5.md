# Платформа, фаза 5 (P0-P5): пакеты метрик, плечи, поды, правила и экраны платформы Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Дата:** 2026-10-04. **Статус:** черновик на согласование (волна F2, спецификации вперёд), код не менялся.

**Goal:** довести платформенный контур до уровня МВП без реального стенда: пакеты метрик OpenShift и JVM со свёрткой по подам на стороне запроса (P0), метка плеча и признаки сервиса (P1), артефакт данных по подам `pod-view.v1` (P2), правила платформы в политике (P3, связка с ADR 0018 S6-S9), экраны платформы (P4) и аналитический слой с честными пометками (P5).

**Architecture:** ядро остаётся одним и не знает про OpenShift: платформенный сигнал приходит рядом `resource-snapshot.v1` на сервис (по одному снимку и одному анализу на плечо), правила платформы живут в `policy.v1` (ADR 0018), а подробности по подам идут отдельным диагностическим артефактом `pod-view.v1` (ADR 0020), который вердикт не определяет. Свёртка pod → service выполняется запросом (профиль источника), поэтому профили генерируются из единого каталога шаблонов PromQL и проверяются на синтетике без стенда (promtool, канонические ответы, синтетические артефакты).

**Tech Stack:** Kotlin (JUnit 5, `gradlew.bat`), Python 3.14 (`unittest`, только стандартная библиотека, каталог `tools/`), Vue 3 + TypeScript (Playwright), JSON Schema. Production-зависимостей нет. `promtool` из дистрибутива Prometheus нужен только как опциональный инструмент проверки выражений (вопрос владельцу 5).

**Spec:** `docs/adr/0014-resource-series-limits-autostep-arm-api.md` (части 3-6, решения 2026-09-30 и 2026-10-04), `docs/adr/0018-policy-platform-rules-small-samples.md` (разделы 2-3, решения 2026-10-02 и 2026-10-04), `docs/adr/0019-release-history-and-baseline-eligibility.md` (раздел 7), `docs/adr/0020-pod-view-artifact.md`, планы `docs/superpowers/plans/2026-10-02-adr-0018-implementation.md` (срезы B-S1..B-S10) и `docs/superpowers/plans/2026-10-02-autostep-adr-0014.md` (срезы A-S0..A-S5). Материалы вне git (не ссылки): `docs/ui-mockup/implementation-plan.md` (фаза 5, срезы P0-P5), `docs/ui-mockup/feature-gap.md`, `docs/ui-mockup/correlation-catalog.md`, макет `docs/ui-mockup/lt-verdict-ui-mockup.html` и снимки `docs/ui-mockup/screens/` (экраны 01, 03, 06).

База проверки кода: `origin/main` `135ef5a`. Ссылки `файл:строка` сверены с ней; перед стартом каждого среза сверить заново (`git diff --stat origin/main`).

**Нумерация срезов.** `P0a..P5b` - срезы этого плана. `B-S1..B-S10` - срезы плана ADR 0018, `A-S0..A-S5` - срезы плана автошага. `D0` (API рядов, ADR 0014 часть 6), `D2` (глубокий анализ), `D5a/D5b` (история релизов), `C1..C6` (корреляции, фаза 6), `U3..U7` - срезы соседних планов волны F2 (в момент написания их файлы ещё не слиты; их интерфейсы взяты из принятых ADR, а не из черновиков).

## Global Constraints

Каждая задача неявно включает этот раздел; числа скопированы из ADR и кода `135ef5a`.

- Один снимок на плечо, вердикты плеч независимы, общего заголовка нет (ADR 0014 часть 5; ADR 0018 Q10). Число плеч не фиксировано (1, 2, 3 и более); `arm` - только идентификатор.
- Пределы одного снимка: `S_max` 1 024 ряда, `C_max` 1 500 000 ячеек, `B_max` 32 MiB (`ResourceSnapshot.kt:651-654`); шаг целые секунды 1-60; окон 64; правил 256 (`ResourceSnapshot.kt:655-656`).
- Онлайн: до 64 запросов на профиль (`SourceConfig.kt:844`), до 16 профилей (`SourceConfig.kt:843`), один запрос возвращает ровно один ряд (`PromqlSource.kt:247`, `AMBIGUOUS_SERIES`), ожидаемые метки проверяются как подмножество (`PromqlSource.kt:257`, `LABEL_MISMATCH`); файл connections не больше 1 MiB (`SourceConfig.kt:840`); выражение обязано содержать `$__interval` (`SourceConfig.kt:505`).
- `arm`: не более 128 байт, либо у каждого ряда снимка одно и то же непустое значение, либо ни у одного (ADR 0014 часть 5, ошибка `INVALID_ARM_LABEL`, условное поле identity `resource_arm`).
- `pod-view.v1` (ADR 0020, пределы предварительные до замера P2e): сервисов 64, подов `P_max` 256, контейнеров на под 4, рядов `R_max` 2 560, колонок 240, ячеек 614 400, числовой токен 12 байт, файл 12 MiB; `service`, `container`, `metric`, `unit`, `rows[].id` до 128 байт UTF-8, `pod` до 253 байт; pod-view вердикт не определяет, в `modules`, `input_versions`, `limits` не входит.
- Платформенная политика (ADR 0018): сервисов в области и каталоге до 64, развёрнутых проверок до 256 на оценку; сигналы связываются по точным `metric`, `entity` (имя сервиса), `role = system`, `unit` и `aggregation`.
- Диагностические планы: не более 32 проверок аномалий и 16 пар корреляций на план (`DiagnosticPlan.kt:744-745`), эпизодов не более 1 000 (`DiagnosticPlan.kt:750`); план корреляций и ёмкости привязан к хэшу снимка; capacity требует шаг 1, 2, 5 или 10 секунд (ADR 0009).
- Правило идентичности: срез, меняющий исход для допустимого входа, меняет identity в том же PR. Мои identity-срезы (P1a, P1b, P2b) условные: у анализа без плеча и без pod-view байты identity и существующие golden-файлы (`fixtures/slice1/identity/*`) остаются прежними, это проверяется тестом. Идентичность не совмещается в одном PR с B-S1 и срезами ADR 0016 (ADR 0017:173-180).
- Каждый код причины, добавленный в Kotlin, получает запись в `ui/src/verdictReasons.ts` в том же PR (тест `e2e/verdict-summary.spec.ts`); блокирующие причины - `noVerdict: true`.
- Новых production-зависимостей нет; инструменты проверки (`promtool`) - не зависимость продукта и не входят в сборку.
- Проза и документация на русском, идентификаторы и коды на английском. Коммиты атомарные, Conventional Commits, в индекс только файлы задачи; push, merge, rebase только по явному разрешению владельца.
- Перед каждым срезом: `git status --short --branch`, отдельный воркстри и ветка (`git worktree add .worktrees/<имя> -b <ветка> origin/main`), базовый прогон `.\gradlew.bat test`, `npm --prefix ui run typecheck`, `python -m unittest discover -s tools -p "test_*.py"` с записью числа тестов.

## Review Focus

Входы и условия, которые спецификация подразумевает, но базовые тесты задач не покрывают; у каждого есть тест в указанном срезе.

1. Сервисный ряд выглядит непрерывным, хотя часть контейнеров пропала: максимум по доступным контейнерам скрывает потерю ряда использования, потерю limit или потерю самого источника списка контейнеров. Ожидается пропуск, а не «норма» (P0b: три сценария promtool про `memory: a container without a limit`, `a lost usage series`, `without the kube-state container record`; P3a: `NO_VERDICT`, а не `PASS`).
2. Событийный счётчик (OOM, рестарты) без единой серии: отсутствие счётчика не должно давать `NO_VERDICT` при живых подах и не должно фабриковать ноль, если источник самого счётчика мёртв (живость берётся из независимого от счётчика ряда того же источника; P0b: сценарии `oom: ...`, `restarts: ...`).
3. Два плеча с разными сетками, разными шагами или разными единицами: контраст не строится, причина показана, интерполяции нет (P1d: общий явный шаг; P4d: `GRID_MISMATCH`).
4. Смешанный или неоднозначный `arm`, повтор имени пода, pod-view чужого снимка или чужой нагрузки: отказ с кодом, ничего не записывается (P1a, P2a, P2b).
5. Pod-view с сокращённым охватом (`coverage.pods_included < pods_observed_total`) или пропусками `null`: интерфейс не говорит «все поды здоровы» и не рисует пропуск как ноль (P2a: честный `coverage`; P4c: состояния).
6. Эпизоды и корреляции читаются как причина: пометки «наблюдение, не диагноз», окно, лаг, число ячеек, контроль нагрузки, неоткалиброванность видны рядом с каждой находкой (P5a, P5b).

## Минимум для живого демо и полный объём МВП

Демо (по заданию): минимальный коннектор Grafana, базовый анализ по SLA, анализ теста максимума (capacity), глубокий анализ в урезанном виде.

**Что фаза 5 строго обязана дать демо: ничего.** Все четыре сценария демо уже опираются на существующий код: транспорт `grafana_proxy` есть (`SourceTransport.GRAFANA_PROXY`, `SourceConfig.kt:40-45`), SLA по ресурсам работает через правила профиля (`rules`) или снимка, capacity и ряды нагрузки есть. Демо не должно ждать `platform_rules` (B-S6..B-S9), `arm` и pod-view.

**Что фаза 5 может улучшить демо дёшево («демо-минимум платформы»):**

| Срез | Зачем демо | Ограничение |
| --- | --- | --- |
| P0a | пакет OpenShift узнаёт сигналы отношения к limit | S, независим |
| P0b | коннектор Grafana и профили не пишутся руками: `transport: grafana_proxy` и `datasource_uid` в конфигурации генератора; режим `legacy_sla_rules` выпускает базовый SLA по CPU и памяти правилами профиля (путь, который работает сегодня) | профиль с `legacy_sla_rules` несовместим с `platform_rules` (`PLATFORM_RULES_CONFLICT`, ADR 0018 раздел 2): в демо политика без `platform_rules` |
| P0e | локальный docker-стенд отдаёт серии в форме контракта меток, поэтому демо идёт теми же запросами, что и боевой профиль | зависит от того, как устроена демо-линия |

**«Демо+» (если останется время, не обязательно):** P2a-P2c и синтетический режим P2d дают тепловую карту подов из файла для «глубокого анализа в урезанном виде»; P4c-lite (одно плечо, карта без контрастов). Это не ставится на критический путь демо: глубокий анализ в урезанном виде обязан работать на рядах сервисов без pod-view.

**Анализ теста максимума в демо.** Capacity требует файл снимка и capacity-план, привязанный к хэшу этого снимка, шаг снимка 1, 2, 5 или 10 секунд (ADR 0009) и не сочетается с онлайн-сбором в одном job (`LocalApi.kt:1328-1335` отвергает `source_request` вместе с ручным снимком, планами диагностики, ёмкости и трендов и с контекстами источников; срез P2b добавляет туда `pod_view`). Поэтому в демо capacity идёт по файлу: снимок, выгруженный из предыдущего онлайн-прохода (хэш берётся из списка анализов, срез P4a) или подготовленный стендом, плюс план. Шаг онлайн-прохода для такого снимка 5-10 секунд, интервал опроса источника не крупнее шага; стандартный интервал опроса OpenShift 30 секунд для capacity не годится (вопрос 3). Платформенные ряды (шаг 60 секунд) собираются отдельным анализом.

### Рабочий процесс на стенде: два прохода

Онлайн-сбор и ручные входы взаимно исключают друг друга, поэтому платформенный анализ с pod-view, планом диагностики (эпизоды, корреляции) или планом ёмкости - всегда два прохода:

1. **Проход 1, онлайн:** профили P0 собирают снимок плеча; анализ сохраняется, ряды видны в интерфейсе.
2. **Выгрузка:** снимок скачивается (`GET .../resource-snapshot`), его семантический хэш берётся из identity анализа (`resource_snapshot_sha256`, список анализов расширяет срез P4a); повторная проверка скачанных байтов даёт то же значение.
3. **Проход 2, офлайн:** повторный анализ того же входа с файлом снимка плюс `pod_view` (адаптер P2d, живой режим) и/или планом диагностики (P5a, P5b); результат - новый анализ с другим `analysis_id`.

Следствие для плана: P4a - стартовый срез для P2d (живой режим), P5a и P5b, а не конечный интерфейсный; он перенесён в первые волны. Следствие для демо и экранов: платформенный глубокий анализ с pod-view идёт только по файлам (проход 2), а вердикты платформы и карта «сервис x плечо» берутся из прохода 1 (политика с `platform_rules` не является ручным источником и сочетается с онлайн-сбором). Анализы прохода 1 и прохода 2 одного плеча связываются по паре (`resource_arm`, `resource_snapshot_sha256`) из списка анализов (P4a): pod-view для карты подов берётся из анализа прохода 2 с тем же хэшем снимка.

**Полный объём МВП этой фазы:** P0a-P0d, P1a-P1d, P2a-P2e, P3a, P4a-P4d, P5a-P5b. P0e и P1c - желательны, но не блокируют.

## P0b: генератор профилей OpenShift и сценарии promtool

**Цель:** профили источника для платформы не пишутся руками: генератор по списку сервисов и сигналов выпускает `source-connections.v1` со свёрткой по подам на стороне запроса, пакует запросы в профили не больше 64 запросов и не больше 16 профилей, а каждое выражение проверено на синтетических сериях.

**Размер:** L (около 350 строк Python, около 300 строк тестов Python, около 120 строк Kotlin-теста, документ). **Зависит от:** P0a (имена). **Identity:** нет. **Что не входит:** сигналы JVM (P0c), пиковые варианты в боевом профиле (P0d), онлайн-вызов реального источника.

**Контракт сигналов (рабочая таблица шаблонов):**

| Ключ генератора | `series.metric` | unit | Агрегация (до A-S1) | Свёртка в сервис | Вариант с пиком |
| --- | --- | --- | --- | --- | --- |
| `cpu_limit_ratio` | `openshift_container_cpu_limit_ratio` | `ratio` | `interval_mean` | сначала среднее каждого контейнера за интервал, затем максимум по контейнерам и подам | нет (ЦП остаётся средним, ADR 0014) |
| `memory_limit_ratio` | `openshift_container_memory_limit_ratio` | `ratio` | `interval_mean` | то же, пик: `max_over_time` | да |
| `oom` | `openshift_oom` | `events/s` | `interval_rate` | сумма по контейнерам и подам | нет |
| `restarts` | `openshift_restarts` | `events/s` | `interval_rate` | сумма | нет |
| `cpu_throttling` | `openshift_cpu_throttling` | `ratio` | `interval_mean` | отношение для контейнера, максимум по контейнерам | нет |
| `unavailable_replicas` | `openshift_unavailable_replicas` | `count` | `interval_mean` | `spec - available` Deployment | да |
| `pod_imbalance` | `openshift_pod_imbalance` | `ratio` | `interval_mean` | (max - min) / avg по подам | нет |

Принятые проектные решения (отличия от ADR выделены):

- Выражение заканчивается агрегатом `by (namespace)`, поэтому ответ - ровно один ряд, а `labels: {namespace}` проверяется как подмножество.
- **Полнота контейнеров** (ADR 0018 раздел 3: «значение сервиса в ячейке только если известны значения всех ожидаемых контейнеров»): отношения к limit публикуются только при равенстве числа контейнеров с отношением и числа контейнеров, которые платформа ожидает у сервиса (`kube_pod_container_info`, регулярные контейнеры, включая сайдкары): `... and on (namespace) (count(expected) == count(ratio))`. Потеря ряда использования, потеря limit и потеря самого источника списка контейнеров (kube-state) дают пропуск, а не максимум остальных. Контейнер без объявленного limit тоже даёт пропуск (ADR 0018: `NO_VERDICT`). Init-контейнеры в список не входят.
- **Событийные сигналы** считаются как `(rate по контейнерам) or (0 * max(ряд живости))`: ноль появляется только пока независимый от счётчика ряд того же источника показывает живые поды сервиса. Для OOM (счётчик cAdvisor) живость - `container_memory_working_set_bytes` (cAdvisor), для рестартов (счётчик kube-state) - `kube_pod_info` (kube-state). Иначе счётчик, которого ещё не было, давал бы пропуск и `NO_VERDICT` на здоровом сервисе, а мёртвый источник давал бы выдуманный ноль; сценарии «kube-state жив, cAdvisor нет» и наоборот дают пропуск.
- **Метка не ложь:** `max_over_time` допускается только вместе с `aggregation = interval_max`; до A-S1 генератор выпускает среднее (`avg_over_time`) и честную метку `interval_mean` (публиковать максимум как `interval_mean` - ложная метка в хэшируемом контракте, ADR 0014 часть 2). Сигнал, который по определению максимум, в режиме без пика отказывается (`render` бросает `ValueError`).
- Подзапрос `[$__interval:SUB]`: разрешение подзапроса `SUB` (по умолчанию `15s`) должно быть не крупнее интервала опроса; иначе подзапрос возвращает одну точку.
- Сигналы на `rate(...[$__interval])` требуют шаг не меньше удвоенного интервала опроса источника; при меньшем шаге `rate` пуст и ряд превращается в пропуски (не в нули). Это документируется и проверяется в P0d.
- Запросов на стенд: 20 сервисов x 7 сигналов = 140 запросов на плечо, то есть 3 профиля по 64 запроса; файл connections около 144 KB, предел 1 MiB достигается примерно на 950 таких запросов (раньше, чем предел 1 024 рядов), поэтому генератор проверяет оба предела.

```python
EXPECTED = 'kube_pod_container_info{namespace="@ns@"} and on (namespace, pod) @owner@'


def guarded_ratio(usage: str, limit: str, over: str, expected: str = EXPECTED) -> str:
    """Interval aggregation per container first, then the worst container.

    The value is published only while the number of containers with a ratio equals the number of containers the
    platform expects (a lost usage series, a lost limit or a lost kube-state source all give a gap, never the max of the rest).
    """
    ratio = f"({usage} / on (namespace, pod, container) {limit})"
    return (
        f"max by (namespace) ({over}({ratio}[$__interval:@sub@])) "
        f"and on (namespace) (count by (namespace) ({expected}) == count by (namespace) ({ratio}))"
    )


def event_rate(counter: str, alive: str) -> str:
    """Counter rate per service; zero only while a source independent of the counter shows the service alive."""
    rate = f'sum by (namespace) (rate({counter}{{namespace="@ns@",@cont@}}[$__interval]) and on (namespace, pod) @owner@)'
    live = f"(0 * max by (namespace) ({alive} and on (namespace, pod) @owner@))"
    return f"({rate}) or {live}"
```

```python
"""Generate source-connections.v1 profiles for the OpenShift label contract (plan P0b).

One query returns exactly one series (PromqlSource), so every (service, signal) pair is one query and
queries are packed into profiles of at most 64 queries, at most 16 profiles (1 024 series).
"""

import argparse
import json
import re
import sys

from tools.platform_profile_templates import SIGNALS, render

MAX_QUERIES_PER_PROFILE = 64
MAX_PROFILES = 16
MAX_IDENTIFIER_BYTES = 128
MAX_SOURCE_CONFIG_BYTES = 1_048_576
SUBQUERY_STEP = re.compile(r"[1-9][0-9]*s")
SCHEMA_VERSION = "source-connections.v1"
DEFAULT_GOVERNOR = {"requests_per_second": 5, "burst": 5, "timeout_ms": 30000, "max_attempts": 3}


def build_connections(config: dict) -> dict:
    services = config["services"]
    signals = config["signals"]
    peak = bool(config.get("peak_aggregation", False))
    if not services or len(set(services)) != len(services):
        raise ValueError("services must be non-empty and unique")
    unknown = [name for name in signals if name not in SIGNALS]
    if unknown or len(set(signals)) != len(signals):
        raise ValueError(f"unknown or duplicate signals: {unknown}")
    sub = config.get("subquery_step", "15s")
    if not SUBQUERY_STEP.fullmatch(sub):
        raise ValueError("subquery_step must look like 15s")
    legacy = {rule["signal"]: rule for rule in config.get("legacy_sla_rules", [])}
    if set(legacy) - set(signals):
        raise ValueError("legacy_sla_rules reference a signal that is not generated")

    pairs = [(signal, service) for signal in signals for service in services]
    if len(pairs) > MAX_QUERIES_PER_PROFILE * MAX_PROFILES:
        raise ValueError("PLATFORM_PROFILE_TOO_MANY_QUERIES")
    prefix = "ocp" + (f"-{config['arm']}" if config.get("arm") else "")
    size = MAX_QUERIES_PER_PROFILE
    chunks = [pairs[i : i + size] for i in range(0, len(pairs), size)]
    connections = []
    for number, chunk in enumerate(chunks, start=1):
        queries = []
        rules = []
        for signal, service in chunk:
            spec = SIGNALS[signal]
            use_peak = peak and spec.peak
            query_id = f"{service}.{signal}"
            if len(query_id.encode()) > MAX_IDENTIFIER_BYTES:
                raise ValueError(f"query id too long: {query_id}")
            queries.append(
                {
                    "id": query_id,
                    "expression": render(spec, config["namespace"], service, sub, peak=use_peak),
                    "metric": spec.metric,
                    "unit": spec.unit,
                    "entity": service,
                    "role": "system",
                    "aggregation": "interval_max" if use_peak else spec.aggregation,
                    "labels": {"namespace": config["namespace"]},
                }
            )
            if signal in legacy:
                rule = legacy[signal]
                rules.append(
                    {
                        "id": f"{service}.{signal}.{rule['operator']}",
                        "series_id": query_id,
                        "unit": spec.unit,
                        "operator": rule["operator"],
                        "threshold": rule["threshold"],
                        "min_consecutive_cells": rule["min_consecutive_cells"],
                        "effect": rule["effect"],
                    }
                )
        connection = {
            "id": f"{prefix}-{number}",
            "source_kind": "prometheus",
            "transport": config.get("transport", "direct"),
            "base_url": config["base_url"],
            "auth": config.get("auth", {"type": "none"}),
            "governor": config.get("governor", DEFAULT_GOVERNOR),
            "queries": queries,
        }
        if config.get("datasource_uid"):
            connection["datasource_uid"] = config["datasource_uid"]
        if config.get("allow_insecure_http"):
            connection["allow_insecure_http"] = True
        if rules:
            connection["rules"] = rules
        connections.append(connection)
    document = {"schema_version": SCHEMA_VERSION, "connections": connections}
    if len(serialize(document).encode()) > MAX_SOURCE_CONFIG_BYTES:
        raise ValueError("PLATFORM_PROFILE_TOO_LARGE")
    return document


def serialize(document: dict) -> str:
    return json.dumps(document, indent=2, ensure_ascii=False) + "\n"


def main(argv: list[str]) -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("--config", required=True)
    parser.add_argument("--out", required=True)
    args = parser.parse_args(argv)
    with open(args.config, encoding="utf-8") as handle:
        config = json.load(handle)
    document = build_connections(config)
    with open(args.out, "w", encoding="utf-8", newline="\n") as handle:
        handle.write(serialize(document))
    return 0


if __name__ == "__main__":
    sys.exit(main(sys.argv[1:]))
```

## P4a: плечо и хэш снимка в списке анализов запуска

**Размер:** S. **Зависит от:** ничего (поле `resource_arm` читается из identity, если P1a его записал; без P1a оно просто отсутствует). **Identity:** нет. Срез - enabler двухпроходного процесса (раздел «Рабочий процесс на стенде: два прохода»): семантический хэш снимка уже лежит в identity анализа как `resource_snapshot_sha256` (`AnalysisResult.kt:45`) и повторяется при повторной проверке тех же байт, но ни один эндпойнт его не отдаёт (список анализов, `LocalApi.kt:896-905`, содержит только `analysis_id`, `policy_sha256`, `policy_verdict`, `run_validity`); именно поэтому адаптер pod-view (P2d), план диагностики (P5a, P5b) и capacity-план (демо) получают хэш отсюда, а не из ADR-E. ## P4b: карта «сервис x плечо»

## Проверка без реального стенда

Реальный стенд в МВП не входит; проверка идёт слоями. Каждый слой отвечает на свой вопрос, и ни один не заменяет реального прогона (раздел «Риски»).

| Слой | Что проверяет | Чем | Где живёт |
| --- | --- | --- | --- |
| L0 | форма и арифметика ядра и интерфейса | `.\gradlew.bat check`, `python -m unittest discover -s tools -p "test_*.py"`, `npm --prefix ui run typecheck`, `lint`, `test:contracts`, `e2e` | CI (`runtime-quality.yml`) |
| L1 | семантика выражений PromQL (свёртка, защита от потери контейнера, события, пик) на синтетических сериях | `promtool test rules` через `tools/test_platform_promql.py` (при написании плана выполнено в docker: 24 сценария `SUCCESS` (17 OpenShift, 3 сайдкара, 4 JVM); негативный контроль - искажённое ожидание падает) | локально или в необязательном CI-задании (вопрос 5) |
| L2 | форма ответов `query_range`, `AMBIGUOUS_SERIES`, привязка рядов к ключам политики | Kotlin-тесты с локальным `HttpServer` (`PlatformProfileExampleTest`, `PlatformProfileBindingTest`) | CI |
| L3 | сквозное поведение платформы на искусственных, но согласованных артефактах | синтетический генератор P2d: снимки двух-трёх плеч, `pod-view.json`, `expected.json` по закрытой формуле; загрузка в `ltv analyze` и UI | локально, выдержки в e2e |
| L4 | транспорт и пользовательский путь: Grafana proxy, Prometheus, UI | локальный docker-стенд демо-линии со слоем совместимости P0e; интервал опроса 5-10 с | локально, не в CI |

**Оракулы.** (1) Закрытая формула синтетики (`expected.json`) независима от LT Verdict: генератор считает вердикты плеч, худшие поды, статистики окна и контрасты арифметикой по спецификации сценария. (2) Сценарии promtool - второй независимый оракул для выражений: ожидание записано числом, а не получено из того же выражения. (3) Для статистик окна клиента - сравнение с `expected.json` и с серверным `resource_summary` по сервисному ряду (для pod-view серверной статистики в v1 нет, ADR 0020).

**Сценарий приёмки SYN-1** (дымовой, без стенда): 2 плеча x 4 сервиса x 3-6 подов, один сервис с утечкой памяти только на плече B (под `b2`), один с троттлингом на одном поде; профиль P0 с `legacy_sla_rules` или политика B-S9 (после B-S9); ожидается: плечо A `PASS`, плечо B `FAIL` по памяти `payments-svc`; карта «сервис x плечо» показывает ровно эту ячейку; тепловая карта - под `b2` худший; контраст «плечо B - плечо A» положителен на колонках после начала утечки и равен нулю до неё; удаление под из pod-view при сохранённом сервисном ряде не меняет вердикт (pod-view вердикт не определяет).

**Гейт готовности фазы 5 к стендовой приёмке (без реального стенда).** (1) L0 зелёный на `main` после каждого среза. (2) L1 `SUCCESS` на всех сценариях. (3) SYN-1 проходит в e2e для P4b-P4d. (4) Замер P2e выполнен, пределы ADR 0020 подтверждены или пересмотрены владельцем. (5) Документы и `CHANGELOG.md` обновлены. (6) Идентичность: существующие golden-файлы побайтно прежние. Что в гейт НЕ входит (исходный гейт `docs/ui-mockup/implementation-plan.md` фазы 5 требовал стенд с двумя плечами, тест 4-8 часов и повторную приёмку Codex по метрикам платформы): всё это остаётся исходным exit gate фазы 5, он остаётся открытым и не заменяется этим гейтом: синтетические проверки не подтверждают метки экспортёров и поведение на OpenShift. Отдельная веха после МВП.

Прочие риски:

- Первые прогоны на реальном стенде почти наверняка потребуют правки выражений: промтул-сценарии доказывают семантику выражения на синтетике, а не соответствие меткам стенда.
- Выражение сервисного ряда не доказывает полноту подов (ядро видит только свёрнутый ряд): гарантию даёт совместно защита контейнеров, сигнал покрытия и ревью профиля (ADR 0018, граница гарантии).
- `E_max` = 20 480 предварителен (ADR 0014): при 20 сервисах, 7 сигналах и 7 окнах платформа даёт около 1 000 проверок и сводок на плечо, запас большой; 64 окна и 290 рядов (около 27 тысяч) предел превышают.
- Файл connections ограничен 1 MiB: около 950 запросов с тяжёлыми выражениями; предел рядов 1 024 достижим только при более коротких выражениях.
- Общая сетка двух плеч: расходящиеся шаги ломают контраст; смягчается явным общим шагом (P1d) и проверкой в P4d.
- XL-риск P2a и P2b: при превышении оценки остановиться и сообщить (AGENTS.md, п. 10).
- Интервал опроса для capacity (5-10 с) и платформенных сигналов (30 с) несовместим в одном снимке: два разных анализа.

## Вопросы владельцу

Рекомендация указана по каждому вопросу. Блокирующих вопросов нет: без ответа каждый срез идёт по рекомендации; ответы на вопросы 12 и 15 влияют только на срезы P2e и P4b.

1. **Источник pod-view в МВП.** Рекомендация: файл адаптера (`tools/pod_view_adapter.py`, P2d) как принято 2026-10-02; онлайн-производитель (ADR 0020, раздел 4) - после первого стенда, отдельным ADR.
2. **Форма локального стенда.** Варианты: (а) docker-compose с cAdvisor и слоем совместимости (P0e); (б) kind или k3d с kube-state-metrics; (в) поддельный экспортёр с OpenShift-подобными именами. Рекомендация: (а) для демо и ежедневной проверки, плюс синтетика P2d для UI; (б) только как репетиция перед стендом, не в МВП.
3. **Интервал опроса и шаг.** Capacity требует шаг 1, 2, 5 или 10 с, rate-сигналы - шаг не меньше удвоенного интервала опроса, стандартный интервал опроса OpenShift 30 с. Рекомендация: на локальном стенде опрос 5-10 с (иначе capacity невозможен), для реального стенда считать шаг 60 с (8 часов = 480 точек); иллюстрации ADR 0014 про 15 с не принимать за требование.
4. **Генератор профилей в `tools/` или шаблоны запросов в контракте connections.** Рекомендация: генератор (P0b): новая версия контракта connections ради шаблонов - публичное изменение без доказанной потребности (AGENTS.md, минимальные изменения); пересмотр, если ручное сопровождение профилей окажется тяжёлым.
5. **`promtool` как инструмент проверки.** Рекомендация: опциональный локальный запуск сейчас (docker-образ `prom/prometheus`), необязательное CI-задание позже; в сборку и зависимости продукта не входит.
6. **Свёртка JVM-сигналов в сервис.** Рекомендация: худший под (максимум по подам после интервальной агрегации), среднее и разброс - через pod-view; отдельные имена `_avg` не вводить до появления потребности.
7. **Имя сервиса.** Рекомендация: метка `workload` из `namespace_workload_pod:kube_pod_owner:relabel` (допущение 1); если на стенде иначе - параметр шаблона `service_selector` в P0b, а не правка шаблонов под каждый стенд.
8. **Список анализов с плечом.** Рекомендация: добавить `resource_arm` и `resource_snapshot_sha256` в элемент `analyses[]` (P4a), аддитивно; не читать плечо из каталога рядов.
9. **Загрузка входа для пары плеч.** Решено кодом: `createJob(runId, ...)` принимает уже загруженный `runId`, поэтому вход загружается один раз (P1d); дублирования загрузки нет. Подтвердить, что UI-запуск пары заданиями последовательный.
10. **Эпизоды и корреляции в пределах ядра** (32 проверки аномалий, 16 пар). Рекомендация: шаблонный ограниченный план по объявленному порядку сервисов (P5b), пределы не поднимать; автоматический поиск по данным не вводить (риск ложных находок).
11. **Корреляции до приёмки C5.** Рекомендация: показывать с постоянным баннером «не откалибровано» и без слов о причине; скрывать до C5 - дороже и ничего не защищает.
12. **Пределы pod-view после замера.** Решает владелец по результатам P2e (ADR 0020, «Подлежит пересмотру», п. 1); рекомендация ADR: `R_max` 3 072, 737 280 ячеек, 16 MiB, если измерение подтвердит.
13. **Метрика выбора худших подов при превышении `P_max`/`R_max`.** Рекомендация: память (отношение к limit), затем CPU; параметр адаптера `--select worst:<metric>:<limit>`, значение по умолчанию задаётся в конфигурации стенда.
14. **Порядок очереди identity-срезов** (раздел выше): ADR 0016 срез 3 → B-S1 → A-S2 → P1a → P1b → B-S3 → B-S7 → P2b. Подтвердить.
15. **`policy_id` рядом с вердиктом** (решение 2026-10-04, п. 5): в плане ADR 0018 срез под него не оформлен, B-S4 показывает хэш. Рекомендация: добавить поле `policy_id` в результат или список анализов отдельным срезом до P4b (иначе карта показывает только хэш политики плеча); решение не за этим планом.
16. **Виды workload.** Рекомендация: Deployment и StatefulSet в МВП; DeploymentConfig - после ответа стенда (допущение 8).
17. **Двухпроходный процесс на стенде** (онлайн-проход, затем офлайн-повтор с файлом снимка, pod-view и планами): рекомендация - принять как есть, потому что онлайн-сбор сегодня не сочетается ни с одним ручным входом (`LocalApi.kt:1328`); разрешение сочетания меняет публичное поведение и требует отдельного ADR. Стоимость - второй анализ того же входа (по замеру ADR 0014 порядка 16-20 с на нагрузке 1 млн строк).
18. **Проверка на реальном стенде** (вне МВП): рекомендация - зафиксировать список из 15 допущений выше как чек-лист первого прогона и не объявлять фазу 5 принятой, пока он не пройден.
19. **Ранний старт P2a.** ADR 0020 (раздел 7) ставит реализацию P2 после A-S1, D0 и P1a. Контракт и валидатор без подключения (P2a) технически от них не зависят, и ранний старт сократил бы критический путь. Рекомендация: порядок ADR не нарушать; если владелец хочет ускорения, разрешить только P2a (без P2b и API), как явное исключение из раздела 7.

## Результат независимого ревью плана

Ревью: Codex `gpt-6-sol`, `xhigh`, read-only, по воркстри `origin/main` `135ef5a` (редакция плана `21c1a58`); перед ним планом поправлены замечания собственной проверки (защиты полноты PromQL, двухпроходный процесс, порядок срезов). Каждое замечание проверено фактами; все десять приняты полностью или с сужением:

- Принято: P0d зависит от P0c (JVM-сигналы с пиком и тест отказа `jvm_gc_pause` вводит P0c).
- Принято: `arm` в конфигурации генератора влиял только на `id`; выпуск поля профиля `arm` и версии `source-connections.v3` перенесён в P1b с тестом.
- Принято: защита полноты сайдкаров считалась по всем контейнерам и давала бы вечный пропуск; P1c считает ожидаемые именно сайдкары (`kube_pod_container_info` с тем же регулярным выражением), три сценария promtool выполнены.
- Принято с сужением: потеря записи pod → workload у одного живого пода не обнаруживается ни ядром, ни профилем (граница гарантии ADR 0018, раздел 3); гарантия P3a сужена до «контейнер, сервис, недоступная реплика», риск записан как допущение 17; независимый источник состава подов в МВП не вводится.
- Принято: у карты «сервис x плечо» нет источника каталога политики, состояние `NO_RULES` недоказуемо; заменено на `NOT_CHECKED`, строки берутся из `service` evidence.
- Принято: порядок P2 приведён к ADR 0020 (раздел 7: после A-S1, D0, P1a); P2a в первую волну не ставится, ранний старт вынесен вопросом 19; P2c ждёт D0.
- Принято: пустое значение `arm` и управляющие символы отвергает общий разбор меток кодом `INVALID_TEXT`, а не `INVALID_ARM_LABEL`; таблица и тест уточнены.
- Принято: P0b после P0a (общий `CHANGELOG.md`, имена); волна 1 исправлена.
- Принято: условие старта P5b - C3 и P4a, а не ADR-E.
- Принято: «гейт без стенда» переименован в гейт готовности к стендовой приёмке, исходный exit gate фазы 5 остаётся открытым.

Проверено ревью без замечаний: пределы снимка и источника (`ResourceSnapshot.kt:651-656`, `SourceConfig.kt:840-844`), поведение «один ряд на запрос» и подмножество меток (`PromqlSource.kt:247-257`), демо-раздел не ставит `platform_rules`, `arm`, pod-view и `interval_max` на обязательный путь.
