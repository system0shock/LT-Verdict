# LT Verdict: материалы для внешней экспертизы статистического анализа

Архивы `.zip`, упомянутые ниже, хранятся локально и не включены в Git.
Они сохранены без изменений; исторические проверки требуют отдельного доступа
к этим evidence-артефактам. Свежий clone содержит код и отчёты, но не архивы.

Дата: 2026-09-06. Состояние: завершённая приёмка v1, до выбора исправлений.

## 1. Зачем нужна экспертиза

LT Verdict анализирует результаты нагрузочного тестирования вместе с метриками
ресурсов. Пользователь должен получить проверяемые факты о выполнении SLA,
изменениях между прогонами и диагностические кандидаты для дальнейшего изучения.
Нужны полезные выводы для инженера и будущего ИИ-помощника без выдачи
статистических ассоциаций за доказанные причины деградации.

Полная статистическая приёмка v1 завершена. Численные проверки и системные
синтетические сценарии прошли, но выдача главных находок оказалась слишком
шумной в 8 из 28 конфигураций Monte Carlo. Итог приёмки: **FAIL**.
Незавершённых расчётов в этом исследовании нет.

Просим эксперта оценить адекватность проверки и предложить минимальное
обоснованное изменение отбора главных находок. Конкретный метод исправления
не выбран. Этот документ не является утверждённым проектом исправления.

## 2. Что делает система и что именно проверяем

Входы продукта: результаты запросов нагрузочного генератора, временные ряды
ресурсов, заданные окна/ступени нагрузки, SLA, настройки диагностических пар
и доступная информация о сопоставимости прогонов и часов источников.
Интеграции включают JMeter/Gatling, VictoriaMetrics/Prometheus, Grafana proxy,
InfluxDB, PostgreSQL и offline replay. Наличие интеграций не означает,
что данное исследование является полной живой проверкой каждого коннектора.

| Механизм | Проверяемое поведение |
| --- | --- |
| Описательная статистика ресурсов | Counts, coverage, mean, median, quantiles, MAD, variance, slope и сдвиг между половинами окна |
| Эпизоды отклонений | Median/MAD относительно явного reference, абсолютная материальность, минимальная длительность, интервалы и подавленные короткие отклонения |
| Связь нагрузки с ресурсами | Spearman, partial rank association с явно заданными controls, материальность изменения обоих сигналов |
| Lag profile | Ограниченный поиск временного сдвига, полный профиль, единая поддержка, знак lag и ограничения часов |
| Сравнение двух прогонов | Абсолютные/относительные дельты по сопоставленным окнам, материальность, техническая совместимость и подтверждение условий |
| SLA и итоговый verdict | Business/resource thresholds, обязательность данных, статусы при пропусках; диагностика не меняет deterministic verdict |

`CANDIDATE` означает наблюдаемую ассоциацию, эпизод или материальное изменение.
Он не означает статистическую значимость, доказанную причинность или устойчивую
межпрогонную регрессию. Для временной неопределённости используется
`NOT_ESTIMATED`; production p-values и интервалы неопределённости эффекта
в проверяемом срезе не реализованы.

Отдельно различаются `DESCRIPTIVE`, `INSUFFICIENT_DATA`, `NOT_EVALUATED`,
`NO_MATERIAL_CHANGE` и `CANDIDATE`. Отсутствие находки не доказывает здоровье.
Нулевой измеренный RPS не равен отсутствующему throughput; null latency/error
не заменяется нулём. Нет автоматического добавления achieved RPS в controls:
это может быть результат работы системы, а не внешнее воздействие.

Capacity проверялась отдельно, включая CLI/API/UI и консервативные bounds.
Её приёмка не входит в описываемые 28 конфигураций. ИИ-блок ещё не реализован;
предполагается только advisory на основе evidence.

## 3. Три независимых вопроса приёмки

| Gate | Вопрос | Результат v1 |
| --- | --- | --- |
| CORRECTNESS | Соответствуют ли числа, интервалы, статусы и evidence объявленному контракту? | PASS: 109/109 cases MATCH, 0 errors/mismatches |
| APPLICABILITY | Даёт ли анализ допустимую картину на telemetry механистической синтетической системы? | PASS: 421/421 cases MATCH, 830 system runs |
| USEFULNESS | Насколько часто целый отчёт содержит лишние главные находки и обнаруживает заданные эффекты? | FAIL: 28000/28000 reports, 20 configurations PASS, 8 FAIL |
| Core/persisted parity | Совпадает ли вычислительный путь с ingest, сохранением и reload? | PASS на заранее выбранных 84 случаях |

Общий PASS требует всех трёх основных gates. Правильная формула может давать
непригодную для главной сводки частоту случайных кандидатов.

### 3.1. CORRECTNESS: независимые численные эталоны

Отдельный Python stdlib oracle не импортирует production Kotlin и не использует
его outputs как expected. Для коротких контрольных данных используются
`Fraction`/`Decimal`, precision 50 для деления и квадратного корня.

- Quantiles: type 7 с рациональной интерполяцией; median/MAD из определений.
- Sample variance: сумма попарных квадратов различий, делённая на `n(n-1)`.
- Slope: центрированные суммы по исходным timestamps; gaps не сжимают время.
- Spearman: ранги через подсчёт меньших и равных значений, затем Pearson ranks.
- Partial ranks: normal equations с рациональным Gaussian elimination;
  отдельные вырожденные fixtures для singular controls и zero residual variance.
- Lag: ранги/остатки всего выбранного непрерывного участка, затем сдвиг.
  Для `N` точек и максимального сдвига `L` общие anchors:
  `t = L .. N-L-1`, сравнение `X[t]` и `Y[t+k]`. Повторное ранжирование
  каждого lag subset не соответствует проверяемому estimand.
- Load percentiles: из исходных requests, без усреднения cell p95.
  На точных fixtures применяется nearest rank; в системных данных учитывается
  quantization закреплённого Java HdrHistogram 2.2.2.

Числа проверяются по `abs(actual-expected) <= 1e-9 + 1e-9*abs(expected)`.
Counts, masks, timestamps, статусы и reasons сравниваются точно.
Пороговые решения не используют численную tolerance; проверяются равенство
порогу и значения по обе стороны.

Матрица включает пропуски, константы, ties, малую поддержку, вырожденные controls,
нулевой baseline, совпадающие и несовпадающие окна, разные смеси ступеней,
неизвестные часы, знак lag, материальность и неизменность verdict при включении
диагностики. Claims audit проверяет запрещённые утверждения по фиксированным
правилам; это не доказательство отсутствия любой возможной ошибки интерпретации.

### 3.2. APPLICABILITY: моделируем механизм, затем измеряем

Test-only discrete-event service:
`arrivals -> admission pool -> CPU service -> DB service -> downstream wait -> completion`.
Ограниченные ресурсы имеют FIFO queues и заданную мощность. Ожидание очереди
не потребляет CPU service time. Latency получается из событий start/end,
utilization из busy time/capacity, throughput из событий запросов.
Latency не рисуется как функция уже вычисленного CPU utilization ради корреляции.

Базовая модель: CPU 1 worker/10 ms demand, DB 8 workers/2 ms demand,
downstream 38 ms, admission pool 256, ступени 40/70/90/110 rps по 300 s.
Семейства явно меняют эти параметры. Есть clean и noisy варианты;
в noisy используются отдельные потоки вариации service demand и arrivals.

| Семейство | Проверяемый механизм / парное вмешательство |
| --- | --- |
| NT01 | CPU limitation: увеличение CPU workers |
| NT02 | Общий workload driver: CPU association при независимом от CPU downstream delay |
| NT03 | DB limitation: увеличение DB workers |
| NT04 | Ограничение admission pool |
| NT05 | CPU throttling / quota |
| NT06 | Heap/GC pressure и stop-the-world pauses |
| NT07 | Downstream latency step |
| NT08 | Autoscaling и recovery |
| NT09 | Ограничение генератора по in-flight threads |
| NT10 | Разные доли одинаковых нагрузочных ступеней в двух прогонах |

Base и intervention используют одинаковые arrivals, demands и noise streams;
меняется названный механизм. Проверяются также missing telemetry, clock offsets,
coarse grid и temporal scenarios. Всего 400 paired cases/800 runs для десяти
семейств и 21 дополнительный case, суммарно 421 case/830 runs.

Симулятор предварительно проверяется на сохранение количества запросов,
ограничение busy time доступной мощностью, порядок стадий, неотрицательные
длительности/очереди и ручную single-worker рекурсию завершения запросов.
Полные event traces сохраняются. Exporter создаёт JTL и resource snapshots,
которые проходят настоящий persisted-анализ. Expected SLA, статистики и дельты
получаются из request trace и сериализованной telemetry независимыми расчётами.

Окна и SLA задаются до outputs. Пример fixture SLA: window p95 <= 200 ms;
CPU/DB utilization > 0.9 не менее 3 cells. Это параметры эксперимента,
а не универсальные пороги saturation. Окна не подбираются по скрытому моменту
деградации; coarse grid не получает выдуманную субклеточную точность.

Алгоритм не получает hidden cause/intervention flag. Знание механизма evaluator
не делает причину идентифицируемой из наблюдений. Unknown clocks допускают
observed lag/CANDIDATE с `CLOCK_ALIGNMENT_UNKNOWN`, но не утверждение
межисточникового временного порядка. PASS здесь не доказывает перенос
на произвольный боевой стенд и не требует восстановить causal graph.

### 3.3. USEFULNESS: Monte Carlo на уровне целого отчёта

28 заранее заданных конфигураций, по 1000 reports каждая. Единица оценки:
отчёт, а не точка ряда, request или отдельная пара. При нескольких парах
ресурсы независимы друг от друга, но используют один load outcome отчёта.

Общие параметры correlation: grid 1 s, reference 120 cells, evaluation 240 cells,
target 20 requests/s; 20 одинаковых latency requests/cell точно задают cell p95.
CPU `X = 0.5 + 0.2*tanh(Zx)`, latency `Y = 200 + round(40*tanh(Zy)) ms`.
Материальность: `min_abs_effect=0.3`, resource delta 0.1, load delta 20 ms,
`expected_sign=either`; часы declared aligned. Максимальный lag 0 или 10 cells.

AR(1): `Zt = phi*Z(t-1) + sqrt(1-phi^2)*epsilon_t`, `phi=0.8`,
512 начальных значений отбрасываются. Student-t3 строится из независимых
Gaussian draws. Для каждого family/seed/stream отдельный SHA-256-derived PRNG;
inputs сериализованы до запуска с округлением HALF_EVEN до 6 десятичных знаков.

| Семейства | Сценарий | Reports |
| --- | --- | ---: |
| N01/N02/N03 | Независимые X/Y: IID Gaussian, AR(0.8), IID t3; каждая семья с 1/16 pairs и lag 0/10 | 12000 |
| P01/P02/P03 | Одна внедрённая связь среди 16 pairs: положительная lag 0, положительная lag +3, отрицательная lag -3 | 3000 |
| E01/E02/E03 | Нет внедрённых эпизодов, noise Gaussian/AR(0.8)/t3; 1/32 anomaly rules | 6000 |
| P04/P05 | Один эпизод +10/-10 на cells [80,100), AR noise, всего 32 rules | 2000 |
| T01/T02/T03 | Два независимых прогона одного Gaussian/AR(0.8)/t3 процесса, без внедрённого изменения | 3000 |
| P06/P07 | Два AR-прогона, latency всех current requests сдвинута на +40/-40 ms | 2000 |

P01 использует `Zy=Zx+0.25*independent Gaussian` для AR-сигнала;
P02/P03 добавляют сдвиг из расширенного ряда без wrap-around.
Положительный lag означает: resource раньше load.

Episode signals: `100+noise`, absolute delta 5, duration 3 s, modified-z 3.5,
direction either. Reference/evaluation имеют одинаковое распределение в null.
Two-run: 240 cells/run, одинаковые matched windows, подтверждённые условия,
`min_change_percent=5`, `min_error_rate_delta=0.001`; error rate одинаков,
ровно 1 error на каждые 100 requests. Baseline не выбирается из нескольких runs.

Headline определяется заранее: emitted correlation/anomaly finding либо
comparison metric row `CANDIDATE`. `DESCRIPTIVE` coefficient row не headline.
Шум: отчёт с хотя бы одной unexpected/unrelated headline. В null-two-run
реальная случайная материальная разница считается operational noise,
а не ошибкой вычисления дельты.

Критерии применяются к каждой конфигурации отдельно:

- Шум: доля <= 5% **и** верхняя граница двустороннего Wilson 95% <= 7%.
- Detection: доля >= 90% **и** нижняя Wilson 95% >= 85%.
- Для positive reports unrelated extras подчиняются тому же шумовому gate.
- Episode detection: правильный знак и IoU >= 0.5 с истинным интервалом.
- Correlation detection: headline именно внедрённой пары, правильный знак
  коэффициента и signed lag в допуске +/-1 cell.
- Two-run detection: все три p50/p95/p99 являются CANDIDATE правильного направления.
- Ошибки, пропавшие outputs и незавершённые cases не исключаются из учёта.

Wilson характеризует частоту в данном генераторе, а не достоверность отдельной
production-находки. Shared seeds между конфигурациями не дают независимость
для pooled inference. Интервалы по конфигурациям не являются одновременной
95% гарантией на все семейства.

## 5. Проблемы и границы выводов

### 5.1. Отбор корреляционных находок

**Наблюдение:** шум резко растёт на независимых автокоррелированных рядах
при увеличении числа пар и разрешении поиска lag. Сильные внедрённые связи
находятся, но рядом появляется много unrelated candidates.

**Рабочая гипотеза для эксперта:** фиксированный cutoff величины association
и пороги материальности не обеспечивают нужный контроль report-level noise
при временной зависимости и поиске по нескольким парам/лагам. Эксперимент
показывает проблему, но не является доказательством конкретного способа её
исправления. Нельзя считать каждый лаг независимым тестом или автоматически
переносить IID significance formulas на эти данные.

### 5.2. Сравнение двух прогонов

**Наблюдение:** два прогона одного процесса часто дают материальное изменение
p50, достаточное для CANDIDATE. Арифметика соответствует фактическим requests.

**Вопрос:** какое дополнительное evidence должно отделять наблюдаемую дельту
от главной находки, которую инженер воспринимает как устойчивое изменение?
Тысячи requests внутри двух runs не заменяют независимые повторные прогоны.
Оценка временной неопределённости внутри ряда и оценка межпрогонной изменчивости
отвечают на разные вопросы.

### 5.3. Ограничения самой проверки

- Cutoffs и критерии инженерные; универсальная false-positive guarantee
  для реальной telemetry не заявляется.
- Реализация и прежние тесты были известны авторам: исследование не blind.
  Новые inputs/expected были зафиксированы до их production outputs.
- Monte Carlo покрывает конкретные распределения, длительности, число пар,
  лаги и размеры эффектов. Нет полной power curve по слабым эффектам,
  длительности, степени автокорреляции и всем возможным режимам.
- t3 в correlation/two-run проходит bounded transform; это не проверка
  произвольных неограниченных тяжёлых хвостов реальных CPU/latency.
- Успех сильных фиксированных episodes не доказывает чувствительность
  к коротким, слабым или немонотонным эпизодам.
- Механистический симулятор является тестовой моделью, не цифровым двойником
  стенда. Частоты его paired/noisy variants не имеют MC population gate.
- 84-case parity подтверждает заранее выбранное подмножество всех 28
  конфигураций, а не полный persisted replay всех 28000 reports.
- Не проверены качество будущего ИИ, полная живая end-to-end приёмка MVP,
  внешний runtime/performance CI и полный secret/history scan.

Отдельный продуктовый gap `BASELINE-CONDITIONS-01`: отсутствуют UI/API
и постоянное хранение подтверждения условий ручной пары. Для исследования
реальный `compareAnalyses` получает явный internal nullable Boolean контекст
одного вызова из manifest. True/false/default и строгая валидация проверены;
это не закрывает пользовательский workflow и не меняет формулы сравнения.

## 6. Защита от подгонки и воспроизводимость

До acceptance фиксировались методика, generator, independent oracle,
inputs/expected, source archives, dependency locks и manifests с SHA-256.
Одного Git HEAD недостаточно: исследование выполнено в dirty worktree,
исходники дополнительно зафиксированы архивами.

Debug seeds: 0..99; USEFULNESS v1: 1000..1999; APPLICABILITY: 2000..2019.
Пороги и expected после результатов не менялись. Все acceptance seeds v1
теперь раскрыты. Их дальнейшее использование для настройки допустимо только
как development/regression, а не независимая приёмка.

Для следующей версии нужно заранее зафиксировать метод, критерии и новый
диапазон seeds после development-фазы; исходный FAIL остаётся в истории.
Нельзя повторять подбор seeds до PASS или задним числом переименовать
шумные headlines в descriptive ради улучшения старого score.

Среда исследования: Windows 11, Python 3.14.3, Java 21.0.9, Gradle 9.5.0,
Node 24.14.0. Численные expected, actual, score, исходники и команды сохранены.
Полный MC занял 1 h 15 min 5 s; повтор для подготовки этого документа не запускался.

## 7. Вопросы внешнему эксперту

1. Соответствует ли определение report-level noise реальному назначению
   CANDIDATE, особенно в двухпрогонном сравнении? Какие claims и уровни
   представления следует явно разделить до выбора статистического метода?
2. Достаточны ли независимость oracle, выбранные null/positive families
   и системная rubric для заявленных выводов? Какие пробелы способны
   существенно изменить решение, а какие можно оставить за пределами MVP?
3. Какой минимальный подход к отбору correlation headlines учитывает
   автокорреляцию, общий outcome, множество pairs и весь поиск lag?
   Как меняется обоснование для partial ranks с fitted controls?
4. Как обрабатывать p50 two-run candidates без выдуманной межпрогонной
   уверенности по двум runs? Когда достаточно ограниченного описательного
   вывода, а когда нужны повторные runs или оценка временной неопределённости?
5. Если предлагается resampling/test, какие предпосылки обязательны,
   как выбирать block length/lag search и проверять чувствительность,
   как поступать с gaps, nonstationarity и недостатком данных?
6. Как одновременно сохранить detection и ограничить extras? Какие
   дополнительные development-сценарии и независимые acceptance-сценарии
   нужны, чтобы не оптимизироваться только под AR(0.8) и сильные эффекты v1?
7. Каковы стоимость расчёта, ограничения и минимальный объём изменения
   предлагаемого решения? Что конкретно можно отложить до появления
   новых данных или продуктовой потребности?

Предпочтительный ответ: замечания по существенности, рекомендуемый минимальный
вариант, необходимые предпосылки и abstention rules, план проверки без подгонки,
остаточные риски. Если подходов несколько, просим выбрать основной и объяснить
условия, при которых понадобится более сложный.

В roadmap уже упомянуты block bootstrap effect intervals, block permutation
с Holm и TTS. Они **не реализованы и не утверждены как решение**.
Holm не исправляет некорректный null; гарантии unconditional stationary test
не переносятся автоматически на conditional fitted residuals.
Pearson/Kendall и другие коэффициенты также отложены: дополнительный
коэффициент сам по себе не решает показанную проблему отбора.
