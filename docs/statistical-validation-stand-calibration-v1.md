# LT Verdict: проверка и калибровка стат-ядра на боевом стенде

Статус: черновик, 2026-11-12. Инструкция для локального агента на стенде
(модель GLM 5.3 fp8 с доступом к shell). Результат этой работы — development-замер
на реальных прогонах, а не статистическая приёмка: итог v1
([результаты](statistical-validation-results-v1.md)) и протокол C5
([протокол](statistical-validation-correlation-c5-protocol-v1.md)) он не меняет.

## Зачем

Синтетическая приёмка показала два слабых места: сравнение двух прогонов
срабатывает на шуме, а корреляционный отбор и колено ёмкости не откалиброваны.
На реальных прогонах нужно измерить, как это выглядит в действительности.

Твоя задача — **собрать числа и вернуть отчёт по шаблону**. Ты не делаешь
выводов о качестве системы, не подбираешь пороги и ничего не исправляешь.

## Жёсткие правила

1. Только чтение. Не меняй и не удаляй прогоны, политики, профили источников
   и рабочий каталог данных LT Verdict.
2. Все свои запуски делай с отдельным каталогом данных:
   `--data-dir /tmp/ltv-calib/data` и `--out-dir /tmp/ltv-calib/out/<имя>`.
3. Не меняй пороги и планы, чтобы «получилось лучше». Один прогон — один
   запуск с заданными ниже параметрами. Повторять можно только после ошибки
   запуска, и ошибку нужно записать.
4. Запускай анализы по одному, не параллельно, вне окон нагрузочных тестов.
   Если стенд сейчас под тестом — остановись и запиши это в отчёт.
5. В отчёт не попадают имена хостов, сервисов, транзакций, адреса, токены и
   сырые ряды. Сервисы обозначай `S1, S2…`, транзакции `T1, T2…`, прогоны
   `R01, R02…`. Таблицу соответствия оставь на стенде в
   `/tmp/ltv-calib/aliases.json` и не передавай.
6. Если шаг невозможен — не придумывай значения. Пиши `НЕ ВЫПОЛНЕНО` и
   точный текст ошибки или причину.
7. Если команда завершилась с кодом, отличным от 0, 2 и 3, это ошибка запуска.
   Коды 2 (FAIL) и 3 (нет вердикта) — нормальные результаты анализа.

## Шаг 0. Версия и возможности

```text
ltv --version
ltv --help
```

Запиши версию. По тексту `--help` отметь, есть ли:

- `--baseline` у `ltv analyze` и `ltv summary` (нужен для шага 2);
- `ltv source validate` и `ltv source probe` (нужны для шага 6);
- `--stages`, `--correlation`, `--capacity`, `--trend`;
- `python3 --version` (нужен для шага 3б).

Чего нет — соответствующий шаг помечается `НЕ ВЫПОЛНЕНО: нет в версии`.

## Шаг 1. Опись прогонов (до любых анализов)

Составь список всех доступных прогонов с исходным файлом нагрузки
(JTL или Gatling `simulation.log`). Для каждого запиши:

| Поле | Что писать |
| --- | --- |
| alias | `R01…` по возрастанию времени начала |
| начало, длительность | UTC, минуты |
| профиль | имя сценария нагрузки (алиасом `P1, P2…`) |
| версия приложения | как записана у вас; если неизвестна — `?` |
| тип | `плато` (постоянная нагрузка) или `ступени` |
| ресурсы | есть ли снимок ресурсов или доступ к источнику за этот период |
| исход по мнению инженеров | `норма`, `деградация`, `авария`, `?` — только если это где-то уже записано людьми; сам не оценивай |

Затем **раздели список пополам и зафиксируй это до запусков**: прогоны с
нечётным номером — набор `CAL`, с чётным — набор `HOLD`. Все шаги ниже
выполняются только на `CAL`. Набор `HOLD` не анализируй вообще: он нужен
для последующей независимой проверки.

Сохрани опись в `/tmp/ltv-calib/inventory.json` и не меняй после шага 1.

## Шаг 2. Шум сравнения двух прогонов (главный)

Цель: узнать, насколько различаются прогоны, между которыми ничего не менялось.

1. Из `CAL` выбери все пары `(A, B)`, где одинаковы профиль и версия
   приложения, оба прогона типа `плато`, оба с исходом `норма` или `?`,
   и между ними не больше 14 суток. Каждый прогон может входить в несколько
   пар. Если пар меньше 10 — всё равно выполни и запиши число.
2. Для каждого прогона один раз:

   ```text
   ltv analyze <файл> --policy <действующая политика> --stages <стадии, если есть> --data-dir /tmp/ltv-calib/data --out-dir /tmp/ltv-calib/out/<alias>
   ```

   Команда печатает в stderr строку `analysis_id=… run_id=…`. Запиши оба
   значения для прогона. Набор флагов у обоих прогонов пары должен быть
   одинаковым: либо оба с `--stages`, либо оба без.

3. Для каждой пары. Baseline принимается только из каталога данных, файл из
   `--out-dir` не подходит:

   ```text
   ltv summary <run_id B> <analysis_id B> --baseline /tmp/ltv-calib/data/runs/<run_id A>/analyses/<analysis_id A>/analysis-result.json --data-dir /tmp/ltv-calib/data > /tmp/ltv-calib/pairs/<A>_<B>.json
   ```

4. В каждом файле возьми ключ `baseline_comparison`. Метрики лежат в
   `metrics[]` (при `scope = whole_run`) или в `windows[].metrics[]` (при
   `scope = steady_window`). По каждой метрике выпиши `metric`,
   `delta_percent`, `delta` и, если есть, `status` и `reason`. Выпиши также
   `scope` и `warnings`. Если `delta` пуст, а `reason` заполнен
   (например, `INCOMPATIBLE_METRIC_DEFINITION`), пара не сопоставима:
   посчитай её отдельно и в статистику разниц не включай.

Заметной считай разницу, если модуль `delta_percent` не меньше 5, а для
`error_rate_ratio` — если модуль `delta` не меньше 0,001. Это пороги продукта
по умолчанию. Статус `CANDIDATE` в CLI не возникает, поэтому считай сам.

В отчёт:

- число пар; сколько из них `scope = steady_window`;
- по каждой метрике: медиана, p90, p95 и максимум модуля относительной
  разницы; для доли ошибок — то же по абсолютной разнице;
- число несопоставимых пар и их коды `reason`;
- доля пар, где хотя бы у одной метрики разница заметная, и отдельно доля
  по каждой метрике;
- то же самое отдельно для пар внутри одних суток и для пар с разницей
  больше суток.

## Шаг 3. Корреляционный отбор

Только для прогонов `CAL`, у которых есть снимок ресурсов
(`resource-snapshot.v1`) и корреляционный план, привязанный к этому снимку
полем `resource_snapshot_sha256`. Если плана на стенде нет —
`НЕ ВЫПОЛНЕНО: нет плана`, сам план не сочиняй.

```text
ltv analyze <файл> --policy <политика> --resources <снимок> --correlation <план> --data-dir /tmp/ltv-calib/data --out-dir /tmp/ltv-calib/out/<alias>-corr
```

Результат лежит в `<out-dir>/result.json`, нужные записи — в массиве
`evidence`. По каждому прогону выпиши:

- шаг ячейки (секунды) и `paired_cells` по каждому окну;
- из записей `"type": "correlation_pair"`: сколько всего и сколько в каждом
  `status` (`CANDIDATE`, `DESCRIPTIVE`, `BELOW_EFFECT` и другие), коды `reasons`;
- из записей `"type": "correlation_headline_selection"`: сколько всего,
  сколько с `"selected": true`, сколько в каждом `status` и с какими `reasons`
  (в частности, `UNAVAILABLE` с `GENUINE_PARTIAL_UNCALIBRATED`);
- для каждой записи с `"selected": true`: модуль `partial_rho` парной записи,
  `best_lag_ms`, `holm_adjusted_p_value`, тип ресурса (CPU, память, GC и
  т. п., без имени сервиса);
- время выполнения команды в секундах.

В отчёт дополнительно: распределение числа отобранных находок на прогон
отдельно для исходов `норма` и `деградация/авария`.

## Шаг 3б. Плацебо для корреляций

Цель: измерить долю ложных находок. Скрипт циклически сдвигает ресурсные ряды
внутри каждого окна, а нагрузку оставляет на месте. Настоящая связь ресурса с
нагрузкой при этом разрывается, поэтому любая находка на таком снимке — ложная.

Нужны два файла из репозитория в одном каталоге: `tools/correlation_placebo.py`
и `tools/stats_validation.py`. Сторонних пакетов не требуется.

Для каждого прогона из шага 3:

```text
python3 correlation_placebo.py <снимок> --plan <план> --out-dir /tmp/ltv-calib/placebo/<alias> --count 3
```

Скрипт пишет `placebo-1.json … placebo-3.json` и к каждому свой план
`placebo-<n>.plan.json`. Код выхода 4 и строка `error: …` означают отказ:
запиши код причины (`WINDOW_TOO_SHORT`, `WINDOWS_OVERLAP`,
`PLAN_SNAPSHOT_MISMATCH` и т. п.) и переходи к следующему прогону. Если
`WINDOW_TOO_SHORT`, повтори один раз с `--count 1`.

Затем для каждого `n`:

```text
ltv analyze <файл> --policy <политика> --resources /tmp/ltv-calib/placebo/<alias>/placebo-<n>.json --correlation /tmp/ltv-calib/placebo/<alias>/placebo-<n>.plan.json --data-dir /tmp/ltv-calib/data --out-dir /tmp/ltv-calib/out/<alias>-placebo-<n>
```

Вердикт и ресурсные правила плацебо-запусков не учитывай: сдвиг меняет время
нарушений. Выпиши те же счётчики, что в шаге 3: пары по `status`, отбор по
`selected`, `status` и `reasons`.

В отчёт: число плацебо-запусков; доля запусков хотя бы с одной записью
`"selected": true`; всего таких записей и всего гипотез; доля пар со
`status`, отличным от `BELOW_EFFECT`; те же числа отдельно по шагу ячейки и
по числу гипотез в плане (1, 2–8, 9–16). Рядом — те же числа для настоящих
снимков из шага 3.

## Шаг 4. Тренд

Для прогонов `CAL` типа `плато` длительностью от 30 минут с ресурсами и
действующим планом трендов (`--trend <план>`). По каждому прогону: число
проверок, сколько `TREND_OBSERVED`, `NO_MATERIAL_TREND`, `INSUFFICIENT_CELLS`,
`UNAVAILABLE`; для каждого `TREND_OBSERVED` — тип ресурса, наклон, сдвиг
половин в процентах. В отчёт: доля прогонов с исходом `норма`, где есть хотя
бы один `TREND_OBSERVED`.

## Шаг 5. Колено ёмкости

Для прогонов `CAL` типа `ступени` с планом ёмкости (`--capacity <план>`).
**До запуска** запиши для каждого прогона номер ступени, на которой, по
записям инженеров, началась деградация (или `нет`, или `?`). После запуска
выпиши: число ступеней, найдено ли колено и на какой ступени, код причины
(`KNEE_*`), вердикт ёмкости, число ступеней с пометкой малой выборки.
В отчёт: таблица «ступень по записям инженеров / ступень по LT Verdict /
причина».

## Шаг 6. Малые выборки и применимость источников

1. По результатам шага 2: для окна оценки посчитай, сколько транзакций имеют
   число запросов меньше 20, от 20 до 99, от 100 до 999, от 1000. Сколько
   правил получили `SMALL_SAMPLE` и `INSUFFICIENT_SAMPLES`.
2. Для каждого профиля источников:

   ```text
   ltv source validate --connections <профили> --profile <id> --format json
   ltv source probe --connections <профили> --profile <id> --query-id <id> --window-ms 600000 --step-ms <шаг профиля> --format json
   ```

   По каждому запросу: статус, `series_count`, `decoder_check`, единица
   измерения. Запросы с нулём рядов перечисли отдельно (по алиасам).

## Отчёт

Один файл `/tmp/ltv-calib/report.md` со строго такими разделами:

```text
0. Версия ltv, дата, какие шаги выполнены / не выполнены и почему
1. Опись: число прогонов всего, в CAL, в HOLD; по профилям и типам
2. Шум сравнения: таблицы из шага 2
3. Корреляции: таблицы из шагов 3 и 3б
4. Тренд: таблицы из шага 4
5. Колено: таблица из шага 5
6. Малые выборки и источники: таблицы из шага 6
7. Ошибки запусков: команда (без путей и имён), код выхода, текст ошибки
8. Отклонения от инструкции: что сделано иначе и почему
```

Только числа и коды. Без интерпретаций, без рекомендаций, без имён.
Перед отправкой проверь поиском, что в файле нет имён хостов, сервисов,
транзакций, IP-адресов и токенов.
