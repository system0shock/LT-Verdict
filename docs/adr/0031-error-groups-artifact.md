# ADR 0031: Разбивка ошибок прогона (`error-groups.v1`)

Дата: 2026-10-09.

Статус: Accepted (решение исполнителя W2.6 в рамках перечня ревью от 2026-10-08; владелец
читает production-дифф при слиянии PR). Номер 0031 выбран как следующий после 0030; перед
слиянием его нужно перепроверить по `origin/main`.

## Контекст

Разработчик, у которого прогон не прошёл по доле ошибок, не видит в отчётах ни кода ответа, ни
текста ошибки: `LoadSample` их не хранил, `metric_summary` содержит только `error_count` и
`error_rate_ratio`. Ему приходилось открывать JMeter Dashboard (usability B6, W2.6 перечня работ).
Нужны `responseCode` и `failureMessage` в `LoadSample`, топ ошибок по (код ответа, сообщение) в
отчётах и место, где живёт разбивка. [ADR 0029](0029-incident-v0.md) ожидает от W2.6 форму групп
ошибок (`id`, область transaction, интервал, ссылка на evidence) как будущий вход инцидентов W3.7.

Ограничения решения:

1. `analysis_id` и байты `analysis-result.json` существующих прогонов не меняются. Canonical JSON и
   хэши identity не затрагиваются.
2. Минимальный дифф: никаких новых зависимостей и слоёв.

## Решение

### Место хранения: отдельный артефакт каталога анализа

Разбивка пишется файлом `error-groups.json` рядом с `rollup-*.ndjson` и `load-stages.json`.

| Вариант | Результат | Цена |
| --- | --- | --- |
| (a) evidence в `analysis-result` | меняет байты результата каждого прогона с ошибками; под одним `analysis_id` лежали бы два разных результата, то есть нужен новый identity и перегенерация golden | перегенерация и новый `analysis_id` у всех прогонов с ошибками; это работа W3.7 (ADR 0029, решение 2) |
| (b) **артефакт вне identity** (принят) | `analysis_id` и результат не меняются; `manifest.json` включает файл автоматически (`inspectStagedArtifacts`) | у одного `analysis_id` бывают два состояния каталога (до и после W2.6); старые анализы остаются без разбивки |
| (c) пересчёт при отрисовке | ничего не хранится | повторный разбор входа до 4 ГБ при каждом открытии отчёта; недоступно, если исходник удалён |

Файл полностью определяется входом (детерминирован), поэтому два состояния каталога одного
`analysis_id` не противоречат друг другу. Повторный анализ того же входа возвращает сохранённый
анализ без второго прохода и не дописывает файл; манифест существующих анализов не переписывается
(он входит в привязку ИИ-рекомендаций к анализу, `AiAdviceStore`, поэтому переписывание
инвалидировало бы рекомендации). Файл пишется только если был хотя бы один неуспешный сэмпл:
каталоги и манифесты прогонов без ошибок не меняются.

### Что хранит `LoadSample`

`responseCode: String?` и `failureMessage: String?`, оба `null` у успешного сэмпла (долгий прогон не
держит лишних строк).

| Источник | `responseCode` | `failureMessage` |
| --- | --- | --- |
| JTL CSV | столбец `responseCode` | столбец `failureMessage`, если не пуст, иначе `responseMessage` |
| JTL XML | атрибут `rc` | первый непустой `<failureMessage>` сэмпла (читается потоково, не более 4096 символов), иначе атрибут `rm` |
| Gatling text | нет | сообщение строки `REQUEST` со статусом `KO` |
| Gatling binary | нет | сообщение записи `Request` со статусом `KO` |

Столбцы и атрибуты необязательны: ранее принятый вход остаётся валидным (нет столбца: `null`).
Версия парсера в identity не меняется: поток метрик и вердикт прежние.

### Формат `error-groups.v1`

Canonical JSON. Считаются только неуспешные сэмплы видов `JMETER_SAMPLER` и `GATLING_REQUEST`, то
есть ровно те, что дают `overall.error_count`; контейнеры (`JMETER_CONTAINER`, `GATLING_GROUP`)
повторяют ошибки дочерних и не входят.

| Поле | Значение |
| --- | --- |
| `schema_version` | `error-groups.v1` |
| `run_id` | идентификатор прогона |
| `scope_note` | `whole_run`: разбивка за весь прогон, при вердикте по окну steady справочная величина (ADR 0030, R10) |
| `total_error_count` | число неуспешных сэмплов; равно `overall.error_count` |
| `tracked_error_count`, `untracked_error_count` | ошибки в отслеживаемых ключах и вне них; `total = tracked + untracked` |
| `tracked_group_count`, `omitted_group_count`, `omitted_error_count` | число отслеживаемых ключей; ключи и ошибки вне топа; `tracked = сумма groups[].count + omitted_error_count` |
| `limits` | `groups_max` 20, `tracked_groups_max` 2048, `code_chars_max` 64, `message_chars_max` 200 |
| `groups[]` | не более 20 групп, по убыванию `count`, затем по метке, пути групп, виду, коду, сообщению (байты UTF-8) |

Группа: `id` (`errgrp-` + SHA-256 канонического JSON `{scope, response_code, message}`), `scope`
(`kind: transaction`, `label`, `group_path`, `sample_kind`), `response_code` и `message` (строка или
`null`), `message_truncated`, `count`, `from_epoch_ms` (первое начало сэмпла-ошибки) и `to_epoch_ms`
(последнее окончание). Ключ группы: (метка, путь групп, вид, код, сообщение). Читатель игнорирует
неизвестные ключи верхнего уровня.

### Лимиты и недоверенный текст

Код и сообщение приходят из файла пользователя (тело ответа сервера, текст ассерта) и считаются
недоверенными данными. Перед группировкой текст очищается: символы управления, форматные (в том числе
двунаправленности и нулевой ширины), разделители строк и абзацев, неназначенные и одиночные
суррогаты заменяются пробелом, серии пробелов сворачиваются, края обрезаются; код не длиннее 64
символов (code points), сообщение не длиннее 200, после обрезки добавляется `…` и ставится
`message_truncated`. Отслеживается не более 2048 различных ключей и 16 MiB их текстов; ошибки
остальных ключей идут в `untracked_error_count`. Цена лимита: ключ, впервые встреченный после
заполнения учёта, попадает в «прочие» (даже если он доминирует по числу); сообщения с вариативными
числами и идентификаторами не нормализуются (замена чисел это отдельное решение с риском склеить
разные ошибки). Читатель отчёта очищает текст ещё раз, потому что файл каталога данных это тоже
недоверенный вход.

Экранирование: HTML `escape`; AsciiDoc: одна литеральная секция `[subs=specialchars]`, каждая
строка начинается с числа ошибок, поэтому текст сообщения не может быть строкой `----`; Confluence:
`&`, `<`, `>`, `"`, `'` экранируются, управляющих символов нет (XML 1.0).

### Чтение

Читатель берёт файл из каталога анализа, уже проверенного `readAnalysis` (пути и размеры
манифеста): обычный файл без ссылок, не более 1 MiB, глубина JSON не более 8, не более 20 групп,
`schema_version` и `run_id` совпадают, счётчики неотрицательные. Любое нарушение трактуется как
«разбивка недоступна». SHA-256 файла не перепроверяется (как у `rollup-60s.ndjson`).

### Публичные контракты

- Новый файл `error-groups.json` каталога анализа (этот ADR).
- `summary.txt` получает блок `top errors (whole run, <N> total):` с не более чем 5 строками
  `<count> <code> <message> [<transaction>]` (с отступом в два пробела) только при наличии групп.
- `ltv summary` (`cli-summary.v1`) получает необязательный ключ `error_groups`
  (`scope`, `total_error_count`, `other_error_count`, `groups[]` не более 5) только при наличии групп.
- Отчёты HTML, AsciiDoc, Confluence получают раздел «Ошибки» / `Error groups`; HTML и AsciiDoc
  принимают необязательный параметр с байтами файла.
- Не меняются: `analysis-result.v1`, `identity`, `analysis_id`, коды выхода, вывод `analyze` в stdout,
  HTTP-контракты, схемы `docs/contracts`.

## Совместимость с ADR 0029

Группа несёт `id`, область `scope {kind, label, group_path, sample_kind}`, интервал
`from_epoch_ms`/`to_epoch_ms` и лежит в артефакте с SHA-256 в `manifest.json`. Для атома TRANSACTION
ADR 0029 требует ещё `finding_id`, `evidence_id` и `window_id`. Их даёт поправка к ADR 0029 перед
кодом W3.7: evidence-ссылка на артефакт (путь и SHA-256) со списком `id` групп и, при необходимости,
новый тип находки; она меняет результат и identity (как и `incident_method`), поэтому принадлежит
W3.7. Область ключа группы в артефакте хранит сырую метку и путь групп для сопоставления с областью
транзакции в `metric_summary`; очищается только показ. Разбивка по окнам стадий в v1 не считается.

## Ограничения

- Разбивка за весь прогон, без окон стадий.
- Анализы, созданные до W2.6, остаются без разбивки; отчёт говорит об этом явно. Пересчёта нет.
- Сообщения не нормализуются: ошибки с вариативными идентификаторами дают много групп.
- Gatling не даёт кода ответа.
