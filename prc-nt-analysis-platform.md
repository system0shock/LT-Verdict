# ПРК: Платформа анализа результатов нагрузочного тестирования

**Рабочее название:** NT Verdict
**Статус:** проектная концепция (PRC), версия 0.3 — развитие MVP-концепции v0.1. В v0.3 учтены уточнения: контролируемый SLA-редактор в GUI и отчётность в Confluence с цифровым первоисточником
**Дата:** июль 2026

---

## 1. Назначение и границы

Децентрализованная платформа-дистрибутив для анализа результатов нагрузочного тестирования. Каждая команда разворачивает платформу в собственном контуре. Платформа объединяет три класса данных в единую модель прогона, выносит детерминированный вердикт по версионируемому контракту правил и генерирует формальный протокол НТ.

Источники данных:

1. **Результаты прогонов Gatling / JMeter** — сырые артефакты инструментов (JTL, simulation.log) плюс real-time поток из backend-листенеров.
2. **Аппаратные метрики** — CPU, память, диски, сеть, GC, пулы соединений из существующей VictoriaMetrics команды (node_exporter, cAdvisor, JMX-экспортеры). Платформа **не собирает метрики параллельно** — она читает окна прогонов из уже существующего мониторинга.
3. **APM из ELK** — транзакции, спаны и ошибки из индексов Elastic APM (форк ELK), read-only доступ через REST API.

Инварианты (не обсуждаются при реализации): факты → детерминированный вердикт → интерпретация; вердикт воспроизводим побайтово из тех же входов и той же версии правил; fail-closed — неполные данные дают `NO_VERDICT`, а не «зелёный по умолчанию»; конфигурация-как-код, UI не является источником истины; append-only журнал решений; сырые данные не покидают контур команды (152-ФЗ, PCI DSS).

Вне границ MVP: запуск тестов (платформа анализирует, не оркестрирует), запись в системы мониторинга, автоматический RCA-агент (закладывается интерфейсной точкой расширения, реализуется после MVP), интеграция с CI-гейтами (появляется естественно после стабилизации вердикта).

## 2. Архитектура

Модульный монолит — выбор в пользу простоты дистрибуции: одна команда получает один контейнер ядра плюс PostgreSQL и объектное хранилище, а не событийную шину с тремя сервисами. Модули с жёсткими внутренними контрактами позволяют распилить на сервисы позже, если появится центральная инсталляция.

```
┌────────────────────── NT Verdict Core ──────────────────────┐
│                                                             │
│  Ingest            Collectors          Analysis             │
│  ├─ JTL stream     ├─ VM adapter       ├─ Normalizer (HDR)  │
│  ├─ Gatling log    │  (PromQL windows) ├─ Validity gates    │
│  └─ Graphite/     └─ ELK APM adapter   ├─ Verdict engine    │
│     Influx intake     (ES REST, RO)    └─ Comparator        │
│                                        (baseline / KS-test)  │
│  Output                                                      │
│  ├─ Protocol generator (adoc + графики → Confluence)         │
│  ├─ REST API                                                 │
│  └─ GUI (SPA + SLA-редактор)                                 │
└──────────────┬───────────────────┬──────────────────────────┘
               │                   │
        PostgreSQL            MinIO / S3
   (метаданные прогонов,   (сырые JTL/simulation.log,
    вердикты, правила,      HDR-снапшоты, протоколы)
    журнал решений)
```

### 2.1 Ingest результатов Gatling/JMeter

**JMeter.** Два канала. Post-run: потоковый парсер JTL (чанками, без загрузки файла в память — JTL на десятки миллионов строк не должен требовать гигабайты RAM). Real-time: Backend Listener (Graphite/InfluxDB-протокол) → приёмник платформы, для live-наблюдения; источником истины для вердикта остаётся post-run парсинг сырого JTL. Сохраняются оба уровня иерархии — Transaction Controllers и вложенные сэмплеры со связью parent→child — для drill-down вклада запросов в деградацию транзакции.

**Gatling.** С версии 3.12 simulation.log — недокументированный бинарный формат, меняющийся между минорными версиями. Поэтому основной канал — Graphite DataWriter Gatling → Graphite-приёмник платформы (протокол plaintext, стабилен годами), а бинарный парсер simulation.log — опциональный модуль, пиннящийся на конкретные версии Gatling с явным fail-closed при неизвестной версии формата.

### 2.2 Коллектор аппаратных метрик (VM)

Адаптивная выборка из общей VictoriaMetrics: в разделяемом мониторинге живут десятки автономных систем, поэтому каждая команда описывает в конфиге маппинг «логическая метрика платформы → PromQL-запрос со своими лейблами» (`cpu_usage` → `rate(node_cpu_seconds_total{cluster="X",mode!="idle"}[1m])`). Платформа запрашивает `/api/v1/query_range` только в окне прогона (с преролом для warmup-фазы), с автоматическим подбором шага под длительность прогона и лимитом на кардинальность ответа. Результат сохраняется как факт прогона — при последующем пересчёте вердикта не зависит от retention исходной VM.

### 2.3 Коллектор APM из ELK

Read-only сервисный аккаунт к ES REST API. Чтение агрегаций из `traces-apm*` / `metrics-apm*` (или их аналогов в форке — схема индексов фиксируется на этапе обследования) в окне прогона: латентность транзакций по сервисам, error rate, топ медленных спанов. Композитные агрегации вместо scroll по сырым документам — платформе нужны распределения, а не терабайты трейсов. Схема-контракт индексов версионируется; расхождение схемы форка с ожидаемой — fail-closed с диагностикой, а не тихие нули.

### 2.4 Нормализация и вердикт

Единое нормализованное представление: бакетированные HDR-гистограммы (интервал × транзакция × фаза) с фазовой разметкой прогона (ramp-up / steady / ramp-down). Все производные метрики (перцентили, throughput, таблицы сравнения) выводятся из гистограмм — это устраняет математически некорректное усреднение перцентилей и позволяет корректно мёржить окна. Warmup вырезается из вердикта по фазовой разметке.

Verdict engine: версионируемый контракт правил (YAML, хранится в Git команды, платформа берёт по ref), пороги SLA + дельты к baseline-прогону с учётом статистической значимости (KS-тест на гистограммах — ±12% на 200 сэмплах и на 2 млн сэмплов не равнозначны). Validity gates до вердикта: полнота данных всех трёх источников, длительность steady-фазы, отсутствие дыр в метриках. Выход — `verdict.json` + запись в append-only журнал решений (кто/что/какая версия правил/хэши входов).

### 2.5 Протокол НТ: цифровой первоисточник и Confluence

Канонический формат протокола — **AsciiDoc**, а не Markdown. Основания: у adoc одна строгая спецификация (Asciidoctor) против зоопарка md-диалектов, то есть детерминированный рендер; полноценные таблицы с объединением ячеек, без которых формальный протокол НТ не собрать; includes и атрибуты для композиции шаблонов. Шаблон протокола — часть конфигурации команды, не кода.

Графики рендерятся детерминированно из нормализованных данных платформы (JVM-рендерер), не скриншотами Grafana: SVG как канонический артефакт (диффабелен, воспроизводим) плюс PNG для инлайн-отображения — Confluence DC не рендерит SVG-вложения инлайн без плагинов.

Публикация: adoc конвертируется в Confluence storage format и публикуется через REST API идемпотентно — страница адресуется по ключу прогона (title + labels: run_id, вердикт, сервис), повторная публикация создаёт новую версию страницы, и нативное версионирование Confluence становится дополнительным аудит-слоем. Графики прикладываются вложениями. Полный воспроизводимый комплект (adoc + SVG/PNG + `verdict.json`) лежит в MinIO; **Confluence — витрина, не источник истины**. Docx из MVP выпадает; при необходимости формальной подписи добавляется как опциональный экспорт из того же adoc позже.

### 2.6 GUI и SLA-редактор

GUI: список прогонов, карточка прогона (вердикт, гейты, таблицы, CDF), сравнение двух прогонов, SLA-редактор.

SLA-редактор — строго структурный, свободное редактирование запрещено по построению. Форма генерируется из JSON Schema контракта правил: метрики выбираются только из реестра логических метрик (того же, что питает маппинг-конфиг коллекторов), компараторы — из фиксированного словаря типов правил (порог, дельта к baseline со значимостью), значения проходят валидацию типов и диапазонов, фазы — из фазовой разметки. Поля raw-YAML в GUI нет ни для редактирования, ни для вставки.

Цикл изменения: черновик в форме → каноническая сериализация в YAML → diff с текущей версией → создание ветки и MR в Git-репозитории правил через API (GitLab/Bitbucket) → merge после ревью человеком. Инвариант «UI не источник истины» сохраняется: GUI — редактор, Git — истина. Вердикты пинятся на commit-hash версии правил. В CI репозитория правил стоит тот же пакет валидаторов, что и в платформе, поэтому «свободная» правка в обход GUI напрямую в Git тоже не пройдёт мимо схемы. Fallback, если сервисная интеграция с Git API не согласуется: внутренний append-only реестр версий правил с двухступенчатым подтверждением (автор ≠ утверждающий) и экспортом в Git; точка решения — этап 0.

## 3. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Ядро | Kotlin 2.x + Spring Boot 3.x | Родной стек команд банка; HdrHistogram — JVM-нативная библиотека (org.hdrhistogram) без потери точности на сериализации |
| Гистограммы | HdrHistogram + сжатые снапшоты (V2 encoding) | Мёржатся без потери, компактны, воспроизводимы |
| Метаданные | PostgreSQL 15+ | Прогоны, вердикты, журнал решений (append-only таблица), версии правил |
| Артефакты | MinIO (S3 API) | Сырые JTL/simulation.log, HDR-снапшоты, готовые протоколы; переживает согласование ИБ проще, чем внешние S3 |
| Доступ к данным | jOOQ + Flyway | Типизированный SQL, миграции как код |
| Парсинг JTL | Собственный потоковый CSV-парсер (Jackson CSV / univocity) | Контракт поведения наследуется от jtl-comparator (нормализация лейблов, auto/tc/samplers) |
| Graphite/Influx intake | Netty-приёмник plaintext-протокола | Общий канал для Gatling DataWriter и JMeter Backend Listener |
| ES-клиент | elasticsearch-java (RO) | Пиннится на версию форка |
| Протоколы | AsciidoctorJ + шаблоны adoc | Одна спецификация против зоопарка md-диалектов, сложные таблицы, includes; детерминированный рендер |
| Графики | JFreeChart/XChart → SVG + PNG | Рендер из нормализованных данных; SVG — канонический артефакт, PNG — для инлайна в Confluence |
| Публикация | Confluence REST API | Идемпотентная публикация по ключу прогона; нативное версионирование страниц как доп. аудит |
| GUI | React + Vite, статика из ядра; SLA-редактор как schema-driven формы | Один контейнер на выходе, без отдельного фронт-деплоя |
| Поставка | Helm chart (OpenShift) + docker-compose (для команд без кластера) | Дистрибутив, а не сервис |

Сознательно **не** в стеке: Kafka (внутри платформы избыточна для модульного монолита — очереди на PostgreSQL advisory/SKIP LOCKED достаточно на объёмах одной команды), собственная TSDB (метрики уже есть у команды), ML-компоненты в контуре вердикта.

## 4. Требования к инфраструктуре

### 4.1 Ресурсы (на одну командную инсталляцию)

| Компонент | vCPU | RAM | Диск | Примечание |
|---|---|---|---|---|
| Core (API + collectors + verdict) | 2, burst 4 | 6 GiB | — | Парсинг потоковый, RAM-профиль плоский |
| Parse worker (Job) | 2–4 burst | 4 GiB | 50 GiB ephemeral | Поднимается на время разбора артефакта |
| PostgreSQL | 2 | 8 GiB | 100 GiB SSD | ~1–2 GiB метаданных на 1000 прогонов |
| MinIO | 2 | 4 GiB | 0.5–2 TiB | Определяется retention сырых JTL (~1–10 GiB/прогон) |
| GUI/ingress | 0.5 | 512 MiB | — | |
| **Итого** | **~10** | **~24 GiB** | **~1 TiB** | Либо одна ВМ 12 vCPU / 32 GiB под docker-compose |

### 4.2 Сетевые доступы (egress наружу закрыт; источники данных — строго read-only, два узко ограниченных write-исключения)

- VictoriaMetrics команды: HTTP `/api/v1/query_range` (порт 8428 / vmselect 8481), RO.
- ES форка ELK: HTTPS 9200, сервисный аккаунт с RO на `traces-apm*`, `metrics-apm*`, индексы ошибок.
- Git (внутренний): чтение репозитория правил по ref; плюс write-исключение №1 — создание веток и MR через API от сервисного аккаунта (merge — только человеком).
- Confluence DC: HTTPS, write-исключение №2 — сервисный аккаунт с правом записи **только в выделенный space**, без права удаления страниц.
- Входящие: Graphite plaintext (2003/tcp) от генераторов нагрузки; HTTPS для GUI/API за SSO банка.

### 4.3 Безопасность и комплаенс

Секреты — в OpenShift Secrets / Vault, не в конфиге платформы. TLS на всех внешних интерфейсах, аутентификация GUI через корпоративный SSO (OIDC/AD). Аккаунты к источникам данных (VM, ELK, чтение правил) — строго read-only: платформа физически не может испортить мониторинг или ELK, что радикально упрощает согласование с ИБ. Два write-канала ограничены по scope и не касаются данных: Confluence — только выделенный space без удаления, Git — только ветки/MR в репозитории правил, слияние выполняет человек. Данные прогонов не покидают namespace команды; между командами переносимы только версии правил и схема вердикта. Заявки на сервисные аккаунты и сетевые доступы подаются на этапе 0 — в банке это самый длинный lead time проекта.

## 5. Этапы и таймлайн

Допущения: 2 разработчика full-time + инженер НТ ~25% на предметную экспертизу и пилот. Этапы 2 и 3 независимы и идут параллельно.

| Этап | Содержание | Длительность | Критерий выхода (fail-closed gate) |
|---|---|---|---|
| **0. Обследование** | Фиксация схемы индексов APM в форке ELK; SLA-контракт первого пилотного сценария в машиночитаемом виде; adoc-шаблон протокола команды; заявки на доступы/аккаунты, включая space Confluence и Git API; решение Git-MR vs внутренний реестр правил | 2 нед | Подписанный SLA-контракт + образцы реальных JTL/simulation.log/индексов; заявки поданы; решение по циклу правок SLA зафиксировано |
| **1. Ingest-ядро** | Потоковый парсер JTL, Graphite-приёмник (Gatling + JMeter BL), модель прогона, фазовая разметка, HDR-нормализация, PostgreSQL+MinIO | 4 нед | Реальный JTL 10M+ строк разбирается в потоке < 2 GiB RAM; перцентили сходятся с эталоном jtl-comparator на контрольных данных |
| **2. Коллектор VM** | Конфиг маппинга метрик, выборка окон, адаптивный шаг, снапшоты аппаратных метрик как факты прогона | 3 нед ∥ | Прогон обогащается метриками из боевой VM команды; повторная выборка даёт идентичный снапшот |
| **3. Коллектор APM/ELK** | ES-адаптер, агрегации транзакций/спанов/ошибок, версионируемый схема-контракт индексов | 3 нед ∥ | Латентности APM за окно прогона сходятся с ручной выборкой в Kibana; чужая схема даёт диагностируемый отказ |
| **4. Verdict engine** | Правила из Git, validity gates, KS-сравнение с baseline, verdict.json, журнал решений | 3 нед | Вердикт воспроизводится байт-в-байт на повторном прогоне engine; выключение любого источника даёт NO_VERDICT |
| **5. Протокол + GUI** | Adoc-генератор + детерминированный рендер графиков, публикация в Confluence, REST API, SPA, SLA-редактор с MR-циклом | 4 нед | Протокол опубликован в Confluence и принят командой вместо ручного; правка SLA из GUI доезжает до Git-MR, после merge вердикт подхватывает новый commit-hash правил |
| **6. Пилот** | 2–3 команды, дистрибутив (Helm + compose), документация развёртывания, стабилизация | 3 нед | Команда разворачивает платформу по документации без участия авторов; ≥10 прогонов с вердиктами и протоколами в Confluence |

**Критический путь:** 0 → 1 → 4 → 5 → 6 = 16 недель; этапы 2–3 параллельно внутри окна этапов 1–4. **Итого: ~16–18 недель (~4–4,5 месяца)** при двух разработчиках; при одном — этапы 2–3 последовательно, ~21–22 недели.

## 6. Риски

| Риск | Вероятность | Митигция |
|---|---|---|
| Бинарный формат simulation.log Gatling меняется между версиями | Высокая | Graphite DataWriter как основной канал; бинарный парсер пиннится на версии, неизвестная версия — fail-closed |
| Схема APM-индексов форка ELK отличается от ванильной | Высокая | Фиксация схемы на этапе 0 по реальным индексам; версионируемый схема-контракт |
| Согласование доступов/аккаунтов ИБ дольше плана | Высокая | Заявки на этапе 0; все аккаунты RO; этапы 1 и 4 не блокируются доступами |
| Baseline-корпуса на старте нет — сравнительные правила «повисают» | Средняя | MVP-вердикт работает на абсолютных SLA-порогах; схема протокола с первого дня проектируется как будущий baseline-корпус (полный provenance: commit/build, хэш конфига сценария, стенд, датасет) |
| Шаблоны протоколов различаются между командами сильнее ожидаемого | Средняя | Шаблон — конфигурация; на пилоте ограничиваемся 2 шаблонами |
| Кардинальность метрик в разделяемой VM | Средняя | Лимиты на размер ответа query_range, явная ошибка вместо OOM |
| Конвертация adoc → Confluence storage format теряет разметку на сложных таблицах | Средняя | Фиксация подмножества adoc-конструкций в шаблоне; golden-тесты рендера на реальном шаблоне команды; графики — PNG-вложениями, не SVG инлайн |
| Сервисная интеграция с Git API не согласуется ИБ | Средняя | Fallback: внутренний append-only реестр версий правил с двухступенчатым подтверждением и экспортом в Git; решение фиксируется на этапе 0 |

## 7. Открытые вопросы (перенос из v0.1 + новые)

2. Передача фазовой разметки из JMeter: маркеры в JTL vs тайминги из плана теста — прототипировать на этапе 1.
3. Минимальный набор детерминированных RCA-правил (не агент) для MVP: стоит ли включать в этап 4 или вынести за MVP.
