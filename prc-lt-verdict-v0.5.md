# ПРК: LT Verdict — платформа анализа результатов нагрузочного тестирования

**Название:** LT Verdict (финализировано; в v0.3 — «NT Verdict»)
**Статус:** проектная концепция (PRC), версия 0.5 — заменяет v0.4 (`prc-lt-verdict-v0.4.md`, сохранена для истории)
**Дата:** август 2026

**Изменения v0.5 (по итогам ревью `k3-prc-review.md` и вычитки):**
- Retention и append-only разведены: append-only — только журнал решений и журнал доставки; сырые артефакты неизменяемы (SHA-256) в течение retention, удаления фиксируются в журнале (§1, §2.2).
- Пакет validity gates: насыщенность генераторов (coordinated omission), пересечение прогонов на одном стенде, profile conformance (плановая интенсивность), clock sync (§2.1, §2.4, §2.6).
- Re-verdict — явная операция: новая версия правил или правка фаз → новая запись журнала со ссылкой на предыдущую; версия фазовой разметки входит в хэши входов журнала (§2.6).
- Регистрация дополнена: плановая интенсивность, класс прогона (official/adhoc), comparability key (сценарий × стенд × датасет × профиль нагрузки); TTL для непрошедших прогонов (§2.1).
- Операции восстановления FAILED_*: retry parse / re-collect / force-finalize (§2.2).
- Протокол для NO_VERDICT — явная часть этапа 5 (§2.7).
- Ожидаемый SHA-256 артефакта декларируется клиентом при инициации загрузки (§2.2).
- Уточнён версионный роутинг парсера: в бинарном формате версия встроена в Run-запись; текстовый формат 3.9.5–3.12 идентичен и валидируется по структуре записей (§2.3).
- InfluxDB-приёмник (line protocol) для live-view — точка решения на этапе 0 (§2.3, §3).
- Вердикт считается только по steady-фазе; warmup и ramp-down вырезаются по фазовой разметке (§2.6).
- Baseline на MVP — ручное назначение по comparability key; автостарение и защита от ratcheting — post-MVP (§2.6).
- Явно отложены за границы MVP: PII/secret sanitization на ingest, уведомления/вебхуки, shadow-режим калибровки, авто-старение baseline (§1).
- Сроки переведены в разряд ориентировочных: основная единица планирования — критерий выхода этапа; разработка ведётся с активным использованием AI-ассистента (§5).
- Исправления вычитки: опечатка «Митигция», арифметика итоговой трудоёмкости (нижняя граница этапа 1 поднята до 3 нед, итого 13–16,5), уточнение строки GUI/ingress, GUI вынесен из блока Output на диаграмме.
- Диапазон поддержки Gatling расширен до **3.9–3.15.1, строго OSS**: текстовый парсер (3.9–3.12) и бинарный парсер (3.13–3.15.1) — оба в скоупе MVP; бинарный парсер больше не отложенный модуль. Gatling Enterprise не поддерживается (§2.3).
- **Разработка ведётся вне боевой среды**: доступы к VM/ELK/Git API/Confluence на этапах разработки не требуются и не запрашиваются; интеграции строятся на фикстурах, мок-серверах и локальных аналогах; оформление доступов и боевая сверка — отдельный трек на развёртывании/пилоте (§4.3, §5). Этап 0 сжат до контрактной подготовки на синтетических/локально сгенерированных данных.
- ИИ-треки перенесены **в скоуп MVP**: RCA с ИИ (детерминированные findings-детекторы + локализация + кодовый агент), ИИ-ассистент по настройке, ИИ-анализ/нарратив в протоколах — строго слой интерпретации, после вердикта, асинхронно (новый §2.9; §3–5: новый этап 6 «RCA с ИИ», пилот сдвинут на этап 7; оценки трудоёмкости пересчитаны).

## 1. Назначение и границы

Децентрализованная платформа-дистрибутив для анализа результатов нагрузочного тестирования. Каждая команда разворачивает платформу в собственном контуре. Платформа объединяет три класса данных в единую модель прогона, выносит детерминированный вердикт по версионируемому контракту правил и генерирует формальный протокол НТ.

Источники данных:

1. **Результаты прогонов Gatling / JMeter** — сырые артефакты инструментов (simulation.log, JTL), доставляемые push'ем в ingest API (с генераторов вручную/curl-обёрткой или из Jenkins pipeline). **Gatling — целевой инструмент, строго OSS** (поддержка 3.9–3.15.1: текстовый формат 3.9–3.12, бинарный 3.13–3.15.1). Real-time канал (Graphite/Influx) — только live-наблюдение, не вход вердикта.
2. **Аппаратные метрики** — CPU, память, диски, сеть, GC, пулы соединений из существующей VictoriaMetrics команды. Платформа **не собирает метрики параллельно** — читает окна прогонов из существующего мониторинга.
3. **APM из ELK** — транзакции, спаны и ошибки из индексов Elastic APM (форк ELK), read-only доступ через REST API.

Инварианты (не обсуждаются при реализации): факты → детерминированный вердикт → интерпретация; вердикт воспроизводим побайтово из тех же входов и той же версии правил; fail-closed — неполные данные дают `NO_VERDICT`, а не «зелёный по умолчанию»; конфигурация-как-код, UI не является источником истины; append-only журнал решений и append-only журнал доставки; сырые артефакты неизменяемы и хранятся с SHA-256 в течение retention (TTL), удаления фиксируются в журнале; сырые данные не покидают контур команды (152-ФЗ, PCI DSS).

Вне границ MVP: оркестрация запуска тестов (закладывается контракт регистрации прогона — запуск остаётся ручным или из Jenkins, §2.1), запись в системы мониторинга, Gatling Enterprise (FrontLine) — поддерживается строго OSS, интеграция с CI-гейтами (появляется естественно после стабилизации вердикта), PII/secret sanitization на ingest (hook маскирования — post-MVP; проблема признана: JTL могут содержать payload/ПДн/токены в URL), уведомления и вебхук по завершении анализа (post-MVP; строятся одним компонентом с заделом под Jenkins-гейт), shadow-режим калибровки вердикта на исторических прогонах (post-MVP; метрики успеха пилота при этом собираются с первого дня, §5 этап 7), автоматическое старение baseline и защита от ratcheting (на MVP baseline назначается вручную по comparability key, §2.6).

## 2. Архитектура

Модульный монолит — выбор в пользу простоты дистрибуции: одна команда получает один контейнер ядра, PostgreSQL и выделенный каталог артефактов на диске виртуальной машины (bind mount в контейнер). Модули с жёсткими внутренними контрактами позволяют распилить на сервисы позже.

### 2.1 Жизненный цикл прогона и регистрация (задел под управление запуском)

Прогон — сущность с явным жизненным циклом: `REGISTERED → COLLECTING → COMPLETE → VERDICT | NO_VERDICT` (+ `FAILED_*` на ошибках обработки, + `EXPIRED` для прогонов, не начавшихся в плановом окне).

Регистрация выполняется **до старта теста**: `POST /api/v1/runs` принимает scenario_id, стенд, vcs-commit сборки, хэш конфига сценария, датасет, плановое окно прогона, **границы фаз** (ramp-up / steady / ramp-down — план теста их знает), **плановую интенсивность** (профиль нагрузки — вход gate'а profile conformance, §2.6) и **класс прогона** (`official | adhoc` — фильтр baseline-eligibility и отладочных прогонов из отчётности). Возвращает `run_id` и ingest token. Поле `trigger: manual | jenkins | ci` фиксирует способ запуска. Набор регистрацияционных полей образует **comparability key** (сценарий × стенд × датасет × профиль нагрузки) — основу сопоставимости прогонов при выборе baseline (§2.6) и provenance-каркас будущего baseline-корпуса.

Прогон, так и не вышедший из `REGISTERED` (плановое окно прошло, артефакты не доставлены), помечается `EXPIRED` по TTL с записью в журнал — список прогонов и детекция пересечений окон не засоряются зависшими регистрациями.

Это даёт:

- **Окно для коллекторов** — VM/ELK-адаптеры работают по окну из регистрации (+ преролл для warmup), а не по факту появления файла.
- **Детерминированную фазовую разметку** — фазы приезжают при регистрации, правятся через API/GUI; каждая правка инкрементирует версию разметки, версия входит в хэши входов журнала решений (§2.6); эвристика по throughput — только подсказка в GUI, не вход вердикта (иначе страдает воспроизводимость).
- **Plan-vs-fact** — плановая интенсивность из регистрации сверяется с фактической в validity gates (§2.6).
- **Provenance-каркас** — commit, конфиг, стенд, датасет, класс прогона — с первого прогона.
- **Задел под запуск**: запуск остаётся ручным (с удалённых машин) или из Jenkins — Jenkins-пайплайн это те же два вызова: `register` перед стартом + `upload/finalize` после. Платформа не оркестрирует: ни расписаний, ни управления генераторами, ни агентов.

### 2.2 Ingest API доставки артефактов

`POST /api/v1/runs/{id}/artifacts` — потоковая загрузка чанками через Core в `<artifact-root>/staging` → `finalize` → задача парсинга. Ожидаемый SHA-256 декларируется клиентом при инициации загрузки; при `finalize` Core сверяет фактический хэш с заявленным и атомарно переносит файл в content-addressed каталог `<artifact-root>/objects/sha256/<prefix>/<hash>`; staging и objects находятся на одном файловом томе. Аутентификация по ingest token — артефакт пушится с любой машины обычным curl, без кредов платформы на сторонних хостах. Каталог PostgreSQL связывает прогон с content-hash, повторная загрузка того же содержимого переиспользует существующий объект. Поддерживаются возобновление прерванной загрузки и квоты на размер (превышение — явная ошибка с диагностикой, не тихий обрез). Загрузка через GUI — обёртка над тем же API (fallback для ручного сценария).

Операции восстановления для `FAILED_*`-состояний — первоклассные операции lifecycle: **retry parse** (повторный запуск задачи парсинга без повторной загрузки артефакта), **re-collect** (повторная выборка окна коллекторами — с этапа 2), **force-finalize** (фиксация частично загруженного артефакта с диагностикой, когда генератор умер и полная загрузка невозможна). Прогон, зависший в `COLLECTING`, — штатная ситуация, обрабатываемая этими операциями, а не экзотика.

Пилот работает с одной активной репликой Core. Недоступность или переполнение каталога артефактов останавливает новые загрузки с явной диагностикой; горизонтальное масштабирование ingest и S3-адаптер находятся за границами MVP.

Pull платформой с генераторов (SSH/SMB) и забор из Jenkins artifacts **не строятся**: первое требует кредов и сетевых согласований «платформа → генераторы», второе — кредов к Jenkins API и знания job-структуры; push закрывает оба сценария одним контрактом.

Все артефакты хранятся неизменяемыми с SHA-256 в течение retention; журнал доставки фиксирует, кто и когда что доставил, а также удаления по TTL.

### 2.3 Парсеры результатов прогонов

**Gatling (целевой инструмент, строго OSS; Enterprise вне скоупа).** Основной и единственный канал вердикта — собственный парсер simulation.log; поддерживаемый диапазон — **3.9–3.15.1**. Фактура (проверена по исходникам `gatling/gatling`, теги 3.9.5–3.15.1):

- **Текстовый формат (3.9–3.12).** Строчный формат (tab-separated записи Run/User/Request/Group/Error, абсолютные таймстемпы) **идентичен** между 3.9.5, 3.11.5 и 3.12.0; отличается только упаковка: 3.9.x — каталог с несколькими `.log`, 3.12 — один файл. Один потоковый парсер покрывает диапазон.
- **Бинарный формат (3.13–3.15.1).** Появился в 3.13 и не менялся по 3.15.1 включительно: DataInputStream, big-endian, 5 типов записей, версия Gatling встроена в первую (Run) запись. Бинарный парсер входит в скоуп MVP (исследование формата уже проведено).

Версионный роутинг: для бинарного формата версия Gatling читается из Run-записи файла (известная версия 3.13–3.15.1 — парсинг); для текстового (3.9–3.12) формат между версиями идентичен и валидируется по структуре записей. Неизвестная версия/структура — fail-closed с диагностикой (`NO_VERDICT`, «Gatling X.Y не поддерживается, поддерживаются: …»). Поддержка новой версии = diff ридера в исходниках Gatling (~10 минут) + golden-фикстура.

Оракул валидации — штатный HTML-отчёт Gatling: один и тот же лог прогоняется через отчёт Gatling и через платформу, перцентили и счётчики обязаны совпасть. Иерархия групп (group → request) сохраняется для drill-down — аналог Transaction Controllers JMeter.

**JMeter.** Потоковый парсер JTL (чанками, без загрузки файла в память): JTL на десятки миллионов строк разбирается < 2 GiB RAM и ≤ 5–10 минут на 2 vCPU. Сохраняются оба уровня иерархии — Transaction Controllers и вложенные сэмплеры со связью parent→child. Контракт поведения наследуется от jtl-comparator (нормализация лейблов, auto/tc/samplers); эталон сверки — jtl-comparator на контрольных данных.

**Graphite / Influx (live-view only).** Netty-приёмник plaintext-протокола Graphite (порт 2003) для Gatling DataWriter и JMeter Backend Listener — исключительно live-наблюдение за идущим прогоном. Если у команд JMeter Backend Listener пишет в InfluxDB (выясняется на этапе 0), добавляется приёмник line protocol на отдельном порту. **Не вход вердикта**: live-канал несёт предагрегированные по интервалам значения (count, min/max/mean, заранее настроенные перцентили), из которых нельзя восстановить HDR-гистограммы, корректно смержить окна или провести KS-тест. (В v0.3 Graphite был основным каналом Gatling — исправлено: это противоречило §2.6 «все производные из гистограмм».)

### 2.4 Коллектор аппаратных метрик (VM)

Адаптивная выборка из общей VictoriaMetrics: каждая команда описывает в конфиге маппинг «логическая метрика платформы → PromQL-запрос со своими лейблами». В маппинг включаются **хосты стенда и хосты генераторов нагрузки**: перегруженный генератор даёт мусорные латентности (coordinated omission) и ложный вердикт — его CPU/GC в окне прогона проверяются validity gate'ом (§2.6). Платформа запрашивает `/api/v1/query_range` только в окне прогона (из регистрации, §2.1, с прероллом), с автоподбором шага под длительность и лимитом на кардинальность ответа. Результат сохраняется как факт прогона — пересчёт вердикта не зависит от retention исходной VM.

### 2.5 Коллектор APM из ELK

Read-only сервисный аккаунт к ES REST API. Чтение агрегаций из `traces-apm*` / `metrics-apm*` (или аналогов в форке — схема фиксируется на этапе 0) в окне прогона: латентность транзакций по сервисам, error rate, топ медленных спанов. Композитные агрегации вместо scroll по сырым документам. Схема-контракт индексов версионируется; расхождение — fail-closed с диагностикой.

### 2.6 Нормализация и вердикт

Единое нормализованное представление: бакетированные HDR-гистограммы (интервал × транзакция × фаза) с фазовой разметкой из регистрации прогона (детерминированной, §2.1). Все производные метрики (перцентили, throughput, таблицы сравнения) выводятся из гистограмм — устраняется некорректное усреднение перцентилей, окна мёржатся корректно. **Вердикт считается только по steady-фазе**: warmup и ramp-down вырезаются по фазовой разметке.

Verdict engine: версионируемый контракт правил (YAML, хранится в Git команды, платформа берёт по ref), пороги SLA + дельты к baseline-прогону со статистической значимостью. KS-сравнение выполняется на бакетированных ECDF из HDR-гистограмм; в спецификации этапа 4 фиксируются: точная формулировка статистики, поведение при малых N и **политика множественных сравнений** (ограничение набора сравниваемых метрик или поправка — десятки метрик × десятки транзакций иначе дадут гарантированные ложные срабатывания).

Validity gates до вердикта (fail-closed пакет):

- полнота данных всех трёх источников;
- длительность steady-фазы не ниже минимальной;
- отсутствие дыр в метриках;
- **насыщенность генераторов** — CPU/GC хостов генераторов в окне прогона (§2.4): перегруженный генератор → coordinated omission → вердикт недостоверен;
- **отсутствие конкурентных прогонов** — пересечение окон двух прогонов на одном стенде детектируется по регистрациям (§2.1): смешанные метрики делают оба вердикта мусорными;
- **profile conformance** (анти-Goodhart) — отклонение фактической интенсивности от плановой (§2.1) сверх конфигурируемого порога → `NO_VERDICT`: «утихомиренный» тест не должен получать зелёный вердикт;
- **clock sync** — скью часов генераторов/VM/ELK/платформы сверх допуска → `NO_VERDICT` с диагностикой: оконные коллекторы молча предполагают NTP-синхронность, скью 30 с = смещённые окна без единой ошибки.

Выход — `verdict.json` + запись в append-only журнал решений (кто/что/какая версия правил/**хэши входов, включая версию фазовой разметки** — правка фаз через API/GUI является входом вердикта); UPDATE/DELETE на таблице журнала запрещены на уровне роли БД.

**Re-verdict — явная операция**: пересчёт прогона с новой версией правил или исправленной фазовой разметкой создаёт новую запись журнала со ссылкой на предыдущий вердикт; старые вердикты не перезаписываются. Инфраструктура re-verdict — основа будущего dry-run правил (прогон новой версии правил по последним N прогонам).

Baseline на MVP: baseline-прогон назначается **вручную** по **comparability key** (сценарий × стенд × датасет × профиль нагрузки, §2.1) — сравнение имеет смысл только для сопоставимых прогонов. Автоматическое старение baseline и защита от ratcheting (пошаговая деградация через сравнение с «последним зелёным») — post-MVP.

`verdict.json` сериализуется канонически: сортировка ключей, фиксированные форматы чисел, **без wall-clock timestamps и случайных UUID** — иначе инвариант «побайтовой воспроизводимости» непроверяем. Поле `findings` заполняется детерминированными findings-детекторами (этап 4, §2.9) — детерминизм детекторов сохраняет инвариант побайтовой воспроизводимости.

### 2.7 Протокол НТ: цифровой первоисточник и Confluence

Канонический формат протокола — **AsciiDoc** (Asciidoctor): одна строгая спецификация, детерминированный рендер, полноценные таблицы с объединением ячеек, includes и атрибуты для композиции шаблонов. Шаблон протокола — часть конфигурации команды, не кода.

Графики рендерятся детерминированно из нормализованных данных платформы (JVM-рендерер): SVG как канонический артефакт (диффабелен, воспроизводим) + PNG для инлайн-отображения (Confluence DC не рендерит SVG-вложения инлайн без плагинов).

Публикация: adoc конвертируется в Confluence storage format и публикуется через REST API идемпотентно — страница адресуется по ключу прогона (title + labels: run_id, вердикт, сервис), повторная публикация создаёт новую версию страницы; нативное версионирование Confluence — дополнительный аудит-слой. Графики — вложениями. Полный воспроизводимый комплект (adoc + SVG/PNG + `verdict.json`) лежит в каталоге артефактов; **Confluence — витрина, не источник истины**. Docx — опциональный экспорт из того же adoc, после MVP.

Отдельный обязательный артефакт этапа 5 — **протокол для `NO_VERDICT`**: самый востребованный протокол — когда вердикта нет. Генерируется тем же генератором из диагностики validity gates: какие гейты не пройдены, каких данных не хватило, рекомендуемые действия.

Детерминированная часть протокола побайтово воспроизводима; ИИ-секции (§2.9) включаются как отдельно помеченные («AI-generated, требует подтверждения») и требованию воспроизводимости не подлежат.

### 2.8 GUI и SLA-редактор

GUI: список прогонов (с состояниями lifecycle), карточка прогона (вердикт, гейты, таблицы, CDF, live-графики Graphite/Influx-канала для идущего прогона, ИИ-разбор прогона в режиме вопросов — §2.9), сравнение двух прогонов, SLA-редактор.

SLA-редактор — строго структурный, свободное редактирование запрещено по построению. Форма генерируется из JSON Schema контракта правил: метрики — только из реестра логических метрик, компараторы — из фиксированного словаря типов правил, значения проходят валидацию типов и диапазонов, фазы — из фазовой разметки. Поля raw-YAML в GUI нет.

Цикл изменения: черновик в форме → каноническая сериализация в YAML → diff с текущей версией → ветка и MR в Git-репозитории правил через API (GitLab/Bitbucket) → merge человеком. Инвариант «UI не источник истины» сохраняется. Вердикты пинятся на commit-hash версии правил. В CI репозитория правил — тот же пакет валидаторов, что и в платформе. Fallback, если интеграция с Git API не согласуется: внутренний append-only реестр версий правил с двухступенчатым подтверждением (автор ≠ утверждающий) и экспортом в Git; точка решения — этап 0.

Ассистент настройки ИИ (§2.9) ускоряет заполнение форм: кандидаты маппинга из discovery по VM, пороги по статистике baseline-корпуса, генерация начального SLA-контракта и adoc-шаблона — результат только через структурные формы с MR-циклом.

### 2.9 ИИ-слой: интерпретация, RCA, ассистирование настройке

ИИ-треки входят в скоуп MVP, но живут строго в слое интерпретации: инвариант «факты → детерминированный вердикт → интерпретация» сохраняется — ИИ не влияет на вердикт, выполняется асинхронно после него, весь ИИ-вывод помечен «AI-generated, требует подтверждения» и журналируется с версией модели. В verdict.json ИИ-вывод не попадает (кроме `findings` от детерминированных детекторов).

1. **RCA с ИИ** — объяснение вердикта до строки кода. Пайплайн: детерминированные findings-детекторы (change-point на окне, GC↔p99, насыщение пулов соединений↔latency, error fingerprinting) пишут в `findings` (§2.6) → детерминированная локализация: спаны и стектрейсы APM несут service.name, transaction.name, class/method, file:line → маппинг service→repo в конфиге → RO-клон кода SUT на vcs-commit (из регистрации, §2.1) в эфемерном контейнере с закрытым egress → ИИ-агент (headless Gigacode CLI в sandbox-контейнере) анализирует **только узкий контекст** (класс + соседи + деплой-конфиги) → ранжированные гипотезы со ссылками file:line. **Только статика**: без сборки и исполнения чужого кода; лимиты CPU/RAM/времени. Спан без маппинга → честное «код недоступен». Дешёвый первый шаг — локализация по спанам/стектрейсам работает без доступа к коду и даёт «где» до того, как агент даст «почему».
2. **Ассистент настройки ИИ** — снижение стоимости onboarding'а новых команд. Детерминированный discovery `ltv init` (опрос VM на доступные метрики/лейблы, кандидаты маппинга, стартовый SLA-контракт и adoc-шаблон) + ИИ-слой (выбор маппинга, порогов по статистике baseline-корпуса, генерация шаблонов). Результат — только через структурные формы SLA-редактора с MR-циклом (§2.8): инвариант «UI не источник истины» сохраняется.
3. **ИИ-анализ и нарратив в протоколах** — детерминированные секции анализа в протоколе (error fingerprinting: топ ошибок по типам/сообщениям; trend view) + отдельно помеченные ИИ-секции в adoc (анализ прогонов, выводы); вход — verdict.json + findings + факты прогона; опционально — ИИ-разбор прогона в GUI (режим вопросов по карточке прогона).

Общие требования к ИИ-CLI: headless-режим (stdin/stdout, exit codes, timeout/cancel), отсутствие внешнего egress из sandbox, аудит версии модели, журналирование prompt/output (опросник п.12–14). Разработка вне боевой среды: фикстуры RCA — синтетический репозиторий SUT с planted-дефектами (локальный git).

## 4. Требования к инфраструктуре

### 4.1 Ресурсы (на одну командную инсталляцию)

| Компонент | vCPU | RAM | Диск | Примечание |
|---|---|---|---|---|
| Core (API + ingest + collectors + verdict + parsing) | 2, burst 4 | 6 GiB | 0.5–2 TiB на отдельном томе | Каталог артефактов монтируется в контейнер; объём определяется retention (~1–10 GiB/прогон) |
| PostgreSQL | 2 | 8 GiB | 100 GiB SSD | ~1–2 GiB метаданных на 1000 прогонов |
| Ingress | 0.5 | 512 MiB | — | TLS-терминация и раздача SPA-статики GUI (сборка раздаётся ядром, отдельного GUI-контейнера нет) |
| AI sandbox (RCA-агент, ИИ-CLI) | 2 | 4 GiB | — | Эфемерные контейнеры, egress закрыт, лимиты CPU/RAM/времени; точные лимиты по паспорту CLI (опросник п.14) |
| **Итого** | **~7–9** | **~19 GiB** | **0.5–2 TiB + 100 GiB SSD для PostgreSQL** | Рекомендуемая ВМ: 12 vCPU / 32 GiB; каталог артефактов — отдельный том/bind mount |

### 4.2 Сетевые доступы (egress наружу закрыт; источники — строго read-only, два узких write-исключения)

- VictoriaMetrics команды: HTTP `/api/v1/query_range` (8428 / vmselect 8481), RO.
- ES форка ELK: HTTPS 9200, сервисный аккаунт RO на `traces-apm*`, `metrics-apm*`, индексы ошибок.
- Git (внутренний): чтение репозитория правил по ref; write-исключение №1 — ветки и MR через API от сервисного аккаунта (merge — только человеком).
- Git SUT (внутренний): RO-клонирование на коммит для RCA-агента (§2.9) — эфемерное, без сборки и исполнения.
- Confluence DC: HTTPS, write-исключение №2 — сервисный аккаунт с записью **только в выделенный space**, без удаления страниц.
- Входящие: HTTPS 443 (GUI/API/**ingest push** — аутентификация по ingest token, scope ограничен конкретным run_id) за SSO банка; Graphite plaintext 2003/tcp и (при решении этапа 0) Influx line protocol от генераторов (только live-view).

### 4.3 Безопасность и комплаенс

Секреты — в OpenShift Secrets / Vault. TLS на всех внешних интерфейсах, аутентификация GUI через SSO (OIDC/AD). Аккаунты к источникам — строго RO. Ingest token — одноразовый scoped-креденшел на доставку артефактов конкретного прогона, не даёт доступа к данным. Каталог артефактов монтируется только в Core, доступен сервисному пользователю, запрещает исполнение файлов и размещается на шифруемом томе; retention и резервное копирование настраиваются отдельно от PostgreSQL. Два write-канала (Confluence space, Git MR) ограничены по scope и не касаются данных. Данные прогонов не покидают контур команды; между командами переносимы только версии правил и схема вердикта. Оформление сервисных аккаунтов и доступов выполняется **отдельно, вне скоупа разработки**: разработка ведётся вне боевой среды (фикстуры, мок-серверы, локальные аналоги — локальный git как репозиторий правил, локальные прогоны Gatling OSS как источник эталонных артефактов), доступы к боевым системам требуются только на развёртывании/пилоте. Sandbox-контейнеры ИИ-агентов (§2.9): egress закрыт, лимиты CPU/RAM/времени, только статика (без сборки и исполнения чужого кода); prompt/output журналируются с версией модели.

## 5. Этапы и таймлайн

**Ресурсная модель:** 1 инженер НТ, part-time (проект совмещается с текущими задачами) + фронтир AI-ассистент разработки (основной объём кода, тестов и документации — AI; инженер — постановка, ревью, интеграции, предметная экспертиза); точечные консультации администраторов источников данных (VictoriaMetrics, ELK) и DevOps (OpenShift, дистрибутив).

**Принцип планирования:** разработка ведётся с активным использованием AI, поэтому основная единица планирования — **этап с fail-closed критерием выхода**, а не календарная дата. Трудоёмкости ниже — ориентир для планирования занятости и доступов; порядок этапов и зависимости постоянны. Ориентировочная цель: пилот на одной команде — до конца января 2027 (достигается при нижних границах оценок и своевременных доступах; жёстким ограничением не является).

Принятие протокола командой — на развёртывании |
| **6. RCA с ИИ** | Локализация по спанам/стектрейсам, маппинг service→repo, RO-клон SUT на vcs-commit (эфемерный контейнер, только статика), агент Gigacode headless на узком контексте, гипотезы с file:line, аудит; фикстуры — синтетический репозиторий SUT с planted-дефектами | 2–3 нед | На синтетическом репозитории SUT агент находит planted-дефект и даёт гипотезу со ссылкой file:line, инженер подтверждает; ИИ строго после вердикта, вердикт неизменен. Может идти параллельно этапу 5 |
| **7. Дистрибутив и пилот на одной команде** | Дистрибутив (Helm + compose), документация развёртывания, боевая интеграция (доступы оформляются отдельным треком, вне скоупа разработки), стабилизация, сбор метрик успеха пилота (время разбора, доля протоколов без ручных правок) | 1–1,5 нед | Команда разворачивает платформу по документации без авторов; ≥10 прогонов с вердиктами и протоколами. Пилот — одна команда; расширение — после MVP |

**Итого инженерная трудоёмкость (ориентировочно): 16,5–22 FTE-недели.**
Первый вердикт по реальному прогону (этапы 0–4): **9,5–12,5 FTE-недель**.

Календарная длительность зависит от квоты времени на проект (ориентир):

| Квота | Первый вердикт | Полный MVP (инженерная часть) |
|---|---|---|
| 50% (~20 ч/нед) | ≈ 5–6 мес | ≈ 8–11 мес |
| 30% (~12 ч/нед) | ≈ 8–10,5 мес | ≈ 13,5–18 мес |

Критический путь: 0 → 1 → (2, 3 последовательно, на фикстурах) → 4 → 5 → 6 → 7; этап 6 может частично перекрываться с этапом 5 (зависит от этапов 3–4, не от 5). Разработка не зависит от доступов к боевым системам; интеграционные сюрпризы (форк ELK, Confluence storage format) проявляются на развёртывании — резерв на их разбор заложен в вилки этапов 3, 5 и в этап 7.

## 6. Риски

| Риск | Вероятность | Митигация |
|---|---|---|
| Единственный исполнитель, part-time: конкуренция с текущими задачами, bus factor | Высокая | AI несёт основную кодовую нагрузку; все решения фиксируются документами (PRC, протокол решений); инкрементальные demo-вердикты; защищённая квота времени — через руководство |
| Доступы и инфраструктура не готовы к моменту развёртывания | Средняя | Разработка от доступов не зависит (фикстуры/моки/локальные аналоги); оформление доступов — отдельный трек перед пилотом; все аккаунты RO |
| Расхождение фикстур и боевой среды (схема форка ELK, форматы ответов VM/Confluence) | Средняя | Версионируемые схема-контракты, fail-closed с диагностикой; контрактные тесты против записанных ответов; сверка на развёртывании |
| Схема APM-индексов форка ELK отличается от ванильной | Высокая | Фиксация схемы на этапе 0; версионируемый схема-контракт; fail-closed |
| Формат simulation.log — внутренний API Gatling, может измениться в новой версии | Средняя (исследовано) | Версия встроена в бинарный файл → fail-closed роутинг; текстовый формат идентичен 3.9–3.12 и валидируется по структуре; бинарный стабилен 3.13–3.15.1; проверка новой версии = diff исходников (~10 мин) + фикстура |
| Baseline-корпуса на старте нет | Средняя | MVP-вердикт на абсолютных SLA-порогах; baseline назначается вручную по comparability key (§2.6); provenance при регистрации формирует корпус с первого прогона |
| Ложный вердикт из-за перегруженного генератора / конкурентного прогона / «утихомиренного» теста / скью часов | Средняя | Пакет validity gates (§2.6): генераторы, пересечение окон, profile conformance, clock sync |
| Шаблоны протоколов различаются между командами | Средняя | Шаблон — конфигурация; на пилоте ≤2 шаблонов |
| Кардинальность метрик в разделяемой VM | Средняя | Лимиты на размер ответа query_range, явная ошибка вместо OOM |
| Переполнение или потеря локального каталога артефактов | Средняя | Отдельный том, квоты загрузки, мониторинг свободного места, настраиваемый retention и резервное копирование; при недоступности — явный отказ ingest |
| Конвертация adoc → Confluence storage format теряет разметку | Средняя | Фиксированное подмножество adoc в шаблоне; golden-тесты рендера; графики — PNG-вложениями |
| Сервисная интеграция с Git API не согласуется ИБ | Средняя | Fallback: внутренний append-only реестр версий правил, решение — этап 0 |
| Расползание скоупа «дешёвыми» дополнениями | Средняя | Скоуп MVP зафиксирован v0.5 (включая ИИ-треки §2.9); новые идеи — в бэклог post-MVP и следующую версию PRC, не в текущие этапы |
| Галлюцинации ИИ-агента: правдоподобный шум вместо причины | Высокая | Детерминированная локализация до агента (только узкий контекст); ранжированные гипотезы со ссылками file:line, «AI-generated, требует подтверждения», подтверждает инженер |
| Headless ИИ-CLI (Gigacode/Qwen) недоступен или ограничен в контуре | Средняя | Опросник п.12–14 до старта этапов 5–6; fallback: детерминированные findings + локализация без агента («где» работает без «почему») |
| Trust surface: RO-доступ к Git SUT для RCA | Средняя | Клонирование только RO на коммит, эфемерный контейнер, egress закрыт, только статика; без сборки/исполнения чужого кода |

## 7. Открытые вопросы

1. **InfluxDB**: пишет ли JMeter Backend Listener пилотной команды в InfluxDB? Отложено до развёртывания — разработка не зависит; если да, приёмник line protocol на отдельном порту добавляется отдельным модулем (live-view only).
2. Ролевая модель SLA-редактора: кто утверждает MR с правкой правил, нужен ли two-man rule для прод-контрактов.
3. Структура space в Confluence: страница на прогон vs дерево «сервис → сценарий → прогоны», политика архивирования.
4. Глубина биндинга переопределений метрик (per-система vs per-сценарий) — решить на этапе 0 по первому SLA-контракту.
5. **Доставка крупных JTL с удалённых генераторов** (вопрос развёртывания, разработку не блокирует). Допускается ли установка подписанного uploader CLI на машины генераторов и Jenkins-агенты? Если да — определить порядок установки и обновления, сетевой маршрут к Core, разрешение chunked/resumable upload, TLS/proxy-ограничения и максимальный размер артефакта. Если нет — выбрать согласованный канал передачи файлов размером 0,5–3 ГБ через Core ingress или Jenkins.
6. **Headless ИИ-CLI** (требуется для ИИ-треков MVP, этапы 5–6): выбор CLI (Gigacode/Qwen Code), headless-режим (stdin/stdout, exit codes, timeout/cancel), sandbox и egress-ограничения, аудит версии модели, хранение prompt/output (опросник п.12–14).

Закрытые в v0.5 вопросы: ИИ-треки (RCA с ИИ, ассистент настройки, ИИ-анализ протоколов) включены в скоуп MVP как слой интерпретации (§2.9); Gatling — **строго OSS**, Enterprise не поддерживается; диапазон поддержки 3.9–3.15.1, бинарный парсер (3.13+) в скоупе MVP; разработка вне боевой среды — интеграции на фикстурах и моках, доступы оформляются отдельным треком на развёртывании; retention/append-only разведены (§1, §2.2); вебхук и уведомления — явно post-MVP одним компонентом (бывший вопрос v0.4 №2); re-verdict — явная операция с версией фаз в хэшах входов (§2.6); протокол NO_VERDICT — в этапе 5 (§2.7); класс прогона и плановая интенсивность — при регистрации (§2.1); вердикт только по steady-фазе (§2.6). Закрытые в v0.4 вопросы (из v0.3): имя продукта — **LT Verdict**; фазовая разметка — детерминированная, при регистрации (§2.1); версии Gatling — 3.9.5/3.12, текстовый парсер (§2.3); способ доставки результатов — push через ingest API (§2.2); минимальные RCA-правила — за границами MVP, поле `findings` зарезервировано (§2.6).
