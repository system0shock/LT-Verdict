# LT Verdict — протокол решений (2026-07-20)

Контекст: ревью PRC v0.3 (`prc-nt-analysis-platform.md`), переоценка сроков под «1 разработчик + фронтир-модель», дополнения к скоупу. Название продукта: **LT Verdict**.

## Принятые решения

- **D1. Amendments R1–R9 к PRC приняты** (см. ниже), кроме R3 — пересмотрен по итогам исследования формата simulation.log (см. D5).
- **D2. Получение результатов — push через ingest API.** `POST /api/v1/runs/{id}/artifacts` (chunked upload → MinIO staging → finalize → задача парсинга), аутентификация по run token. GUI-upload — fallback поверх того же API. Pull с генераторов и забор из Jenkins artifacts — не строим. Дедупликация по content-hash, resume загрузки, квоты.
- **D3. Задел под управление запуском (без оркестрации).** Run registration API (`POST /api/v1/runs`: scenario_id, стенд, vcs-commit, датасет, плановое окно, границы фаз) → run_id + ingest token; lifecycle прогона `REGISTERED → COLLECTING → COMPLETE → VERDICT | NO_VERDICT (+FAILED_*)`; Jenkins = тот же контракт (register + upload/finalize из pipeline); поле `trigger: manual|jenkins|ci` в модели прогона. Не строим: оркестрацию генераторов, расписания, агентов.
- **D4 (пересмотрено ×2). Целевой срок: пилот на одной команде — до конца января 2027.** Трудоёмкость: 13–16 FTE-недель (первый вердикт, этапы 0–4: 8,5–11). Помесячно: авг–сен — этапы 0–1; сен–окт — этапы 2–3; ноя — этап 4; дек — этап 5; янв 2027 — этап 6. Достижимо при занятости ~50%; пилот ограничен одной командой. Ресурсная модель: 1 инженер НТ part-time + AI-ассистент + точечные консультации администраторов (VM, ELK) и DevOps. **ИБ-согласования, выдача доступов и график пилотной команды исключены из оценки** (заявки — в первую неделю, параллельно; коллекторы до выдачи доступов — на фикстурах).
- **D5. Gatling — целевой инструмент. Основной канал — парсер simulation.log, НЕ Graphite.** Команды используют **3.9.5 и 3.12 → обе текстовые**: строим текстовый парсер (проще бинарного, ~2–3 дня). Бинарный парсер (3.13+) — отложенный модуль: добавляем, когда первая команда обновится; версия встроена в файл, роутинг fail-closed. Graphite DataWriter — только live-наблюдение, не вход вердикта.
- **D6. Оба канала в MVP:** Gatling (simulation.log) и JMeter (JTL) строятся в этапе 1.

## Исследование формата simulation.log Gatling (по исходникам gatling/gatling)

| Версия | Формат simulation.log |
|---|---|
| ≤ 3.11 | Текстовый (tab-separated), несколько `.log` файлов на прогон |
| 3.12 | Текстовый, один файл |
| 3.13 – 3.15.1 (текущая) | **Бинарный** (DataInputStream, big-endian). Reader идентичен 3.13→3.15 — формат стабилен с момента введения |

**Важно: строчный формат текстовых версий идентичен 3.9.5 ↔ 3.11.5 ↔ 3.12.0** (проверено по `LogFileReader.scala` соответствующих тегов: те же `Raw*Record`-экстракторы, те же позиции полей). Различается только упаковка: 3.9.5 — каталог с несколькими `.log`, 3.12 — один файл. ⇒ **Один текстовый парсер покрывает обе целевые версии**, отличается лишь file discovery.

Факты по бинарному формату (из `LogFileReader.scala`):
- 5 типов записей (1-байтный header): Run/User/Request/Group/Error; Run — всегда первая.
- **Версия Gatling встроена в Run-запись** → fail-closed роутинг парсера тривиален.
- Таймстемпы — int-дельты от старта прогона; строки — length-prefixed + байт JDK compact-string coder (LATIN1/UTF16); кэш строк по индексу.
- Assertions — boopickle-блобы, пропускаем по length-prefix (не нужны).
- Сам Gatling версионно-лочит файл (assert на exact version) — формат внутренний «by design», но фактически не менялся 3 минорные версии.
- Точка слома в PRC указана неверно: бинарный переход — 3.12→3.13, не «с 3.12».

Вывод: **текстовый парсер (целевые версии 3.9.5/3.12) — ~2–3 дня** с golden-фикстурами; бинарный (3.13+) — ~3–5 дней, отложен до первой команды на 3.13+. Оракул валидации — собственный HTML-отчёт Gatling. Поддержка новой версии = diff reader-исходников (≈10 мин) + фикстура. Точка слома в PRC указана неверно: бинарный переход — 3.12→3.13, не «с 3.12».
