- Производитель pod-view (платформа, срез P2d): `python -m tools.pod_view_adapter`
  строит `pod-view.v1` из Prometheus-совместимого источника (живой режим,
  проход 2: файл подаётся в анализ вместе со снимком ресурсов, онлайн-сбор с
  `pod_view` не сочетается) и, с `--synthetic spec.json`, выпускает
  детерминированный набор без стенда: `load.jtl`, `resource-snapshot.json` с
  меткой `arm`, `pod-view.json` и `expected.json` (эталон `max`/`mean`/`last`
  по строкам и заложенный эффект сценария, считается закрытой формулой, а не
  запуском LT Verdict). Сценарии: `balanced`, `leak-on-arm-b-pod-b2`,
  `throttle-on-one-pod`. Адаптер ставит колонки по правым границам интервала,
  пропуск и `NaN` пишет как `null`, округляет значение до 12 байт без
  экспоненты, выбирает поды до файла (`--select worst:<metric>:<limit>`) с
  честным `coverage` и отказывает, если файл не уложился бы в пределы ядра.
  Только стандартная библиотека; ядро, схема `pod-view.v1`, API и интерфейс не
  меняются. Набор метрик живого режима (CPU и память к limit по контейнеру,
  throttling, CPU пода) выбран как рабочее решение среза и на реальном
  OpenShift не проверялся; проверка авторизации источника не входит.
