# Каталог корреляционных гипотез v1

Каталог (`correlation-catalog.v1.json`, схема `correlation-catalog.schema.json`)
это версионируемый файл данных: фиксированный до просмотра данных список
гипотез по исходам нагрузки. Ядро каталог не знает и не читает. Внешний
инструмент `tools/correlation_catalog.py` разворачивает каталог в обычный
`correlation-plan.v1`; формат плана, evidence и контракты ядра не меняются
(ADR 0022, Д5).

## Структура каталога

Корень: `schema_version` (`correlation-catalog.v1`), `families`,
необязательный `event_families`.

Семья (`families[]`) это один исход и список причин:

| Поле | Смысл |
| --- | --- |
| `id` | Идентификатор семьи (до 128 байт), входит в `id` пары |
| `outcome` | `response_time_p95_ms`, `error_rate` или `throughput_rps`; исходы p99 и паузы GC контрактом ядра не поддерживаются и в каталог не входят. Один исход, одна семья |
| `min_load_delta` | `min_load_delta` пары, больше 0 |
| `hypotheses` | От 2 до 16 гипотез |

Гипотеза (`hypotheses[]`), все поля обязательны:

| Поле | Смысл |
| --- | --- |
| `id` | Идентификатор в семье |
| `kind` | `cause` или `control`. В семье есть хотя бы одна причина и одна контрольная гипотеза (CPU генератора нагрузки): она не должна срабатывать, срабатывание означает артефакт измерения |
| `scope` | `service` (ряд сервиса исхода), `downstream` (ряд нижестоящего сервиса по объявленному ребру), `load_generator` (ряд с ролью `generator`) |
| `metric`, `unit` | Имя метрики и единица ряда снимка, по которым ряд ищется и проверяется |
| `expected_sign` | `positive`, `negative` или `either`, объявляется заранее |
| `max_lag_cells` | Лаг в ячейках, от 0 до 4 (в плане `max_lag_ms` равен лагу, умноженному на `step_ms` снимка) |
| `min_abs_effect` | Порог эффекта, от 0,3 до 1 |
| `min_resource_delta` | `min_resource_delta` пары, в единице ряда, больше 0 |
| `controls` | До 4 из `target_rps`, `concurrency`: контроли, постоянные внутри стадии. `achieved_rps` в каталоге не используется: он меняется внутри стадии, а контроль, который ядро действительно использует, делает пару `UNAVAILABLE` (`GENUINE_PARTIAL_UNCALIBRATED`) |

`event_families[]` (`id`, `note`) описывает семьи-события без пар. В версии 1
это `oom-restarts`: OOM и перезапуски события, а не ряд; корреляция неприменима,
используются порядок эпизодов и тренды.

Одна пара `(scope, metric)` в семье встречается один раз: два описания одного ряда
дали бы дубль пары, который ядро отвергает (`DUPLICATE_PAIR`).

## Развёртыватель

```text
expand(catalog, snapshot, stages, outcome, topology_edges)
    -> (correlation-plan.v1 | None, skipped)
```

- `snapshot`: `resource-snapshot.v1`. Читайте файл с `parse_float=Decimal`
  (командная строка так и делает), иначе семантический хэш снимка может разойтись
  с ядром на длинных значениях.
- `stages`: идентификаторы окон снимка (стадии); они попадают в `window_ids` каждой
  пары. Список непустой, без повторов, каждое окно есть в `snapshot.windows`
  (если окна в снимке объявлены), иначе ошибка `STAGES_INVALID` или
  `STAGE_NOT_FOUND`.
- `outcome`: `{"load_metric", "service"}` исхода, для которого семья создаётся.
  Правило активации (нарушение SLA или найденный эпизод по исходу) вычисляет
  вызывающая сторона и передаёт `None`, если оно не сработало; тогда плана нет.
- `topology_edges`: объявленный вручную список рёбер `(вызывающий, вызываемый)`.
  Граф в ядро не передаётся; в плане остаётся только текст `topology_basis`.

Правила:

1. Ряд ищется по `metric`, `entity` (сервис исхода или вызываемый сервис) и
   роли (`system`, для генератора `generator`). Ряды платформенных профилей уже
   сведены к худшему поду сервиса (ADR 0018). Если подходящих рядов несколько,
   гипотеза пропускается (`SERIES_AMBIGUOUS`): под не выбирается по данным и
   по корреляции с исходом. Значения рядов не читаются.
2. Единица ряда должна совпасть с `unit` каталога, иначе `UNIT_MISMATCH`:
   пороги `min_resource_delta` заданы в этой единице.
3. Для контроля `target_rps` (единица `requests/s`) и `concurrency` (единица
   `count`) в снимке должен быть ровно один ряд с `metric`, равным названию
   контроля; его `id` идёт в `series_id`. Иначе гипотеза пропускается
   (`CONTROL_SERIES_MISSING`, `CONTROL_SERIES_AMBIGUOUS`). Цена: без таких рядов
   в снимке в семье остаются только гипотезы без контроля (контрольная гипотеза), и
   плана нет. Контроль, меняющийся внутри стадии, отключает находку этой пары
   на стороне ядра (`GENUINE_PARTIAL_UNCALIBRATED`).
4. Гипотеза `downstream` даёт по одной паре на каждое объявленное ребро с
   вызывающим, равным сервису исхода. Нет ребра: `TOPOLOGY_EDGE_MISSING`; нет ряда
   вызываемого сервиса: `SERIES_MISSING` для `<id>@<вызываемый>`.
5. Лаг, умноженный на `step_ms`, больше 60 000 мс (предел схемы плана):
   `LAG_EXCEEDS_PLAN_LIMIT`, гипотеза пропускается, а не обрезается.
6. Нет метрики в снимке: гипотеза выключается и в семью не входит. Размер семьи
   для Holm равен числу пар плана, он воспроизводим.
7. Если после пропусков не осталось ни одной причины (только контрольная
   гипотеза или ничего), плана нет (`None`), контрольная гипотеза получает
   `ONLY_CONTROL_LEFT`. Исход не из каталога: `OUTCOME_NOT_IN_CATALOG`; семья не
   активирована: `OUTCOME_NOT_ACTIVATED`.
8. Больше 16 пар после раскрытия рёбер: ошибка `FAMILY_SIZE_EXCEEDED`, пары не
   обрезаются. Больше 16 гипотез в самом каталоге это ошибка загрузки.

Результат детерминирован: пары отсортированы по `id` (`<семья>.<гипотеза>`,
для нижестоящих `<семья>.<гипотеза>@<сервис>`), окна отсортированы, порядок рёбер
значения не имеет. `clock_alignment` пары равен `declared_aligned`, если так
объявлено в `snapshot.provenance`, иначе `unknown`. План содержит только
`schema_version`, `resource_snapshot_sha256` и `pairs`.

`skipped` это ведомость пропусков вида `{"hypothesis", "reason"}`. В план она не
входит: парсер ядра отвергает неизвестные поля плана. Коды причин принадлежат
инструменту и в словари причин отчёта (`ReportReasons.kt`,
`verdictReasons.ts`) не входят.

## Командная строка

```powershell
python tools/correlation_catalog.py --snapshot resources.json --stages steady `
  --service orders --load-metric response_time_p95_ms --edges orders:billing `
  --out correlation.json --skipped-out skipped.json
```

Код возврата 0: план записан. Код 1: плана нет, ведомость пропусков выведена в
stderr. Файл плана подаётся в `ltv analyze --correlation`.

## Ограничения

- Семья по стадии: на одну стадию приходится не более 16 пар; при `F` семьях
  отчёта `F * m <= 50`, рекомендуемый предел `F <= 3` (ADR 0022). Несколько
  стадий в одном плане корректно считаются ядром после среза K1 (стадийные
  семьи); до него все пары такого плана получают `UNAVAILABLE` (измерено:
  10 пар на 2 стадии дают `FAMILY_SIZE_UNSUPPORTED`).
- Версия 1 содержит три семьи: p95, ошибки, пропускная способность. Из рабочего
  материала в неё не вошли строки, для которых в снимках платформы нет рядов с
  известным именем и единицей: пулы и блокировки БД, сеть, частота GC,
  ошибки OpenSearch как ряд. Строка «загрузка CPU к лимиту» не взята отдельно:
  она почти дублирует троттлинг, каталог берёт один из двух. Метрики
  `service_response_time_p95`, `service_error_rate` (ряды нижестоящих сервисов по
  ребру) и `cpu_used` с ролью `generator` объявлены каталогом и должны
  присутствовать в снимке под этими именами.
- Знаки, лаги и пороги типовые и не откалиброваны на реальных прогонах; метод
  отбора не откалиброван на реальных данных (ADR 0022, приёмка C5).
- Напряжение, зафиксированное, но не решённое: в семье пропускной способности
  CPU генератора нагрузки в рабочем материале главная причина (знак `negative`),
  а ADR 0022 требует в каждой семье контрольную гипотезу, которая не должна
  срабатывать. Версия 1 следует ADR: CPU генератора объявлен контрольной
  гипотезой со знаком `negative`; его срабатывание означает, что упёрся
  генератор, а не система.
- Контроли каталога (`target_rps`, `concurrency`) это ряды снимка, которые
  должен подготовить источник; снимок без них даёт план без соответствующих
  гипотез. Генератор профилей платформы выпускает их блоком `load_generator`
  ([пакеты метрик](../../../user/platform-metric-packs.md)); откуда брать
  запланированную нагрузку на боевом стенде, решает владелец. Рабочий материал называл контролем «RPS» и не уточнял,
  какой.
