# ADR 0036: Предложение стадий нагрузки по данным прогона (`ltv stages detect`)

Дата: 2026-11-19.

Статус: Accepted (волна 0, 2026-11-20). Реализация PR 1
(`ltv stages detect`) была выполнена при статусе Proposed по решению владельца 2026-11-19 (раздел
«Решения владельца 2026-11-19») и влита в `main` в волне 0. Номер 0036 выбран как
следующий после 0035 (ADR о библиотеке графиков UI, при начале этой работы открытый PR, к вечеру
2026-11-19 влит в `origin/main` как #267). Перед слиянием номер нужно перепроверить по
`origin/main`.

Рабочий план, алгоритм с константами, фикстуры и критерии приёмки:
[2026-11-19-w4-1-stage-detection.md](../superpowers/plans/2026-11-19-w4-1-stage-detection.md).

## Контекст

[ADR 0030](0030-load-stages-steady-window.md) ввёл явные стадии нагрузки (`load-stages.v1`):
человек объявляет разгон, плато и остановку смещениями от начала прогона, стадии `steady`
становятся окнами вердикта. Автоопределения плато там нет: это решение владельца 3 и отклонённая
альтернатива («новый статистический метод и источник недетерминизма; D1 заморожен»). Подсказка
границ откладывалась «позже как зонд doctor или MCP».

На практике человек часто не знает границ точно: профиль задан в сценарии JMeter, а фактический
разгон зависит от генератора. Ошибка в объявлении молча сдвигает окно (раздел «Ловушка начала
прогона» руководства). Решение владельца 2026-11-19: автоопределение стадий обязательно для
продукта; пока оно работает как предложение, которое человек подтверждает. Инструмент строит
документ `load-stages.v1` по данным нагрузки, человек проверяет его, правит и передаёт как обычный
явный вход. Полностью автоматическое применение без подтверждения в объём не входит.

Ограничения решения:

1. `ltv analyze`, identity, `analysis_id`, канонический JSON и хэши identity не меняются. Стадии
   остаются явным входом (`--stages`, часть `stages` задания API).
2. Одинаковые байты входа дают одинаковое предложение: нет случайности и часов.
3. Нужна только нагрузка (JTL JMeter или журнал Gatling); источник мониторинга не нужен.
4. Не удалось определить уверенно — явный отказ с причиной, а не плохая догадка (принцип
   fail-closed, как в [ADR 0012](0012-auto-window-recognized-period.md) и
   [ADR 0026](0026-capacity-knee-diagnostic.md)).

Источник идеи: детектор ступеней конкурента LoadLens (Apache-2.0, `AI/step_detector.py`). Это
только ориентир по подходу: окно подтверждения, порог скачка от шума плато, доля выборок на плато
как признак «плато нет», пометка устойчивого падения внутри ступени. Код не копируется; ниже
описан собственный метод с собственными фикстурами. Главные отличия: глобальная кусочно-линейная
сегментация вместо сканирования окном, шум по первым разностям вместо второго прохода по
остаткам плато, нет параметра «ожидаемая длина ступени» от пользователя.

## Решения владельца 2026-11-19

1. Автоматическое определение стадий объявлено обязательным для продукта. Это явное исключение
   из заморозки D1 перечня ревью 2026-10-08 («статметоды не принимаются до конца волны 3»).
   ADR остаётся Proposed; реализация PR 1 (`ltv stages detect`) идёт.
2. Ступенчатый профиль (несколько плато): два режима с переключателем, а не одно правило (D12).
3. Режим `--like <load-stages.json>` одобрен следующим срезом (PR 1b, D13); в PR 1 не входит.
4. Код выхода `3` для отказа метода остаётся (D8).
5. Открытыми остаются поле стадий в форме UI (снятие ADR 0030 R12, D10) и проверка метода на
   корпусе реальных прогонов до перевода в Accepted (раздел «Открытые вопросы»).
6. Признак деградации по задержке и ошибкам (бывший открытый вопрос 4) добавляется: участок,
   который предложение исключило бы после начала первой стадии steady, сравнивается по доле
   ошибок и средней задержке с опорной ступенью, и деградировавший участок не исключается
   (D14). Метод перестаёт быть только по RPS: версия `rps-plateau-segmentation.v2`.

## Решение

### D1. Предложение, а не применение

Предложение строится отдельной командой и отдельным маршрутом API. Ни `ltv analyze`, ни
`AnalysisService` его не вызывают и не читают. Анализ получает стадии только явным файлом, как
сегодня, поэтому решение владельца 3 из ADR 0030 («ядро не угадывает окна при анализе») остаётся в
силе: угадывает отдельный инструмент, а решает человек. По той же причине не нарушается
[ADR 0012](0012-auto-window-recognized-period.md) (границы теста не угадываются при выборке
источника) и [ADR 0009](0009-explicit-capacity-stages.md) (план ёмкости не выводится из данных:
предложение это `load-stages.v1`, не `capacity-plan.v1`).

Заморозка D1 перечня ревью 2026-10-08 («статметоды не принимаются до конца волны 3») не
действует для этой работы: владелец 2026-11-19 объявил автоопределение стадий обязательным и
назвал это явным исключением из заморозки.

### D2. Вход: ряд числа запросов по секундам от начала прогона

Начало прогона вычисляется тем же правилом, что в анализе: минимальный `started_at` среди всех
выборок всех видов (`AnalysisService.kt:282,310`, `RunPeriod.kt:59`), включая setUp-группу,
health-check и контейнеры. Конец прогона это максимум `started_at + elapsed`. Число запросов
считается только по выборкам `JMETER_SAMPLER` и `GATLING_REQUEST` (как секундные корзины ядра,
`Metrics.kt:212-215`), по моменту старта, в секундных ячейках от начала прогона. Так смещения
предложения означают ровно то же, что смещения при анализе со стадиями.

Ряд строит собственный лёгкий проход по образцу `recognizeRunPeriod` (`RunPeriod.kt:41-66`):
два чтения входа через `parseInput` (первое находит начало прогона, второе раскладывает старты по
секундам), без гистограмм и без каталога данных. Два чтения нужны потому, что строки JTL не
упорядочены по времени старта, а ячейки отсчитываются от минимума. Прогон длиннее 604800000 мс
(предел смещения `load-stages.v1`) не обрабатывается.

### D3. Метод `rps-plateau-segmentation.v2`

Сегментация и классификация (пункты ниже) идут только по ряду числа запросов, как в первой
версии `rps-plateau-segmentation.v1`. Версия 2 (решение владельца 2026-11-19) добавляет проверку
исключаемых участков по задержке и ошибкам (D14), которая меняет границы и роли стадий; поэтому
это новая версия того же метода, а не новое имя: сегментация не изменилась, а прежние
предложения без строк `stretch` получены версией 1.

1. **Ширина ячейки.** Секундный ряд агрегируется в ячейки ширины `W` из фиксированной лестницы
   1, 2, 5, 10, 15, 30, 60, 120, 300 с: берётся наименьшая `W`, при которой ячеек не больше 2400, а
   верхний квартиль числа запросов в ячейке не меньше 50 (пуассоновский шум ячейки плато не больше
   примерно 14 %). Ячейки отсчитываются от начала прогона, поэтому все границы кратны `W`.
2. **Шум.** `σ` это робастная оценка шума ряда по первым разностям: `1,4826 · MAD(Δc) / √2`,
   не меньше одного запроса на ячейку (разрешение ряда).
3. **Сегментация.** Ряд делится на отрезки, на каждом из которых число запросов описывается
   прямой (уровень и наклон). Разбиение оптимально по сумме квадратов остатков со штрафом
   `3 · σ² · ln n` за каждый отрезок (критерий BIC для трёх параметров отрезка), отрезок не короче
   трёх ячеек. Метод точный (динамическое программирование), без случайности; на 2400 ячейках это
   несколько миллионов операций.
4. **Классификация отрезков.** `FLAT` (дрейф уровня за отрезок не больше 10 %, разброс остатков не
   больше 25 % уровня), `IDLE` (уровень не больше 2 % наибольшего), `RISING`, `FALLING`,
   `UNSTABLE`. Долгий (не меньше 60 с) падающий отрезок, теряющий не больше 25 % уровня, это
   `FLAT` (удержание, D4). Соседние `FLAT` с неразличимыми уровнями и длиной не меньше 30 с сливаются;
   короткий растущий `FLAT` между плато считается переходом (поправка при реализации PR 1,
   раздел «Реализовано»).
5. **Выбор steady.** Кандидат в steady это `FLAT` длиной не меньше 30 с, у которого уровень не
   меньше половины наибольшего плато или длина не меньше 3/4 самого длинного плато. Низкое и
   короткое плато в начале (прогрев) становится частью разгона; ступени профиля ёмкости
   одинаковой длины становятся стадиями-ступенями. Какие из ступеней получают роль `steady`,
   решает режим D12.
6. **Края.** Граница стоит на краю ячейки, где сегментация нашла смену уровня. Крайняя ячейка
   стадии steady остаётся в ней, только если её число запросов в пределах `2σ` от уровня плато;
   иначе граница сдвигается внутрь (не больше чем на две ячейки).

Все константы названы и обоснованы в плане; они выбраны по синтетическим профилям и опорной
фикстуре `fixtures/stages/ramp-steady-rampdown.jtl` и **не калибровались на корпусе реальных
прогонов**. Таблица констант с обоснованиями находится в плане (раздел «Константы»). Ширина ячейки, шум, найденные отрезки и причина каждой границы печатаются вместе с
предложением, чтобы результат объяснял себя сам; сами значения констант не печатаются, они
задаются версией метода (`rps-plateau-segmentation.v2`) и таблицей плана.

### D4. Главное правило: после начала steady ничего не уходит молча, деградация не исключается

Правило (уточнено 2026-11-19 по второму ревью и решению владельца о задержке и ошибках): **от
начала первой стадии steady до конца прогона ничто не покидает окна вердикта молча, и
деградация не исключается никогда**, с одним явным исключением: деградировавший рост после
последней ступени (`DEGRADED_RISE_EXCLUDED`, D14) исключается, потому что у него нет ступени той
же нагрузки, а слить его с плато значит слить два уровня; он назван, уверенность `LOW`, решение
за владельцем (открытый вопрос 4). Каждый исключённый участок длиной 60 с (`DROP_MIN_MILLIS`) и
больше после этого момента назван предупреждением с моментом и длительностью, и предложение с
таким участком никогда не получает `HIGH`. По одному RPS нельзя отличить плановую остановку от
обвала системы при той же подаваемой нагрузке; поэтому каждый исключаемый участок после этого
момента, **любой длительности**, сравнивается по доле ошибок и средней задержке с опорной ступенью
(D14), и деградировавший участок остаётся в окне вердикта. Участок без деградации исключается, как
раньше (короче 60 с без предупреждения, от 60 с назван); участок, по которому выборок слишком
мало для суждения, тоже исключается как раньше, и предупреждение участка от 60 с говорит, что
суждения нет.

Включить разгон в steady значит вернуть ошибку, которую исправлял ADR 0030 (ложный FAIL). Вырезать
падение молча значит спрятать отказ: в замкнутой модели JMeter RPS падает, когда система
тормозит, и окно без этого участка дало бы ложный PASS. Поэтому:

- всё до первой стадии steady (простой setUp, прогрев, разгон) исключается без предупреждения;
- соседние плато одного уровня (в пределах порога слияния) это одна ступень, и всё между ними
  остаётся в ней: провал не вырезается, ставится `LOAD_DROP_INSIDE_STEADY` по самому глубокому
  месту провала и уверенность `LOW`;
- плато другого уровня, ставшее кандидатом в steady (D3, п. 5), это отдельная ступень, как бы
  быстро ни менялся уровень (ADR 0030: два уровня не сливаются в одно окно). Исключение: плато, не
  ставшее кандидатом (ниже половины наибольшего и короче 3/4 самого длинного), отдельной ступенью
  не становится. После последней ступени такое плато остаётся в ней (например, 60 мин на 100 rps,
  затем 10 мин на 40 rps дают одну стадию `steady` с `LOAD_DROP_INSIDE_STEADY` и `LOW`); короткие
  всплески в режиме `top` тоже остаются внутри ступени. Эти уровни сливаются в одно окно, но
  названы предупреждением. Переход вниз всегда назван `LOAD_DECLINE_BETWEEN_STEPS`;
  переход вверх длиной от 60 с после первой стадии steady назван `LOAD_RISE_BETWEEN_STEPS`;
  провал до 60 с и больше между плато одного уровня, если он стал зазором, назван
  `LOAD_DECLINE_BETWEEN_STEPS`;
- долгий рост (`RISING` от 60 с) всегда заканчивает ступень: дальше идёт следующая ступень или
  исключённый хвост `after-steady` с предупреждением `RISE_AFTER_STEADY`. Хвост считается ростом
  после steady, только если его последний длинный (от 60 с) отрезок с нагрузкой кончается выше
  уровня ступени больше чем на порог слияния; иначе рост остаётся в ступени, а то, что идёт за
  ним, это обычный хвост (ревью 2026-11-19, N2: шумовой рост в конце плато превращал обвал в
  исключённый «рост»);
- долгое удержание не прячется в остановке: падающий отрезок от 60 с, теряющий не больше 25 %
  уровня (`HOLD_MAX_DRIFT_RATIO`), это плато;
- хвост после последней ступени: спад остаётся в последней ступени, если он неглубокий (теряет
  не больше половины своего уровня, `STEADY_LEVEL_RATIO`, `LOAD_DROP_INSIDE_STEADY`, как
  раньше) **или** деградировал (D14: `DEGRADED_TAIL_KEPT`, уверенность `LOW`). Остановкой
  (`ramp-down`) становятся простой, участки короче 60 с и долгий глубокий спад, только если
  хвост целиком не деградировал или по нему мало выборок. Исключённый хвост длиной от 60 с назван
  всегда: `LONG_RAMP_DOWN` (уровни в начале и в конце хвоста, длительность, при недостатке
  выборок `degradation=NOT_JUDGED`), без зависимости от длины плато. Уверенность `LOW`, если
  хвост не короче 300 с (`LONG_TAIL_LOW_MILLIS`), иначе `MEDIUM`;
- провал между ступенями и нижняя ступень режима `top` после первой стадии steady, если они
  деградировали, тоже не исключаются (D14): провал становится своим окном `gap-K`
  (`DEGRADED_GAP_KEPT`), нижняя ступень становится своим окном (`DEGRADED_STEP_KEPT`). Два уровня
  плато в одно окно не сливаются и здесь.

Разрыв на 50 % для деградировавшего спада снят: спад исключается, только если он глубокий **и**
не деградировал (или по нему мало выборок). Для здорового спада разрыв остаётся сознательно:
спад, теряющий 49 %, оценивается в окне (`LOW`), теряющий 51 % исключается и назван; здоровый
глубокий спад с задержкой и ошибками не хуже плато это плановая остановка, исключать его
безопасно.

### D5. Отказ вместо догадки

Предложение не строится, если выполнено любое из условий (проверяются в этом порядке):

| Код | Условие |
| --- | --- |
| `INPUT_INVALID` | вход непригоден (`INVALID`) |
| `INPUT_CHANGED` | вход изменился между двумя чтениями (например, JTL ещё пишется); код выхода `4` |
| `NO_REQUEST_SAMPLES` | нет выборок-запросов |
| `RUN_TOO_LONG` | прогон длиннее 604800000 мс |
| `RUN_TOO_SHORT` | прогон короче 60 с (до выбора ширины ячейки) или меньше 12 ячеек (после выбора) |
| `RATE_TOO_LOW` | ни одна ширина ячейки не даёт 50 запросов в верхнем квартиле |
| `RATE_OUT_OF_RANGE` | переполнение целых сумм при сегментации (защитный код, на реальных нагрузках недостижим) |
| `IDLE_GAP_INSIDE_RUN` | простой не короче 30 с между плато (похоже на два теста в одном файле, как `AUTO_WINDOW_MULTI_TEST_SUSPECTED` в ADR 0012) |
| `NO_PLATEAU` | нет кандидата в steady или плато занимают меньше 30 % прогона без начального простоя (непрерывный рост) |
| `LEAD_IN_TOO_LONG` | вместо `RATE_TOO_LOW` или `NO_PLATEAU`, когда до нагрузки есть простой от 30 с (например, setUp за часы до теста): `lead_in_ms` и доля прогона |
| `TOO_MANY_STAGES` | стадий получилось больше 16 (предел `load-stages.v1`) |

Отказ не пишет файл и объясняет причину измеренными фактами (ширина ячейки, доля плато, длина
простоя).

### D6. Уверенность: правила, а не вероятность

Уровень `HIGH`, `MEDIUM` или `LOW` выводится по явным правилам и всегда сопровождается пометкой
`calibrated=false`. `HIGH` означает только «ни одно правило не сработало», а не измеренную
надёжность: метод ни разу не запускался на реальном тесте, константы не калиброваны.

- `LOW`: `LOAD_DROP_INSIDE_STEADY`, `HOLD_NOT_EVALUATED`, хвост (`LONG_RAMP_DOWN` или
  `RISE_AFTER_STEADY`) не короче 300 с, любое предупреждение о деградации D14
  (`DEGRADED_TAIL_KEPT`, `DEGRADED_GAP_KEPT`, `DEGRADED_STEP_KEPT`, `DEGRADED_RISE_EXCLUDED`).
- `MEDIUM`: `LEAD_IN_IDLE`, `STEADY_DRIFT` (дрейф ступени целиком больше 5 %), `DEGRADED_INPUT`,
  `LOAD_DECLINE_BETWEEN_STEPS`, `LOAD_RISE_BETWEEN_STEPS`, `LOW_LEVEL_STEP` (стадия steady ниже
  половины наивысшей ступени), хвост от 60 до 300 с, граница steady видна меньше чем на `6σ`,
  разброс ступени целиком больше 15 %.
- `HIGH`: иначе.

Вероятностей и доверительных интервалов нет: для них нужна калибровка на корпусе (как в ADR 0026).

### D7. Вывод: обычный `load-stages.v1`, нового контракта нет

Предложение это канонические байты `load-stages.v1` (та же функция сериализации, что у валидатора;
тест проверяет, что `validateLoadStages` принимает их и возвращает те же канонические байты).
Обёртка `stage-proposal.v1` с объяснением и уверенностью не вводится: предложение не сохраняется
в каталоге данных и не входит ни в один артефакт, а объяснение нужно человеку один раз. Самый
малый вариант достаточен: документ отдельно (его можно сразу передать в `--stages`), объяснение
отдельно.

Имена стадий: `lead-in` (простой до первой нагрузки, если он есть), `ramp-up`, `steady` при одном
плато (тогда правила с `window_ids: ["steady"]` работают без правок) или `step-1` ... `step-N` при
нескольких, `ramp-down`. Имена ступеней одинаковы в обоих режимах D12, режим меняет только роли;
при нескольких плато правило с `window_ids: ["steady"]` окна не находит, его нужно привязать к
`step-N`. Конец последней стадии округляется вверх до сетки `W`; конец steady за
концом прогона обрезается при анализе (`clipped_to_run_end`, ADR 0030 R1).

### D8. CLI: `ltv stages detect <input> [--out <file>] [--steady-steps top|all]`

- stdout (или файл `--out`): канонические байты предложения, только при успехе.
- stderr: объяснение строками `ключ=значение` на английском, в стиле `summary.txt`: метод, режим
  ступеней (`steady_steps`), статус, уверенность, ширина ячейки, шум, отрезки, причина каждой
  границы (уровни до и после, контраст в `σ`, сдвиг края), проверенные участки D14 (строки
  `stretch`), предупреждения, причина отказа. Строки стабильны и проверяются тестами.
- Коды выхода: `0` предложение построено; `3` не определено (как `NO_VERDICT`: инструмент ничего не
  утверждает; подтверждено владельцем 2026-11-19); `4` вход непригоден (`INPUT_INVALID`, как
  `INVALID` у `ltv analyze`), не найден или не распознан, `--out` уже существует или не записан;
  `64` ошибка использования (в том числе значение `--steady-steps` не `top` и не `all`).
- Каталог данных не открывается и не блокируется: команду можно запускать рядом с `ltv ui`.
- `--out` не перезаписывает существующий файл и не следует по ссылкам (как `PG_REPORT_EXISTS`).

### D9. Сопоставимость: определить один раз, переиспользовать файл

Хэш объявления входит в ключ сопоставимости (ADR 0030 R6). Предложение, построенное заново для
каждого прогона, может сдвинуться на ячейку, и тогда прогоны станут несопоставимыми
(`compatible = false`). Порядок работы, который фиксирует руководство: построить предложение на
одном прогоне профиля, проверить, сохранить файл рядом со сценарием и передавать его во все прогоны
этого профиля. Границы кратны ширине ячейки, что уменьшает дрожание, но не исключает его.

### D10. UI: поле стадий и кнопка «Предложить стадии» (отдельный PR после CLI)

Сегодня в форме нового анализа поля стадий нет (ADR 0030 R12), а `createJob` в `ui/src/api.ts`
не отправляет часть `stages`, хотя API её принимает. Второй PR добавляет:

- поле стадий в форме нового анализа (редактируемый JSON) и отправку части `stages`;
- кнопку «Предложить стадии», которая заполняет поле предложением и показывает объяснение;
  анализ запускает человек, предложение без его действия не применяется;
- маршрут `POST /api/runs/{runId}/stage-proposal` без тела. POST, а не GET: вычисление читает весь
  вход дважды, и защита сессией, `Origin` и CSRF как у `POST /api/jobs`
  ([ADR 0002](0002-slice-1-runtime-filesystem-security.md)) ограничивает его вызов. Вычисление
  идёт вне event loop, одновременно не больше одного (`409 BUSY`, как захват PostgreSQL),
  неизвестный прогон даёт `404`. Ответ `200` содержит `status`, `reason`, `method`,
  `confidence`, `calibrated`, `warnings`, `proposal` (объект `load-stages.v1` или `null`),
  `parameters`, `segments`, `boundaries`. Это добавочный маршрут локального API, не
  версионированный документ; русский текст объяснения строит UI из полей (как фраза стадий по
  ADR 0030 R10).

Это частично снимает ADR 0030 R12 (форма загрузки стадий в UI): требуется подтверждение
владельца.

### D11. Детерминизм

Счётчики и префиксные суммы целые (`Long`, переполнение даёт отказ, а не неверный результат),
медианы нижние, арифметика `double` на JVM строго IEEE 754, логарифм через `StrictMath`, при
равенстве стоимостей выбирается самая ранняя граница. Порядок строк во входе на результат не
влияет. Числа в объяснении округляются `HALF_EVEN` до трёх знаков. Проверка D14 считает число
выборок, число ошибок и сумму `elapsed` целыми (`Math.addExact`) по секундам старта; доля ошибок
и средняя задержка это одно деление точных целых в `double`, накопления в плавающей точке нет,
поэтому порядок строк на суждение не влияет.

### D12. Ступенчатый профиль: режим `--steady-steps top|all`

Решение владельца 2026-11-19: два режима с переключателем.

- `all` (режим A): роль `steady` получает каждая ступень, отобранная правилом D3, п. 5 (уровень
  не ниже половины наибольшего плато или длина не меньше 3/4 самого длинного). Ступень ниже
  половины наивысшей получает `LOW_LEVEL_STEP`.
- `top` (режим B): роль `steady` получает каждая ступень на уровне наивысшей (в пределах порога
  слияния D3, п. 4): равные плато не выбираются шумом, и набор окон не меняется от прогона к
  прогону одного профиля. Остальные плато выводятся стадиями с ролью `excluded` под теми же
  именами `step-K`. Исключённая ступень после первой стадии steady или после перехода вниз
  (например, soak после спада или нижний уровень между двумя верхними) получает
  `HOLD_NOT_EVALUATED` (уровни, длительность) и уверенность `LOW` (D4); нижние ступени профиля
  ёмкости, идущие вверх до первой стадии steady, исключаются без предупреждения. Нижняя ступень
  после первой стадии steady, которая деградировала относительно ступени наивысшего уровня
  (D14), получает роль `steady` как отдельное окно (`DEGRADED_STEP_KEPT`); поэтому `top` может
  дать несколько окон и разных уровней, но каждое окно остаётся одного уровня.

Режим меняет только роли стадий. Границы стадий, их число и отказы от режима не зависят. Исключение
(D14): участки проверяются только после начала первой стадии steady, а она и набор исключённых
нижних ступеней зависят от режима; поэтому решение D14 и сдвинутая им граница (например,
деградировавший зазор перед ступенью, которая steady только в `all`) могут различаться между
режимами.
Признаки окна вердикта (`LOAD_DROP_INSIDE_STEADY`, `STEADY_DRIFT`, контраст границ и разброс)
считаются только по стадиям с ролью `steady`. При одном плато режимы дают одинаковые байты
предложения, объяснения различаются только значением `steady_steps`. Режим печатается в первой
строке объяснения.

Умолчание владелец не назвал. Исполнитель выбрал `top`: окно steady, собранное из ступеней разного
уровня, смешивает распределения задержек разных нагрузок. Выбор ждёт слова владельца.

### D13. Режим `--like <load-stages.json>` (запланирован, PR 1b)

Одобрен владельцем 2026-11-19 следующим срезом после PR 1. Команда проверяет, подходит ли уже
принятое объявление профиля этому прогону, и при совпадении оставляет его байты и хэш без
изменений. Это убирает дрожание границ на ячейку между прогонами и потерю сопоставимости с
baseline по ключу ADR 0030 R6 (D9). Набросок задач в плане (PR 1b); в PR 1 не реализуется.

### D14. Проверка исключаемых участков по задержке и ошибкам (решение владельца 2026-11-19)

**Данные.** Второе чтение входа (D2) рядом с числом запросов в секунду копит число неуспешных
выборок (`success=false`, то же определение, что у `error_rate_ratio` анализа) и сумму `elapsed`,
с тем же фильтром выборок (`JMETER_SAMPLER`, `GATLING_REQUEST`) и по той же секунде старта. Три
массива по одному `Long` на секунду: не больше 3 · 604801 · 8 байт, около 14,5 МБ на 7 суток
(новых около 9,7 МБ). Переполнение суммы `elapsed` даёт отказ `RATE_OUT_OF_RANGE`.

**Какие участки проверяются.** Каждый участок после начала первой стадии steady, который роли по
нагрузке (D3, D12) исключили бы, **любой длительности** (ревью 2026-11-19, N1: обвал 50 с на
40 rps, около 2000 запросов с 5000 мс и 50 % ошибок, исключался молча, потому что проверка
начиналась с 60 с). Судить ли участок, решает число выборок (ниже), а не длительность.
`DROP_MIN_MILLIS` по-прежнему решает только, называть ли здоровый участок: здоровый или
несудимый участок короче 60 с не печатается и предупреждения не получает, как раньше;
деградировавший короткий участок сохраняется и называется так же, как длинный.

| Участок (`kind`) | Опорная ступень |
| --- | --- |
| `TAIL`: хвост после последней ступени (будущий `ramp-down`) | последняя ступень |
| `GAP`: зазор между ступенями, переход вниз | предыдущая ступень (выше) |
| `GAP`: зазор между ступенями, переход вверх | следующая ступень (выше) |
| `STEP`: нижняя ступень режима `top` | последняя стадия steady перед ней (наивысший уровень) |
| `AFTER_STEADY`: рост после последней ступени | последняя ступень (ниже; см. ниже) |

Опорная ступень всегда та, нагрузка которой не ниже нагрузки участка: деградация это «хуже, чем
система держала при той же или большей нагрузке». Переход вверх, сравнённый с нижней ступенью,
отмечал бы обычный рост задержки с нагрузкой (колено), поэтому для него опорой служит следующая,
более высокая ступень. Опоры и участки берутся из раскладки по нагрузке до любых решений D14:
сохранённый участок никогда не становится опорой другого. Опорная ступень меряется по своим
границам после сдвига краёв (D3, п. 6) и может захватить край деградировавшего участка; это
уменьшает запас, но не меняет знак (раздел «Реализовано»).

**Суждение.** По точным суммам за весь участок и за всю опорную ступень (не по ячейкам):
`n`, `f`, `e` (выборки, ошибки, сумма `elapsed`), доля ошибок `p = f / n`, средняя задержка
`m = e / n`. Участок `DEGRADED`, если хуже по ошибкам **или** по задержке:

- ошибки: `p ≥ 2 · p_ref` и `p − p_ref ≥ 0,01` и `f − n · p_ref ≥ 4 · √max(1, n · p_ref)`;
- задержка: `m ≥ 1,5 · m_ref` и `m − m_ref ≥ 50 мс`.

У хвоста `TAIL` ошибки считаются деградацией, только если их избыток ещё и больше
`2 · r_ref · m_ref` (`STOP_IN_FLIGHT_FACTOR`: частота запросов опорной ступени в секунду,
умноженная на её среднюю задержку в секундах, это число запросов в полёте). Остановка теста
(JMeter Stop, конец длительности) роняет запросы в полёте; с проверкой любой длительности короткий
хвост в несколько секунд с такими ошибками иначе выглядел бы деградацией: при 100 rps и 100 мс
хвост 4 с, 230 выборок, 10 ошибок (4,3 % против 0,5 %) проходит все три условия, но избыток 8,8
меньше допуска около 20,8 (2 · 100,5 rps · 0,103 с). Настоящие короткие обвалы далеко выше допуска (N1: избыток около 1000).
Проверка по задержке остаётся без допуска.

`NOT_JUDGED`, если у участка или у опорной ступени меньше 200 выборок
(`DEGRADED_MIN_SAMPLES`); иначе `HEALTHY`. Обоснование каждого порога в таблице констант плана.

**Действия.** Деградировавший участок не исключается, два уровня плато в одно окно не сливаются:

- `TAIL`: последняя ступень продлевается до конца прогона (`DEGRADED_TAIL_KEPT` вместо
  `LONG_RAMP_DOWN`), стадии `ramp-down` нет; если последняя ступень была исключённой нижней
  ступенью `top`, она получает роль `steady`. Хвост, в отличие от зазора, не отдельное окно:
  за ним нет другой ступени, это продолжение той же ступени при падающей нагрузке, и так же D4
  с первой версии оставляет в ступени неглубокий спад. Главное: при одном плато окно остаётся
  одно, `steady`, и правило политики с `window_ids: ["steady"]` (обычный случай, руководство)
  видит обвал; отдельное окно хвоста такое правило молча пропустило бы. Цена: деградировавший
  хвост тянет вниз и пропускную способность окна, так что правило `throughput_rps ≥ …` может
  упасть из-за хвоста; хвост при этом деградировал, причина `FAIL` настоящая, хотя метрика другая;
- `GAP`: зазор становится отдельной стадией `steady` с id `gap-K` (перед `step-K`;
  `DEGRADED_GAP_KEPT` вместо `LOAD_DECLINE_BETWEEN_STEPS` или `LOAD_RISE_BETWEEN_STEPS`, в нём id
  опорной ступени). Ступени не расширяются (ревью 2026-11-19, N3: слитый с ступенью 100 rps
  подъём 30→100 rps за 240 с при 400 мс опускал её до 91,7 rps, и правило `throughput_rps ≥ 95`
  на ступени давало `FAIL` не по той причине; так же спад 100→40 опускал ступень до 91,9 rps).
  Стадия `gap-K` занимает ровно промежуток между ступенями, порядок и непересечение
  `load-stages.v1` сохраняются. Если сохранённые зазоры доводят число стадий до 17 и больше,
  предложение отказывает с `TOO_MANY_STAGES` (D5), как при любом превышении: зазор не теряется
  молча;
- `STEP`: нижняя ступень `top` получает роль `steady` как отдельное окно (`DEGRADED_STEP_KEPT`
  вместо `HOLD_NOT_EVALUATED`);
- `AFTER_STEADY`: остаётся исключённым, предупреждение `DEGRADED_RISE_EXCLUDED` вместо
  `RISE_AFTER_STEADY`, уверенность `LOW`. Опоры той же или большей нагрузки у этого участка нет,
  включить его в окно плато значит слить в одно окно нагрузку выше плато (ADR 0030), а отдельное
  окно для прерванного разгона это новое решение о ролях. Вопрос передан владельцу (раздел
  «Открытые вопросы», п. 4).

Предупреждения `DEGRADED_*` несут, кроме уровней и длительности, долю ошибок и среднюю задержку
участка и опорной ступени и id опорной ступени; уверенность `LOW`. Участок `NOT_JUDGED` оставляет
поведение и предупреждение RPS-метода, к предупреждению добавляется `degradation=NOT_JUDGED` с
числом выборок. Каждый проверенный участок печатается строкой `stretch` (D8) с точными счётчиками.

**Безопасное направление.** Ложное «деградировал» оставляет в окне участок нагрузки не выше плато
и названо предупреждением; пропущенный обвал это молчаливый ложный `PASS`. Поэтому пороги
выбраны скорее чувствительными: плановая остановка, во время которой система случайно
деградировала, теперь остаётся в окне, и это правильно: вердикт должен её видеть.

## Открытые вопросы

1. Умолчание `--steady-steps`: исполнитель выбрал `top` (D12), ждёт слова владельца. Режим `top`
   может дать несколько окон `steady`: каждая ступень наивысшего уровня и (D14) каждая
   деградировавшая нижняя ступень и каждый деградировавший зазор `gap-K`. Владелец спрошен,
   ответа нет; поведение сохранено.
1a. Нижняя ступень после наивысшей в режиме `top` (D12): сейчас `excluded` с
    `HOLD_NOT_EVALUATED` и `LOW`. Рекомендация исполнителя, согласованная с D4 (после начала
    steady ничего не прячется): в `top` делать `steady` наивысшую ступень и все ступени после
    неё; окна остаются раздельными, перцентили разных уровней не смешиваются. Не реализовано,
    ждёт слова владельца.
2. Поле стадий в форме UI снимает ADR 0030 R12 (D10): ждёт подтверждения владельца.
3. Проверка метода на корпусе реальных прогонов (в том числе со ступенями и падениями) до
   перевода ADR в Accepted: корпус и порядок прогона не определены.
4. Признак деградации по задержке и ошибкам решён владельцем 2026-11-19 и реализован (D14).
   Остаётся вопрос: деградировавший рост после последней ступени (`AFTER_STEADY`, например
   прерванный разгон до 200 rps с задержкой 3 с) сейчас исключён с `DEGRADED_RISE_EXCLUDED` и
   `LOW`. Варианты: оставить так; сделать его отдельным окном `steady` (не сливая с плато; но
   тогда правило без `window_ids` проверит и прерванный разгон). Ждёт слова владельца.
5. Участки до начала первой стадии steady не проверяются (D4 их исключает молча, кроме нижней
   ступени после перехода вниз с `HOLD_NOT_EVALUATED`, например ступень 60 rps между 100 и
   120 rps в `top`): у них нет опорной стадии steady перед ними.

- Ограничения метода: модель «уровень плюс наклон» не различает плановое снижение нагрузки и
  деградацию, различает их только проверка D14 по задержке и ошибкам; обвал пропускной

  от остановки; профиль из многих коротких ступеней (меньше 30 с) не распознаётся; константы не
  калиброваны.
- Для перевода в Accepted: слово владельца по открытым вопросам (умолчание D12, D10 и снятие
  ADR 0030 R12) и прогон метода на корпусе реальных прогонов с записанным результатом.
  Исключение из заморозки D1 и роли ступеней (D12) владелец решил 2026-11-19.

  - пороги D14 не калиброваны на реальных прогонах.

## Не входит

- Автоматическое применение предложения без подтверждения человеком и любое использование
  детектора внутри `ltv analyze` или `AnalysisService`.
- Сохранение предложения в каталоге данных, версионированная схема предложения, MCP-инструмент.
- Вывод `capacity-plan.v1` (ступени ёмкости с целями) и детектор колена (ADR 0026).
- Определение стадий по ресурсам или числу потоков (`allThreads`). Границы стадий по-прежнему
  ищутся только по ряду числа запросов; доля ошибок и средняя задержка (решение владельца
  2026-11-19, D14) только решают, исключать ли участок, который сегментация уже нашла.
- Локализация объяснения в CLI. Сравнение с уже принятым объявлением (`--like`) запланировано
  отдельным срезом (D13).
- Визуальный дизайн UI (во втором PR определяется только маршрут и поведение).
