# ADR 0018: Правила платформы по сервисам и режим малой выборки

Статус: Proposed, 2026-10-01; редакция 2026-10-02 вносит решения владельца по 14 вопросам (раздел «Решения владельца (2026-10-02)»). Принятие самого ADR владелец подтвердит отдельно.

База: `origin/main` `e8e096f`; ссылки `файл:строка` ниже сверены с этой базой. Редакция 2026-10-02 синхронизирована с `origin/main` `8cd67b5` (влиты PR #25, #26, #29-#31): они не затрагивают цитируемый код политики, ресурсов, результата и baseline; сдвинулись только строки `docs/user/slice-1-local-analysis.md` (вставка 8 строк), они обновлены. Решения D1-D9 сформулированы автором; ответы владельца 2026-10-02 учтены в них и записаны отдельным разделом. Не подтверждено владельцем только то, что явно помечено в разделе «Открытые вопросы владельцу» (подтверждения Q12 пока нет).

Номер 0016 зарезервирован для ADR о семантике метрик; его черновика нет в `origin/main`. ADR 0017 принят (`docs/adr/0017-baseline-candidates-and-confirmation.md:1-5`), поэтому 0018 свободен. ADR-C плана внедрения (история релизов, baseline) далее называется ADR 0019. Два файла с номером 0010 и безномерной correlation ADR в `docs/adr/` к этому решению не относятся.

## Контекст

Это ADR-B плана внедрения из материалов владельца вне репозитория. Стенд на момент написания: плечи OpenShift (сейчас два), примерно 20 сервисов на плечо, у каждого два сайдкара, плюс БД; тесты длятся 4–8 часов. **Число плеч не фиксируется**: их может быть 1, 2, 3 и более, `arm` — только идентификатор плеча (решение владельца 2026-10-02). Владелец ведёт не более примерно 10 протоколов на протяжении 2–4 релизов. Jenkins находится вне объёма. Одна нагрузка направлена на все плечи; снимок и анализ создаются отдельно для каждого плеча, вердикты независимы, а UI не должен считать одинаковые бизнес-метрики несколько раз. Это решение владельца уже записано в ADR 0014 (`docs/adr/0014-resource-series-limits-autostep-arm-api.md:484-540`, `:582-589`).

Сейчас `policy.v1` описывает только четыре бизнес-метрики и области `overall` либо точную `transaction` (`Model.kt:23-58`). Ресурсные SLA-правила живут в снимке, а онлайн-профиль источника тоже содержит `rules` и переносит их в ресурсные правила (`ResourceSnapshot.kt:69-77`, `SourceConfig.kt:90-97`, `:383-395`, `:546-568`). Такое устройство не задаёт политику по ожидаемым сервисам и создаёт риск двух владельцев одного SLA-порога. `MetricPacks.kt:113-129` лишь группирует уже имеющиеся ряды по именам; ядро не вычисляет смысл OpenShift-сигнала из имени.

| Тема | Принято в ADR или видно в продукте | Есть в `src/main` на `e8e096f` |
| --- | --- | --- |
| Пределы снимка | ADR 0014 принял измеренные `S_max = 1 024`, `C_max = 1 500 000`, `B_max = 32 MiB`; `E_max = 20 480` остаётся предварительным (`0014:3-9`, `:1019`) | Пределы снимка подняты (`ResourceSnapshot.kt:651-656`; `resource-snapshot.schema.json:14`). Старые числа 64 ряда, 500 000 ячеек и 16 MiB для снимка неактуальны. |
| Плечо | ADR 0014 принял отдельный снимок и анализ на плечо, метку `arm` и условный `resource_arm` в identity (`0014:484-540`, `:1028-1071`) | В `ResourceSnapshot.kt:52-60` нет специального поля `arm`; срез ещё нужен. |
| Пиковая агрегация | ADR 0014 принял `interval_max` для правил `gt` (`0014:1068-1070`, `:1092-1105`) | Enum содержит только `interval_mean` и `interval_rate` (`ResourceSnapshot.kt:92-96`; `resource-snapshot.schema.json:31`). |
| Карточка F1 | Карточка сохраняет найденное нарушение рядом с `NO_VERDICT` (`verdictSummary.ts:295-301`; `verdict-summary.spec.ts:148-163`) | UI есть; новые причины малой выборки и правила платформы ещё не поддержаны. |
| Baseline | ADR 0017 принят, в том числе запрет совмещать изменения identity в одном переходе (`0017:173-180`) | Кандидат statistical baseline уже обязан иметь `VALID` и `analysis_coverage.status = COMPLETE` (`BaselineComparison.kt:101-104`). |

Минимум выборки сейчас фактически равен одному наблюдению: `observed` отказывает только при `sampleCount == 0` (`Policy.kt:209-219`), а оконный путь дополнительно отказывает для полностью пустого окна (`WindowPolicy.kt:25-33`). Поэтому правило по трём–пяти наблюдениям может получить обычный `PASS` или `FAIL`. По материалам владельца вне репозитория это существенный дефект. Малые выборки чаще возникают в отдельных стадиях и редких транзакциях, чем за весь прогон: считать нужно наблюдения **области конкретного правила в конкретном окне**.

Предпосылки реализации этого ADR: срез ADR 0016, ограничивающий значение перцентиля наблюдаемым максимумом, и нужные срезы ADR 0014 для плеча и `interval_max`. До исправления HDR-округление может дать ложный `FAIL` именно на небольшой выборке: в материалах владельца вне репозитория приведён случай 100 сэмплов по 60 000 мс с опубликованным p95 60 031 мс. В текущем коде перцентили берутся через `getValueAtPercentile`, а максимум хранится отдельно (`Metrics.kt:292-305`). Этот ADR не заменяет ADR 0016.

## 1. Минимум выборки и режим малой выборки

### Счёт и gate

Единица `n` — `MetricSummary.sampleCount` после binding правила к `overall` либо единственной подходящей транзакции, внутри оцениваемого окна. Binding остаётся точным: отсутствие или неоднозначность транзакции дают `TRANSACTION_NOT_FOUND` либо `AMBIGUOUS_TRANSACTION` (`Policy.kt:190-207`). Gate выполняется после binding и до сравнения с порогом, в общем `evaluatePolicy` и оконном пути. Валидность входа и отсутствие политики проверяются раньше (`Policy.kt:96-99`).

| `n` для бизнес-правила, кроме throughput | Оценка правила | Причина и режим |
| --- | --- | --- |
| `0` | `NO_VERDICT`, как сейчас | `METRIC_NOT_AVAILABLE`; код причины сохраняется для совместимости с F1 (`Policy.kt:112-116`, `verdictReasons.ts:27`). Для полностью пустого окна остаётся также `BUSINESS_OBSERVATIONS_NOT_FOUND`. |
| `1..sample_floor-1` (по умолчанию `1..19`) | `NO_VERDICT`, порог не сравнивается | Новая блокирующая причина `INSUFFICIENT_SAMPLES`. |
| `sample_floor..min_samples-1` (по умолчанию `20..99`) | Порог сравнивается; вердикт сохраняется (вариант 1, ниже) | Информационная метка `SMALL_SAMPLE`; она сама не превращает правило в `NO_VERDICT`. |
| `min_samples` и выше (по умолчанию 100) | Обычный `PASS` либо `FAIL` | Режим `FULL`. |

Значения **настраиваемые без изменения ядра** (решение владельца 2026-10-02). Запасные константы ядра: `MIN_SAMPLES_FLOOR = 20`, `MIN_SAMPLES_DEFAULT = 100`. Порядок приоритета: поле правила `min_samples` перекрывает значение по умолчанию политики (необязательный верхнеуровневый объект `defaults` с полями `sample_floor` и `min_samples`), а оно перекрывает запасную константу. Все целые от 1 до 1 000 000; действующий `min_samples` не может быть ниже действующего пола (`MIN_SAMPLES_BELOW_FLOOR`). Пол ниже 20 допустим, но документация обязана предупредить, что тогда p95 может совпасть с максимумом. Для `throughput_rps` с `gte` gate при положительном `n` **не применяется**: малое число запросов за полную длительность окна и есть низкая измеренная пропускная способность, которую правило должно иметь возможность признать `FAIL`. Нуль остаётся `METRIC_NOT_AVAILABLE` по действующему контракту (`Policy.kt:213-219`); изменение этого случая требует отдельного решения. Указание `min_samples` у правила throughput отвергается как неприменимое поле, чтобы валидный файл не содержал порог без эффекта.

Числа 20 и 100 — **допущения, не калибровка стенда** (оговорка владельца сохранена): поэтому они настраиваемы. При nearest-rank p95 совпадает с максимумом для `n < 20`; для p99 соответствующий порядок величины — 100. Точная граница для текущего HdrHistogram зависит от его округления и должна быть зафиксирована тестом после ADR 0016. При 100 наблюдениях хвост p95 содержит около пяти наблюдений, а один ошибочный ответ меняет долю ошибок на 1 процентный пункт. Для p99 на практике следует задавать `min_samples` порядка 1 000 в самом правиле. Ни одно из этих соображений не доказывает статистическую достаточность конкретного прогона.

Нынешний `evaluatePolicy` складывает блокирующие и прочие причины в один `reasons`, после чего любая причина побеждает найденный `FAIL` (`Policy.kt:94-106`, `:137-143`). Реализация должна разделить причины, блокирующие вердикт, и информационные причины покрытия. `INSUFFICIENT_SAMPLES` блокирует; `SMALL_SAMPLE` — нет. Аналогичное различие уже существует для ресурсных diagnostic-правил: их причины попадают в coverage, а статусы не попадают в SLA-свёртку (`ResourceStatistics.kt:62-72`).

### Связь режима малой выборки с PASS, FAIL, NO_VERDICT: выбранный вариант и отклонённые

Решение владельца: вердикт на малой выборке не должен выдаваться молча или скрываться, он помечается режимом малой выборки. **Трактовка подтверждена владельцем 2026-10-02: вариант 1** (рассчитанные `PASS`/`FAIL` остаются, помечаются `SMALL_SAMPLE`). Варианты 2 и 3 сохранены как отклонённые альтернативы с ценой.

| Последствие при `sample_floor <= n < min_samples` | Вариант 1: буквальное прочтение, **выбран владельцем** | Вариант 2 (отклонён) | Вариант 3 (отклонён) |
| --- | --- | --- | --- |
| Правило | Рассчитанный `PASS` или `FAIL` остаётся вердиктом; добавляется `SMALL_SAMPLE`. | Рассчитанный `FAIL` остаётся `FAIL`; рассчитанный `PASS` становится `NO_VERDICT` с `INSUFFICIENT_SAMPLES`. Ориентировочный `PASS` виден с меткой. | Любой рассчитанный исход становится `NO_VERDICT` с `INSUFFICIENT_SAMPLES`. Ориентировочный `PASS`/`FAIL` виден с меткой. |
| `policy_verdict`, если других правил нет | `PASS` либо `FAIL` | `FAIL` либо `NO_VERDICT` | `NO_VERDICT` |
| Код CLI при `VALID` | 0 либо 2, как сейчас; метка только в JSON | 2 для `FAIL`, 3 для бывшего `PASS` | 3 |
| `analysis_coverage` | `INCOMPLETE` из-за `SMALL_SAMPLE` | `INCOMPLETE` | `INCOMPLETE` |
| Statistical baseline | Исключён автоматически | Исключён | Исключён |
| Будущий baseline «только из PASS» в ADR 0019 | Обязан отдельно требовать отсутствие правил в режимах `SMALL_SAMPLE` и `INSUFFICIENT`. | Малого `PASS` нет. | Малого `PASS` нет. |
| Цена | Скрипт, читающий только код возврата, видит обычный `PASS`/`FAIL`. | Асимметрия сложнее для пользователя; малый ориентировочный `PASS` блокирует иной достоверный `FAIL`. | Официальный `FAIL` скрыт за `NO_VERDICT`, хотя находка остаётся видимой. |

Фиксированный пример: R1 проверяет p95 транзакции `checkout` в окне `steady-1`; `n = 30`, `min_samples = 50`, p95 укладывается в порог. Независимое R2 проверяет `error_rate_ratio` для `overall`, имеет большую выборку и достоверный `FAIL`. При действующем приоритете `NO_VERDICT` над `FAIL` (раздел 6) вариант 1 даёт итог `FAIL`, код CLI 2 и метку `SMALL_SAMPLE` у R1. Варианты 2 и 3 дают R1 статус `NO_VERDICT`, поэтому одна редко посещаемая транзакция переводит общий итог в `NO_VERDICT`, код 3. Нарушение R2 остаётся в findings и видно в карточке F1, но вердикт `FAIL` не выдаётся.

Если у той же R1 `n = 12`, она получает `NO_VERDICT` с `INSUFFICIENT_SAMPLES` **при любом варианте**. Пол сам способен закрыть `FAIL` R2. Для редких транзакций владелец может выбрать окна, где наблюдений достаточно, или осознанно снизить `min_samples` до действующего пола; сам пол он тоже может изменить в `defaults`. Пол сохраняется (решение владельца Q2).

Выбран вариант 1: он ближе к формулировке владельца «пометить, не скрывать вердикт» и сохраняет достоверную находку R2. Его слабость компенсируется машинной меткой, явным текстом F1 и ограничением baseline. Коды возврата CLI остаются 0/2 (решение владельца Q6); метка `SMALL_SAMPLE` — в JSON результата и в UI. Ориентировочные UI-формулировки: «PASS — режим малой выборки: 30 сэмплов при минимуме 50» и «FAIL — режим малой выборки: 30 сэмплов при минимуме 50». Итоговый копирайт — задача среза UI. `SMALL_SAMPLE` в `verdictReasons.ts` имеет `noVerdict: false`, `INSUFFICIENT_SAMPLES` — `true`; нельзя выдавать информационную метку за причину блокировки.

### Результат и baseline

Без изменения схемы результата к объекту `policy_check` в `evidence[]` аддитивно добавляются `sample_count`, применённое `min_samples` и `sample_mode`. Допустимые значения `sample_mode`: `FULL`, `SMALL_SAMPLE` (`sample_floor <= n < min_samples`), `INSUFFICIENT` (`0 < n < sample_floor`, блокирующая причина `INSUFFICIENT_SAMPLES`) и `NOT_GATED` (правило `throughput_rps` с положительным `n`, исключённое из gate); при `n = 0` поле не ставится, чтобы отсутствие наблюдений не называлось малой выборкой. В `analysis_coverage.reasons` добавляется `SMALL_SAMPLE` либо `INSUFFICIENT_SAMPLES`. Сейчас любая причина делает `analysis_coverage.status = INCOMPLETE` (`AnalysisResult.kt:149-155`). Нового значения `policy_verdict` и нового верхнеуровневого поля результата не требуется: верхний уровень схемы закрыт, а `analysis_coverage` и элементы `evidence` допускают аддитивные поля (`analysis-result.schema.json:37-64`).

`INCOMPLETE` автоматически исключает анализ из кандидатов statistical baseline (`BaselineComparison.kt:101-104`). Ручной выбор baseline эту проверку не выполняет. ADR 0019 обязан для правила «baseline только из `PASS`» требовать, чтобы ни одно правило анализа не было в режиме `SMALL_SAMPLE` или `INSUFFICIENT` (`NOT_GATED` допустим). Старые сохранённые анализы не имеют метки и могут быть `VALID` и `COMPLETE` при малой выборке, поэтому они остаются допустимыми кандидатами statistical baseline (`BaselineComparison.kt:97-112`). **Решение владельца (Q11): да.** Отбор кандидатов statistical baseline требует присутствия блока `verdict_gates` в identity анализа; анализ без него считается «режим выборки неизвестен» и исключается до повторного анализа. Это меняет отбор для старых анализов и оформляется вместе с ADR 0019.

| --- | --- | --- | --- |
| Только `min_samples` в правиле; отсутствие поля сохраняет прежнюю оценку, opt-in | Меняется лишь `policy_sha256`, которого нет в ключе сопоставимости. | Нет. | Дефект существующих политик остаётся. |
| Запасные константы ядра default-on, значения по умолчанию политики и поле правила; условный блок `verdict_gates` (запасные константы) вне `SEMANTIC_FIELDS` — **выбрано владельцем (Q3)**; фактические значения политики входят в `policy_sha256` | Меняется `analysis_id` каждого нового анализа с политикой; старые анализы неизменны. | Нет: ключ сопоставимости не меняется. | Вердикт существующей политики в новом анализе может получить метку или стать `NO_VERDICT`. |
| Константы в `limits` либо повышенная версия `policy-evaluation` | Меняется `limits` или `modules`, входящий в ключ. | Да, для затронутых протоколов. | Отклоняется как лишний переход identity; ADR 0017 требует отдельного повторного закрепления при каждом таком переходе. |

`policy_sha256` входит в identity (`AnalysisResult.kt:43`), но не в `SEMANTIC_FIELDS` (`BaselineComparison.kt:942-943`). Детали рекомендованного блока — раздел 8.

## 2. Область «сервис x плечо» и binding политики

Единица итогового вердикта — анализ **одного плеча**; плеч может быть любое число (1, 2, 3 и более). ADR 0014 уже определил по одному снимку и анализу на плечо, метку `arm` у рядов и условный `resource_arm` в identity; эти срезы ещё требуется реализовать (`0014:484-540`). ADR 0018 зависит от них, но не переопределяет их контракт.

Одна политика протокола применяется ко всем анализам плеч одного прогона, пока ожидаемые сервисы и пороги плеч одинаковы (решение владельца Q8): `policy_sha256` одинаков, хэши снимков и `resource_arm` различаются. Поля `arm` в платформенном правиле нет. Опечатка в таком поле могла бы тихо отключить проверку плеча и дать ложный `PASS`. Если наборы сервисов или пороги плеч различаются, используются два (или больше) явных файла политики, без `arm` внутри правила; ядро при этом не меняется.

### Выбор политики на запуск и несколько политик

Политика выбирается при каждом запуске анализа; ядру она заранее не известна. CLI: `ltv analyze --policy <файл>` (`CommandLine.kt:116-119`, `:190`); API: часть multipart `policy` в `POST /api/jobs` (`LocalApi.kt:1216-1223`); интерфейс: поле `Policy file` экрана запуска (`ui/src/RunSetup.vue:104-115`). Библиотеки политик, версионирования и привязки политики к протоколу или системе в продукте нет (это отдельная работа плана владельца вне репозитория). Решение владельца Q4: допускается **несколько разных политик** (по протоколам и системам). Это согласуется с текущим выбором без изменения ядра: каждая политика — отдельный файл `policy.v1` со своим `policy_id`, нужный файл указывается при запуске; различие политик в identity — `policy_sha256`, поэтому два анализа одной нагрузки под разными политиками имеют разные `analysis_id`. При нескольких плечах пользователь передаёт анализу каждого плеча тот же файл (или, при различии сервисов и порогов, файл этого плеча). Риск ошибки выбора файла для плеча остаётся: UI должен показывать `policy_id` и хэш рядом с вердиктом. Ключ сопоставимости baseline от политики не зависит (`policy_sha256` не входит в `SEMANTIC_FIELDS`), поэтому сравнение анализов под разными политиками формально допустимо; правила выбора baseline по политике относятся к ADR 0019.

Область платформенного правила имеет форму `{"kind":"service","services":["a","b"]}`. Список непустых точных имён — список **ожидаемых** сервисов, поэтому отсутствие сервиса обнаруживается. Один элемент `platform_rules[]` является шаблоном проверки для каждого сервиса списка, а не 20 скопированными правилами. При 20 сервисах и 6–7 сигналах это 120–140 развёрнутых проверок; копирование правил приблизило бы политику к пределу 256 (`Policy.kt:31`, `ResourceSnapshot.kt:656`). Wildcard и regex не вводятся.

Для пары «правило × сервис» binding ищет в снимке ряд с точными `metric = signal`, `entity = имя сервиса`, `role = system`. Нужен ровно один ряд и совпадающая `unit`. Binding не опирается на случайное совпадение `series_id`.

| Состояние пары | Рекомендуемый исход |
| --- | --- |
| Ровно один ряд с нужной единицей | Развернуть в `ResourceRuleV1` с `seriesId` найденного ряда. |
| Ряда нет, включая отсутствующий ожидаемый сервис | `NO_VERDICT`, `RESOURCE_SERIES_NOT_FOUND`; существующий ресурсный код причины (`ResourceStatistics.kt:260`). |
| Подходит больше одного ряда | `NO_VERDICT`, новый `PLATFORM_SERIES_AMBIGUOUS`; не выбирать первый. |
| Ряд найден, но `unit` отличается | `NO_VERDICT`, новый `PLATFORM_UNIT_MISMATCH`; единицы не конвертируются. |
| Политика содержит `platform_rules`, снимок не передан | `NO_VERDICT`, `RESOURCE_SNAPSHOT_REQUIRED`, если есть хотя бы одно правило `effect=sla`; заявленная проверка не отбрасывается. |
| Агрегация ряда не равна заявленной в правиле | `NO_VERDICT`, новый `PLATFORM_AGGREGATION_MISMATCH` (см. раздел 3). |

Исходы binding в таблице относятся к правилам `effect=sla`. Для `effect=diagnostic` те же ситуации не блокируют вердикт: статус проверки `NO_VERDICT` не входит в SLA-свёртку, причина попадает в coverage и finding/evidence, как у нынешних diagnostic-правил (`ResourceStatistics.kt:62-72`); без снимка diagnostic-только политика даёт причину в coverage, а не `NO_VERDICT`.

После binding правило разворачивается в обычное `ResourceRuleV1` с детерминированным id `<rule.id>/<service>`, затем оценивается существующим `evaluateRule` через `evaluateResources` (`ResourceSnapshot.kt:69-77`, `ResourceStatistics.kt:21-74`, `:251-319`). Валидатор проверяет предел id 128 байт UTF-8 и отсутствие коллизий после разворачивания. Сохраняется тип evidence `resource_policy_check`; к нему добавляются `platform_rule_id` и `service`. Новый вычислитель и новый столбец вердикта не нужны.

Число развёрнутых правил вместе с допустимыми diagnostic-правилами снимка должно укладываться в существующий предел 256 ресурсных правил **на оценку**. Предварительный бюджет evidence ADR 0014: `E = W × (S + R)`, `E_max = 20 480` (`0014:1019`). Например, `6 × (290 + 140) = 2 580`; `64 × (290 + 140) = 27 520` превышает предварительный бюджет и при его реализации должно отвергаться как `RESOURCE_LIMIT_EXCEEDED`. Нельзя представлять `E_max` как уже измеренный и реализованный предел.

**Один владелец SLA-порога.** Если политика содержит `platform_rules`, ни снимок, ни профиль источника не могут одновременно поставлять ресурсные правила `effect=sla`: комбинация отвергается до анализа с `PLATFORM_RULES_CONFLICT`, код CLI 4. `effect=diagnostic` в снимке остаётся допустимым, в том числе guard генератора ADR 0009 (`docs/adr/0009-explicit-capacity-stages.md:34-35`). Если `platform_rules` нет, прежний путь SLA-правил снимка и профиля сохраняется. Миграция переносит пороги из снимка/профиля в политику; дальнейшая правка порога меняет `policy_sha256`, а не semantic hash снимка. К последнему уже привязаны планы трендов, capacity и diagnostics (`TrendPlan.kt:100`, `CapacityPlan.kt:117`, `DiagnosticPlan.kt:166`).

Сайдкары учитываются как часть сервиса. Запрос профиля источника сворачивает поды и контейнеры в один ряд на `service × signal`, `entity` равен имени сервиса. Для давления применяется максимум, для событийных счётчиков сумма, для недоступных реплик максимум по обслуживающим сервис workload. Ядро не знает контейнеров внутри ряда. Цена такой свёртки — потеря различимости контейнеров; артефакт по подам относится к ADR-D. Необязательные ряды «худший сайдкар» соответствуют варианту C ADR 0014 (`0014:59-63`). БД проходит тот же binding с `entity` имени БД как сервиса; владелец объявляет её сигналы, по умолчанию diagnostic.

## 3. Правила платформы

Рекомендуемая форма элемента `platform_rules[]`: `id`, `signal` (точное значение `series.metric`), `scope`, `operator`, `threshold`, `unit`, обязательное `aggregation` (`interval_mean`, `interval_rate` или, после соответствующего среза ADR 0014, `interval_max`/`interval_min`), `min_consecutive_cells`, `effect`, необязательное `window_ids`. Поле `aggregation` фиксирует, по какому смыслу значений автор правила задал порог; binding требует равенства с `aggregation` найденного ряда, иначе `NO_VERDICT` `PLATFORM_AGGREGATION_MISMATCH`. Вычислитель сам агрегацию не проверяет (`ResourceStatistics.kt:290-319`), поэтому без этого поля сглаженный пик давал бы ложный `PASS`. `operator = gt | lt` означает **условие нарушения**, как в ресурсных правилах (`ResourceStatistics.kt:298-302`). У бизнес-правил `lte | gte` означает условие прохождения (`Policy.kt:117-121`). Редактор и карточка обязаны различать эти смыслы. ADR не фиксирует SLA-пороги: их задаёт владелец в политике. Имена новых `series.metric` ниже рабочие и уточняются с профилем источника в срезе P0; ядро не выводит по имени единицу, знаменатель или эффект.

| Сигнал | Определение, источник, единица | Свёртка в сервис и ряд | Форма правила и эффект по умолчанию | Оговорка |
| --- | --- | --- | --- | --- |
| Близость памяти к лимиту: `openshift_memory_limit_ratio` (рабочее имя) | Для каждого контейнера, включая сайдкары: memory working set / объявленный Kubernetes/OpenShift memory limit; `ratio`. Это отношение величин одного контейнера, а не отношение сумм по сервису. | Максимум отношений по контейнерам и подам: порог «по каждому поду отдельно» сводится к максимуму по подам; для проверки всплеска — `interval_max`. | `gt 0.80` (базовый профиль владельца, переопределяется), `min_consecutive_cells` в ячейках; `sla`. | Если limit не задан или не получен, ряд отсутствует либо имеет пропуски: `NO_VERDICT`, а не ноль. Владелец может понизить сигнал до `diagnostic`. До среза `interval_max` доступен лишь `interval_mean`: среднее сглаживает пики. Владелец может осознанно объявить `aggregation = interval_mean` в правиле (выбор попадает в `policy_sha256`, запись в provenance снимка), но SLA «по пику» до появления `interval_max` не заявляется; при автошаге ADR 0014 сбор такого правила отказывается до сети (`0014:1092-1105`), поэтому пара шагов фиксируется явно. |
| Близость CPU к лимиту: `openshift_cpu_limit_ratio` (рабочее имя) | Для каждого контейнера: использование CPU / объявленный CPU limit; `ratio`. | Максимум отношений по контейнерам и подам; уровневая величина, поэтому `interval_mean` (ADR 0014 оставляет ЦП средним). | `gt 0.40` (базовый профиль владельца, переопределяется); `sla`. | Если CPU limit не задан, ряд отсутствует: `NO_VERDICT`, а не ноль; владелец может понизить сигнал для таких сервисов до `diagnostic`. Единица «под» против «контейнер» уточняется (вопрос 3 раздела «Открытые вопросы владельцу»). |
| Рост памяти / утечка | `openshift_memory_working_set`, JVM Old Gen, non-heap и headroom; единицы соответствуют рядам. | Описательный `trend-plan.v1`, а не SLA-правило платформы. | `diagnostic`; вывод «наблюдается тренд», не причинный диагноз. | L0 не годится для пилы после рестартов: результат зависит от фазы окна (`docs/adr/0011-trend-plan-l0-materiality.md:123-140`). |
| OOM: `openshift_oom` | Приращение счётчика OOM за время / секунды; `events/s`. | Сумма событий по подам и контейнерам; `interval_rate`. | `gt 0`, `min_consecutive_cells = 1`; `sla`. | Сброс счётчика при пересоздании пода и потеря первого приращения нового ряда **не проверены на стенде**. Запрос профиля применяет `increase`/`rate`; это проверяется на реальных данных. Для `gt 0` по неотрицательному `interval_rate` усреднение интервала не скрывает событие (среднее положительно, если приращение положительно), но правило автошага ADR 0014 отвергает `gt` на агрегации не `interval_max`; для OOM и рестартов нужен либо фиксированный шаг без автошага, либо исключение для неотрицательных событийных приращений; **ожидает подтверждения владельца (вопрос 1 раздела «Открытые вопросы владельцу»)**. |
| Перезапуски: `openshift_restarts` | Приращение счётчика рестартов подов/контейнеров, включая сайдкары, / секунды; `events/s`. | Сумма по сервису; `interval_rate`. | `gt 0`, `min_consecutive_cells = 1`; `sla`. | Те же не проверенные эффекты сброса счётчика. Плановый rollout исключается областью окон, а не скрытым исправлением ряда. |
| CPU throttling: `openshift_cpu_throttling` | Доля throttled CPU periods от всех CPU periods за интервал; `ratio`; нулевой знаменатель даёт пропуск. | Отношение считается для контейнера, затем максимум по контейнерам сервиса; для пиков — `interval_max`. | `gt` порога владельца; `diagnostic` (решение владельца: остаётся diagnostic, если нет иного указания). | Это симптом; его влияние на задержку отражают бизнес-метрики. Повышение до `sla` — отдельный выбор владельца. |
| Доступность: `openshift_unavailable_replicas` | `desired - available` из состояния workload сервиса; `count`. | Максимум по относящимся к сервису workload, затем максимум в интервале. | `gt 0`, `min_consecutive_cells >= 2`; `sla`. | Единый нулевой порог не требует разного `pod_count` для каждого сервиса. Ряд обязателен в профиле P0: агрегат `max by` по оставшимся подам не показывает пропавший под. Краткий rollout допускается длиной серии. |
| JVM heap/headroom, Old Gen, non-heap, GC, пулы; `openshift_pod_imbalance`, сеть, файловая система, БД | Определение и единица задаются отдельным запросом профиля. | По смыслу конкретного ряда; без неявной агрегации в ядре. | `diagnostic` по умолчанию. | Повышение до `sla` возможно лишь после определения источника, единицы, знаменателя и покрытия. |

Для события `gt 0` важно получать именно **приращение за интервал**, а не накопленный счётчик: иначе один старый OOM давал бы нарушение в каждом следующем окне. Для availability важно сравнивать `desired` и `available`, а не принимать присутствующие поды за полный состав сервиса. До реализации профиля P0 эти значения и гарантия покрытия не проверены.

**Покрытие pod→service.** Ядро не интерпретирует имена сигналов, поэтому сама политика объявляет сигнал покрытия: при непустом `platform_rules` обязателен необязательный в остальном верхнеуровневый объект `platform_coverage` с полем `signal` (рекомендуемое значение `openshift_unavailable_replicas`). Валидатор требует, чтобы каждый сервис из любой области `platform_rules` входил и в область правила `effect=sla` по этому сигналу, иначе `PLATFORM_COVERAGE_MISSING`. Так пропавший под не может дать `PASS` по непрерывному ряду памяти из-за забытого правила доступности; но ядро по-прежнему не проверяет, что запрос профиля честно считает desired минус available. Это граница гарантии, не более.

Только `effect=sla` входит в вердикт. Нарушение diagnostic-правила остаётся в findings, а его пропуски попадают в coverage (`ResourceStatistics.kt:62-64`). `min_consecutive_cells` считает соседние нарушающие **ячейки**, не секунды; в строгом режиме пропуск обрывает серию (`ResourceStatistics.kt:269-296`), при допуске пропусков действует правило раздела 5. Длительность равна числу ячеек, умноженному на шаг снимка. При автошаге ADR 0014 она меняется; подписи UI и документация должны показывать шаг, иначе тот же численный минимум воспринимается как прежняя длительность. Эффект `interval_max` — серия интервалов с пиками, не непрерывное превышение внутри каждого интервала (`0014:1092-1125`).

### Базовый профиль SLA платформы

Владелец задал базовые значения (2026-10-02): CPU не выше 40 % от CPU limit **каждого пода отдельно**; память не выше 80 % от memory limit каждого пода; OOM и рестарты равны нулю; оценка на каждом плече отдельно; CPU throttling остаётся diagnostic. Значения переопределяются протоколом и настраиваемы. Это **предустановка политики, а не вшитые в ядро правила**: ядро не добавляет правила неявно, потому что тогда вердикты менялись бы без изменения политики, а ядро пришлось бы учить смыслу имён сигналов. Предустановка поставляется как пример `docs/contracts/policy/v1/examples/valid/` и как шаблон редактора политики (срез U4), копируется в политику протокола, и дальше действует то, что записано в политике.

| Правило | Сигнал (рабочее имя) | Условие нарушения | Агрегация ряда | effect |
| --- | --- | --- | --- | --- |
| CPU | `openshift_cpu_limit_ratio` | `gt 0.40` | `interval_mean` | `sla` |
| Память | `openshift_memory_limit_ratio` | `gt 0.80` | `interval_max`; до среза ADR 0014 — `interval_mean` с оговоркой раздела 3 | `sla` |
| OOM | `openshift_oom` | `gt 0` | `interval_rate` | `sla` |
| Рестарты | `openshift_restarts` | `gt 0` | `interval_rate` | `sla` |
| CPU throttling | `openshift_cpu_throttling` | порог задаёт протокол | `interval_mean` | `diagnostic` |
| Покрытие (`platform_coverage`) | `openshift_unavailable_replicas` | `gt 0` | `interval_max` | `sla` |

Строка покрытия добавлена автором как следствие требования `platform_coverage` (выше), в списке владельца её не было. `min_consecutive_cells` не задан владельцем: это параметр шаблона. Сервисы перечисляются явно (wildcard нет); применять ли CPU 40 % ко всем сервисам или к выбранным — открытый вопрос. «По каждому поду отдельно» выражается так: ряд сервиса — максимум отношения по подам (и контейнерам), поэтому порог пода превышен тогда и только тогда, когда превышен порог ряда; какой именно под, ряд не показывает (артефакт по подам — ADR-D). Предположение, не подтверждённое владельцем: лимиты в Kubernetes задаются на контейнер, поэтому отношение считается по контейнеру, а не по сумме контейнеров пода.

## 4. Окно правила и стадии

Сегодня все бизнес- и ресурсные правила проверяются в каждом окне (`WindowPolicy.kt:25-42`, `ResourceStatistics.kt:33-47`). Окна либо явно перечислены в снимке, либо образуют `run-intersection` (`ResourceSnapshot.kt:143-184`). При неявном окне разгон и завершение входят в оценку. Автоопределение стационарных стадий не вводится: ADR 0009 отверг автоматический детектор и использует явные ступени (`docs/adr/0009-explicit-capacity-stages.md:1-35`).

Рекомендуется считать стадией именованное окно `snapshot.windows`. Необязательный массив уникальных `window_ids` добавляется бизнес- и платформенному правилу; каждый id не длиннее 128 байт UTF-8. Нет поля — правило действует во всех окнах, сохраняя старое поведение. Есть поле — правило участвует только в названных окнах. Уровневого `default_window_ids` в политике нет: несколько повторённых id яснее второго механизма умолчаний.

Если в окне нет применимых бизнес-правил, бизнес-часть получает `NO_POLICY`, а не пустой `PASS`, который сейчас получился бы из ветки `else` после фильтрации всех правил (`Policy.kt:101-142`). Пустое окно без применимых бизнес-правил не должно затем принудительно превращаться в `BUSINESS_OBSERVATIONS_NOT_FOUND`: нынешний оконный gate (`WindowPolicy.kt:28-33`) применяется лишь когда есть правило, которому нужны наблюдения. Ресурсная часть уже даёт `NO_POLICY` при отсутствии SLA-правил (`ResourceStatistics.kt:66-72`).

Неизвестный id окна при binding даёт `NO_VERDICT` с `RULE_WINDOW_NOT_FOUND`, по образцу `TRANSACTION_NOT_FOUND`; это зависит от предъявленного снимка, поэтому одна лишь валидация JSON политики не может решить вопрос. Бизнес-правило с `window_ids` при анализе без снимка получает ту же причину: названных окон нет. Для **развёрнутого платформенного** правила окно с меньшим числом ячеек, чем `min_consecutive_cells`, даёт `NO_VERDICT` с `RULE_WINDOW_TOO_SHORT`. Иначе проверка физически не может найти достаточную серию и ложно даёт `PASS` (`ResourceStatistics.kt:269-270`, `:315-319`). Исправление такого случая для существующих правил снимка и профиля здесь не выполняется.

Для протокола 4–8 часов рекомендуется явно назвать стационарные стадии и привязать SLA-правила к ним. Редкую транзакцию следует проверять в тех стадиях, где она действительно вызывается и достигает своего `min_samples`; объединять её с пустой стадией только ради общего окна нельзя. `throughput_rps` по-прежнему делится на полную длительность соответствующего окна (`docs/adr/0005-resource-window-sla.md:12-19`; `docs/user/slice-1-local-analysis.md:606-611`). Конкретные стадии остаются решением владельца протокола.

## 5. Пропуски данных

Сегодня любой `null` в окне SLA-правила обрывает серию и даёт `NO_VERDICT` с `MISSING_RESOURCE_CELLS`, даже если отдельная серия нарушений уже найдена; findings сохраняются (`ResourceStatistics.kt:290-319`). Отсутствующие данные источника должны оставаться пропусками, а не нулями (`docs/adr/0007-opt-in-online-sources.md:17-19`). Карточка F1 уже показывает найденное нарушение при `NO_VERDICT` (`verdictSummary.ts:295-301`). Решение владельца 2026-10-02: пропуски на практике случаются; нужны детекция, предупреждение с долей покрытия и **настраиваемый допуск**.

Правила D6.

1. **Детекция и предупреждение.** Для каждой проверки платформенного правила в окне публикуются `expected_cells`, `missing_cells`, `longest_gap_cells` и доля покрытия (аддитивные поля evidence `resource_policy_check`; те же счётчики уже есть в `resource_summary`, `ResourceStatistics.kt:151-154`). Причина `RESOURCE_GAPS` (уже существует, `ResourceStatistics.kt:132`) остаётся информационной: попадает в coverage, не блокирует вердикт, карточка F1 показывает долю покрытия.
2. **Допуск** действует только для платформенных правил `effect=sla`; правила снимка и профиля остаются строгими. Параметры `max_missing_fraction` (число от 0 до 1) и `max_gap_cells` (целое не меньше 0) задаются в `defaults` политики и переопределяются в правиле. Если доля пропущенных ячеек окна не больше `max_missing_fraction` **и** самый длинный разрыв не длиннее `max_gap_cells`, правило оценивается по наблюдённым ячейкам (`PASS` или `FAIL`) с причиной `RESOURCE_GAPS` (coverage `INCOMPLETE`, поэтому анализ не попадает в кандидаты statistical baseline); иначе `NO_VERDICT` с существующим `MISSING_RESOURCE_CELLS`, находки сохраняются. Значения `0` и `0` дают прежнее строгое поведение.
3. **Предлагаемые умолчания** (запасные константы ядра, пишутся в `verdict_gates`): `max_missing_fraction = 0.05`, `max_gap_cells = 3`. Это **предложение автору владельца, владелец числа не подтверждал**.
4. **Серия через пропуск.** При допуске пропущенные ячейки между двумя нарушающими ячейками входят в длину серии (консервативно): иначе одна пропущенная ячейка внутри нарушения разрывала бы серию и давала ложный `PASS` (`ResourceStatistics.kt:293-296`). Пропуск на краю серии её не продлевает. Это единственное изменение вычислителя, и оно действует только в режиме допуска.
5. **Граница `PASS` при допуске.** `PASS` не доказывает отсутствия нарушения внутри допущенного пропуска (при шаге 15 с и трёх ячейках это до 45 с); это сознательно принятый риск допуска.

Покрытие платформы учитывается по `service × signal × window × arm` **до** свёртки pod→service на границе профиля: профиль обязан представить ожидаемый сервис и его доступность. При этом ядро получает только сервисный ряд и не может самостоятельно доказать, что запрос не потерял один из подов. Сигнал покрытия `platform_coverage` (раздел 3) — обязательная защита от случая, когда `max by` по сохранившимся подам выглядит непрерывным после исчезновения другого пода.

| Наблюдение | Причина | Влияние на SLA-вердикт |
| --- | --- | --- |
| Ожидаемый сервис или его сигнал не дал ряда | `RESOURCE_SERIES_NOT_FOUND` | `NO_VERDICT` |
| Более одного ряда подходят к точной паре | `PLATFORM_SERIES_AMBIGUOUS` | `NO_VERDICT` |
| Единица ряда не совпадает с правилом | `PLATFORM_UNIT_MISMATCH` | `NO_VERDICT` |
| Нет снимка для объявленных `platform_rules` с `effect=sla` | `RESOURCE_SNAPSHOT_REQUIRED` | `NO_VERDICT` |
| В связанном ряду `null` в пределах допуска (`max_missing_fraction`, `max_gap_cells`) | `RESOURCE_GAPS` (информационно) | Оценка по наблюдённым ячейкам, `PASS` или `FAIL`; coverage `INCOMPLETE` |
| Пропуски сверх допуска (или допуск 0/0) | `MISSING_RESOURCE_CELLS` | `NO_VERDICT`; найденные нарушения остаются в findings |
| То же у `effect=diagnostic` | Причина остаётся в coverage | Само diagnostic-правило не меняет вердикт |
| Сервисный ряд непрерывен, но исчез под до агрегации | Обнаруживается рядом `unavailable_replicas`, если профиль его поставил | SLA-проверка availability; гарантия профиля ещё не проверена |

Частота пропусков на реальных длительных прогонах не измерена (пункт 9 плана замера ADR 0014 не выполнен, `0014:1128-1130`): предложенные 5 % и 3 ячейки подлежат проверке на стенде. Допуск не меняет приоритета `NO_VERDICT` над `FAIL` (раздел 6): пропуск в пределах допуска не является `NO_VERDICT`, пропуск сверх допуска — является.

## 6. Свёртка business x resource x platform по окнам и плечам

Рекомендуемая свёртка использует существующую структуру результата. В **каждом анализе плеча** для каждого окна:

1. Бизнес-часть сворачивает применимые правила: блокирующий `NO_VERDICT`, затем найденный `FAIL`, затем `PASS`; нет применимых правил — `NO_POLICY`.
1. Ресурсная часть сворачивает `effect=sla` из снимка **либо** развёрнутые платформенные правила. Diagnostic-правила не участвуют. Порядок уже реализован как `NO_VERDICT > FAIL > PASS`, пустой список — `NO_POLICY` (`ResourceStatistics.kt:46-72`).
1. `jointVerdict` соединяет бизнес- и ресурсный вердикты окна: `NO_VERDICT` побеждает, оба `NO_POLICY` дают `NO_POLICY`, затем побеждает `FAIL`, иначе `PASS` (`WindowPolicy.kt:46-55`).
1. `overallVerdict` сворачивает окна: любой `NO_VERDICT`, затем все `NO_POLICY`, затем любой `FAIL`, иначе `PASS` (`WindowPolicy.kt:57-63`).

Платформенные правила являются ресурсными после binding, поэтому отдельного третьего столбца в `window_policy_summary` нет; существующие `business_verdict` и `resource_verdict` сохраняют смысл (`WindowPolicy.kt:65-80`). Между плечами ядро ничего не сворачивает и не сохраняет «вердикт стенда»: UI показывает независимые вердикты каждого плеча (число плеч любое) и одну общую бизнес-часть, как требует ADR 0014 (`0014:582-589`). **Решение владельца Q10:** сначала независимые вердикты без общего заголовка «все плечи»; если заголовок понадобится позже, он будет производным только в UI и должен быть помечен как производный.

Приоритет `NO_VERDICT` над `FAIL` уже принят для политики: ADR 0003 прямо задаёт `NO_VERDICT`, если транзакция не найдена или неоднозначна, даже при провале другого правила (`docs/adr/0003-policy-v1-metrics-evidence.md:133-141`). ADR 0005 сохраняет находки при таком вердикте (`docs/adr/0005-resource-window-sla.md:12-19`). F1 показывает их рядом с причиной, по которой вердикт пока не выдан. **Решение владельца Q5: вариант K, порядок сохраняется**, найденное нарушение показывается.

| Случай | K: сохранить `NO_VERDICT > FAIL`, **выбран владельцем** | C: установленный `FAIL` побеждает пропуск (отклонён) |
| --- | --- | --- |
| В одном окне R1 нашло SLA-нарушение, R2 имеет пропущенную ячейку | Итог окна `NO_VERDICT`, код CLI 3; finding R1 виден. | Итог мог бы стать `FAIL`, код 2, лишь если нарушение R1 уже окончательно доказано. |
| Одно плечо имеет `FAIL`, другое — `NO_VERDICT` | Сохраняются независимые вердикты каждого плеча; общего заголовка нет. | Независимые вердикты в ядре остаются; возможный будущий производный заголовок при ином приоритете был бы `FAIL`. |
| `TRANSACTION_NOT_FOUND`, `AMBIGUOUS_TRANSACTION`, `RULE_WINDOW_NOT_FOUND`, неоднозначный платформенный ряд либо `INVALID`/`DEGRADED` вход | `NO_VERDICT` | Тоже `NO_VERDICT`: структурная привязка или валидность не восстанавливается найденным нарушением. |

Аргумент в пользу C ограничен: для ресурсного правила уже найденная серия из `min_consecutive_cells` подряд нарушающих наблюдённых ячеек не исчезнет при заполнении других пропусков. Для бизнес-перцентиля, доли ошибок и throughput результат при неполных наблюдениях не обладает той же монотонностью. Поэтому C потребовал бы специального режима только для доказанного ресурсного нарушения и валидного бизнес-прогона. Он меняет ADR 0003 и ADR 0005, результаты существующих входов и golden-тесты; повышение версии `policy-evaluation` меняет `modules` ключа сопоставимости и требует отдельного повторного закрепления baseline по ADR 0017. Копирайт F1 тоже пришлось бы изменить. Выбор K оставляет этот переход вне ADR 0018.

## 7. Версия схемы политики и совместимость

Выбран вариант A (решение владельца Q4): аддитивно расширить `policy.v1` на месте. Поля `min_samples` и массив `window_ids` необязательны у бизнес-правила; верхнеуровневые `defaults`, `platform_rules` и `platform_coverage` необязательны. Существующий обязательный непустой `rules` остаётся: политика только с `platform_rules`, без бизнес-правил, невозможна (решение владельца Q13; `Policy.kt:429-447`; `policy.schema.json:4-27`). `schema_version` и `input_versions.policy` остаются `policy.v1` (`AnalysisResult.kt:95-104`). Старый валидный JSON сохраняет прежние canonical bytes и `policy_sha256`, так как валидатор хэширует исходный canonical JSON (`Policy.kt:61-70`); **оценка** старого файла может измениться из-за default-on gate раздела 1. Новый файл старый строгий читатель отвергнет как `UNKNOWN_FIELD` (`Policy.kt:429`, `:444`, `:544`), что безопаснее тихого игнорирования. Несколько политик по протоколам и системам — это несколько файлов `policy.v1` (раздел 2), версия схемы для этого не меняется.

| Вариант | Выгода | Цена и решение |
| --- | --- | --- |
| A. Расширить `policy.v1` на месте — **выбран владельцем** | Один файл на протокол; свойства бизнес-правила остаются в самом правиле; `input_versions.policy` и ключ сопоставимости не меняются. | Это сознательное ослабление замороженного v1. Старые читатели не читают новые файлы; схема, редактор и документация меняются совместно. |
| B. Ввести `policy.v2` | Читатель явно отказывает по версии; граница контракта чище. | Изменяется `input_versions.policy`, входящий в ключ baseline (`BaselineComparison.kt:942-943`); при миграции протокола нужно повторное закрепление. Существующие редактор и подсказка для ИИ привязаны к v1 (`docs/user/slice-1-local-analysis.md:361-366`, `:483-498`). |
| C. Отдельный `platform-policy.v1` | Не меняет форму `policy.v1` для платформенных правил. | Второй файл и хэш, новый вход multipart job; `min_samples` и `window_ids` бизнес-правил всё равно требуют изменения политики, а прежнее владение SLA в снимке остаётся проблемой. |

ADR 0005 прямо говорил, что `policy.v1` остаётся неизменным (`docs/adr/0005-resource-window-sla.md:12-19`, `:34-37`). ADR 0009 оставил guard в ресурсных diagnostic-правилах (`docs/adr/0009-explicit-capacity-stages.md:34-35`); ADR 0011, как это пересказывает ADR 0014, отверг расширение `resource-snapshot.v1` «новым видом правила» ради необязательной возможности, которую можно вынести в отдельный план (`docs/adr/0014-resource-series-limits-autostep-arm-api.md:167-193`). Здесь `min_samples` и `window_ids` являются свойствами самого правила политики, а платформенное SLA-правило должно разделять с бизнес-правилами владение протоколом. Это обоснование выбора A, а не утверждение, что прежние ADR уже разрешили его. Переход к v2 требуется при смене смысла существующего поля или оператора, новом обязательном поле либо несовместимой свёртке.

Рекомендуемые проверки нового контракта:

| Поле или связь | Проверка |
| --- | --- |
| `defaults` | Необязательный объект с полями `sample_floor` и `min_samples` (целые 1..1 000 000), `max_missing_fraction` (0..1), `max_gap_cells` (целое 0..100 000); неизвестные поля отвергаются. |
| `min_samples` | Целое 1..1 000 000; не ниже действующего пола, иначе `MIN_SAMPLES_BELOW_FLOOR`; для правил throughput поле неприменимо. |
| `max_missing_fraction`, `max_gap_cells` в правиле платформы | Необязательны; перекрывают `defaults`; допустимы только у `platform_rules` и только при `effect=sla` (иначе неприменимое поле). |
| `platform_rules[].scope` | Только `kind=service`, непустой массив уникальных точных имён, каждое до 128 байт UTF-8, не более 64 сервисов на правило; нарушение — `INVALID_SCOPE`. |
| `id` | Уникален совместно в `rules` и `platform_rules`; существующий `DUPLICATE_RULE_ID` расширяется на оба массива. Проверяется и длина развёрнутого `<id>/<service>`. |
| `window_ids` | Непустой массив уникальных id до 128 байт UTF-8, если поле присутствует; неверная форма — `WINDOW_IDS_INVALID`. Существование id проверяется при binding со снимком. |
| `platform_coverage` | Обязателен при непустом `platform_rules`; `signal` — непустая строка до 128 байт; каждый сервис области покрыт `effect=sla` правилом по этому сигналу, иначе `PLATFORM_COVERAGE_MISSING`; `aggregation` в правиле платформы обязателен и принадлежит набору из раздела 3. |
| Общее число проверок | После разворачивания выполняются предел 256 ресурсных правил и бюджет evidence раздела 2; переполнение — `RESOURCE_LIMIT_EXCEEDED`. |
| Бизнес-метрики | Четыре существующие метрики и сочетания `lte`/`gte` не меняются (`Model.kt:37-51`, `Policy.kt:449-463`). |

Редактор политики в срезе U4 и нормативная подсказка для ИИ должны поддерживать и сохранять `defaults`, `platform_rules`, `platform_coverage`, `min_samples`, `window_ids`. Нынешний редактор описан только для старых полей (`docs/user/slice-1-local-analysis.md:361-366`), а подсказка запрещает стадии и новые поля (`:483-498`); без её обновления правка или повторная генерация может молча потерять новые правила.

## 8. Влияние на identity

Identity строится как canonical JSON с `policy_sha256` и другими верхнеуровневыми ключами (`AnalysisResult.kt:26-58`). Ключ сопоставимости baseline выбирает лишь `source_type`, `engine`, `parsers`, `modules`, `input_versions`, `outputs`, `histogram`, `normalization`, `limits`; `policy_sha256` в этом списке нет (`BaselineComparison.kt:603-610`, `:942-943`).

| Вклад | Решение и следствие |
| --- | --- |
| Байты политики | Новые поля меняют `policy_sha256` только у файлов, которые их содержат. Развёрнутые правила детерминированно выводятся из политики и снимка; отдельный хэш разворачивания не нужен. |
| Запасные константы gate | Только при наличии политики добавить верхнеуровневый `verdict_gates` с запасными значениями `min_samples_floor`, `min_samples_default`, `max_missing_fraction_default`, `max_gap_cells_default`, `throughput_exempt`. Блок не входит в `SEMANTIC_FIELDS`. Фактические значения, заданные политикой (`defaults`, поля правил), входят в `policy_sha256`. |
| `analysis_id` и кэш | Из-за `verdict_gates` новый анализ с политикой получает иную identity и пересчитывается. Сохранённый старый анализ неизменяем. Анализ без политики (`NO_POLICY`) не меняется. |
| Сопоставимость baseline | Ключ остаётся прежним; автоматического повторного закрепления baseline из-за одного `verdict_gates` нет. Golden-тест обязан показать одинаковый ключ до и после. Риск старого закреплённого baseline с малой выборкой решает ADR 0019, см. раздел 1. |
| Версии | `input_versions.policy = policy.v1` остаётся (`AnalysisResult.kt:99`); `modules` не повышаются при рекомендуемой свёртке K. Помещение gate в `limits` изменило бы ключ. |
| Плечо | `resource_arm` и его включение в ключ относятся к отдельному срезу ADR 0014 (`0014:494-540`), не к этому изменению. |
| Результат | Появляются причины и аддитивные поля evidence; golden-фикстуры результата обновляются даже там, где итоговый `PASS`/`FAIL` не изменился. |

Это осознанный компромисс: новое default-on поведение меняет `analysis_id`, но не объявляет метрики другого поколения для baseline. ADR 0017 предписывает не совмещать изменения identity: срез gate выпускается отдельно от `resource_arm` и ADR 0016 (`docs/adr/0017-baseline-candidates-and-confirmation.md:173-180`). Этот компромисс подтверждён владельцем (Q3).

## Следствия

Рекомендуемый порядок реализации: сначала ADR 0016 с ограничением перцентиля максимумом и необходимые срезы ADR 0014 для плеча и `interval_max`; затем отдельные PR для (1) gate выборки, настраиваемых значений и режима, (2) окон правил, (3) правил платформы с допуском пропусков и предустановкой SLA. Порядок не превращает предварительный `E_max` в принятый предел. Production dependencies не добавляются. Публичные изменения — схема `policy.v1`, причины и аддитивное evidence результата, поведение CLI/UI и условный блок identity — фиксируются в плане реализации до кода.

| Альтернатива | Причина отклонения в рекомендуемом проекте |
| --- | --- |
| Сохранённый общий вердикт стенда в ядре | Владелец определил независимые вердикты плеч; смешение лишило бы анализ собственного смысла. Общий заголовок «все плечи» не вводится (решение владельца Q10). |

## Риски и непроверенное

- Пороги 20 и 100, а также допуск 5 % и 3 ячейки не калиброваны по прогонам стенда; потому они настраиваемы. Граница, на которой текущий HdrHistogram перестаёт давать p95, равный максимуму, не проверена; до ADR 0016 существует риск ложного `FAIL`.
- Сбросы OOM/restart-счётчиков и потеря первого приращения нового ряда после пересоздания пода на стенде не проверены. Смысл и запрос каждого сигнала должен быть зафиксирован профилем P0.
- Ядро не видит исходный состав подов после pod→service. Гарантия покрытия зависит от запроса, поставляющего `openshift_unavailable_replicas`; его отсутствие должно быть обнаружено проверкой ожидаемых рядов.
- `E_max = 20 480` предварителен. `interval_max` и `arm` приняты в ADR 0014, но ещё отсутствуют в `src/main`. Частота пропусков за реальные восьмичасовые прогоны неизвестна; `PASS` при допущенных пропусках не исключает нарушения внутри пропуска.
- Вариант 1 (выбран) не даёт отдельного кода возврата для малого `PASS`/`FAIL` (решение владельца Q6: коды 0/2): скрипт, читающий только exit code, не увидит режим и должен читать метку `SMALL_SAMPLE` в JSON. UI-тексты раздела 1 ориентировочные.
- Онлайн-сбор: один запрос даёт один ряд (ADR 0007), поэтому 120–140 проверок на плечо означают столько же запросов; предел профиля 32 запроса при 16 профилях (`0014:87-88`), то есть набор сигналов делится минимум на пять профилей на плечо. Полноту набора на каждом плече проверяет политика через binding (отсутствие ряда — `NO_VERDICT`).
- Capacity: оценка ступени читает вердикт окна и не проверяет `analysis_coverage` (`CapacityAnalysis.kt:139-141`), поэтому без правки ступень с `SMALL_SAMPLE` и `PASS` попала бы в границу ёмкости как подтверждённая. Решение владельца Q14 (раздел «Решения владельца (2026-10-02)»): ступень считается неподтверждённой при `n < min_samples`; при обычных ступенях не менее 20 минут это редкость.
- Старый вручную закреплённый baseline может иметь малую выборку без новой метки. Ключ сопоставимости это не меняет; отбор кандидатов statistical baseline требует `verdict_gates` (Q11), а ручной выбор и повторный анализ определяет ADR 0019.
- Выбор политики на запуск ручной: для анализа плеча можно передать не тот файл. Смягчение — показ `policy_id` и хэша рядом с вердиктом; библиотека политик вне объёма.
- Единица базового профиля SLA (под или контейнер) и применимость CPU 40 % ко всем сервисам не подтверждены владельцем.

## Открытые вопросы владельцу

1. **Q12, ожидает подтверждения владельца.** Пояснение. Правило автошага ADR 0014 (решение (a)) отказывает в сборе до сети, если автошаг огрубляет ряд с порогом `gt`, а агрегация ряда не `interval_max`. OOM и рестарты — неотрицательные приращения с условием «больше нуля»: усреднение интервала, сумма и максимум остаются положительными, если в интервале было хоть одно положительное значение, то есть событие не теряется (минимум обнулил бы его). Вариант 1: отдельной правкой ADR 0014 исключить такие неотрицательные событийные ряды из отказа. Вариант 2: не менять ADR 0014 и для этих сигналов запретить автошаг (фиксированный шаг). **Рекомендация автора: вариант 1.** До подтверждения действует вариант 2, как более строгий.
1. **Допуск пропусков: числа.** Предложение автора: `max_missing_fraction = 0.05` и `max_gap_cells = 3`. Владелец их не подтверждал; частота пропусков на стенде не измерена. Рекомендация: принять как стартовые запасные значения и пересмотреть по первым реальным прогонам.
1. **Базовый профиль SLA.** (а) Применять CPU 40 % к **всем** сервисам или только к выбранным? Рекомендация: список сервисов явный в политике протокола; предустановка содержит все сервисы протокола, но для тех, у кого нет CPU limit, правило понижается до `diagnostic`, иначе нет ряда и `NO_VERDICT`. (б) Единица «под»: отношение считается по контейнеру (лимиты Kubernetes задаются на контейнер, сайдкар со своим limit иначе скрыт) или по сумме контейнеров пода? Рекомендация: по контейнеру, с максимумом по контейнерам и подам. (в) Строка покрытия `openshift_unavailable_replicas` добавлена автором как следствие `platform_coverage`: оставить в предустановке?

## Не входит

Jenkins; артефакт с данными по подам (ADR-D); история релизов и правило «baseline только из `PASS`» (ADR 0019, которому передаётся требование об отсутствии правил в режимах `SMALL_SAMPLE` и `INSUFFICIENT`); библиотека и версионирование политик; печать хэша (ADR-E); ограничение советов ИИ (ADR-F); корреляции и их калибровка (ADR-G, фаза C); реализация автошага ADR 0014; новые production dependencies. Свёртка подов адаптером остаётся границей П-1 ADR 0014 (`0014:1173-1179`).

**REPORT-ONLY наблюдение вне объёма** (остаточный риск принят владельцем, Q9): у существующего ресурсного правила из `snapshot.rules` или профиля окно с числом ячеек меньше `min_consecutive_cells` не может создать finding и сейчас получает `PASS` (`ResourceStatistics.kt:269-270`, `:315-319`). Этот ADR предлагает защиту только для новых развёрнутых платформенных правил; старый путь не исправляется без отдельного решения владельца.
