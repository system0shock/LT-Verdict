## Ruling'и PR A

**P1. Предупреждение `WHOLE_RUN_METRICS_WITH_STAGES` уходит из PR A в PR C.** План относит его к PR A, но оно требует правки
`ui/src/types.ts` и `ui/src/shell/labels.ts`, а поручение для PR A исключает UI и видимость. Почему: R7 владельца отдаёт подписи
«весь прогон, справочно» PR C; серверное предупреждение и его UI-тип должны ехать вместе, иначе закрытое объединение
`BaselineComparisonWarning` разойдётся с ответом. Цена ошибки: в промежутке между PR A и PR C сравнение с эталоном двух
прогонов со стадиями не предупреждает; на практике вход со стадиями до PR B недоступен, поэтому окна появляются не раньше PR B.

**P2. Пустой список `stages` даёт `STAGES_NO_STEADY`**, а не `RESOURCE_LIMIT_EXCEEDED`: стадий меньше одной это отсутствие
стадии `steady`, и сообщение точнее. Верхняя граница (17 стадий) остаётся `RESOURCE_LIMIT_EXCEEDED`.

**P3. Смещение принимается как целое число по значению, не по написанию.** Токен `1e3` равен 1000 и канонизируется как
`1000` (хэш совпадает с написанием `1000`); дробное значение (`1500.5`) даёт `INVALID_TYPE`; целое вне `0..604800000` даёт
`INVALID_STAGE_OFFSET`. Почему: так ведёт себя валидатор плана динамики (`int` через `BigDecimal`), а канонические байты и хэш
не зависят от написания. Цена ошибки: нулевая, хэш считается от канонических байт.

**P4. `stage_binding` это типизированный вариант в НОВОМ семействе `StageEvidence`** (корень `sealed interface`, кодирование
`ITEM_JSON`), потому что корни `AnalysisEvidence` и `DerivedEvidence` закреплены тестами, перечисляющими подклассы. Образцы не
меняются. Стадия `excluded` не имеет `clipped_to_run_end` (поле опускается), у `steady` оно всегда есть (`true`/`false`).

**P5. Канонические байты объявления получаются из разобранной модели** (стадии отсортированы по `from_offset_ms`), поэтому
переставленный порядок стадий и иное написание чисел дают тот же `load_stages_sha256`. В каталог анализа пишутся эти байты.

**P6. `steady`, начинающаяся в `runEnd` или позже, даёт `STAGE_OUTSIDE_RUN` (`from >= runEnd`), а не только `from > runEnd`.**
Поправка владельца называет `from > runEnd`. Случай `from == runEnd` после обрезки даёт окно нулевой длины:
`WindowMetricsAccumulator` отвергает его (`INVALID_METRIC_WINDOW`), а throughput делится на ноль. Окно нулевой длины не содержит выборок
(выборка стартует раньше конца прогона), поэтому это «steady за концом прогона» по смыслу. Цена ошибки: стадия, начинающаяся ровно в
последнюю миллисекунду, даёт ошибку вместо пустого окна; владелец может вернуть строгое `>` вместе с обработкой нулевого окна.

**P7. Смещение проверяется по значению в таком порядке:** сканер (токен до 64 байт, экспонента до 64: `1e400` и 70-значное число дают
`RESOURCE_LIMIT_EXCEEDED`), затем целочисленность (`1500.5` даёт `INVALID_TYPE`), затем диапазон (`1e20` и `-1` дают
`INVALID_STAGE_OFFSET`). Образец плана динамики (`intValueExact` даёт `INVALID_TYPE` и для целого вне диапазона) не копируется.

**P8. Порядок `evidence` берётся из ADR 0030, а не из строки AC6 плана.** `stage_binding` стоит после метрик «весь прогон»
(`metric_summary` и `diagnostic` базовой оценки), там же, где в режиме снимка стоит `resource_binding`; так ведёт себя
`evaluateSharedWindowPolicy`, и ADR это называет. Строка AC6 «`stage_binding` первым» неверна. `window_metric_summary` по окнам
добавляются сразу после оконной оценки, до свидетельств источника (`source_summary`) и контекста postgres; порядок закреплён тестом
со стадиями и офлайн-контекстом источника.

**P9. Широкие числа (требование «1e400 через вклеивание»).** Все поля `StageBindingEvidence` это `Long`, `String` или `Boolean`,
поэтому `JsonUnquotedLiteral` не нужен; `stage_binding` и `window_metric_summary` идут внутри `evidence`, который
`encodeAnalysisResult` уже вклеивает без кодирования через kotlinx. Числа в `load-stages.v1` ограничены 604800000.

**P10. `tools/verify_slice0.py` не меняется.** Он проверяет только контракты run, result и incident; примеры планов (policy, resources,
trend, capacity) проверяются Kotlin-тестами. Примеры `load-stages.v1` проверяет `LoadStagesTest`. Схему JSON Schema нельзя
использовать для `OVERLAPPING_STAGES`, `DUPLICATE_STAGE_ID`, `STAGES_NO_STEADY` (это проверки валидатора, они описаны в `description`).

**P11. Платформенная политика без бизнес-правил невозможна:** `validatePolicy` отвергает пустой `rules` (`EMPTY_RULES`). Из трёх
тестов R4 остаются два (SLA вместе с бизнес-правилами; правило без SLA); третий («только платформенная политика») не существует.

## Критерии приёмки PR A

AC1-AC3, AC5 (без CLI/API), AC6 (порядок по P8), AC7, AC8, AC9 (только ядро: коды `STAGES_*_CONFLICT` и `STAGE_OUTSIDE_RUN` из сервиса и из
`analyzeWithSources`), AC10, AC11a (края оценки), AC12, AC13 (ранняя посторонняя выборка сдвигает окна, это видно по
epoch-границам `stage_binding`) и часть AC4: identity и результат без стадий равны прежним байтам (существующие golden-тесты
проходят без правок; новый `LoadStagesCompatibilityTest` проверяет отсутствие ключей стадий). Части AC4 про `junit.xml`,
`summary.txt`, `cli-summary.v1`, HTML и AC11 относятся к PR C: в PR A эти форматы не меняются, поэтому побайтовых снимков для них
в PR A нет.
