# ADR 0033: Зонды источников, проверка профилей и перезагрузка профилей

Дата: 2026-10-09.

Статус: Proposed (в Accepted переводится только по слову владельца). Номер 0033 выбран как
следующий после 0032; на `origin/main`, в удалённых ветках и в открытых PR на 2026-10-09 он
свободен, перед слиянием его нужно перепроверить. ADR записывает контракты работы W3.1
[перечня работ](../superpowers/plans/2026-10-08-review-work-plan.md) до кода (PR 0). Реализация идёт
PR 1-5 плана [2026-10-09-w3-1-probes-doctor.md](../superpowers/plans/2026-10-09-w3-1-probes-doctor.md);
нумерация ruling'ов P1-P12 и вопросов Q1-Q3 ниже та же, что в плане (P13 плана это сам ADR).
Решения владельца по Q1-Q3 нет. **Q1 (ad hoc выражение)** блокирует часть реализации: режим не
реализуется и не входит в контракты (см. P2). Для Q2 (P6) и Q3 (P10) действует рекомендация плана до
слова владельца.

## Контекст

Чтобы настроить профиль Prometheus, VictoriaMetrics или InfluxQL, сегодня нужно: записать профиль в
файл, перезапустить `ltv ui`, запустить анализ с источником, прочитать `identity.json` ради
`resource_snapshot_sha256`, написать план (capacity, trend, pod-view) и запустить анализ повторно.
Ни одного шага «выполнить запрос и посмотреть, что вернулось» нет: боевой декодер
`decodePromqlMatrix` требует ровно одну серию (`AMBIGUOUS_SERIES` при `results.size != 1`) и не
показывает, сколько серий пришло и какие у них метки (usability B7). Профили читаются один раз при
старте `ltv ui --connections`, поэтому правка файла требует перезапуска (B5). PRC v0.6 (FR-MOD-06,
критерий 13) требует, чтобы `ltv doctor` заранее показывал доступные и пропущенные возможности.

Ограничения решения:

1. Боевой анализ не меняется: `decodePromqlMatrix`, `decodeInfluxqlResponse`, `AnalysisService`,
   identity, `analysis_id`, `analysis-result.json` побайтово прежние (сверка с релизом 0.1.0).
2. Источники только по явному действию ([ADR 0007](0007-opt-in-online-sources.md), PRC критерий 11):
   проверки без сети по умолчанию, сеть только по `--online` или явному вызову зонда.
3. Агент (Claude Code, Qwen Code, MCP-прокси над локальным API, W3.2) не видит учётных данных,
   адресов профилей, тел ответов и текстов исключений источника.
4. Новых зависимостей и новых видов источников нет (заморозка ширины D1 перечня).
5. Зонд ничего не сохраняет: ни в каталог данных, ни в identity.

## Решение

### P1. Боевой анализ не ослабляется, зонд читает ответ отдельным декодером

`SourceProbe.kt` разбирает `data.result` своим сканером (число серий, метки, число ненулевых ячеек
на серию) и, кроме этого, вызывает нетронутый боевой декодер на тех же байтах. Результат боевого
декодера идёт в поле `decoder_check` (`accepted` или код отказа). Пользователь видит
одновременно «запрос вернул 7 серий» и «боевой декодер не принял бы это: `AMBIGUOUS_SERIES`».

Разбор ответа зонда по видам. PromQL (`prometheus`, `victoria_metrics`): `status` должен быть
`success`, `data.resultType` равен `matrix`, серии берутся из `data.result[]` (`metric` со строковыми
значениями, `values[]`; запись с `histograms` или `histogram` это отказ `UNSUPPORTED_HISTOGRAM`); непустой
`warnings` не отказ, а предупреждение `SOURCE_WARNINGS`. InfluxQL (`influxdb`): `results[]` должен
содержать ровно один оператор (иначе `MALFORMED_RESPONSE`), `error` оператора это `INFLUXQL_QUERY_FAILED`,
`messages` это предупреждение `SOURCE_WARNINGS`, `partial: true` это предупреждение
`SOURCE_PARTIAL_RESPONSE`; серии берутся из `series[]` (`tags` как метки, `columns`, `values[]`), отсутствие
`series` или пустой массив это ноль серий. Для обоих видов `observed_cells` серии это число строк значений
с конечным числом (NaN и бесконечности и `null` не считаются), `expected_cells` это число ячеек окна.
Разбор ответа идёт тем же строгим сканером JSON, что в боевом декодере; сбой сканера это
`MALFORMED_RESPONSE` (или `RESOURCE_LIMIT_EXCEEDED` для лимитов сканера).

`decoder_check` присутствует только при `status: OK` (при `FAILED` он равен `null`) и отвечает на узкий вопрос: принял бы боевой декодер этот ответ (число серий, метки
запроса профиля, сетка времени, значения). Он не проверяет конфликт метки плеча (`arm`),
отрицательные значения событий (`non_negative_events`) и лимиты снимка после разбора
(`SOURCE_SNAPSHOT_LIMIT_EXCEEDED`). Для ad hoc выражения (если Q1 будет решён «да») у запроса нет
метаданных профиля, поэтому «принято» не равно «анализ примет»; документация говорит это прямо.

### P2. Допустимые запросы (режим ad hoc ожидает решения владельца, Q1)

- `profile_query`: `query_id` из сохранённого профиля; выражение берётся из профиля. Реализуется в
  PR 1.
- `ad_hoc`: выражение в теле запроса для видов `prometheus`, `victoria_metrics`, `influxdb`, с теми
  же проверками, что у профиля (PromQL содержит `$__interval`; InfluxQL проходит
  `validateInfluxqlExpression`), не длиннее 4096 байт UTF-8, без управляющих символов кроме `\n` и
  `\t`. **Ожидает решения владельца (Q1): не реализуется и не входит в публичные контракты, пока
  владелец не ответит.** Это явная выдача возможности: ни `127.0.0.1`, ни CSRF не ограничивают агента,
  получившего токен через `GET /api/bootstrap` (так делает MCP-прокси), а лимиты зонда не ограничивают
  стоимость выражения на стороне Prometheus (длина выражения, размер ответа и число подробных серий её не
  бьют; настоящая защита это окно до часа, один запрос и собственные лимиты Prometheus). Рекомендация
  плана: «да» с лимитами P4. Альтернатива: только `query_id` (агент правит файл, перезагружает профили
  и зондирует сохранённые запросы; строже, но лишний круг на каждую итерацию). Ответ «нет» убирает ad hoc
  из контрактов без других изменений.
- Для `opensearch` и `postgresql` выражений нет: зонд это проверка профиля (`profile_check`, P8).
- Адрес только из сохранённого профиля (`profile_id`). URL, путь, заголовки, учётные данные и
  параметры HTTP в запросе зонда не принимаются; неизвестное поле тела это `INVALID_PROBE`.

### P3. Запрос зонда равен боевому по построению

Построение параметров (`query`, `start`, `end`, `step` для PromQL; `db`, `q`, `epoch` для InfluxQL)
выносится из `PromqlSource.acquire` в одну `internal` функцию, которую вызывают и анализ, и зонд;
`$__interval` и плейсхолдеры InfluxQL подставляет та же `resolvedExpression`. Это единственная правка
боевого кода: перенос без изменения поведения, тесты `PromqlSourceTest` и `SourceAnalysisTest` не
редактируются. Окно зонда: `window_ms` по умолчанию 300 000 (максимум 3 600 000), `step_ms` по умолчанию
15 000 (целые секунды 1000..60000, как требует сетка снимка), число ячеек `window/step` целое от 1 до 240,
`end_epoch_ms` по умолчанию «сейчас». Результаты зонда нигде не сохраняются.

### P4. Лимиты зонда

Один HTTP-запрос и одна попытка (без повторов и ожидания `Retry-After`); ответ не более 4 МиБ
(`SOURCE_RESPONSE_TOO_LARGE`); общий срок 15 с **включая ожидание лимитера** (токены и параллельность
`OriginState` ждут без срока, поэтому зонд передаёт в `SourceHttp` функцию `checkCancelled`, которая
бросает `SOURCE_TIMEOUT` после срока); таймаут одного запроса `min(таймаут origin, 15 с)`;
подробно описанных серий не более 20, ключей меток не более 16, образцов значений на ключ не более 5,
каждая строка не более 128 кодовых точек и 256 байт UTF-8 после очистки (это правило главное; «128 байт» в P4 плана описка, она исправлена в плане этим же PR); тело запроса API не
более 16 КиБ; одновременно не более двух зондов (`409 BUSY`). Зонд идёт через тот же `OriginState`
(лимит частоты и параллельности профиля) и не обходит governor. `series_count` точный по всему ответу
(он ограничен 4 МиБ). Цена: ответ крупнее 4 МиБ даёт отказ, а не счёт; пользователь сужает селектор.

### P5. Что видит агент и что нет

Для вывода новых команд и маршрутов (зонд, проверка, `doctor`, перезагрузка) агент видит: `id`, вид, транспорт, плечо профиля; коды и числа; метки и число ячеек серий зонда после очистки.
Не видит в этих выводах: `base_url` (даже origin), имена и значения переменных окружения, тип и параметры TLS,
заголовки, тела ответов, тексты исключений. Порядок обработки каждой строки метки (ключа и значения):
(1) **маскирование до усечения**: строка заменяется на `***`, если содержит как подстроку любое
значение учётных данных профиля, прочитанное из окружения для этого запроса, или начинается со слов
`Bearer`, `Basic`, `Token` (с пробелом после слова), с `-----BEGIN`, `eyJ`; значение заменяется на `***`, если ключ содержит
`pass`, `secret`, `token`, `key`, `auth`, `cred` (без учёта регистра); (2) очистка `cleanErrorText`
(управляющие, форматные, bidi, неназначенные символы в пробел; предел в кодовых точках), затем
усечение до 256 байт UTF-8 по границе символа; число замен идёт в `redacted_count`. Исключение вне этой работы (только в отчёт, контракт не меняется): существующий
`GET /api/grafana` уже отдаёт `base_url` профилей `grafana_proxy`. Гарантия узкая и
названа: зонд не выдаёт учётные данные профиля и известные формы секретов. Печатный текст метки остаётся
недоверенными данными собственного Prometheus владельца (возможная инъекция в агента), поэтому навык
MCP (W3.2) обязан помечать метки как данные. Вывод CLI проходит ту же очистку: `ltv` может запустить сам
агент. Цена ошибки: маскирование по именам даёт ложные срабатывания (метка `monitoring_key` станет
`***`); это безопасная ошибка.

### P6. Тексты ошибок источника не пересылаются (Q2)

Отказ источника это код из закрытого списка и необязательное число `http_status` (для 4xx/5xx). Текст
`error` Prometheus (фрагмент разобранного выражения) не пересылается: он недоверенный и мог бы стать
каналом инъекции в агента. Цена: агент правит выражение без подсказки парсера. Пересмотр после пилота.

### P7. Офлайн по умолчанию

`ltv doctor` и `ltv source validate` по умолчанию делают только локальные проверки (разбор файла, URL
профиля, наличие переменных окружения с учётными данными, файлы TLS и срок клиентского сертификата,
согласованность правил и рядов); сетевые проверки только у `ltv doctor` с `--online`. `ltv source validate` и `ltv source hash` офлайн всегда (флага `--online` у них нет); `ltv source probe` по определению делает один запрос. `POST /api/sources/validate`
офлайн всегда; `POST /api/sources/probe` онлайн по определению (его вызов и есть явное действие).
Отличие от [ADR 0007](0007-opt-in-online-sources.md): зонд не запускает анализ и ничего не сохраняет, но
делает исходящий запрос по явной команде пользователя или агента. Цена: `ltv doctor` без `--online` не
поймает неверный адрес; вывод говорит «сеть не проверялась: нужен --online».

### P8. Проверка профилей OpenSearch и PostgreSQL (PR 5)

Тело `POST /api/sources/probe` для видов `opensearch` и `postgresql` содержит только `profile_id`;
`query_id`/`expression` для них `INVALID_PROBE`. OpenSearch: запрос строит `buildOpenSearchQuery` по
отображению профиля (`group_limit` не больше 10), метод POST через новый ограниченный вызов `SourceHttp`;
в отчёт идут число групп, шардов и коды покрытия, никаких сообщений и образцов. PostgreSQL:
`capturePostgresPhase` под тем же `postgresCapturePermit`, что и `/api/sources/postgresql/pre`; лимиты P4
к нему не применимы (набор JDBC-запросов со своими таймаутами, read-only); в отчёт идут `connected`,
`read_only`, `database_matches`, наличие расширений, число таблиц и коды статусов (`PG_CREDENTIALS_MISSING`,
`PG_CREDENTIALS_INVALID`, `PG_CONNECTION_FAILED`, `PG_READ_ONLY_REQUIRED`, `PG_DATABASE_MISMATCH`,
`PG_CAPTURE_FAILED`), содержимое фазы не возвращается и не сохраняется. Часть отделима: без неё PR 1-4
выполняют критерий для Prometheus, VictoriaMetrics, InfluxQL.

### P9. Перезагрузка профилей: явная, из того же файла, атомарная (PR 3)

`POST /api/sources/reload` без тела; сервер перечитывает ровно тот путь, который получил при старте
(`--connections`), через `readSourceFile` (обычный файл, без ссылок, предел 1 МиБ) и заменяет в
`AtomicReference` неизменяемый набор (профили HTTP, профили PostgreSQL, `SourceHttp`, `PromqlSource`,
ревизия). Путь из запроса не принимается никогда. Доверие к файловой системе то же, что при старте:
проверяется только последний компонент пути. Байты читаются один раз в ограниченный буфер, от него же
считаются ревизия (SHA-256) и разбор. Разбор не удался: старый набор остаётся, `422
SOURCE_CONFIG_INVALID` с кодом без текста файла. Без `--connections`: `404 SOURCE_RELOAD_NOT_CONFIGURED`.
Параллельная перезагрузка: `409 BUSY`. Успешная перезагрузка не чаще одной в 5 с (`429
RELOAD_TOO_FREQUENT`). Каждая операция (приём задания, старт задания, зонд, проверка, маршрут Grafana,
захват PostgreSQL) берёт набор один раз и работает только с ним, иначе профиль нового поколения и
`SourceHttp` старого дали бы `SOURCE_PROFILE_NOT_CONFIGURED`. Профиль исчез между приёмом и стартом
задания: `SOURCE_PROFILE_NOT_FOUND`. Профиль изменился: анализ идёт по новому определению, и это видно в
evidence (хэши выражений и `query_set_sha256` входят в `source_summary` и identity). Смена только
`base_url` в доказательствах не видна (так и сегодня при перезапуске с новым файлом); это принято.
Цена: один origin получает до числа живых поколений потоков лимита, а не два; ограничение частоты держит
число поколений малым. Запрет перезагрузки при активных заданиях был бы хуже.

### P10. Хэш снимка: две формы, без новой логики (команда в PR 1, API в PR 3)

`ltv source hash <resource-snapshot.json>` и `POST /api/resources/semantic-hash` вызывают
`validateResourceSnapshot` и выдают `semantic_sha256`, `config_sha256`, `load_input_sha256`, число
рядов и ячеек. Форма `ltv source hash --run <run-id> --analysis <analysis-id> [--data-dir]` читает
`resource_snapshot_sha256` из identity сохранённого анализа через `RunBundleStore.readVerifiedAnalysis`
(проверка манифеста и хэшей уже в ней; пересчёта по значениям рядов нет). Форма открывает каталог данных
с исключающей блокировкой и при запущенном `ltv ui` на том же каталоге даёт `DATA_DIR_BUSY` (выход 6).
Исходы: анализ не найден (`ANALYSIS_NOT_FOUND`, 4), нет снимка ресурсов
(`RESOURCE_SNAPSHOT_NOT_PROVIDED`, 4), пакет повреждён (`ANALYSIS_CORRUPT`, 4). Планы capacity, trend,
pod-view по-прежнему привязаны к хэшу снимка и не сочетаются с онлайн-сбором в одном вызове
(`SOURCE_INPUT_CONFLICT`): это вторая половина usability B5 и отдельная работа (Q3).

### P11. Размещение команд

`ltv source` уже существует (`pre|post`); добавляются `validate`, `probe`, `hash`. `ltv doctor`
отдельный верх (PRC 17.2). Новая логика в новых файлах `cli/`, в `CommandLine.kt` только диспетчер и
справка.

### P12. Статусы, `resource_side` и коды выхода

Статус самого зонда независим от агрегации ниже: `status` документа `source-probe.v1` это `OK` (ответ
получен и разобран; `series_count` может быть 0 и `decoder_check.accepted` может быть ложным) или
`FAILED` (запрос не выполнен или ответ не разобран). Код выхода `ltv source probe`: 0 при `OK` (в том
числе при `decoder_check.accepted = false`), 7 при `FAILED`. Агрегация `OK/WARN/FAIL/SKIPPED` и
`resource_side` относится только к `ltv doctor` (PR 2).

Статус проверки: `OK`, `WARN`, `FAIL`, `SKIPPED`. Запрос с `decoder_check.accepted = false` это `FAIL`,
кроме `EMPTY_RESULT`: пустой ответ в окне «сейчас» это `WARN`. Запрос, не выполненный из-за
`maxRequestsPerRun`, это `SKIPPED` (`SOURCE_REQUEST_CAP_EXCEEDED`) и `WARN` на профиль. `resource_side`
на профиль и в целом (худшее по порядку `READY`, `DEGRADED`, `UNAVAILABLE`): `NOT_PROBED` без `--online`
и без офлайн-`FAIL`; `UNAVAILABLE` при любом офлайн-`FAIL` или если все запросы `FAIL`; `DEGRADED`, если
часть запросов `FAIL`/`WARN`; `READY`, если все приняты. Нагрузочный вердикт доступен всегда (источники
необязательны, PRC критерий 4). Коды выхода `ltv doctor`: 0 отчёт построен, провалов нет; **7** отчёт
построен, есть хотя бы один `FAIL`; 4 файл подключений не читается или не разобран; 64 usage. Значения 2
и 3 заняты вердиктом анализа, 6 каталогом данных. Константа `EXIT_DOCTOR_FAILED = 7` вводится в PR 1,
потому что `ltv source probe` тоже выходит кодом 7.

### Совместимость с MCP (W3.2)

Инструмент `probe_source` будет тонким прокси над `POST /api/sources/probe` и `validate`: аргументы
`profile_id`, `query_id` (и `expression`, если Q1 «да»), `window_ms`, `step_ms`; URL и учётные данные не
принимаются; ответ это `source-probe.v1`/`source-check.v1` как есть. Мутирующие вызовы требуют
сессионного cookie и CSRF-токена из `GET /api/bootstrap`: получает их MCP-прокси, не агент.

| Схемы `source-probe.v1`, `source-check.v1`, `resource-hash.v1` (каталог `docs/contracts/sources/probe/v1`) | новые, `additionalProperties: false` | 1 | новые |
| Схемы `doctor-report.v1`, `source-reload.v1` | новые | 2, 3 | новые |

| Закрытые списки кодов | коды зонда (список в плане) | 1-5 | новые |

Не меняются: `analysis-result`, `identity.json`, `analysis_id`, канонический JSON и хэши identity,
`SourceRequest` и `source-request.v4`, `source-connections.v1..v3`, `decodePromqlMatrix` и
`decodeInfluxqlResponse`, `GET /api/sources`, зависимости production.

### Закрытые списки кодов

`SOURCE_AUTH_UNAVAILABLE`, `SOURCE_AUTH_INVALID`, `SOURCE_HTTP_AUTH`, `SOURCE_HTTP_429`,
`SOURCE_HTTP_5XX`, `SOURCE_HTTP_STATUS`, `SOURCE_HTTP_ERROR`, `SOURCE_TIMEOUT`,

`INFLUXQL_QUERY_FAILED`, `UNSUPPORTED_RESULT_TYPE`, `UNSUPPORTED_HISTOGRAM`, `RESOURCE_LIMIT_EXCEEDED`.
Любой другой сбой транспорта сводится к `SOURCE_HTTP_ERROR`, текст не пересылается. Коды PR 5
(`OPENSEARCH_INVALID_MAPPING`, `PG_*`) добавляются вместе с PR 5.

`decoder_check.code` (при `accepted: false`) это код боевого декодера на тех же байтах: `EMPTY_RESULT` (ноль

`docs/contracts/sources/probe/v1` вместе с PR, который вводит схему.

## Что не входит

- Новые источники и виды запросов (D1), запись профилей через API, произвольные адреса и учётные данные в
  запросе зонда.
- Ослабление `decodePromqlMatrix` или «по подам» в боевом анализе (боевой анализ по-прежнему требует
  ровно одну серию).
- Хэширование сохранённого снимка через API (для этого есть маршруты identity и снимка анализа) и
  пересчёт хэша сохранённого анализа.
- Предложение запроса по метрик-паку, авто-подбор меток, генератор профилей, «capability preview» по
  пакам PRC 17.2.
- Текст ошибок источника в ответе (P6), чтение профилей Jenkins, горячая перезагрузка по изменению файла.
- Планы без хэш-привязки к снимку (Q3, отдельная работа).

## Отклонённые альтернативы

- Ослабить боевой декодер, чтобы он принимал несколько серий: меняет содержимое снимка и identity
  (`source_acquisition_sha256`); зонд читает ответ отдельным декодером (P1).
- Принять URL, заголовки или учётные данные в запросе зонда: превращает локальный API в прокси ко
  всему, что видит машина (SSRF); адрес только из сохранённого профиля.
- Переслать агенту текст ошибки Prometheus: недоверенный текст как канал инъекции (P6).
- Менять набор профилей на месте в существующих `SourceHttp` и `PromqlSource`: `SourceHttp` отвергает
  профиль, не равный своей копии, а состояние лимитов живёт внутри экземпляра; нужна новая тройка (P9).
- Запретить перезагрузку при активных заданиях: долгие загрузки блокировали бы настройку.
- Сеть по умолчанию в `ltv doctor`: нарушает ADR 0007 и критерий 11 PRC (P7).

## Следствия

- Агент с токеном bootstrap получает возможность выполнять запросы из сохранённых профилей к источнику
  владельца в пределах лимитов P4; ad hoc выражения (если Q1 «да») расширяют это до любого
  read-only выражения. Это новая граница доверия, названная здесь явно.
- Печатный текст меток источника остаётся данными: навыки, которые передают его агенту, обязаны это
  оговаривать.
- Пересечения: W3.7 и W3.1 PR 3 правят `fixtures/http-layer/*`; порядок слияния и регенерация описаны в
  плане. W3.2 использует контракты этого ADR как есть.
- Документация: `docs/user/online-sources.md` получает разделы зонда, `ltv doctor` и перезагрузки; фраза
  «изменение файла требует перезапуска backend» убирается в PR 3.
- Новых зависимостей production нет.

## Тест-критерии

1. Фиктивный Prometheus, ответ из 7 серий: `series_count: 7`, метки, `decoder_check` `AMBIGUOUS_SERIES`;
   `decodePromqlMatrix` на тех же байтах по-прежнему отвергает ответ.
2. Параметры запроса зонда по `query_id` побайтно равны параметрам `PromqlSource.acquire` на том же окне.
3. Один запрос, одна попытка, ответ не более 4 МиБ, общий срок не более 15 с с ожиданием лимитера;
   третий параллельный зонд получает `409 BUSY`.
4. Ни один вывод (JSON, CLI, ответ API) не содержит значений и имён переменных окружения, `base_url`,
   тел ответов, текстов исключений; метки очищены и ограничены.
5. `ltv source validate` и `ltv source hash` без `--online` не делают сетевых запросов; хэш равен
   `resource_snapshot_sha256` из `identity.json` анализа с тем же снимком.
6. Зонд не меняет каталог данных, `analysis_id` и байты анализа.
7. Схемы с примерами проверены тестом (valid принимаются, каждый invalid отвергается).
8. (PR 3) Правка файла и `POST /api/sources/reload` без перезапуска: новый профиль виден и принимается
   заданием; неверный файл оставляет прежний набор.
