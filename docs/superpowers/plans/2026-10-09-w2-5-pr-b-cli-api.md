## Ruling'и PR B

**Q1. Порядок проверок сочетаний совпадает с таблицей ADR 0030:** ёмкость, затем снимок, затем онлайн-источник. В CLI они
проверяются после разбора флагов и до чтения любого входа (в том числе до `SOURCE_INPUT_CONFLICT`), код печатается без
пояснения, выход 4. Почему: пользователь видит причину «два источника окон», а не побочный отказ. Цена ошибки: сочетание из трёх
флагов сообщает первый из трёх кодов, а не все.

**Q2. API: сочетания дают `422 INVALID_STAGES` с одним элементом `errors[]`** (`json_pointer` указывает на конфликтующую часть:
`/capacity_plan`, `/resource_snapshot`, `/source_request`). Проверка в `bindJob` до разрешения прогона и до проверки онлайн-запроса
(иначе её опередил бы 400 «Online acquisition cannot be combined...»). Почему: так сказано в плане («`422 INVALID_STAGES` с одним
`errors[]` элементом кода из таблицы»). Цена ошибки: клиент, разбирающий 400 для `source_request`, получает 422 только вместе
со стадиями.

**Q3. Любой `RESOURCE_LIMIT_EXCEEDED` валидатора стадий (размер, глубина, 17 стадий) даёт `413`**, как у остальных планов
(`trend_plan`: превышение числа проверок тоже 413). Остальные ошибки валидатора это 422 `INVALID_STAGES`; `MALFORMED_JSON`
остаётся 422 (как у снимка).

**Q4. Лимит запроса задания и число частей не меняются.** Стадии нельзя сочетать со снимком, планами и онлайн-запросом, поэтому
вместе со стадиями число частей не доходит до `MAX_JOB_PARTS`, а размер части (64 КиБ) помещается в запас `MAX_JOB_REQUEST_BYTES`.
Цена ошибки: нулевая.

**Q5. `STAGE_OUTSIDE_RUN` и `STAGES_*_CONFLICT` из сервиса попадают в `diagnostic.code` FAILED-задания** (сообщение по-английски,
как у соседних кодов). Защита в сервисе нужна для прямых вызовов; через API сочетания отсекает `bindJob` раньше.

**Q6. Прогон без `--stages` и без части `stages` побайтово прежний** (вывод CLI, коды выхода, ответы API). Строка `analyze` в
`usageText()` получает `[--stages <load-stages.json>]`, это единственное изменение `--help` и оно записано в ADR 0030.

## Критерии приёмки

- CLI: `--stages` с допустимым файлом и политикой даёт PASS/FAIL по окну steady (выход 0/2), без политики 0; `NO_VERDICT` 3;
  повтор флага 64; нечитаемый или недопустимый файл 4 со строками `<code> <pointer>: <message>`; `--stages` вместе с `--resources`,
  `--capacity`, `--connections/--source` печатают `STAGES_RESOURCES_CONFLICT`, `STAGES_CAPACITY_CONFLICT`, `STAGES_SOURCE_CONFLICT`
  (выход 4, без чтения входа и без обращения к источнику); `--source-context` со стадиями проходит; `steady` за концом прогона
  печатает `STAGE_OUTSIDE_RUN` (выход 4), `excluded` за концом проходит; `--help` содержит `--stages`.
- API: часть `stages` даёт задание с окном `steady` в результате; недопустимый файл 422 `INVALID_STAGES` с `errors`; 17 стадий и
  файл больше лимита 413; повтор части 400 `MALFORMED_REQUEST`; сочетания 422 `INVALID_STAGES`; `STAGE_OUTSIDE_RUN` даёт
  `FAILED` с `diagnostic.code`.
- Без стадий: существующие тесты и снимки `fixtures/http-layer`, `fixtures/storage-layout`, `fixtures/typed-boundary` проходят без
  обновления.
