# Локальный анализ в Slice 1

Slice 1 анализирует локальные JMeter JTL и Gatling logs без отправки данных в
сеть, кроме явно запрошенного ИИ-разбора: он отправляет evidence анализа и
системный prompt на endpoint ИИ-runner без запроса согласия (см.
[advisory-ai.md](advisory-ai.md#что-и-куда-отправляется)). Доступны Web UI и
эквивалентный CLI.

## Требования и сборка

Для сборки из repository нужны JDK 21 и Node.js 24.14.0. Все версии runtime и
frontend dependencies закреплены lockfiles.

Windows PowerShell:

```powershell
.\gradlew.bat installDist
.\build\install\ltv\bin\ltv.bat ui
```

Linux:

```bash
./gradlew installDist
./build/install/ltv/bin/ltv ui
```

Приложение откроет случайный URL вида `http://127.0.0.1:<port>`. Если браузер
нельзя открыть автоматически, URL будет напечатан в terminal. Остановите
runtime через `Ctrl+C`.

По умолчанию данные находятся в `~/.lt-verdict`. Другой каталог задаётся так:

```text
ltv ui --data-dir <path>
```

Один data directory обслуживает только один CLI/UI writer process. Для двух
одновременных процессов укажите разные directories.

### Память при большом снимке ресурсов

Снимок ресурсов принимается до 1 024 рядов, 1 500 000 ячеек (ряды x точки) и
32 MiB. Разбор держит в куче около 200-250 байт на ячейку, поэтому крупный
снимок требует больше памяти, чем прежний предел (64 ряда, 500 000 ячеек,
16 MiB). Максимум кучи JVM по умолчанию равен четверти ОЗУ; `-Xmx` в приложении
не задан. Числа получены замером 2026-09-30 ([ADR 0014](../adr/0014-resource-series-limits-autostep-arm-api.md))
на синтетических снимках до 1,97 млн ячеек с нагрузкой в 1 и 10 млн строк:

| Что | Куча JVM | ОЗУ при куче по умолчанию |
| --- | --- | --- |
| Наименьшая проверенная куча для одного анализа (нижняя граница по единичным прогонам, не рекомендация) | 384 МБ | около 1,5 ГБ |
| Рекомендуется для одного анализа | 512 МБ | не менее 2 ГБ |
| Ориентир с запасом для одного анализа со снимком до 1,5 млн ячеек | 1 GiB | 4 ГБ |
| Два одновременных анализа | 2 GiB | 8 ГБ |

При меньшем ОЗУ или меньшей автоматически выбранной куче задайте максимум явно
через `JAVA_OPTS` (стартовые скрипты `ltv` и `ltv.bat` его читают), например:

```powershell
$env:JAVA_OPTS = "-Xmx1g"
.\build\install\ltv\bin\ltv.bat ui
```

```bash
JAVA_OPTS="-Xmx1g" ./build/install/ltv/bin/ltv ui
```

Если кучи не хватило, анализ завершается ошибкой `OutOfMemoryError: Java heap
space` при разборе снимка. Файл, который нужно отвергнуть (например, ряд из
десятков миллионов чисел), разбирается в дерево до проверки числа ячеек, поэтому
ему нужна куча больше, чем допустимому снимку: замер на файле 32 MiB из
16,8 млн элементов показал `OutOfMemoryError` при `-Xmx1g` и обычный отказ
`VALUES_LENGTH_MISMATCH` при `-Xmx1536m` (для 16 MiB порог был между 512 и
768 МБ). Не проверялись снимки с максимально длинными метками
и значениями (до 34 байт на ячейку: такой файл не поместится в 32 MiB при
1,5 млн ячеек и будет отвергнут по размеру), загрузка через веб-интерфейс на
пределе размера и онлайн-сбор. Для онлайн-сбора действует собственный потолок
числа рядов, см. [онлайн-источники](online-sources.md).

### Целостность хранилища

SHA-256 входного файла вычисляется один раз при приёме и входит в `run_id`
(`<тип источника>-<sha256>`); SHA-256 артефактов анализа вычисляется при записи
и сохраняется в `manifest.json`. При открытии, списке и повторном чтении
прогона и анализа эти хэши заново не считаются (исключения: небольшой
`identity.json` сверяется с `analysis_id`, а история сверяет хэши `run.json`,
result и identity): проверяются существование файлов, их размер, форма metadata и manifest. Поэтому список прогонов не читает
входные файлы и остаётся быстрым при больших входах. Обратная сторона: если
файл в data directory изменён вручную или испорчен диском без изменения размера,
LT Verdict этого не заметит; одинаковый `run_id` при чтении не доказывает
одинаковые байты. Data directory считается доверенным локальным хранилищем, в
которое пишет только LT Verdict. Решение и границы описаны в дополнении к
[ADR 0002](../adr/0002-slice-1-runtime-filesystem-security.md).

## Поддерживаемые файлы

- JMeter JTL CSV с header и UTF-8 data;
- JMeter JTL XML с `sample`/`httpSample` и nesting;
- Gatling OSS text `simulation.log` 3.9–3.12;
- Gatling OSS binary `simulation.log` 3.13–3.15.1.

Формат определяется по содержимому, не по extension. Максимальный input —
4 GiB. Исходный upload целиком хранится как immutable `inputs/source.bin`;
response bodies, response headers и XML payload fields не извлекаются в
результаты и не показываются.

Timestamps должны быть epoch в миллисекундах. Значения в диапазоне
`1000000000..99999999999` отклоняются как `INVALID_SAMPLE_TIMESTAMP`: это epoch
в секундах, который иначе молча дал бы run window в 1970 году. Для JMeter
перегенерируйте JTL с `-Jjmeter.save.saveservice.timestamp_format=ms`.

### JMeter CSV и Transaction Controller

Transaction Controller с «Generate parent sample» (и без него) пишет в CSV
отдельную строку контроллера рядом со строками дочерних сэмплеров. LT Verdict
узнаёт такую parent-строку только по стандартным признакам JMeter: столбец
`responseMessage` полностью равен
`Number of samples in transaction : N, number of failing samples : M`
(регистр, пробелы и ASCII-цифры значимы, частичное совпадение не считается) и
столбец `dataType` пуст. Оба столбца должны быть в заголовке ровно по одному
разу; если какого-то нет, распознавание выключено и все строки считаются
сэмплерами (как раньше); дубль любого из них даёт `INVALID_JMETER_CSV_HEADER`.
`dataType` пишется при `jmeter.save.saveservice.data_type=true` (значение по
умолчанию).

Режим определяется по всему файлу:

| Содержимое файла | Parent-строки | Остальные строки |
| --- | --- | --- |
| Есть parent-строки и есть хотя бы одна другая | отдельная транзакция (`JMETER_CONTAINER`), в общие числа не входят | сэмплеры: общие числа, RPS, ошибки и графики считаются по ним |
| Только parent-строки (`jmeter.save.saveservice.subresults=false`) | сэмплеры | нет |
| Нет parent-строк | нет | сэмплеры |

Итог: стандартный CSV с Transaction Controller больше не считается дважды;
контроллер виден как транзакция, и правило SLA можно привязать к его label.
Если контроллер и обычный сэмплер имеют один label, правило с этим именем даёт
`AMBIGUOUS_TRANSACTION` и `NO_VERDICT` (раньше строки сливались в одну
сводку). Сравниваемые прогоны нужно записывать с одним значением `subresults`:
контроллер как `JMETER_CONTAINER` (с дочерними) и как сэмплер
(`subresults=false`) считаются разными транзакциями.

Ограничения (известные):

- режим один на файл: при `subresults=false` и обычных сэмплерах вне
  контроллеров parent-строки считаются контейнерами и в общие числа не входят,
  хотя дочерних у них нет; сохраняйте дочерние (`subresults=true`, значение
  по умолчанию в JMeter);
- вложенные контроллеры при `subresults=false` дают только parent-строки:
  вход считается как «только parent-строки», вложенный контроллер считается
  вместе с внешним;
- сэмплер, который одновременно пишет пустой `dataType` и в точности это
  сообщение (возможно только при ручной настройке скрипта), в файле с
  дочерними считается parent: он уходит из общих чисел, но остаётся видимым
  как транзакция;
- иерархия не восстанавливается: `groupPath` пуст, число `N` из сообщения не
  используется;
- другие версии JMeter, кроме 5.6.2 и 5.6.3, и плагины не проверены.

Версия разбора CSV поднята (`jmeter-csv` 2, `jmeter-jtl-csv.v2`): тот же файл с
parent-строками получает новый `analysis_id` и пересчитывается; прежние
результаты остаются читаемыми, но с новыми несопоставимы для baseline
(`INCOMPATIBLE_METRIC_DEFINITION`), эталон нужно закрепить заново. Для файлов
без parent-строк числа не меняются, но identity меняется всё равно. Для
распознавания parent-строк парсер перед основным проходом просматривает файл:
если в нём нет текста «Number of samples in transaction : », это один быстрый
проход по байтам, иначе просмотр завершается, как только найдены и parent, и
другая строка.

## Анализ через UI

Шаги ниже описывают прежний (английский) интерфейс. Он открывается адресом
`/?shell=old` (см. «Новый интерфейс»); по умолчанию открывается новая оболочка,
её вкладки описаны в разделе «Новый интерфейс».

1. В `Runs` выберите `Load test log`.
2. При необходимости выберите `Policy file` или продолжите без policy.
3. Для загруженной policy исправьте поля в editor и дождитесь статуса
   `Policy is valid`.
4. При необходимости выберите `Resource snapshot`, затем нажмите `Analyze run`.
5. Следите за upload percentage, job state и processed bytes.
6. Откройте карточку вердикта: она первый блок страницы, над формой запуска, а
   её краткая копия закреплена в шапке. Ниже просмотрите policy checks,
   transactions и sparse normalized data.

Повтор тех же input bytes переиспользует run. Новая policy создаёт новый
immutable analysis, не изменяя прежний.

### Сохранённые результаты и графики

В списке принятых прогонов выберите файл, затем нужный analysis. Под именем
файла показаны тип источника и первые 8 символов SHA-256 содержимого: файлы с
одинаковым именем, но разным содержимым различаются по этому идентификатору.
Полный run ID виден во всплывающей подсказке при наведении курсора. Рядом с
analysis показаны его id, validity и verdict. Результат можно открыть после
перезагрузки страницы без повторного upload или запуска job. Если для input
ещё нет законченных analyses, UI сообщает об этом. Списки имеют пагинацию;
порядок по id не обозначает порядок завершения.

Графики показывают RPS, число ошибок за bucket и P95 latency по выбранным
normalized data. Время отсчитывается от начала прогона. Отсутствующие buckets
разрывают линии; они не заменяются нулями. Rollup и границы интервала задаются
теми же controls, что и для таблицы. Одна страница содержит не более 500
buckets; индикатор и переход к следующему интервалу не позволяют принять её
за весь прогон. Таблица остаётся доступным текстовым представлением графиков.

### Скачать результат

Для открытого analysis доступны `Download JSON`, `Download HTML` и `Download AsciiDoc`.
JSON совпадает по bytes с сохранённым `analysis-result.json`. HTML открывается
локально без приложения и сетевого доступа. Он строится на сервере по
сохранённому результату и начинается с русских блоков, сопоставимых с
интерфейсом:

- «Вердикт и причины»: вердикт словами, число нарушенных правил, валидность
  прогона, покрытие данных и причины с расшифровкой кодов (неизвестный код
  печатается как есть с нейтральной фразой);
- «Правила»: для каждой проверки правило, область, метрика, условие, порог с
  единицей, измеренное значение, окно, выборка, статус и причина. Округление
  не превращает нарушение в равенство: знаки добавляются до 20;
- «Транзакции»: до 200 строк по влиянию (сначала нарушения, затем ошибки, p99,
  выборка), остаток одной строкой «и ещё N»; полный список остаётся в разделе
  `Overall and transaction metrics`;
- «Ограничения»: правила не заданы, неполное покрытие, файл разобран не
  полностью, малая выборка, диагностика не доказывает причину.

Далее идут прежние английские разделы (идентификаторы, validity, verdict,
coverage, metrics, policy checks, findings, evidence и canonical JSON); они
помечены `lang="en"`, корень документа `lang="ru"`. Страница не содержит
`script`, `img`, `form`, `base` и внешних ресурсов, значения из результата
экранируются, действует CSP `default-src 'none'`.
AsciiDoc — детерминированный UTF-8 report с теми же разделами; значения из
analysis остаются compact JSON tokens внутри literal blocks с `specialchars`,
поэтому текст input не становится AsciiDoc directive или markup. Canonical JSON
сохраняет исходные bytes как точный machine-readable export. Конвертация и
публикация AsciiDoc не входят в этот local export.
Графики в этот первый HTML export не входят.

Просмотр и экспорт не создают новых analyses и не меняют вердикт.
Baseline comparison, N-run history и остальные форматы относятся к следующим
изменениям Slices 8–9.

### Состояния и действия

| Состояние | Значение | Действие |
| --- | --- | --- |
| Uploading | Input потоково принимается и хешируется | Дождаться окончания upload или нажать `Cancel upload` |
| `QUEUED` | Analysis принят bounded queue | Дождаться worker или отменить |
| `PROCESSING` | Parser/metrics читают input | Следить за processed bytes или отменить |
| `BUSY` | Worker и bounded queue заняты | Дождаться или отменить queued job, затем повторить |
| `COMPLETE` | Canonical result опубликован | Просмотреть result и evidence |
| `FAILED` | Runtime не завершил analysis | Проверить diagnostic и повторить после устранения причины |
| `CANCELLED` | Analysis отменён | Input остаётся доступен для нового запуска |

Пока файл загружается (состояние `UPLOADING`), форма недоступна, а рядом с
индикатором есть кнопка `Cancel upload`. Отмена обрывает запрос в браузере:
анализ не создаётся, форма снова доступна, фокус возвращается на выбор файла,
показывается пояснение «Upload cancelled». Сервер при обрыве соединения удаляет
временный файл загрузки и не публикует прогон. Если отмена пришлась на момент,
когда сервер уже получил весь файл, прогон может остаться в списке принятых,
но без анализа. Кнопка скрывается, как только upload завершён и создаётся job.

Если страницу перезагрузили во время анализа, UI после загрузки снова показывает
панель самой старой активной задачи (`QUEUED` или `PROCESSING`) с прогрессом и
кнопкой `Cancel analysis`; по завершении результат открывается как обычно. Если
одновременно активны две задачи (по умолчанию одна выполняется, вторая в
очереди), панель
показывает первую; вторая появится после её завершения или отмены и повторной
загрузки страницы. Задачи хранятся в памяти и не переживают перезапуск
приложения.

Если запрос статуса задачи временно не удался (сеть, ответ 5xx, 408 или 429), UI
показывает «Connection problem» и повторяет запрос с задержкой 0,5 с,
удваивающейся до 10 с; после первого успешного ответа опрос продолжается как
обычно. После 10 неудач подряд или 2 минут UI показывает «Connection lost» и
кнопку `Retry`: задача на сервере могла продолжиться, её идентификатор не
теряется, `Cancel analysis` остаётся доступной. Ошибки 4xx (кроме 408 и 429),
например неизвестная задача, не повторяются.

### Validity и verdict

| Результат | Значение |
| --- | --- |
| `VALID + NO_POLICY` | Input полностью разобран; metrics доступны, policy не задана |
| `VALID + PASS` | Все applicable policy rules выполнены |
| `VALID + FAIL` | Нарушено хотя бы одно applicable rule |
| `INVALID + NO_VERDICT` | Recognized input оказался malformed; `PASS` невозможен |
| `DEGRADED + NO_VERDICT` | Доступна только неполная информация; причина сохранена |
| `NO_VERDICT` с incomplete coverage | Required transaction отсутствует или неоднозначна |

### Карточка вердикта

Карточка стоит первым блоком страницы; в шапке остаётся ссылка с тем же
вердиктом, она закреплена при прокрутке (на экранах шире 680 px) и ведёт к
карточке. Данные только из сохранённого результата, ядро и контракты не
менялись. Проверка здесь это одно правило в одном окне (без окон одно правило).

- `FAIL`: до трёх нарушенных проверок с правилом, измеренным значением и
  порогом; остальные счётчиком, полный список в таблицах правил ниже. Для
  SLA-правил ресурса показаны наблюдавшиеся значения, интервал (UTC) и число
  ячеек подряд.
- `PASS`: первые проверки с порогом. Для SLA-правил ресурса измеренное значение
  в результате не хранится, поэтому показаны только порог и «нарушений нет».
  Если у правила запросов меньше рекомендуемого минимума, `PASS` остаётся
  `PASS`, но результат помечен причиной `SMALL_SAMPLE` (см. «Минимум выборки»);
  число запросов показано отдельным фактом. Такая проверка в карточке получает
  пометку «режим малой выборки: 30 сэмплов при минимуме 50», к чипу вердикта
  добавляется «· малая выборка», а в описании сказано, для скольких проверок
  выборка меньше рекомендуемой. Это пометка, а не причина отсутствия вердикта и
  не изменение кода выхода CLI. То же относится к `FAIL`: нарушение остаётся
  нарушением и помечается так же.
- `NO_POLICY`: пороги не проверялись, потому что не заданы политика и SLA-правила.
- `NO_VERDICT`: блок «Почему вердикта нет» с причиной словами, правилами или
  окнами и сырым кодом для поддержки. Если нарушения уже найдены, они показаны
  отдельным блоком: вердикт по ним не выдаётся, пока не проверены остальные
  правила. Причины неполного покрытия, не повлиявшие на вердикт, показаны
  отдельно и вердикт не отменяют. Для `INSUFFICIENT_SAMPLES` правило названо
  вместе с числами: «rare-p95 (окно steady-1, сэмплов: 12, нужно не меньше 20)».

Последним фактом карточки показан хэш политики, по которой получен вердикт
(«Политика (хэш)»: первые 12 символов `policy_sha256`; `не задана`, если анализ
выполнен без политики). Перед ним стоит факт «Политика (id)» с именем политики
(`policy_id` из файла политики); он есть, только если имя удалось прочитать.
Имя также показано в строке анализа в списке сохранённых анализов. Факты
появляются, когда список сохранённых анализов прогона уже загружен и содержит
выбранный анализ; сразу после свежего задания они могут показаться позже
остальных. Политик можно использовать несколько (по протоколам и системам):
разные политики на одной нагрузке дают разные анализы с разными `analysis_id`,
различаются они по имени и хэшу.

Имя политики берётся из копии политики `policy.json`, которую анализ сохраняет в
своём наборе (она же даёт `policy_sha256`). Анализы, созданные до появления этой
копии, и анализы без политики показываются без имени: ни ошибки, ни пустого
факта нет. Набор анализа неизменяем, поэтому повторный запуск того же входа с
той же политикой не добавит имя в старый анализ (`analysis_id` совпадает, набор
возвращается как есть). Если `policy.json` изменён без смены размера, не
сходится с `policy_sha256` или не разбирается, список анализов по-прежнему
открывается, а имя не показывается. Пропавший или изменённый по размеру файл,
как и любой другой артефакт набора, считается повреждением хранилища.

### Причины NO_VERDICT и что делать

| Код | Что значит | Что сделать |
| --- | --- | --- |
| `EMPTY_INPUT` | Во входном файле нет ни одного запроса | Проверить, что выбран нужный файл и он не пуст |
| `INVALID_JMETER_CSV_HEADER` | В заголовке JMeter CSV нет обязательного столбца или он повторяется | Экспортировать JTL с `timeStamp`, `elapsed`, `label`, `success`, каждый один раз |
| `MALFORMED_JMETER_CSV`, `MALFORMED_JMETER_XML`, `MALFORMED_GATLING_TEXT`, `MALFORMED_GATLING_BINARY` | Файл повреждён; карточка показывает позицию в файле | Скопировать файл заново или переэкспортировать |
| `UNSAFE_XML` | В XML есть DTD или внешние сущности | Экспортировать XML без них |
| `UNSUPPORTED_GATLING_TEXT`, `UNSUPPORTED_GATLING_BINARY` | Версия журнала Gatling не поддерживается (для текстового журнала также повторная или неполная запись `RUN`) | Использовать поддерживаемую версию из раздела «Поддерживаемые файлы» |
| `TRUNCATED_GATLING_BINARY` | Бинарный журнал оборван; `run_validity` равен `DEGRADED` | Дождаться конца теста и взять полный журнал |
| `INVALID_SAMPLE_TIMESTAMP` | У запроса недопустимая отметка времени, возможно секунды вместо миллисекунд | Экспортировать время в миллисекундах эпохи |
| `RESOURCE_LIMIT_EXCEEDED` | Превышен предел обработки | Сократить прогон или число транзакций |
| `METRIC_NOT_AVAILABLE` | В области правила нет ни одного запроса | Проверить область правила и границы окна |
| `TRANSACTION_NOT_FOUND` | Транзакция из правила не найдена в результатах | Сверить имя в правиле с логом, включая регистр и пробелы |
| `AMBIGUOUS_TRANSACTION` | Имя подходит нескольким транзакциям | Сделать имена уникальными или изменить правило |
| `BUSINESS_OBSERVATIONS_NOT_FOUND` | В окне нет запросов нагрузки | Исправить границы окна в снимке ресурсов |
| `RULE_WINDOW_NOT_FOUND` | Окно из `window_ids` правила не найдено в снимке ресурсов (либо анализ без снимка, окон нет): правило не проверено | Исправить id окна в правиле или добавить окно в снимок (см. «Окна правил») |
| `INSUFFICIENT_SAMPLES` | В области правила есть запросы, но их меньше пола выборки (по умолчанию 20): порог не сравнивался | Взять более длинный прогон или осознанно снизить `sample_floor` (см. «Минимум выборки») |
| `RESOURCE_SERIES_NOT_FOUND` | Ряд из правила отсутствует в снимке | Добавить ряд или исправить `series_id` |
| `MISSING_RESOURCE_CELLS` | В ряду есть пропуски в окне оценки | Дополнить снимок или сузить окно |

Коды `CAPACITY_*` показываются в той же карточке, если результат получен в
режиме `capacity_step`; сам режим описан в ADR 0009.

Ступень не подтверждается (причина `CAPACITY_INSUFFICIENT_SAMPLES`, вердикт
ступени `INDETERMINATE`), если в её окне меньше запросов, чем действующий минимум
(`defaults.min_samples` политики, иначе запасное значение 100), либо хотя бы у
одного бизнес-правила этого окна пометка малой выборки (`sample_mode` равен
`SMALL_SAMPLE` или `INSUFFICIENT`). Число запросов окна считается по всем
запросам окна и записывается в `window_policy_summary` (`sample_count`; поле
`min_samples` только если политика задаёт `defaults.min_samples`). Условие
применяется и без политики. При очень низкой нагрузке (около 0,1 запроса в секунду
и меньше) ступень по этой причине не подтвердится: задайте
`"defaults": { "min_samples": N }` в политике, если для вашего профиля это
осознанно допустимо. Анализ в режиме `capacity_step` получает новый
`analysis_id` (в identity появляется блок `verdict_gates`, у анализа без
политики с ключами `min_samples_default` и `capacity_stage_sample_gate`); ключ
сопоставимости baseline не меняется, сохранённые анализы не изменяются.
Missing one-second bucket означает отсутствие samples, а не нулевое значение.
UI показывает такую секунду как `Missing / no samples` и не скрывает короткие
spikes заполнением или усреднением готовых percentiles.

### Ошибки upload/API

| --- | --- | --- |
| `MALFORMED_REQUEST` / 400 | Некорректный multipart или query | Повторить с корректным file/query |
| `MALFORMED_JSON` / 400 | Policy не является допустимым JSON | Исправить policy до анализа |
| 403 | Неверные Host, Origin, local session или CSRF | Перезагрузить только открытый local URL |

## Новый интерфейс

По умолчанию LT Verdict открывает новую оболочку: `http://127.0.0.1:<порт>/`.
Прежний интерфейс остаётся только по явному выбору:

- адрес `/?shell=old` или ссылка «Старый интерфейс» в шапке открывают прежний
  интерфейс и запоминают выбор в `localStorage` браузера (ключ `ltv.shell`,
  значение `old`); при следующих открытиях без параметра он остаётся прежним.
  Это единственное, что интерфейс сохраняет в браузере: данные анализа,
  политики и тексты не сохраняются;
- адрес `/?shell=new` открывает новую оболочку и сбрасывает сохранённый выбор;
- любое другое значение параметра (`shell=NEW`, пустое, лишние символы)
  игнорируется, и действует сохранённый выбор, а без него новая оболочка;
- если браузер запрещает `localStorage` (приватный режим, блокировка), выбор
  не запоминается: по умолчанию открывается новая оболочка, а `?shell=old`
  действует, пока адрес с этим параметром открыт; переход на адрес без
  параметра возвращает новую оболочку.

Чтобы вернуться из прежнего интерфейса к новому, откройте `/?shell=new` (или
очистите данные сайта в браузере). Прежний интерфейс остаётся доступным до
завершения перехода; данные, API и результаты у обоих интерфейсов общие.

Оболочка состоит из левой панели вкладок и шапки. Шапка закреплена при
прокрутке на экранах шире 680 px и показывает выбранный прогон, чип вердикта
(он открывает вкладку «Обзор» и карточку вердикта), переключатель темы и ссылку
на старый интерфейс.

Вкладки идут в порядке макета; при открытии страницы активна «Новый анализ»,
после выбора прогона или завершения анализа открывается «Обзор».

| Вкладка | Что показывает сейчас |
| --- | --- |
| Новый анализ | Экран запуска: файл нагрузки, правила, данные о системе, планы, блок готовности к запуску; ниже импорт из Jenkins |
| Обзор | Карточка вердикта, «Требует внимания», ключевые метрики, график нагрузки с общим курсором, ссылки на скачивание, сохранённая аналитика, панель Grafana |
| Глубокий анализ | График нагрузки и до шести рядов ресурсов на общей шкале времени с общим курсором в миллисекундах, пороги правил, выбор рядов, период и шаг ячеек |
| Таблицы | Русские таблицы «Правила» и «Транзакции», затем метрики, ресурсы, источники и нормализованные данные |
| Сравнение | Baseline: выбор и статистика |
| Правила | Шаблоны политики или файл, русский редактор порогов, правила по каждой транзакции |
| ИИ-разбор | Совет ИИ по выбранному анализу; модель, версия prompt и ошибки на русском берутся из ответа сервера (см. [advisory-ai.md](advisory-ai.md)) |

Навигация с клавиатуры: стрелки переключают вкладки (вверх и вниз или влево и
вправо, по кругу), `Home` и `End` переходят к первой и последней, `Tab`
выводит фокус из списка вкладок. Выбор сохранённого анализа в списке слева
открывает вкладку «Обзор». Ошибки и статус задачи видны на любой вкладке.

Тема берётся из настроек системы и переключается в памяти страницы; после
перезагрузки возвращается системная. Вкладка тоже не сохраняется.

Список принятых прогонов и сохранённых анализов слева в новой оболочке
подписан по-русски (в прежнем интерфейсе подписи остаются английскими).

Что пока не готово: содержимое остальных вкладок показано существующими
панелями, их подписи остаются английскими. Вкладки «Новый анализ» и «Правила»
русские.

### Вкладка «Обзор»

Под карточкой вердикта вкладка показывает три блока. Все данные берутся из
уже готового результата анализа и уже загруженной страницы интервалов
нагрузки; ничего не пересчитывается и новых запросов к серверу нет.

**Требует внимания.** Список пунктов в фиксированном порядке: нарушения
правил, причины, по которым нет вердикта, «политика не задана», неполные
данные и диагностика. Что попадает в список:

- нарушения: проверки бизнес-правил со статусом `FAIL` и SLA-проверки
  ресурсов со статусом `FAIL` (или `NO_VERDICT` при найденных нарушениях);
  в карточке вердикта показаны первые три, здесь все;
- причины `NO_VERDICT` теми же словами, что в карточке;
- неполные данные: причины неполного покрытия из результата, файл нагрузки,
  разобранный не полностью, и ряды ресурсов без единого значения в окне
  SLA-правила (кроме рядов генератора нагрузки). Причины покрытия показаны
  так же, как в карточке вердикта; сами по себе единичные пропуски ячеек
  ряда отдельным пунктом не считаются;
- диагностика: проверки ресурсных правил с `effect: diagnostic` и статусом
  `FAIL` (например `downstream-slow`, `db-saturated`, загрузка ЦП), найденные
  тренды (`TREND_OBSERVED`) и пары корреляций, которые отбор главной находки
  выбрал (`selected = true` в evidence `correlation_headline_selection`). Пара
  без `selected`, с причиной `HOLM_NOT_REJECTED`, `MATERIALITY_NOT_MET` или
  `UNAVAILABLE`, в список не попадает, как и результат без evidence отбора
  (анализы до отбора главной находки). Пункты диагностических правил и трендов
  помечены «диагностика, не причина», пункт корреляции пометкой «ассоциация, не
  причина; не откалибровано» и текстом: стадия, ряд ресурса и исход, лаг в
  секундах, ранговая корреляция, скорректированная вероятность, число
  проверенных гипотез, версия метода («при дрейфе ряда ненадёжно» для `v1`).
  Они показывают, что значения менялись вместе, в одну сторону или вышли за
  порог, это повод для проверки, а не вывод; на вердикт SLA-правил они не
  влияют. Исключение: в анализе ёмкости сработавшее диагностическое правило
  генератора нагрузки (guard) даёт причину `CAPACITY_GUARD_FAILED` и может
  привести к `NO_VERDICT`; эта причина уже показана в блоке причин. Пункт
  диагностического правила ведёт на вкладку «Глубокий анализ», где ряды
  непройденных правил выбраны первыми (не более шести рядов). Отсутствие пункта
  не доказывает, что всё в порядке.

Пустой список означает только то, что в результате нет перечисленного. При
`NO_POLICY` в списке есть пункт с переходом к форме запуска, где можно
задать политику. Кнопка в пункте («Открыть таблицу правил» и подобные)
переключает вкладку на «Таблицы» (или «Новый анализ»), прокручивает к нужной
секции и переводит фокус на её таблицу. К отдельной строке таблицы переход
пока не делается. Если пунктов больше шести, остальные скрыты кнопкой
«Показать ещё».

**Ключевые метрики прогона.** Пропускная способность, p95, p99 и максимум
отклика по всему прогону; формулы те же, что в таблицах вкладки «Таблицы».
Длительность, число запросов и доля ошибок остаются в фактах карточки
вердикта.

**Нагрузка по времени.** Три ряда друг под другом на общей шкале времени от
начала прогона: запросы в секунду, ошибки за интервал и p95 отклика. У каждого
ряда своя шкала (максимум подписан), единицы не смешиваются. Пропущенные
интервалы не соединяются линией и указаны текстом. Одновременное изменение
рядов подсказывает, где искать, но причину не доказывает.

Курсор один на все ряды. С клавиатуры: перейти к ползунку «Курсор по времени»,
стрелки влево и вправо двигают его по интервалам, `Home` и `End` переходят к
краям; мышь или касание над графиком ставят курсор на ближайший интервал.
Значения под курсором видны в заголовках рядов, а программы чтения экрана
получают их через значение ползунка (отдельной живой области нет, чтение не
повторяется). График показывает весь прогон: «Обзор» читает интервалы сам,
страницами по 500, и не зависит от шага и диапазона вкладки «Таблицы». Шаг
подбирается автоматически из 1, 10, 30 и 60 с: для прогона до 8 часов 20 минут
так, чтобы интервалов было не больше 1 500 (4-часовой тест рисуется шагом 10 с,
1 440 интервалов; короткий прогон остаётся с шагом 1 с), для более длинного
остаётся шаг 60 с. Шаг написан под графиком. При шаге больше 1 с запросы в
секунду усреднены за шаг, ошибки сложены, p95 посчитан по всем запросам шага,
а точное время внутри шага не видно и короткие всплески могут сгладиться
(значения по секундам видны на вкладке «Таблицы»). Защитный предел загрузки:
12 страниц шага 60 с (6 000 интервалов); сервер принимает не более 100 000
заполненных секундных интервалов, поэтому на практике предел не достигается, но
если бы он был достигнут, это сказано под графиком. Для прогона, файл
нагрузки которого не удалось разобрать, интервалов нет, нагрузка не
запрашивается, и вместо графика показан текст.

### Вкладка «Глубокий анализ»

Вкладка идёт после «Обзора» и открывает ту же шкалу времени глубже: нагрузка и
выбранные ряды ресурсов стоят друг под другом, курсор один на все ряды. Данные
рядов берутся из сохранённого анализа по API рядов (см. «Ряды ресурсов по API»),
файл снимка не скачивается; нагрузка берётся из тех же интервалов
(`/buckets`), что и в «Обзоре», с шагом, который подбирается под период.

**Что на экране.**

- Слева список рядов снимка с фильтром по имени (по `id` и метрике). Можно выбрать
  до шести рядов; когда выбрано шесть, остальные флажки отключены, и под списком
  сказано почему. При открытии выбраны ряды, у которых есть проверка правила не в
  статусе `PASS` (нарушенные правила первыми), затем ряды по порядку каталога.
- Две дорожки нагрузки (запросы в секунду и p95) и по дорожке на выбранный ряд.
  У каждой дорожки своя шкала, единицы не смешиваются. Для ряда указано, как
  считалось значение ячейки: среднее, максимум или минимум за интервал.
- Пунктирная линия порога на дорожке ряда, для которого в результате есть
  проверка `resource_policy_check`. Если правило пройдено, линия и подпись серые
  («порог правила: выше/ниже X»); красными они становятся с подписью «нарушение
  выше/ниже X», только когда ядро вернуло для правила `FAIL` хотя бы в одном окне.
  Если одно правило проверялось в нескольких окнах, линия одна. Вывод о нарушении
  делает ядро: график его не пересчитывает.
- Период: поля «С» и «По» в минутах от начала прогона (дробные допустимы) и
  кнопка «Весь прогон». Границы привязываются к границам ячеек наружу (период
  не уже заданного); результат показан текстом под полями. Неверный период
  (отрицательный, «с» не меньше «по») не отправляется.
- Шаг ячеек подбирается сам: наименьший шаг, кратный шагу снимка, при котором в
  периоде не больше 1 500 ячеек на ряд. Шаг нагрузки выбирается из 1, 10, 30 и
  60 с (так умеет `/buckets`) и тоже указан текстом. Вручную шаг в этом срезе не
  меняется.

**Курсор.** Курсор один на все дорожки и хранит время в миллисекундах от начала
прогона; значение показано в миллисекундах и как `ч:мм:сс`. Мышь или касание над
графиком ставят курсор на ближайший момент, ползунок «Курсор по времени» двигает
его по ячейкам самой частой дорожки (стрелки, `Home`, `End`). На каждой дорожке
показано значение ячейки, в которую попал момент курсора. Если в этот момент у
ряда нет данных, написано «нет данных». Если шаг ячейки укрупнён и часть исходных
ячеек не наблюдалась, значение помечено «наблюдено k из n»: среднее, максимум или
минимум посчитаны только по наблюдённым и могут отличаться от значения по полной
ячейке. Линия ряда не соединяет ячейки через пропуск.

**Когда чего нет.**

- Анализ без снимка ресурсов: ряды не запрашиваются, показаны только дорожки
  нагрузки и сообщение «Ряды ресурсов не загружены». Время отсчитывается от
  начала прогона.
- Файловый снимок (в том числе анализ теста максимума `capacity`) и онлайн-снимок
  с составными идентификаторами рядов открываются одинаково. У онлайн-снимка без
  объявленных окон показан весь прогон.
- Период целиком до начала прогона (снимок может начинаться раньше прогона):
  нагрузка не запрашивается, это сказано текстом.
- Нагрузка за период длиннее предела (12 страниц по 500 интервалов) показывается
  не вся, это сказано текстом: сузьте период.

**Предупреждение о часах.** Часы генератора нагрузки и кластера ядро не сверяет
(`clock_alignment: not_verified_by_core`). Сдвиг между нагрузкой и ресурсами на
графике неотличим от причинной связи; совпадение по времени подсказывает, где
искать, и ничего не доказывает.

**Числа.** Значения рядов это числа двойной точности из ответа API, они не
авторитетны: точные значения лежат в файле снимка и в статистиках окна
(`resource_summary`). Новых статистик периода (перцентили, скользящие средние)
вкладка не считает. Закрепление рядов, ручной шаг, таблица агрегатов и стадии в
этот срез не входят.

### Вкладка «Новый анализ»

Экран запуска заменяет в новой оболочке прежнюю форму «Run setup». Запуск идёт
тем же путём: файл нагрузки загружается, затем создаётся задача с теми же
частями запроса, что и из прежней формы; новых запросов к серверу и новых
полей нет. Подписи и сообщения проверок на экране русские; английскими
остаются сообщения об ошибках, которые присылает сервер, и блок импорта из
Jenkins под формой. Редактор политики находится на вкладке «Правила».

Экран состоит из пяти разделов и блока «Готовность к запуску»:

| Раздел | Что в нём |
| --- | --- |
| 1. Нагрузочный тест | Файл JMeter JTL (CSV или XML) или Gatling `simulation.log`. Обязателен только он |
| 2. Правила | Файл политики, ошибки её проверки, сводка политики и кнопка «Править правила» (открывает вкладку «Правила»). Без политики вердикт не выдаётся: результат получит статус `NO_POLICY`, метрики остаются доступны |
| 3. Данные о системе | Снимок ресурсов, контекст OpenSearch, онлайн-источники с окном и шагом, PostgreSQL (профиль, кнопки снимков «до» и «после», файлы «до», «после» и отчёт pg_profile) |
| 4. Планы анализа | Планы корреляций, ёмкости и трендов (файлы) |
| 5. ИИ-разбор | Переключатель «Запросить ИИ-разбор после анализа» (выключен по умолчанию): после завершения анализа совет ИИ запросится сам. Без него совет запрашивается кнопкой на вкладке «ИИ-разбор» |

**Файл или онлайн.** Снимок ресурсов, три плана и контекст OpenSearch берутся
из файлов. Если выбрать онлайн-источник, эти поля очищаются и блокируются:
снимок создаётся во время анализа, а смешивать файлы и онлайн-запрос сервер не
принимает. Файлы PostgreSQL от выбора онлайн-источника не зависят. Окно
источника задаётся автоматически по файлу нагрузки или явным периодом. Начало
и конец окна (UTC epoch), шаг, запас по краям и максимальный простой на этом
экране указываются в секундах; на сервер они уходят в миллисекундах, так что
запрос тот же, что из прежней формы (там поля остаются в миллисекундах).
Шаг: целые секунды от 1 до 60.

**Готовность к запуску.** Блок справа (на узком экране под формой) перечисляет,
что выбрано, и объясняет, почему кнопка «Запустить анализ» недоступна. У
каждой строки есть текстовое состояние: «Готово», «Не задано», «Внимание»
или «Нужно». Кнопку блокируют только эти условия:

- не выбран файл нагрузки;
- идёт загрузка файла, анализ или снимок PostgreSQL;
- параметры онлайн-источника не проходят проверку (число профилей, шаг,
  запас, простой, начало и конец окна);
- выбран план корреляций, ёмкости или трендов, но нет снимка ресурсов из
  файла (сервер отклоняет такой запуск сразу по самому факту плана без
  снимка);
- явное окно источника содержит больше 100 000 ячеек (длина окна, делённая на
  шаг): увеличьте шаг или сократите период;
- в редакторе политики есть ошибки (раньше запуск в этом случае молча не
  начинался).

Остальное только предупреждает. Файл политики, который сервер не принял, не
блокирует запуск: анализ пойдёт без правил и получит `NO_POLICY`, блок
готовности говорит об этом прямо. Число ячеек авто-окна страница проверить не
может: оно считается на сервере по распознанному периоду прогона, и при выходе
за 100 000 ячеек сервер вернёт `AUTO_WINDOW_SPAN_UNSUPPORTED` (увеличьте шаг
или задайте явное окно). Под списком «Что получится» перечислено, что войдёт в
результат (вердикт по правилам или метрики без вердикта, ряды ресурсов,
диагностика по планам, контекст OpenSearch и PostgreSQL, ИИ-разбор).

**ИИ-разбор при запуске.** Переключатель «Запросить ИИ-разбор после анализа»
(выключен по умолчанию) выражает намерение запустить разбор, а не разрешение:
продукт не запрашивает согласие на отправку данных в ИИ (ADR 0023). Когда анализ
завершится, приложение само запросит совет для этого анализа (тот же запрос, что
кнопка «Получить рекомендации») и покажет состояние, результат и ошибки на
вкладке «ИИ-разбор». Evidence анализа и системный prompt при этом уходят на
endpoint ИИ-runner; сегодня это внешний сервис ModelStudio (Singapore), подробности
в [advisory-ai.md](advisory-ai.md#что-и-куда-отправляется). Запрос относится
только к одному запуску: как только сервер принял файл и создал задачу анализа,
переключатель выключается (если загрузка не удалась, он остаётся включённым);
повторный запуск или открытие сохранённого анализа ничего не запрашивает без
нового включения. Состояние переключателя нигде не сохраняется: если страницу
перезагрузить во время анализа, совет не запросится, и его можно запросить
вручную. Если не удалось прочитать состояние совета или сервер отказал (например,
ИИ занят или не настроен), анализ остаётся готовым, причина показана на вкладке
«ИИ-разбор», а совет запрашивается вручную кнопкой на этой вкладке. Вердикт SLA
совет не меняет.

Что пока не перенесено из макета: метки плеч и выбор плеч OpenShift, пакеты
метрик, бюджет рядов, выбор baseline в форме
(baseline выбирается на вкладке «Сравнение»), перетаскивание файла и пример
прогона.

### Вкладка «Правила»

Вкладка собирает политику для следующего запуска: выберите шаблон или
загрузите файл `policy.v1`, поправьте пороги и вернитесь на вкладку «Новый
анализ». Правки сразу проверяются сервером (тот же `POST /api/policies/validate`,
что и раньше), сообщения сервера остаются английскими и выводятся с указателем
JSON. Политика применяется к следующему запуску или к пробному прогону на
открытом прогоне (раздел ниже): вердикт уже выполненных анализов не меняется.
На вкладке «Новый анализ» остаются поле файла политики и сводка
(идентификатор, число правил, число правил по отдельным транзакциям) с кнопкой
«Править правила»; редактор в окне один, поэтому на странице нет повторяющихся
идентификаторов полей.

**Шаблоны.** Выбор шаблона заменяет текущий черновик его копией.

| Шаблон | Что в нём |
| --- | --- |
| Базовый API (SLA) | p95 не более 1000 мс (1 с) и доля ошибок не более 0.05 (5 %), область «весь прогон». Это SLA владельца продукта |
| Строгий API | p95 не более 500 мс, p99 не более 1500 мс, доля ошибок не более 0.001 (0.1 %) |
| API с пропускной способностью | p95 не более 1000 мс, доля ошибок не более 0.01 (1 %), пропускная способность не менее 100 RPS |

Шаблоны «Строгий API» и «API с пропускной способностью» это стартовые
значения, а не нормативы: поправьте их под ваш SLA. Шаблоны проверяются схемой
`policy.v1` в `npm --prefix ui run test:contracts`.

**Единицы порога.** Время отклика задаётся в миллисекундах, пропускная
способность в запросах в секунду (RPS). Порог ошибок остаётся долей от 0 до 1,
как в контракте и файлах политики; рядом с полем написан пересчёт: у `0.05`
подсказка «= 5 %». Метрики и условия в списках подписаны по-русски («p95
отклика, мс», «не более»), в файл по-прежнему попадают коды метрик и
операторов. Поля политики, которых нет в редакторе (например, `window_ids` или
неизвестные поля), при правке сохраняются.

**Минимум выборки.** Под идентификатором политики два поля `defaults`: «Пол
выборки политики» (`defaults.sample_floor`) и «Минимум выборки политики по
умолчанию» (`defaults.min_samples`); у каждого правила (кроме правила
пропускной способности) поле «Минимум выборки правила» (`min_samples`). Это целые
`1..1000000`; пустое поле удаляет ключ из файла, а когда в `defaults` не остаётся
ни одного ключа, удаляется и сам блок. Приоритет, смысл и таблица результатов
описаны в разделе о малой выборке ниже; числа 20 и 100 это допущения, а не
калибровка стенда, поэтому они и настраиваются. Если пол задан ниже 20,
рядом с ним показывается предупреждение: p95 может совпасть с максимумом
выборки. Для правила `throughput_rps` поля нет: ядро отвергает его как
`FIELD_NOT_APPLICABLE`, поэтому при смене метрики правила на пропускную
способность уже заданный минимум удаляется. Ограничения проверяет сервер, а не
браузер: значение вне `1..1000000` даёт `MIN_SAMPLES_OUT_OF_RANGE`, минимум
правила ниже пола `MIN_SAMPLES_BELOW_FLOOR`, дробное число `INVALID_TYPE`; сообщение
выводится с указателем JSON (например, `/rules/0/min_samples`). Прежний
интерфейс (`?shell=old`) этих полей не показывает.

**Правила по каждой транзакции.** В `policy.v1` нет правила «для каждой
транзакции»: область правила это весь прогон или транзакция с точным именем.
Поэтому SLA «по каждому эндпоинту» разворачивает браузер. Кнопка «Правила по
каждой транзакции» берёт транзакции открытого прогона (те же, что в таблице
«Транзакции») и копирует на каждую правила «весь прогон» по времени отклика и
ошибкам (пропускная способность не копируется). Порядок такой: выберите
шаблон, запустите анализ, откройте вкладку «Правила», нажмите кнопку и запустите
анализ повторно. Правила разворота:

- идентификатор новой копии `<идентификатор правила>--txNNN`, где `NNN` порядковый
  номер транзакции в порядке имён; имя транзакции лежит только в области
  правила. Если базовый идентификатор длиннее 121 байта (лимит схемы 128), разворот
  отклоняется, а не укорачивает идентификатор;
- транзакции с одним именем в разных путях или типах пропускаются и
  перечисляются: правило на них дало бы `AMBIGUOUS_TRANSACTION` и
  `NO_VERDICT` всего прогона; они остаются только под правилом «весь прогон»;
- транзакции с числом наблюдений меньше пола (`defaults.sample_floor`, иначе 20)
  пропускаются и перечисляются с числом наблюдений: правило на них дало бы
  `INSUFFICIENT_SAMPLES` и `NO_VERDICT` всего прогона. Чтобы такая транзакция
  попала под правило, нужен прогон с большим числом наблюдений либо
  согласованное снижение `defaults.sample_floor` и минимума (это правка
  политики вручную);
- транзакции с пустым именем пропускаются: сервер не принимает правило с пустым
  именем области;
- если правил получилось бы больше 256 или политика превысила бы 1 МиБ (лимиты
  сервера), разворот отклоняется целиком, политика остаётся прежней;
- повторное нажатие на том же прогоне не создаёт дублей и ничего не меняет:
  правило с той же метрикой, условием и транзакцией пропускается, правила,
  заданные вручную, не перезаписываются;
- развёрнутые правила действительны только для транзакций того прогона, по
  которому они построены, поэтому при новом развороте прежние развёрнутые
  правила заменяются. Развёрнутым считается правило с областью «Транзакция» и
  идентификатором, оканчивающимся на `--txNNN` (три цифры и более). Такие
  правила удаляются и создаются заново по транзакциям открытого прогона;
  правила «весь прогон» и правила, заданные вручную, не затрагиваются (за
  исключением случая с `--txNNN` ниже). Панель
  сообщает, сколько правил удалено и сколько добавлено. Лимиты (256 правил,
  1 МиБ) считаются уже после удаления, при отказе политика остаётся прежней,
  в том числе её прежние развёрнутые правила;
- порог, исправленный вручную в развёрнутом правиле, при повторном развороте
  вернётся к значению правила «весь прогон». Чтобы сохранить правку, смените
  идентификатор правила (уберите окончание `--txNNN`): тогда оно станет
  ручным. Ручное правило с областью «Транзакция» и идентификатором,
  оканчивающимся на `--txNNN`, будет удалено при новом развороте.

Порядок для нового прогона: откройте его результат, на вкладке «Правила»
нажмите «Правила по каждой транзакции» и запустите анализ повторно; без этого
развёрнутые правила прежнего прогона дали бы `TRANSACTION_NOT_FOUND` и
`NO_VERDICT`. Новая транзакция, которой не было в прогоне, по которому
выполнен разворот, остаётся только под правилом «весь прогон».

До первого анализа список транзакций клиенту неизвестен (файл нагрузки
разбирает сервер), поэтому кнопка недоступна с подсказкой «Список транзакций
появится после первого анализа». Постоянное правило «для каждой транзакции»,
которое действует на любой новый прогон за один проход, потребует новой
области в `policy.v1`, правки ядра и ADR; в этот срез оно не входит.

**Пробный прогон на открытом прогоне.** Кнопка «Проверить на открытом прогоне»
внизу вкладки применяет черновик к прогону, который выбран в списке слева, без
повторной загрузки файла. Это не симуляция в браузере, а обычный анализ ядром
того же прогона (то же задание, что и при запуске с экрана «Новый анализ»),
поэтому вердикт совпадает с обычным запуском. Что важно знать:

- каждая проверка создаёт сохранённый анализ этого прогона и добавляет его в
  список анализов; если политика и входные данные те же, что у существующего
  анализа, сервер возвращает его, и новый не создаётся;
- снимок ресурсов, диагностический план, планы ёмкости и трендов, контекст
  источников и снимки PostgreSQL не передаются: проверяются только правила
  нагрузки. Прежние анализы этого прогона с такими файлами не меняются;
- кнопка недоступна, пока не выбран прогон, нет политики, у черновика есть
  ошибки проверки сервером или идёт другой анализ; двойное нажатие не создаёт
  второго задания; ответ «очередь занята» (`BUSY`) показывается как на «Новом
  анализе», кнопка остаётся рабочей;
- вкладка «Правила» остаётся открытой: под кнопкой появляется итог (заголовок
  и краткая метка вердикта, например «Прогон не проходит — нарушено проверок:
  1 из 3», «нарушено 1 из 3») и кнопка «Открыть обзор», которая ведёт на полную
  карточку вердикта. Итог показывается только для завершённой проверки и
  исчезает при любой правке черновика, в том числе сделанной, пока проверка
  ещё идёт (тогда итога не будет совсем: он относился бы к прежнему черновику);
  при сбое или отмене итога нет, ошибка видна в строке состояния задания;
- от нажатия кнопки до конца проверки заблокированы список прогонов, список
  анализов и запуск на экране «Новый анализ»; отмена задания в строке
  состояния снимает проверку, и устаревший ответ не публикуется. Если связь с
  сервером потеряна, проверка прекращается; после «Retry» готовый результат
  откроется обычным образом на вкладке «Обзор», без итога на вкладке «Правила».

### Вкладка «Сравнение»

В новой оболочке вкладка «Сравнение» это панель baseline целиком по-русски
(заголовок «Сравнение с baseline»); в прежнем интерфейсе та же панель остаётся
прежней английской «Baseline comparison». Порядок работы и API те же, что в
разделе «Baseline: ручной выбор и статистический автовыбор»: серия сравнения,
«Назначить baseline», выбор окон, «Сравнить выбранный анализ», «Сбросить
baseline» и раздел «Статистический выбор».

Над формой написано главное: сравнение показывает изменения, но вердикт не
меняет; статус «кандидат» появляется только после вашего
подтверждения, что условия прогонов сопоставимы. Подтверждение это форма
«Плановые условия для этой пары анализов» с тремя вариантами («Подтверждаю:
плановые условия теста те же», «Не подтверждено», «Неизвестно») и кнопкой
«Сохранить решение об условиях»: решение сохраняется на сервере для точной
пары анализов (и пары окон, если они введены), а не по имени серии. Рядом с
таблицей отклонений строка статуса говорит либо «Условия подтверждены вами»,
либо «Условия не подтверждены: изменения только описательные, статус
«кандидат» невозможен».

Предупреждения выводятся русским текстом в том порядке, в котором их вернул
сервер; неизвестный код выводится как есть. Статусы окон написаны словами
(«описательно», «без заметных изменений», «существенное изменение (кандидат)»,
«недостаточно данных», «не оценивалось»); «кандидат» отмечает существенное
изменение в любую сторону, в том числе улучшение, и не доказывает регрессию.
У кодов причин показаны расшифровка и
сам код в скобках (например «нулевой baseline (ZERO_BASELINE)»); неизвестный
код остаётся кодом. Числа, дельты, статусы и предупреждения берутся только из
ответа сервера, интерфейс ничего не пересчитывает и вердикт не меняет.
Сообщения об ошибках сервера остаются на английском. Внутренности развёрнутого
графика сравнения («Графики baseline и текущего прогона») пока английские.

Что пока не перенесено из макета: выбор baseline из истории релизов, выбор
транзакции и график с порогом. Предупреждения и заметка о малой выборке как
baseline появятся вместе с серверным допуском такого baseline.

### Вкладка «Таблицы»

В новой оболочке вкладка начинается с русских таблиц: «Ёмкость» (только у
анализа теста максимума), «Правила», «Транзакции» и «Тренды» (только если
задан план трендов); остальные разделы вкладки (метрики прогона, ресурсы,
источники, диагностика, нормализованные данные) пока остаются в прежнем виде и
английскими. В прежнем интерфейсе
таблицы остались прежними английскими «Policy results» и «Transaction metrics»;
в «Policy results» добавлен столбец `Sample` (`30 / 50 · SMALL_SAMPLE`).

Таблица «Правила» показывает по строке на каждую проверку политики в порядке
результата: идентификатор правила, область («весь прогон» или транзакция),
метрику, условие с порогом («не более 2 000 мс»), измеренное значение, окно,
выборку (например «30 из 50 · малая выборка»; для правил без порога выборки
«3 650 · без порога», для старых результатов прочерк), статус и причину. Статус всегда
написан словами («Нарушение», «В норме»,
«Нет вердикта»), цвет только дополняет его. Если у проверки нет значения,
вместо числа написано «нет данных», а для кода причины показаны расшифровка и
сам код; неизвестный код выводится как есть. Если округление скрывает разницу
между измеренным значением и порогом, добавляются знаки после запятой, чтобы
нарушение не выглядело равенством. Если в результате нет проверок правил по
метрикам нагрузки (политика не задана или заданы только правила ресурсов),
вместо таблицы выводится пояснение.

Таблица «Транзакции» показывает по строке на транзакцию: выборку, ошибки и их
долю, p50, p95, p99, RPS и статус по её правилам. Поиск (по пути и имени
транзакции) и фильтр статуса работают в браузере, без запросов к серверу.
Порядок по умолчанию такой же, как раньше: сначала нарушившие правила, затем
по числу ошибок, p99 и выборке (это написано над таблицей). Кнопки в
заголовках сортируют по столбцу
(повторное нажатие меняет направление), текущая сортировка видна и
скринридеру. Строки идентифицируются результатом ядра, поэтому транзакции с
одним именем в разных группах остаются различимыми. Состояние поиска и
сортировки нигде не сохраняется. Числа берутся только из результата анализа,
интерфейс ничего не пересчитывает и вердикт не вычисляет.

Таблица «Ёмкость» появляется, если результат содержит сводку теста максимума.
Над таблицей: ось нагрузки, граница ёмкости словами (от какой до какой
нагрузки, верхняя граница не включается; для границы только сверху или только
снизу сказано, чего именно не найдено), вердикт по ёмкости, точка перегиба
(в этой версии ядро её не определяет, это написано прямо) и причины
с расшифровкой и кодом. В таблице по строке на ступень: цель, достигнутая
нагрузка (p05 за 10 с), наблюдавшийся минимум и максимум, число полных
интервалов из ожидаемых, подтверждённая нагрузка, итог ступени («Выдержана»,
«Нарушение», «Не подтверждена», «Без правил»), причины и ссылки на данные.
Ступень с причиной `CAPACITY_INSUFFICIENT_SAMPLES` помечена «малая выборка»:
в окне меньше запросов, чем минимум, либо у правила окна малая выборка. Такая
ступень не подтверждена и не определяет границу ёмкости. Сама метка не
означает нарушения SLA, а результат SLA в этом окне для границы не
используется. Числа ёмкости показаны с теми цифрами, которые вернул сервер,
без округления. Где данных нет, написано «нет данных», неизвестный код
причины или итога выводится как есть.

Таблица «Тренды» (проверки трендов ресурсов) показывает по строке на проверку:
ряд, окно, заявленное направление («рост», «снижение», «любое»), статус
(«Наблюдается», «Не существенно», «Мало данных», «Недоступно»), наблюдаемое
направление, наклон в секунду, сдвиг половин окна, медиану, требуемый сдвиг,
число наблюдённых и ожидаемых ячеек и причины с расшифровкой и кодом. Над
таблицей написано число проверок по статусам и пояснение метода
`slope-materiality.v1`: тренд это диагностика, на вердикт он не влияет, а
отсутствие находки не доказывает отсутствие деградации; неопределённость не
оценивается. Единицы берутся из ряда; если единицы в ряду нет, число
показано без неё.

## Policy: import, edit и download

`Policy file` импортирует один JSON object `policy.v1`. После успешной
validation UI показывает editor для `policy_id`, rules, metric, operator,
threshold и scope. `Add rule`/`Remove rule` меняют только текущий draft;
`Download policy` сохраняет его как `policy.json`. В новой оболочке то же
самое делает вкладка «Правила» (с шаблонами и русскими подписями). Это отдельное действие от
экспорта готового analysis через `Download JSON`/`Download HTML`/`Download AsciiDoc`.

Перед использованием сохранённого файла выполните:

```text
ltv policy validate <policy.json>
```

Valid command печатает canonical policy JSON и возвращает exit `0`.

### Четыре разрешённые метрики

| Metric | Operator | Threshold |
| --- | --- | --- |
| `response_time_p95_ms` | `lte` | число `>= 0`, milliseconds |
| `response_time_p99_ms` | `lte` | число `>= 0`, milliseconds |
| `error_rate_ratio` | `lte` | число от `0` до `1` |
| `throughput_rps` | `gte` | число `>= 0`, requests/second |

Error rate и throughput сравниваются как exact ratios через cross-multiplication
с `BigDecimal`; display rounding не влияет на verdict. Latency observations для
policy остаются integer milliseconds.

Ниже contract example из tracked fixture. Числа показывают JSON shape и не
являются рекомендуемым SLA: замените их согласованными значениями.

```json
{
  "schema_version": "policy.v1",
  "policy_id": "all-metrics",
  "rules": [
    {
      "id": "overall-p95",
      "metric": "response_time_p95_ms",
      "operator": "lte",
      "threshold": 100,
      "scope": {
        "kind": "overall"
      }
    },
    {
      "id": "orders-p99",
      "metric": "response_time_p99_ms",
      "operator": "lte",
      "threshold": 100,
      "scope": {
        "kind": "transaction",
        "name": "POST /orders"
      }
    },
    {
      "id": "overall-errors",
      "metric": "error_rate_ratio",
      "operator": "lte",
      "threshold": 0.5,
      "scope": {
        "kind": "overall"
      }
    },
    {
      "id": "orders-throughput",
      "metric": "throughput_rps",
      "operator": "gte",
      "threshold": 0.1,
      "scope": {
        "kind": "transaction",
        "name": "POST /orders"
      }
    }
  ]
}
```

### Минимум выборки

Каждое бизнес-правило (метрики задержки и доли ошибок) проверяет, сколько
запросов попало в его область (всего прогона, одна транзакция или окно).
Правило `throughput_rps` этой проверкой не охватывается.

| Запросов `n` в области правила | Результат правила | Причина |
| --- | --- | --- |
| `0` | `NO_VERDICT` | `METRIC_NOT_AVAILABLE` |
| `1` до `sample_floor - 1` | `NO_VERDICT`, порог не сравнивается | `INSUFFICIENT_SAMPLES` |
| от `sample_floor` до `min_samples - 1` | обычный `PASS` или `FAIL` с пометкой | `SMALL_SAMPLE` (информационная) |
| `min_samples` и больше | обычный результат | нет |

Пол по умолчанию равен 20, рекомендуемый минимум равен 100. Значения задаются
политикой: у правила `min_samples`, для всей политики блок `defaults` с полями
`sample_floor` и `min_samples` (целые `1..1000000`). Приоритет такой: поле
правила, затем `defaults`, затем запасная константа ядра (20 и 100). Минимум не
может быть меньше пола; нарушение даёт `MIN_SAMPLES_BELOW_FLOOR`.

```json
{
  "schema_version": "policy.v1",
  "policy_id": "sample-gate",
  "defaults": { "sample_floor": 20, "min_samples": 100 },
  "rules": [
    {
      "id": "checkout-p99",
      "metric": "response_time_p99_ms",
      "operator": "lte",
      "threshold": 800,
      "scope": { "kind": "transaction", "name": "POST /checkout" },
      "min_samples": 1000
    }
  ]
}
```

`SMALL_SAMPLE` не превращает вердикт в `NO_VERDICT`: достоверный `FAIL` остаётся
`FAIL`, а `PASS` остаётся `PASS`. Пометка попадает в `analysis_coverage.reasons`
(статус покрытия становится `INCOMPLETE`) и в проверку правила
(`policy_check`: поля `sample_count`, `sample_floor`, `min_samples`,
`sample_mode` со значениями `FULL`, `SMALL_SAMPLE`, `INSUFFICIENT`,
`NOT_GATED`). Код выхода CLI не меняется: `0` для `PASS`, `2` для `FAIL`, `3`
для `NO_VERDICT`. По решению пользователя малая выборка должна быть пригодна как baseline с
предупреждением, но пока это не включено: автоматический отбор baseline по
статистике исключает анализ со статусом покрытия `INCOMPLETE`, в том числе из-за
`SMALL_SAMPLE`; допуск с предупреждением вводится отдельным срезом. Ручной выбор
baseline этой проверки не выполняет.

Внимание: при выборке меньше 100 запросов p95 и p99 опираются на единицы
наблюдений, а при `n` меньше 20 p95 может совпасть с максимумом. Ложный `FAIL`
по p95 на малой выборке возможен, оценивайте его осторожно.

Существующие политики, не задающие `defaults`, на коротких прогонах теперь дают
`NO_VERDICT` (меньше 20 запросов в области правила) или пометку `SMALL_SAMPLE`
(от 20 до 99). Чтобы вернуть прежнее поведение на малых входах, укажите
`"defaults": { "sample_floor": 1, "min_samples": 1 }`. Анализ с политикой
получает новый `analysis_id`, поскольку запасные константы входят в identity;
уже сохранённые анализы не меняются.

### Окна правил

Бизнес-правило можно привязать к именованным окнам снимка ресурсов (`windows`)
необязательным полем `window_ids`: непустой массив уникальных непустых строк, до
128 байт UTF-8 каждая. Без поля правило проверяется во всех окнах, как раньше. С
полем оно проверяется только в названных окнах и пропускается в остальных.

```json
{
  "schema_version": "policy.v1",
  "policy_id": "window-ids",
  "rules": [
    {
      "id": "checkout-p95-steady",
      "metric": "response_time_p95_ms",
      "operator": "lte",
      "threshold": 800,
      "scope": { "kind": "transaction", "name": "POST /checkout" },
      "window_ids": ["steady-1", "steady-2"]
    }
  ]
}
```

- Окно, в котором нет ни одного применимого бизнес-правила, получает
  бизнес-вердикт `NO_POLICY`, а не пустой `PASS`. Такое окно не требует запросов
  нагрузки и не получает `BUSINESS_OBSERVATIONS_NOT_FOUND`. Окно с `NO_POLICY`
  не меняет общий вердикт, пока другое окно проверено; если проверять нечего ни в
  одном окне (нет ни бизнес-правил, ни SLA-правил ресурсов), вердикт `NO_POLICY`.
- Id окна, которого нет в снимке, даёт `NO_VERDICT` с причиной
  `RULE_WINDOW_NOT_FOUND` и evidence `rule_window_check` (`rule_id`,
  `window_id`). Опечатка в id не может дать `PASS`, даже если другие правила
  прошли или нарушены. Без снимка ресурсов окон нет, поэтому правило с
  `window_ids` даёт `NO_VERDICT` с той же причиной. В режиме `capacity_step`
  итоговый `PASS` или `FAIL` по ёмкости при такой опечатке тоже заменяется на
  `NO_VERDICT`, причина `RULE_WINDOW_NOT_FOUND` попадает в причины ёмкости.
- Число запросов для минимума выборки считается по области правила в оцениваемом
  окне. Редкую транзакцию привязывайте к окнам, где она набирает `min_samples`
  (например, к стадиям с нагрузкой). Без привязки у неё в разгоне и завершении
  окна будет малая выборка. Разгон и завершение входят в оценку, если окно
  неявное (`run-intersection`) или вы сами включили их в окно снимка.
- Анализ без `window_ids` не меняется: `analysis_id` и результат остаются прежними.
  Файл политики с `window_ids` имеет другой `policy_sha256`, поэтому у такого
  анализа другой `analysis_id`.

Ошибка формы поля (пустой массив, повтор, не строка, слишком длинный id) даёт
`WINDOW_IDS_INVALID` с указателем `/rules/<i>/window_ids`. Существование id
проверяется уже при анализе, не при `ltv policy validate`.

### Правила платформы

Платформенные SLA-пороги (CPU, память, OOM, рестарты, доступность реплик) можно
хранить в политике рядом с бизнес-правилами (ADR 0018, решения D3 и D4). Один
элемент `platform_rules[]` задаёт шаблон проверки, а ядро разворачивает его по
сервисам в обычные ресурсные правила и оценивает тем же вычислителем, что и
правила снимка. Секции необязательные; политика без них не меняется.

```json
{
  "schema_version": "policy.v1",
  "policy_id": "platform-services",
  "rules": [
    {
      "id": "overall-errors",
      "metric": "error_rate_ratio",
      "operator": "lte",
      "threshold": 0.01,
      "scope": { "kind": "overall" }
    }
  ],
  "platform_services": ["orders", "payments"],
  "platform_coverage": { "signal": "openshift_unavailable_replicas" },
  "platform_rules": [
    {
      "id": "cpu-share",
      "signal": "openshift_container_cpu_limit_ratio",
      "scope": { "kind": "all_services", "except": ["payments"] },
      "operator": "gt",
      "threshold": 0.4,
      "unit": "ratio",
      "aggregation": "interval_mean",
      "min_consecutive_cells": 2,
      "effect": "sla"
    },
    {
      "id": "replicas",
      "signal": "openshift_unavailable_replicas",
      "scope": { "kind": "all_services" },
      "operator": "gt",
      "threshold": 0,
      "unit": "count",
      "aggregation": "interval_max",
      "min_consecutive_cells": 1,
      "effect": "sla"
    }
  ]
}
```

- Поля правила: `id`, `signal` (точное значение `metric` ряда снимка), `scope`,
  `operator`, `threshold`, `unit`, `aggregation`, `min_consecutive_cells`
  (1..100 000), `effect` (`sla` или `diagnostic`) и необязательное `window_ids`
  (как у бизнес-правил). Правил до 256; всех проверок после разворачивания тоже не
  больше 256.
- `operator` здесь `gt` или `lt` и означает **условие нарушения** (как у
  ресурсных правил снимка), в отличие от `lte` и `gte` у бизнес-правил, где
  оператор описывает условие прохождения. `min_consecutive_cells` считает соседние
  нарушающие ячейки сетки снимка, а не секунды.
- Область `{"kind":"service","services":[...]}` называет **ожидаемые** сервисы
  явным списком. Область `{"kind":"all_services","except":[...]}` берёт каталог
  `platform_services` (до 64 уникальных имён) без `except`; каталог обязателен, а
  каждое имя в `except` обязано входить в каталог, иначе `INVALID_SCOPE` (опечатка
  не должна молча оставлять сервис без проверки). Область, опустевшая после
  `except`, тоже `INVALID_SCOPE`. Wildcard и regex не поддерживаются. Если состав
  сервисов или пороги плеч различаются, используйте отдельный файл политики на
  плечо: поля плеча в правиле нет.
- Привязка ряда: для пары «правило × сервис» нужен ровно один ряд снимка с
  `metric = signal`, `entity` равным имени сервиса и `role = system`; `unit` и
  `aggregation` ряда должны совпасть с заявленными в правиле, единицы не
  пересчитываются. Развёрнутая проверка называется `<id правила>/<сервис>`
  (`cpu-share/orders`), её evidence `resource_policy_check` получает поля
  `platform_rule_id` и `service`.
- Покрытие. Если есть хотя бы одно платформенное правило `effect = sla`,
  обязательна секция `platform_coverage` с `signal` (рекомендуется
  `openshift_unavailable_replicas`). Для каждой пары «сервис × окно», где
  действует такое правило, должно быть правило покрытия: тот же сигнал, `gt`,
  порог `0`, `min_consecutive_cells = 1`, `effect = sla`, агрегация
  `interval_max`, область которого включает сервис, а `window_ids` включают окно
  (без `window_ids` правило покрытия действует во всех окнах; у покрываемого
  правила без `window_ids` покрытие тоже должно быть без `window_ids`; окна одного
  правила могут покрывать несколько правил покрытия вместе). Иначе
  ошибка `PLATFORM_COVERAGE_MISSING`. Так пропавший под не даёт `PASS` по
  непрерывному ряду другого сигнала. Граница гарантии: ядро не проверяет, что
  запрос профиля источника честно считает `desired - available`.
- Один владелец SLA-порога. Если в политике есть `platform_rules`, снимок и
  профиль источника не могут одновременно поставлять ресурсные правила
  `effect = sla` (`diagnostic`-правила снимка допустимы, в том числе проверки
  генератора для ёмкости). Пороги переносят из снимка или профиля в политику;
  дальнейшая правка порога меняет `policy_sha256`, а не хэш снимка. Политика без
  `platform_rules` работает как раньше.
- Допуск пропусков действует только у платформенных правил `effect = sla` и
  описан в разделе «Допуск пропусков» ниже; правила снимка и профиля источника
  остаются строгими.

Причины, блокирующие вердикт (`NO_VERDICT`), у платформенных `sla`-правил:

| Причина | Когда |
| --- | --- |
| `RESOURCE_SERIES_NOT_FOUND` | У ожидаемого сервиса нет ряда сигнала, в том числе сервис исчез целиком |
| `PLATFORM_SERIES_AMBIGUOUS` | Подходит больше одного ряда сервиса, ядро не выбирает первый |
| `PLATFORM_UNIT_MISMATCH` | Единица ряда отличается от `unit` правила |
| `PLATFORM_AGGREGATION_MISMATCH` | Агрегация ряда отличается от `aggregation` правила |
| `PLATFORM_SERVICE_NOT_IN_CATALOG` | Для области `all_services` в снимке есть ряд сигнала у сервиса, которого нет ни в каталоге, ни в `except` |
| `RULE_WINDOW_TOO_SHORT` | В окне меньше ячеек, чем `min_consecutive_cells`: серию физически нельзя найти |
| `RULE_WINDOW_NOT_FOUND` | Id из `window_ids` платформенного правила не найден среди окон снимка |
| `RESOURCE_SNAPSHOT_REQUIRED` | В политике есть платформенное `sla`-правило, а снимок не передан |

У правил `effect = diagnostic` те же ситуации не блокируют вердикт: причина
попадает в покрытие (`analysis_coverage`), а само правило в вердикт не входит. Без
снимка политика только с `diagnostic`-правилами получает
`RESOURCE_SNAPSHOT_REQUIRED` как информационную причину.

#### Допуск пропусков

Источники метрик теряют точки, поэтому у платформенного `sla`-правила пропуски в
ряду сервиса допускаются в заданных пределах (ADR 0018, решение D6). Допуск
задают два необязательных поля: `max_missing_fraction` (число, `0 <= x < 1`: доля
пропущенных ячеек окна) и `max_gap_cells` (целое `0..100000`: самый длинный разрыв
подряд в ячейках сетки снимка). Их можно указать в `defaults` политики и
переопределить в правиле; приоритет такой: правило, затем `defaults`, затем запасные
значения ядра 5 % (`0.05`) и 3 ячейки. Это допущения владельца, на реальных
прогонах они не измерены. У правила `effect = diagnostic` поля не применимы
(`FIELD_NOT_APPLICABLE`), диагностическое правило остаётся строгим; вне диапазона
поле даёт `TOLERANCE_OUT_OF_RANGE`.

```json
{
  "defaults": { "max_missing_fraction": 0.1, "max_gap_cells": 5 },
  "platform_rules": [
    {
      "id": "replicas",
      "signal": "openshift_unavailable_replicas",
      "scope": { "kind": "all_services" },
      "operator": "gt",
      "threshold": 0,
      "unit": "count",
      "aggregation": "interval_max",
      "min_consecutive_cells": 1,
      "effect": "sla",
      "max_missing_fraction": 0,
      "max_gap_cells": 0
    }
  ]
}
```

(фрагмент: остальные секции политики опущены; полный пример лежит в
`docs/contracts/policy/v1/examples/valid/platform-gap-tolerance.json`).

- Если в окне правила есть пропуски, но их доля не больше `max_missing_fraction`,
  самый длинный разрыв не длиннее `max_gap_cells` и наблюдена хотя бы одна ячейка,
  правило оценивается по наблюдённым ячейкам: `PASS` или `FAIL` с информационной
  причиной `RESOURCE_GAPS`. Такой анализ получает статус покрытия `INCOMPLETE`
  (`analysis_coverage.status`) и поэтому не станет кандидатом для statistical
  baseline. Доля покрытия считается интерфейсом из счётчиков.
- Иначе правило получает `NO_VERDICT` с `MISSING_RESOURCE_CELLS`, а найденные
  нарушения остаются в findings. Окно целиком из пропусков всегда даёт
  `NO_VERDICT`, при любых значениях допуска. Значения `0` и `0` возвращают строгое
  поведение: любой пропуск блокирует вердикт.
- Evidence `resource_policy_check` платформенных правил получает счётчики
  `expected_cells`, `observed_cells`, `missing_cells` и `longest_gap_cells` (в окне
  оценки).
- Серия через пропуск. Нарушающие ячейки по обе стороны пропуска считаются серией
  только как гипотеза. `FAIL` выдаётся лишь тогда, когда `min_consecutive_cells`
  нарушающих ячеек идут подряд среди наблюдённых. Если серия достигает минимума
  только за счёт пропущенных ячеек, правило получает `NO_VERDICT` с
  `MISSING_RESOURCE_CELLS`, а находка сохраняется с пометкой `presumed: true`
  (поле `cell_count` такой находки считает и пропущенные ячейки внутри цепочки). Так
  один пропуск внутри нарушения не даёт ни ложного `PASS`, ни недоказанного `FAIL`.
- Граница `PASS`. `PASS` при допуске не доказывает, что нарушения не было внутри
  допущенного пропуска: при шаге 15 с и трёх пропущенных ячейках это до 45 с.
  Это принятый риск допуска; снижайте `max_gap_cells`, если он неприемлем.
- Правило покрытия (`platform_coverage`) тоже платформенное `sla`-правило и тоже
  получает допуск по умолчанию; чтобы потеря точки сигнала недоступности реплик
  блокировала вердикт, задайте у него `"max_missing_fraction": 0` и
  `"max_gap_cells": 0`.
- Identity. Анализ с политикой, где есть `platform_rules`, добавляет в
  `verdict_gates` ключи `max_missing_fraction_default` (`"0.05"`) и
  `max_gap_cells_default` (`"3"`), поэтому такой анализ получает новый
  `analysis_id`. Анализы без `platform_rules` и ключ сопоставимости baseline не
  меняются.

Ошибки привязки политики к снимку проверяются до создания анализа: CLI завершается
кодом 4, API отвечает 422 с телом `{valid:false, errors}`, задача онлайн-источника
получает диагностику с тем же кодом.

| Код | Причина |
| --- | --- |
| `PLATFORM_RULES_CONFLICT` | В политике есть `platform_rules`, а снимок или профиль поставляет ресурсное правило `effect = sla` |
| `DUPLICATE_RULE_ID` | Развёрнутый id (`<id>/<сервис>`) совпал с id правила снимка или с другим развёрнутым id |
| `RESOURCE_LIMIT_EXCEEDED` | Развёрнутых проверок вместе с правилами снимка больше 256 или развёрнутый id (в том числе сервиса вне каталога) длиннее 128 байт UTF-8 |

Анализ без `platform_rules` не меняется: `identity.json`, ключ сопоставимости
baseline и `analysis_id` прежние. Файл политики с платформенными секциями имеет
другой `policy_sha256`, поэтому у такого анализа другой `analysis_id`. Прежняя
версия отвергает такой файл как `UNKNOWN_FIELD`. Имена сигналов (`openshift_*`) в
ядро не зашиты: оно сопоставляет только точную строку.

### Exact transaction matching

Transaction scope имеет ровно форму:

```json
{
  "kind": "transaction",
  "name": "POST /orders"
}
```

`name` сравнивается с exact label, без regex, wildcard, fuzzy matching,
auto-rename или регистра-независимого поиска. Если label не найден, coverage
получает `TRANSACTION_NOT_FOUND`. Если одинаковый label соответствует нескольким
distinct `(group path, label, kind)`, coverage получает
`AMBIGUOUS_TRANSACTION`. Оба случая дают всей policy `NO_VERDICT`, даже если
другое rule уже нарушено.

### Ошибки validation

UI и CLI используют один validator. Ошибка содержит stable `code`, JSON Pointer
и message. Текущая версия возвращает первую найденную ошибку.

| Code | Причина |
| --- | --- |
| `MALFORMED_JSON`, `INVALID_UTF8`, `POLICY_READ_ERROR` | Policy нельзя прочитать как допустимый UTF-8 JSON |
| `MISSING_FIELD`, `UNKNOWN_FIELD`, `INVALID_TYPE` | Нарушена strict contract shape |
| `DUPLICATE_OBJECT_KEY` | Object содержит повторный, в том числе escaped-equivalent, key |
| `INVALID_SCHEMA_VERSION` | `schema_version` не равен `policy.v1` |
| `EMPTY_IDENTIFIER` | Пустой `policy_id`, rule id или transaction name |
| `EMPTY_RULES`, `DUPLICATE_RULE_ID` | Нет rules или rule ids не уникальны |
| `UNKNOWN_METRIC`, `UNKNOWN_OPERATOR` | Metric/operator не поддерживается |
| `METRIC_OPERATOR_MISMATCH` | Operator не соответствует metric |
| `THRESHOLD_OUT_OF_RANGE` | Threshold отрицателен или ratio не входит в `0..1` |
| `MIN_SAMPLES_OUT_OF_RANGE` | `sample_floor` или `min_samples` вне `1..1000000` |
| `MIN_SAMPLES_BELOW_FLOOR` | Действующий минимум выборки меньше действующего пола |
| `TOLERANCE_OUT_OF_RANGE` | `max_missing_fraction` вне `0 <= x < 1` или `max_gap_cells` вне `0..100000` |
| `FIELD_NOT_APPLICABLE` | Поле не применимо к правилу: `min_samples` у `throughput_rps`; `max_missing_fraction` и `max_gap_cells` у платформенного правила `effect = diagnostic` |
| `WINDOW_IDS_INVALID` | `window_ids` правила пуст, не массив строк, содержит повтор, пустую строку или id длиннее 128 байт UTF-8 |
| `INVALID_SCOPE` | Scope не равен exact `overall` или `transaction` form; у платформенного правила: неизвестный `kind`, пустой или повторяющийся список сервисов, `all_services` без каталога `platform_services`, `except` вне каталога, область пуста после `except` |
| `INVALID_MINIMUM` | `min_consecutive_cells` платформенного правила вне `1..100000` |
| `UNKNOWN_AGGREGATION`, `UNKNOWN_EFFECT` | Агрегация или effect платформенного правила не поддерживается |
| `PLATFORM_AGGREGATION_OPERATOR_MISMATCH` | Платформенное правило `gt` с порогом `0` и агрегацией `interval_min` |
| `PLATFORM_COVERAGE_MISSING` | Нет правила покрытия для пары «сервис × окно» платформенного `sla`-правила |
| `RESOURCE_LIMIT_EXCEEDED` | Превышен размер, depth, count или lexical numeric limit |

Невалидная policy отклоняется до создания analysis и не превращается в
`NO_POLICY`.

## Baseline: ручной выбор и статистический автовыбор

В панели **Baseline comparison** можно закрепить один сохранённый analysis:

1. Откройте нужный run и saved analysis либо выполните analysis файла.
2. Укажите **Comparison series**: например, scenario и test environment.
3. Нажмите **Set as baseline**. Полные run/analysis IDs появятся в панели.
4. Откройте другой analysis и нажмите **Compare selected analysis**.

Выбор хранится в data directory, переживает reload и перезапуск приложения.
Он не меняется при новых runs или повторном анализе того же input. **Clear
baseline** снимает выбор, не удаляя исходные RunBundles. Один активный baseline
не означает, что все runs в хранилище автоматически сопоставимы.

Для автовыбора раскройте **Statistical selection**. Последовательно открывайте
analyses и добавляйте их через **Add selected candidate**. Нужны 3–20 разных
runs; несколько analyses одного input не считаются несколькими прогонами.
Проверьте состав серии и подтвердите **Same planned test conditions**, затем
нажмите **Select statistically**. Добавление/удаление кандидата снимает
подтверждение, чтобы оно не применялось незаметно к другой серии. Это
подтверждение относится только к однородности набора кандидатов. Тестируемый
прогон в кандидаты не добавляйте: выбирайте кандидатов из истории. Обычно
серия состоит из 2–4 релизов, а минимум для statistical selection равен 3
кандидатам, поэтому на малой серии чаще подходит ручной эталон.

Подтверждаются заданные scenario/mix, environment/dataset, модель и план
нагрузки, pacing и ограничения генератора. Равенство фактического RPS не
требуется: падение throughput может быть частью наблюдаемой деградации.
Программа проверяет техническую семантику метрик, но не восстанавливает
заданный профиль из JTL. Невалидный/неполный кандидат или отсутствующие
метрики отклоняют запрос с причиной; предыдущий baseline сохраняется.

Алгоритм `median-rank-v1` выбирает один реальный прогон, ближайший к центральным
рангам overall P95, throughput и error rate с одинаковыми весами. При равенстве
score выбор определяется IDs, а не порядком добавления. Полный состав серии и
scores сохраняются; раздел **Selection scores** объясняет выбор. Это
эвристика типичного представителя, не доказательство устойчивой нормы или
статистической значимости. Нестабильная либо смешанная серия может дать плохой
эталон. Автоматического включения новых runs и rolling baseline нет.

Таблица сравнения показывает P95/P99 в ms, throughput в requests/second и
error rate в ratio (`0.01 = 1%`). Числа округляются для отображения максимум
до 6 знаков после точки; расчёт дельт выполняется до округления. Нулевой
baseline допускает абсолютную дельту, но относительная будет `N/A
(ZERO_BASELINE)`. Отсутствующие значения не заменяются нулями.
Различие определений метрик даёт `INCOMPATIBLE_METRIC_DEFINITION` для дельт,
оставляя исходные значения видимыми. `UNCONFIRMED` означает, что решение для
этой пары не сохранено или не `CONFIRMED`; `USER_CONFIRMED` выдаётся только
после явного сохранения решения **Confirmed same planned test conditions**
для точной пары baseline/current (и пары окон, если окна заданы). Для
statistical baseline пара строится по выбранному победителю. Членство в серии
кандидатов условия не подтверждает, а решение не является машинной проверкой
сценария. Решение относится к паре analyses, а не к составу серии: смена
кандидатов при том же победителе его не сбрасывает; **Clear baseline**
удаляет все сохранённые решения.

Над таблицей могут появиться предупреждения (`warnings`): сравнение с самим
собой (`BASELINE_IS_CURRENT_ANALYSIS`; `BASELINE_IS_CURRENT_RUN`, когда тот же
прогон проанализирован с другой policy или окнами) и
`CURRENT_IN_CANDIDATE_SET` (сравниваемый прогон входил в набор кандидатов, то
есть эталон выбран с его участием). Они не блокируют сравнение и не меняют
числа, `comparability`, verdict, validity и coverage. Сравнение двух окон одного
прогона допустимо, предупреждение при этом остаётся.

Если в одном из окон нет ни одного сэмпла, все строки окна (нагрузка и ресурсы)
получают статус `INSUFFICIENT_DATA` с причиной `EMPTY_WINDOW`, дельты `N/A`,
значения ресурсов остаются видимыми, а окно получает причины
`BASELINE_WINDOW_EMPTY` и/или `CURRENT_WINDOW_EMPTY`. Интерфейс подсказывает
проверить границы окна и синхронизацию часов генератора и кластера. Настоящий
ноль при непустом окне по-прежнему даёт `ZERO_BASELINE`. Если эталон создан по
старым правилам анализа (`INCOMPATIBLE_METRIC_DEFINITION` или отказ
`BASELINE_MIXED_SEMANTICS`), интерфейс предлагает пересчитать его: заново
проанализировать исходные данные и закрепить baseline; старые анализы остаются
читаемыми.

Новые анализы с планом диагностики записывают для окна без сэмплов
(`window_metric_summary`) задержки `p50`, `p95`, `p99` и `max` как `null`
(«не измерено»), а не как `0`; пропускная способность остаётся числом `0` за
длительность окна, процент ошибок `null`. Настоящая задержка 0 мс при непустом
окне остаётся числом `0`. Анализы, сохранённые раньше, содержат нули и читаются
как прежде; пустое окно определяется по числу сэмплов, поэтому при сравнении
совместимых анализов обе формы дают `EMPTY_WINDOW`. Версия модуля диагностики в
identity выросла с `2` до `3`: старый и новый анализ с планом диагностики
несопоставимы (`INCOMPATIBLE_METRIC_DEFINITION`), эталон, созданный раньше,
нужно закрепить заново.

Дельты не меняют `policy_verdict`, validity или coverage и сами по себе не
доказывают регрессию версии. Сравнение читает сохранённые artifacts, не создаёт
job и не обращается к внешним источникам. Текущие JSON/HTML/AsciiDoc reports
по-прежнему экспортируют исходный analysis, без этой отдельной comparison view.
Transaction comparison, графические overlays и N-run history пока не входят
в реализованную часть baseline. Подробные правила — в
[ADR 0004](../adr/0004-local-baseline-selection.md).

## Аппаратные метрики и совместные SLA

Optional `Resource snapshot` — подготовленный локальным адаптером JSON
`resource-snapshot.v1`, привязанный к SHA-256 загруженного load log.
Приложение не обращается к VM/Grafana. Используйте
[контракт](../contracts/resources/v1/resource-snapshot.schema.json) и
[пример](../contracts/resources/v1/examples/valid/basic.json); замените hash,
timestamps и значения своими данными, а thresholds — согласованными SLA.

Series содержит metric, unit, entity, role `system|generator`, aggregation
`interval_mean|interval_rate|interval_max|interval_min` и значения на общей UTC grid. `null` означает gap,
а не ноль. Raw counters, instant samples и percentile series сначала требуется
преобразовать в поддерживаемую семантику в адаптере. Credentials и URL в snapshot
не передавайте. Limits: файл 32 MiB, 1 024 series, 100 000 points на series,
1 500 000 cells суммарно, 64 непересекающихся окна и 256 resource rules.
Крупный снимок требует больше памяти, см. раздел «Память при большом снимке
ресурсов».
Не более 10 000 интервалов resource threshold violations на analysis;
превышение даёт `RESOURCE_FINDINGS_LIMIT_EXCEEDED` без partial result.
Оконные бизнес-метрики ограничены 10 000 потенциальных histograms:
число окон × (overall + число policy-referenced transaction identities).

Метка плеча. Ключ метки ряда `arm` зарезервирован под идентификатор плеча
(например, `A` и `B` при сравнении двух конфигураций стенда на одной нагрузке).
Либо `arm` есть у каждого ряда снимка с одним и тем же значением (непустой
текст, не более 128 байт UTF-8), либо ни у одного. Смесь, разные значения и
слишком длинное значение дают `INVALID_ARM_LABEL` с JSON-указателем на ряд или
метку; пустое значение или управляющие символы дают `INVALID_TEXT` по
`/series/N/labels/arm`. Файл, где `arm` уже использовался смешанно, теперь
отвергается; других правок формата нет, `resource-snapshot.v1` и схема не
менялись. Значение `arm` записывается в `identity.json` условным полем
`resource_arm` и входит в ключ сопоставимости: анализы разных плеч, а также
анализ с плечом и анализ без плеча не сравниваются с baseline и не попадают в
одну динамику (причина `INCOMPATIBLE_METRIC_DEFINITION`). У снимка без `arm`
поле `resource_arm` отсутствует, `identity.json` и `analysis_id` прежние.

Explicit windows задают интервалы `[from_epoch_ms, to_epoch_ms)` на grid внутри
load run. Без windows берутся полностью включённые ячейки пересечения run и
snapshot; отброшенные края отражаются в evidence. Sample относится к окну по
start timestamp: latency не обрезается на правом краю, RPS делится на полную
длительность окна. Бизнес-правила existing `policy.v1` проверяются на этих же
окнах, включая exact transaction matching.
Transaction identity разрешается по каталогу всего прогона; окно меняет
наблюдения, но не снимает неоднозначность одинаковых labels разных paths/kinds.
Binding evidence показывает границы и отброшенные края. Clock alignment помечен
`not_verified_by_core`: сведения адаптера в raw provenance не являются
независимой проверкой синхронизации часов.

Resource rule задаёт series_id, unit, `gt|lt`, threshold,
`min_consecutive_cells` и effect `sla|diagnostic`. Сравнение означает нарушение;
например, `gt` считает превышения. Null разрывает последовательность. Порог
interval mean не означает превышение в каждый instant. CPU cores, ratio и bytes
не конвертируются автоматически. Без правил нет автоматического saturation.
Платформенные SLA-пороги по сервисам хранятся в политике, см. раздел «Правила
платформы»; вместе с ними снимок не должен содержать правил `effect = sla`.

UI и reports показывают min/max, mean/median, Q05/Q25/Q75/Q95, IQR, unscaled MAD,
sample standard deviation, slope/sec и split-half median shift, а также
observed/expected cells и gaps. Малые/пустые выборки дают null и причины, не
фиктивные нули. Это описательные статистики, не confidence, change point или
доказательство причинности.

Общий verdict и verdict каждого окна учитывают обязательные бизнес- и resource
SLA. Любые недостающие необходимые данные дают `NO_VERDICT`, даже если другое
правило уже нарушено; наблюдаемые нарушения всё равно остаются в evidence.
При полных данных любое нарушение даёт `FAIL`, иначе `PASS`. Без обязательных
правил — `NO_POLICY`. Diagnostic rules не влияют на verdict. Resource gaps
не меняют load validity; invalid/degraded load не получает PASS.

Snapshot и настройки входят в identity; исходные bytes сохраняются в immutable
bundle. Семантически одинаковые данные с другим transport provenance могут
переиспользовать предыдущий analysis и его первоначальный provenance.
Без snapshot поведение прежнего load-only анализа сохраняется. Baseline не
переназначается. Автоматическая сегментация и capacity bounds пока
не вычисляются.

### Ряды ресурсов по API

Сохранённый анализ со снимком отдаёт ряды ресурсов JSON-ответом
(`resource-series.v1`, [схема](../contracts/resources/v1/resource-series.schema.json)),
без скачивания файла снимка. Это два read-only маршрута; `resource-snapshot` и
`analysis-result.v1` не менялись, прежние маршруты работают как раньше.

- Каталог: `GET /api/runs/{runId}/analyses/{analysisId}/resource-series?after=&limit=`.
  Ряды в порядке `id` (как в снимке), страница до 256 рядов (`limit` 1..256, по
  умолчанию 256), курсор `after` исключительный, следующая страница по
  `next_after` (`null` на последней). Для каждого ряда: `id`, `metric`, `unit`,
  `entity`, `role`, `aggregation`, `reducer`, `labels` и `observed_cells`.
  Дополнительно сетка снимка (`grid`) и объявленные окна (`windows`, возможно
  пусто; разрешённые окна, включая `run-intersection`, лежат в evidence результата).
- Значения: `GET .../resource-series/values?series_id=...&from_ms=&to_ms=&step_ms=&limit=`.
  `series_id` повторяется, от 1 до 32 разных идентификаторов, ряды в ответе идут в
  порядке запроса. Идентификатор кодируется как компонент URL (`/`, `%`, `+`,
  пробел и не-ASCII допустимы). Остальные параметры задаются не более одного
  раза; лишние параметры отвергаются.

**Укрупнение шага.** Ячейка укрупнённой сетки покрывает
`[начало + k * step_ms, начало + (k + 1) * step_ms)`; `step_ms` кратен шагу
снимка (по умолчанию равен ему), а `from_ms` и `to_ms` лежат на границах ячеек
(`to_ms` допускает конец сетки; по умолчанию вся сетка). Границы не округляются:
нарушение даёт `400`. Шаг крупнее всей сетки допустим и даёт одну ячейку.
Для ряда `interval_mean` и `interval_rate` значение ячейки это среднее по
наблюдённым исходным ячейкам, для `interval_max` максимум, для `interval_min`
минимум (поле `reducer`).

**Пропуски и `observed`.** Ячейка без наблюдённых исходных значений равна `null`.
Если на одну ячейку приходится больше одной исходной (`source_cells_per_cell > 1`),
ответ содержит массив `observed`: сколько исходных ячеек реально наблюдалось.
Ячейка, где `observed` меньше `source_cells_per_cell`, неполная: среднее или
экстремум посчитаны только по наблюдённым значениям и могут отличаться от
значения по полной ячейке. Последняя ячейка сетки может быть короче
(`last_cell_source_cells`). Такие ячейки следует показывать как неполные, не как
полноценные.

**Страница и коды.** `limit` это число укрупнённых ячеек на ряд, по умолчанию
`min(2 000, 100 000 / число рядов)`. Ответ ограничен 100 000 ячеек
(`число рядов * limit`): превышение даёт `413 RESOURCE_LIMIT_EXCEEDED`, а не
усечённый ответ; `limit` вне 1..100 000 даёт `400`. Следующая страница начинается
с `next_from_ms` (`null`, когда ячейки кончились). Коды: `400` (параметры, границы,
дубликат или более 32 идентификаторов, пустой или слишком длинный идентификатор),
`404` (нет анализа, нет снимка, неизвестный ряд), `413` (размер страницы).
Лимиты страницы и каталога предварительные (ADR 0014, «Уточнения D0»): они
пересматриваются после замера.

**Длина адреса.** Сервер Netty отвергает строку запроса длиннее 4 096 байт
ответом `400`: 32 идентификатора по 128 байт (около 4,5 КБ) в неё не помещаются
(проверено тестом), а 20 таких идентификаторов проходят. Ряды с длинными
идентификаторами нужно запрашивать пакетами по длине адреса и не более чем по 32
идентификатора.

**Числа.** Значения ответа это числа двойной точности (`numeric_encoding:
"ieee754-double"`), они не авторитетны: точные десятичные значения лежат в файле
снимка, а статистики окна в `resource_summary` результата. Ответ привязан к
снимку хэшем `resource_snapshot_sha256` (тот же, что в результате анализа).
Часы ряда и нагрузки ядро не сверяет (`clock_alignment: not_verified_by_core`).

Один разобранный снимок хранится в памяти сервера для повторных запросов;
первый запрос по новому анализу разбирает файл снимка заново, поэтому занимает
заметно больше времени, чем последующие.

## CLI

```text
ltv ui [--data-dir <path>] [--analysis-parallelism <n>] [--histogram-significant-digits <3..5>]
ltv analyze <input> [--policy <policy.json>] [--resources <snapshot.json>] [--histogram-significant-digits <3..5>] [--data-dir <path>]
ltv policy validate <policy.json>
ltv report <run-id> <analysis-id> --format json|html|asciidoc [--data-dir <path>]
```

`ltv analyze` печатает canonical `analysis-result.v1` в stdout.

**Точность перцентилей.** Перцентили p50, p95 и p99 считаются по гистограмме
HdrHistogram и не бывают выше максимума отклика. Значения до 2047 мс точны. Выше
гистограмма округляет вверх внутри диапазона: при трёх значащих цифрах
относительная погрешность меньше 0,1 % (60000 мс может дать 60031 мс, если
максимум прогона больше). Опубликованное значение никогда не ниже точного
перцентиля, поэтому порог `lte` не даёт ложный `PASS`, но у самого порога ложный
`FAIL` из-за округления возможен. Графики и ответ `/buckets` применяют то же
ограничение максимумом и к ранее сохранённым analyses: их неизменяемый результат
не переписывается, а p95 графика (по интервалу) может стать ниже необрезанного
значения HDR той же гистограммы менее чем на 0,1 %.

Параметр `--histogram-significant-digits <n>` (целое `3..5`, по умолчанию `3`)
задаёт число значащих цифр гистограммы для всех analyses этого запуска; он есть
у `ltv ui` и `ltv analyze`, но не входит в запрос API и файл policy. Другое
значение, повтор параметра или нечисловое значение завершает запуск usage error
(`64`). Больше цифр даёт меньшую погрешность, но занимает больше памяти: на
модели при выборке 101 000 сэмплов в одной гистограмме 4 и 5 цифр занимают
около 1,9 и 2,1 раза больше памяти, чем 3, а сжатая запись растёт примерно на
37 %. Перед включением значения выше 3 проверьте расход памяти и времени на
вашем стенде. Точность входит в identity: смена значения создаёт новый analysis,
а analyses с разной точностью нельзя сравнивать с эталоном (нужно закрепить
эталон заново).

`ltv report` читает уже сохранённый analysis, проверяет его manifest и выводит
JSON, UTF-8 HTML либо UTF-8 AsciiDoc в stdout. `--format` обязателен. Для сохранения файла
перенаправьте stdout, сохранив исходную кодировку/bytes. На Windows используйте
PowerShell 7.4+ либо redirection в `cmd`; Windows PowerShell 5.1 перекодирует
native stdout ([поведение redirection](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_redirection)).
Перед запуском CLI остановите UI, использующий тот же data
directory; скачивание из работающего UI доступно без остановки.

Успешный export возвращает `0` даже для `FAIL` или `NO_VERDICT`: exit описывает
экспорт, исходный verdict остаётся в отчёте. Отсутствующий run/analysis даёт
`4`; usage error — `64`; повреждение сохранённых данных — `70` без partial
report в stdout.

| Exit | Значение |
| ---: | --- |
| `0` | `PASS`, `NO_POLICY`, valid policy или успешный export (в том числе `PASS` с пометкой `SMALL_SAMPLE`: метку читайте из JSON) |
| `2` | `FAIL` |
| `3` | `NO_VERDICT` или `DEGRADED` |
| `4` | Invalid/unsupported input, неверный resource snapshot/binding или отсутствующий analysis для export |
| `5` | Invalid policy |
| `6` | `DATA_DIR_BUSY` |
| `64` | Usage error |
| `70` | Unexpected internal failure |

## Описательная диагностика одного прогона

Optional `correlation-plan.v1` включает только явно перечисленные пары и правила
аномалий. В UI выберите файл плана вместе с resource snapshot. CLI:

```powershell
.\build\install\ltv\bin\ltv.bat analyze input.jtl --resources resources.json --correlation correlation.json --data-dir data
```

План ссылается на **semantic** SHA-256 snapshot, не hash исходного JSON файла.
Его можно взять из `resource_snapshot_sha256` сохранённого `identity.json`
предварительного анализа с тем же snapshot без плана; файл лежит в
`data/runs/<run-id>/analyses/<analysis-id>/identity.json`. Адаптер может
подготовить план по [контракту](../superpowers/plans/2026-09-05-load-resource-correlation.md).
Исходный `correlation-plan.json` сохраняется рядом и защищён manifest.

Правило аномалии выбирает signal, непересекающиеся reference/evaluation windows,
направление, минимальное абсолютное изменение и длительность. Modified-Z
использует reference median/MAD; при MAD=0 остаётся только абсолютный порог.
Reference — явно выбранный режим, не автоматически доказанная норма. Пропуски
разрывают эпизоды; короткие превышения учитываются в suppressed count.
Нарушения SLA отображаются независимо от фильтра аномалий.

Корреляция показывает исходный Spearman и conditional rank association при
выбранных controls; при недостатке наблюдений коэффициент отсутствует. Лаг
положителен, если resource наблюдается раньше load outcome; неизвестные часы
запрещают трактовать это как технический порядок событий. Achieved RPS может
сам падать из-за деградации: он не выбирается автоматическим контролем.
Не усредняются cell percentiles; диагностический P95 требует минимум20 requests
в ячейке (технический порог, не confidence level).
Окно без сэмплов в evidence `window_metric_summary` показывает задержки `null`,
а не нули (см. раздел про сравнение с эталоном).

`CANDIDATE` — наблюдаемая ассоциация/эпизод, не доказанная причина.
`DESCRIPTIVE`, `INSUFFICIENT_DATA` и `NO_MATERIAL_CHANGE` различаются.
Uncertainty сырых коэффициентов всегда `NOT_ESTIMATED`; `HIGH confidence`
отсутствует. Отдельный слой выбора главной находки p-values публикует:
evidence `correlation_headline_selection` несёт `p_value_b10`, `p_value_b20`,
`max_p_value`, `holm_adjusted_p_value` и `selected` для каждой гипотезы
объявленного семейства.

Находка `correlation_candidate` публикуется только при `selected = true`, то
есть когда Holm-скорректированное p не выше 0.05 и порог материальности пройден.
Метод `mbb-lag-max-holm.v1`: moving-block bootstrap (999 реплик, блоки 10 и 20),
статистика `max |rho|` по всему объявленному поиску лагов, консервативный
max-p по двум длинам блока и одна поправка Holm на объявленное семейство.
Неотклонённая гипотеза означает `HOLM_NOT_REJECTED`, а не отсутствие связи.

Слой работает только для одного окна, одной outcome-метрики, не более 16 гипотез,
30–240 непрерывных ячеек и без фактически использованных controls. За пределами
этой полосы всё семейство получает `UNAVAILABLE` с точной причиной
(`MULTI_WINDOW_FAMILY_UNSUPPORTED`, `FAMILY_OUTCOME_MISMATCH`,
`FAMILY_SIZE_UNSUPPORTED`, `FAMILY_GRID_MISMATCH`,
`OBSERVATION_COUNT_UNSUPPORTED`, `LAG_ANCHOR_COUNT_UNSUPPORTED`,
`GENUINE_PARTIAL_UNCALIBRATED`, `COMPUTATION_LIMIT_EXCEEDED`), и находки не
публикуются вовсе, хотя сырые коэффициенты и статусы остаются в evidence.
Принятая остаточная частота шумных
отчётов 7.7–13.2% измерена на development-seeds в NumPy и не является измеренной
гарантией JVM-реализации.

Новая оболочка (`?shell=new`) показывает корреляции честно и до приёмки метода
(ADR 0022, Д10). В «Обзоре» и на вкладке «Таблицы», в блоке «Гипотезы для
проверки», видны только отобранные пары (`selected = true`), всегда с пометкой
«ассоциация, не причина; не откалибровано». Ряд, исход, лаг и коэффициент берутся
из `correlation_pair` той же пары и окна: это коэффициент и лаг с наибольшим
модулем, которые и проверял отбор. Лаг показан в секундах со знаком из evidence
(положительный: ряд ресурса наблюдается раньше исхода, часы источников не
сверялись). Скорректированная вероятность и число гипотез семьи взяты из
evidence отбора; меньше 0,0001 показано как «< 0,0001». Семьи, которые не удалось
проверить (`UNAVAILABLE`), перечислены отдельной строкой словами, например «нагрузка
менялась внутри стадии» для `GENUINE_PARTIAL_UNCALIBRATED`, и в находки не входят;
неизвестный код причины выводится как есть. Если ни одна пара не отобрана, блок
так и пишет, и это не означает отсутствия связей. Контрастов (под против соседей,
плечо A и B) нет. Старый интерфейс таблицу пар и все её статусы показывает
по-прежнему на английском; сырое evidence остаётся доступным в раскрывающемся
блоке «Raw diagnostic evidence» в обеих оболочках. Метод не откалиброван на
реальных данных стенда: до приёмки C5 демонстрационные входы должны быть
помечены «синтетические данные».

Все declared pairs и причины непроверяемости остаются в evidence. Optional
diagnostic limit не меняет бизнес-/ресурсный SLA verdict. Без плана старый
результат не меняется, и baseline не переназначается.

## Рост метрики в пределах SLA

Optional `trend-plan.v1` отвечает на вопрос «растёт ли метрика, даже если порог
не пересечён». В UI выберите файл плана вместе с resource snapshot. CLI:

```powershell
.\build\install\ltv\bin\ltv.bat analyze input.jtl --resources resources.json --trend trend.json --data-dir data
```

План ссылается на тот же **semantic** SHA-256 snapshot, что и correlation plan,
и объявляет не более 32 проверок. Каждая проверка задаёт series, окно,
направление (`increase`, `decrease`, `either`), минимум наблюдаемых ячеек
(30 и больше) и `magnitude_gate` из двух положительных величин: минимального
абсолютного наклона в единицах series в секунду и минимального абсолютного
сдвига медиан половин окна в процентах от медианы окна. Обе величины объявляются
**до** прогона.

Тренд наблюдается только если прошли оба порога и обе статистики согласованы по
знаку; при `either` требуемый знак берётся из наклона. Используются те же
`slope_per_second` и `split_half_shift`, что публикует `resource_summary`.
Пропуски не заполняются и не сжимают время: проверка видит
`expected_cells`, `observed_cells`, `missing_cells`, `longest_gap_cells` и
reason `RESOURCE_GAPS`.

Кроме общего минимума, в каждой половине окна должно быть не меньше
`floor(min_cells / 2)` наблюдаемых ячеек (при `min_cells` 30 это 15 в каждой
половине). Иначе сдвиг половин сравнивал бы медиану многих точек с единичной, и
проверка отказывает с `INSUFFICIENT_CELLS` и reason `TREND_HALF_CELLS_NOT_MET`.

Статусы: `TREND_OBSERVED`, `NO_MATERIAL_TREND`, `INSUFFICIENT_CELLS`,
`UNAVAILABLE`. Каждый отказ несёт точный reason — `NO_OBSERVATIONS`,
`TREND_MIN_CELLS_NOT_MET`, `TREND_HALF_CELLS_NOT_MET`,
`INSUFFICIENT_OBSERVATIONS`, `TREND_MEDIAN_ZERO`
(процентный порог не определён при нулевой медиане), `TREND_DIRECTION_MISMATCH`,
`TREND_DIRECTION_DISAGREEMENT`, `TREND_SLOPE_BELOW_MINIMUM`,
`TREND_SHIFT_BELOW_MINIMUM`, `TREND_SERIES_NOT_FOUND` (ряд не найден),
`TREND_WINDOW_NOT_FOUND` (окно не найдено), `RUN_NOT_VALID` (прогон недействителен).
Каждый `TREND_OBSERVED` дополнительно несёт
`STATIONARITY_NOT_EVALUATED`: объявленное окно не доказывает стационарность,
детектора смены режима нет, поэтому ступень нагрузки может выглядеть как рост.

**Ограничение: ряды со сбросами.** L0 не применим к рядам с перезапусками
(память с рестартами подов, циклы OOM, пила GC). На синтетической пиле без
роста огибающей (3 цикла по 40 ячеек, значение от 200 до 980 в каждом) окно от
границы цикла даёт `TREND_OBSERVED` с направлением `increase` и сдвигом половин
+200 (33,9 % медианы 590), а то же окно, сдвинутое на 20 ячеек, даёт
`TREND_OBSERVED` с направлением `decrease` и сдвигом -200: знак определяет фаза
окна, а не поведение метрики. Выбирайте окно внутри одного цикла или не
объявляйте проверку на таком ряду.

`resource_trend` — finding с `effect=diagnostic`: он не меняет бизнес- или
ресурсный verdict и не попадает в `analysis_coverage`. Это наблюдение, а не
диагноз: рост памяти или пула не является доказательством утечки, причины или
исчерпания ресурса. Отсутствие находки не доказывает отсутствие роста.
Uncertainty остаётся `NOT_ESTIMATED`; p-values в этом уровне нет.

Сохраняются `trend-plan.json` (исходные загруженные байты) и `trend.json`
(`trend.v1`); оба доступны для скачивания рядом с capacity-артефактами. Без
плана результат, identity и verdict не меняются.

## Сравнение двух окон

В панели baseline comparison явно задайте id окна baseline и current. Для
сохранённых analyses с correlation plan доступны window summaries и точные
resource bindings. Старые analyses без этих summaries дают `NOT_EVALUATED`,
но их прежние overall deltas остаются доступными.

Пороги материальности задаются **до** сравнения: процент изменения для обычных
метрик (default5%) и абсолютная разность error-rate ratio (default0.001, то
есть0.1 процентного пункта). При нулевом baseline относительная дельта
неопределена; абсолютная сохраняется, это не `NO_MATERIAL_CHANGE`.

Сравниваются load P50/P95/P99, error rate и achieved RPS, resource median/Q95
при точном совпадении series binding. Число samples и длительность окон видны.
Одинаковые имена окон или достигнутый RPS не доказывают одинаковых заданных
условий. Разные ступени не объединяются в средний percentile; результат
относится к этим двум измерениям, а не к популяции запусков версии продукта.

## Локальная security boundary

UI работает только на `127.0.0.1`, использует in-memory CSRF token и strict
same-origin session. Runtime не выполняет outbound requests. Не публикуйте
loopback port через proxy и не считайте private API server authentication.
Детали хранения и limits описаны в
[архитектуре runtime](../architecture/slice-1-local-runtime.md).
