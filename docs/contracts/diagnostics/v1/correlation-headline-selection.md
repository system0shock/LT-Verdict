# Correlation headline selection contract v1

`correlation-plan.v1` не получает новых input fields. При наличии pairs
`analysis-result.v1.evidence` дополнительно содержит по одному объекту на
pair/window. Семья (family) равна паре «стадия, исход»: все гипотезы с одним
`window_id` и одним `load_metric` (стадия это именованное окно
`snapshot.windows`). План делится на семьи по паре `(window_id, load_metric)`,
каждая семья отбирается отдельным вызовом селектора (ADR 0022, Д2):

```json
{
  "id": "...",
  "type": "correlation_headline_selection",
  "pair_id": "cpu-latency",
  "window_id": "steady",
  "method": "mbb-lag-max-holm.v2",
  "rng": "java-random-sha256-seed.v1",
  "status": "SELECTED",
  "family_hypotheses": 1,
  "family_count": 1,
  "representation": "first_difference",
  "source_cells": 120,
  "analysed_points": 119,
  "bootstrap_replicates": 999,
  "block_lengths_cells": [10, 20],
  "alpha": "0.05",
  "p_value_b10": "0.001",
  "p_value_b20": "0.012",
  "max_p_value": "0.012",
  "holm_adjusted_p_value": "0.012",
  "selected": true,
  "reasons": []
}
```

`family_hypotheses` это размер семьи `m` (объявленные гипотезы, включая
недоступные), `family_count` это число семей `F` отчёта: число различных пар
`(window_id, load_metric)` в парах плана. `F` определяется планом, а не данными:
короткая, пустая или недоступная семья не меняет долю остальных. Каждая семья
проверяется на уровне `alpha / F` (граница объединения, ADR 0022, Д3), поэтому
`alpha` публикует фактический уровень семьи (`0.05 / F`, canonical decimal до 12
знаков, например `"0.016666666667"` при `F = 3`); при `F = 1` это прежнее `"0.05"`,
и результат совпадает с прежним побитно.

## Представление: первые разности (метод v2, ADR 0022, Д4)

Метод `mbb-lag-max-holm.v2` отбирает ассоциации по **первым разностям** рядов
ресурса и исхода. Метод версии `mbb-lag-max-holm.v1` работал по уровням;
строка метода входит в seed генератора случайных чисел, поэтому p-значения v2 не
сопоставимы с p-значениями v1 на тех же данных. Поля плана не меняются:
представление задано версией метода и одинаково для всех гипотез; выбирать его по
данным нельзя.

- Разности берутся внутри самой длинной непрерывной серии полных ячеек стадии
  (пропуск ряда ресурса, ячейка без исхода или без значения контроля обрывают серию;
  разность через разрыв не берётся, пропуск не заполняется). Серия из `N`
  ячеек даёт `N - 1` разностей; разность получает метку времени позднейшей ячейки.
- `source_cells` равно `N` (ячеек серии до разности), `analysed_points` равно
  `N - 1` (длина разностной серии, которую видит отбор). Пределы `OBSERVATION_COUNT_UNSUPPORTED`
  (30-1 920), число якорей `analysed_points - 2L >= 30` и потолок вычисления относятся к
  разностной серии: допустимо от 31 до 1 921 исходной ячейки при `L = 0`. Серия
  короче этого даёт `PAIR_NOT_EVALUABLE` (коэффициента нет, гипотеза остаётся в
  размере семьи как `p = 1`).
- Ранги, `raw_rho`, `partial_rho`, профиль лагов (`lag_profile`, `best_lag_ms`,
  `best_lag_rho`, `lag_used_cells`) в `correlation_pair`, порог `min_abs_effect`,
  знак (`expected_sign`: рост ресурса ведёт к росту исхода) и вход селектора считаются
  по одной разностной серии. `paired_cells` по-прежнему число полных ячеек
  стадии по уровням.
- `min_resource_delta` и `min_load_delta` остаются проверками размаха **уровней**
  стадии (все полные ячейки, до разности): они защищают от шума единиц, а не от формы
  связи. Статус `BELOW_EFFECT` берётся по любому из двух условий: размах ниже порога
  или `|rho|` разностей ниже `min_abs_effect`.
- Контролы (`controls`) остаются на уровнях: к каждой разности относится значение
  контроля в позднейшей ячейке. Контроль, постоянный в стадии, по-прежнему
  отбрасывается как `CONSTANT_CONTROL`; меняющийся (даже линейно) оставляет пару
  `GENUINE_PARTIAL_UNCALIBRATED`.
- Постоянный ряд или счётчик с постоянным шагом даёт после разности константу:
  `NO_RANK_VARIATION`, `PAIR_NOT_EVALUABLE`; гипотеза остаётся в размере семьи.
- Цена: связь через **уровень** (порог, насыщение) разности теряют или размывают;
  метод v2 для таких связей не обещается (ADR 0022, Д8).

Состояние калибровки: для метода v2 есть только development-замер H3 (Python-порт,
раскрытые seeds): на независимых AR(1) доля отчётов с лишней находкой 3,2-3,3 %
при пороге 7 %, на сильном дрейфе 3,5 % против 100 % у уровней, мощность на
линейных связях 99,5-100 %. Приёмка C5 на JVM не проведена; диапазон 7,7-13,2 %
ниже относится к методу v1 на уровнях. Находки метода v2 показываются как
«ассоциация, не причина; не откалибровано».

Decimal fields являются canonical decimal strings либо `null`. `SELECTED`
означает Holm-adjusted p `<=alpha` (уровень семьи) и прежний raw
`status=CANDIDATE`.
`NOT_SELECTED` использует `HOLM_NOT_REJECTED` или `MATERIALITY_NOT_MET`.
`UNAVAILABLE` всегда имеет `selected=false` и public p-fields `null`.

Причины `UNAVAILABLE`:

- `GENUINE_PARTIAL_UNCALIBRATED` — хотя бы один control реально использован;
- `PAIR_NOT_EVALUABLE` — observed lag-max statistic отсутствует;
- `FAMILY_SIZE_UNSUPPORTED` — family содержит больше 16 hypotheses; пустой вход
  возвращает пустой список selections раньше этой проверки, поэтому для пустой
  семьи причина не выдаётся и ни одного selection evidence не публикуется;
- `MULTI_WINDOW_FAMILY_UNSUPPORTED` — hypotheses относятся к разным windows
  (защитная проверка: ядро делит план на семьи само, поэтому в выдаче не
  встречается);
- `FAMILY_GRID_MISMATCH` — timestamps/step/complete-case masks различаются;
- `FAMILY_OUTCOME_MISMATCH` — outcome metric или values различаются (защитная
  проверка, как выше);
- `HOLM_RESOLUTION_INSUFFICIENT` — минимальный bootstrap p `1 / (B + 1) = 0.001`
  не может отклонить гипотезу на первом шаге Holm: `alpha / (F * m) < 0.001`, то
  есть `F * m > 50` при `B = 999` (при `m = 16` это четыре семьи и больше).
  Семья получает `UNAVAILABLE`, а не молча теряет мощность; рекомендуемый
  предел плана `F <= 3`;
- `OBSERVATION_COUNT_UNSUPPORTED` — меньше 30 или больше 1 920 точек разностной
  серии, то есть больше 1 921 исходной ячейки (предел поднят с 240 решением
  ADR 0022, Д9: 1 920 ячеек это 8 часов при шаге 15 с; стадии длиннее по-прежнему
  не принимаются; в выдаче причина встречается у длинных серий, а короткая даёт
  `PAIR_NOT_EVALUABLE`);
- `LAG_ANCHOR_COUNT_UNSUPPORTED` — lag вне `0..10` или anchors меньше 30;
- `BOOTSTRAP_REPLICATE_NOT_EVALUABLE` — surrogate rank correlation вырождена;
- `COMPUTATION_LIMIT_EXCEEDED` — frozen calculation одной семьи превышает
  550 105 344 correlation cell-products (`2 * 999 * сумма по гипотезам
  (2L + 1) * (N - 2L)`, `N` длина разностной серии; это стоимость целевой формы
  Д9: 16 гипотез, лаг 4 ячейки, 1 920 точек; раньше потолок был 150 млн). Форма
  16 гипотез, лаг 10, 1 920 точек (1 275 523 200) по-прежнему недоступна.

Время отчёта на длинных стадиях растёт вместе с потолком (стоимость линейна по
числу произведений). Блоки 10 и 20 на рядах в восемь раз длиннее не измерялись:
длинные стадии калибрует только сценарий `N12-ar08-1920-l4` приёмки C5, которая
ещё не проведена. Потолок действует на одну семью; отчёт из нескольких
длинных семей считает их по очереди, каждую под своим потолком.

Все declared hypotheses семьи участвуют в одном Holm этой семьи. Для unavailable hypothesis
внутреннее correction value равно `1`, даже если его public p остаётся `null`.
Family не сокращается до кандидатов.

Существующий `correlation_pair` evidence сохраняет набор полей; его
коэффициенты и профиль лагов при методе v2 считаются по первым разностям (см.
выше). Существующий
`correlation_candidate` finding сохраняет форму, но появляется только при
`selected=true`. Selector не меняет `policy_verdict`, не доказывает causality и
не даёт universal false-positive guarantee.

JVM использует deterministic `java.util.Random`, seeded через SHA-256. Streams
не bit-identical NumPy PCG64 из disclosed development-repeat, поэтому принятый
там для метода v1 диапазон шумных reports `7.7-13.2%` не является измеренной
гарантией этого port или реальных данных, а development-числа метода v2 (раздел
о представлении) не заменяют приёмку C5 на JVM.
