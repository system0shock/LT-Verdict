# LT Verdict — план разработки (по PRC v0.5)

> **Superseded:** нормативный baseline и текущий план находятся в
> `lt-verdict-prc-prd-v0.6.md` и `docs/development-plan-v0.6.md`.
>
> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** довести LT Verdict от концепции (PRC v0.5) до готового к пилоту дистрибутива: контракты → ingest-ядро → коллекторы → вердикт → протокол/GUI + ИИ-слой → RCA с ИИ → дистрибутив. Разработка ведётся вне боевой среды.

**Architecture:** модульный монолит Kotlin 2 + Spring Boot 3; PostgreSQL 15+ (метаданные, журналы, очереди SKIP LOCKED); content-addressed каталог артефактов на отдельном томе; дистрибутив Helm + docker-compose. Детали — PRC v0.5 §2–3.

**Tech Stack:** Kotlin 2.x, Spring Boot 3.x, Spring Data JDBC + NamedParameterJdbcTemplate, Flyway, HdrHistogram, Netty, elasticsearch-java, AsciidoctorJ, JFreeChart/XChart, React + Vite, Testcontainers.

## Global Constraints

- Инварианты (PRC v0.5 §1): факты → детерминированный вердикт → интерпретация; побайтовая воспроизводимость вердикта из тех же входов и той же версии правил; fail-closed (неполные данные → `NO_VERDICT`); конфигурация-как-код, UI не источник истины; append-only журнал решений и журнал доставки (UPDATE/DELETE запрещены ролью БД); сырые артефакты неизменяемы с SHA-256 в течение retention, удаления в журнал; данные не покидают контур команды.
- Вердикт считается только по steady-фазе; версия фазовой разметки входит в хэши входов журнала решений.
- Парсинг — в ядре с семафором параллелизма (не OpenShift Job): одинаковое поведение в Helm и compose.
- Все внешние источники read-only; write-исключения только два — Confluence (выделенный space) и Git (ветки/MR, merge человеком).
- **Разработка вне боевой среды:** доступы к VM/ELK/Git API/Confluence не требуются и не запрашиваются; интеграции строятся на фикстурах, мок-серверах и локальных аналогах (локальный git как репозиторий правил, локальные прогоны Gatling OSS как источник эталонных артефактов). Оформление доступов и боевая сверка — отдельный трек на развёртывании/пилоте, вне этого плана.
- **Gatling — строго OSS**, диапазон поддержки 3.9–3.15.1: текстовый формат (3.9–3.12) и бинарный (3.13–3.15.1). Gatling Enterprise вне скоупа.
- **ИИ-треки в скоупе MVP** (RCA с ИИ, ассистент настройки, ИИ-анализ протоколов — PRC v0.5 §2.9): строго слой интерпретации, после вердикта, асинхронно; ИИ-вывод помечен «AI-generated, требует подтверждения» и журналируется с версией модели; в verdict.json ИИ-вывод не попадает (кроме `findings` от детерминированных детекторов); ИИ-CLI — headless, sandbox, без внешнего egress (опросник п.12–14); RCA — только статика (без сборки/исполнения чужого кода).
- Сроки — ориентир (разработка с активным использованием AI); планируем от критериев выхода этапов, не от дат. Скоуп MVP заморожен на PRC v0.5; новые идеи — в бэклог post-MVP.
- Каждый этап начинается с детальной спецификации (этап 1: `docs/stage-1-spec.md`) и заканчивается fail-closed gate; gate не пройден — этап не закрыт.

### Task 4: Verdict engine

- [ ] **Step 1:** Написать спецификацию этапа 4 (KS на бакетированных ECDF: точная статистика, малые N, политика множественных сравнений — ограничение набора метрик или поправка).
- [ ] **Step 2:** Загрузка правил из git по commit-hash — против локального репозитория правил (Трек A3); валидаторы общие с CI-пакетом репозитория; fallback — внутренний append-only реестр версий с двухступенчатым подтверждением (равноправный путь при отсутствии Git API на развёртывании).
- [ ] **Step 3:** Validity gates: полнота источников, длительность steady, дыры в метриках, насыщенность генераторов, пересечение прогонов на стенде, profile conformance, clock sync. Любой сбой → NO_VERDICT с диагностикой.
- [ ] **Step 4:** Verdict engine: пороги SLA + дельты к baseline (назначение вручную по comparability key) + KS; каноническая сериализация verdict.json (сортировка ключей, фиксированные форматы чисел, без wall-clock/UUID; поле findings заполняется детекторами Step 5).
- [ ] **Step 5:** Детерминированные findings-детекторы: change-point на окне, GC↔p99, насыщение пулов соединений↔latency, error fingerprinting; запись в `findings`; детерминизм (те же входы → те же findings) покрыт тестами.
- [ ] **Step 6:** Журнал решений: роль БД без UPDATE/DELETE; хэши входов включают версию правил и версию фазовой разметки; re-verdict создаёт новую запись со ссылкой на предыдущую.
- [ ] **Step 7:** Тесты воспроизводимости: байт-в-байт из тех же входов (включая findings); отключение любого источника → NO_VERDICT; regression pack (N эталонных прогонов, вердикты совпадают после пересборки).

**Gate:** вердикт воспроизводится байт-в-байт (включая findings); отключение любого источника → NO_VERDICT; re-verdict даёт новую запись журнала.
