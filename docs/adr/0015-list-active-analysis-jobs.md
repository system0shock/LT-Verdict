# ADR 0015: Перечисление активных задач анализа

Статус: Proposed, 2026-09-29. Дополняет
[ADR 0002](0002-slice-1-runtime-filesystem-security.md) (private loopback HTTP
contract). Источник: дефект UI-JOB-RELOAD-01 приёмки 2026-09-28 (S2). Вариант
решения выбран владельцем 2026-09-29; статус меняется на Accepted после
согласования итогового текста.

## Контекст

Задача анализа существует только в памяти процесса (`AnalysisJobs`); её id
выдаётся в ответе `POST /api/jobs`. После перезагрузки страницы UI не знает id,
не может показать прогресс и не может отменить задачу, хотя
`GET /api/jobs/{jobId}` ещё возвращает `PROCESSING`. Существующего API для
получения id нет: `AnalysisJobs` даёт только `status(id)` и `cancel(id)`.

Хранить id на клиенте нельзя. `localStorage` и `sessionStorage` запрещены тремя
независимыми проверками: правилом ESLint, e2e-проверкой пустого хранилища
(`security-a11y.spec.ts`) и текстом архитектуры (`slice-1-local-runtime.md`).

## Решение

Добавить read-only маршрут `GET /api/jobs?state=active`.

Ответ `200 application/json`:

```json
{ "jobs": [ { "job_id": "...", "state": "PROCESSING", "processed_bytes": 10,
              "total_bytes": 100, "run_id": "...", "analysis_id": null,
              "diagnostic": null } ] }
```

Элемент имеет прежнюю форму `JobStatus` (тот же сериализатор, что у
`GET /api/jobs/{jobId}`); поля и их смысл не меняются.

Состав и порядок. В список входят только задачи в состояниях `QUEUED` и
`PROCESSING`, в порядке принятия (старшая первой). Завершённые (`COMPLETE`,
`FAILED`, `CANCELLED`) не включаются; их по-прежнему можно получить по id через
`GET /api/jobs/{jobId}` (хранятся последние 1 024).

Поведение по числу активных задач:

- 0: `200 {"jobs":[]}`; UI не показывает панель и не выводит ошибку;
- 1: массив из одного элемента;
- 2 и больше (при `parallelism` по умолчанию, равном 1: одна выполняется,
  вторая в очереди; в общем случае не больше `2 * parallelism`): все
  элементы, старшая первой. UI показывает панель только
  первой (старшей) задачи: `job`, `cancel`, `pollJob` и `working` в `App.vue`
  одиночные, и вывод нескольких панелей потребовал бы переделки состояния
  страницы. Остальные задачи остаются активными и видны после завершения или
  отмены первой и нового обновления страницы; это документированное
  ограничение, а не потеря задач.

Ошибки. Единственный допустимый запрос: ровно один параметр `state` со
значением `active`. Отсутствие параметра, другое значение, повтор параметра и
любой другой параметр дают `400 MALFORMED_REQUEST` (та же строгая проверка, что
у остальных списков). Постраничности и `limit` нет.

Безопасность и локальность. Маршрут доступен только через loopback-listener и
защищён так же, как `GET /api/jobs/{jobId}`: проверкой заголовка `Host`
(`127.0.0.1:<port>`); cookie, CSRF и Origin требуются лишь для мутаций и здесь
не нужны. Новых классов данных он не раскрывает: `run_id`, размеры и имена уже
отдаёт `GET /api/runs`, а состояние задач по id уже отдаёт
`GET /api/jobs/{jobId}`. Отмена по-прежнему только через
`DELETE /api/jobs/{jobId}` с cookie, CSRF и Origin. Маршрут не создаёт и не
отменяет задачи, не читает диск и не обращается к внешним источникам.

Лимиты. Размер ответа ограничен числом активных задач,
`2 * parallelism` (исполнитель плюс очередь ёмкости `parallelism`,
`parallelism` не больше числа процессоров). Снимок строится из памяти под
существующей блокировкой `AnalysisJobs`; снимок согласован:
задача, завершившаяся до чтения, в снимок не попадает, а задача, завершившаяся
после, корректно опрашивается по id (`COMPLETE`).

Клиент. UI при загрузке запрашивает список последним шагом инициализации, берёт
первую задачу, находит её run в списке прогонов (подгружая следующие страницы) и
передаёт управление существующему опросу `GET /api/jobs/{jobId}`. Ошибка списка
показывается как обычная ошибка и не блокирует список прогонов и источники.

## Следствия

- Контракты `JobStatus`, `POST /api/jobs`, `GET` и `DELETE /api/jobs/{jobId}`,
  `analysis-result.v1` не меняются; добавляется один маршрут.
- Браузерное хранилище по-прежнему не используется.
- Задачи по-прежнему живут только в памяти и не переживают перезапуск
  приложения; маршрут после перезапуска вернёт пустой список.
- Маршрут находит задачу, запущенную в другой вкладке или окне той же
  локальной сессии.
- Новых зависимостей нет.

## Отклонённые альтернативы

- Id задачи в `localStorage`/`sessionStorage`: запрещено принятой архитектурой
  (правило ESLint, e2e-проверка пустого хранилища, документ архитектуры);
  кроме того, сохранённый id устаревает после перезапуска приложения и не
  видит задач из других вкладок.
- Id задачи во фрагменте URL (`history.replaceState`): не меняет контракт, но
  переживает перезагрузку только в той же вкладке, не находит задачу из другой
  вкладки или окна и требует синхронизации URL в пяти местах интерфейса
  (`analyze`, `selectRun`, `selectAnalysis`, `cancel`, `pollJob`); ослабляет и
  принятое правило «UI не хранит состояние».
- Признак активной задачи в `GET /api/runs`: смешивает список сохранённых
  прогонов с состоянием памяти процесса и меняет форму существующего контракта.
- `GET /api/jobs` без фильтра или с `state=all`: раскрыл бы до 1 024
  терминальных статусов без пользы для UI и потребовал бы постраничности.
- Push (SSE или WebSocket): новый транспорт и состояние соединения ради одного
  запроса при загрузке страницы.
- Показ нескольких панелей активных задач сразу: требует многозадачного
  состояния в `App.vue` и `JobStatus.vue`; вне объёма исправления S2.
