# Чеклист живой приёмки `v0.3.0` на внешнем стенде

Этот документ фиксирует внешние стендовые и хостовые проверки релиза `v0.3.0`,
недоступные в локальной офлайн-среде сборки. Общий порядок приёмки и политика
оформления результатов описаны в [чек-листе приёмки MVP](mvp-acceptance-checklist.md).

## 1. Внешние CLI-агенты (`ltv mcp`) и Linux direct-runner ИИ

- [ ] Запустить `ltv mcp --url http://127.0.0.1:<port>` (или `ltv mcp --data-dir <path> --connections <profiles.json>`) с внешним CLI-агентом (`Claude Code`, `Qwen Code` или `GigaCode`) по инструкции [`skills/lt-verdict-mcp-analysis/SKILL.md`](../skills/lt-verdict-mcp-analysis/SKILL.md).
- [ ] Пройти сквозной MCP-сценарий: `probe_source` -> `validate_policy` -> `analyze` -> `list_incidents` -> `list_transactions` / `get_resource_series` / `compare` -> `save_advice` с `provenance_kind: "self-reported"`, убедившись в отсутствии утечки секретов и сырых URL-credentials.
- [ ] (Опционально, при снятии заморозки или проверке прямого раннера) Проверить `ModelStudioAdvisoryRunner` на Linux в режиме `LT_VERDICT_AI_RUNNER_MODE=local` с живым `GigaCode` согласно [руководству Advisory AI](user/advisory-ai.md).

## 2. Совместимость PromQL-профилей на живых OpenShift, JVM и генераторах

Проверить допущения из [руководства по пакетам метрик](user/platform-metric-packs.md):

- [ ] `kube-state-metrics` v2: присутствуют `kube_pod_container_resource_limits{resource="cpu"|"memory"}` и `kube_pod_container_info` (включая регулярные и sidecar-контейнеры `istio-proxy`, `oauth-proxy`, без init-контейнеров).
- [ ] Правило записи `namespace_workload_pod:kube_pod_owner:relabel` с меткой `workload` и `container_oom_events_total` присутствуют и корректно обрабатываются при пересоздании подов.
- [ ] Метрики JVM (Micrometer `jvm_memory_used_bytes`, `jvm_gc_pause_seconds_max`, `hikaricp_*` и идентификаторы пулов `G1 Old Gen` / `PS Old Gen` / `Tenured Gen`) или имена JMX Exporter соответствуют профилям `platform-jvm-connections.example.json` / `platform-jvm-standalone-connections.example.json`.
- [ ] Нагрузка генераторов (`load_generator`, шаблон `platform-openshift-load-generator-connections.example.json`), шаг опроса 30 с и стоимость подзапросов `[$__interval:SUB]` укладываются в `max_requests_per_run` и бюджет профилей.

## 3. PostgreSQL 15 с TLS и `postgres_exporter`

- [ ] Выполнить строгий прогон интеграционных тестов на реальном PostgreSQL 15 с включённым TLS (без `LT_VERDICT_PG_IT_ALLOW_INSECURE=true`), с `pg_stat_statements` и `pg_profile`:

```powershell
$env:LTV_REQUIRE_POSTGRES = "1"
.\gradlew.bat --no-daemon --no-build-cache cleanTest test --tests '*Postgres*' -x npmCi
```

- [ ] Проверить живой scrape `postgres_exporter` по стартовому профилю [`platform-postgresql-promql-connections.example.json`](contracts/sources/v1/platform-postgresql-promql-connections.example.json) (`pg_up`, `pg_stat_activity`, deadlocks, кэш-хиты, `ltv source probe` и `ltv doctor --online`).

## 4. Живой Jenkins: запуск, корреляция и импорт артефакта

Проверить сценарий из [руководства Jenkins и отчётов](user/jenkins-and-reports.md):

- [ ] Настроить `jenkins-connections.json` (с `JENKINS_USER` и `JENKINS_API_TOKEN` в окружении) и запустить `ltv ui --jenkins-config ...`.
- [ ] Запустить существующую job из UI, проверить передачу и отслеживание `correlation_parameter` (`LT_VERDICT_TRIGGER_ATTEMPT_ID`) через queue/build API и восстановление после потери ответа без повторного `POST`.
- [ ] Подтвердить потоковое скачивание allowlisted-артефакта (JTL / `simulation.log`), проверку размера и SHA-256 и его импорт в RunBundle.

## 5. Валидация PromQL через `promtool`

В локальной офлайн-среде без `promtool` тесты с `@unittest.skipUnless(promtool...)` пропускаются. На хосте с установленным `promtool` или Docker-образом `prom/prometheus:v3.5.5` выполнить:

```powershell
$env:LTV_PROMTOOL_DOCKER_IMAGE = "prom/prometheus:v3.5.5"
python -m unittest tools.test_platform_promql tools.test_platform_stand -v
```

- [ ] Все сценарии `tools.test_platform_promql` и `tools.test_platform_stand` проходят без пропусков.

## 6. Хостовые операции Git: prune worktrees и GPG-подпись тега `v0.3.0`

Если в изолированной среде хоста ACL блокировали очистку метаданных worktree или доступ к `gpg`:

- [ ] Проверить и очистить осиротевшие записи worktree на хосте:

```powershell
git worktree prune --verbose
git worktree list
```

- [ ] После завершения волны финальной верификации на `main` создать аннотированный GPG-подписанный тег `v0.3.0` и отправить его вместе с `main` на remote (при необходимости настроить `gpg.program` / `user.signingkey`):

```powershell
git tag -s v0.3.0 -m "LT Verdict 0.3.0"
git push origin main v0.3.0
```
