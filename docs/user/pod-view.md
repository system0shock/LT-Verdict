# Данные по подам: файл `pod-view.v1`

> **Состояние.** Файл можно подать в анализ (платформа, P2b): флаг `--pod-view`
> команды `ltv analyze` и часть `pod_view` запроса `POST /api/jobs`; анализ
> сохраняет его канонический вид, а два read-only маршрута отдают его по API
> (P2c, раздел «Чтение по API»). Файл строит адаптер `tools/pod_view_adapter.py`
> (P2d, раздел «Получение файла: адаптер и синтетика»); вкладка «Глубокий анализ»
> показывает его тепловой картой и таблицей подов (P4c, раздел «Экран «Поды сервиса»»). Решения и границы:
> [ADR 0020](../adr/0020-pod-view-artifact.md).

## Что это и чем не является

`pod-view.v1` — диагностическая проекция по **одному плечу**: тепловая карта и
таблица подов («поды сервиса × время»). Это не основание вердикта: строки файла
не входят в `resource-snapshot.v1` и `analysis-result.v1`, не участвуют в
правилах SLA, `PASS`/`FAIL` и свёртке вердиктов плеч. Сервисные признаки для
правил по-прежнему готовит адаптер в `resource-snapshot.v1`.

Для каждого плеча готовится свой файл. Ядро только проверяет и канонизирует вход:
оно не считает статистику подов, не выбирает «худшие» поды и ничего не усекает.
Файл сверх любого предела отвергается целиком.

## Как готовить файл

Схема: [`pod-view.schema.json`](../contracts/pod-view/v1/pod-view.schema.json).
Примеры: [допустимый](../contracts/pod-view/v1/examples/valid/two-pods.json),
[со сниженным охватом](../contracts/pod-view/v1/examples/valid/worst-by-metric.json)
и [каталог недопустимых](../contracts/pod-view/v1/examples/invalid/).

- Сетка. `start_epoch_ms`, `step_ms` (целое число секунд, не менее одной) и
  `column_count` (1-240). Колонка — агрегат интервала, его считает производитель
  файла. Для восьми часов это шаг 120 секунд. Шаг должен быть кратен шагу снимка
  ресурсов, а начало совпадать с ним (проверяет подача в анализ, см. «Подача в анализ»).
- Привязка. `load_input_sha256` — SHA-256 входа нагрузки, `resource_snapshot_sha256`
  — семантический хэш снимка того же анализа; оба строчными hex. Необязательный
  `arm` — идентификатор плеча (после P1 равен `arm` снимка).
- Поды. У каждого пода имя `pod` (уникально в файле; при нескольких namespace
  включите namespace в имя), `service` и до четырёх контейнеров с ролью `app`,
  `sidecar` или `init`. Сайдкар — отдельный контейнер со своими строками. Новое
  имя пода после redeploy или масштабирования — это другой под: сшивания нет.
- Строки. `id` (уникален), `pod`, `container` (`null` для уровня пода), `metric`,
  `unit`, `aggregation` (`interval_mean`, `interval_rate`, `interval_max`,
  `interval_min`; `instant` не допускается) и `values` ровно из `column_count`
  чисел или `null`. `null` — пропуск, а не ноль. Пара `(pod, container, metric)`
  уникальна, ссылки на под и контейнер должны быть описаны в `pods`.
- Числа. Токен значения не длиннее 12 байт и без экспоненты (`0.62`, а не
  `6.2e-1`). Ограничение относится к значениям в `values`; `start_epoch_ms` и
  другие целые поля записываются обычными целыми без дроби и экспоненты.
- Охват (`coverage`). `pods_included` и `rows_included` равны длинам `pods` и
  `rows`. Если адаптер видел больше, чем положил в файл, он отбирает поды до
  файла, указывает `selection.kind = WORST_BY_METRIC` с `metric` и `limit`
  (1-256) и честные `pods_observed_total` и `rows_observed_total`. При
  `selection.kind = ALL` наблюдённое равно включённому.

## Пределы

| Параметр | Предел |
| --- | --- |
| Файл | 12 MiB |
| Сервисы | 64 |
| Поды | 256 |
| Контейнеры на под | 4 |
| Строки | 2 560 |
| Колонки | 240 |
| Идентификатор (`service`, `container`, `metric`, `unit`, `id`, `arm`) | 128 байт UTF-8 |
| Имя пода | 253 байта UTF-8 |
| Токен значения | 12 байт, без экспоненты |
| Глубина JSON | 8 |
| Число значений JSON в файле (скаляры, объекты, массивы) | 639 008 |

Пределы предварительные (ADR 0020): их подтвердит замер в срезе P2e.

Число значений - предел, выведенный из остальных: столько значений содержит файл на предельных
подах, строках и колонках с запасом на служебные поля. Сканер считает значения потоково и отвергает
файл раньше, чем строится дерево JSON, поэтому файл в пределах 12 MiB с миллионами значений не
расходует память. Такая ошибка указывает на корень документа (`""`), а не на массив.

## Что вернёт проверка

Первая найденная ошибка с кодом и JSON-pointer:

| Код | Когда |
| --- | --- |
| `POD_VIEW_INVALID` | неизвестное поле, неверный тип, пустое имя или управляющий символ, неверная длина `values`, число с экспонентой или длиннее 12 байт, `aggregation: instant`, нарушение `coverage`, неверный UTF-8 или JSON |
| `POD_VIEW_LIMIT_EXCEEDED` | превышен предел файла, числа сервисов, подов, контейнеров, строк или колонок, глубина JSON, число значений JSON или длина идентификатора |
| `POD_VIEW_DUPLICATE_ROW` | повтор имени пода, имени контейнера в поде, `id` строки или `(pod, container, metric)` |
| `POD_VIEW_UNKNOWN_POD` | строка ссылается на под или контейнер, которых нет в `pods` |

Токен значения длиннее 12 байт или с экспонентой - ошибка формы значения
(`POD_VIEW_INVALID`), а не превышение предела.

## Подача в анализ

Pod-view прикладывается к анализу вместе с файлом ресурсов (`resource-snapshot.v1`)
того же плеча: без него анализ не запускается. Подать pod-view отдельно от снимка
или вместе с онлайн-сбором (`source_request`) нельзя: онлайн-производитель
pod-view пока не предусмотрен.

```powershell
.\build\install\ltv\bin\ltv.bat analyze input.jtl --resources resources.json --pod-view pod-view.json --data-dir data
```

В API это необязательная файловая часть `pod_view` запроса `POST /api/jobs` рядом
с `resource_snapshot` (до 12 MiB; в запросе теперь допускается до 25 частей).

Привязка проверяется до записи анализа; нарушение возвращается как `422
INVALID_POD_VIEW` (в CLI - код 4) со списком ошибок:

| Код | Когда |
| --- | --- |
| `POD_VIEW_RESOURCE_REQUIRED` | в запросе нет файла ресурсов |
| `POD_VIEW_INPUT_MISMATCH` | `load_input_sha256` не равен SHA-256 файла нагрузки |
| `POD_VIEW_SNAPSHOT_MISMATCH` | `resource_snapshot_sha256` не равен семантическому хэшу снимка этого запроса |
| `POD_VIEW_ARM_MISMATCH` | `arm` pod-view не равен `arm` снимка (если нет у обоих - допустимо) |
| `POD_VIEW_GRID_MISMATCH` | `start_epoch_ms` не равен началу снимка, `step_ms` не кратен шагу снимка или `column_count` не равен `ceil(point_count x шаг снимка / step_ms)` |

Последняя колонка может покрывать неполный интервал: файл обязан охватывать всю
сетку снимка. Если нужна только часть теста, выберите больший `step_ms`, а не
обрезайте охват. Ошибки самого файла (раздел «Что вернёт проверка») тоже дают
`422 INVALID_POD_VIEW`, а превышение предела - `413`.

## Что сохраняется

Анализ с pod-view получает собственный `analysis_id`: pod-view входит в его
identity двумя полями `pod_view_sha256` и `pod_view_version`. К готовому анализу
файл не прикрепляется: чтобы добавить pod-view, запустите анализ заново. Анализ
без pod-view не меняется (байты identity и результата прежние). Файл
сохраняется как `pod-view.json` в каталоге анализа в каноническом виде; манифест
хранит его размер и SHA-256, равный `pod_view_sha256`. Подмену байт файла при том
же размере обнаруживает чтение pod-view (оно сверяет хэш с манифестом и
identity).

Pod-view не меняет результат анализа, вердикт и ключ сопоставимости: анализ с
проекцией и без неё остаётся технически сопоставимым при прочих равных.

## Чтение по API

Сохранённый анализ с pod-view отдаёт его двумя приватными маршрутами только на
чтение (ADR 0020, раздел 6). Это отдельный диагностический ответ: он не содержит
рядов снимка ресурсов и не влияет на вердикт. Сырой файл не скачивается.

- Метаданные: `GET /api/runs/{runId}/analyses/{analysisId}/pod-view`, без
  параметров. Ответ: `schema_version` (`pod-view.v1`), `arm` (строка или `null`),
  `grid` (`start_epoch_ms`, `step_ms`, `column_count`), `coverage` (как в файле),
  `services` (`[{service, pods, rows}]` в порядке байт UTF-8; `pods` и `rows` -
  числа подов и строк сервиса), `pod_view_sha256` и `resource_snapshot_sha256`.
  Значений рядов в ответе нет.
- Значения: `GET .../pod-view/values?service=...`. Параметры, каждый не более
  одного раза, лишние отвергаются: `service` (обязателен), `metric`, `from_ms`,
  `to_ms`, `limit` (1-256 строк, по умолчанию 64), `after`.

**Страницы.** Строки идут в каноническом порядке `(service, pod, container,
metric)` (`container: null` первым). `after` - `id` последней строки предыдущей
страницы, исключительно; следующая страница начинается с `next_after`, на
последней он `null`. `after` обязан быть строкой выбранного набора
`service`/`metric`, иначе `400 INVALID_CURSOR` (в том числе `id` другого сервиса
или несуществующий `id`). Известный сервис с метрикой, которой в нём нет, даёт
пустой список строк, а не ошибку.

**Окно.** `from_ms` и `to_ms` лежат на границах колонок сетки файла
(`start_epoch_ms + k * step_ms`); `from_ms` по умолчанию начало сетки, `to_ms`
конец последней колонки. Другое значение, `to_ms` не больше `from_ms` или вне
сетки даёт `400` без округления. В ответе поле `grid` повторяет применённое окно
(`from_ms`, `to_ms`, `column_count` возвращённых колонок).

**Предел страницы.** Страница содержит не более 100 000 ячеек (`limit` x число
колонок окна). Проверяется заявленный `limit`, а не число найденных строк, поэтому
фильтрами предел не обойти. Превышение даёт `400` с просьбой сузить выбор, а не
усечённый ответ. При пределах файла (256 строк на страницу, 240 колонок, не более
61 440 ячеек) предел сейчас недостижим; он страхует будущее повышение пределов
после замера (P2e).

**Числа.** Значения - числа двойной точности (`numeric_encoding:
"ieee754-double"`), пропуск `null` остаётся `null`. Они предназначены для показа;
точный источник - канонические байты файла (`pod_view_sha256` - их SHA-256).
Статистики окна (`max`, `mean`, `last`) сервер не считает: их считает клиент по
выбранным колонкам.

**Коды ошибок.** Все ответы с ошибкой имеют общий вид `{"error":{"code",
"message","details"}}`.

| Код | Статус | Когда |
| --- | --- | --- |
| `MALFORMED_REQUEST` | 400 | лишний или повторённый параметр, нет `service`, неверное число или имя, `limit` вне 1-256, окно вне границ колонок, страница выше предела ячеек |
| `INVALID_CURSOR` | 400 | `after` не принадлежит выбранному набору |
| `NOT_FOUND` | 404 | нет запуска или анализа |
| `POD_VIEW_NOT_FOUND` | 404 | у анализа нет pod-view |
| `POD_VIEW_SERVICE_NOT_FOUND` | 404 | в pod-view нет сервиса `service` |
| `CORRUPT_POD_VIEW` | 500 | файл повреждён, подменён (хэш не равен манифесту или `pod_view_sha256` identity, в том числе при прежнем размере) или перестал быть допустимым pod-view |

Каждый запрос заново читает файл и сверяет его SHA-256: кэша разобранного
файла нет, поэтому подмену видит следующий же запрос. Разбор идёт по одному
запросу за раз (до 12 MiB в памяти). Стоимость чтения и разбора на пределах
файла ещё не измерена (P2e).

## Экран «Поды сервиса»

На вкладке «Глубокий анализ» нового интерфейса (`?shell=new`) блок «Поды сервиса»
показывает данные по подам по каждому плечу. Постоянная подпись: «Диагностическая
проекция, не основание вердикта».

- **Когда виден.** Только у анализа с хэшем снимка ресурсов
  (`resource_snapshot_sha256` в списке анализов): без снимка pod-view привязать не к
  чему, запросов нет. Данные грузятся по кнопке «Показать данные по подам», потому что
  каждый запрос к API заново читает и проверяет файл.
- **Где ищется файл.** Для каждого плеча - среди анализов запуска с тем же
  `resource_arm` и тем же `resource_snapshot_sha256` (проход 2 лежит в другом анализе,
  чем онлайн-вердикт): сначала выбранный, затем остальные в порядке списка. Следующий
  кандидат пробуется только после `POD_VIEW_NOT_FOUND`; любая другая ошибка
  (`CORRUPT_POD_VIEW`, сбой сети) показывается как ошибка, а не как «нет данных».
  Ни у одного кандидата файла нет: «Нет данных по подам», пустая карта не рисуется.
  Если `arm` или хэш снимка в метаданных файла не совпадают с плечом и анализом,
  данные не показываются.
- **Что загружается.** Метаданные плеча (один запрос) и все строки выбранного сервиса
  страницами по 256 строк (`limit=256`, весь диапазон колонок, не более 61 440 ячеек на
  страницу). Метрики для выбора берутся из загруженных строк, статистики окна (`max`,
  `mean`, `last`) считает клиент по всей сетке; пропуски `null` в них не участвуют, а
  «последнее» - последнее наблюдённое значение. Запросов на сервис и плечо:
  `1 + ceil(строк сервиса / 256)` (при другом сервисе страницы читаются заново).
- **Карта.** Строки - поды (и контейнеры) выбранной метрики, колонки - сетка файла,
  цвет - линейная шкала от минимума до максимума метрики (общая для плеч, если единицы
  метрики совпадают, иначе у каждого плеча своя). Пропуск рисуется штриховкой. На карте
  не более 24 строк (24 x 240 = 5 760 клеток), худшие по максимуму сверху; это фильтр
  показа, данные таблицы он не меняет. Значение клетки - по наведению указателя, полный
  текстовый вид - таблица подов (50 строк, «Показать ещё»).
- **Охват.** «В файле pod-view: N из M подов» берётся из `coverage` файла (это число по
  файлу, а не по сервису); при `pods_included < pods_observed_total` показывается
  предупреждение «охват сокращён», отбор адаптера (`selection`) описан словами.
- **Несопоставимые плечи.** Если сетки времени плеч различаются (начало, шаг или число
  колонок), карты показываются раздельно, с пояснением; единой шкалы времени и общего
  курсора нет.

Замер на подставных ответах (локальный браузер, 240 колонок, один сервис): 78 подов -
5 760 клеток и 5 764 элемента SVG, 158 мс от клика до карты; 256 подов - те же 5 760
клеток и 264 мс. Время включает фиктивный API, на реальном сервере добавляется чтение и
проверка файла. Влияние на сервер (чтение файла без кэша на каждый запрос) не измерялось.

## Получение файла: адаптер и синтетика

`tools/pod_view_adapter.py` (только стандартная библиотека Python 3, запуск из
корня репозитория) - первый производитель `pod-view.v1`. Это инструмент рядом с
продуктом, а не его часть: ядро по-прежнему только проверяет файл.

### Живой режим

Живой режим - проход 2 двухпроходного процесса: pod-view подаётся только офлайн
вместе с файлом снимка ресурсов того же плеча. Привязку (`--load-sha256`,
`--snapshot-sha256`, `--arm`) и сетку (`--start-epoch-ms`, `--step-ms`,
`--columns`) адаптер берёт из аргументов; они должны совпасть с анализом, иначе
подача вернёт `422 INVALID_POD_VIEW` (раздел «Подача в анализ»).

```powershell
python -m tools.pod_view_adapter --prometheus http://prometheus:9090 `
  --namespace shop --services orders-svc payments-svc `
  --start-epoch-ms 1704067200000 --step-ms 120000 --columns 240 `
  --load-sha256 <sha256 файла нагрузки> --snapshot-sha256 <семантический хэш снимка> `
  --arm A --select worst:openshift_container_memory_limit_ratio:24 --out pod-view.json
```

- Колонка `k` - интервал `[start + k * step, start + (k + 1) * step)`; адаптер
  запрашивает правые границы `start + step ... start + columns * step`, как
  сбор снимка, а `$__interval` в запросах равен `--step-ms`. Шаг должен быть
  кратен шагу снимка (раздел «Подача в анализ»).
- Запросов по одному на сочетание (namespace, сервис, метрика): ответ содержит
  все поды сервиса, а сервис пода - это `workload` owner relabel запроса. Метрики
  (`--metrics`, по умолчанию все): `openshift_container_cpu_limit_ratio`,
  `openshift_container_memory_limit_ratio`, `openshift_cpu_throttling` (строки по
  контейнеру) и `openshift_pod_cpu_usage` (строка по поду, `container: null`).
  Выражения собраны из шаблонов контракта меток платформы (P0b); набор метрик -
  рабочее решение среза P2d, на реальном OpenShift он не проверялся.
- Роль контейнера: имя, целиком подходящее под `--sidecar-containers` (по
  умолчанию `istio-proxy`), получает роль `sidecar`, остальные - `app`.
- Пропуск источника, `NaN` и бесконечность записываются как `null`, а не 0.
  Значение округляется до 12 байт без экспоненты (`0.123456789012345` - `0.123456789`);
  целая часть не режется: число, не помещающееся без неё, - ошибка адаптера.
  Очень малое значение может округлиться до `0`.
- `--select worst:<метрика>:<limit>` (метрика из `--metrics`, `limit` 1-256)
  оставляет `limit` подов с наибольшим максимумом метрики по колонкам; поды без
  значений идут последними, равные - по `(service, pod)`. Выбор делается до файла,
  `coverage` пишет `WORST_BY_METRIC` и честные наблюдённые числа. Без `--select`
  адаптер отказывает, если файл не уложился бы в пределы (256 подов, 2 560 рядов,
  64 сервиса, 4 контейнера на под, 12 MiB), а не усекает его.
- При нескольких `--namespace` имя пода становится `namespace/pod`. Под, попавший
  в два сервиса, и повторный ряд `(pod, container, metric)` - ошибки.
- Имена `--namespace` и `--services` должны подходить под `[A-Za-z0-9][A-Za-z0-9._-]{0,99}`
  (они подставляются в запрос). Ответ отвергается, если источник вернул
  предупреждения, не матрицу, ряд другого namespace, метку времени вне сетки или
  две точки в одной колонке. Авторизация источника в
  адаптер не входит: `--prometheus` - базовый URL, к которому добавляется
  `/api/v1/query_range`.

Код возврата 0 - файл записан; 2 - ошибка адаптера (сообщение в stderr, файл не
создаётся). Одни и те же ответы дают побайтно равные файлы.

### Синтетика

`python -m tools.pod_view_adapter --synthetic spec.json --out DIR` выпускает
каталог `DIR` из четырёх согласованных файлов без стенда:

| Файл | Что это |
| --- | --- |
| `load.jtl` | нагрузка из `tools/perf/generate_jtl.py` (`load_rows` строк по 10 мс); от неё считается `load_input_sha256` |
| `resource-snapshot.json` | сервисные ряды (худший контейнер сервиса, метрики по контейнеру), метка `arm` на каждом ряду |
| `pod-view.json` | поды, контейнеры и строки; колонка - среднее ячеек снимка |
| `expected.json` | эталон: `max`, `mean` (шесть знаков) и `last` по каждой строке, заложенный эффект (`planted_effect`) и худший под по метрикам; считается закрытой формулой генератора, а не запуском LT Verdict |

Все поля `spec.json` необязательны: `scenario` (`balanced`; `leak-on-arm-b-pod-b2`:
рост памяти второго пода первого сервиса только при `arm: "B"`;
`throttle-on-one-pod`: throttling и CPU второго пода первого сервиса с трети
теста), `arm`, `namespace`, `services` (1-64, имена `svc-01`...),
`pods_per_service` (число или список по сервисам; имя пода `svc-01-b2`),
`containers` (до четырёх имён), `sidecar_containers`, `snapshot_step_ms`,
`pod_step_ms` (положительное кратное шага снимка), `load_rows` (`load_rows * 10 мс` кратно
шагу снимка), `load_seed`, `seed`. Сетки начинаются с первой метки
`generate_jtl.py` (1704067200000), начало не настраивается. Спецификация, которая
вывела бы файл за пределы ядра (подов, рядов, точек и ячеек снимка), отвергается до
записи. Значения - целые тысячные доли по формулам от
`seed`, без плавающей точки и часов, поэтому два прогона побайтно равны. Для
восьми часов: `load_rows` 2 880 000, `snapshot_step_ms` 15 000, `pod_step_ms`
120 000 (240 колонок). Малый набор лежит в
`fixtures/platform/pod-view-synthetic/`: тест проверяет, что спецификация
воспроизводит его байты, а ядро принимает его и привязку к снимку.

Синтетические файлы подаются в анализ как обычно:

```powershell
.\build\install\ltv\bin\ltv.bat analyze DIR\load.jtl --resources DIR\resource-snapshot.json --pod-view DIR\pod-view.json --data-dir data
```

## Канонический вид

Проверка упорядочивает строки по байтам UTF-8 кортежа `(service, pod, container,
metric)` (`container: null` идёт первым), поды — по `(service, pod)`, контейнеры
— по имени. Хэш канонического вида не зависит от порядка ключей объектов, порядка элементов
массивов `pods`, `containers` и `rows` и от написания чисел (`0.50` и `0.5`
равны). Порядок значений в `values` важен: это порядок колонок. Одиночные
суррогаты UTF-16 в именах (`\uD800` без пары) отвергаются.
