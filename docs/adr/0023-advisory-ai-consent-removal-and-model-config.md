## Риск, принятый владельцем

**Что меняется по существу.** До этого решения evidence анализа уходило
внешнему провайдеру только после явного заявления пользователя («Разрешаю
отправить evidence этого анализа и системный промпт в Alibaba ModelStudio
(Singapore)»). После решения продукт отправляет evidence **и системный prompt**
на endpoint, заданный конфигурацией, по явному запуску ИИ-разбора, **без
согласия пользователя анализа и без предупреждения о передаче в самом
действии**.

**Что уходит.** Allowlisted поля проверенного `analysis-result.json`
(`ai-evidence.v1`, ADR 0010, п. 1): метки и пути групп транзакций, метки ресурсов
и сервисов, идентификаторы правил политики, числовые метрики и статусы, причины
вердикта. Credential, профили, сырые SQL и log-тела, файлы репозитория исключены;
секреты внутри свободных меток evidence редактируются по набору шаблонов ключей и токенов (AUD-02, PR #47): секрет вне шаблонов в метке клиента дойдёт до endpoint. Имена
транзакций и сервисов клиента остаются в evidence: это может быть
чувствительная для организации информация.

**Credential.** Relay отправляет credential из env-файла
(`OPENAI_API_KEY`) заголовком `Authorization: Bearer` на endpoint из
конфигурации. Смена endpoint отправляет тот же credential на новый адрес;
оператор обязан подставить credential, выданный именно для этого endpoint.
Credential по-прежнему не попадает в Qwen, argv, advice и provenance (ADR 0010),
но при `allow_insecure_http: true` он идёт по сети открытым текстом;
документация предупреждает об этом, а relay не следует редиректам провайдера
(иначе заголовок ушёл бы на третий адрес).

**Куда.** Сегодня (на 2026-10-05; обновлено решением D3 / ADR 0027) единственный раннер идёт во внешнего провайдера
(ModelStudio, Сингапур). Владелец заявил, что в боевой системе инференс он-прем,
а адрес endpoint задаёт конфигурация. Репозиторий не может ни подтвердить это,
ни проверить: продукт не отличает внутренний endpoint от внешнего. Если
конфигурация указывает на внешний сервис, данные уходят наружу без согласия.
Это следствие выбора варианта А, а не недосмотр.

**Кто отвечает.** Владелец продукта принял риск прямо («риски на мне»);
оператор развёртывания отвечает за то, куда указывает endpoint в конфигурации и
какие модели разрешены. Пользователь анализа не принимает решения об отправке.

**Какие защиты остаются** (ничто из этого не заменяет согласие, но не снято):
явный запуск (кнопка «Получить рекомендации» либо явный переключатель «запросить
ИИ-разбор после анализа», по умолчанию выключен; ADR 0010 открывается словами
«запускается только явно»); allowlist evidence и шаблонная редакция секретов; отсутствие
credential в evidence, argv, advice и provenance; внешняя OS-изоляция и
endpoint-only egress; один immutable совет на analysis; fail-soft; список
разрешённых моделей из конфигурации; запись в provenance, куда ушло evidence
(Д4).

**Последствия, которые нужно показать честно** (закреплены в срезах и
документах, Д5):

- **Приватность.** Утверждение «данные не покидают контур» нигде в продукте и в
  документации не появляется без подтверждения конфигурации. Документация
  пользователя прямо говорит, что evidence и prompt отправляются на endpoint из
  конфигурации без запроса согласия.
- **Тексты в UI.** Чекбоксы и слова «Разрешаю отправить…» убираются целиком;
  текст про ModelStudio из согласия убирается. Если оператор задал
  `endpoint_label` в конфигурации (Д3), UI показывает постоянную
  информационную строку «Данные анализа отправляются в {назначение}» без
  действия пользователя; строка не требует согласия и не блокирует кнопку
  (вопрос 1 раздела «Вопросы, не блокирующие реализацию»).
- **Документация.** `docs/user/advisory-ai.md` и
  `docs/user/slice-1-local-analysis.md` перестают говорить о согласии и
  описывают, что и куда отправляется; `CHANGELOG.md` отмечает снятие согласия
  как видимое пользователю изменение (`Changed`).
- **Необратимость в рамках одного анализа.** Совет иммутабелен (ADR 0010, п. 4):
  отправка evidence не отзывается.

**Когда пересмотреть.** Решение нужно вернуть на обсуждение, если продукт
станет многопользовательским, если анализ будет касаться данных третьих лиц, или
если конфигурация по умолчанию начнёт указывать на внешнего провайдера в поставке
для пользователей, не принимавших это решение.

## Решение

### Д1. Согласие на отправку в ИИ убрано полностью и всегда

1. Продукт не запрашивает, не проверяет и не хранит согласие на отправку:
   ни при внешнем, ни при внутреннем endpoint, ни в API, ни в UI.
2. Явный запуск сохраняется: совет создаётся только по действию пользователя
   (кнопка либо переключатель «Запросить ИИ-разбор после анализа», выключенный по
   умолчанию). Переключатель выражает намерение запуска, а не согласие, и не
   содержит слов о разрешении или отправке.
3. Область endpoint (`internal` / `external`), профили назначения и
   `endpoint_scope` не вводятся (отклонённая альтернатива Б).

### Д2. Совместимость API (`confirm_external_transfer`)

Публичный контракт `POST /api/runs/{run}/analyses/{analysis}/advice`
меняется явно и аддитивно по смыслу клиента, а не молча:

| Тело запроса | Ответ |
| --- | --- |
| пустое тело, `{}` | принимается (раньше 400) |
| `{"confirm_external_transfer":true}` | принимается; поле **устарело и игнорируется**, чтобы существующие клиенты не сломались |
| `{"confirm_external_transfer":false}` | 400 `MALFORMED_REQUEST`: клиент, явно отказавшийся от отправки, не получает отправку молча |
| `{"model_id":"<slug>"}` (с `confirm_external_transfer:true` или без) | принимается, если слаг есть в конфигурации (Д3); иначе 400 |
| любые другие ключи, дубликаты ключей, не объект, тело больше 512 байт | 400 `MALFORMED_REQUEST` |

Обоснование: безопасный по умолчанию отказ клиенту, который отправил `false`;
обратная совместимость для клиентов, всегда присылавших `true` (UI до среза CM1
и внешние скрипты); никакого удаления поля до отдельного решения. Защита от
неоднозначных дубликатов JSON-ключей, ради которой появилось регулярное
выражение, сохраняется явной проверкой (разбор закрытым объектом с отказом на
дубликат). Изменение отмечается в `CHANGELOG.md` (`Changed`) и в
`docs/user/advisory-ai.md`. Коды ошибок не добавляются; перечень `AdviceFailure`
не меняется. В `AdviceUnavailableReason` добавляется одно значение
`MODEL_CONFIG_INVALID` (Д3, п. 6); UI уже выводит неизвестные причины как код с
нейтральной подписью (срез U6a).

Статус задания (`POST`, `GET/DELETE /api/advice-jobs/{id}`) получает
аддитивное поле `model_id` (выбранная модель). Это закрывает ограничение плана
ADR 0021 (вопрос В5): модель видна и у `FAILED`, и у `UNAVAILABLE`.

### Д3. Файл конфигурации моделей

1. **Расположение.** Абсолютный путь в переменной окружения
   `LT_VERDICT_AI_MODELS_FILE` (рядом с `LT_VERDICT_AI_CREDENTIAL_ENV_FILE`,
   `LT_VERDICT_AI_RUNTIME_ROOT`, `LT_VERDICT_AI_QWEN_ROOT`). Файл не содержит
   секретов; его рекомендуется держать вне репозитория и data directory, как
   credential. Прочитывается один раз при старте процесса; смена требует
   перезапуска. Нет переменной: действует встроенная конфигурация по умолчанию
   (текущее поведение: ModelStudio и модель `deepseek-v4-flash-0731`), так что
   развёртывание без файла работает, как до этого ADR.
2. **Формат** (UTF-8 JSON, закрытый объект, схема
   `docs/contracts/advice/v1/ai-models.schema.json`, `schema_version`
   `ai-models.v1`; новый публичный контракт, добавляется срезом CM2):

   ```json
   {
     "schema_version": "ai-models.v1",
     "endpoint": {
       "url": "https://models.internal.example/v1/chat/completions",
       "label": "Внутренний шлюз моделей",
       "allow_insecure_http": false
     },
     "default_model": "qwen3.8-max",
     "models": [
       { "id": "qwen3.8-max", "label": "Qwen 3.8 Max" },
       { "id": "deepseek-v4-flash-0731", "label": "DeepSeek V4 Flash" }
     ]
   }
   ```

   Поля: `models` (обязательно, 1-32 элемента, `id` и `label`), `default_model`
   (обязательно, один из `id`), `endpoint` (необязательно; без него действует
   встроенный endpoint ModelStudio): `url` (адрес chat completions), `label`
   (необязательная подпись назначения для UI), `allow_insecure_http`
   (необязательно, по умолчанию `false`).
3. **Валидация слагов и значений** (в Kotlin при чтении файла, повторно на
   каждом узле цепочки, Д4): `id` соответствует
   `^[A-Za-z0-9][A-Za-z0-9._:/-]{0,127}$`, не содержит `..` и `//`, уникален;
   `label` 1-80 символов без управляющих; `default_model` входит в `models`;
   `endpoint.url`: схема `https` (`http` только при
   `allow_insecure_http: true`, явное допущение оператора для внутренней сети),
   непустой host, без userinfo, query и fragment, не более 512 байт; размер
   файла не более 65 536 байт; **неизвестные ключи и дубликаты имён свойств на любом уровне
   отвергаются** до принятия файла (иначе адрес или модель зависели бы от
   парсера; поле `api_key` или любое другое лишнее не принимается молча). Credential остаётся в
   env-файле `LT_VERDICT_AI_CREDENTIAL_ENV_FILE` и в конфигурацию моделей не
   попадает.
4. **Значение по умолчанию.** Модель по умолчанию это `default_model`; запрос без
   `model_id` использует её. В встроенной конфигурации это
   `deepseek-v4-flash-0731`.
5. **Что видит UI.** Конфигурация попадает в `GET /api/bootstrap`
   аддитивным полем `advisory_ai` (рекомендация вопроса 8 принята):
   `{ "default_model_id": "…", "endpoint_label": "…"|null, "models":
   [{"id": "…", "label": "…", "measured": true|false}] }` либо `null`, если ИИ не
   подключён. **Адрес endpoint в UI не отдаётся**, только подпись. Признак
   `measured` вычисляется кодом и равен `true` только для **пары** (слаг,
   endpoint): слаг входил в эксперимент ADR 0021 (сейчас
   `deepseek-v4-flash-0731`) и endpoint это встроенный ModelStudio, на котором он
   проводился; тот же слаг на другом endpoint считается неизмеренным. В файле
   признака нет: оператор не может
   объявить модель проверенной (ср. ADR 0010, п. 6). Существующие поля bootstrap
   не меняются; это правка закрытого списка ADR 0002 и записана здесь.
6. **Охват до CM4.** Загрузчик (CM2) читает конфигурацию раньше, чем CM4 научит
   запуск ею пользоваться. Чтобы эта щель не выдавала назначение, которого нет,
   до CM4 файл с `endpoint.url`, отличным от встроенного, или со слагами, не
   входящими во встроенный список, отвергается как `MODEL_CONFIG_INVALID`
   (проверка снимается в CM4); подпись `endpoint_label` и список моделей в
   bootstrap до CM4 не могут описывать иное назначение, чем фактическое.
7. **Ошибки конфигурации.** Файл есть, но не читается или не проходит проверку:
   ИИ недоступен (`UNAVAILABLE`, причина `MODEL_CONFIG_INVALID`), `advisory_ai`
   равно `null`, причина без значений файла пишется в stderr процесса
   (указатель на поле и код ошибки). Запуск процесса не прерывается: основной
   анализ от ИИ не зависит.
8. **Запрещено.** Произвольные строки от пользователя вместо модели: слаг
   берётся только из конфигурации, запрос с чужим слагом даёт 400; слаг и адрес
   не собираются в командную строку и не интерполируются в оболочку (Д4, п. 3);
   endpoint не принимается из запроса; секреты в файле.

### Д4. Выбор модели

1. **Запрос.** UI шлёт `model_id` (Д2); сервер ищет слаг в конфигурации и далее
   передаёт **значение из конфигурации**, а не присланную строку; без поля берёт
   `default_model`.
2. **Передача в relay и launcher.** Kotlin передаёт launcher параметры
   `-ModelId` и `-UpstreamUrl` отдельными элементами argv (сейчас модель и адрес
   зашиты в launcher и relay константами); launcher передаёт relay переменные
   окружения (`ADVISORY_RELAY_MODEL`, `ADVISORY_RELAY_UPSTREAM`) и Qwen
   `--model` из переменной окружения. Relay по-прежнему имеет **один**
   фиксированный destination на процесс: он задаётся оператором через
   конфигурацию при запуске совета, а не запросом; relay сверяет модель в теле
   запроса и в кадрах ответа с переданным значением (сегодня с константой),
   удаляет провайдерские поля маршрутизации, пересылает не более двух запросов
   (ADR 0021 Д2); редиректы провайдера не отслеживаются (закрепляется тестом); credential отправляется только на этот destination, а host, на который relay реально отправил запрос, попадает в `relay-result` и далее в provenance.
3. **Защита от произвольных строк.** Каждый узел (Kotlin при чтении файла,
   `param` launcher с `ValidatePattern` и разбором URL, relay при старте, shell
   Qwen) повторно проверяет шаблон слага и правила URL из Д3; значения идут
   только элементами argv и переменными окружения, не строкой оболочки, не в
   `Invoke-Expression`, не в имена файлов и каталогов (имена строятся из
   `invocation_id`). Контрактный тест согласованности: слаг и адрес в Kotlin,
   launcher, relay и shell не могут разойтись (ADR 0021 Д5, п. 4).
4. **«Одна модель, один запрос» (ADR 0021).** Сохраняется: выбор делается до
   запуска, один совет это один запуск с одной закреплённой моделью и
   не более двух пересланных запросов в одном диалоге (повтор по Д2 ADR 0021);
   fallback на другую модель в продукте не вводится (fallback на Codex остаётся
   только в харнессе холдаута).
5. **Provenance (аддитивно, `ai-advice.v1`).** `provenance.model_id`: `const`
   заменяется строкой с шаблоном слага из Д3 (закрытого списка в схеме больше
   нет, так как набор моделей определяет оператор); значение записывается
   **наблюдённое** (launcher сообщает модель, с которой работал relay; Kotlin
   сверяет её с выбранной). Новое `provenance.endpoint_host` (host и порт назначения, без пути и
   учётных данных): след того, куда ушло evidence; значение **наблюдённое**:
   его сообщает relay (куда он реально отправил запрос), а не конфигурация.
   Для новых советов поле обязательно при записи и проверяется при чтении
   (запись нового совета без него отвергается); отсутствие допустимо только у
   прежних советов и означает ModelStudio (схема различает эпохи условием, как
   `provider_requests` в ADR 0021 Д4; предложение автора, вопрос 2 раздела
   «Вопросы, не блокирующие реализацию»). Чтение (ADR 0021 Д3)
   не требует, чтобы слаг входил в **текущую** конфигурацию: смена файла не
   делает прежние советы нечитаемыми; проверяются шаблон слага и закрытый набор
   ключей. `schema_version` остаётся `ai-advice.v1`; `ai-advice-output.v1` и
   `ai-evidence.v1` не меняются.
6. **Холдаут и приёмка.** Предрегистрация фиксирует модель (ADR 0021 Д7);
   выбор в продукте на холдаут не влияет (харнесс закрепляет модель сам). Приёмка
   относится к тройке (модель, метка prompt, runner); модели вне эксперимента
   показываются с пометкой `measured = false` (Д5), и prompt v2 после Prompt-PR
   применяется только к моделям, у которых холдаут по P1-P5 пройден; остальные
   остаются на v1 до собственного прогона (реализуется в Prompt-PR); пригодность к v2, как и `measured`, определяется парой (слаг, endpoint).
7. **Иммутабельность.** Один совет на analysis (ADR 0010, п. 4) сохраняется:
   выбор модели действует на **первый** совет анализа; сравнивать модели на одном
   анализе продукт не позволяет (вопрос 6 сводки: оставить). Несколько советов
   на анализ потребовали бы изменить хранение и ADR 0010, п. 3-4, и не
   предлагаются.
8. **Права и цена.** Ролей в продукте нет (локальный single-user, сессия и
   CSRF, ADR 0002); выбор ограничен списком оператора. Задержка и цена модели
   различаются (DeepSeek 57-131 с на запрос, GLM 197-262 с, ADR 0021 Д2, п. 6);
   окна времени и предел 300 с на повтор не меняются, рост доли `TIMEOUT` у
   медленной модели ожидаем и показывается как есть.

## Исключения из принятых правил

| Правило | Что меняется |
| --- | --- |
| ADR 0010, п. 5 (единственный runner, exact model и endpoint) | Модель и endpoint задаются конфигурацией развёртывания (по умолчанию прежние); runner остаётся один (`gigacode-qwen-code`); relay имеет один фиксированный destination на процесс, но он берётся из конфигурации, а не из константы; несколько провайдеров в одном процессе не вводятся |
| ADR 0010, «Последствия» (relay с фиксированным destination, model и одним upstream request) | Destination и model фиксируются конфигурацией при запуске, остальное без изменений (повтор по ADR 0021 Д2) |
| ADR 0021, Д3 (закрытый набор provenance и закрытое значение модели) | Новое необязательное `endpoint_host`; `model_id` проверяется шаблоном, а не равенством константе |
| ADR 0021, Д4 (`model_id` остаётся `const`) | `const` заменяется строкой с шаблоном; закрытый append-only `enum` не вводится, потому что набор определяет оператор |
| ADR 0021, Д5 (механизм выбора модели не вводится) | Вводится: файл конфигурации и выбор на запрос; пункты 2-4 Д5 (параметр `-ModelId`, сверка в relay, тест согласованности) сохраняются |
| ADR 0021, Д6, п. 4 (согласие на отправку остаётся верным) | Согласия нет (Д1) |
| ADR 0010, п. 4 и ADR 0021 Д2, Д7 | Не меняются |

## Отклонённые альтернативы

- **Б. Согласие по области endpoint** (первая редакция этого ADR): `external`
  требует согласия, `internal` нет; область задаёт профиль назначения в коде.
  Отклонено владельцем: «всегда снимать».
- **В. Подтверждение оператора в конфигурации** (флаг вида
  `LT_VERDICT_AI_EXTERNAL_TRANSFER_ACK`, без флага ИИ недоступен): отклонено
  владельцем вместе с Б.
- **Область как свободный флаг окружения:** опечатка отправляла бы данные
  наружу без согласия, а ADR 0010, п. 6 запрещает флагу объявлять границу
  проверенной. После выбора А не нужна.
- **Закрытый append-only набор моделей в коде и `enum` схемы** (ADR 0021 Д5, п.
  1): противоречит запросу владельца на настраиваемый файл слагов.
- **Ввод имени модели пользователем в UI:** произвольная строка в argv, relay и
  provenance.
- **Несколько провайдеров в одном процессе:** registry провайдеров, ADR 0021 Д5.
- **`GET /api/ai/config` вместо поля в bootstrap:** новый маршрут без выигрыша;
  данные постоянны на время процесса.

2. **`provenance.endpoint_host`.** Записывать, куда ушло evidence
   (рекомендация: да, это единственный след при снятом согласии). Альтернатива:
   не вводить (минимум изменений в схеме).
3. **Выбор модели на экране «Новый анализ»** (вопрос 9): да, рядом с
   переключателем намерения; решение автора ADR, не владельца.
4. **`measured` для моделей вне эксперимента.** Строка в UI и prompt v1 (вопрос
   7 сводки, по рекомендации). Если владелец не хочет пометки, `measured` не
   отдаётся.

## Следствия

### Объём реализации

Запрошено: убрать согласие на отправку из продукта, добавить выбор модели в UI,
настраиваемый файл конфигурации моделей. Необходимо для этого: Д1-Д5 и срезы
CM1-CM5. Не требуется: область endpoint и профили, он-прем раннер как отдельный
срез (адрес задаётся конфигурацией), выбор данных для модели, несколько советов
на анализ, несколько провайдеров в одном процессе, fallback модели в продукте,
структурный `ai-advice.v2`, правки `io.ltverdict.core`.

### Риски и остаточные ограничения

- Принятый риск отправки без согласия (раздел «Риск, принятый владельцем»);
  продукт не может проверить, что endpoint внутренний.
- Relay с конфигурируемым destination: ошибка в проверке URL или в передаче
  значений ослабит ограничение «один destination»; закрепляется тестами и
  проверкой каждого узла (Д4, п. 3). Egress контейнера до адреса
  из конфигурации (внутренняя сеть, прокси, DNS) в репозитории не
  проверялся и зависит от развёртывания.
- Закрытый разбор тела POST заменяет проверенный regex; ошибка в проверке
  дубликатов ключей закрепляется тестом первым.
- Модель вне эксперимента даёт советы с неизвестными дефектами (T1-T7 ADR
  0021); пометка в UI это называет, но не исправляет.
- Правки закрытой схемы provenance и контракта bootstrap идут параллельно с
  Runtime-PR-B плана ADR 0021: порядок слияния любой, но конфликты ожидаемы.
- Не проверено на реальном внутреннем endpoint: поведение Qwen Code с
  произвольным OpenAI-совместимым сервером (формат tool call, стриминг), слаги с
  `/` и `:` на таком сервере.
