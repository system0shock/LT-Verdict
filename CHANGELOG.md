Все значимые пользовательские изменения LT Verdict фиксируются в этом файле.
Формат основан на Keep a Changelog, версии следуют Semantic Versioning.

## [Unreleased]

## [0.1.0] - 2026-10-09

### Added

- Демо-стенд: необязательный сценарий теста на 4 часа `soak-4h` (60 RPS, 864 000 запросов,
  JTL около 33 МБ, ряды ресурсов Prometheus на весь интервал; трудоёмкость запроса на ЦП
  медленно растёт, SLA за весь тест проходит, а ряды показывают исчерпание запаса по ЦП).
  Включается `docker compose -f docker-compose.yml -f docker-compose.soak.yml up -d --wait`;
  три прежних сценария и запуск по умолчанию не меняются. Политика `policies/soak-4h.json`
  повторяет шаблон «Базовый API (SLA)». Код продукта не менялся; описание, замеры и порядок
  показа: README стенда и `docs/user/demo-script.md` (сценарий 4).
- Новая оболочка, вкладка «Таблицы»: русские таблицы «Ёмкость» (ступени
  теста максимума, граница ёмкости словами, итог ступени, причины, метка «малая
  выборка» у ступени с `CAPACITY_INSUFFICIENT_SAMPLES`) и «Тренды» (проверки
  трендов ресурсов, статусы и причины по-русски). Прежние английские разделы
  скрыты только в новой оболочке; в прежнем интерфейсе они не менялись. Данные,
  API и серверные контракты не менялись, интерфейс ничего не пересчитывает.
- Вкладка «Сравнение» новой оболочки (срез U5a) по-русски: панель baseline с
  формой явного подтверждения условий пары (ADR 0017), предупреждениями в
  порядке сервера, статусами окон словами и текстом «вердикт сравнение не
  меняет, статус «кандидат» только после подтверждения». Тексты берутся из
  `ui/src/shell/labels.compare.ts`; прежний интерфейс остаётся английским, API,
  серверные контракты и числа сравнения не менялись. Длинные идентификаторы окон
  переносятся и не дают горизонтальной прокрутки.
- Имя политики рядом с вердиктом (ADR 0018, срез S1a). Элемент списка
  `GET /api/runs/{runId}/analyses` получает необязательное поле `policy_id`
  (строка или `null`, ключ есть всегда); анализ с политикой теперь сохраняет её
  копию `policy.json` в своём наборе (канонические байты, давшие
  `policy_sha256`), имя читается оттуда с проверкой размера и хэша. Карточка
  вердикта показывает факт «Политика (id)» перед хэшем, список анализов тоже.
  Анализы без политики и созданные раньше остаются с `null`, ошибки нет.
  `analysis-result.v1`, identity и `analysis_id` не менялись.
- Новая оболочка открывается по умолчанию. Прежний интерфейс только по
  явному выбору: `/?shell=old` запоминает выбор в `localStorage` (ключ
  `ltv.shell`), `/?shell=new` сбрасывает его; без доступного хранилища
  действует оболочка по умолчанию. Ссылка «Старый интерфейс» в шапке ведёт на
  `?shell=old`. Данные, API и серверные контракты не меняются.
- Вкладка «Правила» новой оболочки (срез U4a): три шаблона
  политики (`api-basic` с SLA владельца: p95 не более 1000 мс и доля ошибок не
  более 0.05 в целом; `api-strict` и `api-throughput` как стартовые значения) или
  файл, редактор порогов по-русски с подсказками единиц (миллисекунды, RPS,
  доля ошибок с пересчётом «= 5 %»), сохранение неизвестных полей политики при
  правке. Кнопка «Правила по каждой транзакции» разворачивает правила «весь
  прогон» на транзакции открытого прогона в браузере (в `policy.v1` правила «для
  каждой транзакции» нет): пропускает транзакции с малой выборкой и с
  одинаковым именем в разных путях, отклоняет разворот целиком при более чем 256
  правилах, не создаёт дублей. На вкладке «Новый анализ» остались файл политики
  и сводка с кнопкой «Править правила». Прежний интерфейс, API, схема политики и
  ядро не менялись.
- Генератор профилей OpenShift (платформа, срез P0b): `tools/platform_profiles.py`
  по описанию окружения выпускает `source-connections.v1` с запросами пакета
  `openshift` (ЦП и память контейнеров к лимитам, рестарты, OOM, троттлинг,
  перекос подов; свёртка по подам на стороне запроса). Шаблоны проверены
  `promtool` на 20 сценариях; примеры лежат в `docs/contracts/sources/v1/`.
  Профили выпускаются без `scrape_interval_ms`: платформенный анализ запускается
  с `step_mode: fixed` (режим `auto` отказывает с
  `AUTO_STEP_SCRAPE_INTERVAL_REQUIRED`). Метки экспортёров реального стенда не
  проверялись; допущения перечислены в `docs/user/platform-metric-packs.md`.
  Схемы, API и identity не менялись.
- Сигналы JVM в генераторе профилей (платформа, срез P0c): куча, старое
  поколение, вне кучи, потоки, CPU процесса, пауза GC, доля времени GC и
  насыщение пула соединений (Micrometer) выпускаются теми же шаблонами; сервис
  берёт худший под. `jvm_gc_pause` выпускается только в пиковом режиме
  (`interval_max`). Выражения проверены `promtool` (29 сценариев вместе с
  OpenShift); защиты полноты по подам у сигналов JVM нет, метки Micrometer
  реального стенда не проверялись. Схемы, API и identity не менялись.
- Генератор платформенных профилей понимает интервал опроса (платформа, срез
  P0d): при `scrape_interval_ms` в конфигурации он выпускает
  `source-connections.v3` с этим полем в каждом профиле, и автошаг `auto` с
  такими профилями работает; без поля выход прежний (`v1`, байты примеров не
  менялись). При заданном `request_step_ms` генератор отказывает до записи
  файла, если шаг меньше интервала опроса, если сигнал на `rate` получит шаг
  меньше удвоенного интервала (`PLATFORM_RATE_WINDOW_TOO_SHORT`); отдельно, при
  заданном `scrape_interval_ms`, - если шаг подзапроса выбранного сигнала
  крупнее интервала опроса. Подзапрос `[$__interval:SUB]` по-прежнему не
  переживает огрубление шага (`AUTO_STEP_QUERY_NOT_INTERVAL_BOUND`).
  Схемы, API и identity не менялись.
- Карточка вердикта показывает хэш политики (ADR 0018, срез S4): последний
  факт «Политика (хэш)» с первыми 12 символами `policy_sha256` выбранного
  анализа либо `не задана` без политики. Данные берутся из уже существующего
  списка сохранённых анализов; API, результат и identity не менялись. Тест
  закрепляет, что две политики на одной нагрузке дают два анализа с разными
  `analysis_id` и одинаковым ключом сопоставимости. `policy_id` в карточке не
  показывается.
- Карточка вердикта, вкладка «Обзор» и таблица правил показывают режим малой
  выборки (ADR 0018): пометка «режим малой выборки: N сэмплов при минимуме M» у
  проверки, суффикс «малая выборка» в чипе вердикта, число сэмплов в причине
  `INSUFFICIENT_SAMPLES` и столбец «Выборка» в таблице правил. Вердикт, коды
  выхода и контракты не меняются.
- Вкладка «Таблицы» новой оболочки (`?shell=new`) показывает русские таблицы
  «Правила» (область, метрика, порог, измерено, окно, статус, причина) и
  «Транзакции» (выборка, ошибки, p50, p95, p99, RPS, статус; поиск, фильтр
  статуса и сортировка в браузере). Прежний интерфейс и серверные контракты не
  меняются.
- Автошаг онлайн-сбора (ADR 0014, срез S2): запрос источника `source-request.v4`
  с обязательным `window.step_mode` (`fixed` или `auto`; `max_idle_gap_ms` целое число секунд) и поле профиля
  `scrape_interval_ms` в `source-connections.v3`. В режиме `auto` заявленный шаг
  остаётся, пока `рядов × ячеек <= 1 500 000`, иначе планировщик до первого
  запроса к источнику выбирает наименьший подходящий целый шаг не выше 60 с.
  Огрубление отказывает с кодами `AUTO_STEP_UNSATISFIABLE`,
  `AUTO_STEP_SCRAPE_INTERVAL_REQUIRED`, `AUTO_STEP_BELOW_SCRAPE_INTERVAL`,
  `AUTO_STEP_QUERY_NOT_INTERVAL_BOUND`, `AUTO_STEP_RULE_IN_CELLS` и
  `AUTO_STEP_AGGREGATION_MISMATCH` (срез S3, см. ниже).
  `source_summary` для `v4` публикует `step_origin`, `requested_step_ms`,
  `series_count`, `cell_budget`, `cells_per_series` и предупреждение
  `RESOLUTION_REDUCED`; поля входят в `source_acquisition_sha256`. Документы
  `v1`-`v3` и их сводки не меняются; сборка без `v4` и `scrape_interval_ms`
  отказывает на таком документе (`SOURCE_REQUEST_INVALID`,
  `SOURCE_CONFIG_INVALID`). Исключение для событийных приращений и UI режима
  шага не входят в срез.
- Правила по длительности (ADR 0014, срез S3): правило профиля в
  `source-connections.v3` объявляется полем `min_consecutive_span_ms` (1 -
  86 400 000 мс) вместо `min_consecutive_cells`; при сборке длительность
  переводится в ячейки как `ceil(span / step)`, а `source_summary` профиля
  публикует `rule_spans` (входит в `source_acquisition_sha256`). Огрубление
  шага в режиме `auto` теперь проверяет каждое правило: правило в ячейках
  отказывает `AUTO_STEP_RULE_IN_CELLS`, а агрегация ряда, не сохраняющая пик для
  оператора (`gt` - `interval_max`, `lt` - `interval_min`), отказывает
  `AUTO_STEP_AGGREGATION_MISMATCH`; ряды без подходящего правила попадают в
  `RESOLUTION_REDUCED`. Документы `source-connections.v1`, `v2` и сводки
  профилей без правил по длительности не меняются.
- Исключение для событийных приращений (ADR 0014, срез S4): запрос в
  `source-connections.v3` можно объявить `non_negative_events: true`; для такого
  ряда и правила `gt` с порогом не выше 0 огрубление шага допускается при
  `interval_mean`, `interval_rate` и `interval_max`, правило в ячейках
  допустимо только с `min_consecutive_cells = 1`; `gt` с порогом выше 0 и `lt`
  исключения не получают. Профиль с таким рядом, правилом `gt` не выше 0 и
  `interval_min` отвергается при чтении конфигурации при любом шаге.
  Отрицательное значение в объявленном ряду переводит запрос в `FAILED` с
  причиной `NEGATIVE_EVENT_VALUE` (проверка санитарная). Ряд со средним или
  скоростью перечисляется в `RESOLUTION_REDUCED`. Документы `v1` и `v2` поле не
  принимают.
- Снимок ресурсов `resource-snapshot.v1` принимает агрегации `interval_max` и
  `interval_min` (максимум и минимум за интервал сетки, ADR 0014); профили
  онлайн-источников получают их без правок конфигурации. Изменение аддитивно:
  прежние снимки остаются валидными с тем же хэшем, а метка агрегации входит в
  хэш нового снимка. Ось нагрузки capacity по-прежнему требует `interval_mean`.
  Односторонняя совместимость: сборка без этих значений отказывает на таком
  снимке с `UNSUPPORTED_AGGREGATION`.
- Демо-стенд `tools/demo-stand/` (Docker Compose: Prometheus, Grafana, генератор синтетических прогонов) для живого показа:
  три сценария (SLA FAIL, тест максимума, насыщение БД), профиль `grafana_proxy`, дашборд и политики.
  Это демо-инфраструктура, не зависимость продукта; код продукта не менялся.
- Параметр запуска `--histogram-significant-digits <3..5>` у `ltv ui` и
  `ltv analyze` (по умолчанию `3`): число значащих цифр гистограммы
  перцентилей (ADR 0016). Значение входит в identity анализа; смена даёт новый
  `analysis_id`, а analyses с разной точностью несопоставимы для baseline. Вне
  диапазона `3..5` запуск завершается usage error (`64`). Выше 3 растёт память
  (около 1,9 и 2,1 раза при больших выборках), замерьте на стенде заранее.
- Вкладка «Новый анализ» новой оболочки (срез U2, предпросмотр за `?shell=new`):
  русский экран запуска из пяти разделов (нагрузочный тест, правила, данные о
  системе, планы анализа, ИИ-разбор) со всеми текущими полями и блок
  «Готовность к запуску», который перечисляет выбранное, список «Что
  получится» и причины, по которым кнопка «Запустить анализ» недоступна. Кнопку
  блокируют только перечисленные условия (нет файла, занято, ошибка запроса
  источника, план корреляций, ёмкости или трендов без снимка ресурсов, ошибки
  в черновике политики, больше 100 000 ячеек в явном окне источника).
  Запуск идёт тем же путём и с теми же частями запроса, что из прежней формы;
  API, контракты и зависимости не менялись. В разделе «ИИ-разбор» есть галка
  согласия: после завершения анализа совет запрашивается сам тем же вызовом,
  что кнопка на вкладке «ИИ-разбор», согласие действует на один запуск и нигде
  не хранится. Поля окна источника на этом экране заданы в секундах (на сервер
  уходят миллисекунды, как раньше).
- Ответ `comparison` содержит `warnings`: `BASELINE_IS_CURRENT_ANALYSIS`,
  `BASELINE_IS_CURRENT_RUN`, `CURRENT_IN_CANDIDATE_SET`; причины окна
  `BASELINE_WINDOW_EMPTY`, `CURRENT_WINDOW_EMPTY`. Панель Baseline comparison
  показывает предупреждения, форму подтверждения условий для обоих режимов,
  подсказку про пустое окно и подсказку «эталон создан по старым правилам,
  пересчитайте»; смена идентификаторов окон сразу показывает решение новой
  пары.
- Вкладка «Обзор» новой оболочки (срез U1, предпросмотр за `?shell=new`):
  блок «Требует внимания» (нарушения правил, причины `NO_VERDICT`, неполные
  данные, найденные тренды и кандидаты в корреляции с пометкой «диагностика,
  не причина» и переходами к таблицам), ключевые метрики прогона и три ряда
  нагрузки (RPS, ошибки, p95) на общей шкале времени с одним курсором для
  клавиатуры и мыши. Данные берутся из готового результата и уже загруженной
  страницы `/buckets`; API, контракты и зависимости не менялись.
- Новая оболочка интерфейса (срез U0, предпросмотр): токены, светлая и тёмная
  темы, вкладки «Новый анализ» (открывается первой), «Обзор», «Таблицы»,
  «Сравнение», «Правила» (в разработке), «ИИ-разбор» и шапка с прогоном и
  вердиктом; списки прогонов и анализов слева подписаны по-русски. Включается только
  параметром адреса `?shell=new`; по умолчанию открывается прежний интерфейс без
  изменений, API и контракты не менялись. Тема и вкладка нигде не сохраняются.
- Авто-окно выборки источника: `source-request.v3` с `window.origin` `auto`
  выводит окно из периода, распознанного по timestamps самой нагрузки, и
  отказывает до внешних запросов с `AUTO_WINDOW_UNAVAILABLE`,
  `AUTO_WINDOW_MULTI_TEST_SUSPECTED` или `AUTO_WINDOW_SPAN_UNSUPPORTED`,
  требуя явное окно. Распознанный период сохраняется run-артефактом
  `runs/<runId>/run-period.json` (`run-period.v1`), привязан к hash нагрузки и
  переиспользуется при повторном открытии. `v1` и `v2` принимаются без
  изменений; CLI `--source` и file part `source_request` принимают все три
  версии, UI отправляет только `v3` и по умолчанию предлагает авто-окно.
  Смещение часов генератора и системы мониторинга не компенсируется (ADR 0012).
- Provenance окна в `source_summary` для `source-request.v3`: `window_origin`,
  а для авто-окна также распознанный период, заявленный и фактически
  применённый margin, допуск простоя, число и длительность простоев и
  `auto_window_status`. UI показывает эти поля таблицей `Window` в секции
  source acquisition; summaries `v1`/`v2` и ручной импорт OpenSearch-контекста
  полей окна не получают.
- Опубликована схема `source-request.v2` с valid/invalid примерами,
  подключёнными к Ajv contract check: рантайм принимал `v2` с появлением
  multi-profile selection, но опубликованные контракты фиксировали только `v1`,
  поэтому проверять документы `v2` было нечем.
- Optional `trend-plan.v1` и L0-детектор роста ресурсных метрик в пределах SLA:
  объявленные проверки (не более 32) на уже публикуемых `slope_per_second` и
  `split_half_shift` с двумя заранее объявленными порогами материальности и
  требованием согласия знаков. Статусы `TREND_OBSERVED`, `NO_MATERIAL_TREND`,
  `INSUFFICIENT_CELLS`, `UNAVAILABLE` с точными reason-кодами; finding
  `resource_trend` с `effect=diagnostic`. Вердикт и `analysis_coverage` не
  меняются, p-values и оценка неопределённости отсутствуют
  (`uncertainty=NOT_ESTIMATED`), рост не трактуется как утечка или причина.
  Доступно через CLI (`--trend`), API (part `trend_plan`) и UI; артефакты
  `trend-plan.json` и `trend.json`, в identity — модуль
  `resource-trend-evaluation`.
- Подготовка к приёмке: advisory AI jobs/API/UI и изолированный ModelStudio/Qwen
  runtime, consent, отмена и fail-soft без изменения deterministic verdict.
  Изменённый prompt требует отдельной оценки качества; пилот не возобновлялся.
- Jenkins profiles и журнал trigger/queue/build/artifact, восстановление неизвестного
  исхода без автоматического повторного POST; импорт проверенного artifact в RunBundle.
- Локальная N-run/transaction аналитика, OpenSearch chart markers и capability coverage
  JVM/OpenShift; Grafana source links и bounded PNG render по явному запросу.
- Confluence-ready XHTML export и offline onboarding skill/wrapper с проверкой
  подтверждённого hash и добавлением нового внешнего metadata manifest.

- Платформенные правила в политике (ADR 0018, срез S6, строгий режим). `policy.v1`
  получает необязательные секции `platform_services` (каталог ожидаемых сервисов),
  `platform_coverage` (сигнал покрытия) и `platform_rules`: правило-шаблон
  (`signal`, `scope`, `operator` `gt|lt` как условие нарушения, `threshold`, `unit`,
  `aggregation`, `min_consecutive_cells`, `effect`, необязательное `window_ids`)
  разворачивается по сервисам области (`service` или `all_services` с `except`) в
  ресурсные проверки `<id>/<сервис>` и оценивается тем же вычислителем, что и
  правила снимка; в evidence `resource_policy_check` добавлены `platform_rule_id` и
  `service`. Отсутствие ряда, неоднозначный ряд, чужая единица или агрегация, ряд
  сервиса вне каталога, окно короче серии, неизвестное окно и отсутствие снимка дают
  `NO_VERDICT` с причинами `RESOURCE_SERIES_NOT_FOUND`, `PLATFORM_SERIES_AMBIGUOUS`,
  `PLATFORM_UNIT_MISMATCH`, `PLATFORM_AGGREGATION_MISMATCH`,
  `PLATFORM_SERVICE_NOT_IN_CATALOG`, `RULE_WINDOW_TOO_SHORT`, `RULE_WINDOW_NOT_FOUND`,
  `RESOURCE_SNAPSHOT_REQUIRED`, а не `PASS`. Политику с платформенным `sla`-правилом
  валидатор принимает, только если для каждой пары «сервис × окно» есть правило
  покрытия (`PLATFORM_COVERAGE_MISSING`). Политика с `platform_rules` не совмещается
  со снимком или профилем, поставляющим ресурсные `sla`-правила: ошибка привязки
  `PLATFORM_RULES_CONFLICT` до создания анализа (CLI код 4, API 422). Допуск
  пропусков в этом срезе строгий (любой пропуск даёт `NO_VERDICT`). Анализы без
  `platform_rules`, `identity.json`, ключ сопоставимости baseline и `analysis_id` не
  меняются; файл политики с платформенными секциями имеет другой `policy_sha256`, а
  прежняя версия отвергает его как `UNKNOWN_FIELD`. Схема и примеры `policy.v1`
  обновлены. Словарь причин отчёта пополнен кодом `RULE_WINDOW_NOT_FOUND`, которого
  не хватало после среза S5.
- Допуск пропусков у платформенных правил (ADR 0018, срез S7). У `sla`-правил из
  `platform_rules` можно задать `max_missing_fraction` (`0 <= x < 1`) и
  `max_gap_cells` (`0..100000`) в `defaults` политики и в самом правиле; запасные
  значения ядра: 5 % ячеек и разрыв до 3 ячеек (допущения владельца, на стенде не
  измерены). Пропуски в пределах допуска не блокируют вердикт: правило оценивается
  по наблюдённым ячейкам (`PASS` или `FAIL`) с информационной причиной
  `RESOURCE_GAPS`, анализ получает `analysis_coverage.status = INCOMPLETE`. За
  допуском, при допуске `0` и `0` и для окна без единой наблюдённой ячейки остаётся
  `NO_VERDICT` с `MISSING_RESOURCE_CELLS`; правила снимка, профиля источника и
  `diagnostic`-правила остаются строгими (поля допуска у `diagnostic` дают
  `FIELD_NOT_APPLICABLE`, значение вне диапазона - `TOLERANCE_OUT_OF_RANGE`).
  Серия через пропуск: если нарушение достигает `min_consecutive_cells` только за
  счёт пропущенной ячейки, правило получает `NO_VERDICT` с находкой
  `presumed: true`, а `FAIL` выдаётся только по серии из наблюдённых ячеек.
  Evidence `resource_policy_check` платформенных проверок получает
  `expected_cells`, `observed_cells`, `missing_cells`, `longest_gap_cells`. `PASS`
  при допуске не доказывает отсутствия нарушения внутри допущенного пропуска.
  Меняется identity: анализ с политикой, где есть `platform_rules`, добавляет в
  `verdict_gates` ключи `max_missing_fraction_default` и `max_gap_cells_default` и
  получает новый `analysis_id` (повторный анализ того же входа не перезапишет
  сохранённый). Анализы без `platform_rules` и ключ сопоставимости baseline не
  меняются; новых кодов причин в словарях интерфейса и отчёта нет. Схема и
  примеры `policy.v1` обновлены. Интерфейс (доля покрытия, пометка находки) придёт
  срезом S8.

  («Принят …», с секундами), под ним остаются тип источника и SHA-256; имя файла
  показывается, пока оно отличает прогоны, и у прогона без времени приёма. В
  шапке выбранного анализа добавлены политика (идентификатор, иначе 8 символов
  хэша; для NO_POLICY строки нет) и метка плеча, если она есть. Данные уже были
  в интерфейсе: API, контракты, идентичность прогонов и анализов, старый
  интерфейс не менялись.
- Новая оболочка: при смене вкладки, выборе анализа и завершении анализа
  страница прокручивается наверх, поэтому вердикт на «Обзоре» виден на первом
  экране (1280x720); раньше оставалась прежняя прокрутка. Левая панель на
  экранах шире 960 px закреплена и прокручивается отдельно, списки «Принятые
  прогоны» и «Сохранённые анализы» ограничены по высоте. API, схемы и ядро не
  менялись. Одинаковые имена прогонов (`load.jtl` из разных каталогов) по-прежнему
  различаются по хэшу в подписи: имя берётся из загруженного файла.
- Новая оболочка, вкладка «Таблицы»: блок «Нормализованные данные» (раньше
  «Normalized data») по-русски, а таблица интервалов времени показывает первые
  50 строк с кнопками «Показать ещё 50» и «Показать все (N)» вместо всех 900
  строк на 15-минутном прогоне (страница была около 23 600 px в высоту). Данные,
  API и график не менялись; прежний интерфейс показывает все строки как раньше.
- Отчёт и UI: при `missing_transaction=warn` и вердикте `PASS` или `FAIL` сводка
  считает выполненные проверки отдельно от пропущенных (правила по пропавшей
  транзакции): «проверок: 2, не вычислено: 1», «нарушено проверок: 1 из 2, не
  вычислено: 1». Вердикт, `analysis-result` и схемы не менялись; без
  пропущенных проверок тексты прежние. `summary.txt` и JUnit уже показывали
  статусы отдельно и не менялись.
- Windows-скрипт `bin\ltv.bat` из дистрибутива больше не падает при длинном
  пути установки. Раньше скрипт перечислял все jar-файлы в одной командной
  строке, и при пути около 125 символов и длиннее `cmd.exe` отвечал «The input
  line is too long» или «The syntax of the command is incorrect» (лимит
  командной строки 8191 символ). Теперь classpath задан как `%APP_HOME%\lib\*`
  (проверено на пути 205 символов с пробелами и кириллицей: `analyze` и `ui`
  работают). Linux-скрипт `bin/ltv`, формат вывода, коды выхода, API и состав
  `lib/` не менялись. Побочное следствие: любой дополнительный jar, положенный
  в `lib`, попадает в classpath.
