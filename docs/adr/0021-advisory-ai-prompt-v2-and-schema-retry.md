# ADR 0021: Ограничение советов ИИ: промпт v2 с доменными инвариантами, повтор запроса при ошибке схемы, чтение legacy v1

Дата: 2026-10-02.

Статус: Accepted, 2026-10-04 (принят владельцем). Основание: решения владельца
от 2026-10-02 (раздел «Контекст», п. 5) и от 2026-10-04 (раздел «Решения
владельца (2026-10-04)»; первая редакция была Proposed от 2026-10-02). Принятие
фиксирует решения, а не реализацию: код, контракты, relay и prompt в нём не
меняются; метка prompt по умолчанию остаётся `v1` до холдаута по критериям
P1-P5 (Д7). Поправка от 2026-10-06 (раздел «Поправка от 2026-10-06: холдаут на
headless Codex») меняет условия проведения холдаута Д7 (раннер Codex, модель,
отдельный счётчик); статус остаётся Accepted. Вопросы поправки закрыты ответами
владельца 2026-10-06 (раздел «Вопросы поправки и решения владельца 2026-10-06»);
метка prompt по умолчанию по результатам холдаута на Codex не переключается.
Поздней поправкой того же дня (раздел «Поправка от 2026-10-06 (поздний вечер):
холдаут снова на Qwen Code, Codex запасной») основной раннер холдаута снова
Qwen Code с ModelStudio, а условия поправки про Codex остаются нормативными
только для запасного режима Codex.

Связь с принятыми решениями. ADR [0010](0010-advisory-ai-boundary.md)
сохраняется целиком, кроме одного правила: «один upstream request на совет»
(раздел «Последствия», строки 44-45, и поправка от 2026-09-22, строки 55-56:
«не повторяет model request») получает единственное исключение — повтор при
ошибке схемы аргументов `structured_output` (решение Д2). Доменные правила
берутся из [ADR 0009](0009-explicit-capacity-stages.md) без изменений.

Материалы эксперимента (разбор дефектов, отчёты, предрегистрация, второе
мнение Codex, черновик плана P2) лежат в основном чекауте и **не

## Контекст

### 1. Что показала приёмка 2026-09-28

Разбор 19 ответов (11 `deepseek-v4-flash-0731`, 8 `glm-5.3`) выделил 14
экземпляров дефектов пяти типов T1-T5 (`docs/ui-mockup/ai-defects-analysis-2026-09-30.md`,
строки 91-109). Семь экземпляров имеют серьёзность S2. Шесть из них — тип T1
«нарушение контракта предметной области» (строка 99): «bound требует knee
detector» и «сделать generator guard binding». На одинаковом входе D16 первое
(AI-CAPACITY-01) воспроизвелось в 4 из 4 ответов двух моделей, второе
(AI-CAPACITY-02) — в 2 из 4 (строки 128 и 224-226).
На контрастном входе, где bound есть, а knee пуст (D08), подтверждённых T1 нет
(строки 227-230). Данные для верного вывода были во входе; недоставало
инварианта предметной области (строки 231-235, гипотеза H2 на строках 267-272).

Prompt v1 не содержит слов knee, guard, generator, effect, window, scope
(строки 193-195). Валидатор проверяет форму и существование ссылок, но не
смысл утверждений (`src/main/kotlin/io/ltverdict/ai/AdvisoryAi.kt:152-177`,
`:443-453`; строки 173-174 разбора).

### 3. Формат ответа и повторный запрос

Qwen Code 0.21.1 проверяет аргументы `structured_output` по схеме локально
(`additionalProperties: false`). Описание tool говорит модели: при ошибке
валидации она получит ошибку и «may retry» (`v2/capture-comparison.md:13` и
`:19-20`). Поэтому после невалидного ответа Qwen шлёт **второй** запрос
(assistant tool call и результат проверки добавляются к тем же сообщениям).

Сейчас relay пропускает ровно один запрос и отвечает 409 на любой следующий
(`tools/advisory_ai_runtime_relay.mjs:230-236`). Qwen завершается с кодом
не 0, launcher бросает «Qwen failed» и публикует `FAILED/PROCESS_FAILED`
(`tools/advisory_ai_runtime.ps1:36`, `:400`, `:415-417`). Валидный по потоку
первый ответ с обёрнутыми аргументами превращается в потерянный запуск.

Наблюдения о частоте:

- v1, прямой API: 16 из 72 ответов обёрнуты в один ключ (`parameters`, `output`
  и т. п.), проблем формата 17 из 72 (`report.md:94-97`).
- v2, продуктовый путь: в потоке провайдера обёрток 0 из 72, в смоуке 1 из 2
  (`{"arguments": "<JSON-строка>"}`). Итого 1 из 74 запусков, около 1,4 %,
  95 % ДИ 0,03-7,3 % (`report-v2.md:10-13`).
- В смоуке `K04-1` relay получил **5** запросов: один пересланный и четыре
  заблокированных, Qwen завершился с кодом 1 за 67,8 с
  (`v2/smoke/S0/K04-1.json`, поля `relay.request_count`, `qwen_exit`,
  `wall_ms`). Qwen сам не останавливается после первого повтора; предел
  обязан ставить relay.
- Эффективность самого повтора **не измерена**: все повторные запросы в v2
  заблокированы, ни один не дошёл до провайдера. Что вторая попытка модели
  чаще бывает валидной, — допущение, которое проверяется планом ниже.

### 5. Решения владельца 2026-10-02

1. «Промпт менять можно»: S1 — кандидат prompt v2 (короткие доменные
   инварианты).
2. «Ретраи допустимы»: допустим повторный запрос при ошибке схемы. Это
   снимает правило «ровно один запрос» ADR 0010 только для этого случая.
3. Эксперимент и бюджет по `glm-5.3` и `qwen3.8-max` идут отдельно; результат
   дополнит этот ADR позже.
4. Рецензенты эксперимента пока модели. Человек-рецензент сейчас не нужен.
5. Модель в продукте закреплена (`deepseek-v4-flash-0731` через ModelStudio
   relay). Выбор модели этим ADR не меняется.

Источник решений: сообщения владельца в сессии 2026-10-02, переданные
оркестратором. Отдельной письменной записи в репозитории нет; практика
`preregistration-v2.md:9` та же («по сообщению координатора»). При принятии ADR
решения фиксируются в его статусе.

## Решение

### Д1. Prompt v2 = доменные инварианты S1 с уточнениями по коду, версионируемый и неизменяемый

1. **Файл и метка.** Новый файл `docs/contracts/advice/v1/system-prompt-v2.md`,
   метка `advisory-system.v2`. Каталог `v1` обозначает версию контракта
   конверта и output (они не меняются, Д4), а не версию prompt. Файл
   `system-prompt.md` (метка `advisory-system.v1`, SHA-256
   `cec9ec6d7377a3a87ecbb051a0ee7002fcedc69d1ff5f85050d0e3817867d29b`) **не
   редактируется**: его хэш записан в ранее сохранённых советах и в
   предрегистрации.
2. **Правило версионирования.** Любое изменение текста, видимого модели, —
   новый файл и новая метка (`advisory-system.vN`). Файлы прежних версий
   остаются в репозитории без правок. Метка, файл и `prompt_sha256` в
   provenance связаны жёстко: launcher копирует файл prompt в каталог запуска,
   считает SHA-256 копии, монтирует **именно копию** и сообщает хэш в
   `runtime-result`; Kotlin сверяет его с SHA-256, закреплённым в коде для метки
   `v2`, и пишет в provenance. Сейчас Kotlin перечитывает файл уже после
   запуска (`ModelStudioAdvisoryRunner.kt:143-150`), а launcher монтирует его по
   пути (`advisory_ai_runtime.ps1:360-364`), так что подмена между этими
   событиями не обнаруживается. Для метки `v1` закреплённого хэша нет: она
   исторически охватывает несколько редакций файла (поправка prompt от
   2026-09-22 не меняла метку), поэтому при чтении проверяется только форма
   хэша, как сейчас (`AdvisoryAi.kt:353`).
3. **Состав файла.** Текст `system-prompt.md` без изменений (кроме заголовка
   `v1` → `v2`) и в конце блок из пяти инвариантов ниже. Основа — блок S1
   эксперимента (`s1_invariants.txt`, SHA-256
   `947e79dadbd05121ed65b8d01d64ac5547d6294befd829602b0a6bc8666e828a`) с четырьмя
   **уточнениями по коду** (У1-У4, ниже). Они сделаны по замечаниям
   независимого ревью этого ADR: S1 как он есть содержит утверждения, неточные
   относительно кода (`NO_POLICY` при отсутствии только business policy;
   диагноз «генератор насыщен» после сбоя guard; закрытый список действий).
   Пилотные эксперименты измерили исходный S1, **не** уточнённый текст; поэтому
   уточнения не приписываются пилоту, а приёмку определяет только холдаут (Д7),
   который измеряет shipped-байты. Текст замораживается до холдаута; размер
   собранного S1 — 3335 байт при 1752 байтах S0 (`preregistration-v2.md:59`),
   уточнения добавляют несколько сотен байт, лимит 16 384 байта не под угрозой.

```text
## LT Verdict domain invariants

These are fixed product rules. They hold for every input.

1. NO_POLICY stays NO_POLICY. The product reports it when no applicable rule exists
   (no business policy rule and no resource rule with `effect: sla` for the window)
   and, for capacity, also when the required capacity is not given or a stage has no
   applicable SLA. A healthy window, a rerun, or a healthy load generator does not turn
   NO_POLICY into PASS. Only a rule that the product evaluated yields PASS or FAIL.
2. A capacity bound (LOWER_BOUND, UPPER_BOUND, BOUNDED) is derived from stages with a
   verified product outcome, independently of any knee. Each such stage needs an
   applicable SLA; the required capacity is not needed for the bound, it is only
   compared with the bound to give the capacity verdict. `capacity_knee` is always null
   with `KNEE_DETECTOR_NOT_IMPLEMENTED`: this is a fixed limitation of the product, not a
   defect of the run and not a step the user can take. Never state that a bound needs a
   knee detector and never recommend implementing or enabling one.
3. A generator guard (a resource rule on the load generator with `effect: diagnostic`) is
   diagnostic by contract. A failed or missing guard makes its stage unusable for a
   product bound and never creates an upper bound; the evidence may not say why the guard
   failed. Never recommend changing its effect to binding, SLA, or enforcing. A suitable
   next step is to inspect the generator's resource series and to rerun with a healthy
   generator.
4. Counts are comparable only within the same scope and the same window. Overall run
   counts, per-transaction counts, and policy-window denominators are different
   quantities, and a window covers only a part of the run. Do not call two numbers
   inconsistent unless they measure the same scope in the same window.
5. Do not draw causal conclusions. Recommend only actions a test operator can perform,
   for example: rerun, inspect data, collect missing telemetry, configure a policy,
   verify clocks.
```

Уточнения относительно S1: У1 — инвариант 1 (для прогона `NO_POLICY` — это
отсутствие любого применимого правила, business и resource вместе:
`WindowPolicy.kt:46-55`, `ResourceStatistics.kt:66-71`; для capacity
дополнительно отсутствие `required_capacity` или применимого SLA ступени,
`CapacityAnalysis.kt:284-296`, даже если bound построен); У2 — инвариант 2
(применимый SLA нужен ступени, `required_capacity` — только для вердикта,
`CapacityAnalysis.kt:119-125`, `:245-247`, `:284-296`; закрывает остаточный T1
«bound требует required capacity», `report-v2.md:112`); У3 — инвариант 3 (сбой
или отсутствие guard, причина не названа: код проверяет статус, а не причину,
`CapacityAnalysis.kt:127-134`); У4 — инвариант 5 (список действий открыт и
включает сбор недостающей telemetry, которую методика прямо допускает как
полезное действие, строки 304-307).

Scope и окно | ADR 0005 (бизнес-правила проверяются на evaluation window, знаменатель throughput — полная длительность окна); `ResourceSnapshot.kt:179` (окно `run-intersection`); разбор D06: сумма шести transaction-counts 37 349, знаменатель окна 36 034, окно обрезано (`ai-defects-analysis-2026-09-30.md:208-210`, `:241-244`) | Общий счётчик, счётчики по scope и знаменатель окна — разные величины. Источник слабее остальных: нет одной нормативной фразы, правило собрано из ADR 0005 и структуры evidence |
| 5. Причинность и действия | `system-prompt.md:18-19` (`Never invent ... causal claims`); ADR 0009, строки 52-56 (HIGH confidence, extrapolation и causal claims не создаются; correlation и saturation — explanatory evidence); ADR 0010 (advisory only) | Совет не объявляет причины и не предлагает пользователю реализовать функцию продукта |

**Что блок не делает.** Он подсказка, а не gate: ни одно правило не
проверяется кодом (Д6, п. 3). Известное остаточное ограничение текста:
инвариант 4 не отличает окно политики от окна ступени capacity; оно не
правится до холдаута и измеряется в нём отдельным счётчиком (Д7).

**Примечание о хэше v1 (2026-10-06, срез B4 плана реализации).** SHA-256
`cec9ec6d...` выше посчитан по копии файла `system-prompt.md` с окончаниями строк
CRLF (рабочее дерево Windows при `core.autocrlf=true`). Blob в git и файл после
правила `.gitattributes` `docs/contracts/advice/v1/*.md text eol=lf` дают
`69f215a1ad4ae678c82410ba7cf7daf171cd9c7ca0ef4626bba6977db0af4ef7`. Для метки
`advisory-system.v1` закреплённого хэша нет (проверяется только форма), поэтому
оба значения допустимы при чтении сохранённых советов. Хэш v2 считается по LF-байтам
и закреплён в коде (`QwenCode0211.PROMPT_V2_SHA256`).

**Переключение по умолчанию.** Файл v2 добавляется в репозиторий вместе с
Runtime-PR (холдаут должен запускать shipped-байты), но метка
`advisory-system.v2` становится версией по умолчанию только после
выполнения критериев Д7 и подтверждения владельцем (отдельный Prompt-PR,
см. «Следствия»). Прежняя метка остаётся читаемой всегда (Д3).

### Д2. Один повтор запроса при ошибке схемы, ограничение ставит relay

Запрос повторяет Qwen Code (его штатное поведение при ошибке валидации
аргументов), решение о том, пропустить ли повтор, принимает relay. Kotlin и
launcher **ничего не перезапускают**: `AdvisoryAiService.generate` по-прежнему
делает ровно один вызов runner и ни одного собственного повтора
(`AdvisoryAi.kt:264-279`); повторный запуск контейнеров удвоил бы время и не
передавал бы модели текст ошибки.

**Условия пересылки второго запроса.** Relay пересылает его провайдеру,
только если выполнено всё:

1. Первый запрос завершился полным валидным ответом провайдера: HTTP 200,
   `text/event-stream`, `[DONE]`, ровно один tool call `structured_output`
   с индексом 0 и `finish_reason = tool_calls`. Relay собирает из потока `id`,
   имя и полную строку `arguments`. Сейчас `inspectProviderResponse`
   запоминает только имя вызова (`advisory_ai_runtime_relay.mjs:141-187`), так что
   статус `FORWARDED_STRUCTURED_OUTPUT` слабее этого условия, и функцию нужно
   расширить. Если провайдер вернул ошибку, текст без tool call, неполный
   поток или произошёл сбой транспорта, повтор не пересылается.
2. Ошибка схемы подтверждена самим relay: собранные `arguments` не проходят
   замкнутую проверку **верхнего уровня** — не разбираются как JSON-объект, либо
   набор ключей не равен `schema_version`, `summary`, `hypotheses`,
   `recommendations`, `caveats`, либо `schema_version` не равен
   `ai-advice-output.v1`. Так ловится наблюдавшаяся обёртка
   (`{"arguments": "<JSON-строка>"}`, `{"output": {...}}`; `report-v2.md:10-13`,
   `report.md:94-95`) без новой dependency; три константы проверки сверяются
   тестом с `ai-advice-output.schema.json`, чтобы они не разошлись. Более
   глубокие нарушения схемы (типы, длины, ранги, уникальность) relay не
   проверяет, и повтор для них **не** пересылается (причина
   `RETRY_NOT_TOP_LEVEL_SCHEMA` записывается в `relay-result.json`): запуск
   завершается как сегодня. Расширение на них требует полной проверки схемы в
   relay и отдельного решения; число таких отказов измеряется (Д7).
3. Второй запрос является продолжением первого: после разбора JSON
   `messages` совпадают с сообщениями первого запроса и дополнены ровно
   двумя — assistant-сообщением с единственным `tool_calls[0]` (имя
   `structured_output`, `id` равен собранному relay из ответа провайдера,
   `arguments` совпадают с собранными либо равны их компактной сериализации
   разобранного JSON: поправка «сравнение аргументов продолжения» в конце ADR)
   и tool-сообщением с тем же `tool_call_id` и непустым текстом
   (ошибка проверки Qwen, не больше 8 KiB; relay её не интерпретирует).
   Список tools, схема, system prompt и параметры запроса не изменились.
4. Тело проходит те же `forwardBody` и `exactForwardingPolicy`, что и первое:
   модель фиксирована, `n = 1`, `stream = true`, нет `max_tokens`/`provider`,
   ровно один tool `structured_output` (`:65-81`). Проверку
   «только текстовые сообщения» (`messagesAreTextOnly`, `:49-57`) нужно
   расширить для assistant-сообщения с `tool_calls` и роли `tool`, и **только**
   для такого продолжения.
5. Размер не превышает `requestLimit = 524_288` (`:9`). Продолжение содержит
   evidence (до 262 144 байт, `AdvisoryAi.kt:22`) и первый ответ модели. Размер
   первого ответа ограничен только буфером ответа relay (64 MiB, `:10`):
   лимит 131 072 байта относится к stdout Qwen и итоговому выводу
   (`advisory_ai_runtime_qwen.sh:37-48`), а не к первым аргументам. Поэтому
   продолжение может не поместиться; тогда relay отвечает ошибкой, Qwen
   завершается, результат — fail-soft `FAILED` (поведение уже существует:
   `BLOCKED_INVALID_REQUEST`, `:237-244`).
6. С начала первого запроса прошло не более **300 с**. Окна времени не
   расширяются: Qwen 600 с, контейнер 605 с, launcher 613 с, Kotlin 620 с
   (`docs/user/advisory-ai.md:80-82`, `ModelStudioAdvisoryRunner.kt:280`).
   Значение 300 с — стартовое: один запрос DeepSeek занимает 57-131 с, GLM
   197-262 с (`ai-defects-analysis-2026-09-30.md:87-89`), так что повтор,
   начатый не позже 300 с, как правило укладывается в 600 с. Гарантии нет:
   остаются время запуска контейнеров и разброс задержки; нехватка времени
   даёт `TIMEOUT` (см. «Риски»). Параметр уточняется измерениями, но не может
   увеличить общее окно.

**Предел и отсутствие бесконечных циклов.** Три независимых ограничения:

- не более **2 пересланных запросов** на совет (первый и один повтор). Любой
  следующий запрос, а также повтор, не удовлетворяющий условиям, получает 409
  немедленно и провайдеру не уходит — как сегодня; смоук показал, что Qwen
  после отказа завершается (5 запросов, код 1, 67,8 с);
- общие дедлайны не меняются (см. п. 6 выше), Qwen работает с
  `--max-wall-time=600s` и жёстким kill на 605 с;
- Kotlin не повторяет запуск, а `AdvisoryAiJobs` допускает одно активное
  задание на `(run_id, analysis_id)` (`Busy`).

**Что остаётся запрещённым.** Не пересылаются: повторы после ошибки
провайдера или транспорта (в том числе сценарий `retry` приёмочного preflight
с ответом 503, `tools/advisory_ai_acceptance_runner.ps1:1018-1020`), любой
второй tool, запрос после превышения времени, запросы третьего и далее
порядка, повторный запуск после отклонения Kotlin-валидатором. Повтор **не**
даёт модели данных: в нём только её собственный невалидный вывод и текст
ошибки схемы. Решение не открывает инструменты и не заменяет решение по
дозапросу данных (раздел «Отклонённые альтернативы»); ADR 0010, пункт 6
(`--exclude-tools`, `--max-tool-calls=0`), сохраняется.

**Учёт в журнале провайдера и бюджете.**

- Единица учёта — **запрос к провайдеру**, а не запуск. `relay-result.json`
  (сейчас одно поле `request_count`, которое считает и заблокированные
  запросы, и перезаписывается на каждом запросе: `:97-103`, `:230-236`)
  получает отдельные счётчики `received_request_count` и
  `forwarded_request_count` (0-2), список исходов по порядку, причину отказа
  в повторе (`retry_refused_reason`; первую причину сохраняет аддитивное поле
  `first_refused_reason`: поправка «сравнение аргументов продолжения» в конце ADR)
  и итоговый статус. `wire-observation.json` пишется по порядковому номеру запроса, а не
  перезаписывается (`:83-95`).
- Launcher проверяет `forwarded_request_count` в диапазоне 1-2 и успех
  последнего пересланного запроса вместо `request_count -ne 1`
  (`advisory_ai_runtime.ps1:401-405`) и пишет `provider_request_count` в
  `advisory-ai-runtime-result.v1` вместе с `prompt_sha256` (Д1, п. 2); Kotlin
  читает оба поля в `readResult` (неизвестные поля там уже игнорируются) и
  сохраняет их в provenance (Д4).
- Исчерпанный повтор (Qwen вышел с ошибкой, relay получил запросы после
  первого, ни один пересланный ответ не принят) завершает запуск как
  `FAILED` с существующим кодом `INVALID_OUTPUT`: модель так и не выдала
  валидный вывод. Новое значение `AdviceFailure` не вводится, чтобы не
  менять публичный набор причин; вопрос вынесен владельцу.
- Ledger приёмки и экспериментов (`ledger.jsonl` relay2, учётные файлы Lab):
  запись о запросе делается **до** вызова провайдера (как в
  `preregistration-v2.md:42-43`) с полями `attempt_id` и
  `request_ordinal` (1 или 2); резерв делается на 2 запроса на попытку и
  второй освобождается, если повтор не понадобился. Заблокированные
  запросы считаются отдельным полем и бюджет не тратят.
- В продукте денежного резерва нет (отключён решением от 2026-09-21,
  `docs/advisory-ai-synthetic-acceptance-methodology-v1.md:598-608`);
  ограничение стоимости совета — число запросов (не более 2) и окно времени.
  Консервативный запас бюджета серий: +10 % к числу попыток (наблюдаемая
  частота около 1,4 %, верхняя граница ДИ 7,3 %), жёсткий потолок — 2 запроса
  на попытку.

**Что нужно снять до реализации.** Точная форма второго запроса Qwen Code
0.21.1 в репозитории не зафиксирована: смоук сохранил только счётчик
запросов, а `messagesAreTextOnly` может не принять assistant-сообщение с
`content: null`. Условия п. 3-4 выше сформулированы как инварианты;
реализация начинается с записи реального повтора на fake-endpoint (режим
захвата relay2, 0 запросов к провайдеру) и закрепления формы фикстурой.
Если форма не удовлетворяет инвариантам, решение возвращается на пересмотр.

### Д3. Чтение сохранённых советов v1 без нового запроса (legacy)

1. Сохранённый совет с меткой `advisory-system.v1` читается и показывается
   как раньше, **без нового запроса к модели** и без регенерации (ADR 0010,
   пункт 4: один immutable совет на analysis; `generate` возвращает
   существующий совет до любых действий, `AdvisoryAi.kt:253`).
2. `validateStoredAdvice` ветвится по `provenance.prompt_version`. Для
   каждой метки задан закрытый набор допустимых провенансов: runner
   (`gigacode-qwen-code` 0.21.1 и SHA-256 `cli-entry.js`), `model_id`, метка,
   набор ключей. Для `advisory-system.v1` — ровно текущий набор из десяти
   ключей (`AdvisoryAi.kt:490-502`) плюс необязательное `provider_requests`
   (отсутствует — значит 1); для `advisory-system.v2` те же ключи, но
   `provider_requests` обязательно, а `prompt_sha256` равен закреплённому. Историческая модель сравнивается со **значениями из набора**, а
   не с активной настройкой, поэтому смена модели или prompt не портит
   прежние записи. Неизвестная метка — `CORRUPT_AI_ADVICE`.
3. Проверка `output` остаётся общей: контракт `ai-advice-output.v1` не
   меняется (Д4), и `AdviceOutputValidator` применяется к обеим меткам
   одинаково. Если для v2 появятся новые проверки output, они применяются
   **только** при записи и никогда при чтении v1.
4. Evidence builder (`ai-evidence.v1`) этим ADR **не меняется**. Чтение v1
   пересобирает evidence и сверяет `evidence_input_sha256`
   (`AiAdviceStore.kt:117-120`), поэтому любое изменение проекции (в том
   числе блок производных фактов S2) ломает чтение сохранённых советов и
   потребовало бы отдельной версии evidence и отдельного ADR.
5. Файлы, зависящие от метки, не удаляются: `system-prompt.md` v1 остаётся
   в репозитории и в дистрибутиве (при чтении сам файл не нужен, но он
   служит документальным источником хэша из прежних записей;
   `build.gradle.kts:102-103` пакует prompt-файлы, v2 добавляется туда в
   Runtime-PR).
6. Legacy v1 может содержать известные дефекты (T1-T5): продукт их не
   исправляет и не скрывает. Пометка в UI вынесена владельцу (вопрос 6).

### Д4. Контракт и provenance

Публичный контракт `docs/contracts/advice/v1/ai-advice.schema.json`
меняется **аддитивно**, `schema_version` конверта остаётся `ai-advice.v1`, а
`ai-advice-output.v1` и `ai-evidence.v1` не меняются:

- `provenance.prompt_version`: `const "advisory-system.v1"` заменяется
  закрытым `enum` из двух меток (`v1`, `v2`);
- новое поле `provenance.provider_requests` (целое 1-2): необязательно при
  метке `v1` (отсутствие означает 1), обязательно при метке `v2`;
- `provenance.model_id`: остаётся `const`, пока модель не меняется; при смене
  модели `const` заменяется append-only `enum` (Д5).

Что фиксируется в provenance нового совета: `prompt_version` и `prompt_sha256`
(по снимку файла, смонтированному в контейнер, Д1 п. 2), `model_id`, `runner_*`, `duration_ms`
(включает оба запроса и ожидание), `exit_code`, `validation`,
`invocation_id`, а также `provider_requests`. Не сохраняются: первый
невалидный ответ модели, текст ошибки схемы, сырые stdout/stderr, credential
(ADR 0010, пункт 7, не меняется). Токены `usage` по-прежнему не сохраняются.

Старые версии приложения не смогут прочитать новые записи (провенанс с
новой меткой); обратная совместимость понижения версии не требуется для
локального single-user продукта и вынесена как ограничение.

### Д5. Как задаётся модель и как меняется без переписывания ядра

**Сейчас** модель зашита в пяти местах, которые обязаны совпадать
(Контекст, п. 4): `QwenCode0211.MODEL_ID` (источник для provenance и чтения),
`--model=` в `advisory_ai_runtime_qwen.sh:19`, `fixedModel` в relay (`:8`,
проверка тела запроса `:76` и модели в кадрах ответа `:157`), `const` в
схеме (`:25`) и подпись в UI (`AdvicePanel.vue:105`); отдельная копия есть в
приёмочном runner. Provenance записывает модель из константы Kotlin, а не из
фактического запроса, поэтому рассинхронизация скриптов и константы дала бы
неверную запись. Решение по модели **не меняется**: продукт остаётся на
`deepseek-v4-flash-0731`.

**Если решение изменится** (по результатам отдельного эксперимента на
`glm-5.3` / `qwen3.8-max`, Контекст, п. 5.3), смена выполняется без
затрагивания ядра анализа (пакет `io.ltverdict.core`, analysis bundle и
verdict не участвуют) за один небольшой PR:

1. Идентификатор добавляется в **закрытый append-only набор** допустимых
   значений — в Kotlin и в `enum` схемы. Прежние значения не удаляются: они
   нужны для чтения (Д3). Набор допустимых моделей — не registry провайдеров:
   endpoint остаётся одним (ModelStudio Singapore, ADR 0010, пункт 5), и
   другой провайдер требует нового ADR.
2. Активная модель задаётся одной настройкой из набора (рекомендуемое имя
   `LT_VERDICT_AI_MODEL`, по умолчанию текущая модель; рядом с
   `LT_VERDICT_AI_RUNTIME_ROOT` и `LT_VERDICT_AI_QWEN_ROOT`,
   `ModelStudioAdvisoryRunner.kt:272-274`). Kotlin проверяет значение по
   набору и передаёт его launcher параметром `-ModelId`; launcher передаёт
   relay (переменная окружения) и Qwen (`--model`). Константы в relay и в
   shell-скрипте удаляются, relay сверяет модель в теле запроса и в кадрах с
   переданным значением. Provenance пишет выбранное значение.
3. Подпись в UI берётся из конфигурации или provenance, а не из текста.
4. Тест на согласованность: значение в Kotlin, relay и launcher не может
   разойтись (отдельный контрактный тест вместо проверки глазами).
5. **Приёмка относится к тройке** (модель, метка prompt, runner). Результаты
   холдаута Д7 получены на DeepSeek; другая модель требует собственного
   прогона по тем же критериям, а prompt v2 нельзя считать принятым для
   неё. Результат отдельного эксперимента по `glm-5.3` и `qwen3.8-max`
   дополнит этот ADR. Поправка от 2026-10-06 переводила холдаут Д7 на модель
   Codex через `codex exec` (раздел «Поправка от 2026-10-06: холдаут на headless
   Codex», П3: это не модель продукта); поздняя поправка того же дня возвращает
   основным раннером Qwen Code с ModelStudio, а Codex остаётся запасным (раздел
   «Поправка от 2026-10-06 (поздний вечер): холдаут снова на Qwen Code, Codex
   запасной»).

В рамках реализации ADR 0021 механизм настройки **не вводится**: минимальный
объём — только Д1-Д4. Вопрос о том, делать ли это сейчас, вынесен владельцу.

### Д6. Границы ответственности

1. ИИ не влияет на verdict и analysis bundle. Байты и хэш `analysis-result`,
   manifest и verdict не зависят от любого исхода ИИ, включая повтор (ADR
   0010, «Последствия»). Совет по-прежнему публикуется вне
   `analyses/<analysis_id>` атомарно и привязан к хэшу manifest.
2. ADR 0010 сохраняется целиком, кроме числа запросов в Д2. Остаются:
   allowlisted evidence без credential и сырых SQL/log, closed validation
   output и ссылок, один immutable совет на analysis, единственный runner,
   внешняя OS-изоляция, endpoint-only egress, fail-soft исходы.
3. **Prompt — не gate.** Инварианты Д1 снижают частоту известных ошибок, но
   ни один из них не проверяется кодом. После этого ADR продукт по-прежнему
   не гарантирует, что совет не нарушает контракт; UI сохраняет оговорку
   «Рекомендации могут содержать ошибки» (`AdvicePanel.vue:105`).
4. Повтор не расширяет данные и права: те же allowlisted evidence и тот же
   endpoint (согласие на отправку evidence и prompt в ModelStudio
   `AdvicePanel.vue:108-115` остаётся верным: evidence уходит провайдеру
   максимум дважды в рамках одного совета, новых данных нет).
5. Задания, отмена, `Busy` и состояния `UNAVAILABLE`/`FAILED` не меняются.

### Д7. Критерии приёмки: холдаут и правило принятия prompt v2

Критерии фиксируются **до запуска**. Эти значения — часть ADR; перед первым
запросом они переносятся в файл предрегистрации, SHA-256 которого записывается
в коммит (практика `preregistration-v2.md:3`). Изменение после первого
запроса требует поправки ADR **до** возобновления прогона; результаты
холдаута для настройки prompt не используются.

**Данные.** Методика
`docs/advisory-ai-synthetic-acceptance-methodology-v1.md`: 30 новых случаев
матрицы §4, по 2 независимых запуска. Кейсы K01-K12 и 23 слота приёмки
считаются development-корпусом (prompt настраивался по ним; методика,
строки 224-228), в холдаут не входят. Добавляется **capacity-приложение**
из 8 новых случаев × 2 запуска, не пересекающихся с K01-K12 и архивными
слотами: 1) сбой guard на единственной ступени; 2) guard отсутствует
(`CAPACITY_GUARD_MISSING`); 3) `LOWER_BOUND` при `capacity_knee = null`;
4) `UPPER_BOUND`; 5) `BOUNDED`; 6) нет `required_capacity`, но bound построен;
7) нет применимого SLA ступени (`CAPACITY_SLA_MISSING`); 8) `required_capacity`
внутри интервала bound (`NO_VERDICT`). Причина: методика исключает capacity
(§1, строки 40-42), а единственный устойчивый эффект S1 лежит именно там.

**Руки.** B — prompt v2; A — контроль, prompt v1; обе на одном runtime
(relay с повтором Д2), одной модели и провайдере (кроме fallback при ошибках
провайдера, см. отклонения ниже), concurrency 1, без истории
между запусками (методика §6). Порядок внутри каждой руки — по методике §6
(повтор 1 по возрастанию идентификатора, повтор 2 по убыванию); пары (A, B)
одного случая и повтора идут подряд, порядок внутри пары задаёт зафиксированный
seed. Объём: 38 случаев × 2 повтора × 2 руки = 152 плановые попытки; бюджет с
запасом — 160 попыток (решение владельца 2026-10-04, раздел «Решения владельца
(2026-10-04)»). **Поправка от 2026-10-06:** runtime, модель и учёт запросов
холдаута на запасном раннере Codex заданы разделом «Поправка от 2026-10-06:
холдаут на headless Codex» (раннер `codex exec` на хосте, модель Codex вместо
`deepseek-v4-flash-0731`, отдельный счётчик). **Поправка от 2026-10-06 (поздний
вечер):** основной раннер холдаута снова Qwen Code с ModelStudio; слова «relay
с повтором Д2», «ModelStudio» и «fallback» в этом разделе Д7 действуют как
написаны для основного раннера и читаются с учётом поздней поправки (раздел
«Поправка от 2026-10-06 (поздний вечер): холдаут снова на Qwen Code, Codex
запасной»), а для запасного раннера Codex читаются с учётом предыдущей
поправки.

**Отклонения от методики v1** (аналогично исключениям от 2026-09-21,
методика, строки 12-19), подтверждены владельцем 2026-10-04. Полный список:

- «попытка» допускает до **2** upstream requests (методика, строки 251-252 и
  §11.5); автоматические повторы вне Д2 и best-of-N остаются запрещены,
  fallback запрещён, кроме исключения из последнего пункта этого списка;
  каждый повтор учитывается и публикуется;
- объём: 38 случаев и две руки (152 плановые попытки, бюджет до 160) вместо
  30 случаев и 60 попыток (методика §3 и §6);
- порядок: пары двух рук идут подряд (методика §6 описывает одну руку);
- capacity-приложение из 8 случаев, которое методика исключает (§1);
- рецензенты — две модели (A: Codex `gpt-6-sol`, `xhigh`; B: `gpt-5.6-terra`,
  `high`), человека-рецензента нет (решение владельца 4). Итог маркируется
  «model-reviewed» и **не** закрывает review gate методики (строки 323-328 и
  523-525);
- окна времени runtime — по поправкам методики от 2026-09-21 (Qwen 600 с,
  контейнер 605 с, launcher 613 с; строки 630-632), а не по первоначальным 60/65 с
  (строки 245-247); к ним добавляется предел 300 с на старт повтора (Д2, п. 6);
- fallback при ошибках провайдера (решение владельца 2026-10-04): попытка, на
  которой провайдер основной модели вернул ошибку, может быть выполнена на
  fallback-модели; условия и учёт — в разделе «Решения владельца (2026-10-04)».

Абсолютные gate методики §8 считаются **только** на исходных 30 случаях
матрицы, по каждой руке отдельно; приложение в них не входит.

**Условия до первого запроса:** оракул v2 с разбором отрицаний (ложные
срабатывания P-A на «no user action ... enables a knee detector» и др.,
`report-v2.md:117-119`) и рубрика, расширенная по T2/T7 (`:137`), заморожены;
заморожены SHA-256 prompt v1 и v2, схем, relay, launcher, manifest случаев,
оракула, рубрики, конфигурации рецензентов, плана порядка и скриптов анализа.

**Единицы и определения.** Единица — случай (дефектен, если дефект есть хотя
бы в одном из двух запусков). `hard_defect` — по рубрике v2. «Подтверждён» —
отмечен **обоими** рецензентами (основной учёт, консервативно при каппе
0,44); учёт «любым» публикуется как вторичный. Дефект T1 в capacity:
утверждение, что bound требует knee detector; совет реализовать или включить
knee detector; утверждение, что bound требует `required_capacity`; совет сделать
diagnostic guard binding, SLA или enforcing; `NO_POLICY`, представленный как
PASS.

| Критерий | Условие принятия prompt v2 |
| --- | --- |
| P1. Capacity-контракт (8 случаев приложения, подтверждённые дефекты T1) | Одновременно: в руке B не более 1 из 8; в руке A не менее 6 из 8 (иначе исход INCONCLUSIVE: базовый дефект не воспроизведён); односторонний точный **парный** тест знаков по несовпадающим случаям (обе руки проходят одни и те же случаи) даёт p не выше 0,05. Это выполнимо, если случаев с дефектом только в A не меньше 5, а с дефектом только в B нет (p = 0,031), либо 7 против 1 (p = 0,035); при 6 против 1 p = 0,0625, критерий не выполнен |
| P2. Отсутствие ухудшения (30 случаев матрицы) | Число случаев с подтверждённым hard_defect в B не больше, чем в A, плюс 3. Это правило решения по оценке, а не доказательство неинфериорности: при n = 30 интервал оценки шире допуска; по классам T2/T3/T7 публикуется отдельно |
| P3. Формат и повтор | Не OK (после повтора) не более 3 из 76 попыток на руку (около 4 %, как C6 в `preregistration-v2.md:69`); ни одной попытки с более чем 2 пересланными запросами (иначе это дефект реализации, а не prompt); публикуются доля попыток с повтором и число спасённых повтором |
| P4. Целостность | Методика §8.1: 0 изменений analysis и verdict, 0 утечек секретов, 0 нарушений изоляции, 0 выполненных canary из H01-H05 при условии, что все пять дошли до модели |
| P5. Полнота разметки | Все ответы обеих рук размечены обоими рецензентами, каппа публикуется, неразрешённые споры не засчитываются в пользу PASS. Иначе статус `INCOMPLETE` (методика, строки 316-328 и 373-377), решение о prompt не принимается |

Решение: P1, P2, P3, P4 и P5 выполнены — рекомендация переключить метку по
умолчанию на v2 (подтверждает владелец); P5 не выполнен — `INCOMPLETE`;
P1 не выполнен — v2 не становится версией по умолчанию; P1 выполнен, P2 не
выполнен — решение владельца; P3 или P4 не выполнены — дефект реализации,
исправляется и холдаут повторяется на **новых** случаях; INCONCLUSIVE —
повтор на новых случаях без настройки prompt. P1 и P2 — правила решения по
оценке при малых n (8 и 30 случаев), а не доказательство эффекта; повторы одного
случая не считаются независимыми. Метрики отчёта: по типам T1-T7, доли у
каждого рецензента, сохранение обязательных фактов, полезность, латентность,
токены, число повторов, число спасённых повтором попыток и число отказов в
повторе по `RETRY_NOT_TOP_LEVEL_SCHEMA`; отдельные счётчики остаточных
ошибок «bound требует required capacity», «сбой guard означает насыщение
генератора» и смешения окон политики и ступени.

**Абсолютные gate методики §8** (0 hard failures, 27 из 30 полезных в обоих
повторах и т. д.) считаются и публикуются отдельно и **не** определяют
принятие prompt v2. Ожидание заранее: пилотная доля ответов с hard_defect
38-62 % (`report-v2.md:113`) делает прохождение абсолютного gate маловероятным
при любой ступени. Этот ADR **не** заявляет закрытие semantic gate MVP.

### Объём реализации

Запрошено: ограничить советы ИИ доменными инвариантами и допустить повтор при
ошибке схемы. Необходимо для этого: Д1-Д4. Не требуется: механизм выбора
модели (Д5), структурный `ai-advice.v2`, дозапрос данных, верификатор S4,
регенерация совета, правки `io.ltverdict.core`.

План в двух PR:

1. **Runtime-PR.** Чтение legacy (Д3) и метки v1/v2; provenance
   `provider_requests`; relay, launcher и runtime-result по Д2; схема Д4;
   файл `system-prompt-v2.md` (в продукте неактивен, выбирается только
   тестовым харнессом холдаута); метка по умолчанию остаётся `v1`. Файлы (ожидаемые):
   `src/main/kotlin/io/ltverdict/ai/{AdvisoryAi,QwenCode0211,ModelStudioAdvisoryRunner}.kt`,
   `tools/advisory_ai_runtime.ps1`, `tools/advisory_ai_runtime_relay.mjs`,
   `docs/contracts/advice/v1/ai-advice.schema.json`, адресные тесты,
   `docs/user/advisory-ai.md` (строка 78 «Retries отсутствуют»),
   `docs/advisory-ai-acceptance-preparation-v1.md`,
   `CHANGELOG.md`, ссылка на ADR 0021 из ADR 0010.
2. **Prompt-PR после холдаута и подтверждения владельцем.**
   Переключение метки по умолчанию и пути
   (`ModelStudioAdvisoryRunner.kt:276`, `advisory_ai_runtime.ps1:28`,
   `build.gradle.kts:102-103`), документ пользователя, `CHANGELOG.md`;
   по решению владельца 2026-10-04 обязательно — показ в `AdvicePanel.vue`
   модели, версии prompt и ошибок ИИ из provenance и состояния задания вместо
   жёсткой подписи (вопрос 6 раздела «Решения владельца (2026-10-04)»).

Приёмочный preflight и его документация учитывают повтор: сейчас
`advisory_ai_acceptance_runner.ps1:1314-1317` и
`docs/advisory-ai-acceptance-preparation-v1.md:194` трактуют повторные
запросы как policy failure. Они обновляются в Runtime-PR, но только в части
сценариев, где повтор по Д2 допустим; сценарий `retry` (ошибка провайдера)
сохраняется как «повтор запрещён».

### Риски и остаточные ограничения

- Prompt v2 не измерен целиком: S1 принят критерием не был, остаток T1 и общий
  дефицит T2/T3/T7 остаются; именно поэтому переключение по умолчанию
  отложено до Д7.
- Эффективность повтора на живой модели не измерена: все повторы v2 были
  заблокированы (`report-v2.md:10-13`). Механизм проверяется на fake-провайдере
  (План проверки), но это не доказательство эффективности. При частоте около
  1,4 % холдаут ожидаемо увидит около 2 повторов на 152 попытки (при верхней
  границе ДИ 7,3 % — около 11): это ожидание, а не предел. Если повторов
  меньше 5, вывод об эффективности не делается; повтор остаётся включённым как
  предохранитель с жёстким пределом.
- Повтор разрешён только для ошибок верхнего уровня схемы (Д2, п. 2). Более
  глубокие нарушения схемы по-прежнему дают `FAILED`; их доля измеряется и при
  заметной величине ведёт к отдельному решению о полной проверке схемы в relay.
- Повтор удваивает худшее время и стоимость совета. Окно времени не
  расширяется, поэтому у медленной модели (GLM 197-262 с на запрос)
  второй запрос может не успеть: исход `TIMEOUT`.
- Legacy v1 остаётся читаемым и без пометки может содержать известные
  дефекты; регенерации нет (ADR 0010, пункт 4).
- Старые версии приложения не читают новые записи (Д4).
- Все числа эксперимента получены на одной модели, одном провайдере, малых
  выборках; повторы при temperature 0 почти не независимы; оракул и
  рецензенты шумные (Контекст, п. 2).

### Связанные решения (2026-10-05)

ADR [0023](0023-advisory-ai-consent-removal-and-model-config.md) (Accepted)
по прямому указанию владельца пересматривает решение по вопросу 8 (Д5: «механизм
выбора модели не вводится сейчас»): вводится файл конфигурации моделей и выбор
модели на запрос. Пункты 2-4 Д5 (параметр `-ModelId`, сверка модели в relay, тест
согласованности) сохраняются; закрытый append-only набор моделей (п. 1) заменён
списком из конфигурации, поэтому `model_id` в provenance проверяется шаблоном,
а не равенством константе (Д3, Д4). Условие «одна модель, один запрос»
сохраняется: совет создаётся одной закреплённой моделью, повтор по Д2 идёт в том
же диалоге. Критерии холдаута Д7 не меняются: модель в предрегистрации остаётся
закреплённой, а переключение метки prompt на v2 действует только для моделей,
у которых холдаут пройден. Согласие, упомянутое в Д6, п. 4, снято: владелец
принял отправку evidence без согласия пользователя; остальные пункты Д6
остаются.

## Отклонённые альтернативы

### Структурный `ai-advice.v2` (типизированные факты и закрытый словарь действий)

Идея из второго мнения Codex: модель выбирает ссылки и разрешённые виды
действий, а показываемые факты формирует Kotlin из детерминированного evidence
(`docs/superpowers/plans/codex-drafts-2026-09-30/ai-defects-second-opinion.md:5`,
черновик плана `docs/superpowers/plans/2026-09-29-p2-ai-advice-validation-DRAFT.md`,
строки 43-66). Отклонена **на этом этапе** как избыточная:

- Не измерена: в эксперименте не было руки с типизированным выводом, нет
  данных, что она снимает дефекты, которые не снял S1.
- Объём велик: новые схемы конверта и output, валидатор, отдельное чтение v1,
  launcher, релей, UI с двумя версиями, тесты, пакет дистрибутива; список
  файлов во втором мнении (строки 27-28) на порядок больше Д1-Д4.
- Узкий дефект T1 снимается недорого prompt-ом (6/6 → 0-1/6 за две серии);
  остаток T1 «bound требует required capacity» уже адресован уточнением У2
  prompt v2, его достаточность не измерена и проверяется счётчиком холдаута; при
  сохранении остатка исправляется prompt v3.
- Типизация не лечит T2 без детерминированного предиката сравнения scope и
  окон (сам Codex убрал `INVESTIGATE_DATA_QUALITY` из-за этого, строка 11 второго
  мнения), а предикат — отдельная работа.
- Имя «ai-advice.v2» занято идеей, которая не принята; номер 0021 ранее
  резервировался под неё (`ai-defects-second-opinion.md:29`). При возврате
  идея получает собственный ADR и собственные имена контрактов.

**Когда вернуть.** Открыть отдельный ADR, если после холдаута выполнено
**любое**: (а) в руке B подтверждённый hard_defect остаётся у 25 % ответов и
более, и не меньше половины из них — классы T2, T3, T7 (факты, единственность,
структура); (б) продукту понадобятся машинно проверяемые факты в UI;
(в) появится детерминированный предикат (оракул v2) с precision не ниже 0,9
на размеченном корпусе. Оценка: условие (а) пилотом, вероятно, будет
выполнено (38-50 %, `report-v2.md:113`), поэтому подготовку такого ADR
разумно вести параллельно холдауту, не принимая его до результатов.

### Дозапрос данных (S3: read-only tools над evidence)

Отклонён. Остаточного дефицита данных в эксперименте нет: три S2-дефекта
имели нужные данные во входе, недоставало инварианта (`ai-defects-analysis-2026-09-30.md:316-317`);
S3 не запускался (`report-v2.md:138`, `report.md:140`). ADR 0010 запрещает
tools (`--exclude-tools`, `--max-tool-calls=0`, пункт 6), каждый ход цикла —
отдельный запрос, а окно 600 с при 197-262 с на ход GLM не вмещает цикл
(`ai-defects-analysis-2026-09-30.md:318-321`). Повтор по Д2 **не** является
S3: он не открывает данные и tools. Вернуться к S3 можно только при
измеренном остаточном дефиците данных на плотных входах и новом ADR.

### Верификатор S4 как обязательный gate перед сохранением

Отклонён как обязательный gate по цифрам эксперимента:

- Охват низкий. v1: оракул находит 13 из 46 подтверждённых дефектных ответов
  (recall 0,28), семантический поднабор P-A/P-B/P-C/P-I — 8 из 46
  (recall 0,17); пропущено 83 % (`report.md:114-118`). v2: recall 0,43 по
  рецензенту A и 0,36 по B (`report-v2.md:115`), пропущено 57-64 %. Gate дал
  бы ложное чувство проверенности.
- Точность умеренная. Precision оракула 0,76 (v1, 13 из 17) и 0,62 (v2, 16 из
  26 по каждому рецензенту, 13 из 26 = 0,50 по подтверждению обоими;
  `report-v2.md:18` и `:115-117`); даже самый узкий предикат P-A (knee)
  сработал 9 раз, оба рецензента подтвердили 6 из 9 (`report-v2.md:116`).
  Остальные 3 срабатывания не подтверждены обоими; ложными их называть без
  отдельного разбора нельзя, но блокировка по ним была бы спорной: потенциально
  хорошие советы превращались бы в `FAILED`.
- Цена блокировки. S4 в пилоте отбрасывал 5, 4 и 3 ответа из 24 на S0, S1 и
  S2 (`report-v2.md:72`), то есть 21 %, 17 % и 12 % ответов; повтор по Д2 не
  спасает от семантического отклонения, поэтому пользователь получал бы отказ
  без совета.
- Сам эталон нестабилен (каппа 0,441), а предикаты подобраны по известным
  дефектам; охват вне выборки не измерен и не может быть оценён
  (`ai-defects-analysis-2026-09-30.md:359-360`).

S4 остаётся инструментом **измерения** в холдауте, не gate. **Когда
вернуть**: оракул v2 с precision не ниже 0,9 при не менее 30 подтверждённых
срабатываниях и recall не ниже 0,8 на дефектах класса capacity-контракта на
размеченном корпусе (после холдаута), либо решение владельца о фильтрации
«лучше пустой совет, чем вредный».

### Новая версия конверта (`ai-advice.v2`) только ради prompt и счётчика запросов

Отклонена в пользу аддитивной правки `ai-advice.v1` (Д4): конверт, output и
evidence не меняются, нужны два поля provenance. Смена версии конверта
потребовала бы типов UI (`ui/src/types.ts`), второй схемы, ветвления по
версии конверта и заняла бы имя, которое уже связано с отклонённым
структурным вариантом. Минимальная правка согласуется с политикой
наименьшего изменения. Риск: аддитивная правка смешивает в одной схеме две
эпохи provenance; он снят закрытым набором допустимых кортежей и условием
обязательности поля. Вынесено владельцу (вопрос 4).

### Разворот обёрток вместо повтора

Отклонён: Qwen отвергает обёрнутые аргументы до того, как relay или launcher
получают вывод, а разворот по эвристике принимал бы вывод вне контракта.
Правила разворота v1 не были предрегистрированы и по отчёту не дают
вывода (`report.md:13-14`, `:102-106`).

### Повтор на уровне Kotlin или более одного повтора

Отклонён: повторный запуск контейнеров удваивает время и не передаёт модели
текст ошибки схемы (повтор Qwen его передаёт); несколько повторов
растягивают худшее время и стоимость при измеренной частоте около 1,4 %.
Если холдаут покажет, что один повтор чаще не спасает, предел пересматривается
отдельным решением.

### Повторять при любой ошибке, включая ошибки провайдера

Отклонён: HTTP-ошибки и сбои транспорта сегодня не повторяются, и
приёмочный preflight проверяет именно это (`advisory_ai_acceptance_runner.ps1:1018-1020`,
`:1317`); повтор по ошибке схемы — единственное исключение.

fallback возвращается к решению 2026-10-04 в условиях «предложение автора»,
подтверждаемых при заморозке предрегистрации (раздел «Поправка от 2026-10-06
(поздний вечер): холдаут снова на Qwen Code, Codex запасной», Р2 и вопрос В2).

Владелец: при ошибках фоллбэк на Codex, эквивалентный GLM 5.3. Fallback-модель
— не флагманская модель Codex, эквивалентная GLM 5.3; она выбирается на момент
запуска и фиксируется в предрегистрации (в этом ADR не названа). Условия ниже в
цитате не заданы; это **предложение автора ADR**, которое владелец подтверждает
или меняет при заморозке предрегистрации (до первого запроса):

1. Fallback существует только в харнессе холдаута. Модель в продукте
   по-прежнему закреплена (Контекст, п. 5, решение 5), ADR 0010 и Д5 не
   меняются, relay продукта fallback не получает.
2. Триггер — ошибка провайдера основной модели (HTTP-ошибка, сбой транспорта,
   недоступность), а не ошибка схемы: её закрывает повтор Д2. Точный перечень
   классов ошибок и число неудач до переключения фиксирует предрегистрация.
3. Конфигурация fallback-модели (идентификатор, провайдер, SHA-256 конфигурации)
   замораживается до первого запроса вместе с остальным списком Д7; ledger
   маркирует каждую попытку моделью и провайдером.
4. Попытки на fallback-модели не считаются попытками основной модели: до
   заморозки предрегистрации ADR не разрешает смешивать их в P1-P5. Как
   исключаются пары (парная попытка другой руки) или перезапускаются на
   основной модели за счёт запаса, определяет предрегистрация; доля
   fallback-попыток публикуется в отчёте.
5. Это отклонение от методики v1 (запрет fallback) и от условия «одна модель и
   провайдер» Д7; оно перечислено в списке отклонений Д7.

### П1. Раннер, модель и кто запускает

1. **Раннер.** Холдаут (руки A и B) исполняет харнесс на **хосте** (ответ 19)
   вызовами `codex exec` в headless-режиме. Рука C и разведка W3 плана ИИ, если
   запускаются, идут на том же раннере и той же модели (W1 требует совпадения с
   руками A и B). Qwen Code, relay и launcher продукта и ModelStudio в холдауте
   не участвуют. Ключ ModelStudio не используется и не читается.
2. **Кто запускает.** Исполнитель проекта (корневой агент или назначенный им
   исполнитель) локально, concurrency 1, без истории между запусками (методика
   §6). Старт после заморозки предрегистрации и подтверждения владельцем:
   условие Д7 «до первого запроса» сохраняется.
3. **Модель.** Не флагманская модель Codex, которую владелец приравнял к
   GLM 5.3. Идентификатор и уровень рассуждения выбираются при запуске и
   замораживаются предрегистрацией; в ADR они не названы (как в разделе
   «Fallback при ошибках провайдера» и в ADR 0024, Д10 п. 5). Условие Д7 «одна
   модель и провайдер» сохраняется: обе руки (и рука C) идут на одной модели с
   одним уровнем рассуждения; меняется только то, какая это модель.
4. **Передача входа.** Prompt v1/v2 и evidence уходят в `codex exec` через
   stdin; способ (один текст или раздельные части, получение ответа по схеме
   `ai-advice-output.v1`) определяет проба п. 6 и замораживает предрегистрация.
   Системная роль продукта в этом раннере не воспроизводится, поэтому сравнение
   рук A и B внутри раннера корректно, а прямое сравнение с запусками через
   Qwen Code нет (см. «Перенос»).
5. **Запреты** (минимальный набор, действует независимо от статуса ADR 0024;
   по смыслу повторяет его Д10 п. 2 для одиночного вызова):
   - `-s read-only`; `-C` пустой каталог вне репозитория на запуск; собственные
     инструменты Codex (оболочка, правка, чтение файлов) не источник данных,
     вход модели только evidence случая;
   - сеть сверх канала к провайдеру модели не допускается;
   - stdin только ASCII; не-ASCII данные доставляются способом, который прошёл
     round-trip проверку хэша (иначе вход модели не тот, что отправлен); случай,
     для которого такой способ не найден, до заморозки заменяется другим случаем
     той же ячейки матрицы (предложение автора);
   - запись только в каталог харнесса (п. 2 ниже); в каталог данных продукта и
     в `analyses/` писать нельзя.
6. **Проба раннера до первого запроса.** Условия те же, что в ADR 0024, Д10
   п. 7: ограничение инструментов и записи, сеть песочницы, round-trip не-ASCII,
   способ получения ответа по схеме, наличие потока событий и `usage`,
   внутренние ходы на вызов, сохраняет ли Codex сессии и логи и где.
   Контрольные проверки не опираются на поток событий: файл-канарейка вне
   `-C` (чтение должно не удаться) и попытка сетевого обращения (должна не
   удаться). Если запрет не подтверждён ни потоком событий, ни контрольными
   проверками, холдаут не стартует. Что невыполнимо, записывается в
   предрегистрацию как ограничение, а не обходится. Проектом подтверждено только
   следующее: запуск `codex exec -m <модель> -c model_reasoning_effort=<уровень>
   -s read-only|workspace-write -C <каталог> -o <файл> -` с prompt через stdin,
   порча не-ASCII в stdin на этой машине и невидимость файлов вне `-C` в режиме
   read-only (ADR 0024, Д10); всё остальное не проверено. Сессии и логи Codex
   остаются вне репозитория и вне отчётов; сырые stdout и stderr в git не
   попадают.
7. **P4 и хост.** Хост без контейнера означает, что OS-изоляция продукта (ADR
   0010) в холдауте не наблюдается; изоляцию оценивают продуктовые preflight
   тесты и проба контейнера (план ИИ, «Итоги пробы контейнера»), а не холдаут.
   Это условие план ИИ (H0, п. 7) записал как поправку Д7 по P4 до первого
   запроса. Здесь оно фиксируется как факт: в холдауте измеримы 0 изменений
   analysis и verdict, 0 утечек секретов и 0 выполненных canary из H01-H05 (при
   условии, что все пять дошли до модели); пункт P4 «0 нарушений изоляции» не
   измеряется, и итог P4 публикуется с пометкой «изоляция не оценивалась в
   холдауте», а не «выполнено» (подтверждено владельцем 2026-10-06, вопрос 3 раздела
   «Вопросы поправки и решения владельца 2026-10-06»).

### П2. Учёт запросов, счётчик и данные

1. **Единица учёта: один вызов `codex exec`.** Число запросов к провайдеру
   внутри одного вызова (внутренние ходы Codex) может быть ненаблюдаемо (не
   проверено). Если проба это подтвердит, единицей остаётся вызов, а отчёт
   прямо пишет, что внутренние ходы не наблюдаются; поправочное число не
   вводится.
2. **Отдельный счётчик и каталог вне git.** Холдаут ведёт собственный ledger в
   каталоге харнесса вне git (не каталог данных продукта, не ledger
   ModelStudio). Запись резерва пишется атомарно **до** вызова; прогон
   останавливается по достижении предела и по файлу `STOP`. Пробные вызовы,
   перезапуски после сбоя и любые дополнительные вызовы расходуют тот же
   счётчик. Каждая запись несёт `runner: codex-headless`, `data_class:
   test_stand`, идентификатор холдаута, `attempt_id`, номер вызова в попытке,
   руку (`arm`) и этап (`stage`, для руки C), модель, уровень рассуждения и
   случай из замороженного манифеста; харнесс отвергает случай вне манифеста.
   Случаи холдаута синтетические (методика §5), реальных данных клиента на
   входе нет, поэтому `data_class` равен `test_stand`.
3. **Числа, которые остаются.** 160 попыток (152 плановые и запас 8 только для
   перезапуска попыток, сорвавшихся по ошибкам провайдера или инфраструктуры;
   перечень классов ошибок фиксирует предрегистрация); потолок 320 вызовов (2 на
   попытку); рука C до 252, разведка W3 36; общий лимит ИИ-запросов 900, из
   которых на ModelStudio израсходовано 221. Решение
   владельца 2026-10-06 (вопрос 8): вызовы Codex ведутся отдельным счётчиком с нуля и
   в лимит 900 не входят; лимит 900 остаётся пределом запросов ModelStudio (221
   израсходовано). Ledger холдаута применяет собственные пределы плана (320, 252,
   36). Пилот ADR 0024 («+140», потолок 210) тоже ведёт отдельный счётчик вне 900, и
   арифметика «829 + 140 = 969» снимается: вызовы Codex в 900 не входят. Потолок 320
   остаётся верхней границей плана, но повтора на попытку нет (вопрос 2), на
   попытку приходится один вызов, и достижимы лишь 160.
4. **Повтор Д2 в холдауте не исполняется.** Д2 свойство relay продукта; в
   контуре Codex relay нет, а повторный запрос в диалоге Qwen не имеет
   аналога. Повтор на уровне харнесса (второй вызов после ошибки схемы верхнего
   уровня) был бы другим механизмом, а не Д2, и не вводится:
   решение владельца 2026-10-06 (вопрос 2): повтора нет, попытка равна одному
   вызову `codex exec`, ответ с ошибкой схемы считается «не OK».
5. **Fallback отменён** (решение владельца 2026-10-06, вопрос 5: «без fallback»).
   Решение 2026-10-04 («Если будут ошибки, то фоллбэк на кодекс, эквивалентный GLM
   5.3») было условным и сформулировано для основной модели DeepSeek; теперь
   основная модель холдаута сама модель Codex, и у fallback нет отдельной цели.
   Поэтому отклонение «fallback при ошибках провайдера» (список отклонений Д7 и
   раздел «Fallback при ошибках провайдера») не применяется, а сорвавшиеся
   попытки перезапускаются за счёт запаса 8 (условие запаса не меняется; перечень
   классов ошибок фиксирует предрегистрация). Другая fallback-модель владельцем не
   названа и не вводится.

### П3. Перенос результатов и что холдаут на Codex не доказывает

1. **Модель не боевая.** Модель холдаута приравнена владельцем к GLM 5.3, точное
   соответствие не доказано, боевая модель (он-прем) и модель продукта сейчас
   (`deepseek-v4-flash-0731`) другие. Выводы о качестве читаются как
   **направление** эффекта prompt v2 на модели-заменителе, а не как величины для
   моделей продукта.
2. **Приёмка относится к тройке (модель, prompt, runner)** (Д5, п. 5; «Связанные
   решения (2026-10-05)»: метка v2 действует только для моделей, у которых
   холдаут пройден). Холдаут на Codex проверяет тройку (модель Codex, v1/v2,
   `codex exec`) и **ни одной модели из конфигурации продукта**. Поэтому
   выполнение P1-P5 на Codex это основание для разговора о переключении
   метки, но не выполнение условия ADR 0023 ни для одной модели продукта.
   Решение владельца 2026-10-06 (вопрос 1): результат это направление; для метки по
   умолчанию на модели продукта нужен подтверждающий прогон на этой модели и этом
   runner (после восстановления лимитов Qwen или на боевой модели), объём которого
   назначает владелец. Метка по умолчанию по холдауту Codex не переключается.
3. **Что холдаут больше не измеряет.** Поведение Qwen Code 0.21.1, relay и
   launcher продукта; эффективность повтора Д2 на живой модели (остаётся не
   измеренной, как в разделе «Риски и остаточные ограничения»); часть P3,
   связанную с пересланными запросами и повтором; изоляцию (п. 7 П1).
   Ожидания, полученные на DeepSeek через Qwen (около 1,4 % обёрнутых ответов,
   2-11 повторов на 152 попытки, 38-62 % ответов с hard_defect), на Codex не
   переносятся: для модели Codex частота ошибок схемы и дефектов неизвестна.
4. **Сравнимость.** Числа холдаута на Codex напрямую не сопоставляются с
   сериями v1-v3 на DeepSeek и с приёмкой GLM 5.3 (другой runner, другой способ
   передачи prompt, другая модель). Базовый дефект T1 (зависимость bound от knee)
   воспроизводился у DeepSeek и у `glm-5.3` (Контекст, п. 1), у модели Codex это
   не показано: если в руке A меньше 6 из 8, по действующему правилу P1 исход
   INCONCLUSIVE. Это не дефект поправки, а риск, который учтён критерием. Мост
   сравнимости с DeepSeek (руки A и B на K01-K12 на Codex-модели) не строится, пока
   владелец не скажет иначе (вопрос 7).
5. **Рецензенты того же семейства.** Рецензенты Д7 (A: `gpt-6-sol`, B:
   `gpt-5.6-terra`) и модель под тестом из одного семейства: смещение в пользу
   «своего» стиля исключить нельзя. Общий слепой пул всех рук снижает его для
   сравнения рук A и B, но не для абсолютной оценки. Итог по-прежнему
   «model-reviewed» и не закрывает review gate методики. Решение владельца
   2026-10-06 (вопрос 6): рецензенты Codex, риск смещения публикуется.
6. **Повторяемость.** Управляемость temperature в headless Codex не проверена;
   повторы описательные, независимыми не считаются (как и прежде).
7. **Правило решения и критерии без relay.** Тексты P3 («не OK после повтора»,
   «не более 2 пересланных запросов», публикация доли повторов и спасённых
   попыток) и P4 («0 нарушений изоляции») этой поправкой не меняются, но в
   контуре Codex на хосте их исходные условия не измеримы: нет relay и повтора
   Д2, нет OS-изоляции продукта. Решение владельца 2026-10-06 (вопросы 2 и 3): P3
   читается как «не OK не более 3 из 76 на руку» без пересланных запросов и без

### Р1. Раннер, модель, runtime

1. **Раннер.** Холдаут (руки A и B; рука C и разведка W3 плана ИИ, если запускаются, на
   том же раннере и той же модели, W1) исполняет харнесс на **хосте** запуском Qwen
   Code 0.21.1 с продуктовыми флагами через relay харнесса: так задавал Д7 до
   поправки от 2026-10-06 и так работали пилоты v1-v3 (план ИИ, H0 п. 7 и H1).
   Провайдер ModelStudio. Ключ читается харнессом из окружения исполнителя в память
   relay и не пишется в файлы, журналы, argv и контейнер. Relay харнесса реализует
   повтор Д2 теми же векторами, что relay продукта (план ИИ, H1), иначе холдаут
   измеряет не поставляемые байты.
2. **Модель.** Условие Д7 «одна модель и провайдер» сохраняется: обе руки (и рука C)
   идут на одной модели. Модель берётся из конфигурации моделей ADR 0023 (Д3, Д4 п. 6:
   «харнесс закрепляет модель сам»; выбор в продукте на холдаут не влияет) и
   замораживается предрегистрацией. Исходная модель Д7 и встроенной конфигурации:
   `deepseek-v4-flash-0731` на встроенном endpoint ModelStudio. Назвал ли владелец
   другую модель, в записи решения нет: вопрос В1.
3. **Runtime.** Хост, concurrency 1, без истории между запусками (методика §6). Выбор
   «Хост» (раздел 1.A, п. 19 сводки) относится к runtime, а не к раннеру, поэтому
   сохраняется; следствие для P4 см. в Р2.
4. **Кто запускает.** Исполнитель проекта локально, старт после заморозки и
   подтверждения владельцем (поправка от 2026-10-06, П1 п. 2, без изменения).

### Р3. Запасной раннер Codex: условия применения

1. **Когда.** Только по решению владельца и при исчерпании лимитов Qwen (оговорка
   «пока» решения 2026-10-06). Недоступность ModelStudio сама по себе решением не
   считается: она закрывается перезапуском за счёт запаса 8 (Д7, раздел «Бюджет
   холдаута»).
2. **Как.** Тем же способом, что любое изменение условий: Д7 требует поправки ADR до
   возобновления прогона, а условие «одна модель и провайдер» не допускает смешивать
   в P1-P5 попытки двух моделей (раздел «Fallback при ошибках провайдера», п. 4).
   Поэтому до первого запроса режим выбирается в предрегистрации; после первого
   запроса Qwen переход на Codex оформляется поправкой ADR и новой предрегистрацией, а
   судьба уже выполненных попыток Qwen определяется этой поправкой (вопрос В3).
3. **Что действует.** Поправка от 2026-10-06 (П1-П4, вопросы 1-11 и решения владельца
   по ним) целиком, как записано. Проба AGP (ADR 0024, Д10) относится к пилоту и пробу
   холдаута (П1, п. 6) не заменяет.
4. **Отличие от fallback.** Fallback по ошибкам провайдера (Р2) работает внутри серии
   на уровне попытки и учитывается отдельным счётчиком; запасной раннер заменяет
   весь раннер серии.

  отдельный лимит.
- **В6. Доступность Qwen и ModelStudio.** Решение «пока» оставляет открытым, остались
  ли лимиты провайдера (проверка равна платному запросу и до заморозки не выполнялась).

## Поправка от 2026-10-06 (ночь): сравнение аргументов продолжения

Статус ADR остаётся Accepted. Поправка уточняет условие 3 решения Д2 и ничего
не расширяет: ограничения на число запросов, окно, тип ошибки, список полей и
размер не меняются.

### Что показали сохранённые потоки и реальный Qwen Code

Условие 3 требовало, чтобы `arguments` продолжения были равны собранным relay из
потока строкой. Реальный провайдер (DeepSeek через ModelStudio) присылает JSON
аргументов с пробелами после `:` и `,` (143 из 143 сохранённых потоков), а Qwen
Code 0.21.1 присылает аргументы обратно пересериализованными без пробелов:
ровно `JSON.stringify(JSON.parse(arguments))` (проверено на локальной заглушке
провайдера, в том числе для экранированного не-ASCII, чисел вида `1.0` и ключей-
индексов). Строки различались при равных значениях, relay отвечал
`RETRY_CONTINUATION_MISMATCH`, и повтор Д2 на реальном провайдере практически не
срабатывал. Общие векторы A2 были записаны компактно и этого не ловили.

### Правило

`arguments` продолжения принимаются, если выполнено одно из двух:

1. они равны собранной строке побайтно (как раньше; это единственный способ для
   текста, который не разбирается как JSON);
2. они равны `JSON.stringify(JSON.parse(<собранная строка>))`: то же разобранное
   значение, записанное единственным каноническим способом.

Это структурное равенство значений плюс одна допустимая запись. Любая другая
запись отклоняется с `RETRY_CONTINUATION_MISMATCH`, даже если значение похоже:
другой порядок ключей (порядок ключей объекта сохраняется, массивов тоже), иные
пробелы, отступы, экранирование (`é` вместо `é`), иная запись числа
(`2.0` вместо `2`), повторяющиеся ключи, лишний или недостающий ключ, число
вместо строки, изменённое значение, в том числе внутри строки-обёртки
`{"arguments": "<JSON-строка>"}` (строка внутри не разбирается и не
нормализуется). Нет допуска на расхождение значений. Продолжение не может
принести провайдеру новый текст: допустимых записей ровно две, и обе являются
функцией собранных аргументов. Границы разбора JSON в JavaScript воспроизводятся
так же, как их воспроизводит Qwen Code: из повторяющихся ключей остаётся
последний, число вне диапазона `double` (`1e400`) записывается как `null`, число с
избыточной точностью округляется. Запись поток-в-продолжение при этом не
расширяется: Qwen не выбирает содержимое, а лишь пересериализует то, что прислал
провайдер (закреплено тестом «continuation arguments are a function of the stream
text»). На практике в ответах таких значений нет.

Выбор порядка ключей: если бы продолжение сравнивалось без учёта порядка, relay
принимал бы запись, которой Qwen Code никогда не присылает. Узкое правило не
теряет ни одного наблюдённого продолжения и не ослабляет проверку «тот же вызов».
Если Qwen Code сменит способ сериализации (версия закреплена, 0.21.1), повтор
перестанет срабатывать безопасно (отказ), а не небезопасно; счётчик отказов
`RETRY_CONTINUATION_MISMATCH` в холдауте Д7 это покажет.

### Первая причина отказа

Qwen после отказа продолжает слать запросы, и `retry_refused_reason` затиралась
значением `RETRY_LIMIT_REACHED`, из-за чего терялась причина, нужная счётчику Д7
(`RETRY_NOT_TOP_LEVEL_SCHEMA`). Relay теперь пишет в `relay-result.json` ещё одно
поле `first_refused_reason`: первую причину отказа или `null`, пока отказов не
было. `retry_refused_reason` не меняется, `schema_version` результата
(`advisory-ai-runtime-relay.v1`) тоже: поле аддитивное, launcher и Kotlin его не
читают. Поле фиксирует первую причину в порядке записи: Qwen шлёт запросы
последовательно, ожидая ответа; при искусственно пересекающихся запросах порядок
записи может отличаться от порядка номеров (так же, как у `retry_refused_reason`).

### Следствия

- Поведение продукта меняется: повтор Д2 теперь срабатывает, когда провайдер
  присылает аргументы с пробелами (до поправки он отклонялся). Число запросов к
  провайдеру на совет по-прежнему не больше 2.
- Общие векторы `tools/advisory_ai_relay_retry_vectors.json` расширены вариантами
  с пробелами (4 вектора, всего 12), их SHA-256 изменился: копию и закреплённую
  сумму в тесте relay2 харнесса (H1, вне `main`) нужно обновить при переносе
  правки; relay2 переносится после слияния отдельно.
- Прежние векторы и их ожидаемые исходы не менялись.

`docs/user/advisory-ai.md` (повтор принимается и при записи аргументов с
