## Контекст

### Перцентили HDR

В ядре используется `PackedHistogram(1, 86_400_000, 3)` (`Metrics.kt:15-18`, `:268-273`). При трёх значащих цифрах значения меньше 2048 мс хранятся точно. Начиная с 2048 мс `getValueAtPercentile` возвращает верхнюю границу эквивалентного диапазона. Перебор значений 1–3000 мс показал первое превышение над наблюдённым значением при 2048 мс. Расчёт на HdrHistogram 2.2.2 для 100 одинаковых сэмплов даёт:

| Наблюдённое значение, мс | p50 = p95 = p99, мс |
| --- | --- |
| 2047 | 2047 |
| 2048 | 2049 |
| 4095 | 4095 |
| 4096 | 4099 |
| 60000 | 60031 |
| 86400000 | 86441983 |

Последнее значение перцентиля превышает даже настроенный `highestTrackableValue` 86 400 000 мс. Для значений от 2048 мс относительное превышение строго меньше `1/1024` (около 0,0977 %); наибольшее найденное при переборе — `9,73e-4`.

Сейчас `MutableMetrics.summary` публикует эти значения без ограничения фактическим максимумом (`Metrics.kt:265-283`, `:300-302`). Из summary они попадают в `UtcLoadMetrics`, policy evidence и сравнение с порогом `lte` (`Policy.kt:215-216`, `:306-308`), а также в диагностическое evidence (`DiagnosticAnalysis.kt:765-767`). Bucket API вычисляет p95 при чтении сжатой гистограммы (`LocalApi.kt:1524`, `:1530-1538`); статический график отчёта делает то же (`StaticLoadChart.kt:90-106`). Python-оракул воспроизводит округление (`tools/applicability_validation.py:28-34`): тест сейчас ожидает для `[4094]` значение `4095` (`tools/test_applicability_validation.py:79-84`).

Ограничение перцентиля фактическим максимумом устраняет превышение над `max`, но не делает оценку точной. Для `95 × 60000 + 5 × 60010` точный p95 равен 60000 мс, HDR даёт 60031 мс, а ограничение максимумом оставляет 60010 мс. Для `100 × 60000 + 1 × 70000` точный p95 равен 60000 мс; HDR и после ограничения даёт 60031 мс. Поэтому порог между точным и опубликованным значением всё ещё может дать ложный `FAIL`.

### Пустое окно

Внутренняя `emptySummary` записывает четыре нуля латентности (`Metrics.kt:317-324`), а `window_metric_summary` публикует их как измерения (`DiagnosticAnalysis.kt:747-770`). Нулевая выборка не имеет измеренной латентности; настоящий сэмпл длительностью 0 мс имеет. `error_rate_ratio` для пустой выборки уже равен `null`, тогда как `throughput_rps` является точным отношением нуля к длительности окна (`Metrics.kt:296-297`).

ADR 0017, уже реализованный в PR #26, закрывает пустое окно на стороне потребителя: baseline-сравнение читает `sample_count` (`BaselineComparison.kt:441`, `:470`) и выдаёт `INSUFFICIENT_DATA` с `EMPTY_WINDOW`. Тесты проверяют старую форму с `0` и новую форму с `null` (`BaselineComparisonTest.kt:593`, `:630`, `:671-673`). Здесь меняется только производитель evidence.

### Parent-строки Transaction Controller в JMeter CSV

CSV-парсер назначает каждой строке `JMETER_SAMPLER` (`JtlCsvParser.kt:79-97`); такой kind входит в overall и 1-секундные buckets (`Metrics.kt:117`, `:212`), а также в UTC load (`UtcLoadMetrics.kt:51`). XML-парсер различает контейнер по вложенным `sample` (`JtlXmlParser.kt:88-96`).

Поведение реального JMeter проверено запусками JMeter 5.6.2 (отчёт `report.md`) и повторено автором ADR на JMeter 5.6.3 для планов A, B, C3, E1: стандартный CSV, три потока, пять итераций, Transaction Controller с тремя дочерними сэмплерами (JSR223), локальный запуск `jmeter -n -t <plan>.jmx -l <out>.jtl -Jjmeter.save.saveservice.output_format=csv -Jjmeter.save.saveservice.subresults=<true|false>`.

| Сценарий JMeter | Что попадает в CSV | Продуктовый парсер до этого ADR |
| --- | --- | --- |
| Transaction Controller с «Generate parent sample», `subresults=true` | Parent-строка контроллера и строки дочерних | Все строки sampler: 60 строк вместо 45, ошибок 30 вместо 15 (вариант с assertion, JMeter 5.6.2) |
| Transaction Controller без parent sample, любое `subresults` | Строка контроллера с тем же сообщением и строки дочерних как независимые сэмплы | То же |
| Transaction Controller с «Generate parent sample», `subresults=false` | Только parent-строки (15 из 15), дочерних нет | Валидный вход: единственная измеряемая единица — контроллер |
| Simple Controller, Module Controller | Parent-строк нет, только дочерние | Без изменений |

Признаки parent-строки в обоих режимах и на обеих версиях: `responseMessage` равно `Number of samples in transaction : N, number of failing samples : M`, `dataType` пустой (у дочерних JSR223/HTTP `text`), `URL` равно `null`; `bytes` равно сумме байт дочерних (33 = 3 × 11). Пример (`A_tc_parent_true.sub_true`):

```text
1790889796879,545,TC-parent,200,"Number of samples in transaction : 3, number of failing samples : 0",TG 1-2,,true,,33,30,3,3,null,0,0,6
1790889796879,398,child1,200,OK,TG 1-2,text,true,,11,10,3,3,null,5,0,2
```

Геометрия строк (вложенность по времени и потоку, порядок в файле) надёжным признаком не служит: при `Generate parent sample` parent записан до дочерних, без него после них, а при отключённом «Include duration of timer and pre-post processors» интервалы дочерних выходят за интервал parent.

Контрпримеры, проверенные на реальном JMeter 5.6.2: HTTP-сэмплер, чей сервер возвращает reason phrase, совпадающую с сообщением контроллера, пишет `dataType = text` и parent не является. Сэмплер с пустым `dataType` и таким же сообщением возможен только искусственно (скрипт явно задаёт и пустой тип данных, и текст сообщения); прогон такого JSR223-плана завершён не был, поведение следует из правила ниже.

Что проверено и что нет:

- Литералы «Number of samples in transaction : » и «, number of failing samples : » находятся в константах `TransactionController.class` и `TransactionSampler.class` в `ApacheJMeter_core.jar` версий 5.6.2 и 5.6.3 и отсутствуют в `messages.properties`; следовательно, текст не локализуется. Проверка выполнена по байткоду; исходники JMeter не читались.
- Не проверено: версии JMeter, кроме 5.6.2 и 5.6.3; другие значения `jmeter.save.saveservice.*`, кроме `subresults`; смешанный файл (`subresults=false` плюс обычные сэмплеры вне контроллера) и вложенные контроллеры при `subresults=false` (поведение следует из правила, а не из прогона).
- В обеих локальных установках `lib/ext` содержит посторонние jar (в 5.6.2 `jmeter-agent-Alpha-0.1.jar`, в 5.6.3 `jmeter-agent-0.5.0-beta.jar`, `jmeter-plugins-casutg`, `-dummy`, `-tst`, `-manager`). Plugins не меняют Transaction Controller, но это не доказано; golden-фикстуры нужно получить на чистом официальном дистрибутиве.

### Identity

Все изменения влияют на воспроизводимый результат. `analysis_id` вычисляется из identity, а сохранённый результат возвращается из кэша по этому id (`AnalysisService.kt:133-134`). Если оставить прежнюю identity, повторный анализ может вернуть старые числа. Блок `modules` входит в семантический ключ baseline и истории динамики (`BaselineComparison.kt:942-943`, `RunComparison.kt:424-425`), поэтому новая версия общего модуля `metrics` затронет analyses всех источников, включая analyses без diagnostics.

## Решение

### Перцентили

Сохранить `significantDigits = 3` по умолчанию, конфигурацию гистограммы и HdrHistogram 2.2.2. Для каждого непустого summary ограничивать p50, p95 и p99 фактическим максимумом записанных сэмплов:

```text
published_p(q) = min(histogram.getValueAtPercentile(q),
                     observed_max_latency_ms)
q ∈ {50, 95, 99}
```

Для непустой выборки это возвращает инвариант:

```text
p50 <= p95 <= p99 <= max_latency_ms
```

Опубликованный перцентиль не меньше точного перцентиля: HDR возвращает верхнюю границу диапазона, а максимум не меньше любого значения. Для положительного точного значения он меньше `точный × (1 + 2^-10)` при трёх цифрах; при точном нуле остаётся нулём. Для правила `lte` это безопасная оценка в одном направлении: `PASS` не возникает из-за занижения перцентиля, но ложный `FAIL` из-за округления внутри диапазона остаётся возможным.

Правило применяется к `MutableMetrics.summary` (`Metrics.kt:300-302`). Через него исправляются обычные и оконные summary, `UtcLoadMetrics` с существующим порогом `MIN_P95_SAMPLES = 20` (`UtcLoadMetrics.kt:67`, `:76-80`, `:102`), policy и диагностическое evidence. Порог числа сэмплов в UTC load не меняется.

Отдельно применять то же правило при декодировании p95 в bucket API (`LocalApi.kt:1537`) и статическом графике (`StaticLoadChart.kt:105`). Для bucket брать поле строки `max_latency_ms`, а не `histogram.maxValue`: последнее само является верхней границей диапазона и для сэмпла 60000 мс равно 60031 мс. Bucket API применяет правило к любому сохранённому анализу единообразно (решение владельца). Согласовать Python-оракул и его тест: `[4094]` должен давать опубликованное значение `4094`, сохраняя расчёт HDR до ограничения.

### Пустое окно

Только в evidence типа `window_metric_summary`, если `sample_count == 0`, публиковать `null` во всех четырёх полях `latency_ms`:

```text
sample_count == 0
=> latency_ms.{p50,p95,p99,max} = null
=> error_count = 0
=> error_rate_ratio = null
=> throughput_rps = 0 / duration
```

`throughput_rps` остаётся точной дробью: за окно измерено ровно ноль сэмплов (решение владельца). Латентность при отсутствии сэмплов не измерена. Если `sample_count > 0`, все четыре поля остаются числами; реальная латентность 0 мс остаётся числом `0`.

Это единственное публикуемое оконное evidence с латентностью. Оконный `metric_summary` не добавляется в результат (`WindowPolicy.kt:27`, `includeMetricEvidence = false`). Внутренняя `emptySummary` остаётся числовой (`Metrics.kt:317-324`); window-независимый `metric_summary` также сохраняет числовой тип латентности (`Policy.kt:276-312`). Схема `analysis-result.v1` не меняется: `evidence` задан как массив объектов без вложенной схемы (`docs/contracts/result/v1/analysis-result.schema.json:54-59`). `WindowMetricSummaryEvidence` уже допускает `null` (`ui/src/types.ts:293`), а `MetricSummaryEvidence` остаётся числовым (`ui/src/types.ts:146`).

### Parent-строки Transaction Controller в JMeter CSV

Колонка-маркер не вводится. Parent определяется только стандартными признаками JMeter; эвристик по геометрии, порядку строк, `bytes` или `URL` нет.

Строка является parent-строкой, если выполняются оба условия:

```text
responseMessage полностью совпадает с
  Number of samples in transaction : [0-9]+, number of failing samples : [0-9]+
dataType равен пустой строке
```

Сравнение чувствительно к регистру и пробелам, цифры только ASCII, частичные совпадения не принимаются. Признак доступен, если в заголовке есть ровно по одной колонке `responseMessage` и `dataType`. Если какой-либо из них нет, признак недоступен и все строки остаются `JMETER_SAMPLER` (прежнее поведение, без предупреждения: сообщение о недоступности стало бы coverage reason и дало `NO_VERDICT`). Дубль любой из этих колонок делает вход `INVALID` с `INVALID_JMETER_CSV_HEADER`, как для обязательных колонок (`JtlCsvParser.kt:128-132`). Колонка `dataType` в нестандартных CSV с `jmeter.save.saveservice.data_type=false` отсутствует, поэтому для таких файлов признак недоступен.

Классификация определяется режимом всего файла:

| Содержимое файла | Parent-строки | Остальные строки |
| --- | --- | --- |
| Есть parent-строки и есть хотя бы одна не-parent строка | `JMETER_CONTAINER` | `JMETER_SAMPLER` |
| Только parent-строки (`subresults=false` при включённом parent sample) | `JMETER_SAMPLER` | нет |
| Нет parent-строк | нет | `JMETER_SAMPLER` |

Во втором случае контроллер остаётся единственной измеряемой единицей, как сейчас: JMeter при `subresults=false` и включённом «Generate parent sample» не пишет дочерние, поэтому «все parent → `INVALID`» сломало бы валидный вход. В первом случае overall, 1-секундные buckets, rollups, UTC load, RPS и ошибки считаются по дочерним строкам; parent образует отдельный уровень транзакции. Overall непуст в каждой из трёх веток: `JMETER_CONTAINER` присваивается только при наличии не-parent строки. `groupPath` у CSV остаётся пустым, иерархия не восстанавливается, число `N` из сообщения не используется.

Как parent-транзакция попадает в метрики и правила. `JMETER_CONTAINER` входит в точную сводку транзакции так же, как контейнер JMeter XML (`Metrics.kt:117`, `:208-227`; матрица ADR 0003): число сэмплов, ошибки, перцентили и throughput берутся из строк контроллера по тому же окну прогона. Правило policy с `scope.transaction.name`, равным label контроллера, оценивает бизнес-транзакцию (`Policy.kt:199-203`). Идентичность транзакции включает kind: если обычный sampler имеет тот же label, что и контроллер, scope по этому label даёт `AMBIGUOUS_TRANSACTION` и `NO_VERDICT`; flat CSV раньше сливал такие строки в одну сводку, и это изменение поведения. Сравнения транзакций между анализами используют полный ключ с `sample_kind` (`RunComparison.kt:264`): label контроллера как `JMETER_CONTAINER` (с дочерними) и как `JMETER_SAMPLER` (`subresults=false`) считаются разными транзакциями, поэтому сравниваемые прогоны должны быть записаны с одним значением `subresults`. Окно прогона (минимум start, максимум end) по-прежнему строится по всем строкам, включая parent (`AnalysisService.kt:249-250`), как для XML.

Ограничения решения, записанные явно:

- Файл-уровневый режим не различает, записаны ли дочерние контроллера. Смешанный файл с `subresults=false` и обычными сэмплерами вне контроллеров относится к первой строке таблицы: parent-строки исключаются из overall, хотя дочерних у них нет. Обычные сэмплеры остаются в overall, а контроллеры видны только как транзакции. Рекомендация пользователю: сохранять дочерние (значение `subresults=true` по умолчанию в JMeter; в `bin/jmeter.properties` строка закомментирована).
- Вложенные Transaction Controller при `subresults=false` дают только parent-строки; вход попадает во вторую строку таблицы, и вложенный контроллер считается вместе с внешним (прежнее поведение).
- Ложное срабатывание возможно только для сэмплера, который одновременно имеет пустой `dataType` и точное сообщение контроллера (например, скрипт JSR223 задаёт обоими явно). При наличии дочерних такой сэмплер уходит из overall, но остаётся видимым как транзакция `JMETER_CONTAINER`; данные не теряются. Риск для обычных сэмплеров оценён как низкий: HTTP и подобные сэмплеры пишут непустой `dataType`.
- Другие версии JMeter и плагины не проверены (см. выше).

Версия формата: `jmeter-csv` и `input_versions.source` повышаются (раздел «Identity»), потому что для существующих входов меняется результат, а не только для новых.

### Настройка точности гистограммы

Точность `significantDigits` является настройкой анализа, а не константой ядра. Значение по умолчанию 3. Дизайн без изменения ядра:

- Ядро уже параметризовано: `MetricsConfig.significantDigits` (`Metrics.kt:18`), проверка диапазона `1..5` (`Metrics.kt:191`), значение входит в identity (`AnalysisResult.kt:121`, блок `histogram`) и в семантический ключ (`histogram`, `BaselineComparison.kt:942-943`). Декодеры читают точность из самого сжатого V2-кодирования (`decodeFromCompressedByteBuffer`, `LocalApi.kt:1533`, `StaticLoadChart.kt:100`), поэтому bucket API и график менять не нужно.
- Где задаётся: параметр запуска процесса `--histogram-significant-digits <n>` у `ltv ui` и `ltv analyze`, рядом с `--analysis-parallelism` (`CommandLine.kt:702`). Он передаётся как `EngineConfig(metrics = MetricsConfig(significantDigits = n))` в двух местах создания сервиса (`CommandLine.kt:257`, `:491`). Это единственная точка внедрения. Параметр не входит в запрос API и в файл policy: отдельный запрос не должен менять определение метрик внутри серии baseline.
- Границы: при запуске допускается целое `3..5`, иначе процесс не стартует с ошибкой аргумента. Нижняя граница 3 выбрана потому, что 1–2 цифры дают погрешность до 10 % и 1 %. Верхняя граница 5 равна пределу библиотеки. Проверка ядра `1..5` остаётся как есть.
- Что меняется при значении `d`: значения до `subBucketCount` хранятся точно (2048, 32768, 262144 для `d` = 3, 4, 5), выше относительное превышение верхней границы диапазона меньше `1/1024`, `1/16384`, `1/131072`. Правило ограничения максимумом действует при любой точности (при `d` = 4 значение 60000 даёт 60001, ограничение возвращает 60000).
- Влияние на память и размер (оценка на модели, не на продукте: HdrHistogram 2.2.2, `PackedHistogram`, логнормальная латентность `exp(5 + 1,6·z)` мс, значения до 86 400 000 мс):

| Цифры | Занято при 1 000 сэмплов | Занято при 101 000 | Сжатый V2 при 101 000 |
| --- | --- | --- | --- |
| 3 | 2,8 КБ | 9,8 КБ | 3,2 КБ |
| 4 | 3,0 КБ | 19,0 КБ | 4,3 КБ |
| 5 | 3,0 КБ | 20,2 КБ | 4,3 КБ |

При больших выборках одной гистограммы 4 и 5 цифр занимают около 1,9 и 2,1 раза больше памяти, чем 3; сжатая запись растёт примерно на 37 %. Число гистограмм ограничено `MetricsConfig` (`Metrics.kt:19-23`), поэтому до включения значения выше 3 на стенде нужен замер кучи и времени по методике ADR 0014.

- Identity и совместимость: значение уже входит в identity, поэтому смена настройки даёт другой `analysis_id` и пересчёт. Старые и новые анализы с разной точностью несопоставимы (`INCOMPATIBLE_METRIC_DEFINITION`), и baseline нужно закрепить заново. Версия модуля `metrics` при смене настройки не повышается: версия описывает формулу, настройка является данными identity.
- Python-оракул параметризуется точностью (его формула `bit_length() - 11` соответствует 3 цифрам).

### Identity, версии и golden

Повысить версии в `analysis-identity.v1`:

| Компонент | Было | Станет | Область |
| --- | --- | --- | --- |
| Модуль `metrics` | `1` | `2` | Каждый анализ |
| Модуль `load-resource-diagnostics` | `2` | `3` | Только если модуль присутствует |
| Parser `jmeter-csv` | `1` | `2` | Только JMeter CSV |
| `input_versions.source` для CSV | `jmeter-jtl-csv.v1` | `jmeter-jtl-csv.v2` | Только JMeter CSV |

Версии CSV повышаются, потому что принимаемый вход интерпретируется иначе: тот же файл с parent и дочерними строками получает другой результат. Сейчас версия parser жёстко задана как `"1"` для всех источников (`AnalysisResult.kt:67-74`). Реализация должна выбирать её по `SourceType`: у `jmeter-csv` — `"2"`, у остальных parser — `"1"`. Аналогично заменить только CSV-ветку `inputVersion` (`AnalysisResult.kt:247-253`). Версия diagnostic-модуля сейчас `"2"` (`AnalysisResult.kt:78-94`); повышать её лишь при наличии модуля. Блок `limits` не меняется.

Пересчитать canonical bytes, `.sha256` и записи `fixtures/slice1/manifest.json` для `fixtures/slice1/identity/analysis-identity.v1.json` и `analysis-identity-resources.v1.json`. Оба golden содержат `metrics` версии `1` и CSV parser/input старой версии. Golden без diagnostics не должен внезапно получить `load-resource-diagnostics`; его версию в соответствующем анализе проверяет `AnalysisIdentityDiagnosticVersionTest`.

Существующие `fixtures/slice1/**/oracle.json` остаются без изменений: в них нет значений латентности от 2048 мс, а CSV без parent-строк разбирается как раньше. Новые golden-фикстуры берутся из реальных небольших CSV JMeter на чистом официальном дистрибутиве: вход с parent и дочерними строками (`subresults=true`), вход только с parent-строками (`subresults=false`), вход с обычным сэмплером и тем же сообщением при `dataType = text`. Предварительные образцы получены на JMeter 5.6.2 и 5.6.3 (локальные установки, см. «Что проверено»). В `manifest.json` для каждой записать версию и источник дистрибутива, отсутствие плагинов, команду запуска и исходный `.jmx`, а также ожидаемые overall и транзакции, посчитанные независимо от продукта.

### Совместимость со старыми анализами

Сохранённые analyses, их canonical bytes, SHA-256 и baseline bindings не переписываются. Новый запуск тех же входных bytes получает новый `analysis_id` и пересчитывается по новым правилам. Старые результаты остаются читаемыми по прежней identity. Старый анализ CSV с parent и дочерними строками навсегда сохраняет двойной учёт.

Версия `metrics` входит в каждый analysis, поэтому оконное сравнение старого baseline с новым анализом возвращает `NOT_EVALUATED` с причиной `INCOMPATIBLE_METRIC_DEFINITION` (`BaselineComparison.kt:212`); для строк метрик причина тоже `INCOMPATIBLE_METRIC_DEFINITION` (`:569`), если метрики доступны. Если метрик нет (например, у ручного baseline с `INVALID` analysis), приоритет у `MISSING_METRIC` (`:566-570`): это существующее поведение ADR 0016 не меняет. Смешанный старый и новый набор кандидатов получает `BASELINE_MIXED_SEMANTICS` (`BaselineComparison.kt:116`). История динамики исключает старые analyses из сопоставимого ряда и увеличивает `excluded_incompatible_count` (`RunComparison.kt:39-41`). Это относится и к analyses без diagnostics.

Сохранённый `run-period.json` (`RunPeriod.kt:55-58`) строится по интервалам, занятым строками `JMETER_SAMPLER` и `GATLING_REQUEST`, и привязан к hash входа (`SourceAnalysis.kt:169-175`). Теперь это затрагивает существующие входы: для CSV с parent и дочерними строками parent-строки больше не входят в занятые интервалы, но кэшированный период был построен по прежним правилам. Границы периода (первый и последний сэмпл) считаются по всем строкам и не меняются; могут отличаться только факты простоев (`longest_idle_gap`, `idle_gap_count`). Решение: кэшированные периоды не пересчитываются и версия `run-period.v1` не меняется. Последствие: у таких прогонов авто-окно может ещё некоторое время опираться на прежние факты простоев; повторно загруженный вход с другим `run_id` получит новый период. Если это окажется заметным, пересчёт периода выносится отдельной задачей.

Bucket API вычисляет p95 при чтении, не хранит его. Ограничение по `max_latency_ms` действует и на старые analyses (решение владельца): у старого анализа p95 графика может стать 60000 мс, тогда как его неизменяемое evidence содержит 60031 мс. Статический график также является производным представлением. Старые canonical bytes от этого не меняются; различие явно описывается пользователю.

### Граница с ADR 0017 и ADR 0014

ADR 0017 уже реализовал защиту потребителя пустого окна. Она читает `sample_count`, а не числовую латентность (`BaselineComparison.kt:441`, `:456`, `:470`). Старое evidence с `0` и новое с `null` безопасны; порядок слияния изменений любой. Статусы, причины, правила выбора baseline и тесты потребителя ADR 0017 не пересматриваются. Его текст описывает несовместимость baseline с diagnostics; настоящий ADR уточняет более широкое следствие версии общего модуля `metrics` для baseline любого вида.

ADR 0014 принят для измеренных лимитов и отдельно меняет identity через `limits`. По решению владельца эту смену identity не совмещать с ADR 0016: каждая вводится в своём окне пересчёта со своим повторным закреплением baseline (два независимых повторных закрепления). Блок `limits` настоящим ADR не затрагивается.

## Следствия

- В новых анализах p50, p95 и p99 могут стать ниже прежних опубликованных значений менее чем на 0,1 %, прежде всего когда HDR округлял значение выше фактического максимума. Условие `p50 <= p95 <= p99 <= max` гарантируется, но ложный `FAIL` у порога внутри эквивалентного диапазона остаётся возможным.
- Ячейки UTC load и корреляционные диагностики используют тот же p95 (`UtcLoadMetrics.kt:76-80`), поэтому в новых analyses при латентности от 2048 мс их входные значения могут снизиться менее чем на 0,1 %; результаты корреляций пересчитываются только при новом анализе, старые не меняются.
- Пустое окно показывает отсутствие измерения latency как четыре `null`. Нулевой throughput остаётся точным числом, а сэмпл длительностью 0 мс остаётся измерением.
- Стандартный CSV JMeter с Transaction Controller перестаёт считаться дважды без каких-либо действий пользователя: overall, RPS и ошибки считаются по дочерним, контроллер виден как транзакция и годится для SLA. Policy по label, общему для контроллера и дочернего, переходит от одной сводки к `AMBIGUOUS_TRANSACTION`. Для сравнений значение `subresults` должно быть одинаковым.
- Для сравнения с новыми analyses все сохранённые baseline любого вида потребуется закрепить заново. По решению владельца пересчёт проводится сразу после выпуска, окно пересчёта объявляется заранее, пока baseline немного. Старые analyses остаются читаемыми; история динамики отделяет их по семантическому ключу. Интерфейс уже объясняет несовместимость старого эталона (`ui/src/shell/labels.ts:57`).
- В одном старом analysis производный bucket p95 может отличаться от неизменяемого p95 в evidence. Это ожидаемое следствие применения нового правила чтения к старой гистограмме.
- Точность гистограммы становится параметром запуска: смена значения требует пересчёта и повторного закрепления baseline, но не правок ядра.
- Стоимость определения parent в CSV: для выбора режима файла нужен предварительный просмотр (первый проход может завершиться, как только найдены и parent, и не-parent строка; файл без parent-строк просматривается целиком). Допустимый вариант реализации выбирается при реализации; замер времени на CSV объёмом 1 ГиБ до и после входит в проверку.
- В PR реализации обновить `docs/architecture/slice-1-local-runtime.md` (матрица вклада, перцентили, identity, bucket `p95`, настройка точности), `docs/user/slice-1-local-analysis.md` (определение parent в CSV, ограничения, значение `subresults`, параметр точности), `CHANGELOG.md` и пометку в ADR 0003. Новых production-зависимостей и изменения схемы `analysis-result.v1` нет.

## Отклонённые альтернативы

- Колонка-маркер `ltv_transaction_controller_parent`: стандартный JMeter её не пишет, нужен конвертер, а необработанный файл по-прежнему считает parent дважды. Реальный JMeter даёт устойчивые стандартные признаки, поэтому маркер не нужен (решение владельца).
- Вывод parent по геометрии (вложенность по потоку и времени), порядку строк, `bytes` или `URL`: порядок зависит от режима «Generate parent sample», интервалы зависят от «Include duration of timer», `bytes` и `URL` не гарантируют различие. Предупреждающая диагностика без изменения чисел не вводится: сообщение при VALID-входе стало бы coverage reason и дало бы `NO_VERDICT`.
- Признак только по `responseMessage` без `dataType`: сервер или скрипт может вернуть такую reason phrase; пустой `dataType` отсекает HTTP-сэмплеры (проверено на реальном JMeter).
- «Все строки parent → `INVALID`/`EMPTY_INPUT`»: ломает валидный вход `subresults=false`, где контроллер единственная измеряемая единица.
- Повысить `significantDigits` по умолчанию: уменьшает ошибку, но меняет identity и расход памяти; само по себе не гарантирует `percentile <= observed max`. Вместо этого настройка точности.
- Хранить все latency для точного перцентиля: нарушает ограниченную по памяти потоковую модель.
- Брать нижнюю границу диапазона HDR: занижает наблюдаемый перцентиль и может дать ложный `PASS` для `lte`.
- Округлять к середине диапазона или вниз: также может занизить значение и не даёт нужной гарантии для `lte`.
- Оставить `0` вместо `null` в latency пустого окна: смешивает отсутствие выборки с настоящим сэмплом 0 мс.
- Публиковать `null` также для throughput пустого окна: теряет точный факт «ноль сэмплов за заданную длительность»; baseline-потребитель уже скрывает такое окно по `sample_count`.
- Игнорировать неизвестное содержимое при несовпадении шаблона сообщения с частью строки: частичное совпадение не принимается, чтобы не превращать произвольный текст в parent.
- Не менять identity: кэш (`AnalysisService.kt:133-134`) вернёт старый результат и исправление не проявится.
- Применять bucket cap только при новой версии модуля: потребует чтения identity в bucket API ради производного представления и оставит известное превышение у старых анализов.
- Задавать точность в запросе API или в policy: отдельный запрос менял бы определение метрик внутри серии baseline.
- Пересчитать `run-period.json` или поднять `run-period.v1`: затрагивает контракт ради фактов простоев; вынесено отдельной задачей при необходимости.
- Перезаписать старые analyses: нарушит неизменяемость сохранённых артефактов и точную привязку baseline из `0010-baseline-conditions-confirmation.md`.
- Совместить смену identity с ADR 0014: противоречит отдельным этапам и повторным закреплениям, выбранным владельцем.

## План проверки

1. У каждого нового непустого summary и производного p95 выполняется ограничение фактическим максимумом; для `lte` не появляется занижения точного перцентиля.

## Решения владельца (2026-10-02)

Открытых вопросов не осталось.

1. Повторное закрепление baseline: сразу после выпуска пересчитать все эталоны; окно пересчёта объявляется заранее, пока эталонов мало. ADR 0016 и ADR 0014 вводятся в разные окна: два независимых повторных закрепления.
2. Parent Transaction Controller в JMeter CSV: колонка-маркер не вводится; parent определяется стандартными признаками JMeter (точное сообщение и пустой `dataType`); с дочерними строками overall считается по дочерним, parent образует отдельный уровень транзакции; без дочерних parent остаются сэмплерами.
3. Ограничение перцентиля bucket API максимумом применяется ко всем анализам, включая старые, единообразно.
4. `significantDigits = 3` по умолчанию; точность гистограммы является настройкой анализа с описанным выше дизайном, без переписывания ядра; смена требует пересчёта.
5. Версии `jmeter-csv` и `jmeter-jtl-csv.v2` повышаются: принимаемый вход меняется.
6. Строгая трактовка значений: точное совпадение сообщения, пустой `dataType`, дубль колонки делает вход `INVALID`.
7. Throughput пустого окна остаётся числом `0 / duration`.
8. Golden-фикстуры берутся из реального JMeter; провенанс записывается в manifest.
9. Gatling-прогон только со строками `GROUP` остаётся известным остатком: `metric_summary` публикует нулевую латентность, политика даёт `NO_VERDICT` (`GatlingTextParser.kt:84-103`, `Policy.kt:213`); вне объёма ADR.

## Не входит

- Минимальный размер выборки и `INSUFFICIENT_SAMPLES`: это другой дефект и предмет ADR-B.
- Правила выбора baseline, сопоставимости и статусы пустого окна на стороне потребителя: они принадлежат ADR 0017.
- Измеренные лимиты и блок `limits` identity ADR 0014.
- Изменения Gatling и JMeter XML parser, в том числе обработка Gatling-прогона только с `GROUP`.
- Изменение схемы `analysis-result.v1`, Vue-кода и production-зависимостей.
- Пересчёт сохранённых `run-period.json`.
