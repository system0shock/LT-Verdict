# LT Verdict — регламент разработки для Codex и AI-агентов

**Дата:** 2026-08-10

**Статус:** согласованный дизайн

**Область:** Git-процесс, документация, контроль качества и правила работы AI-агентов

## 1. Цель

Создать для LT Verdict единый, понятный и проверяемый процесс разработки, ориентированный в первую очередь на одного разработчика и AI-агентов, но пригодный для подключения небольшой команды.

Регламент должен обеспечить:

- предсказуемую работу с ветками и worktree;
- атомарную и читаемую историю Git;
- явное закрытие этапов проекта и выпуск версий;
- обновление технической и пользовательской документации вместе с кодом;
- доказательную проверку результата до заявления о готовности;
- совместимость с процессными skills пакета Superpowers.

## 2. Принятый подход

Используется облегчённый GitHub Flow с защищённой веткой `main`, короткоживущими тематическими ветками и обязательными Pull Request.

Проектные нормы распределяются по трём уровням:

1. `AGENTS.md` — краткие обязательные инструкции для Codex и других AI-агентов.
2. `docs/development-process.md` — полный человекочитаемый регламент разработки.
3. `.github/` — шаблоны Pull Request и автоматические проверки GitHub Actions.

Отдельные проектные скрипты на данном этапе не создаются. Проверки, которые можно выполнить средствами GitHub Actions без усложнения репозитория, описываются непосредственно в workflow.

## 3. Рассмотренные альтернативы

### 3.1. Только `AGENTS.md`

Минимальная стоимость поддержки, но длинный файл хуже читается, а соблюдение правил остаётся недоказуемым. Вариант отклонён.

### 3.2. `AGENTS.md` + документация + GitHub Actions

Краткие инструкции остаются в контексте агентов, подробности доступны людям, а механические требования проверяются независимо. Это выбранный вариант.

### 3.3. Собственные project skills и набор локальных скриптов

Даёт больше автоматизации, но дублирует существующие процессы Superpowers и преждевременно увеличивает стоимость поддержки. Вариант отложен до появления подтверждённой необходимости.

## 4. Совместимость с Superpowers

Проект не вводит skills, заменяющие или сокращающие процессы Superpowers.

| Проектная потребность | Используемый Superpowers skill | Дополнение проекта |
|---|---|---|
| Проработка новой функции или поведения | `superpowers:brainstorming` | Ссылки на PRC, этап и критерии выхода |
| Подготовка реализации | `superpowers:writing-plans` | Проектные команды проверки и требования к документации |
| Изоляция изменений | `superpowers:using-git-worktrees` | Правила именования веток |
| Реализация и исправления | `superpowers:test-driven-development` | Технологические тестовые команды после появления кода |
| Диагностика ошибок | `superpowers:systematic-debugging` | Доменные инварианты LT Verdict |
| Доказательство готовности | `superpowers:verification-before-completion` | Проектный Definition of Done и exit gate этапа |
| Ревью | `superpowers:requesting-code-review` и `superpowers:receiving-code-review` | PR-шаблон и обязательные проектные проверки |
| Завершение ветки | `superpowers:finishing-a-development-branch` | Запрет самостоятельного push, merge, тегирования и релиза без разрешения пользователя |

Если проектная инструкция и Superpowers описывают один процесс, агент следует Superpowers, а проектную инструкцию применяет как дополнительное ограничение. Прямая инструкция пользователя имеет высший приоритет.

Согласно `superpowers:writing-skills`, новые skills допустимы только для самостоятельной, неочевидной и повторяемой техники. Проектные соглашения остаются в `AGENTS.md`, а механически проверяемые требования — в CI. Перед созданием любого skill обязателен цикл RED–GREEN–REFACTOR с проверкой поведения агента без skill и с ним.

## 5. Git-процесс

### 5.1. Ветки

- `main` должна оставаться работоспособной и пригодной для выпуска.
- Прямые изменения и push в `main` запрещены.
- Каждая задача реализуется в отдельной короткоживущей ветке или worktree.
- Допустимые префиксы: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`, `chore/`.
- После префикса используется короткое описание в kebab-case, например `feat/stage-1-run-registration`.
- Одна ветка и один PR содержат одну законченную задачу без посторонних изменений.
- Перед слиянием ветка должна быть актуальна относительно `main`, если расхождение влияет на результат проверок или создаёт конфликт.

### 5.2. Коммиты

- Используется Conventional Commits: `<type>(<optional-scope>): <imperative summary>`.
- Допустимые основные типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`, `ci`, `chore`, `perf`, `revert`.
- Заголовок формулируется в повелительной форме, описывает результат и не заканчивается точкой.
- Коммит должен быть атомарным: его можно понять, проверить и при необходимости отменить отдельно.
- Форматирование, рефакторинг и изменение поведения не смешиваются без необходимости.
- Тесты и документация, без которых изменение неполно, входят в тот же логический набор коммитов.
- Агент добавляет в индекс только файлы своей задачи и не использует широкое `git add .` при наличии посторонних изменений.
- Агент не изменяет, не переписывает и не объединяет пользовательские коммиты без явного разрешения.

### 5.3. Pull Request и слияние

- Каждый PR связывается с задачей и GitHub Milestone либо явно объясняет отсутствие связи.
- Заголовок PR соответствует Conventional Commits и становится итоговым сообщением squash-коммита.
- Описание содержит цель, границы изменения, способ проверки, влияние на документацию и известные риски.
- Для слияния необходимы зелёный CI, выполненный Definition of Done и ревью diff.
- Используется Squash and Merge, чтобы `main` содержала один итоговый коммит на задачу.
- Агент не выполняет push, merge, rebase общей ветки, создание тега или релиза без явного разрешения пользователя.

## 6. Майлстоуны и версии

Этапы проекта и версии поставляемого продукта учитываются раздельно.

### 6.1. Этапы проекта

- Для этапов плана создаются GitHub Milestones вида `Stage 0 — Discovery`, `Stage 1 — Ingest Core` и далее.
- Issue и PR относятся к конкретному этапу либо явно помечаются как внеплановые.
- Этап закрывается только после выполнения exit gate, зелёного CI, обновления документации и фиксации известных ограничений.
- Результат закрытия описывается в `docs/milestones/stage-N.md`.
- Отчёт содержит достигнутый результат, ссылки или команды проверок, ограничения, незакрытые риски и решение о переходе к следующему этапу.
- На закрывающий коммит в `main` ставится подписанный аннотированный тег `stage-N`.
- Тег этапа неизменяем и не переносится на другой коммит.

### 6.2. Версии продукта

- Поставляемые версии следуют Semantic Versioning: `v0.1.0`, `v0.2.0`, затем `v1.0.0`.
- `CHANGELOG.md` ведётся по принципу Keep a Changelog.
- Изменения добавляются в секцию `Unreleased` в том же PR, где появляется пользовательски заметное изменение.
- При выпуске секция `Unreleased` получает номер версии и дату; сверху создаётся новая пустая секция `Unreleased`.
- Версионный тег является подписанным и аннотированным; он ставится только на проверенный коммит в `main` после явного разрешения пользователя.

## 7. Документация

Документация является частью продукта и обновляется в том же PR, что и соответствующее изменение.

### 7.1. Целевая структура

- `README.md` — назначение, статус, быстрый старт и навигация.
- `docs/architecture/` — архитектура, компоненты, потоки данных и ограничения.
- `docs/adr/` — значимые технические решения, альтернативы и последствия.
- `docs/api/` — контракты API и проверяемые примеры.
- `docs/operations/` — развёртывание, конфигурация, эксплуатация и диагностика.
- `docs/user/` — пользовательские сценарии, инструкции, терминология и FAQ.
- `docs/milestones/` — отчёты о закрытии этапов.
- `docs/superpowers/specs/` — утверждённые дизайны.
- `docs/superpowers/plans/` — планы реализации.

### 7.2. Правила актуальности

- Изменение поведения обновляет соответствующую пользовательскую документацию.
- Изменение архитектуры, API, конфигурации или схемы данных обновляет техническую документацию.
- Значимое решение, меняющее границы компонентов, публичный контракт, модель данных или эксплуатационные свойства, фиксируется ADR.
- Документация не откладывается на отдельную будущую задачу.
- Если документация не требуется, PR содержит явное обоснование `Documentation impact: none`.
- Команды и примеры проверяются перед слиянием.
- Основной язык документации — русский; идентификаторы кода, API, команды и стандартные технические термины сохраняются на английском.
- Устаревший документ заменяется, помечается как superseded или переносится в архив со ссылкой на актуальный источник.

## 8. Правила работы AI-агентов

### 8.1. Делегирование и выбор модели субагента

Superpowers определяет, когда задача допускает или требует делегирования. Проектная политика не заменяет `superpowers:dispatching-parallel-agents`, `superpowers:subagent-driven-development` и `superpowers:requesting-code-review`, а только задаёт модель и reasoning effort для уже обоснованного вызова субагента.

| Класс работы | Модель | Reasoning effort | Примеры |
|---|---|---|---|
| Механическая, массовая, с однозначным результатом | `gpt-5.6-luna` | `low` | поиск файлов и ссылок, инвентаризация, извлечение фактов, проверка форматирования, применение заранее определённого преобразования |
| Обычная инженерная работа и простое ревью | `gpt-5.6-terra` | `medium` | анализ отдельного модуля, реализация ограниченной задачи по готовому плану, написание тестов, проверка локального diff с ясными критериями |
| Сложная инженерная задача | `gpt-5.6-terra` | `high` | анализ нескольких компонентов, нетривиальная диагностика, реализация с несколькими интерфейсами или значимыми компромиссами |
| Сложное и риск-ориентированное ревью | `gpt-5.6-sol` | `max` | безопасность, конкурентность, целостность данных, миграции, публичные контракты, архитектурные изменения, производительность и milestone gate |

Правила делегирования:

- модель выбирается по риску и требуемому суждению, а не по размеру текста задачи;
- механическая задача должна иметь явный вход, ожидаемый формат результата и проверяемый критерий завершения;
- Luna не принимает архитектурных решений, не выполняет сложное ревью и не утверждает готовность результата;
- простое ревью считается сложным и передаётся Sol Max, если оно затрагивает хотя бы одну из перечисленных риск-областей;
- независимые задачи можно делегировать параллельно; задачи с общей изменяемой областью или последовательной зависимостью выполняются последовательно;
- корневой агент проверяет вывод субагента и несёт ответственность за итоговое решение;
- если требуемая модель недоступна, используется ближайшая более сильная доступная модель с не меньшим reasoning effort;
- сложное ревью нельзя понижать до Luna; при недоступности Sol Max корневой агент сообщает об ограничении и не объявляет review gate пройденным без согласованной замены.

Названия `Luna`, `Terra` и `Sol Max` в проектной документации означают соответственно `gpt-5.6-luna` с `low`, `gpt-5.6-terra` с указанным для класса effort и `gpt-5.6-sol` с `max`.

### 8.2. Обязательный рабочий порядок

Перед изменениями агент:

1. Загружает применимые инструкции и skills.
2. Проверяет `git status`, текущую ветку и наличие посторонних изменений.
3. Изучает относящиеся к задаче PRC, спецификации, ADR и планы.
4. Определяет проверяемые критерии готовности.
5. Для реализации использует отдельную ветку или worktree согласно Superpowers и ограничениям среды.

Во время работы агент:

- сохраняет пользовательские изменения и не исправляет несвязанные проблемы;
- следует утверждённой спецификации и плану;
- применяет TDD к функциям, исправлениям, рефакторингу и изменениям поведения;
- при неожиданном результате переходит к систематической диагностике;
- не добавляет production-зависимость и не меняет публичный контракт без явного отражения этого решения в плане или ADR;
- делает небольшие тематические коммиты только из файлов своей задачи;
- обновляет документацию вместе с изменением.

Перед заявлением о готовности агент:

1. Повторно читает требования и проверяет их по пунктам.
2. Просматривает полный diff и `git status`.
3. Запускает свежие применимые тесты, сборку, линтеры и документальные проверки.
4. Проверяет отсутствие секретов, временных файлов и несвязанных изменений.
5. Проводит ревью согласно Superpowers.
6. Сообщает выполненные команды, их результат, ограничения и непроверенные предположения.

Агент не объявляет задачу, этап или релиз завершёнными без свежих доказательств проверки.

## 9. GitHub Actions без проектных скриптов

На документальной стадии CI должен проверять:

- корректность Markdown;
- работоспособность внутренних и внешних ссылок с допустимой политикой повторных попыток для временно недоступных внешних ресурсов;
- формат заголовка PR как Conventional Commit;
- отсутствие очевидных секретов.

После появления исполняемого кода CI расширяется проверками проекта:

- сборка;
- unit- и integration-тесты;
- статический анализ и форматирование;
- проверка миграций базы данных;
- проверки API-контрактов;
- специализированные performance- и golden-тесты, предусмотренные спецификацией этапа.

Workflow используют закреплённые версии GitHub Actions. Проверки не должны автоматически изменять файлы PR.

## 10. Definition of Done

Задача считается готовой, когда одновременно выполнены все применимые условия:

- требования и критерии приёмки выполнены;
- для изменения поведения подтверждён цикл RED–GREEN–REFACTOR;
- свежие проверки CI проходят;
- полный diff просмотрен и отревьюирован;
- техническая и пользовательская документация обновлена либо обоснованно не требуется;
- значимые решения зафиксированы в ADR;
- пользовательски заметные изменения добавлены в `CHANGELOG.md`;
- в изменениях нет секретов, временных файлов и несвязанного содержимого;
- известные ограничения и риски явно перечислены;
- слияние, тегирование и публикация выполняются только после решения пользователя.

Этап проекта считается закрытым только при выполнении Definition of Done всех входящих задач, exit gate этапа, milestone-отчёта и постановки разрешённого пользователем подписанного аннотированного тега.

## 11. Обработка исключений

- Если обязательная проверка недоступна, агент не считает её пройденной: он описывает причину, риск и способ последующей проверки.
- Если существующие тесты не проходят до начала работы, агент фиксирует baseline и запрашивает решение перед продолжением реализации.
- Если правило неприменимо, PR должен объяснить это наблюдаемым условием, а не общим утверждением.
- Срочность не отменяет TDD, проверку, документацию или пользовательское разрешение на операции с удалённым репозиторием.
- Исправления регламента проходят тот же PR-процесс, что и остальные изменения.

## 12. Критерии внедрения регламента

Регламент считается внедрённым, когда:

- в корне создан согласованный `AGENTS.md`;
- создан `docs/development-process.md`;
- создан шаблон Pull Request;
- настроены применимые проверки GitHub Actions без отдельных проектных скриптов;
- существующие документы получили понятную навигацию из `README.md` либо отмечены как исторические;
- правила проверены на одном тестовом документальном PR до начала основной реализации.
