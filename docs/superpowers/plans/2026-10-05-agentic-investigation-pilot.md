# Агентное расследование ИИ: отчёт разведки Qwen Code и план пилота на headless Codex

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ответить на предложение владельца (расширить ИИ-разбор до агентного расследования) ограниченным пилотом в харнессе на **headless Codex** (решение владельца 2026-10-06: лимиты Qwen на исходе): проверить осуществимость, безопасность контура и описательное качество расследования относительно одношагового разбора (prompt v1/v2) и руки C плана ИИ. Поведение Qwen Code 0.21.1 (нативные `agent` и `workflow`, реестр, бюджеты) изучено пробами на mock relay (Часть 1) и пилотом **не проверяется**.

**Architecture:** пилот не меняет продукт. Инструменты ядра и чтения репозитория исполняет шлюз; шлюз ничего не вычисляет, а отдаёт заранее записанные ответы ядра («пакет ответов») и маскированное содержимое снимка репозитория и не имеет маршрута наружу; в пилоте шлюз вызывает харнесс, модель к нему не подключается. Единственная рука расследования: D2, своя оркестрация вокруг одиночных вызовов `codex exec` (один шаг равен одному вызову), порядок и рецензия заданы кодом. Руку D1 (нативный `agent` Qwen) пилот не исполняет. Харнесс ведёт счётчик запросов пилота (ledger) с резервом до вызова, отделяет данные пилота от данных продукта и пишет журнал источников и действий. Раннер продукта (Qwen, relay, две сети, токен шлюза) описан в ADR 0024 Д2 и проверяется отдельно перед продуктизацией.

**Tech Stack:** Codex CLI (`codex exec`, пилот), Node.js (шлюз, заглушка `codex` для тестов), Python (харнесс, `unittest`), PowerShell. Docker Engine 29.2.1 и Qwen Code 0.21.1 нужны только для проб Части 1 и для проверки Qwen до продукта. Новых production-зависимостей нет.

### 1.3 Оценка осуществимости нативного workflow (Qwen)

1. **Технически осуществимо** при конфигурации: `--safe-mode`, без `--bare`, `--mcp-config` (HTTP к контейнеру инструментов), `--allowed-mcp-server-names=ltcore`, `--exclude-tools` по точному перечню (все инструменты, кроме `agent` и `structured_output`), `--allowed-tools=agent`, агенты в `/work/.qwen/agents` (read-only mount), `cwd` не репозиторий, relay с лимитом запросов и сверкой модели. Это **не** текущая изоляция ADR 0010 п. 6, а её замена набором проверок.
2. **Нативный `workflow` (скрипт) не рекомендуется**: модель сама пишет JS, исполняемый в `node:vm`; `maxTurns` агента перекрыт 50 ходами; лимит агентов по умолчанию 1000; токеновый бюджет мягкий (проверяется на входе диспетчера, проба: перерасход 1000 из 700); родитель всё равно решает, вызвать ли `workflow`; ещё 4,4 КБ описания на каждый запрос. Нативный `agent` проще и поддаётся ограничению `maxTurns`.
3. **Порядок и независимость рецензии не принуждаются**: hooks под `--safe-mode` недоступны, `structured_output` доступен с первого хода. Продукт может только проверить журнал после запуска и отказать в публикации.
4. **Цена**: запрос основного агента 27-39 КБ против 5,3 КБ у одношагового разбора (описание `agent` 12 КБ), минимальный конвейер orchestrator + researcher + reviewer 7-11 запросов и 76-212 КБ суммарно (пробы `r15`, `r3s`, `r3`) без реального evidence.
5. **Вывод**: нативный путь достаточен для **эксперимента**; для продукта аргументов в его пользу меньше, чем у своей оркестрации (D2): экономии запросов нет, исключений из ADR 0010 больше, порядок недетерминирован. Выбор между D1 и D2 **для продукта** откладывается до живой проверки Qwen (вопрос 15); в пилоте на Codex D1 не исполняется.

### 1.4 Бюджет и контроль (Qwen)

| Механизм | Что реально ограничивает (проба) | Достаточность |
| --- | --- | --- |

### 1.5 Оценка запросов, токенов и задержки (Qwen и ModelStudio; оценка)

Число запросов для нативной руки: `N = (m + 1) + Σ(k_i + 1)`, где `m` число вызовов `agent`, `k_i` число раундов вызовов инструментов у ребёнка `i` (параллельные вызовы раунда считаются одним). Пример пробы `r15`: `m = 2`, researcher `k = 1`, reviewer `k = 1`, итого `3 + 2 + 2 = 7`. Типичный случай расследования: `m = 2`, `k_1 = 3`, `k_2 = 2` дают 10; ошибка схемы итога добавляет 1 (ADR 0021 Д2); предел relay 16. Для руки D2 (свои одиночные вызовы) число запросов по тому же порядку: шаги расследования `s` плюс рецензия плюс итог (6-12); именно эти числа (около 10 на расследование, потолок 16, 11 в смоке) использует бюджет пилота ниже, где один шаг равен одному вызову `codex exec`.

Входные токены (оценка, 3,5-4 байта на токен, evidence порядка 6,5 тыс. токенов как в экспериментах ADR 0021): одношаговый разбор около 7 тыс.; нативный запуск `3 × (6,5 + 7,7) тыс.` на основном агенте плюс контексты детей (исследователь около 21 тыс., рецензент около 6 тыс.) то есть порядка 70 тыс., то есть в 8-12 раз больше. Выходные токены: основной итог около 13-16 тыс. (как в наблюдении прежних серий для других моделей) плюс 2-6 тыс. на каждый вспомогательный ход, то есть в 2-3 раза больше. Задержка: последовательные запросы; один запрос DeepSeek 57-131 с (итоговый), короткие ходы короче; ожидание 5-20 минут на расследование против 1-2 минут; для GLM 5.3 ещё в 2-3 раза больше. **Это не измерение и не прогноз для Codex**: токены и задержку Codex пилот измерит, если проба покажет, что `usage` и время доступны (метрики ниже); на Qwen эти числа остаются оценкой до живой проверки.

### 2.1 Инструменты ядра

Закрытый набор v1 только чтение (ADR 0024 Д3): `core_facts_list`, `core_result_get`, `core_series_catalog`, `core_series_values`, `core_compare_baseline`, `core_verify_number`; инструменты репозитория `repo_list`, `repo_read`, `repo_search`. Инструмент это **поиск готового ответа ядра**, а не вычисление в шлюзе. Пилот собирает **пакет ответов ядра** (`ltcore-tool-pack.v1`, закрытая структура пилота вне git и вне контрактов продукта) скриптом на хосте, который вызывает существующие GET-маршруты запущенного приложения: серии (`resource-series`, `resource-series/values`, D0a), `comparison`, `result` и проекцию evidence; пакет монтируется в шлюз read-only. Запрос вне пакета даёт `OUT_OF_LIMIT`. Продуктовый код не меняется, шлюз не имеет маршрута наружу (приложение слушает только `127.0.0.1` и проверяет `Host`, так что из контейнера оно недостижимо без нового listener: вопрос 13). `core_verify_number` ищет значение по ссылке или серии и сравнивает с заявленным, арифметики не выполняет; `core_stat` из v1 исключён (считать перцентили в Node это не ядро; p50/p95/p99 уже в `result`). Контракт ответа: `tool_contract`, `call_id`, `analysis_manifest_sha256`, `result`, `result_sha256`, `truncated`, `notes[]`, типизированные ошибки. Воспроизводимость: один вызов при тех же `pack_sha256`, `snapshot_tree_sha256`, `tool_version` и `masking_version` даёт тот же `result_sha256` (ADR 0024 Д3, п. 4); повтор журнала даёт побайтно те же ответы. Корреляции только прочитанные из сохранённого результата (заголовки ADR 0022); новых ad hoc корреляций в v1 нет (множественные сравнения).

### Контракт relay продукта (раннер Qwen; не исполняется в пилоте на Codex)

Этот раздел относится к AG6Q и AG7. Текущий relay продукта пилоту и руке D1/D2 на Qwen не подходит и копируется как есть быть не может: он (после #78) допускает ровно один инструмент `structured_output`, только текстовые сообщения (кроме продолжения повтора схемы) и не более двух запросов, а модель не отклоняет, а перезаписывает на закреплённую до проверки (`tools/advisory_ai_runtime_relay.mjs:82-100`, `:109`, `:118-124`, `:341-358`, `:383-387`). Relay расследования (копия `relay2.mjs` плана ИИ) обязан:

1. проверять `model` во **входящем** теле до перезаписи, отклонять несовпадение (409) и писать в журнал;
2. для каждого запроса определять роль по SHA-256 системного prompt (оркестратор, исследователь, рецензент; в руке D2 шаги) и требовать, чтобы множество имён инструментов запроса **в точности равнялось** списку роли (`mcp__ltcore__...`); неизвестный prompt или лишнее имя: 409 и счётчик;
3. допускать сообщения ролей `assistant` с `tool_calls` и `tool`, не расширяя набор инструментов;
4. считать и ограничивать пересланные запросы на расследование (16) с атомарным резервом до пересылки;
5. ограничивать размеры тела запроса и ответа, писать журнал запроса (роль, размер, исход, `usage`) без текстов.

В пилоте на Codex эти проверки замещает харнесс (ledger, шаги D2, журнал вызовов); соответствие условий проверяет AGP.

### Методика сравнения

1. **Руки.** A: prompt v1, один запрос; B: prompt v2, один запрос (ADR 0021); C: черновик, проверка, итог тремя одиночными вызовами (W1 плана ИИ, если к моменту пилота выполнена); D2: расследование своей оркестрацией (AG2); E: дешёвая база сравнения: одношаговый совет (prompt v2) с заранее отобранными детерминированным правилом фрагментами репозитория (файлы по именам сервисов и ключам конфигурации из evidence), без агента и без рецензента. Руки D1 нет: нативный `agent` есть только в Qwen. Все руки идут на одной Codex-модели с одним уровнем рассуждения, замороженными предрегистрацией; управляемость temperature не проверена, повторяемость описательная.
2. **Случаи.** 8 repo-случаев AG3 и 4 evidence-only случая из K01-K12. Прежние результаты рук S0 и S1 эксперимента ADR 0021 на K01-K12 получены на DeepSeek и с моделью пилота несопоставимы: руки A и B на 4 evidence-only случаях **прогоняются заново** на модели пилота (по одному запросу на случай и руку, 8 запросов). Для repo-случаев новые запросы нужны для A, B и E (3 × 8 = 24) и, если рука C доступна, для C (24).
3. **Холдаут не используется.** Выбор случаев и правил фиксируется предрегистрацией до первого вызова.
4. **Разметка.** Слепой пул, перемешивание, два рецензента-модели, человека нет (как в ADR 0021 Д7); итог маркируется «model-reviewed». Рецензенты (Codex) и модель пилота (Codex) из одного семейства: смещение не исключено, публикуется. Для repo-случаев оракул причины и детерминированные Q4, Q5 не зависят от рецензентов. Утверждения о коде рецензент оценивает по цитируемым фрагментам снимка, которые пул предоставляет вместе с ответом.
5. **Сопоставимость.** Рука D2 получает больше информации (код, ядро), чем A и B; прямое сопоставление качества по repo-случаям нечестно по построению (A и B кода не видят). Поэтому: на repo-случаях D2 сравнивается с E и (если есть) C; на evidence-only случаях D2 сравнивается с A и B как проверка отсутствия ухудшения (рука C на них не запускается и не финансируется); стоимость и задержка сравниваются на всех. Рука E отвечает на вопрос, сколько эффекта на repo-случаях даёт сам доступ к коду, а сколько агентность: если E близка к D2 по попаданию причины, агентность не окупается.
6. **Статистика.** При n = 12 выводы описательные: таблицы, интервалы Уилсона, парный знаковый тест только там, где различий не меньше 5; никаких заявлений об эффекте без правила, зафиксированного заранее.
7. **Перенос.** Результаты по качеству читаются как направление для модели, приравненной к GLM 5.3, а не как величины для боевой модели; стоимость, задержка и пороги по запросам и времени не переносятся на Qwen (ADR 0024 Д10, п. 5).

### Критерии продолжения и остановки (предложение автора, подтверждает владелец до первого вызова; вопрос 12)

Остановка немедленная (любое одно): исполненная канарейка, утечка приманки секрета в advice, журнал или UI, выход за корень или запись, чтение мимо шлюза (если поток событий это показывает), запись в каталог данных продукта, изменение хэшей анализа, случай вне манифеста, превышение предела расследования или предела пилота.

Продолжение на AG6 после дымового прогона (G4), если выполнено всё: Q4 100 %, Q5 100 % либо пометка, S1-S4 чисты, медианная задержка не больше 15 минут, не OK (в том числе остановленных пределом 11 до итога) не больше 1 из 3 запусков (в первой редакции было 1 из 6 при двух руках; при одной руке выборка вдвое меньше, порог подтверждает владелец, вопрос 12). Пороги «медиана запросов не больше 12, p95 не больше 16» из первой редакции действуют в AG6 (предел 16); в смоке при пределе 11 они ничего бы не отсеяли. Пороги по запросам и времени относятся к Codex-пилоту и являются порогами решения «стоит ли тратить дальше», а не доказательством качества и не прогнозом для Qwen.

**Решение о дальнейшей работе** (G5; владелец по итогам AG6; это не принятие режима и не утверждение о качестве): продолжать к предрегистрированному холдауту на реальных инцидентах с человеческой оценкой стоит, если выполнено всё: на repo-случаях внесённая причина в топ-3 минимум в 5 из 8 и рука D2 не хуже руки E по этому показателю более чем на 1 случай в пользу E; на evidence-only случаях подтверждённых `hard_defect` не больше, чем у руки B, плюс 1 из 4; стоимость и задержка приемлемы владельцу. Иначе режим отклоняется, продукт остаётся на prompt v1/v2 и (по W5 плана ИИ) возможной руке C. Пилот не даёт оснований для общего вывода о качестве: восемь случаев с внесёнными дефектами, руки A и B без доступа к коду, модель, не равная боевой, и две модели-рецензента без человека. Положительное решение G5 не снимает G6 (живая проверка Qwen).
