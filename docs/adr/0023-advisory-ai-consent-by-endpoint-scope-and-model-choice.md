# ADR 0023: Согласие на отправку в ИИ по области endpoint и выбор модели в UI

Дата: 2026-10-04.

Статус: Proposed. Решения владельца 2026-10-04 (раздел «Контекст», п. 1)
фиксируют намерение, а механизм ниже предложен автором и не принят владельцем:
вопросы с рекомендациями собраны в разделе «Вопросы владельцу». Этот ADR
ничего не меняет в коде, контрактах, схемах, prompt и пользовательских
документах. Номер 0023 выбран как следующий после 0022; перед слиянием его
нужно перепроверить по `origin/main` (на 2026-10-04 файлов с номером 0023 и выше
нет ни в `docs/adr/`, ни в открытых ветках).

Связь. ADR [0010](0010-advisory-ai-boundary.md) и ADR
[0021](0021-advisory-ai-prompt-v2-and-schema-retry.md) (Accepted) не
переписываются: добавлены только ссылки и поправки в их разделах «Последствия» и
«Следствия». ADR 0021 Д5 («механизм выбора модели не вводится сейчас, при
решении о смене модели отдельным PR», решение владельца по вопросу 8 от
2026-10-04) этим ADR **пересматривается по прямому указанию владельца**: выбор
модели теперь запрошен. Закрытый append-only набор моделей, параметр
`-ModelId`, сверка модели в relay и тест согласованности берутся из Д5 без
изменений; новое здесь только выбор на каждый запрос из набора, разрешённого
развёртыванием.

## Контекст

### 1. Решения владельца 2026-10-04

Источник: сообщения владельца, переданные оркестратором (отдельной письменной
записи в репозитории нет; практика та же, что в ADR 0021). Прямые цитаты:

- «Галочку про "разрешаю отправку" нужно вообще убрать. Не забудь про выбор
  модели.»
- «В боевой системе используется headless qwen.» (про инференс ИИ-разбора;
  ранее: «Инференс он-прем, безопасность обеспечена»).

Из них следуют два решения: (А) убрать согласие на отправку из продукта; (Б)
добавить выбор модели в UI. Текст согласия про Alibaba ModelStudio в боевой
системе убирается.

### 3. Что эти решения меняют по существу

Согласие защищает от **неосознанной внешней передачи**: пользователь явно
видит, что evidence анализа (метки транзакций и ресурсов, пути групп, метрики,
идентификаторы правил) и системный prompt уходят провайдеру в Сингапуре. Это
единственный механизм продукта, который выражает границу «данные покинули
периметр». Выше по стеку защита другая: ADR 0010 отсекает credential, SQL и
log-тела, но метки транзакций и ресурсов в evidence входят.

Если боевой инференс on-prem и endpoint лежит внутри периметра, согласие
действительно теряет смысл: передачи за периметр нет, пользователь ничего не
разрешает. Но:

1. **Сегодня «on-prem» не свойство кода.** Продукт ничем не отличает внутренний
   endpoint от внешнего: единственный раннер внешний. Утверждение «безопасность
   обеспечена» относится к развёртыванию, которого в репозитории нет. Если
   убрать галку безусловно, **текущий** раннер начнёт отправлять evidence в
   Сингапур по одному клику без предупреждения.
2. **Защита исчезает при подключении внешнего endpoint.** Без механизма, который
   привязывает отсутствие согласия к проверяемому свойству назначения, любая
   смена endpoint (ошибка конфигурации, подмена профиля, новый раннер)
   превращается в тихую внешнюю передачу.
3. **Слова «headless qwen» подтверждают только то, что CLI headless.** Это уже
   верно для текущего раннера. Что именно в боевой системе отличается
   (endpoint, протокол, модель, нужен ли relay, как проверяется «внутри
   периметра»), в репозитории не описано; это входные данные владельца для
   отдельного ADR раннера (вопрос 3).
4. **Галка PR #40 несёт и намерение.** Она не только разрешает отправку, но и
   включает автозапуск совета после анализа. ADR 0010 начинается словами
   «запускается только явно». Убрать галку целиком значит либо запускать ИИ
   после каждого анализа (время, нагрузка, `Busy`), либо потерять автозапуск;
   нужен ответ владельца (вопрос 4).
5. **Выбор модели упирается в ADR 0010, п. 4.** Совет иммутабелен и один на
   analysis; выбор другой модели для анализа, у которого совет уже есть, вернёт
   старый совет. Сравнивать модели на одном анализе правило не позволяет
   (вопрос 6).

## Решение (предлагается)

### Д1. Согласие определяется назначением, а не пользователем

**Рекомендованный механизм (вариант Б из раздела «Варианты»).** Требование
согласия выводится из **области endpoint** активного профиля назначения:
`endpoint_scope` принимает значения `external` и `internal`.

1. **Профиль назначения** — закрытый набор в коде (не registry провайдеров,
   как и в ADR 0021 Д5, п. 1): `endpoint_scope`, подпись назначения
   (`endpoint_label`), закрытый список моделей. Сейчас один профиль: ModelStudio
   (Singapore), `endpoint_scope = external`, подпись «Alibaba ModelStudio
   (Singapore)», модель `deepseek-v4-flash-0731`.
2. **Область не настраивается отдельным флагом.** ADR 0010, п. 6: «конфигурационный
   флаг не может объявить boundary проверенной». Поэтому самостоятельной
   настройки `endpoint_scope=internal` нет: профиль ModelStudio всегда
   `external`, и перемаркировать его нельзя. `internal` появляется только вместе
   с профилем on-prem раннера, чей ADR определяет, что именно продукт проверяет
   (например: адрес назначения из закрытой конфигурации; relay или сеть
   контейнера, у которых нет маршрута наружу; запрет прямого egress). До такого
   ADR значение `internal` недостижимо; это не недосмотр, а граница решения.
3. **Состояние по умолчанию и отказ в закрытом режиме.** Нет профиля, область
   неизвестна, конфигурация не читается: считается `external`, согласие
   обязательно. Это поведение текущей реализации; она остаётся безопасной.
4. **Сервер — единственный источник правды.** Клиент область не присылает и не
   выбирает; сервер проверяет согласие по области активного профиля. Скрытая
   клиентом галка не влияет на безопасность: запрос без согласия при `external`
   получает 400.
5. **Область фиксируется в provenance** (Д4) как факт: куда фактически ушло
   evidence этого совета.

| | `external` | `internal` |
| --- | --- | --- |
| API | Тело `{"confirm_external_transfer":true}` обязательно (как сегодня); иначе 400 `MALFORMED_REQUEST` | Согласие не требуется; принимаются пустое тело, `{}` и прежнее `{"confirm_external_transfer":true}` (обратная совместимость клиентов; значение игнорируется) |
| UI, вкладка «ИИ-разбор» | Чекбокс и текст согласия с подписью назначения из профиля; кнопка заблокирована без согласия | Чекбокса нет; строка факта «Внутренний инференс: данные не покидают контур»; кнопка доступна сразу |
| UI, «Новый анализ» (PR #40) | Галка согласия и автозапуска, текст согласия с подписью назначения из профиля | Переключатель «Запросить ИИ-разбор после анализа» без слов «разрешаю» и без текста про отправку: это намерение запуска, не согласие (вопрос 4) |
| Provenance | `endpoint_scope: "external"` | `endpoint_scope: "internal"` |

### Д2. Изменения API (аддитивные)

1. **Конфигурация ИИ в `GET /api/bootstrap`** (рекомендация; альтернатива —
   отдельный `GET /api/ai/config`, вопрос 8). Область и список моделей
   неизменны на всё время жизни процесса, а UI читает bootstrap один раз при
   старте. Новое поле `advisory_ai`: объект
   `{ "endpoint_scope": "external|internal", "endpoint_label": "…", "models":
   [{"id": "…", "label": "…", "measured": true|false}], "default_model_id":
   "…" }` либо `null`, если ИИ не подключён. Существующие поля не меняются;
   это правка закрытого списка ADR 0002 (`{csrf_token,max_upload_bytes}`),
   поэтому она записывается здесь, а тесты bootstrap расширяются.
2. **Тело `POST .../advice`: закрытый разбор вместо regex.** Допустимы ключи
   `confirm_external_transfer` (булево, `true`) и `model_id` (строка из набора
   Д5); остальные ключи, дубликаты и объект больше 256 байт дают 400. Защита
   от неоднозначных дубликатов JSON-ключей, ради которой регулярное выражение
   появилось (комментарий в `LocalApi.kt:817`), сохраняется явной проверкой на
   дубликаты. Пустое тело допустимо только при `internal`.
3. **Статус задания** (`GET/DELETE /api/advice-jobs/{id}`, ответ `POST`):
   аддитивное поле `model_id` (выбранная или принятая по умолчанию модель). Это
   закрывает ограничение плана ADR 0021 (вопрос В5): модель видна и у `FAILED`
   или `UNAVAILABLE`, где provenance нет.
4. Коды ошибок не добавляются: неизвестная или не разрешённая развёртыванием
   модель, а также тело, недопустимое для области (например, `external` без
   согласия), дают существующий 400 `MALFORMED_REQUEST`. Перечни `AdviceFailure` и `AdviceUnavailableReason` не
   меняются.

### Д3. UI

1. Конфигурация берётся из `bootstrap()`; если её нет или она не разобрана,
   UI ведёт себя как при `external` (показывает согласие). На безопасность это
   не влияет (Д1, п. 4), только на удобство.
2. Подпись назначения в тексте согласия и в `willAdvice` берётся из
   `endpoint_label`, а не из строки в компоненте: после смены профиля старый
   текст про ModelStudio не остаётся неправдой. Владелец сказал убрать текст
   про ModelStudio; в `internal` его нет, в `external` текст остаётся, иначе
   пользователь отправляет данные в Сингапур, не видя этого (вопрос 1).
3. Выбор модели: список из `advisory_ai.models` в обоих местах (вкладка
   «ИИ-разбор» и раздел «ИИ-разбор» экрана «Новый анализ»); предвыбрана
   `default_model_id`; при одной модели селектора нет, показывается её подпись.
   Выбор живёт только в состоянии страницы (браузерное хранилище запрещено
   правилами UI-плана). До запроса показывается выбранная модель; после ответа
   и в `FAILED`/`UNAVAILABLE` (поле `model_id` задания) та же модель; в готовом
   совете значения берутся из provenance (решение владельца о показе модели,
   версии prompt и ошибок остаётся в силе: ADR 0021, п. 6).
4. Для модели с `measured = false` показывается строка «Модель не входила в
   эксперимент ADR 0021: качество советов не проверено». Для моделей, которых
   там нет, prompt v2 после Prompt-PR не применяется (Д5, п. 6).
5. Если совет для анализа уже существует, селектор и согласие не показываются
   (ADR 0010, п. 4): показывается готовый совет с моделью из provenance и
   фраза «Совет создаётся один раз на анализ; другая модель потребует нового
   решения» (вопрос 6).

### Д4. Контракт `ai-advice.v1` и provenance (аддитивно)

Согласуется с Д4 ADR 0021 (`provider_requests`, enum метки prompt): правки
схемы идут одним PR, чтобы два изменения закрытого объекта `provenance` не
расходились.

- `provenance.model_id`: `const` заменяется закрытым append-only `enum` (ADR
  0021 Д5, п. 1); значения не удаляются.
- Новое необязательное поле `provenance.endpoint_scope` (`external` или
  `internal`). Отсутствие означает `external`: все прежние советы шли через
  ModelStudio. Новый код всегда пишет поле.
- Чтение (ADR 0021 Д3) сверяет **пару** `(model_id, endpoint_scope)` с таблицей
  профилей в коде: подделанная пометка `internal` у модели внешнего профиля даёт
  `CORRUPT_AI_ADVICE`. Таблица содержит модели **всех** известных профилей
  (append-only), поэтому смена активного профиля не портит прежние записи.
- `schema_version` остаётся `ai-advice.v1`; `ai-advice-output.v1` и
  `ai-evidence.v1` не меняются.

### Д5. Выбор модели

1. **Источник списка: сервер, не пользователь.** Два уровня.
   - Код (закрытый append-only набор, он же `enum` схемы): все модели, которые
     продукт когда-либо мог выдать, у каждой профиль (область и подпись) и признак
     `measured`. Это нужно для чтения сохранённых советов и для защиты. Сейчас в
     наборе одно значение `deepseek-v4-flash-0731`.
   - Развёртывание: подмножество набора и модель по умолчанию, одна настройка в
     окружении рядом с `LT_VERDICT_AI_RUNTIME_ROOT` и `LT_VERDICT_AI_QWEN_ROOT`
     (рекомендуемые имена `LT_VERDICT_AI_MODELS` и `LT_VERDICT_AI_MODEL`, как в
     ADR 0021 Д5, п. 2). Значение вне набора или вне профиля активного раннера
     делает ИИ недоступным (`UNAVAILABLE`; какая из существующих причин, выбирает
     CM1, перечень не расширяется), а не молча подменяется. Один процесс имеет один активный профиль: все модели списка
     делят один endpoint и одну область. Другой провайдер требует нового ADR
     (ADR 0021 Д5, п. 1, не меняется).
2. **Как выбор попадает в запрос.** UI шлёт `model_id` в теле POST (Д2).
   Сервер ищет строку в таблице и дальше передаёт **значение из таблицы**, а не
   присланную строку; при отсутствии поля берёт модель по умолчанию. Kotlin
   передаёт значение launcher параметром `-ModelId`, launcher передаёт relay
   (переменная окружения) и Qwen (`--model`), как в ADR 0021 Д5, п. 2.
3. **Защита от произвольных строк.** Значение никогда не попадает в командную
   строку оболочки как фрагмент: оно передаётся одним элементом argv и
   переменной окружения. Помимо точного совпадения с таблицей, каждый узел
   (Kotlin, `param` launcher с `ValidatePattern`, relay, shell-скрипт Qwen)
   проверяет шаблон `^[a-z0-9][a-z0-9._-]{0,63}$` как вторую линию защиты.
   Relay сверяет модель в теле запроса и в кадрах ответа с переданным ему
   значением (сегодня с константой), провайдерские поля маршрутизации по-прежнему
   удаляются. Launcher сообщает в `runtime-result` модель, с которой работал
   relay; Kotlin сверяет её с выбранной и пишет в provenance **наблюдённое**
   значение.
4. **«Одна модель, один запрос» (ADR 0021).** Сохраняется: выбор делается до
   запуска, один совет это один запуск с одной закреплённой моделью, не более
   двух пересланных запросов по Д2 ADR 0021 (повтор идёт в том же диалоге и с
   той же моделью). Fallback на другую модель в продукте не вводится; fallback
   на Codex остаётся только в харнессе холдаута и в набор не входит.
5. **Холдаут.** Предрегистрация фиксирует модель (ADR 0021 Д7). Выбор модели в
   продукте на холдаут не влияет: харнесс закрепляет модель собственным relay.
   Модель по умолчанию в продукте остаётся той, на которой идёт холдаут. Приёмка
   относится к тройке (модель, метка prompt, runner) (ADR 0021 Д5, п. 5).
6. **Prompt по умолчанию и неизмеренные модели.** Prompt-PR ADR 0021
   (переключение метки на v2) действует только для моделей, у которых холдаут по
   P1-P5 пройден; остальные остаются на v1 до собственного прогона. Реализуется
   таблицей в коде (метка prompt по умолчанию на модель) в самом Prompt-PR, а не
   здесь.
7. **Иммутабельность.** Один совет на analysis (ADR 0010, п. 4) сохраняется:
   выбор модели действует на **первый** совет анализа. Несколько советов одного
   анализа (по одному на модель) потребовали бы изменить хранение (путь
   `advice/<analysis>` и сверку по manifest) и ADR 0010, п. 3-4; это не
   предлагается (вопрос 6).
8. **Права.** В продукте нет ролей: локальный single-user процесс, мутации
   защищены сессией и CSRF (ADR 0002). Выбирать можно только из списка,
   разрешённого оператором развёртывания; расширить список запросом нельзя.
   Цена и задержка модели меняются (DeepSeek 57-131 с на запрос, GLM 197-262 с,
   ADR 0021, Д2, п. 6); окна времени и предел 300 с на повтор не меняются, у
   медленной модели рост доли `TIMEOUT` ожидаем и показывается как есть.

### Д6. Что остаётся прежним

- Deterministic analysis и verdict не зависят от ИИ ни при каком выборе.
- Evidence и его allowlist (ADR 0010, п. 1; `ai-evidence.v1`) не меняются; при
  `internal` evidence остаётся тем же. Выбор данных, уходящих в модель, остаётся
  отложенным решением владельца 2026-10-04 (чекбоксы макета вне МВП).
- Внешняя OS-изоляция, endpoint-only egress, fail-soft, отмена, `Busy`, один
  совет на analysis (ADR 0010).
- Правило повтора и окна времени ADR 0021 Д2; метка prompt по умолчанию `v1`
  до холдаута.

### Исключения из принятых правил (вступают с принятием этого ADR)

Поправки в ADR 0010 и ADR 0021 только ссылаются сюда; сами правила меняются
так и только так:

| Правило | Что меняется |
| --- | --- |
| ADR 0010, п. 5 (единственный runner, exact model и endpoint) | Вместо одной модели и одного endpoint закрытый набор профилей назначения; сейчас в нём один профиль (ModelStudio, одна модель). Новая модель в профиле добавляется отдельным PR на модель с записью о приёмке (вопрос 5), другой endpoint это новый профиль и ADR раннера (OP). До такого PR «другие модели» остаются возможностью, а не поведением |
| ADR 0021, Д3 (закрытый набор ключей provenance) | К набору добавляется необязательное `endpoint_scope`; отсутствие означает `external` |
| ADR 0021, Д4 (`model_id` остаётся `const`, пока модель не меняется) | `const` заменяется append-only `enum`, как Д4 и Д5 уже предусматривали при смене модели |
| ADR 0021, Д5 (механизм не вводится сейчас) | Вводится: выбор на запрос из набора, разрешённого развёртыванием |
| ADR 0021, Д6, п. 4 (согласие на отправку остаётся верным) | Верно для `external` без изменений; для `internal` согласие не требуется |
| ADR 0010, п. 4 и ADR 0021 Д2, Д7 | Не меняются |

| Вариант | Суть | Для | Против |

| А. Убрать безусловно | Тело POST без согласия, UI без галки во всех развёртываниях | Буквальное чтение «убрать вообще»; минимум кода | При единственном раннере на ModelStudio **evidence уходит в Сингапур без ведома пользователя**; защита от неосознанной передачи пропадает целиком и не возвращается при смене endpoint |

Согласие по области профиля **(рекомендуется)** | Д1: `external` требует согласия, `internal` нет; область — свойство профиля в коде, не флаг | Совпадает с решением владельца для боевой системы (внутренний инференс без галки); безопасно по умолчанию; граница выражена кодом и provenance | Пока нет on-prem раннера, галка остаётся при всех сценариях; «убрать вообще» достигается с появлением профиля `internal` |

Рекомендация: **Б**. Если «убрать вообще» должно действовать уже сейчас, на
сегодняшнем внешнем раннере, нужно В (не А): оно снимает галку и оставляет
защиту закрытой по умолчанию (вопрос 2).

Отклонены: **область как свободный флаг** (`endpoint_scope` в окружении,
независимый от назначения: одна опечатка отправляет evidence наружу без
согласия, а ADR 0010, п. 6, запрещает флагу объявлять границу проверенной);

provenance; нет сверки приёмки); **несколько провайдеров в одном процессе**
(registry провайдеров, ADR 0021 Д5, п. 1); **согласие в браузерном
хранилище** (запрещено правилами UI-плана и не защищает сервер).

## Угрозы и защита

| Угроза | Защита |
| --- | --- |
| Тихая внешняя передача после снятия галки | Область — свойство профиля, ModelStudio всегда `external`; сервер проверяет согласие; по умолчанию `external` |
| Оператор объявил внешний endpoint внутренним | `internal` выдаёт только профиль с собственным ADR; настройка области не существует; пара `(model_id, endpoint_scope)` сверяется при чтении; остаточный риск: ADR on-prem профиля определяет, что проверяется (вопрос 3), до него `internal` недостижим |
| Клиент пропускает согласие или не даёт его (в том числе случайно, скрыв галку) | Сервер единственный источник правды; клиент область не присылает; при `external` запрос без согласия получает 400. Граница гарантии: защита от пропущенной или случайной внешней передачи; намеренный клиент API может прислать `true` сам (как сегодня), согласие здесь явное заявление вызывающего, а не аутентификация |
| UI не получил конфигурацию | Показывается согласие (`external`), сервер всё равно проверяет |
| Произвольная строка вместо модели | Точное совпадение с таблицей, значение из таблицы дальше, шаблон id в каждом узле, одним элементом argv |
| Расхождение модели в Kotlin, relay и launcher | Контрактный тест согласованности (ADR 0021 Д5, п. 4); relay сверяет модель в кадрах; provenance пишет наблюдённое |
| Совет модели вне приёмки выглядит так же надёжно | Признак `measured`, строка в UI, prompt v1 до собственного прогона (Д5, п. 6) |
| Сохранённые советы нечитаемы после смены модели | Таблица профилей append-only, чтение сверяет кортеж, а не активную настройку (ADR 0021 Д3) |
| Стоимость и время слабой модели | Окна времени не расширяются; число запросов не более 2 на совет; выбор только из списка оператора |

## План проверки

Этот PR: `markdownlint-cli2` по затронутым файлам, проверка ссылок скриптом,
`git diff --check`, независимое ревью Codex (read-only).

Срезы реализации (тесты пишутся в самих срезах, до кода):

- Kotlin (`LocalApiTest`, `AdvisoryAiTest`): при `external` тело без согласия и
  с `false` отвергается, прежний тест остаётся; при `internal` принимаются

## Вопросы владельцу

Рекомендации даны для каждого; ответа на 1-3 достаточно, чтобы принять ADR.

1. **Механизм снятия согласия.** Варианты из раздела «Варианты по согласию».
   Рекомендация: Б (согласие по области профиля). Следствие: для
   сегодняшнего ModelStudio галка и текст про Сингапур остаются, пока не
   появится профиль `internal`. Если текст про ModelStudio нужно убрать и в
   `external`, пользователь будет отправлять данные в Сингапур, не видя
   назначения; не рекомендуется.
2. **Нужно ли снять галку уже сейчас на внешнем раннере.** Рекомендация: нет,
   дождаться профиля `internal`. Если да: вариант В (подтверждение оператором
   в конфигурации), не безусловное снятие.
3. **Что такое «headless qwen» в боевой системе.** Нужны входные данные для
   ADR on-prem раннера: адрес и протокол endpoint (OpenAI-совместимый ли),
   идентификаторы моделей, нужен ли relay и credential, как проверяется
   «endpoint внутри периметра» (сеть, DNS, firewall). Без них `internal`
   остаётся недостижимым значением, а слова «безопасность обеспечена»
   продукт ничем подтвердить не может. Рекомендация: подготовить такой ADR как
   отдельный срез OP.
4. **Галка PR #40 при `internal`.** Рекомендация: заменить переключателем
   «Запросить ИИ-разбор после анализа» (намерение запуска сохраняется, слов
   про согласие нет). Альтернатива: запускать ИИ после каждого анализа
   автоматически (нарушает «запускается только явно» ADR 0010; нагрузка и
   `Busy`).
5. **Список моделей.** Нужны идентификаторы, подписи и модель по умолчанию:
   для внешнего профиля `deepseek-v4-flash-0731` (по умолчанию, измерена);
   кандидаты ADR 0021 (`glm-5.3`, `qwen3.8-max`) не принимались; для
   on-prem профиля назвать владельцу. Рекомендация: добавлять модели в
   append-only набор отдельным PR на модель с записью о приёмке.
6. **Один совет на анализ.** Выбор модели действует на первый совет;
   сравнить две модели на одном анализе продукт не даёт. Рекомендация:
   оставить правило ADR 0010, п. 4; несколько советов на анализ вынести в
   отдельное решение (меняет хранение и схему путей), сравнение моделей
   делать харнессом, как сейчас.
7. **Неизмеренные модели.** Рекомендация: показывать строку «не входила в
   эксперимент ADR 0021» и держать prompt v1 до собственного холдаута (Д5,
   п. 6). Альтернатива: не помечать (скрывает разницу в доверии).
8. **Где отдавать конфигурацию.** Рекомендация: аддитивное поле в
   `GET /api/bootstrap` (одно чтение при старте, данные постоянны, меньше
   всего нового). Альтернатива: отдельный `GET /api/ai/config` (не касается
   рукопожатия безопасности ADR 0002, но новый маршрут).
9. **Выбор модели на экране «Новый анализ».** Рекомендация: да, тот же
   селектор рядом с переключателем намерения; выбор не хранится вне страницы.
10. **Данные, уходящие в модель.** Решение владельца 2026-10-04 (откладывается)
    не затрагивается; evidence строится целиком (`ai-evidence.v1`).

## Следствия

### Объём реализации

Запрошено: убрать согласие на отправку из продукта и добавить выбор модели в
UI. Необходимо для этого: Д1-Д5 и срезы CM1-CM5; для самого факта «убрать»
дополнительно срез OP (профиль `internal`). Не требуется: выбор данных для
модели, несколько советов на анализ, несколько провайдеров, fallback модели в
продукте, структурный `ai-advice.v2`, правки `io.ltverdict.core`.

### Риски и остаточные ограничения

- Пока нет профиля `internal`, решение (А) в продукте не действует:
  галка остаётся. Это сознательная цена безопасности по умолчанию.
- `internal` декларируется профилем, а не доказывается продуктом; что именно
  проверяется, определит ADR on-prem раннера. До него утверждение «данные не
  покидают контур» не может появиться в UI.
- Закрытый разбор тела POST заменяет проверенный regex; ошибка в проверке
  дубликатов ключей ослабит защиту, поэтому она закрепляется тестом первой.
- Выбор модели без приёмки тройки может дать советы с неизвестными дефектами
  (T1-T7 ADR 0021); строка в UI это называет, но не исправляет.
- Правка закрытой схемы provenance и контракта bootstrap одновременно с
  правками ADR 0021 увеличивает риск конфликтов; порядок срезов зафиксирован.

### Документация

Documentation impact этого PR: добавлены ADR 0023 и поправки к ADR 0010 и 0021,
планы UI и ИИ обновлены; поведение, контракты и пользовательские документы не
менялись, `CHANGELOG.md` не обновляется (нет видимого пользователю изменения).
Документы пользователя и `CHANGELOG.md` обновляются в срезах реализации
(CM5 и следующих).
