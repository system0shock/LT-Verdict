# W2.4: честные заголовки ядра (план реализации)

Строка W2.4 перечня [2026-10-08-review-work-plan.md](2026-10-08-review-work-plan.md): «CANDIDATE переименовать в «материальная дельта,
значимость не оценена»; в окне вердикта публиковать долю разгона и простоев; помечать throughput-правила на таких окнах». Критерий:
«Отчёт и UI не содержат «кандидат» без оговорки». Основание: ревью ядра R1, R2 (36,8 % ложных `CANDIDATE` на автокоррелированном нуле;
вердикт по всему прогону вместе с разгоном). Связанные ADR: [0017](../../adr/0017-baseline-candidates-and-confirmation.md),
[0028](../../adr/0028-baseline-conditions-confirmation.md), [0030](../../adr/0030-load-stages-steady-window.md) (R7: W2.4 берёт долю из
`stage_binding`, заголовок «окно вердикта» PR C расширяет, а не заменяет).

Класс задачи (brainstorming): bounded. Меняются существующие тексты и отображение, форма публичных документов не меняется.

## Ruling'и

**H1. «Переименовать» значит отображаемый текст, wire не меняется.** Строка `CANDIDATE` лежит в JSON сравнения, в `ui/src/types.ts`, в
скриптах валидации (`tools/usefulness_validation.py`, `tools/applicability_*`), в тестах и в ответах HTTP. Смена wire это публичный
контракт: AGENTS.md требует ADR, а читатели `comparison/history` ломаются. Почему: критерий готовности говорит об «отчёте и UI», то есть о
показе. Цена ошибки: если владелец хочет и wire, нужны ADR, смена enum в `types.ts`, фикстур и скриптов (отдельный PR; на `analysis_id`
это не влияет, потому что сравнение в identity не входит, но вход в golden и пользовательские скрипты по `status == CANDIDATE` ломается).

**H2. Формулировка.** Статус окна и его строк: «материальная дельта, значимость не оценена». Вводный абзац и строка условий:
«Статус «материальная дельта, значимость не оценена» появляется только после вашего подтверждения…». Английский набор: `CANDIDATE
(material delta, significance not assessed)`. Слова «кандидат» остаются только у кандидатов baseline (набор эталонных прогонов), это
отдельное понятие и оговорки не требует. Цена ошибки: длинная подпись в узкой колонке (заметно, не ломает).

**H3. Доля вне окна это отношение двух чисел из уже записанного результата.**

- Стадии: `stage_binding.excluded_millis` / (`evaluated_millis` + `excluded_millis`); в ядре `excluded = (run_to - run_from) - evaluated`,
  поэтому знаменатель равен длине прогона по выборкам.
- Окна снимка ресурсов: длина прогона `resource_binding.run_to_epoch_ms - run_from_epoch_ms`, оценено = сумма `to_epoch_ms - from_epoch_ms`
  по `window_policy_summary` (окна снимка не пересекаются, ядро отвергает `OVERLAPPING_WINDOWS`), вне окна = разница. Ничего нового в
  результате не нужно.
- Одно число «разгон, остановка, простои и прочее»: разделить их можно только для стадий роли `excluded` (есть имена), но «простой»
  между стадиями и «разгон» без объявленной стадии неразличимы; у неявного окна `run_intersection` «вне окна» это ещё и время вне
  снимка и неполные крайние ячейки (`ResourceSnapshot.kt:172,210`, совет Astra). Поэтому подпись говорит «и прочее», а число точное.
  Разделение потребовало бы нового поля; не делаем. Простой внутри окна остаётся в знаменателе throughput и долей не виден.
- Округление: целые доли на тысячу (полуверх), вывод `13,3 %`; если вне окна есть время, но доля меньше 0,1 %, пишем «меньше 0,1 %».
  Целочисленная арифметика, чтобы Kotlin и TypeScript совпадали.
- Доля выводится независимо от вердикта (это факт о покрытии прогона окном), в отличие от фразы PR C, которая зависит от `decided`.
  Для прогона без окон ничего не выводится (отрицательные тесты, байты прогонов без стадий и без окон прежние).
Цена ошибки: для явных окон снимка с зазорами «вне окна» включает и зазоры между окнами (так и задумано: они не оценены).

**H4. Throughput на окне.** Правило `policy_check` с `metric = throughput_rps` и непустым `window_id` оценено по окну, а не по всему
прогону (доля разгона и простоев в среднюю RPS не входит). Подпись метрики: «пропускная способность (throughput на окне)» в строке
правила и тексте нарушения HTML, в карточке вердикта и таблице правил UI. Остальные метрики на окне не помечаются (p95 и доля ошибок
на окне и так названы окном в соседней колонке; помечать их значит менять больше текста, чем просит критерий). Цена ошибки:
пользователь не видит, что p95 тоже оконный (видит колонку «Окно»).

**H5. Диагностический `CANDIDATE` не трогаем.** Статусы корреляций и сводки диагностики (английский старый вид и дамп evidence в HTML)
уже сопровождаются фиксированными оговорками («не доказывают причинность», `Uncertainty: NOT_ESTIMATED`), а русская оболочка показывает
их как «гипотезы для проверки / ассоциация, не причина». Перенаименование этих статусов отдельный вопрос; в отчёт.

## Критерии приёмки

1. Русский набор подписей: ни одна подпись статуса сравнения не содержит голого «кандидат»; «кандидат» есть только в тексте о кандидатах
   baseline. Английский набор: `CANDIDATE` показан с пояснением. Тест Playwright проверяет показ строки с оговоркой в панели сравнения.
2. (Случаи Astra) стадия `steady`, обрезанная до конца прогона; две окна с зазором; неявное окно `run_intersection`: доля по формуле.
   Результат со `stage_binding` и результат с `resource_binding` + `window_policy_summary`: HTML, AsciiDoc, Confluence и карточка вердикта
   содержат долю вне окна, посчитанную по формуле H3; результат без окон не содержит этой строки; результат, у которого убраны свидетельства
   окон, рендерится побайтово как прогон без окон.
3. Правило throughput с `window_id` помечено в HTML и в UI новой оболочки (карточка вердикта, таблица правил); старая английская таблица
   правил `AnalysisView.vue` показывает код метрики как есть и не входит (в отчёт). Правило с `window_id` помечено, без `window_id` и другие метрики на окне не помечены.
4. Существующие тесты проходят без правок (в тех, что проверяют старый текст «кандидат», нужна минимальная правка; если такие найдутся,
   они перечислены в отчёте). Золотые файлы не меняются.
5. Wire не изменён: `git diff` не затрагивает `docs/contracts`, `ui/src/types*.ts`, fixtures.
