# ADR 0036: Предложение стадий нагрузки по данным прогона (`ltv stages detect`)

Дата: 2026-11-19.

Статус: Proposed (в Accepted переводится только по слову владельца). Реализация PR 1
(`ltv stages detect`) идёт при статусе Proposed по решению владельца 2026-11-19 (раздел
«Решения владельца 2026-11-19»). Номер 0036 выбран как
следующий после 0035 (ADR о библиотеке графиков UI, при начале этой работы открытый PR, к вечеру
2026-11-19 влит в `origin/main` как #267). Перед слиянием номер нужно перепроверить по
`origin/main`.

Рабочий план, алгоритм с константами, фикстуры и критерии приёмки:
[2026-11-19-w4-1-stage-detection.md](../superpowers/plans/2026-11-19-w4-1-stage-detection.md).

## Контекст

[ADR 0030](0030-load-stages-steady-window.md) ввёл явные стадии нагрузки (`load-stages.v1`):
человек объявляет разгон, плато и остановку смещениями от начала прогона, стадии `steady`
становятся окнами вердикта. Автоопределения плато там нет: это решение владельца 3 и отклонённая
альтернатива («новый статистический метод и источник недетерминизма; D1 заморожен»). Подсказка
границ откладывалась «позже как зонд doctor или MCP».

На практике человек часто не знает границ точно: профиль задан в сценарии JMeter, а фактический
разгон зависит от генератора. Ошибка в объявлении молча сдвигает окно (раздел «Ловушка начала
прогона» руководства). Решение владельца 2026-11-19: автоопределение стадий обязательно для
продукта; пока оно работает как предложение, которое человек подтверждает. Инструмент строит
документ `load-stages.v1` по данным нагрузки, человек проверяет его, правит и передаёт как обычный
явный вход. Полностью автоматическое применение без подтверждения в объём не входит.

Ограничения решения:

1. `ltv analyze`, identity, `analysis_id`, канонический JSON и хэши identity не меняются. Стадии
   остаются явным входом (`--stages`, часть `stages` задания API).
2. Одинаковые байты входа дают одинаковое предложение: нет случайности и часов.
3. Нужна только нагрузка (JTL JMeter или журнал Gatling); источник мониторинга не нужен.
4. Не удалось определить уверенно — явный отказ с причиной, а не плохая догадка (принцип
   fail-closed, как в [ADR 0012](0012-auto-window-recognized-period.md) и
   [ADR 0026](0026-capacity-knee-diagnostic.md)).

Источник идеи: детектор ступеней конкурента LoadLens (Apache-2.0, `AI/step_detector.py`). Это
только ориентир по подходу: окно подтверждения, порог скачка от шума плато, доля выборок на плато
как признак «плато нет», пометка устойчивого падения внутри ступени. Код не копируется; ниже
описан собственный метод с собственными фикстурами. Главные отличия: глобальная кусочно-линейная
сегментация вместо сканирования окном, шум по первым разностям вместо второго прохода по
остаткам плато, нет параметра «ожидаемая длина ступени» от пользователя.

## Решения владельца 2026-11-19

1. Автоматическое определение стадий объявлено обязательным для продукта. Это явное исключение
   из заморозки D1 перечня ревью 2026-10-08 («статметоды не принимаются до конца волны 3»).
   ADR остаётся Proposed; реализация PR 1 (`ltv stages detect`) идёт.
2. Ступенчатый профиль (несколько плато): два режима с переключателем, а не одно правило (D12).
3. Режим `--like <load-stages.json>` одобрен следующим срезом (PR 1b, D13); в PR 1 не входит.
4. Код выхода `3` для отказа метода остаётся (D8).
5. Открытыми остаются поле стадий в форме UI (снятие ADR 0030 R12, D10) и проверка метода на
   корпусе реальных прогонов до перевода в Accepted (раздел «Открытые вопросы»).

## Решение

### D1. Предложение, а не применение

Предложение строится отдельной командой и отдельным маршрутом API. Ни `ltv analyze`, ни
`AnalysisService` его не вызывают и не читают. Анализ получает стадии только явным файлом, как
сегодня, поэтому решение владельца 3 из ADR 0030 («ядро не угадывает окна при анализе») остаётся в
силе: угадывает отдельный инструмент, а решает человек. По той же причине не нарушается
[ADR 0012](0012-auto-window-recognized-period.md) (границы теста не угадываются при выборке
источника) и [ADR 0009](0009-explicit-capacity-stages.md) (план ёмкости не выводится из данных:
предложение это `load-stages.v1`, не `capacity-plan.v1`).

Заморозка D1 перечня ревью 2026-10-08 («статметоды не принимаются до конца волны 3») не
действует для этой работы: владелец 2026-11-19 объявил автоопределение стадий обязательным и
назвал это явным исключением из заморозки.

### D2. Вход: ряд числа запросов по секундам от начала прогона

Начало прогона вычисляется тем же правилом, что в анализе: минимальный `started_at` среди всех
выборок всех видов (`AnalysisService.kt:282,310`, `RunPeriod.kt:59`), включая setUp-группу,
health-check и контейнеры. Конец прогона это максимум `started_at + elapsed`. Число запросов
считается только по выборкам `JMETER_SAMPLER` и `GATLING_REQUEST` (как секундные корзины ядра,
`Metrics.kt:212-215`), по моменту старта, в секундных ячейках от начала прогона. Так смещения
предложения означают ровно то же, что смещения при анализе со стадиями.

Ряд строит собственный лёгкий проход по образцу `recognizeRunPeriod` (`RunPeriod.kt:41-66`):
два чтения входа через `parseInput` (первое находит начало прогона, второе раскладывает старты по
секундам), без гистограмм и без каталога данных. Два чтения нужны потому, что строки JTL не
упорядочены по времени старта, а ячейки отсчитываются от минимума. Прогон длиннее 604800000 мс
(предел смещения `load-stages.v1`) не обрабатывается.

### D3. Метод `rps-plateau-segmentation.v1`

1. **Ширина ячейки.** Секундный ряд агрегируется в ячейки ширины `W` из фиксированной лестницы
   1, 2, 5, 10, 15, 30, 60, 120, 300 с: берётся наименьшая `W`, при которой ячеек не больше 2400, а
   верхний квартиль числа запросов в ячейке не меньше 50 (пуассоновский шум ячейки плато не больше
   примерно 14 %). Ячейки отсчитываются от начала прогона, поэтому все границы кратны `W`.
2. **Шум.** `σ` это робастная оценка шума ряда по первым разностям: `1,4826 · MAD(Δc) / √2`,
   не меньше одного запроса на ячейку (разрешение ряда).
3. **Сегментация.** Ряд делится на отрезки, на каждом из которых число запросов описывается
   прямой (уровень и наклон). Разбиение оптимально по сумме квадратов остатков со штрафом
   `3 · σ² · ln n` за каждый отрезок (критерий BIC для трёх параметров отрезка), отрезок не короче
   трёх ячеек. Метод точный (динамическое программирование), без случайности; на 2400 ячейках это
   несколько миллионов операций.
4. **Классификация отрезков.** `FLAT` (дрейф уровня за отрезок не больше 10 %, разброс остатков не
   больше 25 % уровня), `IDLE` (уровень не больше 2 % наибольшего), `RISING`, `FALLING`,
   `UNSTABLE`. Соседние `FLAT` с неразличимыми уровнями и длиной не меньше 30 с сливаются;
   короткий растущий `FLAT` между плато считается переходом (поправка при реализации PR 1,
   раздел «Реализовано»).
5. **Выбор steady.** Кандидат в steady это `FLAT` длиной не меньше 30 с, у которого уровень не
   меньше половины наибольшего плато или длина не меньше 3/4 самого длинного плато. Низкое и
   короткое плато в начале (прогрев) становится частью разгона; ступени профиля ёмкости
   одинаковой длины становятся стадиями-ступенями. Какие из ступеней получают роль `steady`,
   решает режим D12.
6. **Края.** Граница стоит на краю ячейки, где сегментация нашла смену уровня. Крайняя ячейка
   стадии steady остаётся в ней, только если её число запросов в пределах `2σ` от уровня плато;
   иначе граница сдвигается внутрь (не больше чем на две ячейки).

Все константы названы и обоснованы в плане; они выбраны по синтетическим профилям и опорной
фикстуре `fixtures/stages/ramp-steady-rampdown.jtl` и **не калибровались на корпусе реальных
прогонов**. Ширина ячейки, шум, найденные отрезки и причина каждой границы печатаются вместе с
предложением, чтобы результат объяснял себя сам; сами значения констант не печатаются, они
задаются версией метода (`rps-plateau-segmentation.v1`) и таблицей плана.

### D4. Асимметрия: разгон исключается, падение не вырезается

Включить разгон в steady значит вернуть ошибку, которую исправлял ADR 0030 (ложный FAIL). Вырезать
из steady падение нагрузки значит спрятать отказ: в замкнутой модели JMeter RPS падает, когда
система тормозит, и окно без этого участка дало бы ложный PASS. Поэтому:

- всё до первой стадии steady (простой setUp, прогрев, разгон) исключается;
- снижение уровня после начала первой стадии steady никогда не становится границей: участок
  остаётся внутри steady, предложение получает предупреждение `LOAD_DROP_INSIDE_STEADY` с моментом
  и величиной падения и низкую уверенность;
- хвост после последнего плато считается остановкой (`ramp-down`), только если он состоит из
  спада, простоя или коротких (меньше 60 с) участков. Длинное плато на пониженном уровне это
  падение, и оно остаётся в steady. Очень длинная остановка (больше 25 % длины steady и больше
  60 с) даёт предупреждение `LONG_RAMP_DOWN`.

Переходы между возрастающими ступенями профиля ёмкости в стадии не входят (зазоры допустимы
контрактом и попадают в `excluded_millis`).

### D5. Отказ вместо догадки

Предложение не строится, если выполнено любое из условий (проверяются в этом порядке):

| Код | Условие |
| --- | --- |
| `INPUT_INVALID` | вход непригоден (`INVALID`) |
| `NO_REQUEST_SAMPLES` | нет выборок-запросов |
| `RUN_TOO_LONG` | прогон длиннее 604800000 мс |
| `RUN_TOO_SHORT` | прогон короче 60 с (до выбора ширины ячейки) или меньше 12 ячеек (после выбора) |
| `RATE_TOO_LOW` | ни одна ширина ячейки не даёт 50 запросов в верхнем квартиле |
| `RATE_OUT_OF_RANGE` | переполнение целых сумм при сегментации (защитный код, на реальных нагрузках недостижим) |
| `IDLE_GAP_INSIDE_RUN` | простой не короче 30 с между плато (похоже на два теста в одном файле, как `AUTO_WINDOW_MULTI_TEST_SUSPECTED` в ADR 0012) |
| `NO_PLATEAU` | нет кандидата в steady или плато занимают меньше 30 % прогона без начального простоя (непрерывный рост) |
| `TOO_MANY_STAGES` | стадий получилось больше 16 (предел `load-stages.v1`) |

Отказ не пишет файл и объясняет причину измеренными фактами (ширина ячейки, доля плато, длина
простоя).

### D6. Уверенность: правила, а не вероятность

Уровень `HIGH`, `MEDIUM` или `LOW` выводится по явным правилам и всегда сопровождается пометкой
`calibrated=false`. `LOW`: есть `LOAD_DROP_INSIDE_STEADY` или `LONG_RAMP_DOWN`. `MEDIUM`: есть
`LEAD_IN_IDLE` (простой в начале, например setUp), `STEADY_DRIFT` (дрейф плато от 5 до 10 %),
`DEGRADED_INPUT`, либо граница steady видна меньше чем на `6σ`, либо разброс плато больше 15 %.
Иначе `HIGH`. Вероятностей и доверительных интервалов нет: для них нужна калибровка на корпусе
(как в ADR 0026).

### D7. Вывод: обычный `load-stages.v1`, нового контракта нет

Предложение это канонические байты `load-stages.v1` (та же функция сериализации, что у валидатора;
тест проверяет, что `validateLoadStages` принимает их и возвращает те же канонические байты).
Обёртка `stage-proposal.v1` с объяснением и уверенностью не вводится: предложение не сохраняется
в каталоге данных и не входит ни в один артефакт, а объяснение нужно человеку один раз. Самый
малый вариант достаточен: документ отдельно (его можно сразу передать в `--stages`), объяснение
отдельно.

Имена стадий: `lead-in` (простой до первой нагрузки, если он есть), `ramp-up`, `steady` при одном
плато (тогда правила с `window_ids: ["steady"]` работают без правок) или `step-1` ... `step-N` при
нескольких, `ramp-down`. Имена ступеней одинаковы в обоих режимах D12, режим меняет только роли;
при нескольких плато правило с `window_ids: ["steady"]` окна не находит, его нужно привязать к
`step-N`. Конец последней стадии округляется вверх до сетки `W`; конец steady за
концом прогона обрезается при анализе (`clipped_to_run_end`, ADR 0030 R1).

### D8. CLI: `ltv stages detect <input> [--out <file>] [--steady-steps top|all]`

- stdout (или файл `--out`): канонические байты предложения, только при успехе.
- stderr: объяснение строками `ключ=значение` на английском, в стиле `summary.txt`: метод, режим
  ступеней (`steady_steps`), статус, уверенность, ширина ячейки, шум, отрезки, причина каждой
  границы (уровни до и после, контраст в `σ`, сдвиг края), предупреждения, причина отказа. Строки
  стабильны и проверяются тестами.
- Коды выхода: `0` предложение построено; `3` не определено (как `NO_VERDICT`: инструмент ничего не
  утверждает; подтверждено владельцем 2026-11-19); `4` вход непригоден (`INPUT_INVALID`, как
  `INVALID` у `ltv analyze`), не найден или не распознан, `--out` уже существует или не записан;
  `64` ошибка использования (в том числе значение `--steady-steps` не `top` и не `all`).
- Каталог данных не открывается и не блокируется: команду можно запускать рядом с `ltv ui`.
- `--out` не перезаписывает существующий файл и не следует по ссылкам (как `PG_REPORT_EXISTS`).

### D9. Сопоставимость: определить один раз, переиспользовать файл

Хэш объявления входит в ключ сопоставимости (ADR 0030 R6). Предложение, построенное заново для
каждого прогона, может сдвинуться на ячейку, и тогда прогоны станут несопоставимыми
(`compatible = false`). Порядок работы, который фиксирует руководство: построить предложение на
одном прогоне профиля, проверить, сохранить файл рядом со сценарием и передавать его во все прогоны
этого профиля. Границы кратны ширине ячейки, что уменьшает дрожание, но не исключает его.

### D10. UI: поле стадий и кнопка «Предложить стадии» (отдельный PR после CLI)

Сегодня в форме нового анализа поля стадий нет (ADR 0030 R12), а `createJob` в `ui/src/api.ts`
не отправляет часть `stages`, хотя API её принимает. Второй PR добавляет:

- поле стадий в форме нового анализа (редактируемый JSON) и отправку части `stages`;
- кнопку «Предложить стадии», которая заполняет поле предложением и показывает объяснение;
  анализ запускает человек, предложение без его действия не применяется;
- маршрут `POST /api/runs/{runId}/stage-proposal` без тела. POST, а не GET: вычисление читает весь
  вход дважды, и защита сессией, `Origin` и CSRF как у `POST /api/jobs`
  ([ADR 0002](0002-slice-1-runtime-filesystem-security.md)) ограничивает его вызов. Вычисление
  идёт вне event loop, одновременно не больше одного (`409 BUSY`, как захват PostgreSQL),
  неизвестный прогон даёт `404`. Ответ `200` содержит `status`, `reason`, `method`,
  `confidence`, `calibrated`, `warnings`, `proposal` (объект `load-stages.v1` или `null`),
  `parameters`, `segments`, `boundaries`. Это добавочный маршрут локального API, не
  версионированный документ; русский текст объяснения строит UI из полей (как фраза стадий по
  ADR 0030 R10).

Это частично снимает ADR 0030 R12 (форма загрузки стадий в UI): требуется подтверждение
владельца.

### D11. Детерминизм

Счётчики и префиксные суммы целые (`Long`, переполнение даёт отказ, а не неверный результат),
медианы нижние, арифметика `double` на JVM строго IEEE 754, логарифм через `StrictMath`, при
равенстве стоимостей выбирается самая ранняя граница. Порядок строк во входе на результат не
влияет. Числа в объяснении округляются `HALF_EVEN` до трёх знаков.

### D12. Ступенчатый профиль: режим `--steady-steps top|all`

Решение владельца 2026-11-19: два режима с переключателем.

- `all` (режим A): роль `steady` получает каждая ступень, отобранная правилом D3, п. 5 (уровень
  не ниже половины наибольшего плато или длина не меньше 3/4 самого длинного).
- `top` (режим B): роль `steady` получает только последняя, наивысшая ступень; остальные плато
  выводятся обычными стадиями с ролью `excluded` под теми же именами `step-K`.

Режим меняет только роли стадий. Границы стадий, их число, отказы `IDLE_GAP_INSIDE_RUN`,
`NO_PLATEAU` (доля плато считается по всем ступеням: иначе в режиме `top` любой профиль ёмкости
отказывал бы по доле) и `TOO_MANY_STAGES`, а также знаменатель `LONG_RAMP_DOWN` от режима не
зависят. Признаки окна вердикта (`LOAD_DROP_INSIDE_STEADY`, `STEADY_DRIFT`, контраст границ и
разброс плато в уверенности) считаются только по стадиям с ролью `steady`: падение внутри
исключённой нижней ступени не понижает уверенность чистого окна. При одном плато режимы дают
одинаковые байты предложения, объяснения различаются только значением `steady_steps`. Режим
печатается в первой строке объяснения.

Умолчание владелец не назвал. Исполнитель выбрал `top`: окно steady, собранное из ступеней разного
уровня, смешивает распределения задержек разных нагрузок, и перцентили такого окна ничего не
значат. Выбор ждёт слова владельца (раздел «Открытые вопросы»).

### D13. Режим `--like <load-stages.json>` (запланирован, PR 1b)

Одобрен владельцем 2026-11-19 следующим срезом после PR 1. Команда проверяет, подходит ли уже
принятое объявление профиля этому прогону, и при совпадении оставляет его байты и хэш без
изменений. Это убирает дрожание границ на ячейку между прогонами и потерю сопоставимости с
baseline по ключу ADR 0030 R6 (D9). Набросок задач в плане (PR 1b); в PR 1 не реализуется.

## Открытые вопросы

1. Умолчание `--steady-steps`: исполнитель выбрал `top` (D12), ждёт слова владельца.
2. Поле стадий в форме UI снимает ADR 0030 R12 (D10): ждёт подтверждения владельца.
3. Проверка метода на корпусе реальных прогонов (в том числе со ступенями и падениями) до
   перевода ADR в Accepted: корпус и порядок прогона не определены.

## Последствия

- Анализ, identity, `analysis_id`, ключ сопоставимости, канонический JSON, схемы результата и
  `load-stages.v1` не меняются; золотые файлы не перегенерируются.
- Новый код: файл ядра с проходом и методом, команда CLI, маршрут API и поле формы UI (второй PR).
  Новых зависимостей production нет.
- Публичные изменения: команда `ltv stages detect` (строка в `--help`), коды отказа D5, предупреждения
  D6, маршрут API D10, поле стадий в UI. В ADR 0030 добавляется ссылка на этот ADR; строки
  руководства «Автоопределения плато нет» заменяются описанием предложения.
- Ограничения метода: модель «уровень плюс наклон» не различает плановое снижение нагрузки и
  деградацию (поэтому D4); профиль из многих коротких ступеней (меньше 30 с) не распознаётся;
  долгий спад в конце может быть умиранием системы, а не остановкой (только предупреждение);
  константы не калиброваны.
- Для перевода в Accepted: слово владельца по открытым вопросам (умолчание D12, D10 и снятие
  ADR 0030 R12) и прогон метода на корпусе реальных прогонов с записанным результатом.
  Исключение из заморозки D1 и роли ступеней (D12) владелец решил 2026-11-19.

## Реализовано

- PR 1 (`feat/stage-proposal-cli`, номер PR будет назначен при открытии): ядро
  (`core/StageProposal.kt`, `core/StageSegmentation.kt`), команда `ltv stages detect` с
  `--steady-steps top|all` (`cli/CliStages.kt`), тесты на синтетических профилях плана и опорной
  фикстуре, руководство (раздел «Предложение стадий: `ltv stages detect`»). Статус остаётся
  Proposed.
- Отступления от плана, найденные на синтетике (константы не менялись): короткий (меньше
  `MIN_STEADY_MILLIS`) растущий отрезок вида `FLAT` считается переходом между ступенями, и
  отрезки короче `MIN_STEADY_MILLIS` не сливаются с соседним плато. Без этого ступень +10 %
  с переходом 10 с (80 и 90 rps) сливалась в одно окно `steady` с уверенностью `HIGH` и без
  предупреждения, а профиль F11 давал 17 стадий вместо 18.
- Ограничения, подтверждённые прогоном: у пологого склона (шум сравним с ростом за ячейку)
  граница плато может уйти наружу на несколько ячеек (F5: −7 с и +3 с при `W` = 1 с, F10:
  +3 с), захватывая ячейки в пределах 6 % уровня плато; момент `LOAD_DROP_INSIDE_STEADY`
  это начало переходного отрезка, до 1,5 ячейки раньше падения. Фикстура
  `fixtures/slice0/simulation.log` не является поддерживаемым журналом Gatling и даёт
  `INPUT_INVALID` (как у `ltv analyze`).

## Не входит

- Автоматическое применение предложения без подтверждения человеком и любое использование
  детектора внутри `ltv analyze` или `AnalysisService`.
- Сохранение предложения в каталоге данных, версионированная схема предложения, MCP-инструмент.
- Вывод `capacity-plan.v1` (ступени ёмкости с целями) и детектор колена (ADR 0026).
- Определение стадий по ресурсам, числу потоков (`allThreads`) или ошибкам.
- Локализация объяснения в CLI. Сравнение с уже принятым объявлением (`--like`) запланировано
  отдельным срезом (D13).
- Визуальный дизайн UI (во втором PR определяется только маршрут и поведение).
