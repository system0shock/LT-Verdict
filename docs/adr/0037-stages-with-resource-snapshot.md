# ADR 0037: Стадии нагрузки вместе со снимком ресурсов и онлайн-источником

Дата: 2026-11-19.

Статус: Proposed (в Accepted переводится только по слову владельца).

Номер 0037 выбран так: на `origin/main` 2026-11-19 последний ADR 0035; номер 0036
занят неслитым черновиком ADR о предложении стадий нагрузки (ветка
`docs/w4-1-stage-detection-plan`). Перед слиянием номер нужно перепроверить по
`origin/main`.

ADR изменяет ruling R3 [ADR 0030](0030-load-stages-steady-window.md) (стадии
нагрузки): запрет сочетать стадии со снимком ресурсов и с онлайн-запросом
источника снимается, запрет сочетать стадии с планом ёмкости остаётся. Остальные
ruling'и ADR 0030 (R1, R2, R4-R12) не меняются; R5 получает уточнение (D9). В таблице
«Взаимодействие с другими режимами» ADR 0030 меняются строки 3, 4 (D3, D7) и 5 (D9).

План реализации:
[2026-11-19-stages-with-resources.md](../superpowers/plans/2026-11-19-stages-with-resources.md).

## Контекст

ADR 0030 R3 запрещает в одном анализе объявленные стадии (`load-stages.v1`) и
снимок ресурсов, план ёмкости или онлайн-запрос источника. Проверки:
`CommandLine.kt:250-256`, `JobRoutes.kt:443-454`, `AnalysisService.kt:81-85`,
`SourceAnalysis.kt:121-122`; коды `STAGES_RESOURCES_CONFLICT`,
`STAGES_CAPACITY_CONFLICT`, `STAGES_SOURCE_CONFLICT`. Причина в ADR 0030: оба входа
задают окна, а молчаливый приоритет «окна стадий» или «окна снимка» нарушил бы
принцип «вердикт говорит вслух».

Следствие: анализ с данными платформы (CPU, память, поды) не может иметь стадий.
UI не может нарисовать ресурсные ряды с полосами стадий, обзор не показывает ленту
стадий для самого важного прогона, а будущее предложение стадий (черновик ADR 0036)
бесполезно для прогонов с данными платформы. Решение владельца 2026-11-19: запрет
снять, стадии должны работать вместе со снимком ресурсов и онлайн-источниками; как
именно, решает этот ADR; включать ли план ёмкости, ADR рекомендует.

Что показывает код (подробности и ссылки в плане, раздел «Находки»):

1. Окна снимка лежат на сетке снимка: границы явного окна кратны шагу
   (`WINDOW_NOT_ON_GRID`, `ResourceSnapshot.kt:391-400`), неявное окно
   `run-intersection` берёт только полные ячейки внутри пересечения прогона и сетки
   (`ResourceSnapshot.kt:172-195`). Ресурсная оценка режет ряд по
   `cellIndex = (epoch - start) / step` с округлением вниз
   (`ResourceStatistics.kt:49`, `:528`).
2. Границы стадий это `runStart + offset` с точностью до миллисекунды
   (`LoadStages.kt:111-144`); на сетку снимка они почти никогда не попадают. Окно
   стадии, переданное в ресурсную оценку как есть, молча захватило бы неполную
   ячейку разгона в начале и потеряло бы неполную ячейку в конце.
3. Совместная оценка окна (`evaluateSharedWindowPolicy`, `WindowPolicy.kt:8-63`)
   соединяет бизнес- и ресурсный вердикт по `window_id`: у обеих сторон должен быть
   один и тот же набор id окон. Платформенные правила ADR 0018 привязываются к окнам
   через те же `window_ids` (`WindowPolicy.kt:52`, `ResourceStatistics.kt:45`).
4. Онлайн-выборка с явным окном всегда пишет в снимок окно `full` на всю сетку, с
   авто-окном окна не пишет (`PromqlSource.kt:370-383`,
   `SourceAnalysis.kt:583-597`).
5. Аргумент R5 «коллизии id нет» держался на R3: `window_metric_summary` с id
   `window-metric-summary-<sha(window_id)>` пишут и режим стадий
   (`LoadStages.kt:167-170`), и диагностика корреляций (`DiagnosticAnalysis.kt:95`).
   План тренда связывается только с явными окнами снимка (`TrendPlan.kt:109-116`).

## Решение

Стадии и снимок ресурсов сочетаются так: окна оценки задают только стадии, для
всех семейств правил; ресурсная сторона оценивает полные ячейки сетки внутри
каждого окна стадии, и обе пары границ публикуются. Снимок со своими окнами вместе
со стадиями остаётся ошибкой. Онлайн-источник со стадиями строит снимок без окон.
План ёмкости, план корреляций и план тренда со стадиями не сочетаются.

### D1. Один набор окон: окна `steady`

При заданных стадиях окна оценки это стадии `steady` (как в ADR 0030), и других
окон в анализе нет. По ним считаются:

- бизнес-правила `policy.v1` (`rules`);
- SLA-правила снимка (`rules` снимка, `effect = sla` и `diagnostic`);
- развёрнутые платформенные правила `policy.v1` (`platform_rules`, ADR 0018).

`window_id` окна равен id стадии, поэтому `evaluateSharedWindowPolicy`,
`jointVerdict` и `overallVerdict` не меняются. `window_ids` правил политики (и
бизнес-, и платформенных) ссылаются на id стадий; ссылка на id, которого среди
стадий `steady` нет, даёт существующий `RULE_WINDOW_NOT_FOUND` и `NO_VERDICT`.

Рассмотренные варианты: (а) один набор окон, окна задают стадии (выбран); (б) у
каждого семейства своё окно: бизнес по стадиям, ресурсы по окнам снимка, результат
называет оба; (в) приоритет одного источника окон. Почему не (б) и (в), см.
«Отклонённые варианты».

### D2. Ресурсная сторона: полные ячейки внутри окна стадии

Для каждой стадии `steady` с границами `[from, to)` (после обрезки по концу прогона,
R1) ресурсное окно с тем же id:

```text
lo = max(from, snapshot.start)            hi = min(to, snapshot.gridEnd)
resource_from = snapshot.start + ceil((lo - snapshot.start) / step) * step
resource_to   = snapshot.start + floor((hi - snapshot.start) / step) * step
```

Это правило неявного окна `run-intersection` ([ADR 0005](0005-resource-window-sla.md),
`ResourceSnapshot.kt:172-195`), применённое к окну стадии: в ресурсную оценку
попадают только целые ячейки, лежащие внутри окна стадии и внутри сетки снимка.
Бизнес-сторона окна сохраняет точные границы стадии (как в ADR 0030); выборки
относятся к окну по моменту старта, накопитель не меняется.

- `resource_from >= resource_to` (окно стадии не содержит ни одной полной ячейки
  сетки или лежит вне сетки) даёт отказ `STAGE_WINDOW_NO_FULL_CELLS` (новый код, по
  образцу `RESOURCE_WINDOW_NO_FULL_CELLS`). Окно нулевой длины ресурсная оценка не
  принимает.
- Сетка покрывает окно стадии не целиком (сверх обрезки неполных ячеек на краях:
  `resource_from - from >= step` или `to - resource_to >= step`): оценка идёт по
  пересечению, в причины покрытия добавляется информационная причина
  `STAGE_WINDOW_SNAPSHOT_PARTIAL` (`analysis_coverage = INCOMPLETE`, вердикт не
  меняется, анализ не попадает в кандидаты статистического эталона). Альтернатива
  «отказ» вынесена в вопросы владельцу.

Варианты для краёв: (а) внутрь, только полные ячейки (выбран, существующее правило);
(б) наружу, с неполными ячейками (отклонён: в SLA попадает разгон); (в) требовать
границы стадий на сетке (отклонён: смещения от `runStart` в миллисекундах на сетку не
попадают, правило отвергало бы почти любой реальный прогон).

Расхождение бизнес- и ресурсных границ одного окна не скрывается: оно ограничено
неполными ячейками на краях (меньше одного шага с каждой стороны), а если больше,
об этом говорит причина покрытия. Обе пары границ публикуются (D5).

### D3. Снимок со своими окнами и стадии: ошибка (сужение R3)

Снимок, у которого массив `windows` не пуст, вместе со стадиями отвергается кодом
`STAGES_RESOURCES_CONFLICT`. Код прежний, условие уже: раньше любой снимок, теперь
только снимок с собственными окнами. Окна снимка ADR 0018 (раздел 4) рекомендовал
как именованные стадии; снимок с окнами и `load-stages.v1` это два объявления стадий,
и приоритета между ними нет (R3 в этой части остаётся в силе). Снимок без `windows`
(неявный режим, авто-окно онлайн-источника, контекст OpenSearch без базового
снимка) сочетается со стадиями.

Рассмотренные варианты согласования: (а) ошибка при непустых `windows` (выбран);
(б) окна снимка допустимы, если каждая стадия `steady` лежит внутри одного окна
снимка, и тогда окна снимка только ограничивают телеметрию, но не оцениваются
(отклонён: окно снимка по ADR 0005 это окно оценки, и вариант молча меняет его
смысл, а правило с `window_ids` окна снимка неожиданно получает
`RULE_WINDOW_NOT_FOUND`); (в) каждое семейство по своим окнам (см. D1).

Цена: сохранённый снимок онлайн-выборки с явным окном (окно `full`) нельзя
переиграть со стадиями через `--resources`; нужен повторный онлайн-запрос со
стадиями (D7) либо снимок без `windows`. Это вынесено в вопросы владельцу.

Порядок чтения в CLI: чтобы отказ `STAGES_RESOURCES_CONFLICT` шёл в общем порядке
проверок стадий и до чтения политики из stdin, со `--stages` файл снимка читается
раньше политики. Поэтому со стадиями недопустимый снимок сообщается раньше
недопустимой политики; без `--stages` порядок чтения прежний.

### D4. Платформенные правила `policy.v1` (ADR 0018) со стадиями и снимком

Платформенные правила разворачиваются по снимку как сегодня (`expandPlatformRules`,
`validatePlatformBinding`) и проверяются на ресурсных окнах D2. Их `window_ids` это id
стадий. `RULE_WINDOW_TOO_SHORT` считает ячейки ресурсного окна D2. Валидатор
`platform_coverage` (покрытие сервис × окно) не меняется: он проверяет `window_ids`
внутри политики и от источника окон не зависит. Допуск пропусков (ADR 0018, раздел 5)
считается по ячейкам ресурсного окна.

Режим стадий без снимка не меняется: R4 ADR 0030 (`stageResourceSide`,
`NO_VERDICT` с `RESOURCE_SNAPSHOT_REQUIRED` при платформенном SLA-правиле) действует
только при `resources == null`.

### D5. Результат и свидетельства

Схема `analysis-result.v1` не меняется (элементы `evidence` в схеме это объекты без
перечня типов), верхнеуровневых полей нет. Для анализа со стадиями и снимком:

1. `stage_binding` как в ADR 0030; у стадий `steady` три новых необязательных поля:
   `resource_from_epoch_ms` и `resource_to_epoch_ms` (границы D2) и `resource_partial`
   (`true`, если для этой стадии выполнено условие `STAGE_WINDOW_SNAPSHOT_PARTIAL`,
   иначе `false`; добавлено по ревью PR A, чтобы причина покрытия называла стадии).
   Без снимка поля отсутствуют (по умолчанию `null`, `encodeDefaults = false`), байты
   результата режима «только стадии» прежние. `mode = declared_stages`,
   `verdict_scope = STEADY_WINDOW` не меняются.
2. `resource_binding` пишется, как в режиме снимка, с новым значением
   `mode = declared_stages` (значения сейчас `run_intersection` и
   `explicit_windows`; поле в typed-модели и сгенерированном TS это строка, читатели
   по значению не ветвятся). `evaluation_from_epoch_ms`/`evaluation_to_epoch_ms`
   это минимум и максимум ресурсных окон D2, `dropped_*` равны 0 (как у
   `explicit_windows`; обрезка на краях видна по окнам в `stage_binding`),
   `clock_alignment = not_verified_by_core`.
3. `resource_summary` и `resource_policy_check` по каждому окну, как в режиме
   снимка; их `from_epoch_ms`/`to_epoch_ms` это ресурсные границы D2.
4. `window_policy_summary` и `policy_check` по окну, как в ADR 0030; границы в
   `window_policy_summary` это точные границы стадии.
5. `window_metric_summary` по каждому окну `steady`, как в ADR 0030.

Порядок `evidence`: `metric_summary` без окна и `diagnostic` (как сейчас), затем
`stage_binding`, `resource_binding`, затем то, что ресурсная оценка пишет сегодня
(`resource_summary` по окну и ряду, затем `resource_policy_check`), затем по окну
`policy_check`, `window_policy_summary`, при необходимости `rule_window_check`, затем
`window_metric_summary` по окнам, затем, как сегодня, свидетельства источника,
postgres и pod-view. Порядок закрепляется золотым тестом.

Читатели, которые при обоих элементах берут сначала `stage_binding`
(`StageNotice.kt:121-150`, `verdictSummary.ts`), продолжают говорить «по окну steady».
Ресурсные секции UI и отчётов, включаемые наличием `resource_binding`
(`App.vue:1162`, `HtmlReport.kt:33-45`, `AnalysisView.vue:53`), показываются.

### D6. Identity, `analysis_id`, ключ сопоставимости

- Новых полей identity нет. В identity анализа со стадиями и снимком одновременно
  есть поля снимка (`resource_snapshot_sha256`, `resource_config_sha256`,
  `resource_arm`, `input_versions.resources`, лимиты `resource_*`) и поля стадий
  (`load_stages_sha256`, `load_stages_version`, `input_versions.stages`, лимиты
  `stages_*`).
- `modules`: `normalization`, `metrics`, `policy-evaluation`, `resource-statistics`,
  `window-policy-evaluation`, `stage-window-evaluation` (все версии 1). Модуль
  `window-policy-evaluation` указывается один раз: сегодня его добавляют обе ветки
  (`AnalysisResult.kt:42`, `:47`), и без правки он попал бы в список дважды.
  Добавление условное («если ещё нет»), поэтому списки режимов «только снимок» и
  «только стадии» не меняются.
- Отдельный модуль для правила D2 не вводится: правило это существующее правило
  полных ячеек ADR 0005, а сочетание уже отличимо по `modules`, `input_versions` и
  `limits`; версия движка входит в identity и ключ.
- `analysis_id` новый только у нового сочетания. Анализы без стадий, со стадиями
  без снимка и со снимком без стадий получают прежние байты identity и результата;
  сохранённые каталоги анализа не перечитываются и не переписываются. Повторная
  отправка тех же входов возвращает сохранённый анализ, как сегодня.
- Ключ сопоставимости (`semanticKey`, `BaselineComparison.kt:670-681`;
  `comparisonSemanticKey`, `RunComparison.kt:316-327`) кода не меняет. Сочетание
  «стадии и снимок» несовместимо и с «только стадиями», и с «только снимком»
  (разные `modules`, `input_versions`, `limits`); два анализа сочетания с одним
  объявлением стадий и одним плечом совместимы; разные объявления несовместимы
  (звено `load_stages_sha256`). Слоты baseline ([ADR 0019](0019-release-history-and-baseline-eligibility.md))
  не меняются. Эталон ADR 0032 (D5) со стадиями берёт дельты из
  `window_metric_summary`, это работает и здесь.

### D7. Онлайн-источник (`--source`, часть `source_request`)

Стадии с онлайн-запросом разрешены; `STAGES_SOURCE_CONFLICT` больше не выдаётся.
Снимок по-прежнему строится до `AnalysisService` (`analyzeWithSources`), затем
действуют D1-D5.

- Авто-окно (`source-request.v3`/`v4`, `window.origin = auto`): сетка это
  распознанный период ([ADR 0012](0012-auto-window-recognized-period.md)) с запасом
  `margin_ms`, выровненный по шагу. Начало и конец распознанного периода это минимум
  `started_at` и максимум конца выборки (`RunPeriod.kt:59-60`), то есть те же
  `runStart` и `runEnd`, от которых считаются стадии. Значит, каждое окно `steady`
  лежит в сетке, и `STAGE_WINDOW_SNAPSHOT_PARTIAL` для авто-окна невозможна (кроме
  выпавших в ноль краёв короткой стадии, D2). Окон снимок не объявляет, как сегодня.
- Явное окно (`v1`-`v4`): если заданы стадии, снимок строится без массива `windows`
  (окно `full` не пишется), иначе D3 отвергал бы любой такой запрос. Окно запроса
  задаёт только протяжённость сетки и публикуется в `source_summary`, как сегодня.
  Без стадий байты снимка и `source_summary` прежние.
- Проверки стадий, которые зависят от прогона (`STAGE_OUTSIDE_RUN`,
  `STAGE_WINDOW_NO_FULL_CELLS`), выполняются после выборки: границы прогона
  известны после разбора. Для явного окна, не покрывающего стадию `steady`, это
  означает один напрасный онлайн-запрос (как у `RESOURCE_WINDOW_OUTSIDE_RUN`
  сегодня). Предварительная проверка по распознанному периоду до сети не вводится.
- Запрет `SOURCE_INPUT_CONFLICT` (онлайн-запрос вместе со снимком, планом корреляций,
  ёмкости, тренда, pod-view, контекстом) не меняется.

### D8. План ёмкости: запрет остаётся

`STAGES_CAPACITY_CONFLICT` сохраняется. Причины:

1. План ёмкости уже объявляет свои ступени с границами в epoch и привязывает каждую
   к окну оценки снимка по id ([ADR 0009](0009-explicit-capacity-stages.md)); со
   стадиями D3 у снимка нет своих окон, и привязке не к чему относиться. Ссылаться из
   плана на id стадий значит менять контракт `capacity-plan.v1` (ступень целиком
   внутри окна, сетка 10 с UTC, минимум 300 с).
2. Задача, ради которой нужны стадии (исключить разгон из вердикта), в режиме
   ёмкости уже решена: оценка идёт по явным окнам ступеней.
3. Вердикт ёмкости это границы продукта (`BOUNDED`, `LOWER_BOUND` и др.), а не
   вердикт по окну `steady`; соединение двух смыслов требует отдельного решения.

Цена: прогон ступенчатой нагрузки не получает полосы стадий; полосы ступеней ёмкости
UI может рисовать из `capacity_summary` (вне этого ADR).

### D9. План корреляций и план тренда со стадиями: отказ

- План корреляций (`--correlation`, часть `correlation_plan`) со стадиями даёт
  `STAGES_CORRELATION_CONFLICT`. Диагностика пишет `window_metric_summary` с тем же
  id, что режим стадий (уточнение R5: коллизия возможна, как только снимок и стадии
  сочетаются), и её окна читаются из того же накопителя окон.
- План тренда (`--trend`, часть `trend_plan`) со стадиями даёт
  `STAGES_TREND_CONFLICT`. Тренд связывается только с явными окнами снимка
  (`TrendPlan.kt:109-116`), а по D3 их со стадиями нет; без отдельного кода
  пользователь получил бы `TREND_WINDOW_NOT_FOUND` по каждой проверке без объяснения.
- pod-view (`--pod-view`), PostgreSQL (`--postgres-pre/-post`) и офлайн-контекст
  OpenSearch (`--source-context`) окон не задают и со стадиями и снимком
  разрешены. Контекст OpenSearch, который строит снимок поверх базового снимка с
  окнами, попадает под D3.

Обе проверки выполняются до чтения входа в ядре и раньше в CLI и API, тем же кодом.
Они стоят раньше проверок `DIAGNOSTIC_RESOURCE_REQUIRED` и `TREND_RESOURCE_REQUIRED`,
поэтому стадии с планом корреляций или тренда **без** снимка тоже получают новые коды
вместо прежних (строка 5 таблицы «Взаимодействие с другими режимами» ADR 0030 меняется
этим ADR). Сочетание и раньше было отказом; меняется только код.

### D10. `NO_VERDICT`/`NO_POLICY`: гигиена не затрагивается

Бэклог (ADR 0030, R4) записал расхождение: политика, у которой нет применимых
бизнес-правил и есть платформенные SLA-правила, без снимка и без стадий даёт
`NO_POLICY`, а со стадиями без снимка `NO_VERDICT` (`RESOURCE_SNAPSHOT_REQUIRED`).
(Политика из одних `platform_rules` невозможна: `rules` обязателен и непуст,
ADR 0018, раздел 7.) Этот ADR расхождение не трогает: оно живёт только в путях без
снимка, байты которых этот ADR обязан сохранить; при снимке платформенные правила
проверяются по-настоящему (D4) и дают `PASS`, `FAIL` или `NO_VERDICT` по данным, в
обоих режимах одинаково. Правка гигиены остаётся отдельной задачей бэклога.

Примеры. Допустимо: `ramp-steady-down.json` стадий вместе со снимком без `windows`,
построенным для того же JTL; онлайн-запрос `v3` с авто-окном и теми же стадиями;
онлайн-запрос `v2` с явным окном и стадиями (снимок без `windows`). Недопустимо:
стадии и `docs/contracts/resources/v1/examples/valid/basic.json`, если в нём есть
`windows` (`STAGES_RESOURCES_CONFLICT`); стадии и план ёмкости
(`STAGES_CAPACITY_CONFLICT`); стадии и план корреляций
(`STAGES_CORRELATION_CONFLICT`); стадии и план тренда (`STAGES_TREND_CONFLICT`);
стадия `steady` короче шага снимка, не содержащая ни одной полной ячейки
(`STAGE_WINDOW_NO_FULL_CELLS`). Файлы примеров снимка и стадий не добавляются:
пары строятся в тестах (снимок привязан к хэшу конкретного JTL).

### D12. Что получают UI и отчёты (только перечень)

- Ресурсные ряды (CPU, память, поды, платформенные сигналы) анализа со стадиями;
  полосы стадий на этих рядах по `stage_binding.stages[]`, затенение оценённых ячеек
  по `resource_from_epoch_ms`/`resource_to_epoch_ms`.
- Лента стадий в обзоре для анализа с данными платформы.
- Проверки ресурсных и платформенных SLA по окну `steady` в карточке вердикта и в
  `window_policy_summary` (`resource_verdict` по-настоящему, не `NO_POLICY`).
- Причина `STAGE_WINDOW_SNAPSHOT_PARTIAL` в покрытии.
- Предложение стадий (черновик ADR 0036) применимо к прогонам с данными платформы.

Дизайн UI и отчётов в этот ADR не входит; изменения видимости, кроме подписей новых
кодов, идут отдельными срезами.

## Отклонённые варианты

- **Каждое семейство правил по своим окнам** (бизнес по стадиям, ресурсы по окнам
  снимка, результат называет оба). Совместная оценка окна и `jointVerdict` требуют
  общего id окна; второй набор окон означал бы вторую свёртку и новый контракт
  `window_policy_summary`. Ломает единое пространство `window_ids` ADR 0018 (D5):
  платформенное правило с `window_ids: ["steady"]` не нашло бы окна. Окна инцидентов
  (ADR 0029) берутся из `window_policy_summary` и стали бы неоднозначны. При
  неявном снимке ресурсы оценивались бы по всему прогону с разгоном.
- **Вариант «окно снимка внутри стадии `steady`»** (согласованность через вложение):
  то же, что предыдущий, плюс правило вложенности; оценка всё равно по двум наборам
  окон.
- **Молчаливый приоритет** стадий над снимком или наоборот: прямо отвергнут ADR 0030
  (R3) и не нужен, раз D3 исключает два объявления.
- **Окна стадий на снимке как есть** (без выравнивания): неполная ячейка разгона
  попадает в SLA, неполная ячейка конца теряется; поведение зависит от фазы сетки.
- **Выравнивание наружу** (с неполными ячейками): в SLA попадает разгон.
- **Требовать границы стадий на сетке снимка**: смещения от `runStart` в
  миллисекундах почти никогда не кратны шагу; отказ почти всегда.
- **Окна снимка допустимы при согласованности со стадиями** (D3, вариант б): меняет
  смысл окна снимка без смены контракта.
- **Отказ для явного онлайн-окна со стадиями** вместо снимка без окон: оставляет
  рабочим только авто-окно, хотя окно запроса с окнами оценки не связано.
- **Ёмкость со стадиями**: см. D8.
- **Корреляции и тренды по окнам стадий в этом же ADR**: меняют привязку планов
  корреляций и тренда к окнам (`window_metric_summary` с общими id, тренд только по
  окнам снимка); отдельное решение.
- **Отдельный модуль identity для правила D2**: сочетание уже отличимо, версия
  движка входит в ключ; модуль ради будущей смены правила не нужен.
- **Правка гигиены `NO_VERDICT`/`NO_POLICY` здесь же**: меняет байты режимов без
  снимка, которые ADR обязан сохранить (D10).

## Последствия

- Прогоны без стадий, со стадиями без снимка и со снимком без стадий не меняются:
  вердикт, байты `identity.json` и `analysis-result.json`, `analysis_id`, ключ
  сопоставимости, `junit.xml`, `summary.txt`, `cli-summary.v1`, HTML. Это доказывают
  существующие золотые тесты и новые характеризационные файлы, закреплённые до
  изменения кода (план, задача 1).
- Новое сочетание получает настоящие ресурсные и платформенные SLA по окну `steady`;
  платформенное SLA-правило со стадиями больше не обязано давать `NO_VERDICT`, если
  передан снимок.
- Существующие тесты, проверяющие `STAGES_RESOURCES_CONFLICT` на любой снимок и
  `STAGES_SOURCE_CONFLICT`, меняют ожидание по решению владельца
  (`StageWindowPolicyTest`, `CommandLineStagesTest`, `AnalysisJobsStagesTest`,
  `LocalApiStagesTest`); проверки `STAGES_CAPACITY_CONFLICT` остаются.
- ADR 0030: ruling R3 и таблица «Взаимодействие с другими режимами» получают
  пометку «изменено ADR 0037»; R5 получает уточнение о коллизии (D9). Руководство
  пользователя (`docs/user/slice-1-local-analysis.md`, раздел стадий, строки
  2256-2289), `examples/basic/run.md:69-70` и фрагмент `changelog.d/` обновляются в
  PR реализации.
- Новых зависимостей production нет; `CanonicalJson.kt`, вычисление хэшей identity,
  белый список `AdvisoryAi.kt`, `run.v1`, коды выхода CLI не меняются.
- Остаток обрезки внутрь (D2): у каждого края стадии `steady` до одного шага снимка
  минус 1 мс ресурсными правилами не проверяется (при шаге 60 с это до двух минут на
  стадию). Причины покрытия на это нет; видно только по `resource_from_epoch_ms` и
  `resource_to_epoch_ms` в `stage_binding`.
- Окно, которое сетка покрывает не целиком, сохраняет свой `PASS` по ресурсам
  (оценка по покрытой части) с покрытием `INCOMPLETE` и причиной
  `STAGE_WINDOW_SNAPSHOT_PARTIAL`; это исполнение по рекомендации, решение
  владельца по вопросу 1 ещё ждёт.

## Реализовано

Статус остаётся Proposed до слова владельца. Реализация на локальных ветках (PR ещё
не открыты):

- `feat/stages-with-resources-core` (PR A, задачи 1-5 плана): ядро, identity,
  ресурсные окна стадий, сочетание в `AnalysisService`, суженные отказы, задания.
- `feat/stages-with-resources-cli` (PR B, задачи 6-9): CLI, API, онлайн-источник,
  подпись причины `STAGE_WINDOW_SNAPSHOT_PARTIAL` в отчёте и UI, поле
  `resource_partial`, документация, пометки в ADR 0030, фрагмент changelog.

Отличия от текста выше, выявленные при реализации:

- Проверка снимка с окнами в CLI стоит в общем блоке проверок стадий, до чтения
  политики (снимок со стадиями читается раньше политики), чтобы порядок кодов совпадал
  с ядром и API.
- Атом инцидента ресурсного нарушения получает границы нарушенных ячеек самой находки,
  а не границы стадии; границы `window_policy_summary` (точные границы стадии)
  получает только бизнес-атом.

## Вопросы владельцу: исполнение по рекомендации

Решение владельца 2026-11-19: стадии должны работать вместе со снимком ресурсов.
На три вопроса плана ответа владельца пока нет; реализация (PR A, ядро) идёт по
рекомендациям этого ADR. Каждый пункт: **исполнено по рекомендации, ждёт слова
владельца**.

1. Сетка снимка покрывает окно `steady` не целиком (D2): оценка по пересечению,
   информационная причина покрытия `STAGE_WINDOW_SNAPSHOT_PARTIAL`
   (`analysis_coverage = INCOMPLETE`, вердикт по данным). Исполнено по рекомендации,
   ждёт слова владельца.

   Факты ревью PR B для решения: со снимком, обрезанным до 0–75 с (стадия `steady`
   40–100 с), прогон завершается кодом `0`, `summary.txt` показывает
   `rules: 3 (PASS 3, FAIL 0, NO_VERDICT 0)`, `junit.xml` имеет `failures="0"`, и ни
   тот, ни другой не упоминают `INCOMPLETE`. Неполное покрытие видно только в
   `result.json` (`analysis_coverage`, `resource_partial`), HTML-отчёте и UI. Тот же
   результат дал снимок с началом сетки на 60 с. Варианты: (а) печатать причины
   покрытия в `summary.txt` и в `<system-out>` gate `junit.xml` (меняет байты этих
   файлов у всех анализов с неполным покрытием); (б) отвергать такой анализ новым
   кодом. Пока не сделано ни то, ни другое.
2. Снимок с собственными `windows` вместе со стадиями (D3): остаётся ошибкой
   `STAGES_RESOURCES_CONFLICT` с суженным условием; особого случая для единственного
   окна на всю сетку нет. Исполнено по рекомендации, ждёт слова владельца.
3. Планы тренда и корреляций со стадиями (D9): пока отказ явными кодами
   `STAGES_TREND_CONFLICT` и `STAGES_CORRELATION_CONFLICT`. Исполнено по рекомендации,
   ждёт слова владельца.

## Не входит

- План ёмкости со стадиями (D8).
- Планы корреляций и тренда по окнам стадий (D9). Ожидаемый следующий шаг: план
  тренда, привязанный к id стадий. Целевой UI продукта показывает тренды внутри
  стадии `steady` (например, «Soak») рядом с лентой стадий, а по D3 у снимка со
  стадиями своих окон нет, так что тренд без привязки к id стадий этот вид не даст.
- Правка гигиены `NO_VERDICT`/`NO_POLICY` (D10).
- Предварительная проверка покрытия стадий окном онлайн-запроса до сети (D7).
- Дизайн UI и отчётов: полосы стадий на ресурсных рядах, лента стадий в обзоре (D12).
- Автоопределение и предложение стадий (черновик ADR 0036).
- Новые поля `resource-snapshot.v1`, `policy.v1`, `load-stages.v1`.
