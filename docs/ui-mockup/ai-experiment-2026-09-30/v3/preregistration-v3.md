## 0. Решение владельца и порядок

Владелец (по сообщению координатора, 2026-10-02): раунд v3 на других моделях через тот же headless Qwen Code 0.21.1 и `relay2.mjs`; бюджет раунда не более 72 реальных запросов к провайдеру; общий предел 300 жёсткий.
Перед этим файлом сделан один счётный GET `/compatible-mode/v1/models` (ledger, задача `ai-experiment-v3-models`, 1 запрос, ключ из памяти процесса): получены 15 id; точные идентификаторы `glm-5.3` и `qwen3.8-max` присутствуют.
Для информации в списке есть и другие: `glm-5.2`, `qwen3.7-max`, `qwen3.7-plus`, `qwen3.6-flash`, `qwen3.8-flash`, `deepseek-v4-pro`, `deepseek-v4.1-flash` (в раунд не входят). Ledger до раунда: 149 запросов (v1 74, v2 74, models 1), после раунда ожидается 221, остаток около 79.

## 1. Дизайн

- Модели: `glm-5.3`, `qwen3.8-max`. Продуктовая `deepseek-v4-flash-0731` в раунд не входит; данные v2 (та же конструкция: Qwen 0.21.1, relay2, S0/S1 без изменений) - контрольная линия, только описательно, без объединения выборок (другой день, у S0 в v2 было 2 повтора).
- Ступени: S1 (кандидат prompt v2) - 12 кейсов x 2 повтора x 2 модели = 48 запусков; S0 (база) - 12 кейсов x 1 повтор x 2 модели = 24 запуска; всего 72, порядок общий, случайный, `random.Random(20261002)`, `v3/plan-v3.json`. Последовательно.
- Те же 12 кейсов и evidence (манифест `../cases/manifest.json`), те же system prompt S0 (1752 B) и S1 (3335 B), та же конструкция запуска (флаги Qwen, `relay-placeholder`, пустой cwd, один запрос провайдеру на запуск, повторный запрос Qwen блокируется и не считается).
- Отдельного смоука нет: он вышел бы за 72. Первые запуски плана - рабочие; защита от систематического брака (ниже).
- Модель задаётся параметром relay; проверка имени модели в SSE-кадрах relay не расширяется (граница продукта): если провайдер вернёт иное имя, запуск получит `BAD_STREAM`, и прогон остановится по правилу трёх подряд.

## 2. Остановки и бюджет

- Лимиты relay: раунд 72, всего 300 (считает relay до каждого запроса, `ledger.jsonl`), файл `STOP`.
- HTTP не 200 от провайдера (429, квота, 5xx, 401): немедленная остановка, без повтора. Сетевая ошибка: один повтор запуска (считается).
- HTTP 200 без валидного потока `structured_output`: `BAD_STREAM` (сбой формата), прогон продолжается.
- Три подряд запуска не в статусе OK или `SCHEMA_INVALID_RETRY` (то есть BAD_STREAM, QWEN_FAILED, INVALID_OUTPUT и т.п.) - остановка (код 6). После 12 запусков более двух третей не OK - остановка.
- Инфраструктурный сбой (запуск не дошёл до relay, 0 запросов провайдеру): один бесплатный автоповтор запуска; если сбой повторился - остановка и отчёт частичного результата, вслепую не повторять.
- Повторный запрос при ошибке схемы НЕ разрешается (как в продукте сегодня). Фиксируется число запусков `SCHEMA_INVALID_RETRY` по моделям и ступеням (ответ модели отвергнут схемой Qwen). Оценка «сколько запросов спас бы повтор» не делается: считается только число таких ответов.

## 3. Критерий (заморожен)

Единица - кейс. Для каждой модели отдельно сравнивается S1 (ТОЛЬКО повтор 1, чтобы n было равным: 12 ответов S1 против 12 ответов S0) с S0 по тем же условиям, что в v1/v2, теми же функциями (`analyze.py`, `analysis2.criterion2`):
- C0 F_S0 >= 4; C1 F_S1 <= floor(F_S0 / 2); C2 регрессий (S0 чист, S1 с дефектом) не более 1; C3 R_S1 <= R_S0 + 1; C4 B_S1 <= B_S0 + 1;
- C5: число кейсов с hard_defect по рецензенту на S1 не больше, чем на S0, для ОБОИХ рецензентов;
- C6 (формат, на модель): число запусков не в статусе OK из 36 не более 2 (около 5 %); `SCHEMA_INVALID_RETRY` входит в не-OK.
Решение по модели: «S1 принята» при выполнении C0-C5 (C6 отчитывается отдельно, формат не исправляется улучшением prompt).
Межмодельный критерий: S1 «подтверждена на разных моделях», если принята на обеих моделях; «частично» - на одной; иначе «не подтверждена». Результат v2 для deepseek (S1 не принята) в правило не входит.
Вторая повторность S1 используется для воспроизводимости (разведочно): доли ответов с дефектом на всех 24 ответах S1 против 12 ответов S0 с интервалами Клоппера-Пирсона. Всё вне критерия помечается «разведочное». Значимость не условие.

## 4. Рецензенты

Те же два слепых рецензента (A: Codex `gpt-6-sol`, `model_reasoning_effort=xhigh`; B: `gpt-5.6-terra`, `model_reasoning_effort=high`; оба `-s read-only`), одна рубрика `reviewer_rubric_v2.txt` + `derived.txt` на кейс, ответы всех моделей и ступеней перемешаны, имена ответов анонимизированы, модель и ступень скрыты; ключи `v3/review_key_a.json`, `v3/review_key_b.json` (вне воркстри). Один вызов на кейс на рецензента (6 ответов на кейс).
Согласие: каппа Коэна по hard_defect (общая и по моделям), сырое согласие, PABAK, распространённость; каппа по required_facts_preserved; согласие по полезности. Рецензенты v3 работают отдельными сессиями от v2, поэтому сравнение с контролем (deepseek v2) описательное.
Если вызов рецензента завершается инфраструктурной ошибкой (например, «server returned no safety verdict»), он не повторяется вслепую: прогон рецензирования останавливается, частичный результат сообщается.

## 5. Ожидания и ограничения

Ожидание: S1 снижает knee-зависимость bound (T1) на обеих моделях, как на deepseek. Оговорки: малое n (12 кейсов, S0 один ответ на кейс), один провайдер, хостовый запуск без Docker, оракул эвристичен и шумит на отрицаниях (известные ложные срабатывания не исправляются), рецензенты - модели, повторы S1 не независимы, S0 не имеет повторов (нет оценки разброса базы), модели могут по-разному обёртывать ответ (формат сравнивается отдельно).
