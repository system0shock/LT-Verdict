# LT Verdict — регламент разработки

**Статус:** нормативный

**Владелец:** проект LT Verdict

Этот документ определяет обязательный процесс разработки. Краткие инструкции
для AI-агентов находятся в [`AGENTS.md`](../AGENTS.md), а обоснование решений —
в [дизайне регламента](superpowers/specs/2026-08-10-project-development-governance-design.md).

## Принципы

- `main` всегда остаётся работоспособной и пригодной для выпуска.
- Доказательства проверки предшествуют заявлениям о готовности.
- Документация — часть изменения и обновляется в том же PR.
- Production-зависимость не добавляется, а публичный контракт не изменяется без
  явного отражения решения в плане или ADR.
- Необратимые операции и операции с удалённым репозиторием выполняются только
  после явного решения пользователя.

## Жизненный цикл задачи

Каждая задача проходит следующий обязательный порядок:

1. Brief с границами, критериями приёмки и известными рисками.
2. Для новой функции или изменения поведения — brainstorming и утверждённая
   спецификация.
3. План реализации с проверяемыми шагами и командами проверки.
4. Отдельная ветка и, если среда поддерживает, отдельный worktree.
5. Реализация через TDD: RED–GREEN–REFACTOR.
6. Свежая verification: применимые тесты, сборка, линтеры и документальные
   проверки.
7. Review полного diff согласно Superpowers.
8. Решение пользователя о merge, тегировании, публикации или иной удалённой
   операции.

## Ветки и worktree

Проект использует GitHub Flow с защищённой веткой `main`, короткоживущими
тематическими ветками и обязательными Pull Request.

- Прямые изменения и push в `main` запрещены.
- Каждая задача выполняется в отдельной короткоживущей ветке или worktree.
- Допустимые префиксы веток: `feat/`, `fix/`, `docs/`, `refactor/`, `test/`,
  `chore/`.
- После префикса используется короткое описание в kebab-case, например
  `feat/stage-1-run-registration`.
- Одна ветка и один PR содержат одну законченную задачу без посторонних
  изменений.
- Перед слиянием ветка актуализируется относительно `main`, если расхождение
  влияет на результат проверок или создаёт конфликт.
- Ветки и worktree создаются и используются согласно
  `superpowers:using-git-worktrees` и ограничениям среды.

## Коммиты

- Используется Conventional Commits:
  `<type>(<optional-scope>): <imperative summary>`.
- Допустимые основные типы: `feat`, `fix`, `docs`, `refactor`, `test`, `build`,
  `ci`, `chore`, `perf`, `revert`.
- Заголовок формулируется в повелительной форме, описывает результат и не
  заканчивается точкой.
- Коммит атомарен: его можно понять, проверить и при необходимости отменить
  отдельно.
- Форматирование, рефакторинг и изменение поведения не смешиваются без
  необходимости.
- Тесты и документация, без которых изменение неполно, входят в тот же
  логический набор коммитов.
- В индекс добавляются только файлы своей задачи; широкое `git add .` запрещено
  при наличии посторонних изменений.
- Нельзя изменять, переписывать или объединять пользовательские коммиты без
  явного разрешения пользователя.

## Pull Request

- Каждый PR связывается с задачей и GitHub Milestone либо явно объясняет
  отсутствие связи.
- Заголовок PR соответствует Conventional Commits и становится итоговым
  сообщением squash-коммита.
- Описание PR содержит цель, границы изменения, способ проверки, влияние на
  документацию и известные риски.
- Для слияния обязательны зелёный CI, выполненный Definition of Done и review
  полного diff.
- Используется Squash and Merge, чтобы `main` содержала один итоговый коммит на
  задачу.
- Агент не выполняет push, merge, rebase общей ветки, создание тега или релиза
  без явного разрешения пользователя.

## Майлстоуны и версии

Этапы проекта и версии поставляемого продукта учитываются раздельно.

### Этапы проекта

- Для этапов плана создаются GitHub Milestones вида `Stage N` с понятным
  названием этапа, например `Stage 1 — Ingest Core`.
- Issue и PR относятся к конкретному этапу либо явно помечаются как
  внеплановые.
- Этап закрывается только после выполнения exit gate, зелёного CI, обновления
  документации и фиксации известных ограничений.
- Результат закрытия описывается в `docs/milestones/stage-N.md`.
- Milestone-отчёт содержит достигнутый результат, ссылки или команды проверок,
  ограничения, незакрытые риски и решение о переходе к следующему этапу.
- На закрывающий коммит в `main` ставится разрешённый пользователем подписанный
  аннотированный тег `stage-N`. Он неизменяем и не переносится на другой
  коммит.

### Версии продукта

- Поставляемые версии следуют Semantic Versioning: `v0.1.0`, `v0.2.0`, затем
  `v1.0.0`.
- `CHANGELOG.md` ведётся по принципу Keep a Changelog.
- Пользовательски заметные изменения добавляются в секцию `Unreleased` в том
  же PR, где они появляются.
- При выпуске секция `Unreleased` получает номер версии и дату; сверху
  создаётся новая пустая секция `Unreleased`.
- Версионный тег подписывается и аннотируется; он ставится только на
  проверенный коммит в `main` после явного разрешения пользователя.

## Документация

Документация является частью продукта и обновляется в том же PR, что и
соответствующее изменение.

### Целевая структура

- `README.md` — назначение, статус, быстрый старт и навигация.
- `docs/architecture/` — архитектура, компоненты, потоки данных и ограничения.
- `docs/adr/` — значимые технические решения, альтернативы и последствия.
- `docs/api/` — контракты API и проверяемые примеры.
- `docs/operations/` — развёртывание, конфигурация, эксплуатация и диагностика.
- `docs/user/` — пользовательские сценарии, инструкции, терминология и FAQ.
- `docs/milestones/` — отчёты о закрытии этапов.
- `docs/superpowers/specs/` — утверждённые дизайны.
- `docs/superpowers/plans/` — планы реализации.

### Правила актуальности

- `README.md` ссылается только на tracked-документы. Новый нормативный документ
  добавляется в навигацию в том же PR, где он впервые коммитится.
- Изменение поведения обновляет соответствующую пользовательскую документацию.
- Изменение архитектуры, API, конфигурации или схемы данных обновляет
  техническую документацию.
- Значимое решение, меняющее границы компонентов, публичный контракт, модель
  данных или эксплуатационные свойства, фиксируется ADR.
- Документация не откладывается на отдельную будущую задачу. Если она не
  требуется, PR содержит явное обоснование `Documentation impact: none`.
- Команды и примеры проверяются перед слиянием.
- Основной язык prose — русский; идентификаторы кода, API, команды и
  стандартные технические термины сохраняются на английском.
- Устаревший документ заменяется, помечается как superseded или переносится в
  архив со ссылкой на актуальный источник.

## AI-агенты и Superpowers

Проект не вводит skills, заменяющие или сокращающие процессы Superpowers. Если
проектная инструкция и Superpowers описывают один процесс, агент следует
Superpowers, а проектную инструкцию применяет как дополнительное ограничение.
Прямая инструкция пользователя имеет высший приоритет.

Порядок применимых skills: `superpowers:brainstorming` для новой функции или
поведения; `superpowers:writing-plans` для подготовки реализации;
`superpowers:using-git-worktrees` для изоляции; `superpowers:test-driven-development`
для реализации и исправлений; `superpowers:systematic-debugging` для диагностики;
`superpowers:verification-before-completion` для доказательства готовности;
`superpowers:requesting-code-review` и `superpowers:receiving-code-review` для
review; `superpowers:finishing-a-development-branch` для завершения ветки.

Новые project skills допустимы только для самостоятельной, неочевидной и
повторяемой техники. Они создаются по `superpowers:writing-skills` через цикл
RED–GREEN–REFACTOR с проверкой поведения агента без skill и с ним. Skills не
дублируют Superpowers: проектные соглашения остаются в `AGENTS.md`, а
механически проверяемые требования — в CI.

Проектные scripts на данном этапе запрещены. Этот rollout не создаёт ни project
skills, ни project scripts.

## Матрица моделей субагентов

Superpowers определяет, когда задача допускает или требует делегирования.
Проектная политика не заменяет `superpowers:dispatching-parallel-agents`,
`superpowers:subagent-driven-development` и
`superpowers:requesting-code-review`, а задаёт модель и effort для уже
обоснованного вызова субагента.

| Класс работы | Модель | Effort |
| --- | --- | --- |
| Механическая задача с однозначным результатом | `gpt-5.6-luna` | `low` |
| Обычная инженерная задача и простое ревью | `gpt-5.6-terra` | `medium` |
| Сложная инженерная задача | `gpt-5.6-terra` | `high` |
| Сложное риск-ориентированное ревью | `gpt-5.6-sol` | `max` |

- Модель выбирается по риску и требуемому суждению, а не по размеру текста
  задачи. Механическая задача имеет явный вход, ожидаемый формат результата и
  проверяемый критерий завершения.
- Luna не принимает архитектурных решений, не выполняет сложное ревью и не
  утверждает готовность результата.
- Простое ревью считается сложным и передаётся Sol Max, если оно затрагивает
  безопасность, конкурентность, целостность данных, миграции, публичные
  контракты, архитектурные изменения, производительность или milestone gate.
- Независимые задачи можно делегировать параллельно; задачи с общей изменяемой
  областью или последовательной зависимостью выполняются последовательно.
- Корневой агент проверяет вывод субагента и отвечает за итоговое решение.
- Если требуемая модель недоступна, используется ближайшая более сильная
  доступная модель с не меньшим effort. Сложное ревью нельзя понижать до Luna;
  при недоступности Sol Max корневой агент сообщает об ограничении и не
  объявляет review gate пройденным без согласованной замены.

## Definition of Done

Задача готова, когда одновременно выполнены все применимые условия:

- требования и критерии приёмки выполнены;
- для изменения поведения подтверждён цикл RED–GREEN–REFACTOR;
- свежие проверки CI проходят;
- полный diff просмотрен и отревьюирован;
- техническая и пользовательская документация обновлена либо обоснованно не
  требуется;
- значимые решения зафиксированы в ADR;
- пользовательски заметные изменения добавлены в `CHANGELOG.md`;
- в изменениях нет секретов, временных файлов и несвязанного содержимого;
- известные ограничения и риски явно перечислены;
- слияние, тегирование и публикация выполняются только после решения
  пользователя.

## Stage gate

Этап проекта закрыт только при выполнении Definition of Done всех входящих
задач, exit gate этапа, зелёного CI, milestone-отчёта и постановки разрешённого
пользователем подписанного аннотированного тега.

## Исключения и сбои

- Недоступная обязательная проверка не считается пройденной. Агент описывает
  причину, риск и способ последующей проверки.
- Если существующие тесты не проходят до начала работы, агент фиксирует
  красный baseline и запрашивает решение пользователя перед продолжением
  реализации.
- Если правило неприменимо, PR объясняет это наблюдаемым условием, а не общим
  утверждением.
- Срочность не отменяет TDD, проверку, документацию или пользовательское
  разрешение на операции с удалённым репозиторием.
- Исправления регламента проходят тот же PR-процесс, что и остальные изменения.
