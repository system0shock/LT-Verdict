# ADR 0030: Стадии нагрузки и вердикт по окну устойчивого состояния (`load-stages.v1`)

Дата: 2026-10-09.

Статус: Proposed. В Accepted переводится только по слову владельца. Номер 0030
выбран как следующий после 0029 (на `origin/main` 2026-10-09 последний ADR с
номером 0029); перед слиянием его нужно перепроверить по `origin/main`. ADR
фиксирует публичные контракты работы W2.5; кода, схем и примеров в этом PR нет:
схема `load-stages.v1` появится в PR A реализации (см. «Следствия»). Решения
владельца 2026-10-09 (раздел «Решения владельца») приняты как есть. Четыре
ruling'а (R1, R4, R7, R12) вынесены в отдельный раздел «Решения, ожидающие
подтверждения владельца»: до подтверждения они считаются рабочими, а PR A может
начинаться только после ответа владельца по ним либо после явного «принимаю как
написано».

## Контекст

Оконная бизнес-оценка политики сегодня существует только вместе со снимком
ресурсов: при `request.resources != null` вызывается `evaluateSharedWindowPolicy`
(окна из снимка, [ADR 0005](0005-resource-window-sla.md),
[ADR 0012](0012-auto-window-recognized-period.md)), а при `resources == null`
политика считается по всему прогону. Самый частый вход продукта это журнал
JMeter или Gatling без снимка ресурсов. У такого прогона есть разгон и остановка,
и вердикт «по всему прогону» включает их в p95 и throughput: прогон с профилем
«разгон, плато, остановка» получает FAIL по правилу, которое плато выполняет.
Человек знает границы стадий («разгон 40 секунд»), но дать их ядру нечем.

Ограничения решения:

1. Автоопределения плато нет: это новый статистический метод и источник
   недетерминизма (D1 заморожен; границы окна не угадываются, как в
   [ADR 0012](0012-auto-window-recognized-period.md)).
2. Для прогонов без стадий не меняется ничего: ни вердикт, ни байты
   `analysis-result.json` и `identity.json`, ни `analysis_id`, ни ключ
   сопоставимости, ни `junit.xml`, `summary.txt`, `summary` JSON, HTML.
3. Канонический JSON и вычисление хэшей identity не затрагиваются.
4. Окна со стадий нужны инцидентам v0: [ADR 0029](0029-incident-v0.md) делает W2.5
   жёстким предусловием W3.7 (`window_id` и `window_policy_summary` без
   `resource_binding`).
5. Условный ключ по образцу `resource_arm` описан в
   [ADR 0014](0014-resource-series-limits-autostep-arm-api.md); слоты baseline
   (пара series и arm) закреплены [ADR 0019](0019-release-history-and-baseline-eligibility.md)
   и не расширяются.

Рабочий план, расчёты и критерии приёмки:
[2026-10-09-w2-5-steady-state-window.md](../superpowers/plans/2026-10-09-w2-5-steady-state-window.md).

## Решение

Человек объявляет стадии прогона файлом `load-stages.v1` (смещения от начала
прогона). Стадии с ролью `steady` становятся окнами с `window_id`, равным id
стадии, и идут в существующую `evaluateSharedWindowPolicy` с пустой ресурсной
стороной. Контракт оконной оценки не меняется. В результат добавляются только
новые свидетельства `stage_binding` и `window_metric_summary` по каждому окну.
Хэш объявления входит в identity и ключ сопоставимости условно, только когда
стадии заданы.

### Решения владельца (2026-10-09, приняты как есть)

1. Opt-in, расширение существующего контракта. Когда передан снимок ресурсов с
   окнами, бизнес-политика уже сегодня считается только по окнам; W2.5 даёт тот же
   режим без снимка. Для прогонов без объявленных стадий ничего не меняется.
2. Привязка к identity условная: хэш объявления стадий входит в identity только
   при наличии, как `resource_snapshot_sha256` и `resource_arm`. Безусловное
   поле (как `incident_method` в ADR 0029) не нужно.
3. Автоопределения плато нет. Подсказка границ позже как зонд doctor или MCP
   (вне этого ADR).
4. Прогон со стадиями и без них нельзя сравнивать как baseline: объявление
   стадий входит в ключ сопоставимости. Вердикт обязан сказать вслух «по окну
   steady, разгон исключён» в заголовке, отчёте (HTML), сводке/UI и в сообщении
   gate в `junit.xml`.
5. Правила policy уже умеют `window_ids`: привязка правил к окну `steady` идёт без
   изменения схемы policy.

### Ruling'и, принятые без отдельного подтверждения

Формат: что, почему, цена ошибки.

**R2. Окнами становятся только стадии с ролью `steady`; `excluded` окном не
является.** Правила без `window_ids` применяются ко всем окнам; если бы разгон был
окном, правило «p95 не больше 300» без привязки проверялось бы и по разгону и
валило вердикт. Роль `excluded` даёт человеку имя («разгон») и позволяет показать
«исключено N мин». Правило, привязанное к `excluded`-стадии, даёт существующий
`RULE_WINDOW_NOT_FOUND` (fail-closed), не тихий пропуск. Цена ошибки: пользователь
ждёт оценки по разгону; для этого нужен отдельный режим.

**R3. Стадии и снимок ресурсов, `capacity_step`, онлайн-запрос источника
взаимоисключающи: приоритета нет, есть ошибка.** Оба источника определяют окна;
молчаливый приоритет нарушил бы принцип «вердикт говорит вслух». Пользователю со
снимком нужны окна снимка, потери нет. Цена ошибки: отказ там, где можно было
договориться (безопасная сторона).

**R5. Показатели окна публикуются типом `window_metric_summary`, не
`metric_summary`.** Тип уже читают сравнение окон (условия baseline,
[ADR 0028](0028-baseline-conditions-confirmation.md)) и оба отчёта; он содержит
`sample_count`, `error_count`, `error_rate_ratio`, `throughput_rps`,
`latency_ms.{p50,p95,p99,max}`, границы окна. Читатели метрики «весь прогон»
берут `metric_summary` с `scope.kind = overall` через `singleOrNull`; второй такой
элемент (оконный) сломал бы их, вернув `null`. Приватная `windowMetricSummary`
становится `internal` и вызывается из режима стадий. Коллизии id нет: диагностика
требует снимок, а со стадиями снимка быть не может (R3). Цена ошибки: потребитель,
ждущий steady-метрики в `metric_summary`, их не найдёт; новый код читает по
`window_id`.

**R6. Ключ сопоставимости получает условное звено `load_stages_sha256`, слоты
baseline не меняются.** Звено добавляется по образцу `resource_arm`:
отсутствие у обоих равно равенству; отсутствие у одного или разные хэши означают
несовместимость. Окно 5-25 мин и 5-30 мин дают разные p95 и throughput, это разные
метрики. Слот baseline (series, arm) не расширяется: [ADR 0019](0019-release-history-and-baseline-eligibility.md)
это публичный контракт хранилища, а несовместимость уже показывается как
`compatible = false`. Цена ошибки: сохранённый baseline без стадий при переходе на
стадии станет несовместимым и его нужно пересохранить (одна операция); обратный
выбор меняет схему хранилища.

**R8. Результат: только новые свидетельства, верхнеуровневых полей нет.**
Добавляются одно `stage_binding` и по одному `window_metric_summary` на окно.
Новое верхнеуровневое поле потребовало бы изменения белого списка в `AdvisoryAi.kt`
и typed-модели. Цена ошибки: типизация evidence (W2.1 срез 2) должна учесть новый
вариант.

**R9. В каталоге анализа сохраняется `load-stages.json` (канонические байты),
`run.json` не меняется.** Воспроизводимость (ADR 0029: инцидент воспроизводим из
bundle) требует, чтобы объявление лежало рядом с identity, как `policy.json` и
`resource-snapshot.json`. HTTP-маршрута скачивания нет и он не добавляется
(скачивание идёт по явной карте имён). Цена ошибки: агент по API не получит файл,
но получит границы и роли в `stage_binding` результата.

**R10. Фраза о границах генерируется при отрисовке из полей `stage_binding`, в
результате не хранится.** Русский текст не попадает в канонический результат,
поэтому формулировку можно править без смены `analysis_id`.

**R11. Непригодный (`INVALID`) прогон не получает `stage_binding`.** Окна
считаются после разбора выборок, у непригодного прогона нет начала. Вердикт
`NO_VERDICT` ничего не утверждает про steady; identity и `load-stages.json`
пишутся, чтобы ссылка identity не висела.

## Решения, ожидающие подтверждения владельца

Четыре ruling'а не следуют из ответов владельца напрямую. Каждый можно переиграть
до PR A; замена локальна и не меняет identity и ключ сопоставимости, кроме
оговорённого.

**R1. Границы стадий это смещения в миллисекундах от начала прогона, не epoch.**
Начало прогона это минимальный `started_at` среди всех выборок (то же `runStart`,
что в `resource_binding`). Почему: человек знает «разгон 5 минут», а не epoch; тот
же файл применим к любому прогону профиля, поэтому хэш объявления одинаков у
сопоставимых прогонов и ключ сопоставимости не ломается при каждом запуске. С epoch
хэш был бы разным у каждого прогона и ни один прогон не был бы сопоставим с
другим. Привязка к `load_input_sha256`, как у снимка, не нужна: границы
относительные. Стадия `steady` с концом за концом прогона даёт `STAGE_OUTSIDE_RUN`;
стадии `excluded` на конец прогона не проверяются (это подписи; реальные прогоны
заканчиваются на сотни миллисекунд раньше или позже объявленного, и один файл на
профиль не должен падать на части прогонов). Цена ошибки: объявление от другого
профиля молча применится, если длина прогона подходит; смягчено полем
`stage_binding.stages[].from_epoch_ms` в отчёте, ошибкой `STAGE_OUTSIDE_RUN` и
ключом сопоставимости. Если владелец выберет epoch, замена локальна (валидатор и
`resolveStageWindows`).

**R4. Оценка переиспользует `evaluateSharedWindowPolicy` с пустой ресурсной
стороной, платформенные правила в режиме стадий дают `NO_VERDICT`.** Ресурсная
сторона: `windowVerdicts = {окно: NO_POLICY}`, пустые `coverageReasons`,
`findings`, `evidence`; `jointVerdict(бизнес, NO_POLICY)` даёт бизнес-вердикт.
Поведение в окне побайтово то же, что со снимком (пустые окна, малые выборки,
`RULE_WINDOW_NOT_FOUND`). Исключение: платформенные правила (`platform_rules`)
без снимка. Сегодня без снимка и без стадий SLA-правило вместе с применимыми
бизнес-правилами даёт `NO_VERDICT` (причина `RESOURCE_SNAPSHOT_REQUIRED`), а
политика только из платформенных правил даёт `NO_POLICY` с причиной покрытия; в
окне `evaluatePolicy` эту ветку пропускает (`windowId != null`), и в режиме
стадий платформенные правила были бы тихо потеряны. Решение (строже прежнего, не
копия): при любом `platform_rules` с `effect = SLA` ресурсный вердикт каждого окна
`NO_VERDICT` с причиной покрытия `RESOURCE_SNAPSHOT_REQUIRED`; при правилах без SLA
причина информационная, вердикт не меняется. Политика, объявляющая SLA ресурса и
не способная его проверить, не проходит и не молчит. Поведение без стадий не
трогается. Цена ошибки: потерянное SLA-правило дало бы PASS вместо `NO_VERDICT`.
Цена выбранного: политика только из платформенных SLA-правил со стадиями даёт
`NO_VERDICT`, а без стадий `NO_POLICY` (расхождение намеренное).

**R7. Метрики сравнения остаются на «весь прогон»; предупреждение
`WHOLE_RUN_METRICS_WITH_STAGES` только в сравнении с эталоном.** `metric_summary`
без окна пишется как раньше (R5 объясняет, почему читателей трогать нельзя). Но
дельты сравнения двух прогонов со стадиями считаются по метрике «весь прогон», что
противоречит вердикту «по steady». Минимум: предупреждение в существующем массиве
`warnings` ответа сравнения с эталоном (`BaselineComparison.kt`), если у любой
стороны есть `stage_binding`, с расширением закрытого объединения
`BaselineComparisonWarning` и подписей UI. Ответы динамики прогонов
(`RunComparison.buildRunDynamics`) и сравнения транзакций (`compareTransactions`)
поля `warnings` не имеют; предупреждение туда не добавляется и новый контракт
ответа не создаётся. Это обязательство W2.3/W2.4: читать steady-метрики через
`window_metric_summary` при `stage_binding`. Ранжирование кандидатов статистического
эталона остаётся по `metricValue` «весь прогон». Режим `window_comparison`
(ADR 0028) уже работает через `window_metric_summary`. Арифметика сравнения не
меняется. Цена ошибки: динамика и сравнение транзакций двух прогонов с одним
объявлением показывают метрику «весь прогон» без предупреждения; карточка
вердикта и отчёт каждого анализа границы называют вслух.

**R12. Форма загрузки файла стадий в UI не входит.** Первые потребители CLI, API и
MCP (W3.2). UI показывает фразу и таблицу окон; форма загрузки отдельным срезом
после решения по MCP. Цена ошибки: пользователь UI не может задать стадии сам.

## Контракт `load-stages.v1`

Файл: `docs/contracts/stages/v1/load-stages.schema.json` (JSON Schema draft
2020-12) и примеры `examples/valid`, `examples/invalid` создаются в PR A, как
`docs/contracts/resources/v1`. Пока этого файла нет в `main`, ссылок на него в
документах нет.

| Поле | Тип | Правило |
| --- | --- | --- |
| `schema_version` | string | ровно `load-stages.v1` |
| `stages` | array | 1..16 элементов, после разбора отсортированы по `from_offset_ms`, не перекрываются (касание допустимо), зазоры допустимы |
| `stages[].id` | string | непустая, не более 128 байт UTF-8, без управляющих символов, уникальна |
| `stages[].role` | string | `steady` или `excluded`; других значений нет (в частности нет `auto`) |
| `stages[].from_offset_ms` | integer | не меньше 0, не больше 604800000 (7 суток), целое без дробной части |
| `stages[].to_offset_ms` | integer | больше `from_offset_ms`, не больше 604800000 |

Лишние поля отвергаются (`UNKNOWN_FIELD`). Не менее одной стадии `steady`. Файл не
больше 65536 байт, глубина JSON не больше 8; разбор тем же строгим сканером, что у
policy и снимка (дубли ключей, NaN, большие числа запрещены).

Лимиты (попадают в `limits` identity только при стадиях): `stages_plan_bytes_max`
65536, `stages_json_depth_max` 8, `stages_max` 16, `stages_offset_ms_max`
604800000.

Коды ошибок валидации (печатаются как `<code> <json-pointer>: <message>`):
`STAGES_NO_STEADY`, `OVERLAPPING_STAGES`, `DUPLICATE_STAGE_ID`, `INVALID_STAGE`,
`INVALID_STAGE_OFFSET`, `INVALID_TYPE`, `UNKNOWN_ROLE`, `UNKNOWN_FIELD`,
`RESOURCE_LIMIT_EXCEEDED`, `INVALID_SCHEMA_VERSION`. Допустимые примеры:
`ramp-steady-down` (разгон, steady, остановка), `steady-only`, `two-steady`
(две стадии `steady` с исключённой между ними; вердикт это объединение окон).
Недопустимые примеры по одному на каждый код выше (таблица в плане).

Пример объявления:

```json
{
  "schema_version": "load-stages.v1",
  "stages": [
    { "id": "ramp-up", "role": "excluded", "from_offset_ms": 0, "to_offset_ms": 40000 },
    { "id": "steady", "role": "steady", "from_offset_ms": 40000, "to_offset_ms": 100000 },
    { "id": "ramp-down", "role": "excluded", "from_offset_ms": 100000, "to_offset_ms": 120000 }
  ]
}
```

## Как стадии превращаются в окна

1. Для каждой стадии `from = runStart + from_offset_ms`, `to = runStart +
   to_offset_ms` (`Math.addExact`). Начало прогона это минимальный `started_at`,
   конец это максимум `started_at + elapsed`.
2. У стадии `steady` `to > runEnd` даёт `IllegalArgumentException("STAGE_OUTSIDE_RUN")`
   (R1). Стадии `excluded` не проверяются.
3. Окнами становятся стадии `steady`: `ResourceWindowV1(id = stage.id, from, to)`
   в порядке `from`. Окно полуоткрытое `[from, to)`, выборка относится к окну по
   моменту старта (существующий `WindowMetricsAccumulator`, правок накопителя
   нет). Удерживаемые транзакции собираются при `resources != null || stages != null`.
4. Правило policy с `window_ids: ["steady"]` применяется к окну `steady`; правило
   без `window_ids` ко всем окнам `steady`; правило с `window_ids`, которых нет
   среди окон `steady` (в том числе id `excluded`-стадии), даёт `rule_window_check`
   `RULE_WINDOW_NOT_FOUND` и `NO_VERDICT` (существующее поведение).
5. Пустое окно при применимом правиле даёт `BUSINESS_OBSERVATIONS_NOT_FOUND` и
   `NO_VERDICT`; окно меньше порога выборки даёт `INSUFFICIENT_SAMPLES` (существующее).

## Результат и свидетельства

Схема `analysis-result.v1` не меняется, верхнеуровневых полей нет (R8). Для прогона
со стадиями порядок `evidence`: сначала то, что `evaluateSharedWindowPolicy` ставит
впереди (`metric_summary` без `window_id`, `diagnostic`), затем `stage_binding`
(ровно там, где в режиме снимка стоит `resource_binding`), затем по окну
`policy_check` со `window_id`, `window_policy_summary` (`resource_verdict`
`NO_POLICY` или `NO_VERDICT` по R4), при необходимости `rule_window_check`, в конце
по окну `window_metric_summary`. Не появляются `resource_binding`,
`resource_summary`, `resource_policy_check`, `resource_threshold_violation`.

Поля `stage_binding` (snake_case):

| Поле | Значение |
| --- | --- |
| `id` / `type` | `stage-binding` / `stage_binding` |
| `mode` | `declared_stages` |
| `declaration_sha256` | SHA-256 канонических байт объявления (то же значение, что `load_stages_sha256` identity) |
| `run_from_epoch_ms`, `run_to_epoch_ms` | начало и конец прогона |
| `evaluated_window_ids` | id окон `steady` по порядку |
| `evaluated_millis` | сумма длин окон `steady` |
| `excluded_millis` | (`run_to - run_from`) минус `evaluated_millis` (разгон, остановка, зазоры) |
| `stages[]` | `{id, role, from_offset_ms, to_offset_ms, from_epoch_ms, to_epoch_ms}` |
| `verdict_scope` | `STEADY_WINDOW` |

Остаётся прежним: вердикт и evidence прогонов без стадий; `analysis_mode`
`standard`; формат `policy_check` и `window_policy_summary`; коды выхода CLI
(`PASS`/`NO_POLICY` 0, `FAIL` 2, `NO_VERDICT` 3, `INVALID` 4); `analysis_coverage`.

## Identity и ключ сопоставимости

Только для прогонов со стадиями (`stages != null`):

- Необязательные поля `AnalysisIdentityDocument`: `load_stages_sha256` (SHA-256
  канонических байт объявления) и `load_stages_version` = `load-stages.v1`. Паттерн
  `pod_view_*`, `trend_plan_*`; без стадий поля отсутствуют, байты identity прежние
  (`explicitNulls = false`).
- `modules` += `stage-window-evaluation` v1 и `window-policy-evaluation` v1;
  `input_versions.stages` = `load-stages.v1` (новое необязательное поле); `limits` +=
  четыре лимита выше. Эти поля входят в ключ сопоставимости, поэтому режим стадий
  отличается от режима без стадий уже без правки ключа.
- Ключ сопоставимости: условное звено `identity["load_stages_sha256"]` (R6) в
  `semanticKey` (`BaselineComparison.kt`) и `comparisonSemanticKey`
  (`RunComparison.kt`). Те же функции используют кандидаты baseline
  (`BASELINE_MIXED_SEMANTICS`) и динамика прогонов.
- `analysis_id` меняется только у анализов со стадиями. Повторная отправка тех же
  файлов без стадий возвращает старый сохранённый анализ.

Почему условная привязка, а не безусловное поле как `incident_method` (ADR 0029):
безусловное поле перегенерировало бы все золотые identity и сменило `analysis_id`
всех существующих прогонов ради функции, которой они не пользуются. Условное поле
сохраняет побайтовую неизменность прогонов без стадий (решение владельца 2).

## Взаимодействие с другими режимами

Проверки выполняются до чтения входа; CLI и API проверяют те же условия раньше и
печатают тот же код. Онлайн-запрос источника разрешается и снимок строится до
`AnalysisService` (`analyzeWithSources`), поэтому условие 4 проверяется там, до
всякого обращения к источнику.

| № | Условие | Код |
| --- | --- | --- |
| 1 | существующие `CAPACITY_PLAN_REQUIRED`, `CAPACITY_MODE_CONFLICT` | без изменений |
| 2 | стадии и (`capacity != null` или `mode == CAPACITY_STEP`) | `STAGES_CAPACITY_CONFLICT` |
| 3 | стадии и `resources != null` | `STAGES_RESOURCES_CONFLICT` |
| 4 | стадии и `sourceRequest != null` (CLI `--source`, API часть `source_request`) | `STAGES_SOURCE_CONFLICT` |
| 5 | существующие `DIAGNOSTIC_RESOURCE_REQUIRED`, `TREND_RESOURCE_REQUIRED`, `POD_VIEW_RESOURCE_REQUIRED` | без изменений (эти входы требуют снимок, со стадиями он невозможен) |

С `postgres` (пред- и постснимки) поведение прежнее. Офлайн-контекст OpenSearch
(`--source-context`) без снимка разрешён: он добавляет только evidence и окон не
задаёт; если контекст несёт снимок, срабатывает условие 3.

## Видимость

Фраза (константа ядра отображения, R10): `Вердикт посчитан по окну steady, разгон
исключён`. Выводится только когда вердикт вынесен (`run_validity = VALID`,
`policy_verdict` равен `PASS` или `FAIL`). При `NO_VERDICT` (в том числе
`DEGRADED`) и `NO_POLICY` текст нейтральный и вердикта не утверждает: `Окно steady
задано (<ids>), разгон исключён из метрик окна; вердикт: <NO_VERDICT|NO_POLICY>`.
Подстановки берутся из `stage_binding`: id окон, `evaluated_millis` и
`excluded_millis`, границы UTC. Для результата без стадий фраз нет.

| Место | Что показывается |
| --- | --- |
| Карточка вердикта (UI) | короткий маркер в `headline` при PASS и FAIL, полная фраза в `lead`, в `facts` «Окно вердикта» и «Исключено» |
| HTML-отчёт | строка `dt/dd` «Область вердикта» в списке с вердиктом, блок с фразой и таблицей стадий, подпись «метрики по всему прогону справочные» |
| AsciiDoc и Confluence | строка-примечание с той же фразой |
| `summary.txt` | строка `scope: steady window (<ids>), excluded <N> ms`, строка `window[<id>]: ...` на каждое окно; прежняя строка помечается `whole_run (reference only)` |
| `ltv summary` JSON (`cli-summary.v1`) | необязательный массив `windows[]` и число `excluded_ms`; `overall` остаётся «весь прогон» |
| `junit.xml` gate | у FAIL, NO_VERDICT, INVALID суффикс сообщения `scope=steady_window window_ids=<ids> excluded_ms=<N>`; у PASS и NO_POLICY (сообщения нет) дочерний `<system-out>` с той же строкой |
| Сравнение с эталоном (API) | предупреждение `WHOLE_RUN_METRICS_WITH_STAGES` (R7) |

Изменения `summary.txt`, `cli-summary.v1` и `junit.xml` только для прогонов со
стадиями и только добавочные; без стадий байты прежние.

## Отклонённые альтернативы

- Автоопределение плато: новый статистический метод и источник недетерминизма;
  D1 заморожен, границы не угадываются (ADR 0012).
- Новый отдельный контракт оценки вместо расширения существующего: дублировал бы
  оконную оценку; переиспользование даёт побайтово то же поведение в окне.
- Границы в epoch вместо смещений (R1): хэш объявления разный у каждого прогона,
  сопоставимость прогонов невозможна.
- Безусловное поле identity (как `incident_method`): меняет `analysis_id` всех
  существующих прогонов ради необязательной функции.
- Разгон как окно с ролью (R2): правила без `window_ids` проверяли бы и разгон.
- Приоритет «стадии побеждают снимок» или наоборот (R3): молчаливый выбор окон
  противоречит принципу «вердикт говорит вслух».
- Показатели окна в `metric_summary` (R5): ломают читателей метрики «весь прогон».
- Расширение слота baseline (R6): меняет схему хранилища, не нужно при ключе.
- Форма загрузки стадий в UI в этом же срезе (R12): первые потребители CLI, API,
  MCP.

## Следствия

- Прогоны без стадий неизменны; золотые файлы (`fixtures/typed-boundary/golden`,
  `fixtures/slice1`) не перегенерируются; это доказывается существующими золотыми
  тестами без правок и новым тестом совместимости.
- Реализация разбита на PR 0 (этот ADR), PR A (ядро, схема `load-stages.v1`,
  примеры, фикстура, identity и ключ), PR B (CLI и API), PR C (видимость: отчёты,
  UI, junit), PR D (руководство, статус Accepted по слову владельца). Файлы
  контракта, перечисленные выше, создаются в PR A; в документах до этого на них нет
  ссылок.
- Реализация PR A идёт после слияния среза 2 W2.1 (типизация evidence): `stage_binding`
  строится как типизированный вариант по его паттерну. PR B идёт после W2.2 или с
  rebase на неё; пересечения с W2.3 (сравнение с baseline), W2.4 (честные заголовки,
  доля разгона из `stage_binding`), W2.6 (отчёт для людей) и W3.7 (инциденты берут
  `window_id` и `window_policy_summary`) описаны в плане.
- Обязательство W2.3/W2.4: читать steady-метрики через `window_metric_summary` при
  наличии `stage_binding` (R7).
- Границы: нет автоопределения плато; нет загрузки стадий в форме UI; доля
  разгона и пометка throughput-правил это W2.4; инциденты это W3.7.
- Новых зависимостей production нет.

## Тест-критерии

Полный перечень AC1-AC12 в [плане](../superpowers/plans/2026-10-09-w2-5-steady-state-window.md),
фикстура `ramp-steady-rampdown.jtl` с ручным расчётом по плато (p95 194 мс,
throughput 10 rps против 821 мс и 6,01 rps «по всему прогону»). Ключевые:

1. p95 и throughput окна `steady` совпадают с ручным расчётом по плато (AC1, AC2);
   граница полуоткрытая по моменту старта (AC3).
2. Прогон без стадий побайтово прежний: золотые файлы, `junit.xml`, `summary.txt`,
   `cli-summary.v1`, HTML (AC4).
3. Одинаковое объявление даёт один `analysis_id` и `compatible = true`; другое
   объявление, либо наличие и отсутствие стадий, даёт `compatible = false` в
   сравнении baseline, динамике и `BASELINE_MIXED_SEMANTICS` (AC5).
4. В результате со стадиями нет `resource_binding`; есть `stage_binding` и
   `window_policy_summary` окна (AC6); правила и `window_ids` (AC7); платформенные
   SLA-правила дают `NO_VERDICT` (AC8, R4).
5. Сочетания дают `STAGES_*_CONFLICT` до обращения к источнику, `steady` за концом
   прогона даёт `STAGE_OUTSIDE_RUN`, `excluded` за концом проходит (AC9).
6. Валидатор отвергает каждый недопустимый пример ожидаемым кодом, граничные
   случаи 16 и 17 стадий, id 128 и 129 байт (AC10).
7. Фраза присутствует во всех местах видимости и отсутствует без стадий; при
   `NO_VERDICT`, `DEGRADED`, `NO_POLICY` вердикт не утверждается (AC11, AC11a).
8. `INVALID` вход не получает `stage_binding`; `load-stages.json` в каталоге
   анализа, SHA-256 равен `load_stages_sha256` (AC12).
