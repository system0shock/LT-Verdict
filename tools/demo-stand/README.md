# Стенд для живого демо LT Verdict

Локальный стенд на Docker Compose: Prometheus, Grafana с готовым источником
данных и дашбордом, генератор синтетических прогонов с тремя сценариями и
необязательным четвёртым (тест на 4 часа, см. «Сценарий 4»).
Продукт (`ltv ui`) запускается на хосте и берёт ряды ресурсов из Grafana через
профиль `grafana_proxy`.

Это демо-инфраструктура, а не зависимость продукта: в `build.gradle.kts` и
`ui/package.json` ничего не добавляется, в production она не попадает. Данные
синтетические: ядро LT Verdict настоящее, нагрузку и ресурсы строит симулятор
очередей `tools/synthetic_service.py` (детерминированный, одинаковые числа на любой
машине). План показа: [план живого демо](../../docs/superpowers/plans/2026-10-04-live-demo.md),
пошаговый [скрипт показа](../../docs/user/demo-script.md) (12-14 минут).

## Требования

- Docker Desktop (проверено на Docker 29.2.1, Compose v5.0.2).
- JDK 21 и собранный продукт: `.\gradlew.bat installDist` из корня репозитория
  (Node.js 24.14.0 нужен сборке интерфейса).
- Свободные порты `127.0.0.1:19090` (Prometheus) и `127.0.0.1:13000` (Grafana).
  Все порты публикуются только на `127.0.0.1`.

## Запуск

```powershell
cd tools\demo-stand
docker compose up -d --wait
```

Первый запуск скачивает образы: `prom/prometheus:v3.5.5`, `grafana/grafana:12.4.12`,
`python:3.14.3-slim` (теги закреплены). Порядок: генератор пишет `out/`,
`backfill` загружает ряды в TSDB Prometheus, затем стартуют Prometheus и Grafana.
Повторный `up` данные не дублирует (маркер в томе). Чтобы пересоздать данные с нуля:

```powershell
docker compose down -v
docker compose up -d --wait
```

Остановка с удалением томов: `docker compose down -v`. Каталог `out/` в git не
входит.

Тест на 4 часа в этот запуск не входит: он включается отдельной командой, см.
«Сценарий 4» ниже.

Проект compose называется `ltv-demo-stand` (задано в `docker-compose.yml`), а
каталоги `grafana/` и `prometheus/` подключаются как bind-mount. Если выполнить `up` из
другого каталога (например, из другого git worktree), контейнеры пересоздаются с
путями этого каталога; перед удалением такого каталога поднимите стенд заново из
оставшегося.

### Рендер PNG (необязательно)

Кнопка «Render PNG» в интерфейсе требует сервис рендера (образ около 2 ГБ):

```powershell
docker compose --profile render up -d --wait
```

Без него `grafana-render` возвращает `SOURCE_HTTP_5XX` (после повторов, около
20 секунд), а ссылка на панель остаётся доступной.

## Что находится на стенде

| Что | Адрес или путь |
| --- | --- |
| Prometheus | `http://127.0.0.1:19090` |
| Grafana (анонимный просмотр, роль Viewer) | `http://127.0.0.1:13000`, дашборд UID `ltv-demo`, панели 1-6 |
| Источник данных Grafana | UID `ltv-demo-prometheus` (провиженинг, `access: proxy`) |
| Профиль продукта | `connections.demo.json` (`demo-grafana`, восемь рядов, четыре диагностических правила) |
| Запрос окна | `source-request.demo.json` (авто-окно, шаг 10 с, запас 60 с) |
| Политики | `policies/sla-fail.json`, `policies/capacity.json`, `policies/saturation.json`, для теста на 4 часа `policies/soak-4h.json` |
| Сгенерированные входы | `out/<сценарий>/load.jtl`, для ёмкости ещё `resources.json` и `capacity-plan.json` |

Панели дашборда: 1 нагрузка (цель и достигнутая), 2 p95 отклика, 3 занятость
ЦП сервиса и БД, 4 очереди, 5 внешняя зависимость, 6 здоровье генератора. Ссылки
на сценарии лежат в шапке дашборда (ссылка 4-го сценария нужна только в режиме 4 часов,
без него ведёт в пустое окно).

Учётная запись администратора Grafana не создаётся (`GF_SECURITY_DISABLE_INITIAL_ADMIN_CREATION`),
доступен только анонимный просмотр; порт открыт только на `127.0.0.1`. Анонимный Viewer
это **локальная подмена** для демо-стенда: на боевом стенде анонимный доступ к Grafana
недопустим (решение владельца 2026-10-05), доступ идёт по mTLS; что есть в коннекторе
сейчас и что понадобится, описано в [отчёте проверки](../../docs/superpowers/plans/2026-10-05-demo-walkthrough-report.md).

## Сценарии

Данные привязаны к календарю (1 октября 2026, UTC), вокруг каждого теста по две
минуты простоя. Хранение в Prometheus 3650 дней.

| Сценарий | Время (UTC) | Что происходит |
| --- | --- | --- |
| 1. SLA FAIL | 08:02-08:17 | 60 RPS, запас по ЦП; с 08:07 до 08:10 внешняя зависимость замедляется на 400 мс |
| 2. Тест максимума | 09:02-09:32 | ступени по 5 минут: 40, 60, 80, 90, 96, 104 RPS; ёмкость сервиса 100 RPS |
| 3. Насыщение БД | 10:02-10:20 (данные до 10:22) | 40 RPS (5 мин), 84 RPS (8 мин), 40 RPS (5 мин); БД упирается в 100 % занятости |
| 4. Тест на 4 часа (по желанию) | 12:02-16:02 (данные до 16:04) | 60 RPS 4 часа; трудоёмкость запроса на ЦП медленно растёт в 1,66 раза, ЦП доходит до 100 % |

В JTL четыре метки: `GET /api/catalog`, `POST /api/cart`, `POST /api/checkout` и
редкая `POST /api/refund` (около 36 запросов, в тесте на 4 часа 576); 0,2 % запросов помечены ошибкой.

### Сценарии 1 и 3: онлайн-источник через Grafana

Запуск продукта (адрес печатается в консоли):

```powershell
cd tools\demo-stand
..\..\build\install\ltv\bin\ltv.bat ui --data-dir $env:TEMP\ltv-demo-data --connections connections.demo.json
```

Порт при запуске случайный: адрес `http://127.0.0.1:<порт>` печатается в консоли.
В браузере откройте его без параметров (новая оболочка по умолчанию; если раньше был
выбран прежний интерфейс, откройте `/?shell=new`). На вкладке «Новый анализ» выберите
`out\sla-fail\load.jtl`, политику `policies\sla-fail.json` (или шаблон на вкладке
«Правила»), источник `demo-grafana`; после выбора источника появятся поля окна: окно
«Авто», шаг 10 с, запас 60 с (поля пусты по умолчанию, их нужно ввести), затем
запустите анализ. Тот же анализ из командной строки:

```powershell
..\..\build\install\ltv\bin\ltv.bat analyze out\sla-fail\load.jtl --policy policies\sla-fail.json `
  --connections connections.demo.json --source source-request.demo.json --data-dir $env:TEMP\ltv-demo-data
```

Ожидаемый результат (проверено, код выхода 2 у обоих):

- Сценарий 1: `FAIL`, источник `COMPLETE` (8 запросов к Grafana). Нарушены
  `overall-p95` (451 мс при пороге 250) и `checkout-p95` (451 мс при 300). Ошибки
  0,2 % и пропускная способность в норме. Диагностическое правило `downstream-slow`
  нарушено 08:07:00-08:10:00 (ожидание внешней зависимости около 26 запросов против 2).
  Правило `refund-p99` проходит на 35 запросах с пометкой малой выборки
  (`sample_mode: SMALL_SAMPLE`, в интерфейсе «малая выборка»; «Полнота данных» при
  этом показывает INCOMPLETE, хотя источник COMPLETE).
- Шаблон «Базовый API (SLA)» (p95 не более 1000 мс, ошибки не более 5 %) на сценарии 1
  даёт PASS (p95 451 мс); FAIL получается после снижения порога p95 до 250 мс в
  редакторе правил или с файлом `policies\sla-fail.json`. На сценарии 3 шаблон без
  правок даёт FAIL (p95 3 493 мс при 1 000 мс).
- Сценарий 3 (`out\saturation\load.jtl`, `policies\saturation.json`): `FAIL`,
  `overall-p95` 3 493 мс при пороге 800, источник `COMPLETE`. Диагностика
  `db-saturated`: 48 ячеек подряд, 10:07:00-10:15:00, занятость БД 0,998-1,0, ЦП
  сервиса не выше 0,21. Ошибки 128 из 64 320 (0,2 %), порог не нарушен.

Ссылка на панель: на странице «Обзор» раскройте «Grafana evidence», задайте UID
`ltv-demo` и номер панели (например, 5 для сценария 1 или 3 для сценария 3),
«Prepare link» открывает панель за окно прогона, «Render PNG» рисует её (нужен
профиль `render`).

### Сценарий 2: тест максимума, файлами

Онлайн-источник нельзя сочетать с планом ёмкости, а план привязан к хэшам нагрузки
и снимка, поэтому ёмкость запускается файлами, которые подготовил генератор:

```powershell
..\..\build\install\ltv\bin\ltv.bat analyze out\capacity\load.jtl --policy policies\capacity.json `
  --resources out\capacity\resources.json --capacity out\capacity\capacity-plan.json --data-dir $env:TEMP\ltv-demo-data
```

В интерфейсе: те же файлы в полях «Файл нагрузочного теста», «Файл политики»,
«Снимок ресурсов» и «План ёмкости», онлайн-источник не выбирается.

Ожидаемый результат (код выхода 0): граница `BOUNDED [95.745, 103.745)` req/s,
вердикт `PASS` при `required_capacity` 90. Ступени: p95 52, 52, 52, 53, 56 мс, затем
11 543 мс на 104 RPS (`FAIL`). Колено ядро само не определяет:
`capacity_knee` равен `null` с `KNEE_DETECTOR_NOT_IMPLEMENTED`. Если в
`capacity-plan.json` поставить `required_capacity` 100, вердикт станет
`NO_VERDICT` (код 3), при 104 - `FAIL` (код 2).

### Сценарий 4: тест на 4 часа (по желанию)

Требование владельца 2026-10-05: показывать анализ теста не короче 4 часов. Сценарий
`soak-4h` в запуск по умолчанию не входит (он добавляет около минуты генерации и 33 МБ
JTL), его включает файл `docker-compose.soak.yml`:

```powershell
cd tools\demo-stand
docker compose down -v
docker compose -f docker-compose.yml -f docker-compose.soak.yml up -d --wait
```

Это тот же стенд и те же порты, но генератор получает `--scenario all-with-soak`:
три прежних сценария остаются бит в бит (хэши JTL те же), к ним добавляется
`out\soak-4h\load.jtl`, а ряды Prometheus за 4 часа загружаются тем же `backfill`.
Рендер подключается как обычно (`--profile render` перед `up`). Вернуться к трём
сценариям: `docker compose down -v`, удалить `out\soak-4h` (каталог `out/` лежит на
хосте, `down -v` его не трогает и генератор его не чистит) и обычный
`docker compose up -d --wait`.

- Переключение в любую сторону требует `docker compose down -v`: `metrics.om`
  меняется, и защита `backfill` не даст загрузить другие данные в старый том
  («metrics.om changed since the last backfill»).
- В режиме 4 часов каждый `up` заново запускает генератор: около 72 с на 864 000
  запросов (замер в контейнере `python:3.14.3-slim`), пиковая память контейнера
  генератора около 0,5 ГБ (выборка `docker stats`), `out/` около 45 МБ, `backfill`
  около 1 с. Холодный `up` вместе с запуском сервисов занял около 90 с; готовьте стенд заранее.
- Данные детерминированы (seed 7, календарь 1 октября 2026, 12:02-16:02 UTC), хэш
  `load.jtl` начинается с `98d730ce`.

Что в тесте: 60 RPS 4 часа, 864 000 запросов, 0,2 % ошибок (1 728). Нагрузка ровная, но
трудоёмкость запроса на ЦП растёт ступенями от 1,00 до 1,66 от исходной (24 ступени по 10
минут), поэтому занятость ЦП сервиса идёт от 0,59 к 1,0. Первые три часа p95 почти не
меняется (52-62 мс), около 3:20 от начала прогона он начинает расти (77 мс), на 3:40
достигает 144 мс, в последние 10-20 минут около 230 мс. Диагностическое правило
`service-cpu-saturated` (занятость выше 0,95 шесть ячеек подряд) срабатывает примерно с
3:30. Инцидентов и сбоев внешней зависимости в этом сценарии нет.

Запуск анализа тем же профилем `demo-grafana`: файл `out\soak-4h\load.jtl`, политика
`policies\soak-4h.json` (те же два правила, что у шаблона «Базовый API (SLA)»: p95 не
более 1000 мс, ошибки не более 5 %) или сам шаблон, источник `demo-grafana`, окно «Авто»,
шаг 10 с, запас 60 с, максимальный простой 60 с (в `source-request.demo.json` допуск
простоя 1 800 с, для теста без простоев разницы нет). В командной строке:

```powershell
..\..\build\install\ltv\bin\ltv.bat analyze out\soak-4h\load.jtl --policy policies\soak-4h.json `
  --connections connections.demo.json --source source-request.demo.json --data-dir $env:TEMP\ltv-demo-data
```

Ожидаемый результат (проверено на `main` `f257166` плюс этот срез, код выхода 0): `PASS` по
политике (p95 за весь тест 64 мс при пороге 1000, доля ошибок 0,2 % при пороге 5 %), 240
минут, 864 000 запросов, «Полнота данных» COMPLETE (8 запросов к Grafana). Диагностика
`service-cpu-saturated` нарушена, остальные три правила источника в норме. Вердикт по SLA
за весь тест `PASS`, а исчерпание запаса по ЦП в последние полчаса видно только на рядах:
в этом смысл сценария («среднее за четыре часа скрывает деградацию»).

Замеры (машина разработки, 32 процессора; одна репетиция, не гарантия для других машин):

| Что | Значение |
| --- | --- |
| `ltv analyze`, шаг 10 с, `JAVA_OPTS=-Xmx192m` | 8,8 с (1 453 ячейки на ряд, 8 рядов) |
| `ltv analyze`, шаг 60 с, `-Xmx192m` | 8,7 с (243 ячейки на ряд), результат тот же, источник COMPLETE |
| `ltv ui`, `-Xmx512m`: загрузка файла 33 МБ и анализ, от нажатия до «Обзора» | 8,4 с; пик рабочего набора процесса 496 МБ |
| Вкладки «Обзор», «Правила», «Таблицы» (транзакции), «Глубокий анализ» после анализа | открываются без заметной задержки (в пределах 2,5 с) |
| «Глубокий анализ», период 200-240 мин | 3:20:00-4:00:00; по умолчанию выбраны шесть рядов, `service-cpu-busy` среди них |

Шаг и лимиты. Автошаг (ADR 0014) на этом сценарии не нужен: 8 рядов по 1 453 ячейки
(шаг 10 с) дают около 11,6 тысячи ячеек при рабочем лимите 1,5 миллиона, режим `auto`
шаг не огрубил бы. Профиль `connections.demo.json` остаётся `source-connections.v1` без
`scrape_interval_ms`: запрос `v4` с автошагом к нему получит
`AUTO_STEP_SCRAPE_INTERVAL_REQUIRED`, а перевод профиля на `v3` затронул бы три прежних
сценария и не делался. Шаг 60 с годится (запас 60 с и допуск простоя кратны шагу), но
правило `min_consecutive_cells: 6` на шаге 60 с означает уже 6 минут, а не 1 минуту: на
4 часах исход `service-cpu-saturated` тот же, на коротких тестах смысл правила менялся бы.
Вкладка «Глубокий анализ» подбирает шаг сама (не более 1500 ячеек): на 4 часах это 10 с.

## Слой совместимости с платформенными профилями (необязательно)

Профили OpenShift, которые выпускает `tools/platform_profiles.py` (срез P0 плана
платформы), читают семейства метрик в форме контракта меток
([пакеты метрик](../../docs/user/platform-metric-packs.md)). Стенд по умолчанию их
не отдаёт: Prometheus здесь хранит только синтетические ряды `demo_*`, cAdvisor в нём нет,
поэтому шаблоны вернули бы пустоту. Каталог `platform/` содержит фрагменты для
варианта стенда с реальными контейнерами и cAdvisor. В `docker-compose.yml` и
`prometheus/prometheus.yml` ничего не подключено: стенд по умолчанию и его данные не меняются.

| Файл | Что делает |
| --- | --- |
| `platform/prometheus.platform.yml` | полная конфигурация Prometheus (заменяет `prometheus/prometheus.yml`): задание `cadvisor` (цель `cadvisor:8080`), опрос и вычисление правил раз в 5 с, `metric_relabel_configs` |
| `platform/platform-compat.rules.yml` | recording rules контракта меток |
| `platform/profile-config.stand.json` | конфигурация генератора для стенда: `grafana_proxy`, `ltv-demo-prometheus`, `scrape_interval_ms` 5000, `request_step_ms` 10000 |

Relabel (из меток cAdvisor Docker): `namespace` = `shop`, `pod` = `name` (имя
контейнера), `container` = `app`, `workload` = `container_label_com_docker_compose_service`.
Остаются только контейнеры compose-проекта (непустые `name`, проект и сервис): корневые cgroup и чужие
контейнеры хоста отбрасываются; чтобы взять один проект, подставьте его имя вместо
среднего `.+` в регулярном выражении `keep`. Recording rules:

- `namespace_workload_pod:kube_pod_owner:relabel` (значение 1) и `kube_pod_container_info`
  из `container_last_seen` и `container_start_time_seconds`;
- `node_namespace_pod_container:container_cpu_usage_seconds_total:sum_irate`:
  `sum by (...) (irate(container_cpu_usage_seconds_total[1m]))` (окно не меньше двух
  интервалов опроса);
- `kube_pod_container_resource_limits{resource="memory"}` из
  `container_spec_memory_limit_bytes` и `{resource="cpu"}` из
  `container_spec_cpu_quota / container_spec_cpu_period`, только положительные: у
  контейнера без `mem_limit` или `cpus` в compose limit не появляется, и отношение к limit
  даёт пропуск (в политике `NO_VERDICT`), а не ноль. Задайте `mem_limit` и `cpus`
  сервисам приложения.

Отличия от плана и границы (честно):

- К правилам плана добавлены `sum_irate` и `kube_pod_container_info`: без них
  `cpu_limit_ratio` и оба отношения к limit пусты.
- `kube_pod_info` намеренно не записывается: это источник живости сигнала `restarts`, и
  производная от cAdvisor превратила бы рестарты в выдуманный ноль. Без неё `restarts` остаётся пропуском.
- Нет kube-state-metrics: `restarts` и `unavailable_replicas` на стенде не воспроизводятся, в
  `profile-config.stand.json` их нет (подмножество `cpu_limit_ratio`, `memory_limit_ratio`,
  `cpu_throttling`, `oom`). `oom` нужен `container_oom_events_total`; без счётчика при живом контейнере
  сигнал даёт 0.
- Защита полноты слабее боевой: «ожидаемые контейнеры» берутся из того же cAdvisor, поэтому
  исчезновение контейнера целиком из cAdvisor пропуском не станет.
- Демо-профиль `connections.demo.json` остаётся прежним: платформенный профиль выпускается отдельно
  (команда ниже) и применяется к стенду со слоем совместимости.

Профиль выпускается из корня репозитория (имя сервиса в `services` равно имени compose-сервиса приложения;
шаг запроса не меньше 10 с, чтобы `rate` видел две точки при опросе 5 с):

```powershell
python -m tools.platform_profiles --config tools\demo-stand\platform\profile-config.stand.json --out connections.platform.json
```

Проверка: `python -m unittest tools.test_platform_stand -v` из корня репозитория. Без
`promtool` исполняются только структурные проверки; с `promtool` (или образом:
`$env:LTV_PROMTOOL_DOCKER_IMAGE='prom/prometheus:v3.5.5'`) добавляются `promtool check
config/rules` и `promtool test rules`: сценарии P0b повторяются на рядах в форме
cAdvisor после relabel, плюс красные случаи (нулевой limit памяти, квота 0 и -1,
`restarts` без `kube_pod_info`).

Что проверено и что нет. Проверено: `promtool` на синтетике; сквозной прогон (relabel, правила и
шаблоны в настоящем Prometheus v3.5.5) на поддельном экспортёре в форме cAdvisor с корневой cgroup,
контейнерами двух compose-проектов, контейнерами с limit и без. Не проверено: настоящий cAdvisor.
Образ `gcr.io/cadvisor/cadvisor:v0.52.1` на Docker Desktop (хранилище образов containerd) не
распознал контейнеры compose (метка `name` пуста, ошибка «failed to identify the
read-write layer ID»), поэтому имена `container_spec_cpu_quota`/`period`, `container_oom_events_total`
и метки `container_label_*` реального cAdvisor на стенде не подтверждены.

## Известные ограничения

- Значения рядов с более чем 12 знаками после запятой ядро отвергает
  (`RESOURCE_LIMIT_EXCEEDED`), а арифметика с плавающей точкой в Prometheus такие
  значения даёт (`0.6063054999999999`). Поэтому выражения профиля обёрнуты в
  `round(..., 0.000001)`. Без округления четыре из восьми рядов сценария 1 не
  загружаются (проверено), сбор получает статус `PARTIAL`. Решение владельца
  2026-10-05: `round()` остаётся у автора профиля на МВП.
- Страница «Обзор» показывает первые 500 интервалов по 1 с: у сценариев 2 и 3
  дальняя часть теста там не видна, шаг и диапазон меняются на вкладке «Таблицы».
- Вкладка «Глубокий анализ» рисует нагрузку и до шести рядов ресурсов с общим
  курсором для всего окна; по умолчанию выбираются ряды непройденных правил, затем
  остальные по алфавиту (для сценария 3 отметьте `service-cpu-busy`). Линии на ней заливаются как
  многоугольники (дефект D1 в [отчёте проверки](../../docs/superpowers/plans/2026-10-05-demo-walkthrough-report.md)), поэтому для «колена»
  ёмкости надёжнее дашборд Grafana (общий указатель включён).
- Таблица ёмкости («Saved capacity facts»), блоки «Grafana evidence» и «Saved-run
  analytics» в интерфейсе пока английские: русские вкладки «Ёмкость» и «Тренды» (U3b)
  не влиты на момент проверки. Таблицы правил и транзакций, редактор политики и
  шаблоны русские.
- Диагностические правила источника (`downstream-slow`, `db-saturated`) не
  показываются в «Требует внимания»: причину видно на «Глубоком анализе» и в таблицах
  вкладки «Таблицы».
- Окно авто-режима использует запас 60 с; ряды вне прогона обрезаются при связывании.
- Три сценария по умолчанию короткие (15, 30 и 18 минут); тест на 4 часа включается
  отдельно (раздел «Сценарий 4»). Настоящий JTL JMeter в сотни МБ, тест на 8 часов и
  слабая машина показа на стенде не проверялись. «Обзор» на тесте в 4 часа показывает
  только первые 8 минут из 240 (дефект D3 отчёта проверки): смотреть «Глубокий анализ».

## Состав каталога

```text
docker-compose.yml           три сервиса стенда, разовые задания generator и backfill, профиль render
docker-compose.soak.yml      необязательное дополнение: включает тест на 4 часа (generator --scenario all-with-soak)
generator/generate.py        симуляция сценариев, OpenMetrics, JTL, снимок и план ёмкости
prometheus/prometheus.yml    конфигурация Prometheus
grafana/                     провиженинг источника данных и дашборд ltv-demo
connections.demo.json        профиль источника продукта (grafana_proxy)
source-request.demo.json     запрос авто-окна
policies/                    политики трёх сценариев и теста на 4 часа
platform/                    необязательный слой совместимости с платформенными профилями (relabel, recording rules)
```

Генератор проверяется тестом `tools/test_demo_stand.py`
(`python -m unittest tools.test_demo_stand -v` из корня репозитория), слой совместимости
тестом `tools/test_platform_stand.py`.
