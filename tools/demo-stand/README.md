# Стенд для живого демо LT Verdict

Локальный стенд на Docker Compose: Prometheus, Grafana с готовым источником
данных и дашбордом, генератор синтетических прогонов с тремя сценариями.
Продукт (`ltv ui`) запускается на хосте и берёт ряды ресурсов из Grafana через
профиль `grafana_proxy`.

Это демо-инфраструктура, а не зависимость продукта: в `build.gradle.kts` и
`ui/package.json` ничего не добавляется, в production она не попадает. Данные
синтетические: ядро LT Verdict настоящее, нагрузку и ресурсы строит симулятор
очередей `tools/synthetic_service.py` (детерминированный, одинаковые числа на любой
машине). План показа: [план живого демо](../../docs/superpowers/plans/2026-10-04-live-demo.md),
пошаговый [скрипт показа](../../docs/user/demo-script.md) (12-14 минут).

## Требования

- Docker Desktop (проверено на Docker 29.2.1, Compose v5.0.2).
- JDK 21 и собранный продукт: `.\gradlew.bat installDist` из корня репозитория
  (Node.js 24.14.0 нужен сборке интерфейса).
- Свободные порты `127.0.0.1:19090` (Prometheus) и `127.0.0.1:13000` (Grafana).
  Все порты публикуются только на `127.0.0.1`.

## Запуск

```powershell
cd tools\demo-stand
docker compose up -d --wait
```

Первый запуск скачивает образы: `prom/prometheus:v3.5.5`, `grafana/grafana:12.4.12`,
`python:3.14.3-slim` (теги закреплены). Порядок: генератор пишет `out/`,
`backfill` загружает ряды в TSDB Prometheus, затем стартуют Prometheus и Grafana.
Повторный `up` данные не дублирует (маркер в томе). Чтобы пересоздать данные с нуля:

```powershell
docker compose down -v
docker compose up -d --wait
```

Остановка с удалением томов: `docker compose down -v`. Каталог `out/` в git не
входит.

Проект compose называется `ltv-demo-stand` (задано в `docker-compose.yml`), а
каталоги `grafana/` и `prometheus/` подключаются как bind-mount. Если выполнить `up` из
другого каталога (например, из другого git worktree), контейнеры пересоздаются с
путями этого каталога; перед удалением такого каталога поднимите стенд заново из
оставшегося.

### Рендер PNG (необязательно)

Кнопка «Render PNG» в интерфейсе требует сервис рендера (образ около 2 ГБ):

```powershell
docker compose --profile render up -d --wait
```

Без него `grafana-render` возвращает `SOURCE_HTTP_5XX` (после повторов, около
20 секунд), а ссылка на панель остаётся доступной.

## Что находится на стенде

| Что | Адрес или путь |
| --- | --- |
| Prometheus | `http://127.0.0.1:19090` |
| Grafana (анонимный просмотр, роль Viewer) | `http://127.0.0.1:13000`, дашборд UID `ltv-demo`, панели 1-6 |
| Источник данных Grafana | UID `ltv-demo-prometheus` (провиженинг, `access: proxy`) |
| Профиль продукта | `connections.demo.json` (`demo-grafana`, восемь рядов, четыре диагностических правила) |
| Запрос окна | `source-request.demo.json` (авто-окно, шаг 10 с, запас 60 с) |
| Политики | `policies/sla-fail.json`, `policies/capacity.json`, `policies/saturation.json` |
| Сгенерированные входы | `out/<сценарий>/load.jtl`, для ёмкости ещё `resources.json` и `capacity-plan.json` |

Панели дашборда: 1 нагрузка (цель и достигнутая), 2 p95 отклика, 3 занятость
ЦП сервиса и БД, 4 очереди, 5 внешняя зависимость, 6 здоровье генератора. Ссылки
на три сценария лежат в шапке дашборда.

Учётная запись администратора Grafana не создаётся (`GF_SECURITY_DISABLE_INITIAL_ADMIN_CREATION`),
доступен только анонимный просмотр; порт открыт только на `127.0.0.1`.

## Сценарии

Данные привязаны к календарю (1 октября 2026, UTC), вокруг каждого теста по две
минуты простоя. Хранение в Prometheus 3650 дней.

| Сценарий | Время (UTC) | Что происходит |
| --- | --- | --- |
| 1. SLA FAIL | 08:02-08:17 | 60 RPS, запас по ЦП; с 08:07 до 08:10 внешняя зависимость замедляется на 400 мс |
| 2. Тест максимума | 09:02-09:32 | ступени по 5 минут: 40, 60, 80, 90, 96, 104 RPS; ёмкость сервиса 100 RPS |
| 3. Насыщение БД | 10:02-10:20 (данные до 10:22) | 40 RPS (5 мин), 84 RPS (8 мин), 40 RPS (5 мин); БД упирается в 100 % занятости |

В JTL четыре метки: `GET /api/catalog`, `POST /api/cart`, `POST /api/checkout` и
редкая `POST /api/refund` (около 36 запросов); 0,2 % запросов помечены ошибкой.

### Сценарии 1 и 3: онлайн-источник через Grafana

Запуск продукта (адрес печатается в консоли):

```powershell
cd tools\demo-stand
..\..\build\install\ltv\bin\ltv.bat ui --data-dir $env:TEMP\ltv-demo-data --connections connections.demo.json
```

Порт при запуске случайный: адрес `http://127.0.0.1:<порт>` печатается в консоли.
В браузере откройте его без параметров (новая оболочка по умолчанию; если раньше был
выбран прежний интерфейс, откройте `/?shell=new`). На вкладке «Новый анализ» выберите
`out\sla-fail\load.jtl`, политику `policies\sla-fail.json` (или шаблон на вкладке
«Правила»), источник `demo-grafana`; после выбора источника появятся поля окна: окно
«Авто», шаг 10 с, запас 60 с (поля пусты по умолчанию, их нужно ввести), затем
запустите анализ. Тот же анализ из командной строки:

```powershell
..\..\build\install\ltv\bin\ltv.bat analyze out\sla-fail\load.jtl --policy policies\sla-fail.json `
  --connections connections.demo.json --source source-request.demo.json --data-dir $env:TEMP\ltv-demo-data
```

Ожидаемый результат (проверено, код выхода 2 у обоих):

- Сценарий 1: `FAIL`, источник `COMPLETE` (8 запросов к Grafana). Нарушены
  `overall-p95` (451 мс при пороге 250) и `checkout-p95` (451 мс при 300). Ошибки
  0,2 % и пропускная способность в норме. Диагностическое правило `downstream-slow`
  нарушено 08:07:00-08:10:00 (ожидание внешней зависимости около 26 запросов против 2).
  Правило `refund-p99` проходит на 35 запросах с пометкой малой выборки
  (`sample_mode: SMALL_SAMPLE`, в интерфейсе «малая выборка»; «Полнота данных» при
  этом показывает INCOMPLETE, хотя источник COMPLETE).
- Шаблон «Базовый API (SLA)» (p95 не более 1000 мс, ошибки не более 5 %) на сценарии 1
  даёт PASS (p95 451 мс); FAIL получается после снижения порога p95 до 250 мс в
  редакторе правил или с файлом `policies\sla-fail.json`. На сценарии 3 шаблон без
  правок даёт FAIL (p95 3 493 мс при 1 000 мс).
- Сценарий 3 (`out\saturation\load.jtl`, `policies\saturation.json`): `FAIL`,
  `overall-p95` 3 493 мс при пороге 800, источник `COMPLETE`. Диагностика
  `db-saturated`: 48 ячеек подряд, 10:07:00-10:15:00, занятость БД 0,998-1,0, ЦП
  сервиса не выше 0,21. Ошибки 128 из 64 320 (0,2 %), порог не нарушен.

Ссылка на панель: на странице «Обзор» раскройте «Grafana evidence», задайте UID
`ltv-demo` и номер панели (например, 5 для сценария 1 или 3 для сценария 3),
«Prepare link» открывает панель за окно прогона, «Render PNG» рисует её (нужен
профиль `render`).

### Сценарий 2: тест максимума, файлами

Онлайн-источник нельзя сочетать с планом ёмкости, а план привязан к хэшам нагрузки
и снимка, поэтому ёмкость запускается файлами, которые подготовил генератор:

```powershell
..\..\build\install\ltv\bin\ltv.bat analyze out\capacity\load.jtl --policy policies\capacity.json `
  --resources out\capacity\resources.json --capacity out\capacity\capacity-plan.json --data-dir $env:TEMP\ltv-demo-data
```

В интерфейсе: те же файлы в полях «Файл нагрузочного теста», «Файл политики»,
«Снимок ресурсов» и «План ёмкости», онлайн-источник не выбирается.

Ожидаемый результат (код выхода 0): граница `BOUNDED [95.745, 103.745)` req/s,
вердикт `PASS` при `required_capacity` 90. Ступени: p95 52, 52, 52, 53, 56 мс, затем
11 543 мс на 104 RPS (`FAIL`). Колено ядро само не определяет:
`capacity_knee` равен `null` с `KNEE_DETECTOR_NOT_IMPLEMENTED`. Если в
`capacity-plan.json` поставить `required_capacity` 100, вердикт станет
`NO_VERDICT` (код 3), при 104 - `FAIL` (код 2).

## Известные ограничения

- Значения рядов с более чем 12 знаками после запятой ядро отвергает
  (`RESOURCE_LIMIT_EXCEEDED`), а арифметика с плавающей точкой в Prometheus такие
  значения даёт (`0.6063054999999999`). Поэтому выражения профиля обёрнуты в
  `round(..., 0.000001)`. Без округления четыре из восьми рядов сценария 1 не
  загружаются (проверено), сбор получает статус `PARTIAL`.
- Страница «Обзор» показывает первые 500 интервалов по 1 с: у сценариев 2 и 3
  дальняя часть теста там не видна, шаг и диапазон меняются на вкладке «Таблицы».
- Вкладка «Глубокий анализ» рисует нагрузку и до шести рядов ресурсов с общим
  курсором для всего окна; по умолчанию выбираются ряды непройденных правил, затем
  остальные по алфавиту (для сценария 3 отметьте `service-cpu-busy`). Линии на ней заливаются как
  многоугольники (дефект D1 в [отчёте проверки](../../docs/superpowers/plans/2026-10-05-demo-walkthrough-report.md)), поэтому для «колена»
  ёмкости надёжнее дашборд Grafana (общий указатель включён).
- Таблица ёмкости («Saved capacity facts»), блоки «Grafana evidence» и «Saved-run
  analytics» в интерфейсе пока английские: русские вкладки «Ёмкость» и «Тренды» (U3b)
  не влиты на момент проверки. Таблицы правил и транзакций, редактор политики и
  шаблоны русские.
- Диагностические правила источника (`downstream-slow`, `db-saturated`) не
  показываются в «Требует внимания»: причину видно на «Глубоком анализе» и в таблицах
  вкладки «Таблицы».
- Окно авто-режима использует запас 60 с; ряды вне прогона обрезаются при связывании.

## Состав каталога

```text
docker-compose.yml           три сервиса стенда, разовые задания generator и backfill, профиль render
generator/generate.py        симуляция сценариев, OpenMetrics, JTL, снимок и план ёмкости
prometheus/prometheus.yml    конфигурация Prometheus
grafana/                     провиженинг источника данных и дашборд ltv-demo
connections.demo.json        профиль источника продукта (grafana_proxy)
source-request.demo.json     запрос авто-окна
policies/                    политики трёх сценариев
```

Генератор проверяется тестом `tools/test_demo_stand.py`
(`python -m unittest tools.test_demo_stand -v` из корня репозитория).
