LT Verdict

Платформа анализа результатов нагрузочного тестирования · выжимка по проектной концепции (PRC v0.4) · июль 2026

Проблема

Разбор результатов нагрузочных тестов сегодня — ручная работа: перцентили усредняются математически некорректно, сравнение с прошлыми прогонами — «на глаз», протокол НТ собирается вручную в Confluence. Вердикт зависит от исполнителя и невоспроизводим: по одним и тем же данным два инженера могут вынести разные заключения.

Решение

Дистрибутив, который команда разворачивает в своём контуре. Платформа собирает факты прогона из трёх источников — результаты Gatling/JMeter, аппаратные метрики из существующей VictoriaMetrics, APM из ELK — и выносит детерминированный вердикт по версионируемому контракту правил с автоматической публикацией формального протокола в Confluence. Заложен контракт регистрации прогона — задел под запуск из Jenkins и CI-гейты без переделки архитектуры.

Ключевые свойства

  • Воспроизводимость: вердикт побайтово повторяется из тех же входов и версии правил; неполные данные → NO_VERDICT, а не «зелёный по умолчанию».
  • Безопасность: все доступы к источникам — read-only (испортить мониторинг/ELK платформа не может физически); данные прогонов не покидают контур команды (152-ФЗ, PCI DSS).
  • Управляемость: правила вердикта — код в Git; правки из GUI проходят merge request с ревью человеком; append-only журнал всех решений.

Возможности MVP

  • Приём результатов Gatling (3.9.5/3.12) и JMeter: push через API (curl / Jenkins pipeline) или загрузка через GUI.
  • Регистрация прогона с provenance (сценарий, стенд, commit, датасет, фазы нагрузки) — задел под запуск из Jenkins и будущие CI-гейты.
  • Автосбор фактов прогона: аппаратные метрики из VictoriaMetrics и APM из ELK за окно прогона.
  • Детерминированный вердикт по версионируемым SLA-правилам: абсолютные пороги + сравнение с baseline со статистической значимостью; fail-closed при неполных данных.
  • Корректная статистика: перцентили из HDR-гистограмм (без усреднения перцентилей), drill-down по группам и запросам.
  • Протокол НТ в Confluence — автоматически, идемпотентно, с версионированием страниц; воспроизводимый комплект (AsciiDoc + графики + verdict.json) в MinIO.
  • GUI: список и карточка прогона, сравнение двух прогонов, live-наблюдение за идущим тестом, структурный SLA-редактор с циклом merge request.

Ресурсы

  • Персонал: 1 инженер НТ (part-time, совмещение с текущими задачами) + AI-ассистент разработки; точечные консультации администраторов источников данных (VictoriaMetrics, ELK) и DevOps (OpenShift, дистрибутив). Отдельная команда разработки не требуется.
  • Инфраструктура (на команду): ~7–10 vCPU, ~20 GiB RAM, ~1 TiB диск; PostgreSQL + MinIO; развёртывание Helm (OpenShift) или docker-compose.

Сроки: пилот на одной команде — до конца января 2027

Инженерная трудоёмкость — 13–16 недель эквивалента полной занятости; план соответствует сроку при занятости инженера ~50%. Согласования ИБ и выдача доступов идут параллельно разработке (заявки — в первую неделю); их задержка сдвигает коллекторы и пилот, но не увеличивает трудоёмкость.
