# Масштабирование аналитики: агрегация подов, metric packs, детерминированный триаж

**Дата:** 2026-09-22

**Статус:** зафиксированная граница работ. Документ не является ADR, не объявляет
ничего реализованным и не меняет существующие контракты.

**Основание:** фактические ограничения ядра (`core/DiagnosticPlan.kt:741-749`,
`core/CorrelationHeadlineSelection.kt`, `core/ResourceSnapshot.kt`,
`core/MetricPacks.kt`), первичные артефакты приёмки v1
(`build/stats-validation/v1-usefulness/score.json`,
`build/stats-validation/correlation-full-v1-summary.json`), PRC/PRD v0.6
§§11.1, 11.4, 14.2, 17.2–17.4, ADR 0006, ADR 0007.

## Постановка

Боевой стенд — сотни метрик и десятки подов микросервисов. Текущее ядро
рассчитано на объявленный человеком ограниченный набор: одну сервисную область,
несколько десятков series, одно устойчивое окно и одну выводную семью. Документ
фиксирует три пункта, которые отделяют текущий конверт от боевого, и явно
запрещает решать этот разрыв добавлением новых статистических коэффициентов.

## Текущий конверт (измерено по коду)

| Ограничение | Значение | Источник |
| --- | --- | --- |
| series в `resource-snapshot.v1` | ≤64, ≤100 000 точек на series, ≤500 000 ячеек суммарно, файл ≤16 MiB | `ResourceSnapshot.kt` |
| окон / resource rules | ≤64 / ≤256 | `ResourceSnapshot.kt` |
| корреляционных пар | ≤16 | `DiagnosticPlan.kt:743` |
| правил аномалий / controls на пару / lag | ≤32 / ≤4 / ≤10 ячеек | `DiagnosticPlan.kt:744,746,748` |
| выводная семья | ≤16 гипотез, одно окно, один outcome, 30–240 непрерывных ячеек | `CorrelationHeadlineSelection.kt:56-95` |
| расчётный потолок | 150 млн correlation cell-products | `CorrelationHeadlineSelection.kt` |
| series на один mapping | ровно одна, иначе `AMBIGUOUS_SERIES` | ADR 0007 |

За пределами этого конверта селектор отказывает целиком
(`FAMILY_SIZE_UNSUPPORTED`, `MULTI_WINDOW_FAMILY_UNSUPPORTED`,
`FAMILY_OUTCOME_MISMATCH`, `OBSERVATION_COUNT_UNSUPPORTED`), а находка
`correlation_candidate` публикуется только при `selected = true`
(`DiagnosticAnalysis.kt:59-64`). То есть неподдержанная форма плана даёт сырое
evidence без единой находки.

## Арифметика бюджета семьи

Ограничение в 16 гипотез не произвольное: оно следует из разрешения
bootstrap p-value и процедуры Holm.

При `B = 999` минимально достижимое p равно `1/(B+1) = 0.001`. Первая ступень
Holm требует `p <= alpha/m`:

- `m = 16`: порог `0.003125` — достижим с трёхкратным запасом;
- `m = 50`: порог `0.001` — достижим только в предельном случае;
- `m = 300`: порог `1.67e-4` — недостижим ни при каком результате.

Следствие: при сотнях метрик и `B = 999` выводный слой не способен отвергнуть
хотя бы одну гипотезу. Возможны только два пути, и они определяют состав работ:

1. уменьшить объявленную семью до десятков гипотез детерминированным отбором
   (П-3), сохранив текущие `B` и расчётный потолок;
2. поднять `B` до ≥6000 и пересчитать стоимость. Для 300 гипотез, 240 ячеек и
   одной длины блока это порядка 432 млн cell-products, для двух длин — около
   864 млн, то есть в 3–6 раз выше текущего потолка и требует отдельного
   performance gate.

Экспериментально измерено, что происходит при отсутствии контроля семейства:
16 автокоррелированных пар с поиском лага давали ложную главную находку в 91,7 %
отчётов; MBB + lag-max + Holm снизили это до 13,2 % при detection 100 %, что
всё ещё выше заранее объявленного гейта ≤5 %.

## П-1. Агрегация подов выполняется адаптером, не ядром

**Суть.** Свёртка десятков подов в workload-признаки (суммарный и средний CPU,
memory working set, throttling, restarts, replica count, pod imbalance как
отдельная вычисленная series) выполняется до `resource-snapshot.v1`. Ядро
принимает одну series на один логический признак.

**Граница.** Ядро не агрегирует неявно и не угадывает семантику по имени метрики
(ADR 0007). Pod imbalance — отдельная series, подготовленная адаптером, а не
детектор внутри ядра. Смена идентичности пода (restart, reschedule) — разрыв
наблюдений, а не значение.

**Критерий готовности.** Адаптер выдаёт ≤64 series на сервисную область с явными
`aggregation` и `role`; правило свёртки и число исходных реплик сохранены в
provenance; разрывы идентичности видны в coverage reasons.

## П-2. Metric packs и capability gating

**Суть.** Сотни метрик заменяются объявленным паком (PRC/PRD v0.6 §17.3):
logical metric id, query-шаблоны, type/unit, selectors, aggregation,
missing-data policy, subsystem, supported detectors, default lag window.
Команда выбирает пак, а не перечисляет метрики. Наличие возможностей
проверяется до прогона (§17.2 `ltv doctor`), детекторы запускаются только по
доступным capability (§17.4).

**Граница.** Отсутствие метрики означает неполное покрытие и статус
`SKIPPED`/`DEGRADED`, никогда не норму. Pack не расширяет глобальный
обязательный набор данных. Текущий `MetricPacks.kt` — capability-rollup по
строковым именам метрик без статистики; заявленные в §14.2 pod imbalance,
GC pauses, pool saturation, allocation rate им не вычисляются.

**Критерий готовности.** Pack — версионируемый контракт с валидными и
невалидными примерами и негативными тестами; заявленные в паке статистики
вычисляются и попадают в evidence; `doctor` показывает доступность паков до
анализа.

## П-3. Детерминированный триаж с явным бюджетом семьи

**Суть.** Между snapshot и выводным слоем появляется слой, который формирует
объявленную семью гипотез фиксированного размера из всех доступных series и
окон. Триаж детерминирован, версионируется и входит в `analysis-identity.v1`.

**Состав триажа.** Маска качества по `metric × window × operation`
(observed/missing cells, longest gap, coarse grid, clock alignment),
capability-фильтр пака, вырожденность (константная series, zero MAD, отсутствие
ранговой вариации), материальность по описательным статистикам.

**Граница.** Критерии триажа не используют те статистики, по которым затем
выполняется выводный отбор. Семья фиксируется до просмотра эффектов. Отбор по
лучшему p и сокращение `m` задним числом запрещены. Единица бюджета —
`отчёт × окно × endpoint/outcome × ресурс × режим анализа`. Результат триажа,
включая отклонённое с точной причиной, публикуется в evidence и передаётся в
advisory AI вместе с маской качества.

**Критерий готовности.** Повторный триаж того же входа даёт байт-идентичный
список семьи; размер семьи и причина отказа доступны потребителю; шумовая
характеристика выводного слоя измерена на расширенном корпусе для фактического
размера семьи, а не перенесена из прежних 16.

## Явно не входит

- Модельный (LLM) отбор метрик внутри аналитического пути. Недетерминированный
  селектор нельзя включить в identity, а его неявный поиск нельзя учесть в
  размере семьи, что делает Holm неприменимым.
- Автоматический causal inference, code-aware RCA, ML anomaly detection,
  цифровой двойник стенда (post-MVP по PRC/PRD v0.6 §28 и плану v0.6).
- Изменение semantics `policy_verdict`, baseline selection, confirmation of
  conditions и canonical analysis identity.
- Перенос принятых 7.7–13.2 % остаточного шума на новые размеры семьи, новые
  outcome-метрики, мультиоконные планы и JVM-реализацию селектора.

## Проверка

Пункты считаются закрытыми только при наличии измеренного результата в
существующем приёмочном harness: новые null-конфигурации для фактического
размера семьи, новые seeds, заранее замороженные ожидания и опубликованный
отрицательный результат, если он получен.
