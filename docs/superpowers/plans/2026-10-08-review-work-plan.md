**Дата:** 2026-10-08. **Статус:** согласован с владельцем, код не менялся.
**Объект ревью:** `origin/main` @ `6d9e0ac` (202 влитых PR).

Источник: пять независимых ревью (аналитическое ядро, слой ИИ, real-world
usability, архитектура, продукт и PRC) и обсуждение направления MCP с
владельцем. Полные отчёты лежат в scratchpad сессии ревью (`review-summary.md`,
`report-core.md`, `report-ai.md`, `report-usability.md`,
`report-architecture.md`, `report-product.md`); в репозиторий не перенесены.

Пилот на реальных прогонах идёт отдельно, на другой машине, и в этом перечне
не учитывается.

Каждый пункт перед кодом получает свой план (`superpowers:brainstorming`,
`writing-plans`) и блок `REQUESTED / REQUIRED / NOT REQUIRED / EXPECTED FILES`.

## 0. Краткий вердикт ревью

LT Verdict сегодня: честный, воспроизводимый, аккуратно ограниченный SLA-гейт
для JTL/Gatling с хорошей инженерной гигиеной. Это не продукт из PRC v0.6:
синтеза инцидентов нет, аналитический слой не доказан, реальных прогонов и
пользователей кроме владельца нет. «Проверяемый вердикт» означает
воспроизводимость из байтов, а не статистическую обоснованность.

Главные системные проблемы по весу:

1. Ценность не доказана, центральное обещание (инциденты) не построено.
2. Два частых выхода ядра читаются не как то, что они измеряют: сравнение
   прогонов с фиксированными 5 % (36,8 % ложных CANDIDATE на автокоррелированном
   нуле, измерено проектом); вердикт по всему прогону вместе с разгоном;
   каскады fail-closed (`NO_VERDICT` перекрывает найденный `FAIL`, одна
   INDETERMINATE-ступень обнуляет ёмкость).
3. Последняя миля внедрения не пройдена: нет релиза, baseline только в UI,
   однопользовательский режим, планы привязаны хэшами, CLI без `analysis_id`.
4. ИИ: граница «вердикт ↔ совет» выстроена в коде, но отгружается промпт v1
   (hard_defect 84–87 % против 43–61 % у v2), боевой direct-runner не проверен,
   четыре пути раннера, данные экспериментов вне репозитория.
5. Инженерная аккреция под MINIMAL-CHANGE: удаления 2–7 % от добавлений,
   `installLocalApi` ~1 100 строк и 73 маршрута, 0 `@Serializable` при 545
   `JsonObject` в core, циклы core↔storage, документации в 1,7 раза больше кода.

Направление MCP (решение владельца): движок становится инструментом для
внешнего агента (Qwen Code, Claude Code, GigaCode CLI) вместо хостинга
модели внутри. Три сценария по убыванию ценности: (3) агент тянет данные
анализа и запускает свои проверки по коду продукта; (1) настройка policy и
источников через зонды; (2) черновик заключения, только после измерения.

Инциденты (решение владельца 2026-10-08): включены в план как
детерминированный v0 (ADR в волне 2, реализация в волне 3), не откладываются
до пилота. Инцидент v0 отвечает на «что совпало по времени и где», агент
через MCP отвечает на «почему».

## 5. Отложено до итогов пилота

- Решение по PRC после пилота: оставить FR-ANA-04 как MUST с инцидентами v0
  (W2.7, W3.7) либо выпустить PRC v0.7 с позиционированием «доверяемый гейт +
  протокол НТ». Инциденты v0 делаются в любом случае; пилот решает, достаточно
  ли их для обещания «3–7 инцидентов вместо графиков».
- Инциденты v1: межпрогонные инциденты (с baseline), корреляционные семьи как
  evidence, ранжирование по влиянию. Только после пилота и приёмки C5.
- Гейт выборки с учётом квантиля (p99 при n=20..99 равен максимуму).
- Модель шума для сравнения прогонов через run-dynamics (MAD дельт) или
  внутриоконный блочный bootstrap.
- Приёмка C5 корреляций на замороженных seeds, затем холдаут на реальных прогонах.
- Агентное расследование по ADR 0024 (заменяется сценарием 3 через MCP).
- Многопользовательский режим, retention хранилища, `--no-store`.
- Черновик заключения агентом (сценарий 2 MCP): только после измерения тем же
  холдаут-корпусом через MCP-путь.
