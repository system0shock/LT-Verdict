# ПРК: LT Verdict — платформа анализа результатов нагрузочного тестирования

**Название:** LT Verdict (финализировано; в v0.3 — «NT Verdict»)
**Статус:** проектная концепция (PRC), версия 0.4 — заменяет v0.3 (`prc-nt-analysis-platform.md`, сохранена для истории)
**Дата:** июль 2026

**Изменения v0.4:**
- Добавлены ingest API доставки артефактов и жизненный цикл прогона — задел под управление запуском (ручной/Jenkins) без оркестрации (§2.1–2.2).
- Канал вердикта для Gatling — собственный парсер simulation.log; Graphite понижен до live-наблюдения. Фактура по формату проверена по исходникам Gatling 3.9.5–3.15.1 и исправлена (§2.3).
- Оценка сроков пересчитана под ресурсную модель «1 инженер НТ part-time + AI-ассистент»; ИБ-согласования исключены из оценки (§5).
- Исправления по ревью: детерминированная фазовая разметка, каноническая сериализация verdict.json, политика KS-теста, парсинг в ядре (не OpenShift Job), бюджет скорости парсинга.

## 1. Назначение и границы

Децентрализованная платформа-дистрибутив для анализа результатов нагрузочного тестирования. Каждая команда разворачивает платформу в собственном контуре. Платформа объединяет три класса данных в единую модель прогона, выносит детерминированный вердикт по версионируемому контракту правил и генерирует формальный протокол НТ.

Источники данных:

1. **Результаты прогонов Gatling / JMeter** — сырые артефакты инструментов (simulation.log, JTL), доставляемые push'ем в ingest API (с генераторов вручную/curl-обёрткой или из Jenkins pipeline). **Gatling — целевой инструмент** (у команд версии 3.9.5 и 3.12). Real-time канал (Graphite) — только live-наблюдение, не вход вердикта.
2. **Аппаратные метрики** — CPU, память, диски, сеть, GC, пулы соединений из существующей VictoriaMetrics команды. Платформа **не собирает метрики параллельно** — читает окна прогонов из существующего мониторинга.
3. **APM из ELK** — транзакции, спаны и ошибки из индексов Elastic APM (форк ELK), read-only доступ через REST API.

Инварианты (не обсуждаются при реализации): факты → детерминированный вердикт → интерпретация; вердикт воспроизводим побайтово из тех же входов и той же версии правил; fail-closed — неполные данные дают `NO_VERDICT`, а не «зелёный по умолчанию»; конфигурация-как-код, UI не является источником истины; append-only журнал решений и append-only хранение сырых артефактов с хэшами; сырые данные не покидают контур команды (152-ФЗ, PCI DSS).

Вне границ MVP: оркестрация запуска тестов (закладывается контракт регистрации прогона — запуск остаётся ручным или из Jenkins, §2.1), запись в системы мониторинга, автоматический RCA-агент (интерфейсная точка расширения, после MVP), интеграция с CI-гейтами (появляется естественно после стабилизации вердикта).

## 2. Архитектура

Модульный монолит — выбор в пользу простоты дистрибуции: одна команда получает один контейнер ядра плюс PostgreSQL и объектное хранилище. Модули с жёсткими внутренними контрактами позволяют распилить на сервисы позже.

```
┌────────────────────────── LT Verdict Core ──────────────────────────┐
│                                                                     │
│  Run lifecycle        Ingest                 Collectors             │
│  ├─ Registration API  ├─ Artifact push API   ├─ VM adapter          │
│  ├─ State machine     │  (chunked → MinIO)   │  (PromQL windows)    │
│  └─ Phase markup      ├─ simulation.log      └─ ELK APM adapter     │
│                       │  parser (3.9–3.12;                         │
│  Analysis             │  3.13+ — модуль)     Output                 │
│  ├─ Normalizer (HDR)  ├─ JTL stream parser   ├─ Protocol generator  │
│  ├─ Validity gates    └─ Graphite receiver   │  (adoc → Confluence) │
│  ├─ Verdict engine       (live-view only)    ├─ REST API            │
│  └─ Comparator                               └─ GUI (SPA + SLA)     │
│     (baseline / KS)                                                 │
└──────────────┬───────────────────────────┬──────────────────────────┘
               │                           │
        PostgreSQL                     MinIO / S3
   (прогоны, lifecycle,           (сырые артефакты,
    вердикты, правила,             HDR-снапшоты,
    журнал решений)                протоколы)
```

### 2.1 Жизненный цикл прогона и регистрация (задел под управление запуском)

Прогон — сущность с явным жизненным циклом: `REGISTERED → COLLECTING → COMPLETE → VERDICT | NO_VERDICT` (+ `FAILED_*` на ошибках обработки).

Регистрация выполняется **до старта теста**: `POST /api/v1/runs` принимает scenario_id, стенд, vcs-commit сборки, хэш конфига сценария, датасет, плановое окно прогона и **границы фаз** (ramp-up / steady / ramp-down — план теста их знает). Возвращает `run_id` и ingest token. Поле `trigger: manual | jenkins | ci` фиксирует способ запуска.

Это даёт:

- **Окно для коллекторов** — VM/ELK-адаптеры работают по окну из регистрации (+ преролл для warmup), а не по факту появления файла.
- **Детерминированную фазовую разметку** — фазы приезжают при регистрации, правятся через API/GUI; эвристика по throughput — только подсказка в GUI, не вход вердикта (иначе страдает воспроизводимость).
- **Provenance-каркас** для будущего baseline-корпуса (commit, конфиг, стенд, датасет — с первого прогона).
- **Задел под запуск**: запуск остаётся ручным (с удалённых машин) или из Jenkins — Jenkins-пайплайн это те же два вызова: `register` перед стартом + `upload/finalize` после. Платформа не оркестрирует: ни расписаний, ни управления генераторами, ни агентов.

### 2.2 Ingest API доставки артефактов

`POST /api/v1/runs/{id}/artifacts` — потоковая загрузка чанками в MinIO staging → `finalize` → задача парсинга. Аутентификация по ingest token — артефакт пушится с любой машины обычным curl, без кредов платформы на сторонних хостах. Дедупликация по content-hash, возобновление прерванной загрузки, квоты на размер. Загрузка через GUI — обёртка над тем же API (fallback для ручного сценария).

Pull платформой с генераторов (SSH/SMB) и забор из Jenkins artifacts **не строятся**: первое требует кредов и сетевых согласований «платформа → генераторы», второе — кредов к Jenkins API и знания job-структуры; push закрывает оба сценария одним контрактом.

Все артефакты хранятся append-only с SHA-256; журнал фиксирует, кто и когда что доставил.

### 2.3 Парсеры результатов прогонов

**Gatling (целевой инструмент).** Основной и единственный канал вердикта — собственный парсер simulation.log. Фактура (проверена по исходникам `gatling/gatling`, теги 3.9.5–3.15.1):

- У команд версии **3.9.5 и 3.12 — обе текстовые**. Строчный формат (tab-separated записи Run/User/Request/Group/Error, абсолютные таймстемпы) **идентичен** между 3.9.5, 3.11.5 и 3.12.0; отличается только упаковка: 3.9.5 — каталог с несколькими `.log`, 3.12 — один файл. Один потоковый парсер покрывает обе версии.
- Бинарный формат появился **в 3.13** (не в 3.12, как указывалось в v0.3) и не менялся по 3.15.1 включительно: DataInputStream, big-endian, 5 типов записей, версия Gatling встроена в первую запись. Бинарный парсер — отдельный отложенный модуль (~3–5 дней, исследование формата уже проведено), добавляется при появлении первой команды на 3.13+.

Версионный роутинг: версия Gatling читается из Run-записи файла → известная версия — парсинг; неизвестная — fail-closed с диагностикой (`NO_VERDICT`, «Gatling X.Y не поддерживается, поддерживаются: …»). Поддержка новой версии = diff ридера в исходниках Gatling (~10 минут) + golden-фикстура.

Оракул валидации — штатный HTML-отчёт Gatling: один и тот же лог прогоняется через отчёт Gatling и через платформу, перцентили и счётчики обязаны совпасть. Иерархия групп (group → request) сохраняется для drill-down — аналог Transaction Controllers JMeter.

**JMeter.** Потоковый парсер JTL (чанками, без загрузки файла в память): JTL на десятки миллионов строк разбирается < 2 GiB RAM и ≤ 5–10 минут на 2 vCPU. Сохраняются оба уровня иерархии — Transaction Controllers и вложенные сэмплеры со связью parent→child. Контракт поведения наследуется от jtl-comparator (нормализация лейблов, auto/tc/samplers); эталон сверки — jtl-comparator на контрольных данных.

**Graphite (live-view only).** Netty-приёмник plaintext-протокола (порт 2003) для Gatling DataWriter и JMeter Backend Listener — исключительно live-наблюдение за идущим прогоном. **Не вход вердикта**: Graphite-канал несёт предагрегированные по интервалам значения (count, min/max/mean, заранее настроенные перцентили), из которых нельзя восстановить HDR-гистограммы, корректно смержить окна или провести KS-тест. (В v0.3 Graphite был основным каналом Gatling — исправлено: это противоречило §2.6 «все производные из гистограмм».)

### 2.4 Коллектор аппаратных метрик (VM)

Адаптивная выборка из общей VictoriaMetrics: каждая команда описывает в конфиге маппинг «логическая метрика платформы → PromQL-запрос со своими лейблами». Платформа запрашивает `/api/v1/query_range` только в окне прогона (из регистрации, §2.1, с прероллом), с автоподбором шага под длительность и лимитом на кардинальность ответа. Результат сохраняется как факт прогона — пересчёт вердикта не зависит от retention исходной VM.

### 2.5 Коллектор APM из ELK

Read-only сервисный аккаунт к ES REST API. Чтение агрегаций из `traces-apm*` / `metrics-apm*` (или аналогов в форке — схема фиксируется на этапе 0) в окне прогона: латентность транзакций по сервисам, error rate, топ медленных спанов. Композитные агрегации вместо scroll по сырым документам. Схема-контракт индексов версионируется; расхождение — fail-closed с диагностикой.

### 2.6 Нормализация и вердикт

Единое нормализованное представление: бакетированные HDR-гистограммы (интервал × транзакция × фаза) с фазовой разметкой из регистрации прогона (детерминированной, §2.1). Все производные метрики (перцентили, throughput, таблицы сравнения) выводятся из гистограмм — устраняется некорректное усреднение перцентилей, окна мёржатся корректно. Warmup вырезается из вердикта по фазовой разметке.

Verdict engine: версионируемый контракт правил (YAML, хранится в Git команды, платформа берёт по ref), пороги SLA + дельты к baseline-прогону со статистической значимостью. KS-сравнение выполняется на бакетированных ECDF из HDR-гистограмм; в спецификации этапа 4 фиксируются: точная формулировка статистики, поведение при малых N и **политика множественных сравнений** (ограничение набора сравниваемых метрик или поправка — десятки метрик × десятки транзакций иначе дадут гарантированные ложные срабатывания).

Validity gates до вердикта: полнота данных всех трёх источников, длительность steady-фазы, отсутствие дыр в метриках. Выход — `verdict.json` + запись в append-only журнал решений (кто/что/какая версия правил/хэши входов); UPDATE/DELETE на таблице журнала запрещены на уровне роли БД.

`verdict.json` сериализуется канонически: сортировка ключей, фиксированные форматы чисел, **без wall-clock timestamps и случайных UUID** — иначе инвариант «побайтовой воспроизводимости» непроверяем. Поле `findings` зарезервировано в схеме (пустое) — точка расширения под RCA после MVP, чтобы не ломать формат.

### 2.7 Протокол НТ: цифровой первоисточник и Confluence

Канонический формат протокола — **AsciiDoc** (Asciidoctor): одна строгая спецификация, детерминированный рендер, полноценные таблицы с объединением ячеек, includes и атрибуты для композиции шаблонов. Шаблон протокола — часть конфигурации команды, не кода.

Графики рендерятся детерминированно из нормализованных данных платформы (JVM-рендерер): SVG как канонический артефакт (диффабелен, воспроизводим) + PNG для инлайн-отображения (Confluence DC не рендерит SVG-вложения инлайн без плагинов).

Публикация: adoc конвертируется в Confluence storage format и публикуется через REST API идемпотентно — страница адресуется по ключу прогона (title + labels: run_id, вердикт, сервис), повторная публикация создаёт новую версию страницы; нативное версионирование Confluence — дополнительный аудит-слой. Графики — вложениями. Полный воспроизводимый комплект (adoc + SVG/PNG + `verdict.json`) лежит в MinIO; **Confluence — витрина, не источник истины**. Docx — опциональный экспорт из того же adoc, после MVP.

### 2.8 GUI и SLA-редактор

GUI: список прогонов (с состояниями lifecycle), карточка прогона (вердикт, гейты, таблицы, CDF, live-графики Graphite-канала для идущего прогона), сравнение двух прогонов, SLA-редактор.

SLA-редактор — строго структурный, свободное редактирование запрещено по построению. Форма генерируется из JSON Schema контракта правил: метрики — только из реестра логических метрик, компараторы — из фиксированного словаря типов правил, значения проходят валидацию типов и диапазонов, фазы — из фазовой разметки. Поля raw-YAML в GUI нет.

Цикл изменения: черновик в форме → каноническая сериализация в YAML → diff с текущей версией → ветка и MR в Git-репозитории правил через API (GitLab/Bitbucket) → merge человеком. Инвариант «UI не источник истины» сохраняется. Вердикты пинятся на commit-hash версии правил. В CI репозитория правил — тот же пакет валидаторов, что и в платформе. Fallback, если интеграция с Git API не согласуется: внутренний append-only реестр версий правил с двухступенчатым подтверждением (автор ≠ утверждающий) и экспортом в Git; точка решения — этап 0.

## 3. Технологический стек

| Слой | Выбор | Обоснование |
|---|---|---|
| Ядро | Kotlin 2.x + Spring Boot 3.x | Родной стек команд банка; HdrHistogram — JVM-нативная |
| Гистограммы | HdrHistogram + сжатые снапшоты (V2 encoding) | Мёржатся без потери точности, компактны, воспроизводимы |
| Метаданные | PostgreSQL 15+ | Прогоны, lifecycle, вердикты, журнал решений (append-only, запрет UPDATE/DELETE ролью БД), версии правил |
| Артефакты | MinIO (S3 API) | Сырые simulation.log/JTL, HDR-снапшоты, протоколы; staging-зона загрузок ingest API |
| Доступ к данным | jOOQ + Flyway | Типизированный SQL, миграции как код |
| Парсер simulation.log | Собственный потоковый (текст 3.9–3.12; бинарный 3.13+ — отложенный модуль) | Формат исследован по исходникам Gatling; версионный роутинг fail-closed; оракул — HTML-отчёт Gatling |
| Парсинг JTL | Собственный потоковый CSV-парсер (Jackson CSV / univocity) | Контракт поведения от jtl-comparator |
| Graphite intake | Netty-приёмник plaintext (порт 2003) | Только live-наблюдение; не вход вердикта |
| ES-клиент | elasticsearch-java (RO) | Пиннится на версию форка |
| Протоколы | AsciidoctorJ + шаблоны adoc | Одна спецификация, сложные таблицы, детерминированный рендер |
| Графики | JFreeChart/XChart → SVG + PNG | SVG — канонический артефакт, PNG — инлайн в Confluence |
| Публикация | Confluence REST API | Идемпотентная, по ключу прогона |
| GUI | React + Vite, статика из ядра; SLA-редактор как schema-driven формы | Один контейнер на выходе |
| Поставка | Helm chart (OpenShift) + docker-compose | Дистрибутив, а не сервис |

Сознательно **не** в стеке: Kafka (очереди на PostgreSQL SKIP LOCKED достаточно на объёмах одной команды), собственная TSDB, ML-компоненты в контуре вердикта. Парсинг артефактов выполняется **в ядре с семафором параллелизма** (не выносится в OpenShift Job) — одинаковое поведение в Helm и compose дистрибутивах, RAM-профиль потокового парсинга плоский.

## 4. Требования к инфраструктуре

### 4.1 Ресурсы (на одну командную инсталляцию)

| Компонент | vCPU | RAM | Диск | Примечание |
|---|---|---|---|---|
| Core (API + ingest + collectors + verdict + parsing) | 2, burst 4 | 6 GiB | — | Парсинг потоковый с семафором, RAM-профиль плоский |
| PostgreSQL | 2 | 8 GiB | 100 GiB SSD | ~1–2 GiB метаданных на 1000 прогонов |
| MinIO | 2 | 4 GiB | 0.5–2 TiB | Определяется retention сырых артефактов (~1–10 GiB/прогон) |
| GUI/ingress | 0.5 | 512 MiB | — | |
| **Итого** | **~7–10** | **~20 GiB** | **~1 TiB** | Либо одна ВМ 8 vCPU / 24 GiB под docker-compose |

### 4.2 Сетевые доступы (egress наружу закрыт; источники — строго read-only, два узких write-исключения)

- VictoriaMetrics команды: HTTP `/api/v1/query_range` (8428 / vmselect 8481), RO.
- ES форка ELK: HTTPS 9200, сервисный аккаунт RO на `traces-apm*`, `metrics-apm*`, индексы ошибок.
- Git (внутренний): чтение репозитория правил по ref; write-исключение №1 — ветки и MR через API от сервисного аккаунта (merge — только человеком).
- Confluence DC: HTTPS, write-исключение №2 — сервисный аккаунт с записью **только в выделенный space**, без удаления страниц.
- Входящие: HTTPS 443 (GUI/API/**ingest push** — аутентификация по ingest token, scope ограничен конкретным run_id) за SSO банка; Graphite plaintext 2003/tcp от генераторов (только live-view).

### 4.3 Безопасность и комплаенс

Секреты — в OpenShift Secrets / Vault. TLS на всех внешних интерфейсах, аутентификация GUI через SSO (OIDC/AD). Аккаунты к источникам — строго RO. Ingest token — одноразовый scoped-креденшел на доставку артефактов конкретного прогона, не даёт доступа к данным. Два write-канала (Confluence space, Git MR) ограничены по scope и не касаются данных. Данные прогонов не покидают namespace команды; между командами переносимы только версии правил и схема вердикта. Заявки на сервисные аккаунты и доступы подаются **в первую неделю проекта** — это самый длинный внешний lead time, он исключён из оценки трудоёмкости (§5).

## 5. Этапы и таймлайн

**Ресурсная модель:** 1 инженер НТ, part-time (проект совмещается с текущими задачами) + фронтир AI-ассистент разработки (основной объём кода, тестов и документации — AI; инженер — постановка, ревью, интеграции, предметная экспертиза); точечные консультации администраторов источников данных (VictoriaMetrics, ELK) и DevOps (OpenShift, дистрибутив).

**Целевой срок: пилот на одной команде — до конца января 2027.** Помесячный план: авг–сен 2026 — этапы 0–1 (ingest-ядро); сен–окт 2026 — этапы 2–3 (коллекторы); ноя 2026 — этап 4 (первый вердикт); дек 2026 — этап 5 (протокол + GUI); янв 2027 — этап 6 (дистрибутив + пилот). Срок достижим при занятости инженера ~50%.

**Из оценки исключено** как слабопрогнозируемое: согласования ИБ, выдача доступов и аккаунтов, график пилотных команд. Эти процессы запускаются в первую неделю и идут параллельно разработке; их задержка сдвигает этапы 2–3 (частично) и пилот, но не увеличивает трудоёмкость.

Оценка — в трудоёмкости (FTE-недели эквивалента полной занятости, с учётом AI-ускорения написания кода; интеграционная отладка ускоряется слабо и заложена честно):

| Этап | Содержание | Трудоёмкость | Критерий выхода (fail-closed gate) |
|---|---|---|---|
| **0. Обследование (инженерная часть)** | SLA-контракт пилотного сценария в машиночитаемом виде; adoc-шаблон протокола; фиксация схемы индексов ELK-форка; подтверждение версий Gatling (3.9.5/3.12) и OSS vs Enterprise; подача заявок на доступы; решение Git-MR vs внутренний реестр | 0,5–1 нед | Подписанный SLA-контракт + образцы реальных simulation.log/JTL/индексов; заявки поданы |
| **1. Ingest-ядро** | Registration API + lifecycle, ingest push API (chunked, token), парсер simulation.log (текст 3.9.5/3.12), потоковый JTL-парсер, модель прогона, фазовая разметка, HDR-нормализация, PostgreSQL+MinIO | 2,5–3 нед | simulation.log: перцентили совпадают с HTML-отчётом Gatling на контрольных логах; JTL 10M+ строк < 2 GiB RAM и ≤ 5–10 мин на 2 vCPU, перцентили сходятся с jtl-comparator |
| **2. Коллектор VM** | Конфиг маппинга метрик, выборка окон по регистрации, адаптивный шаг, снапшоты как факты прогона | 1,5–2 нед | Прогон обогащается метриками из боевой VM; повторная выборка даёт идентичный снапшот. До выдачи доступа — разработка на фикстурах |
| **3. Коллектор APM/ELK** | ES-адаптер, композитные агрегации, версионируемый схема-контракт индексов | 2–2,5 нед | Латентности APM за окно сходятся с ручной выборкой в Kibana; чужая схема — диагностируемый отказ. До выдачи доступа — фикстуры |
| **4. Verdict engine** | Правила из Git, validity gates, KS на бакетированных ECDF + политика множественных сравнений, канонический verdict.json, журнал решений | 2–2,5 нед | Вердикт воспроизводится байт-в-байт; отключение любого источника → NO_VERDICT |
| **5. Протокол + GUI** | Adoc-генератор + детерминированные графики, публикация в Confluence, REST API, SPA (список/карточка/сравнение, live-view), SLA-редактор с MR-циклом | 3–3,5 нед | Протокол принят командой вместо ручного; правка SLA из GUI доезжает до Git-MR, после merge вердикт подхватывает новый commit-hash |
| **6. Пилот на одной команде (инженерная часть)** | Дистрибутив (Helm + compose), документация развёртывания, стабилизация | 1–1,5 нед | Команда разворачивает платформу по документации без авторов; ≥10 прогонов с вердиктами и протоколами. Пилот — одна команда, до конца января 2027; расширение — после MVP |

**Итого инженерная трудоёмкость: 13–16 FTE-недель.**
Первый вердикт по реальному прогону (этапы 0–4): **8,5–11 FTE-недель**.

Календарная длительность зависит от квоты времени на проект:

| Квота | Первый вердикт | Полный MVP (инженерная часть) |
|---|---|---|
| 50% (~20 ч/нед) | ≈ 4–5,5 мес | ≈ 6,5–8 мес |
| 30% (~12 ч/нед) | ≈ 7–9 мес | ≈ 10–12 мес |

Критический путь: 0 → 1 → (2, 3 последовательно, частично на фикстурах) → 4 → 5 → 6. Буфер на интеграционные сюрпризы (форк ELK, Confluence storage format) заложен в вилки этапов 3 и 5.

## 6. Риски

| Риск | Вероятность | Митигция |
|---|---|---|
| Единственный исполнитель, part-time: конкуренция с текущими задачами, bus factor | Высокая | AI несёт основную кодовую нагрузку; все решения фиксируются документами (PRC, протокол решений); инкрементальные demo-вердикты; защищённая квота времени — через руководство |
| Задержка доступов/аккаунтов ИБ (вне оценки сроков) | Высокая | Заявки в первую неделю; все аккаунты RO; этапы 2–3 разрабатываются на фикстурах до выдачи доступов |
| Схема APM-индексов форка ELK отличается от ванильной | Высокая | Фиксация схемы на этапе 0; версионируемый схема-контракт; fail-closed |
| Формат simulation.log — внутренний API Gatling, может измениться в новой версии | Средняя (исследовано) | Версия встроена в файл → fail-closed роутинг; текстовый формат целевых версий идентичен 3.9.5–3.12; бинарный стабилен 3.13–3.15.1; проверка новой версии = diff исходников (~10 мин) + фикстура |
| Gatling Enterprise (FrontLine) у части команд — иной пайплайн результатов | Неизвестна | Выяснить на этапе 0; у Enterprise свои отчёты, simulation.log может не писаться — тогда для таких команд отдельное решение |
| Baseline-корпуса на старте нет | Средняя | MVP-вердикт на абсолютных SLA-порогах; provenance при регистрации (§2.1) формирует baseline-корпус с первого прогона |
| Шаблоны протоколов различаются между командами | Средняя | Шаблон — конфигурация; на пилоте ≤2 шаблонов |
| Кардинальность метрик в разделяемой VM | Средняя | Лимиты на размер ответа query_range, явная ошибка вместо OOM |
| Конвертация adoc → Confluence storage format теряет разметку | Средняя | Фиксированное подмножество adoc в шаблоне; golden-тесты рендера; графики — PNG-вложениями |
| Сервисная интеграция с Git API не согласуется ИБ | Средняя | Fallback: внутренний append-only реестр версий правил, решение — этап 0 |

## 7. Открытые вопросы

1. **Gatling OSS vs Enterprise** у команд — выяснить на этапе 0 (критично для канала ingest).
2. **Вебхук по завершении анализа** (для будущего Jenkins-гейта) — включать в задел §2.1 или отложить.
3. Ролевая модель SLA-редактора: кто утверждает MR с правкой правил, нужен ли two-man rule для прод-контрактов.
4. Структура space в Confluence: страница на прогон vs дерево «сервис → сценарий → прогоны», политика архивирования.
5. Глубина биндинга переопределений метрик (per-система vs per-сценарий) — решить на этапе 0 по первому SLA-контракту.
6. **Доставка крупных JTL с удалённых генераторов.** Допускается ли установка подписанного uploader CLI на машины генераторов и Jenkins-агенты? Если да — определить порядок установки и обновления, сетевой маршрут к MinIO, разрешение multipart/resume, TLS/proxy-ограничения и максимальный размер артефакта. Если нет — выбрать согласованный канал передачи файлов размером 0,5–3 ГБ через Core ingress или Jenkins.

Закрытые в v0.4 вопросы (из v0.3): имя продукта — **LT Verdict**; фазовая разметка — детерминированная, при регистрации (§2.1); версии Gatling — 3.9.5/3.12, текстовый парсер (§2.3); способ доставки результатов — push через ingest API (§2.2); минимальные RCA-правила — за границами MVP, поле `findings` зарезервировано (§2.6).
