# Скрипт показа живого демо LT Verdict (12-14 минут)

Документ для того, кто ведёт показ. Стенд описан в
[README стенда](../../tools/demo-stand/README.md), план и состав демо в
[плане живого демо](../superpowers/plans/2026-10-04-live-demo.md), результаты
сквозной проверки и список дефектов в
[отчёте](../superpowers/plans/2026-10-05-demo-walkthrough-report.md).
Скрипт проверен прогоном по настоящему интерфейсу на `origin/main` (`6939659`);
если `main` изменился, перепроверьте числа по таблице в конце.

## Что демонстрируется

Ядро LT Verdict настоящее, данные синтетические: нагрузку и ресурсы строит
детерминированный симулятор стенда, числа повторяются бит в бит. Три сценария:

1. SLA FAIL с понятной причиной (Grafana как источник данных, политика, малая выборка).
2. Тест максимума с «коленом» (ёмкость по ступеням).
3. Насыщение ресурса (вкладка «Глубокий анализ» с общим курсором).

## Подготовка за 15 минут до показа

1. Docker Desktop запущен, порты `127.0.0.1:13000` и `127.0.0.1:19090` свободны.
2. Сборка и стенд (из корня репозитория):

   ```powershell
   .\gradlew.bat installDist
   cd tools\demo-stand
   docker compose --profile render up -d --wait
   ```

   Прогретый стенд поднимается за 40 с, без `--profile render` рендер PNG недоступен
   (останется ссылка на панель).
3. Чистый каталог данных и запуск продукта. Ключ ИИ-разбора в окружении
   **не задавать** (`LT_VERDICT_AI_CREDENTIAL_ENV_FILE` пуст): так случайный клик по
   ИИ-разбору не уйдёт провайдеру.

   ```powershell
   $d = "$env:TEMP\ltv-demo-data"
   Remove-Item -Recurse -Force $d -ErrorAction SilentlyContinue
   ..\..\build\install\ltv\bin\ltv.bat ui --data-dir $d --connections connections.demo.json
   ```

   Адрес печатается в консоли (`Responding at http://127.0.0.1:<порт>`): порт каждый раз
   случайный. Открыть его в Chrome без параметров (новая оболочка по умолчанию),
   включить светлую тему кнопкой в шапке, масштаб 100-110 % при 1280x720.
4. Дополнительные входы для сценария 2 (три исхода и малая выборка), в каталоге
   `tools\demo-stand`:

   ```powershell
   $x = "$env:TEMP\ltv-demo-extra"; New-Item -ItemType Directory -Force $x | Out-Null
   $plan = Get-Content out\capacity\capacity-plan.json -Raw
   $plan -replace '"required_capacity":90','"required_capacity":100' | Set-Content "$x\capacity-plan-req100.json" -NoNewline
   $plan -replace '"required_capacity":90','"required_capacity":104' | Set-Content "$x\capacity-plan-req104.json" -NoNewline
   '{"schema_version":"policy.v1","policy_id":"demo-capacity-refund","rules":[{"id":"overall-p95","metric":"response_time_p95_ms","operator":"lte","threshold":300,"scope":{"kind":"overall"}},{"id":"overall-errors","metric":"error_rate_ratio","operator":"lte","threshold":0.01,"scope":{"kind":"overall"}},{"id":"refund-p95","metric":"response_time_p95_ms","operator":"lte","threshold":300,"scope":{"kind":"transaction","name":"POST /api/refund"}}]}' | Set-Content "$x\capacity-small-sample.json" -NoNewline
   ```

5. Вкладки браузера: продукт; дашборд Grafana
   `http://127.0.0.1:13000/d/ltv-demo` (в шапке три ссылки сценариев, время UTC);
   окно проводника с `tools\demo-stand\out`. Файлы удобно выбирать вставкой пути в
   диалог выбора.
6. Прогнать все три сценария один раз «вхолостую» и убедиться, что числа совпадают с
   таблицей проверки внизу; затем перезапустить `ltv ui` с чистым каталогом данных.

Как отличать прогоны в списке слева: все называются `load.jtl`, различаются по
хэшу в подписи: сценарий 1 `c9b049d3`, ёмкость `18be8865`, насыщение `1e4c9315`.

## Что сказать до начала (1,5 минуты)

> Вердикт по нагрузочному тесту у нас считает детерминированное ядро: одни и те же
> входы дают те же числа. Ядро настоящее, а данные синтетические: стенд
> воспроизводит записанные прогоны. Источник метрик ресурсов — Grafana, продукту
> нужен только профиль. Всё, что я покажу, работает на текущей основной ветке;
> чего нет, назову прямо.

### Стенд (1:30-3:00)

Открыть дашборд Grafana. Показать панели «Load», «Response time p95», «Busy ratio»,
«Queues», «External dependency». Шапка: ссылки на окна сценариев.

> Это обычная Grafana с Prometheus: историю трёх прогонов мы загрузили в неё
> заранее. В продукте источник описан профилем `demo-grafana`: какие запросы
> выполнять и какие правила диагностики применять. Токена нет, Grafana открыта
> только на `127.0.0.1`.

### Сценарий 1. SLA FAIL (3:00-7:00)

1. Вкладка «Правила», шаблон «Базовый API (SLA)»: p95 не более 1000 мс, ошибки не
   более 5 %. Показать русский редактор порогов.

   > Шаблон отражает SLA владельца: p95 не более секунды.
2. «Новый анализ»: файл `out\sla-fail\load.jtl`, источник `demo-grafana`, окно «Авто»,
   шаг 10 с, запас по краям 60 с, **«Максимальный простой» оставить 60**. Политика
   уже принята из шаблона. «Запустить анализ» (1-4 с).
3. Результат **PASS**: p95 451 мс при пороге 1000 мс, ошибки 0,2 %.

   > Тест укладывается в SLA секунды, и ядро честно говорит PASS. Зададим жёсткий
   > внутренний порог.
4. «Правила», порог p95 `1000` заменить на `250`, снова «Новый анализ», «Запустить
   анализ». Результат **FAIL**, «нарушено 1 из 2»: «p95 451 мс при пороге ≤ 250 мс»,
   «Что нарушено» и «Требует внимания» на первом экране.

   > Это не подгонка: порог в редакторе изменён на глазах, данные те же.
5. «Правила», кнопка «Правила по каждой транзакции» (появляется после первого
   анализа), повторный запуск. Результат: «нарушено 5 из 10 · малая выборка».
   Вкладка «Таблицы», таблица «Правила»: строка `POST /api/refund`,
   «35 из 100 · малая выборка».

   > Редкая операция, 35 запросов: ядро считает, но помечает результат «малая
   > выборка», PASS или FAIL рассчитан, но помечен как «малая выборка». Заметьте: «Полнота
   > данных» при этом показывает INCOMPLETE (так задано в ADR 0018), хотя источник
   > COMPLETE: подпись в карточке уточняется.
6. Причина. «Глубокий анализ»: ряд `downstream-wait` выше порога 10 в окне около 5:00-8:00 от
   начала прогона (08:07-08:10 UTC) одновременно с ростом p95; ЦП и БД в норме. Поставить курсор в
   окно роста.

   > Причина не в ЦП и не в БД, а во внешней зависимости: совпадение рядов
   > подсказывает, где искать, но причину не доказывает.
7. «Обзор», «Grafana evidence»: UID `ltv-demo`, панель `5`, «Prepare link», «Render
   PNG» (около 8 с; нажать заранее и говорить, пока рисуется).

   > Окно прогона подставлено в панель Grafana автоматически: те же 08:07-08:10, 26
   > запросов в обработке против двух в норме.

Запас: пункт 5 можно пропустить (минус 1 минута).

### Сценарий 2. Тест максимума (7:00-10:00)

1. Перезагрузить страницу (F5): черновик политики и файлы сбрасываются. «Новый
   анализ»: файлы `out\capacity\load.jtl`, `policies\capacity.json`,
   `out\capacity\resources.json`, `out\capacity\capacity-plan.json`; онлайн-источник
   **не выбирать**. «Запустить анализ».

   > Онлайн-источник с планом ёмкости не сочетается: ступени привязаны к хэшам
   > нагрузки и снимка, поэтому здесь файлы.
2. «Обзор»: «Ёмкость подтверждена — требуемая нагрузка выдержана», граница
   `[95.745, 103.745)` запросов в секунду, PASS при требовании 90 RPS.

   > Ядро даёт проверяемую границу между последней выдержавшей ступенью (96 RPS) и
   > первой не выдержавшей (104 RPS). Само «колено» ядро пока не вычисляет:
   > `KNEE_DETECTOR_NOT_IMPLEMENTED`, это называем прямо.

   График на «Обзоре» **не комментировать**: он показывает только первые 8 минут
   (ступени 40 и 60 RPS).
3. Вкладка «Таблицы»: таблица «Правила» по-русски, на ступени 104 `p95` 11 543 мс
   (нарушение). Английскую таблицу «Saved capacity facts» ниже не разбирать.
4. Колено на глаз. Вариант основной: Grafana, ссылка «Scenario 2: capacity», панели
   «Response time p95» и «Busy ratio»: p95 52-56 мс на 40-96 RPS и 11,5 с на 104 RPS,
   занятость ЦП упирается в 1. Вариант в продукте: «Глубокий анализ», смотреть
   `service-cpu-busy` (занятость выходит на порог 0,95 на 96 RPS) и `cpu-queue`;
   график p95 пока рисуется с заливкой и выглядит рампой, его не показывать (дефект D1
   отчёта).
5. Три исхода одной границы (по желанию, 1 минута): в «Новый анализ» подставить
   `%TEMP%\ltv-demo-extra\capacity-plan-req100.json` вместо плана: **NO_VERDICT**
   («границы недостаточно», «Открыть ёмкость»); `capacity-plan-req104.json`: **FAIL**.

   > Одна граница, три требования, три честных исхода. Ядро не округляет в пользу
   > зрителя.
6. Малая выборка в ёмкости (по желанию): политика
   `%TEMP%\ltv-demo-extra\capacity-small-sample.json` с правилом по редкой операции
   `POST /api/refund` вместо `capacity.json`, остальные файлы те же. Результат
   NO_VERDICT, границы `INDETERMINATE`, причины «в окне ступени мало запросов»,
   `CAPACITY_INSUFFICIENT_SAMPLES`.

   > Если на ступени мало запросов, ступень не подтверждается и граница ёмкости не
   > объявляется: ядро отказывается угадывать.

Сокращение: пункты 5 и 6 пропустить (минус 1,5 минуты).

### Сценарий 3. Насыщение ресурса (10:00-13:00)

1. F5. «Правила», шаблон «Базовый API (SLA)» **без правок**. «Новый анализ»: файл
   `out\saturation\load.jtl`, источник `demo-grafana`, шаг 10 с, запас 60 с.
   «Запустить анализ» (около 2 с).
2. «Обзор»: **FAIL**, p95 3 493 мс при пороге ≤ 1 000 мс, источник COMPLETE.
3. «Глубокий анализ». По умолчанию отмечены шесть рядов: сначала ряды непройденных правил (`db-busy`),
   затем остальные по алфавиту. Снять
   `cpu-queue` и `generator-queue`, отметить `service-cpu-busy`. Показать ряды:
   `db-busy` на 1, `service-cpu-busy` не выше 0,21, `db-queue` растёт к 251.
   Двигать курсор (ползунок или мышь) от 8 минут к 10:47 и показать значения.

   > p95 растёт ровно в окне, когда база занята на 100 %, а ЦП сервиса свободен;
   > очередь к базе копится, на 40 RPS после окна всё возвращается. Курсор общий:
   > видно значение каждого ряда в один и тот же момент.
4. Красные подписи «нарушение выше X» у `downstream-wait` и `generator-queue` **не
   комментировать**: это пороги правил, а не факт нарушения (дефект D4 отчёта);
   нарушен только порог `db-busy` 0,95.
5. По желанию Grafana: «Scenario 3: saturation», панели «Busy ratio» и «Queues» как
   подтверждение.

Диагностика `db-saturated` (48 ячеек подряд, 10:07:00-10:15:00) лежит в таблице
«Таблицы» в блоке ресурсов; она не попадает в «Требует внимания» (дефект D2),
поэтому причину показываем на «Глубоком анализе».

## Чего не показывать и не нажимать

- **Не нажимать «Получить рекомендации»** на вкладке «ИИ-разбор» и не ставить галку
  согласия в «Новый анализ» (п. 5): текст про ModelStudio и галка устарели (решение
  владельца: галку убрать, выбор модели добавить), ключ не задан, вызов не нужен.
- Не открывать вкладку «Сравнение», блок «Saved-run analytics», ссылки «Download ...»:
  английские.
- Не показывать таблицы ресурсов и «Source acquisition» на вкладке «Таблицы»: числа до
  34 знаков, «Not available (null)», английские заголовки.
- Не комментировать график «Обзора» для ёмкости (первые 8 минут) и график p95 в
  «Глубоком анализе» ёмкости (рисуется с заливкой).
- Не включать `?shell=old` без вопроса зрителей.
- Не называть сроки готовности «в разработке».

## Вопросы зрителей и честные ответы

| Вопрос | Ответ |
| --- | --- |
| Это реальные данные? | Нет, синтетические: ядро настоящее, входы строит детерминированный симулятор. Стенд воспроизводит записанные прогоны |
| Почему шаблон дал PASS, а потом FAIL? | Шаблон отражает SLA в секунду, затем мы зашли в редактор и поставили порог 250 мс; данные те же |
| Почему сценарий 2 файлами? | Онлайн-источник и план ёмкости не сочетаются: план привязан к хэшам файлов |
| Что делает ИИ? | Совет создаёт внешняя модель после анализа и только по согласию; вердикт SLA она не меняет. В демо не запускается |
| Можно ли подключить наш Prometheus? | Через Grafana-прокси работает; на реальном Prometheus потребуется округление значений (ограничение 12 знаков, описано в README стенда) |
| Сколько занимает анализ? | Секунды: 1-4 с на этих данных |

## Если что-то пошло не так

| Симптом | Действие |
| --- | --- |
| Источник `PARTIAL` или ошибка Grafana | `docker ps` (должны работать `ltv-demo-stand-grafana-1` и `ltv-demo-stand-prometheus-1`), `docker compose up -d --wait` в `tools\demo-stand` |
| «Render PNG» не отвечает (около 20 с) | renderer не поднят: показать «Open source panel», ссылка работает |
| `ltv ui` не стартует | порт занят чужим процессом: запустить заново, порт выбирается случайно; одна копия на каталог данных |
| Нет времени | сценарий 1 п. 5, сценарий 2 п. 5-6, Grafana-подтверждение сценария 3 |
| Продукт недоступен | `ltv analyze` из README стенда и показ JSON-результата |
