# ADR 0026: Диагностический детектор колена ёмкости

Дата: 2026-10-07.

Статус: Proposed. В Accepted переводится только по слову владельца. Номер 0026
выбран как следующий после 0025; перед слиянием его нужно перепроверить по
`origin/main`.

## Контекст

ADR 0009 осознанно исключил детектор колена: это новый статистический метод
без утверждённой калибровки, поэтому ядро отдаёт `capacity_knee: null` и
`knee_reason: KNEE_DETECTOR_NOT_IMPLEMENTED`. Дорожная карта методов
(`docs/statistical-method-roadmap.md`) предусматривает «кусочную load-response
regression» при условии, что диагностическое колено не заменяет подтверждённую
ёмкость по SLA. План v0.6 (`docs/development-plan-v0.6.md`) повторяет: колено
остаётся диагностикой. Владелец хочет показать на демо 2026-10-08 «определение
точки деградации» для теста максимума.

Жёсткие границы решения:

1. Подтверждённая граница ёмкости (`lower_inclusive`, `upper_exclusive`),
   вердикты ступеней и вердикт ёмкости не меняются и не зависят от колена.
2. Колено всегда помечено «диагностика, не откалибровано».
3. Советник ИИ его не видит: замороженный prompt v2
   (`docs/contracts/advice/v1/system-prompt-v2.md`, SHA-256
   `3c0f28bee6517c13c5c854615e7d3d59301893d9723880818e4034a32e9133bf`)
   утверждает, что `capacity_knee` всегда `null`, и не рекомендует детектор.

## Решение

### Метод `piecewise-hinge-ln-p95.v1`

Входы: по каждой ступени плана достигнутая нагрузка `x_i` (`achieved`, p05 за
10 с, то же значение, что в границе ёмкости) и p95 времени отклика `y_i` в окне
ступени (`overall`, миллисекунды, из метрик окна; политика для этого не нужна).
Ступени идут в порядке плана.

Модель на логарифме отклика: `ln(y) = a + b*x + c*max(0, x - x_k)`, то есть
ломаная с изломом в `x_k`, равным нагрузке одной из ступеней. Для каждого
кандидата `k` от третьей ступени до предпоследней модель подгоняется методом
наименьших квадратов (нормальные уравнения 3 на 3, арифметика `double`,
`StrictMath.log`/`exp`, без случайных чисел), выбирается `k` с минимальной
суммой квадратов остатков (SSE). При равенстве побеждает меньшая нагрузка.
Логарифм нужен, чтобы скачок на порядки (52 мс, затем 11,5 с) не заглушал
остальные ступени в SSE: без него при ступенчатом нарастании излом уходит на
ступень позже.

Колено — интервал `[x_k, x_{k+1})`: от последней ступени устойчивой ветки до
первой ступени за изломом. Метод не интерполирует точку внутри интервала: если
за изломом одна ступень, положение излома внутри интервала данными не
определяется. Поэтому в результате названы обе ступени, и в интерфейсе колено
показывается интервалом.

### Отказ вместо догадки

Результат `DETECTED` выдаётся только если выполнены все условия; иначе
`NOT_DETECTED` с одним кодом причины (проверяются в этом порядке):

| Код | Условие отказа |
| --- | --- |
| `KNEE_RUN_NOT_VALID` | прогон не `VALID` |
| `KNEE_STAGE_DATA_MISSING` | у ступени нет `achieved`, нет запросов в окне либо есть `CAPACITY_INSUFFICIENT_SAMPLES` |
| `KNEE_TOO_FEW_STAGES` | ступеней меньше пяти |
| `KNEE_LOAD_NOT_INCREASING` | достигнутая нагрузка не растёт строго от ступени к ступени (например, цикл «разгон, насыщение, восстановление») |
| `KNEE_NO_BREAK` | SSE ломаной больше 25% SSE одной прямой (излом не улучшает описание) либо прямая точная |
| `KNEE_BREAK_NOT_MATERIAL` | p95 за изломом выше экстраполяции устойчивой ветки меньше чем в 1,5 раза |
| `KNEE_BREAK_WITHIN_NOISE` | превышение над экстраполяцией меньше трёх стандартных отклонений остатков устойчивой ветки |

Пороги (`0,25`; `1,5`; `3`; пять ступеней; три точки до излома) выбраны как
консервативные значения по сценарию 2 демо и синтетическим кривым в
`CapacityKneeTest`; они не калибровались на корпусе прогонов и записаны в
самом элементе (`parameters`), чтобы результат объяснял себя сам.

Используется только p95 времени отклика. Доля ошибок не используется: на
сценарии 2 она плоская (0,2%), а второй ряд требует правил совмещения двух
кривых, то есть отдельного среза.

### Где результат хранится

Новый необязательный элемент `evidence` в `analysis-result.v1`:
`{"type": "capacity_knee_diagnostic", "id": "capacity-knee-diagnostic", ...}`,
добавляется после `capacity-summary` только в режиме `capacity_step`, когда
ядро знает метрики окон ступеней. Поля: `method`, `metric`, `load_axis`,
`unit`, `status` (`DETECTED` или `NOT_DETECTED`), `confidence` (всегда
`UNCALIBRATED`), `calibrated: false`, `diagnostic_only: true`,
`last_stable_stage_id`/`last_stable_load`,
`first_degraded_stage_id`/`first_degraded_load` (или `null`), `sse_ratio`,
`excess_factor`, `reasons`, `points` (ступень, нагрузка, p95), `parameters`.
Схема: `docs/contracts/capacity/v1/capacity-knee-diagnostic.schema.json`.

`capacity_summary`, `capacity.json`, `capacity_knee` и `knee_reason` не менялись:
`capacity_knee` по-прежнему `null` с причиной `KNEE_DETECTOR_NOT_IMPLEMENTED`,
потому что это поле означает откалиброванное колено, которого нет. Схема
`analysis-result.v1` допускает любые объекты в `evidence`, поэтому потребители
остаются совместимыми.

### Советник ИИ

`AdvisoryEvidenceBuilder` копировал в доказательства ИИ все элементы
`evidence` (фильтра по типам не было). Теперь он пропускает элементы типа
`capacity_knee_diagnostic`; ссылки `analysis-result.json#/evidence/N` остальных
элементов сохраняют исходные индексы (элемент добавляется в конец).
`capacity_summary` не менялся. Тест закрепляет, что байты и SHA-256
доказательств с этим элементом и без него совпадают. Prompt и его SHA-256 не
менялись. Единственное отличие доказательств ИИ для анализов ёмкости — поля
привязки `analysis_id` и хэш манифеста (см. ниже), как при любой повторной
отправке.

### Identity и сопоставимость

Результат анализа ёмкости теперь содержит лишний элемент, поэтому identity
получает верхнеуровневое поле `capacity_knee_method:
"piecewise-hinge-ln-p95.v1"` (только при плане ёмкости), по образцу `pod_view_*`
(ADR 0020, п. 5). Без этого повторный анализ тех же входов вернул бы из
хранилища старый результат без колена. Версии модулей (`modules`),
`input_versions` и `limits` не менялись, поэтому ключ сопоставимости baseline и
сравнения прогонов остаётся прежним: ранее сохранённые анализы ёмкости
сопоставимы с новыми. Меняется `analysis_id` анализов ёмкости: при повторной
отправке тех же файлов появляется новый анализ рядом со старым, старый не
изменяется. Анализы без плана ёмкости (`standard`) не меняются побайтно.

### Интерфейс

В таблице «Ёмкость» новой оболочки под строкой «Точка перегиба» появляется
строка «Колено (диагностика)»: интервал, названия ступеней, пометка «не
откалибровано, не влияет на границу ёмкости и вердикт» и название метода; при
отказе — причина по-русски. Вычислений в интерфейсе нет. Старая оболочка,
HTML/AsciiDoc-отчёты и экспорт колено не показывают (вне объёма).

## Отклонённые альтернативы

- Заполнить `capacity_knee` числом: поле читают замороженный prompt и
  потребители, а значение не откалибровано.
- Положить диагностику в `capacity_summary`: он целиком копируется в
  доказательства ИИ, и хэши эталонных пакетов изменились бы.
- Непрерывная подгонка положения узла между ступенями: при одной ступени за
  изломом узел данными не определяется, выдавать число значило бы угадывать.
- Подгонка p95 в миллисекундах без логарифма: SSE определяется скачком на
  порядки, и при ступенчатом нарастании излом уходит на ступень позже.
- Порог «p95 выше X» или «рост в N раз»: это калибровочное правило вроде SLA,
  оно дублирует правила политики.
- Бутстреп, p-значения, доверительный интервал: нужны калибровка и корпус;
  статистическая неопределённость остаётся `NOT_ESTIMATED`.

## Следствия

- Новый файл `CapacityKnee.kt` (метод) и точечные дополнения в
  `CapacityAnalysis.kt`, `AnalysisService.kt`, `AnalysisResult.kt`,
  `AdvisoryAi.kt`; новых зависимостей нет.
- Ограничения метода: излом внутри интервала не локализуется; пологий рост и
  шум дают отказ, а не колено; при плавном разгоне за изломом излом
  приписывается ступени, после которой рост становится заметным; причины
  деградации метод не различает.
- Для перехода в Accepted нужны калибровка на корпусе прогонов (пороги,
  поведение на длинных планах, второй ряд — доля ошибок) и решение, поднимать
  ли колено в `capacity_knee` и prompt советника. Это отдельный срез.
