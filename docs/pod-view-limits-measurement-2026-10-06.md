# Замер пределов `pod-view.v1` (срез P2e)

Дата замера: 2026-10-06. Основа: `origin/main` на коммите `249679a` (P2a-P2d в main).
Предмет: проверка предварительных пределов [ADR 0020](adr/0020-pod-view-artifact.md)
(256 подов, 2 560 рядов, 64 сервиса, 4 контейнера на под, 240 колонок, 614 400 ячеек,
12 MiB). Пределы в этом срезе не менялись, продукт не менялся; запись результата в
ADR 0020 и любое изменение пределов - решение владельца.

## Вывод

2 560 рядов, 240 колонок):

| Пик кучи совместного пути со снимком `C_max` (1 024 x 1 440) не выше 512 MB на анализ | Да. Совместный путь (нагрузка 2,88 млн строк, снимок 13,3 МБ, наихудший pod-view на пределе) проходит на `-Xmx384m` (в цепочке из трёх анализов тоже) и не проходит на `-Xmx320m`; без pod-view тот же анализ проходит на `-Xmx256m`. Рекомендация ADR 0020 «Подлежит пересмотру», п. 1 (`R_max = 3 072`) проверена отдельно (раздел «Альтернатива
`R_max = 3 072`»): превышения ориентиров нет и там, а файл из 3 072 рядов с наихудшими идентификаторами и
токенами занимает 12 460 218 байт, то есть тоже умещается в 12 MiB, с запасом 1 %.

Факты для владельца, найденные при замере (продукт не менялся, решения не приняты) - раздел «Находки».

## Условия замера

- Машина: AMD Ryzen 9 7950X3D (16 ядер, 32 логических процессора), 63,2 ГБ ОЗУ, Windows 11, JDK 21.0.9, сборщик G1.
- JVM как у продукта: сборка `installDist` без `applicationDefaultJvmArgs`, поэтому максимум кучи по умолчанию равен
  четверти ОЗУ (16 176 MB). Других флагов нет, кроме `-Xlog:gc` и `-Xmx` там, где он указан. Процесс java привязан сразу после старта к 30 из
  32 логических процессоров (маска `0x3FFFFFFF`; в самих прогонах её значение не записывалось, скрипт после замера доработан и проверен
  на коротком прогоне; два процессора свободны); каждая JVM запускалась под `Invoke-LtvExclusive` (один тяжёлый прогон за раз).
  Другие процессы на машине (агенты, браузер) не останавливались, поэтому разброс времени между прогонами заметен.
- Измерительный код: `src/test/kotlin/io/ltverdict/perf/PodViewLimitsMeasure.kt` (в основной классовый путь не входит,
  запускается вручную тем же `java -cp` с библиотеками `build/install/ltv/lib`), `tools/perf/pod_view_limits_measure.ps1`
  (оркестрация, GC-лог, привязка процессора), `tools/perf/pod_view_limits.py` (данные). Сырые результаты (GC-логи,
  `results.tsv`, `cli.csv`) в git не входят.
- Данные: нагрузка 2 880 000 строк (8 часов, `tools/perf/generate_jtl.py`, 111 349 806 байт), снимок 1 024 ряда x 1 440
  точек с шагом 20 с (1 474 560 ячеек, 13 335 030 байт; без окон и правил), pod-view 240 колонок с шагом 120 с. Хэши
  привязки (`load_input_sha256`, семантический хэш снимка) совпадают с продуктовыми: все анализы завершились `COMPLETE`.
- Повторы: JVM поднималась заново на каждый замер; внутри «этапов» первые три повтора из восьми считаются прогревом
  (тёплые значения - медиана повторов 4-8, «холодное» - самый первый вызов). Совместный путь: один прогрев и три повтора
  (`cli.csv`); цепочка из трёх анализов - один прогон на значение кучи.

| --- | --- | --- | --- |
| F | 990 544 | 976 036 | 8 % |

| LIMIT / ONE-SERVICE | 4 688 228 | 4 621 241 | 37 % |

| P2d-LIMIT | 7 088 206 | 7 088 205 | 56 % |
| LIMIT-WORST | 10 461 626 | 10 392 796 | 83 % |

Размер 12 MiB применяется к входному файлу, а при чтении - к каноническому (хранимому) виду; каноническая запись не
длиннее компактного входа. Предельный файл ADR оценивал в «около 12 MiB» (7 987 200 байт значений плюс 2 МБ метаданных
плюс 25 % запаса): измерено 10,4 МБ без запаса, из них значения 8,0 МБ. Предел 12 MiB для входа считается по сырым байтам: файл тех же форм с отступами и переводами строк
больше компактного, и наихудший такой файл в 12 MiB не уместится.

## API чтения

Те же серверные прогоны; запросы к сохранённому анализу первого плеча, одним клиентом. Время в мс: самый первый запрос
и медиана 15-16 следующих. Каждый запрос заново читает файл из каталога анализа, сверяет SHA-256 с манифестом и identity,
разбирает файл целиком и только потом строит ответ (кэша нет, один файл за раз под одним разрешением).

| Файл | Куча | Метаданные: холодный / тёплый (макс) | Значения: страница `limit=64`, тёплый | Значения: `limit=256`, тёплый | Размер ответа значений |
| --- | --- | --- | --- | --- | --- |
| C | 512m | 191 / 151 (163) | 124 | 133 | 85 866 байт (48 рядов) |
| LIMIT-WORST | 512m | 863 / 427 (464) | 428 | 438 | 158 648 байт (40 рядов) |
| LIMIT-WORST | без `-Xmx` | 561 / 455 (479) | 437 | 369 | то же |
| ONE-SERVICE | 512m | 642 / 353 (412) | 349 | 365 | 114 519 байт (64 ряда) / 457 213 байт (256 рядов) |

Холодное значение - первый запрос после запуска сервера и трёх анализов (JIT и кэши файловой системы). Обход сервиса
из 256 подов (2 560 рядов) страницами по 64 строки - 40 запросов за 14 047 мс (около 350 мс на страницу); с `limit=256`
страница значений стоит те же 365-405 мс, то есть ориентировочно 10 запросов около 4 с (оценка, не замер). Страница не
превышает 100 000 ячеек (предел ADR): 256 x 240 = 61 440.

## Альтернатива `R_max = 3 072`

Измерено на локальной сборке с `MAX_POD_VIEW_ROWS = 3_072` (одна константа, 12 MiB не менялись, сборка не
коммитилась, рабочее дерево удалено). Форма `OVER-ROWS-WORST`: 256 подов, 64 сервиса, 12 рядов на под, 737 280 ячеек,
наихудшие идентификаторы и токены.

| Показатель | `R_max` 2 560 (LIMIT-WORST) | `R_max` 3 072 |
| --- | --- | --- |
| Файл / канонический, байт | 10 461 626 / 10 392 796 | 12 460 218 / 12 377 674 (99 % / 98 % от 12 MiB) |
| Проверка файла, тёплая, мс | 355 | 428 |
| Удержание результата, МБ | 110,5 | 122,8 |
| Наименьшая куча цепочки одного файла | 192m | 192m |
| Цепочка из трёх анализов | 384m проходит | 384m, 512m и без `-Xmx` проходят (подача 1,4-2,2 с, задание 24,6-30,5 с) |
| Ответ API, тёплый, мс | 427-437 | 478-589 |

Рост линеен по числу ячеек; поднимать файл до 16 MiB для наихудшего компактного файла из 3 072 рядов не требуется, но запас
составит около 1 %, а любая печать с отступами его исчерпает. Решение о значениях принимает владелец.

## Находки

Каждый пункт - факт замера, продукт не менялся.

1. Сверхпредельный файл внутри 12 MiB, но с очень большим числом элементов (6,29 млн значений в одной строке), отвергается
   только после построения дерева `JsonElement`: на куче 512 MB заканчивается `OutOfMemoryError`, через HTTP это `500` с телом
   без кода ошибки; на куче 768 MB и больше файл отвергается за 0,5-0,8 с кодом `POD_VIEW_LIMIT_EXCEEDED
   /column_count`. Сканер проверяет размер, глубину и токены, но не число элементов (ADR 0020, раздел 2: «до разбора JSON
   проверяются размер, корректность UTF-8, глубина, токены чисел»). Рекомендованная куча ADR 0014 - 512 MB. Таким же способом
   разбирается и снимок (не измерялось).
2. ADR 0020, раздел 3, говорит, что реализация «освобождает дерево после проверки» и постоянная нагрузка около двух размеров
   файла. Замер: результат `validatePodView` (`PodViewValidation.Valid`) хранит разобранный `PodViewV1` и копию исходных
   байт, а `ltv analyze` и задание держат его до конца анализа; удержание 79-123 МБ (119-189 байт на ячейку, до 17 размеров
   файла), каноническая сериализация вычисляется дважды (в `validatePodView` и в `AnalysisService.analyze`).
   Это объясняет рост требуемой кучи на 64-128 MB (см. «Совместный путь»). Оценка ADR «до 154 МБ временно» (250 байт на
   ячейку) в пределе соблюдена.
3. Чтение по API не кэшируется: на пределе каждый запрос стоит 0,37-0,47 с (метаданные и значения одинаково), обход
   сервиса из 256 подов по 64 строки - 14 с. Экран «Таблицы» (P4) читает страницами; решение о размере страницы и
   возможном кэше принимает владелец.
4. Синтетика P2d не покрывает проектную форму C (12 рядов на под) и предел 256 подов с 4 контейнерами (3 328 рядов
   отвергаются генератором) и снимок до `C_max`; для замера добавлен `tools/perf/pod_view_limits.py`.
5. SHA-256 файла стоит 2-5 мс (ADR оценивал «десятки миллисекунд»); хэширование не узкое место.

## Что не проверено

- Реальный стенд, реальные ряды и распределение длин токенов (синтетика P2d даёт 11-12 байт на ячейку, наш реалистичный
  генератор - 7,6; наихудшее 12 байт).
- Отрисовка в браузере, работа UI с обходом страниц.
- Параллельные чтения API и параллельные задания (`--analysis-parallelism` больше 1): чтения идут под одним разрешением и
  не измерялись одновременно.
- Снимок с окнами и правилами (в замере их нет), нагрузка другого размера, другая версия JDK, ОС, не Windows.
- Тот же вход через онлайн-сбор (pod-view в онлайн-режиме не предусмотрен).
- Время между прогонами шумит на 25-35 %: машина общая, процессы других агентов не останавливались. Разности времени
  меньше 3-4 с между вариантами в таблицах не являются результатом.
