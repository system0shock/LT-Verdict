## Решения владельца 2026-10-05 и что они значат для демо

### Подключение к Grafana: mTLS (вопрос 49)

Решение владельца: анонимный просмотр Grafana на боевом стенде недопустим, доступ
идёт по mTLS; подгонкой на боевом стенде займётся отдельная сессия; от этого
отчёта нужны документация и срез mTLS на коннекторе. Код не менялся. Анонимный Viewer
на `127.0.0.1` в `docker-compose.yml` стенда остаётся **локальной подменой**: он
нужен только затем, чтобы профиль `demo-grafana` обошёлся без токена и сертификата;
README стенда и скрипт показа помечают это явно.

Что есть сейчас (по коду `SourceHttp.kt`, `SourceConfig.kt` и проверке запуском):

- Все профили используют один общий `HttpClient` без собственного `SSLContext`:
  TLS по умолчанию JVM (доверенные CA из хранилища JVM, проверка имени узла
  включена). Схема `https` допустима; профиль `source-connections.v1` знает только
  `auth: none | bearer | token | basic` (значения из переменных окружения), лишние
  поля отвергаются; полей для сертификата, ключа или CA нет.
- Клиентский сертификат уже работает на уровне процесса через системные свойства
  JVM (`javax.net.ssl.keyStore*`, `javax.net.ssl.trustStore*`; стартовые скрипты
  `ltv` и `ltv.bat` читают `JAVA_OPTS`). **Проверено 2026-10-05:** TLS-прокси с
  обязательным клиентским сертификатом (Python `ssl`, `CERT_REQUIRED`, временный CA)
  перед отдельным экземпляром Grafana стенда, профиль `grafana_proxy` с
  `https://127.0.0.1:<порт>`. Без свойств и с одним `trustStore` анализ завершается
  с `SOURCE_ACQUISITION_FAILED` (источник `FAILED`, запросы с кодом
  `SOURCE_HTTP_ERROR`, полнота INCOMPLETE, вердикт по нагрузке рассчитан); с
  `keyStore` и `trustStore` источник COMPLETE, прокси видел клиентский сертификат
  (8 запросов). Настоящий боевой mTLS-узел не проверялся.

Чего нет:

1. Настройки в профиле: ни путей к сертификату, ключу и CA, ни паролей через `*_env`.
2. Разных сертификатов для разных источников: свойства JVM глобальны на процесс (и
   для других HTTPS-клиентов этого процесса), `HttpClient` один на все профили.
3. Безопасного хранения пароля: пароль хранилища в `JAVA_OPTS` виден в командной
   строке процесса.
4. Диагностики: любая ошибка TLS (нет сертификата, CA не доверен, имя не совпало,
   срок истёк) сводится к `SOURCE_HTTP_ERROR`; интерфейс не подскажет причину.
5. Документации: `docs/user/online-sources.md` говорит лишь, что проверка TLS у
   источников всегда включена, а учётные данные по HTTP требуют
   `allow_insecure_http`; `verify-full` там относится к PostgreSQL, mTLS для Prometheus
   и Grafana не описан.

Предложение среза `feat/sources-mtls` (требует ADR: расширение публичного контракта
`source-connections.v1`, ничего не реализовано):

- Необязательный объект `tls` в профиле: `ca_file`, `client_certificate_file` и
  `client_key_file` (PEM) либо `client_keystore_file` (PKCS12), пароли только через
  `*_env`, пути проверяются при загрузке профиля.
- `SSLContext` и `HttpClient` на источник (изоляция между профилями), без глобальных
  свойств JVM; тот же путь для рендера панелей Grafana.
- Коды `SOURCE_TLS_CONFIG_INVALID` и `SOURCE_TLS_HANDSHAKE_FAILED` без путей и
  паролей в сообщении; русский текст в интерфейсе; предупреждение о скором сроке
  сертификата.
- Тесты на встроенном TLS-сервере с обязательным клиентским сертификатом; раздел
  mTLS в `online-sources.md` (подготовка хранилищ, ротация, ограничения).
- На боевом стенде mTLS, как правило, завершает обратный прокси или ingress перед
  Grafana (или Prometheus при `transport: direct`): это уточняется на стенде той
  самой отдельной сессией.

До среза обход через `JAVA_OPTS` годится только для одного источника на процесс и
только на время.

### Точность чисел (вопрос 50)

Решено: `round(..., 0.000001)` остаётся у автора профиля на МВП. Изменений нет;
ограничение описано в README стенда. Остаётся проблема, что ядро отвергает значения с
более чем 12 знаками (`RESOURCE_LIMIT_EXCEEDED`) без подсказки про `round()`:
срез `chore/sources-round-hint` (понятное сообщение в источнике сбора), минор.

### Рендер и резервный вариант (вопросы 51 и 52)

Решено: нужен либо рендер, либо готовые данные как резерв на случай, если живой
источник не поднимется. Проверено: рендер панели Grafana (профиль `render`) работает
(7,7 с); сохранённые анализы открываются без запущенных источников. `ltv ui` с
каталогом данных после репетиции и **без** `--connections` показал список
прогонов, «Обзор» и «Глубокий анализ» сценария 3 (в нём лежит снимок ресурсов
анализа); без Grafana недоступен только блок «Grafana evidence» (запрос панели).
Если источник недоступен во время анализа, анализ завершается с полнотой
INCOMPLETE (`SOURCE_ACQUISITION_FAILED`), вердикт по нагрузке остаётся. Резерв
описан в скрипте показа: резервная копия каталога данных после репетиции, запуск без
`--connections`, заранее сохранённые PNG панелей.

### Длинный тест от 4 часов (вопрос 53)

Решено: малая выборка в показе не нужна, нужен анализ теста хотя бы на 4 часа.
Сценарии стенда: 15 (60 RPS), 30 (ёмкость) и 18 минут (насыщение): ни один не
достигает 4 часов. **Дефект D16:** стенд не покрывает требование.

Возможность проверена без правок стенда: генератор принимает `stage_scale` в
`generate()` (в командную строку не выведен); `generate(['sla-fail'], ..., stage_scale=16)`
даёт тест 14 400 с плюс 2x120 с простоя, 864 000 строк JTL (33,4 МБ), 57 с генерации,
3 блока `promtool` (около 32 тысяч точек). Данные загружены в отдельный
Prometheus и Grafana (свой compose-проект, свои порты, удалены после замера; рецепт в
приложении). Результат:

| Что | Значение |
| --- | --- |
| `ltv analyze`, `grafana_proxy`, шаг 10 с (1 476 ячеек на ряд), запас 60 с | 8,3-8,8 с; проходит и при `-Xmx192m` (меньше не пробовали) |
| UI, загрузка 33 МБ и анализ, `-Xmx512m` | 8,7 с от нажатия до карточки; пик рабочего набора сервера 361 МБ |
| Вкладки «Глубокий анализ» и «Таблицы» после анализа | около 2,5 с каждая (548 строк в таблицах) |
| Результат анализа / каталог данных | 14 КБ / 35 МБ (вход хранится целиком) |
| Вердикт | PASS при политике `sla-fail.json` (p95 за 4 часа 52 мс, 3-минутное замедление растворяется в среднем), диагностика `downstream-slow` FAIL; источник COMPLETE |

Вывод: время и память для 4 часов на этой синтетике укладываются с запасом. «Обзор»
показывает только первые 500 интервалов по 1 с, то есть 8:19 из 4:00:00 (3 %):
для длинного теста он почти бесполезен (усиление D3); «Глубокий анализ» показывает
весь прогон. Не проверено: настоящий JTL JMeter в сотни МБ и 7+ млн строк, 8 часов,
реальный шаг 60 с, браузер при 1,5 тысячи ячеек и 6 рядах на слабой машине.

Предложение среза D16 `feat/demo-stand-soak-4h` (только `tools/demo-stand`): сценарий
`soak-4h` в генераторе (параметр `--stage-scale` в CLI или отдельный сценарий с
плавным ростом p95 и занятости ЦП, чтобы на 4 часах было что показать), его ряды в
Prometheus, `policies/soak-4h.json` (p95 не более 250 мс, ошибки не более 1 %), строка в
README и скрипте; цена: `out/` плюс 33 МБ, генератор около минуты, тест
`tools/test_demo_stand.py` на уменьшенном масштабе.

### Корреляции в демо (вопрос 5)

В демо показываются только отобранные (selected) находки с пометкой «ассоциация,
не причина; не откалибровано» (срез U1 плана корреляций). Сейчас «Обзор» берёт все
`correlation_pair` со статусом `CANDIDATE` и непустым `raw_rho`
(`ui/src/shell/overview.ts`, около строки 150), различия отобранных и неотобранных
пар нет, пометки «не откалибровано» нет (есть общая «диагностика, не причина»).
Это пункт 8 плана [корреляций](2026-10-04-correlations-c1-c6.md), срез U1 (дефект D17).
Стенд плана корреляций не содержит, а онлайн-источник с планом корреляций
несовместим, поэтому сегодня корреляции в демо не показываются; скрипт запрещает их
показ, пока U1 не влит.

## Список дефектов и предложения срезов

Приоритеты: **blocker** (показ невозможен без исправления), **major**
(вводит зрителя в заблуждение или ломает ключевой экран, нужно либо исправить, либо
проговорить и обойти по скрипту), **minor**.

Blocker: нет. Показ возможен с обходами, описанными в скрипте.

| № | Приоритет | Дефект | Предложение среза |
| --- | --- | --- | --- |

## Приложение. Как повторить замер 4-часового теста

Из каталога `tools\demo-stand\generator` (в каталоге `$w` уйдёт около 36 МБ):

```powershell
$w = "$env:TEMP\walk4h"
python -c "import generate, pathlib; generate.generate(['sla-fail'], pathlib.Path(r'$env:TEMP\walk4h\out'), stage_scale=16)"
docker volume create ltv-walk4h_promdata
docker run --rm -v ltv-walk4h_promdata:/prometheus -v "$w\out:/out:ro" --entrypoint promtool prom/prometheus:v3.5.5 tsdb create-blocks-from openmetrics /out/metrics.om /prometheus
```

Отдельный compose-файл (`docker-compose.yml` в `$w`, пути `<repo>` заменить на путь к
дереву) поднимает собственные Prometheus и Grafana на портах 19091 и 13001, не трогая
стенд:

```yaml
name: ltv-walk4h
services:
  prometheus:
    image: prom/prometheus:v3.5.5
    command: [--config.file=/etc/prometheus/prometheus.yml, --storage.tsdb.path=/prometheus, --storage.tsdb.retention.time=3650d]
    volumes:
      - promdata:/prometheus
      - <repo>/tools/demo-stand/prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports: ["127.0.0.1:19091:9090"]
  grafana:
    image: grafana/grafana:12.4.12
    environment: {GF_AUTH_ANONYMOUS_ENABLED: "true", GF_AUTH_ANONYMOUS_ORG_ROLE: Viewer, GF_SECURITY_DISABLE_INITIAL_ADMIN_CREATION: "true"}
    volumes:
      - <repo>/tools/demo-stand/grafana/provisioning:/etc/grafana/provisioning:ro
      - <repo>/tools/demo-stand/grafana/dashboards:/var/lib/grafana/dashboards:ro
    ports: ["127.0.0.1:13001:3000"]
volumes:
  promdata: {name: ltv-walk4h_promdata}
```

Далее `docker compose up -d --wait`, копия `connections.demo.json` с портом 13001 и запуск
`ltv analyze $w\out\sla-fail\load.jtl --policy policies\sla-fail.json --connections ... --source
source-request.demo.json` (при необходимости `JAVA_OPTS=-Xmx512m`). Убрать за собой:
`docker compose down -v` в том же каталоге (только свои контейнеры, том и сеть).
