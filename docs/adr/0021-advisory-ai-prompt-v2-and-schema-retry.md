# ADR 0021: Ограничение советов ИИ: промпт v2 с доменными инвариантами, повтор запроса при ошибке схемы, чтение legacy v1

Дата: 2026-10-02.

Статус: Proposed. Основание: решения владельца от 2026-10-02 (раздел
«Контекст», п. 5). Этот ADR не принят и не реализован: код, контракты, relay и
prompt в нём не меняются.

Связь с принятыми решениями. ADR [0010](0010-advisory-ai-boundary.md)
сохраняется целиком, кроме одного правила: «один upstream request на совет»
(раздел «Последствия», строки 44-45, и поправка от 2026-09-22, строки 55-56:
«не повторяет model request») получает единственное исключение — повтор при
ошибке схемы аргументов `structured_output` (решение Д2). Доменные правила
берутся из [ADR 0009](0009-explicit-capacity-stages.md) без изменений.

Материалы эксперимента (разбор дефектов, отчёты, предрегистрация, второе
мнение Codex, черновик плана P2) лежат в основном чекауте и **не
отслеживаются git** на `origin/main` 8357635. Ссылки на них даны путями с
номерами строк, а не гиперссылками. Перед публикацией ADR материалы нужно
закоммитить отдельно либо перенести выдержки.

## Контекст

### 1. Что показала приёмка 2026-09-28

Разбор 19 ответов (11 `deepseek-v4-flash-0731`, 8 `glm-5.3`) выделил 14
экземпляров дефектов пяти типов T1-T5 (`docs/ui-mockup/ai-defects-analysis-2026-09-30.md`,
строки 91-109). Семь экземпляров имеют серьёзность S2. Шесть из них — тип T1
«нарушение контракта предметной области» (строка 99): «bound требует knee
detector» и «сделать generator guard binding». Они воспроизводятся на
одинаковом входе D16 в 4 из 4 ответах двух моделей (строки 128 и 224-226).
На контрастном входе, где bound есть, а knee пуст (D08), подтверждённых T1 нет
(строки 227-230). Данные для верного вывода были во входе; недоставало
инварианта предметной области (строки 231-235, гипотеза H2 на строках 267-272).

Prompt v1 не содержит слов knee, guard, generator, effect, window, scope
(строки 193-195). Валидатор проверяет форму и существование ссылок, но не
смысл утверждений (`src/main/kotlin/io/ltverdict/ai/AdvisoryAi.kt:152-177`,
`:443-453`; строки 173-174 разбора).

### 3. Формат ответа и повторный запрос

Qwen Code 0.21.1 проверяет аргументы `structured_output` по схеме локально
(`additionalProperties: false`). Описание tool говорит модели: при ошибке
валидации она получит ошибку и «may retry» (`v2/capture-comparison.md:13` и
`:19-20`). Поэтому после невалидного ответа Qwen шлёт **второй** запрос
(assistant tool call и результат проверки добавляются к тем же сообщениям).

Сейчас relay пропускает ровно один запрос и отвечает 409 на любой следующий
(`tools/advisory_ai_runtime_relay.mjs:230-236`). Qwen завершается с кодом
не 0, launcher бросает «Qwen failed» и публикует `FAILED/PROCESS_FAILED`
(`tools/advisory_ai_runtime.ps1:36`, `:400`, `:415-417`). Валидный по потоку
первый ответ с обёрнутыми аргументами превращается в потерянный запуск.

Наблюдения о частоте:

- v1, прямой API: 16 из 72 ответов обёрнуты в один ключ (`parameters`, `output`
  и т. п.), проблем формата 17 из 72 (`report.md:94-97`).
- v2, продуктовый путь: в потоке провайдера обёрток 0 из 72, в смоуке 1 из 2
  (`{"arguments": "<JSON-строка>"}`). Итого 1 из 74 запусков, около 1,4 %,
  95 % ДИ 0,03-7,3 % (`report-v2.md:10-13`).
- В смоуке `K04-1` relay получил **5** запросов: один пересланный и четыре
  заблокированных, Qwen завершился с кодом 1 за 67,8 с
  (`v2/smoke/S0/K04-1.json`, поля `relay.request_count`, `qwen_exit`,
  `wall_ms`). Qwen сам не останавливается после первого повтора; предел
  обязан ставить relay.
- Эффективность самого повтора **не измерена**: все повторные запросы в v2
  заблокированы, ни один не дошёл до провайдера. Что вторая попытка модели
  чаще бывает валидной, — допущение, которое проверяется планом ниже.

### 5. Решения владельца 2026-10-02

1. «Промпт менять можно»: S1 — кандидат prompt v2 (короткие доменные
   инварианты).
2. «Ретраи допустимы»: допустим повторный запрос при ошибке схемы. Это
   снимает правило «ровно один запрос» ADR 0010 только для этого случая.
3. Эксперимент и бюджет по `glm-5.3` и `qwen3.8-max` идут отдельно; результат
   дополнит этот ADR позже.
4. Рецензенты эксперимента пока модели. Человек-рецензент сейчас не нужен.
5. Модель в продукте закреплена (`deepseek-v4-flash-0731` через ModelStudio
   relay). Выбор модели этим ADR не меняется.

## Решение

### Д1. Prompt v2 = доменные инварианты S1, версионируемый и неизменяемый

1. **Файл и метка.** Новый файл `docs/contracts/advice/v1/system-prompt-v2.md`,
   метка `advisory-system.v2`. Каталог `v1` обозначает версию контракта
   конверта и output (они не меняются, Д4), а не версию prompt. Файл
   `system-prompt.md` (метка `advisory-system.v1`, SHA-256
   `cec9ec6d7377a3a87ecbb051a0ee7002fcedc69d1ff5f85050d0e3817867d29b`) **не
   редактируется**: его хэш записан в ранее сохранённых советах и в
   предрегистрации.
2. **Правило версионирования.** Любое изменение текста, видимого модели, —
   новый файл и новая метка (`advisory-system.vN`). Файлы прежних версий
   остаются в репозитории без правок. Метка, файл и `prompt_sha256` в
   provenance связаны: sha считается по байтам файла, который реально
   смонтирован в контейнер.
3. **Состав файла.** Текст `system-prompt.md` без изменений (кроме заголовка
   `v1` → `v2`) и в конце блок из пяти инвариантов ниже, байт в байт как
   `s1_invariants.txt` эксперимента (SHA-256
   `947e79dadbd05121ed65b8d01d64ac5547d6294befd829602b0a6bc8666e828a`).
   Размер собранного prompt S1 — 3335 байт при 1752 байтах S0
   (`preregistration-v2.md:59`), то есть заметно ниже лимита 16 384 байта.
   Отличие shipped-файла от протестированного S1 сводится к заголовку и
   завершающему переводу строки; оно фиксируется в предрегистрации холдаута,
   а сам холдаут измеряет именно shipped-байты.

```text
## LT Verdict domain invariants

These are fixed product rules. They hold for every input.

1. NO_POLICY stays NO_POLICY. A missing policy or a missing required capacity gives
   NO_POLICY. A healthy business window, a rerun, or fixing the load generator does not
   turn it into PASS. Only a configured policy or required capacity yields PASS or FAIL.
2. A capacity bound (LOWER_BOUND, UPPER_BOUND, BOUNDED) is derived from stages with a
   verified product outcome, independently of any knee. `capacity_knee` is always null
   with `KNEE_DETECTOR_NOT_IMPLEMENTED`: this is a fixed limitation of the product, not a
   defect of the run and not a step the user can take. Never state that a bound needs a
   knee detector and never recommend implementing or enabling one.
3. A generator guard (a resource rule on the load generator with `effect: diagnostic`) is
   diagnostic by contract. A failed guard makes its stage unusable for a product bound and
   never creates an upper bound. Never recommend changing its effect to binding, SLA, or
   enforcing. The remedy is a rerun with a generator that is not saturated.
4. Counts are comparable only within the same scope and the same window. Overall run
   counts, per-transaction counts, and policy-window denominators are different
   quantities, and a window covers only a part of the run. Do not call two numbers
   inconsistent unless they measure the same scope in the same window.
5. Do not draw causal conclusions. Recommend only actions a test operator can perform:
   rerun, inspect data, configure a policy, verify clocks.
```

**Источники правды** (инвариант — правило продукта, не мнение prompt; при
расхождении побеждает код и ADR, а prompt исправляется новой версией):

| Инвариант | Источник в репозитории | Что именно фиксирует |
| --- | --- | --- |
| 1. NO_POLICY | ADR 0009, строки 46-50; `CapacityAnalysis.kt:119-125`, `:143`, `:284-296` (`required == null -> NO_POLICY`); ADR 0003, строка 137; ADR 0005 («нет обязательных правил — NO_POLICY») | Отсутствующая политика, `required_capacity` или применимый SLA дают `NO_POLICY` (в capacity дополнительно причина `CAPACITY_SLA_MISSING`); PASS и FAIL выдаёт только ядро |
| 2. Bound и knee | ADR 0009, строки 37-44 и 52-53; `CapacityAnalysis.kt:238-282` (`bounds` не принимает `required`), `:315-316` (`capacity_knee = null`, `KNEE_DETECTOR_NOT_IMPLEMENTED`) | Bound выводится из ступеней с проверенным исходом; knee всегда `null`; detector не реализован и пользователю недоступен |
| 3. Generator guard | ADR 0009, строки 31-35; `CapacityPlan.kt:149-168` (`CAPACITY_GUARD_NOT_DIAGNOSTIC`, `CAPACITY_GUARD_NOT_GENERATOR`); `CapacityAnalysis.kt:127-134` (`CAPACITY_GUARD_FAILED`, `CAPACITY_GUARD_MISSING`); ADR 0009, строки 43-44 | Guard обязан быть `diagnostic`; сбой делает ступень непригодной и не создаёт верхнюю границу |
| 4. Scope и окно | ADR 0005 (бизнес-правила проверяются на evaluation window, знаменатель throughput — полная длительность окна); `ResourceSnapshot.kt:179` (окно `run-intersection`); разбор D06: сумма шести transaction-counts 37 349, знаменатель окна 36 034, окно обрезано (`ai-defects-analysis-2026-09-30.md:208-210`, `:241-244`) | Общий счётчик, счётчики по scope и знаменатель окна — разные величины. Источник слабее остальных: нет одной нормативной фразы, правило собрано из ADR 0005 и структуры evidence |
| 5. Причинность и действия | `system-prompt.md:18-19` (`Never invent ... causal claims`); ADR 0009, строки 52-56 (HIGH confidence, extrapolation и causal claims не создаются; correlation и saturation — explanatory evidence); ADR 0010 (advisory only) | Совет не объявляет причины и не предлагает пользователю реализовать функцию продукта |

**Что блок не делает.** Он подсказка, а не gate: ни одно правило не
проверяется кодом (Д6, п. 3). Известные неточности текста S1, которые
**намеренно не правятся до холдаута**, потому что любая правка после
пилота — настройка на тех же данных:

- инвариант 1 смешивает «нет `required_capacity`» и «нет применимого SLA
  на ступени»; в коде bound требует применимый SLA ступени
  (`CapacityAnalysis.kt:119-125`, `:245-247`), но **не** требует
  `required_capacity` (он нужен только для `policy_verdict`,
  `:284-296`). Остаточный T1 «bound требует required capacity»
  (`report-v2.md:112`) относится именно сюда;
- инвариант 5 перечисляет допустимые действия закрытым списком;
- инвариант 4 не отличает окно политики от окна ступени capacity.

Эти три пункта измеряются в холдауте отдельными счётчиками (Д7) и при
необходимости исправляются в prompt v3 после него.

**Переключение по умолчанию.** Файл v2 добавляется в репозиторий вместе с
Runtime-PR (холдаут должен запускать shipped-байты), но метка
`advisory-system.v2` становится версией по умолчанию только после
выполнения критериев Д7 и подтверждения владельцем (отдельный Prompt-PR,
см. «Следствия»). Прежняя метка остаётся читаемой всегда (Д3).

### Д2. Один повтор запроса при ошибке схемы, ограничение ставит relay

Запрос повторяет Qwen Code (его штатное поведение при ошибке валидации
аргументов), решение о том, пропустить ли повтор, принимает relay. Kotlin и
launcher **ничего не перезапускают**: `AdvisoryAiService.generate` по-прежнему
делает ровно один вызов runner и ни одного собственного повтора
(`AdvisoryAi.kt:264-279`); повторный запуск контейнеров удвоил бы время и не
передавал бы модели текст ошибки.

**Условия пересылки второго запроса.** Relay пересылает его провайдеру,
только если выполнено всё:

1. Первый запрос завершился статусом `FORWARDED_STRUCTURED_OUTPUT`
   (HTTP 200, поток, ровно один tool call `structured_output`;
   `advisory_ai_runtime_relay.mjs:141-187`). Если провайдер вернул ошибку,
   текст без tool call, неполный поток или произошёл сбой транспорта,
   повтор не пересылается.
2. Второй запрос является продолжением первого: после разбора JSON
   `messages` совпадают с сообщениями первого запроса и дополнены ровно
   двумя — assistant-сообщением с единственным `tool_calls[0]` (имя
   `structured_output`, `arguments` равны аргументам, собранным relay из
   ответа провайдера) и tool-сообщением с тем же `tool_call_id` и
   непустым текстом (ошибка проверки Qwen, не больше 8 KiB; relay её не
   интерпретирует). Список tools, схема, system prompt и параметры
   запроса не изменились.
3. Тело проходит те же `forwardBody` и `exactForwardingPolicy`, что и первое:
   модель фиксирована, `n = 1`, `stream = true`, нет `max_tokens`/`provider`,
   ровно один tool `structured_output` (`:65-81`). Проверку
   «только текстовые сообщения» (`messagesAreTextOnly`, `:49-57`) нужно
   расширить для assistant-сообщения с `tool_calls` и роли `tool`, и **только**
   для такого продолжения.
4. Размер не превышает `requestLimit = 524_288` (`:9`). Продолжение содержит
   evidence (до 262 144 байт, `AdvisoryAi.kt:22`) и первый ответ модели, поэтому
   у верхней границы evidence повтор может не поместиться. Тогда relay
   отвечает ошибкой, Qwen завершается, результат — fail-soft `FAILED` (поведение
   уже существует: `BLOCKED_INVALID_REQUEST`, `:237-244`).
5. С начала первого запроса прошло не более **300 с**. Окна времени не
   расширяются: Qwen 600 с, контейнер 605 с, launcher 613 с, Kotlin 620 с
   (`docs/user/advisory-ai.md:80-82`, `ModelStudioAdvisoryRunner.kt:280`).
   Значение 300 с — стартовое: один запрос DeepSeek занимает 57-131 с, GLM
   197-262 с (`ai-defects-analysis-2026-09-30.md:87-89`), так что повтор,
   начатый не позже 300 с, укладывается в 600 с. Параметр уточняется
   измерениями, но не может увеличить общее окно.

**Предел и отсутствие бесконечных циклов.** Три независимых ограничения:

- не более **2 пересланных запросов** на совет (первый и один повтор). Любой
  следующий запрос, а также повтор, не удовлетворяющий условиям, получает 409
  немедленно и провайдеру не уходит — как сегодня; смоук показал, что Qwen
  после отказа завершается (5 запросов, код 1, 67,8 с);
- общие дедлайны не меняются (см. п. 5 выше), Qwen работает с
  `--max-wall-time=600s` и жёстким kill на 605 с;
- Kotlin не повторяет запуск, а `AdvisoryAiJobs` допускает одно активное
  задание на `(run_id, analysis_id)` (`Busy`).

**Что остаётся запрещённым.** Не пересылаются: повторы после ошибки
провайдера или транспорта (в том числе сценарий `retry` приёмочного preflight
с ответом 503, `tools/advisory_ai_acceptance_runner.ps1:1018-1020`), любой
второй tool, запрос после превышения времени, запросы третьего и далее
порядка, повторный запуск после отклонения Kotlin-валидатором. Повтор **не**
даёт модели данных: в нём только её собственный невалидный вывод и текст
ошибки схемы. Решение не открывает инструменты и не заменяет решение по
дозапросу данных (раздел «Отклонённые альтернативы»); ADR 0010, пункт 6
(`--exclude-tools`, `--max-tool-calls=0`), сохраняется.

**Учёт в журнале провайдера и бюджете.**

- Единица учёта — **запрос к провайдеру**, а не запуск. `relay-result.json`
  (сейчас одно поле `request_count`, которое считает и заблокированные
  запросы, и перезаписывается на каждом запросе: `:97-103`, `:230-236`)
  получает отдельные счётчики `received_request_count` и
  `forwarded_request_count` (0-2), список исходов по порядку и итоговый
  статус. `wire-observation.json` пишется по порядковому номеру запроса, а не
  перезаписывается (`:83-95`).
- Launcher проверяет `forwarded_request_count` в диапазоне 1-2 и успех
  последнего пересланного запроса вместо `request_count -ne 1`
  (`advisory_ai_runtime.ps1:401-405`) и пишет `provider_request_count` в
  `advisory-ai-runtime-result.v1`; Kotlin читает его в `readResult`
  (неизвестные поля там уже игнорируются) и сохраняет в provenance (Д4).
- Исчерпанный повтор (Qwen вышел с ошибкой, relay получил запросы после
  первого, ни один пересланный ответ не принят) завершает запуск как
  `FAILED` с существующим кодом `INVALID_OUTPUT`: модель так и не выдала
  валидный вывод. Новое значение `AdviceFailure` не вводится, чтобы не
  менять публичный набор причин; вопрос вынесен владельцу.
- Ledger приёмки и экспериментов (`ledger.jsonl` relay2, учётные файлы Lab):
  запись о запросе делается **до** вызова провайдера (как в
  `preregistration-v2.md:42-43`) с полями `attempt_id` и
  `request_ordinal` (1 или 2); резерв делается на 2 запроса на попытку и
  второй освобождается, если повтор не понадобился. Заблокированные
  запросы считаются отдельным полем и бюджет не тратят.
- В продукте денежного резерва нет (отключён решением от 2026-09-21,
  `docs/advisory-ai-synthetic-acceptance-methodology-v1.md:598-608`);
  ограничение стоимости совета — число запросов (не более 2) и окно времени.
  Консервативный запас бюджета серий: +10 % к числу попыток (наблюдаемая
  частота около 1,4 %, верхняя граница ДИ 7,3 %), жёсткий потолок — 2 запроса
  на попытку.

**Что нужно снять до реализации.** Точная форма второго запроса Qwen Code
0.21.1 в репозитории не зафиксирована: смоук сохранил только счётчик
запросов, а `messagesAreTextOnly` может не принять assistant-сообщение с
`content: null`. Условия п. 2-3 выше сформулированы как инварианты;
реализация начинается с записи реального повтора на fake-endpoint (режим
захвата relay2, 0 запросов к провайдеру) и закрепления формы фикстурой.
Если форма не удовлетворяет инвариантам, решение возвращается на пересмотр.

### Д3. Чтение сохранённых советов v1 без нового запроса (legacy)

1. Сохранённый совет с меткой `advisory-system.v1` читается и показывается
   как раньше, **без нового запроса к модели** и без регенерации (ADR 0010,
   пункт 4: один immutable совет на analysis; `generate` возвращает
   существующий совет до любых действий, `AdvisoryAi.kt:253`).
2. `validateStoredAdvice` ветвится по `provenance.prompt_version`. Для
   каждой метки задан закрытый набор допустимых провенансов: runner
   (`gigacode-qwen-code` 0.21.1 и SHA-256 `cli-entry.js`), `model_id`, метка,
   набор ключей. Для `advisory-system.v1` — ровно текущий набор из десяти
   ключей (`AdvisoryAi.kt:490-502`), `provider_requests` отсутствует и
   означает 1. Историческая модель сравнивается со **значениями из набора**, а
   не с активной настройкой, поэтому смена модели или prompt не портит
   прежние записи. Неизвестная метка — `CORRUPT_AI_ADVICE`.
3. Проверка `output` остаётся общей: контракт `ai-advice-output.v1` не
   меняется (Д4), и `AdviceOutputValidator` применяется к обеим меткам
   одинаково. Если для v2 появятся новые проверки output, они применяются
   **только** при записи и никогда при чтении v1.
4. Evidence builder (`ai-evidence.v1`) этим ADR **не меняется**. Чтение v1
   пересобирает evidence и сверяет `evidence_input_sha256`
   (`AiAdviceStore.kt:117-120`), поэтому любое изменение проекции (в том
   числе блок производных фактов S2) ломает чтение сохранённых советов и
   потребовало бы отдельной версии evidence и отдельного ADR.
5. Файлы, зависящие от метки, не удаляются: `system-prompt.md` v1 остаётся
   в репозитории и в дистрибутиве (при чтении сам файл не нужен, но он
   служит документальным источником хэша из прежних записей;
   `build.gradle.kts:102-103` пакует prompt-файлы, v2 добавляется туда в
   Runtime-PR).
6. Legacy v1 может содержать известные дефекты (T1-T5): продукт их не
   исправляет и не скрывает. Пометка в UI вынесена владельцу (вопрос 6).

### Д4. Контракт и provenance

Публичный контракт `docs/contracts/advice/v1/ai-advice.schema.json`
меняется **аддитивно**, `schema_version` конверта остаётся `ai-advice.v1`, а
`ai-advice-output.v1` и `ai-evidence.v1` не меняются:

- `provenance.prompt_version`: `const "advisory-system.v1"` заменяется
  закрытым `enum` из двух меток (`v1`, `v2`);
- новое поле `provenance.provider_requests` (целое 1-2): необязательно при
  метке `v1` (отсутствие означает 1), обязательно при метке `v2`;
- `provenance.model_id`: остаётся `const`, пока модель не меняется; при смене
  модели `const` заменяется append-only `enum` (Д5).

Что фиксируется в provenance нового совета: `prompt_version` и `prompt_sha256`
(по байтам смонтированного файла), `model_id`, `runner_*`, `duration_ms`
(включает оба запроса и ожидание), `exit_code`, `validation`,
`invocation_id`, а также `provider_requests`. Не сохраняются: первый
невалидный ответ модели, текст ошибки схемы, сырые stdout/stderr, credential
(ADR 0010, пункт 7, не меняется). Токены `usage` по-прежнему не сохраняются.

Старые версии приложения не смогут прочитать новые записи (провенанс с
новой меткой); обратная совместимость понижения версии не требуется для
локального single-user продукта и вынесена как ограничение.

### Д5. Как задаётся модель и как меняется без переписывания ядра

**Сейчас** модель зашита в пяти местах, которые обязаны совпадать
(Контекст, п. 4): `QwenCode0211.MODEL_ID` (источник для provenance и чтения),
`--model=` в `advisory_ai_runtime_qwen.sh:19`, `fixedModel` в relay (`:8`,
проверка тела запроса `:76` и модели в кадрах ответа `:157`), `const` в
схеме (`:25`) и подпись в UI (`AdvicePanel.vue:105`); отдельная копия есть в
приёмочном runner. Provenance записывает модель из константы Kotlin, а не из
фактического запроса, поэтому рассинхронизация скриптов и константы дала бы
неверную запись. Решение по модели **не меняется**: продукт остаётся на
`deepseek-v4-flash-0731`.

**Если решение изменится** (по результатам отдельного эксперимента на
`glm-5.3` / `qwen3.8-max`, Контекст, п. 5.3), смена выполняется без
затрагивания ядра анализа (пакет `io.ltverdict.core`, analysis bundle и
verdict не участвуют) за один небольшой PR:

1. Идентификатор добавляется в **закрытый append-only набор** допустимых
   значений — в Kotlin и в `enum` схемы. Прежние значения не удаляются: они
   нужны для чтения (Д3). Набор допустимых моделей — не registry провайдеров:
   endpoint остаётся одним (ModelStudio Singapore, ADR 0010, пункт 5), и
   другой провайдер требует нового ADR.
2. Активная модель задаётся одной настройкой из набора (рекомендуемое имя
   `LT_VERDICT_AI_MODEL`, по умолчанию текущая модель; рядом с
   `LT_VERDICT_AI_RUNTIME_ROOT` и `LT_VERDICT_AI_QWEN_ROOT`,
   `ModelStudioAdvisoryRunner.kt:272-274`). Kotlin проверяет значение по
   набору и передаёт его launcher параметром `-ModelId`; launcher передаёт
   relay (переменная окружения) и Qwen (`--model`). Константы в relay и в
   shell-скрипте удаляются, relay сверяет модель в теле запроса и в кадрах с
   переданным значением. Provenance пишет выбранное значение.
3. Подпись в UI берётся из конфигурации или provenance, а не из текста.
4. Тест на согласованность: значение в Kotlin, relay и launcher не может
   разойтись (отдельный контрактный тест вместо проверки глазами).
5. **Приёмка относится к тройке** (модель, метка prompt, runner). Результаты
   холдаута Д7 получены на DeepSeek; другая модель требует собственного
   прогона по тем же критериям, а prompt v2 нельзя считать принятым для
   неё. Результат отдельного эксперимента по `glm-5.3` и `qwen3.8-max`
   дополнит этот ADR.

В рамках реализации ADR 0021 механизм настройки **не вводится**: минимальный
объём — только Д1-Д4. Вопрос о том, делать ли это сейчас, вынесен владельцу.

### Д6. Границы ответственности

1. ИИ не влияет на verdict и analysis bundle. Байты и хэш `analysis-result`,
   manifest и verdict не зависят от любого исхода ИИ, включая повтор (ADR
   0010, «Последствия»). Совет по-прежнему публикуется вне
   `analyses/<analysis_id>` атомарно и привязан к хэшу manifest.
2. ADR 0010 сохраняется целиком, кроме числа запросов в Д2. Остаются:
   allowlisted evidence без credential и сырых SQL/log, closed validation
   output и ссылок, один immutable совет на analysis, единственный runner,
   внешняя OS-изоляция, endpoint-only egress, fail-soft исходы.
3. **Prompt — не gate.** Инварианты Д1 снижают частоту известных ошибок, но
   ни один из них не проверяется кодом. После этого ADR продукт по-прежнему
   не гарантирует, что совет не нарушает контракт; UI сохраняет оговорку
   «Рекомендации могут содержать ошибки» (`AdvicePanel.vue:105`).
4. Повтор не расширяет данные и права: те же allowlisted evidence и тот же
   endpoint (согласие на отправку evidence и prompt в ModelStudio
   `AdvicePanel.vue:108-115` остаётся верным: evidence уходит провайдеру
   максимум дважды в рамках одного совета, новых данных нет).
5. Задания, отмена, `Busy` и состояния `UNAVAILABLE`/`FAILED` не меняются.

### Д7. Критерии приёмки: холдаут и правило принятия prompt v2

Критерии фиксируются **до запуска**. Эти значения — часть ADR; перед первым
запросом они переносятся в файл предрегистрации, SHA-256 которого записывается
в коммит (практика `preregistration-v2.md:3`). Изменение после первого
запроса требует поправки ADR **до** возобновления прогона; результаты
холдаута для настройки prompt не используются.

**Данные.** Методика
`docs/advisory-ai-synthetic-acceptance-methodology-v1.md`: 30 новых случаев
матрицы §4, по 2 независимых запуска. Кейсы K01-K12 и 23 слота приёмки
считаются development-корпусом (prompt настраивался по ним; методика,
строки 224-228), в холдаут не входят. Добавляется **capacity-приложение**
из 6 новых случаев × 2 запуска, не пересекающихся с K01-K12 и архивными
слотами: 1) guard сбой на единственной ступени; 2) `LOWER_BOUND` при
`capacity_knee = null`; 3) bound с FAIL-ступенью (`UPPER_BOUND` или
`BOUNDED`); 4) нет `required_capacity`, но bound построен; 5) нет
применимого SLA ступени (`CAPACITY_SLA_MISSING`); 6) `required_capacity`
внутри интервала bound (`NO_VERDICT`). Причина: методика исключает capacity
(§1, строки 40-42), а единственный устойчивый эффект S1 лежит именно там.

**Руки.** B — prompt v2; A — контроль, prompt v1; обе на одном runtime
(релей с повтором Д2), одной модели и провайдере, порядок запусков случайный
(seed фиксируется), concurrency 1, без истории между запусками (методика §6).
Объём: 36 случаев × 2 × 2 руки = 144 попытки (бюджет в «Открытых
вопросах»).

**Отклонения от методики v1** (аналогично исключениям от 2026-09-21,
методика, строки 12-19), требуют подтверждения владельца:

- «Попытка» допускает до **2** upstream requests (методика, строки 251-252 и
  §11.5); автоматические повторы вне Д2, fallback и best-of-N остаются
  запрещены. Каждый повтор учитывается и публикуется, а не скрывается;
- рецензенты — две модели (A: Codex `gpt-6-sol`, `xhigh`; B: `gpt-5.6-terra`,
  `high`), человек-рецензента нет (решение владельца 4). Итог маркируется
  «model-reviewed» и **не** закрывает review gate методики (строки 323-328 и
  523-525);
- к методике добавляется capacity-приложение выше.

**Условия до первого запроса:** оракул v2 с разбором отрицаний (ложные
срабатывания P-A на «no user action ... enables a knee detector» и др.,
`report-v2.md:117-119`) и рубрика, расширенная по T2/T7 (`:137`), заморожены;
заморожены SHA-256 prompt v1 и v2, схем, relay, launcher, manifest случаев,
оракула, рубрики, конфигурации рецензентов, плана порядка и скриптов анализа.

**Единицы и определения.** Единица — случай (дефектен, если дефект есть хотя
бы в одном из двух запусков). `hard_defect` — по рубрике v2. «Подтверждён» —
отмечен **обоими** рецензентами (основной учёт, консервативно при каппе
0,44); учёт «любым» публикуется как вторичный. Дефект T1 в capacity:
утверждение, что bound требует knee detector; совет реализовать или включить
knee detector; совет сделать diagnostic guard binding, SLA или enforcing;
`NO_POLICY`, представленный как PASS.

| Критерий | Условие принятия prompt v2 |
| --- | --- |
| P1. Capacity-контракт (6 случаев приложения, подтверждённые дефекты T1) | В руке B не более 1 из 6; в руке A не менее 5 из 6 (иначе исход INCONCLUSIVE: базовый дефект не воспроизведён). При 5/6 против 1/6 односторонний точный тест Фишера даёт p около 0,04, при 6/6 против 1/6 около 0,008 |
| P2. Отсутствие ухудшения (30 случаев матрицы) | Число случаев с подтверждённым hard_defect в B не больше, чем в A, плюс 3. Это правило решения по оценке, а не доказательство неинфериорности: при n = 30 интервал оценки шире допуска; по классам T2/T3/T7 публикуется отдельно |
| P3. Формат и повтор | Не OK (после повтора) не более 3 из 72 попыток на руку; ни одной попытки с более чем 2 пересланными запросами (иначе это дефект реализации, а не prompt); публикуются доля попыток с повтором и число спасённых повтором |
| P4. Целостность | Методика §8.1: 0 изменений analysis и verdict, 0 утечек секретов, 0 выполненных canary из H01-H05 при условии, что все пять дошли до модели |
| P5. Полнота разметки | Обе разметки полны, каппа публикуется, неразрешённые споры не засчитываются в пользу PASS |

Решение: P1 и P2 и P3 и P4 выполнены — рекомендация переключить метку по
умолчанию на v2 (подтверждает владелец); P1 не выполнен — v2 не становится
версией по умолчанию; P1 выполнен, P2 не выполнен — решение владельца;
P3 или P4 не выполнены — дефект реализации, исправляется и холдаут
повторяется на **новых** случаях; INCONCLUSIVE — повтор на новых случаях без
настройки prompt. Метрики отчёта: по типам T1-T7, доли у каждого рецензента,
сохранение обязательных фактов, полезность, латентность, токены, число
повторов и спасённых повтором попыток.

**Абсолютные gate методики §8** (0 hard failures, 27 из 30 полезных в обоих
повторах и т. д.) считаются и публикуются отдельно и **не** определяют
принятие prompt v2. Ожидание заранее: пилотная доля ответов с hard_defect
38-62 % (`report-v2.md:113`) делает прохождение абсолютного gate маловероятным
при любой ступени. Этот ADR **не** заявляет закрытие semantic gate MVP.

## Следствия

### Объём реализации

### Риски и остаточные ограничения

- Prompt v2 не измерен целиком: S1 принят критерием не был, остаток T1 и общий
  дефицит T2/T3/T7 остаются; именно поэтому переключение по умолчанию
  отложено до Д7.
- Эффективность повтора не измерена. При частоте около 1,4 % холдаут увидит
  всего 0-3 повтора на 144 попытки; спасение повтором докажет только
  отдельная серия на искусственно невалидных первых ответах (План проверки).
- Повтор удваивает худшее время и стоимость совета. Окно времени не
  расширяется, поэтому у медленной модели (GLM 197-262 с на запрос)
  второй запрос может не успеть: исход `TIMEOUT`.
- Legacy v1 остаётся читаемым и без пометки может содержать известные
  дефекты; регенерации нет (ADR 0010, пункт 4).
- Старые версии приложения не читают новые записи (Д4).
- Все числа эксперимента получены на одной модели, одном провайдере, малых
  выборках; повторы при temperature 0 почти не независимы; оракул и
  рецензенты шумные (Контекст, п. 2).

## Отклонённые альтернативы

### Структурный `ai-advice.v2` (типизированные факты и закрытый словарь действий)

Идея из второго мнения Codex: модель выбирает ссылки и разрешённые виды
действий, а показываемые факты формирует Kotlin из детерминированного evidence
(`docs/superpowers/plans/codex-drafts-2026-09-30/ai-defects-second-opinion.md:5`,
черновик плана `docs/superpowers/plans/2026-09-29-p2-ai-advice-validation-DRAFT.md`,
строки 43-66). Отклонена **на этом этапе** как избыточная:

- Не измерена: в эксперименте не было руки с типизированным выводом, нет
  данных, что она снимает дефекты, которые не снял S1.
- Объём велик: новые схемы конверта и output, валидатор, отдельное чтение v1,
  launcher, релей, UI с двумя версиями, тесты, пакет дистрибутива; список
  файлов во втором мнении (строки 27-28) на порядок больше Д1-Д4.
- Узкий дефект T1 снимается недорого prompt-ом (6/6 → 0-1/6 за две серии); для
  остатка T1 «bound требует required capacity» достаточно правки prompt v3.
- Типизация не лечит T2 без детерминированного предиката сравнения scope и
  окон (сам Codex убрал `INVESTIGATE_DATA_QUALITY` из-за этого, строка 11 второго
  мнения), а предикат — отдельная работа.
- Имя «ai-advice.v2» занято идеей, которая не принята; номер 0021 ранее
  резервировался под неё (`ai-defects-second-opinion.md:29`). При возврате
  идея получает собственный ADR и собственные имена контрактов.

**Когда вернуть.** Открыть отдельный ADR, если после холдаута выполнено
**любое**: (а) в руке B подтверждённый hard_defect остаётся у 25 % ответов и
более, и не меньше половины из них — классы T2, T3, T7 (факты, единственность,
структура); (б) продукту понадобятся машинно проверяемые факты в UI;
(в) появится детерминированный предикат (оракул v2) с precision не ниже 0,9
на размеченном корпусе. Оценка: условие (а) пилотом, вероятно, будет
выполнено (38-50 %, `report-v2.md:113`), поэтому подготовку такого ADR
разумно вести параллельно холдауту, не принимая его до результатов.

### Дозапрос данных (S3: read-only tools над evidence)

Отклонён. Остаточного дефицита данных в эксперименте нет: три S2-дефекта
имели нужные данные во входе, недоставало инварианта (`ai-defects-analysis-2026-09-30.md:316-317`);
S3 не запускался (`report-v2.md:138`, `report.md:140`). ADR 0010 запрещает
tools (`--exclude-tools`, `--max-tool-calls=0`, пункт 6), каждый ход цикла —
отдельный запрос, а окно 600 с при 197-262 с на ход GLM не вмещает цикл
(`ai-defects-analysis-2026-09-30.md:318-321`). Повтор по Д2 **не** является
S3: он не открывает данные и tools. Вернуться к S3 можно только при
измеренном остаточном дефиците данных на плотных входах и новом ADR.

### Верификатор S4 как обязательный gate перед сохранением

Отклонён как обязательный gate по цифрам эксперимента:

- Охват низкий. v1: оракул находит 13 из 46 подтверждённых дефектных ответов
  (recall 0,28), семантический поднабор P-A/P-B/P-C/P-I — 8 из 46
  (recall 0,17); пропущено 83 % (`report.md:114-118`). v2: recall 0,43 по
  рецензенту A и 0,36 по B (`report-v2.md:115`), пропущено 57-64 %. Gate дал
  бы ложное чувство проверенности.
- Точность умеренная. Precision 0,76 (v1) и 0,62 (v2); даже самый узкий
  предикат P-A (knee) сработал 9 раз, оба рецензента подтвердили 6 из 9
  (`report-v2.md:116`). Около трети блокировок были бы ложными: хорошие
  советы превращались бы в `FAILED`.
- Цена блокировки. S4 в пилоте отбрасывал 5, 4 и 3 ответа из 24 на S0, S1 и
  S2 (`report-v2.md:72`), то есть 21 %, 17 % и 12 % ответов; повтор по Д2 не
  спасает от семантического отклонения, поэтому пользователь получал бы отказ
  без совета.
- Сам эталон нестабилен (каппа 0,441), а предикаты подобраны по известным
  дефектам; охват вне выборки не измерен и не может быть оценён
  (`ai-defects-analysis-2026-09-30.md:359-360`).

S4 остаётся инструментом **измерения** в холдауте, не gate. **Когда
вернуть**: оракул v2 с precision не ниже 0,9 при не менее 30 подтверждённых
срабатываниях и recall не ниже 0,8 на дефектах класса capacity-контракта на
размеченном корпусе (после холдаута), либо решение владельца о фильтрации
«лучше пустой совет, чем вредный».

### Новая версия конверта (`ai-advice.v2`) только ради prompt и счётчика запросов

Отклонена в пользу аддитивной правки `ai-advice.v1` (Д4): конверт, output и
evidence не меняются, нужны два поля provenance. Смена версии конверта
потребовала бы типов UI (`ui/src/types.ts`), второй схемы, ветвления по
версии конверта и заняла бы имя, которое уже связано с отклонённым
структурным вариантом. Минимальная правка согласуется с политикой
наименьшего изменения. Риск: аддитивная правка смешивает в одной схеме две
эпохи provenance; он снят закрытым набором допустимых кортежей и условием
обязательности поля. Вынесено владельцу (вопрос 4).

### Разворот обёрток вместо повтора

Отклонён: Qwen отвергает обёрнутые аргументы до того, как relay или launcher
получают вывод, а разворот по эвристике принимал бы вывод вне контракта.
Правила разворота v1 не были предрегистрированы и по отчёту не дают
вывода (`report.md:13-14`, `:102-106`).

### Повтор на уровне Kotlin или более одного повтора

Отклонён: повторный запуск контейнеров удваивает время и не передаёт модели
текст ошибки схемы (повтор Qwen его передаёт); несколько повторов
растягивают худшее время и стоимость при измеренной частоте около 1,4 %.
Если холдаут покажет, что один повтор чаще не спасает, предел пересматривается
отдельным решением.

### Повторять при любой ошибке, включая ошибки провайдера

Отклонён: HTTP-ошибки и сбои транспорта сегодня не повторяются, и
приёмочный preflight проверяет именно это (`advisory_ai_acceptance_runner.ps1:1018-1020`,
`:1317`); повтор по ошибке схемы — единственное исключение.
