## Факты по коду (origin/main ff1fc24)

- `metric_summary` с `scope.kind = "overall"` один на анализ (`metric-summary-overall`); метрики окон это отдельный тип
  `window_metric_summary`. Поля: `sample_count`, `error_count`, `error_rate_ratio {numerator,denominator}`,
  `throughput_rps {numerator,denominator}`, `latency_ms {p50,p95,p99,max}`.
- Строка «Транзакции» форматирует их через `formatNumber` и `formatMetric` (единицы «%», «RPS», «мс» через неразрывный пробел, «нет данных» для
  отсутствующих). Те же функции берёт новая таблица, значение не пересчитывается.
- `stageNotice(result) != null` означает наличие `stage_binding` (вердикт по окну steady).

## Ruling'и

1. **Одна таблица из одной строки, не `dl`.** Тот же вид, что «Транзакции», колонки совпадают плюс max; первая
   колонка «Область» несёт подпись. Цена: на узком экране горизонтальная прокрутка внутри `table-wrap` (как везде).
2. **Нет `overall` в evidence: блока нет** (пустого заголовка не рисуем). Ошибка формата результата не ломает отчёт.
3. **Подпись.** `stageNotice != null`: «весь прогон, справочно»; иначе «весь прогон». Пояснение
   `STAGE_REFERENCE_NOTE` под таблицей только при стадиях (текст уже существует, не новый).
4. **Дубль форматирования ячеек** с таблицей транзакций (7 строк) оставлен: политика MINIMAL-CHANGE не требует
   выделять общую функцию ради двух мест; тест сверяет, что overall и транзакция с теми же числами дают одинаковые ячейки.
5. **Приложение не меняется:** сырой блок «Общие метрики и метрики транзакций» остаётся.

## Приёмка

1. Блок между «Прогон» и «Ошибки» (без «Прогон» после диагностики); одна строка, девять колонок.
2. Ячейки равны ячейкам строки транзакции с теми же числами и литералам известного результата.
3. Подпись с оговоркой только при стадиях; без `overall` блока нет.
4. Сравнение со снимком прежнего HTML проходит с одним явно названным новым блоком; golden обновлены отдельным коммитом.
