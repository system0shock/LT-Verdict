# ADR 0018: Правила платформы по сервисам и режим малой выборки

Статус: Proposed, 2026-10-01.

База: `origin/main` `e8e096f`; ссылки `файл:строка` ниже сверены с этой базой. Все решения D1–D9 — **рекомендации, ожидающие решения владельца**. Этот ADR не объявляет их принятыми или реализованными. Особенно это относится к связи режима малой выборки с `PASS`, `FAIL` и `NO_VERDICT`: владелец определил требование показывать режим, но ещё не утвердил его трактовку в вердикте.

Номер 0016 зарезервирован для ADR о семантике метрик; его черновика нет в `origin/main`. ADR 0017 принят (`docs/adr/0017-baseline-candidates-and-confirmation.md:1-5`), поэтому 0018 свободен. Два файла с номером 0010 и безномерной correlation ADR в `docs/adr/` к этому решению не относятся.

## Контекст

Это ADR-B плана внедрения из материалов владельца вне репозитория. Стенд: два плеча OpenShift, примерно 20 сервисов на плечо, у каждого два сайдкара, плюс БД; тесты длятся 4–8 часов. Владелец ведёт не более примерно 10 протоколов на протяжении 2–4 релизов. Jenkins находится вне объёма. Одна нагрузка направлена на оба плеча; снимок и анализ создаются отдельно для каждого плеча, вердикты независимы, а UI не должен считать одинаковые бизнес-метрики дважды. Это решение владельца уже записано в ADR 0014 (`docs/adr/0014-resource-series-limits-autostep-arm-api.md:484-540`, `:582-589`).

Сейчас `policy.v1` описывает только четыре бизнес-метрики и области `overall` либо точную `transaction` (`Model.kt:23-58`). Ресурсные SLA-правила живут в снимке, а онлайн-профиль источника тоже содержит `rules` и переносит их в ресурсные правила (`ResourceSnapshot.kt:69-77`, `SourceConfig.kt:90-97`, `:383-395`, `:546-568`). Такое устройство не задаёт политику по ожидаемым сервисам и создаёт риск двух владельцев одного SLA-порога. `MetricPacks.kt:113-129` лишь группирует уже имеющиеся ряды по именам; ядро не вычисляет смысл OpenShift-сигнала из имени.

| Тема | Принято в ADR или видно в продукте | Есть в `src/main` на `e8e096f` |
| --- | --- | --- |
| Пределы снимка | ADR 0014 принял измеренные `S_max = 1 024`, `C_max = 1 500 000`, `B_max = 32 MiB`; `E_max = 20 480` остаётся предварительным (`0014:3-9`, `:1019`) | Пределы снимка подняты (`ResourceSnapshot.kt:651-656`; `resource-snapshot.schema.json:14`). Старые числа 64 ряда, 500 000 ячеек и 16 MiB для снимка неактуальны. |
| Плечо | ADR 0014 принял отдельный снимок и анализ на плечо, метку `arm` и условный `resource_arm` в identity (`0014:484-540`, `:1028-1071`) | В `ResourceSnapshot.kt:52-60` нет специального поля `arm`; срез ещё нужен. |
| Пиковая агрегация | ADR 0014 принял `interval_max` для правил `gt` (`0014:1068-1070`, `:1092-1105`) | Enum содержит только `interval_mean` и `interval_rate` (`ResourceSnapshot.kt:92-96`; `resource-snapshot.schema.json:31`). |
| Карточка F1 | Карточка сохраняет найденное нарушение рядом с `NO_VERDICT` (`verdictSummary.ts:295-301`; `verdict-summary.spec.ts:148-163`) | UI есть; новые причины малой выборки и правила платформы ещё не поддержаны. |
| Baseline | ADR 0017 принят, в том числе запрет совмещать изменения identity в одном переходе (`0017:173-180`) | Кандидат statistical baseline уже обязан иметь `VALID` и `analysis_coverage.status = COMPLETE` (`BaselineComparison.kt:101-104`). |

Минимум выборки сейчас фактически равен одному наблюдению: `observed` отказывает только при `sampleCount == 0` (`Policy.kt:209-219`), а оконный путь дополнительно отказывает для полностью пустого окна (`WindowPolicy.kt:25-33`). Поэтому правило по трём–пяти наблюдениям может получить обычный `PASS` или `FAIL`. По материалам владельца вне репозитория это существенный дефект. Малые выборки чаще возникают в отдельных стадиях и редких транзакциях, чем за весь прогон: считать нужно наблюдения **области конкретного правила в конкретном окне**.

Предпосылки реализации этого ADR: срез ADR 0016, ограничивающий значение перцентиля наблюдаемым максимумом, и нужные срезы ADR 0014 для плеча и `interval_max`. До исправления HDR-округление может дать ложный `FAIL` именно на небольшой выборке: в материалах владельца вне репозитория приведён случай 100 сэмплов по 60 000 мс с опубликованным p95 60 031 мс. В текущем коде перцентили берутся через `getValueAtPercentile`, а максимум хранится отдельно (`Metrics.kt:292-305`). Этот ADR не заменяет ADR 0016.

## Решение

Рекомендуется принять D1–D9 **вместе как проект решения**, после ответа владельца на вопросы ниже. Никакой пункт таблицы сам по себе не означает принятия.

| ID | Рекомендация | Что остаётся открытым |
| --- | --- | --- |

## 1. Минимум выборки и режим малой выборки

### Счёт и gate

Единица `n` — `MetricSummary.sampleCount` после binding правила к `overall` либо единственной подходящей транзакции, внутри оцениваемого окна. Binding остаётся точным: отсутствие или неоднозначность транзакции дают `TRANSACTION_NOT_FOUND` либо `AMBIGUOUS_TRANSACTION` (`Policy.kt:190-207`). Gate выполняется после binding и до сравнения с порогом, в общем `evaluatePolicy` и оконном пути. Валидность входа и отсутствие политики проверяются раньше (`Policy.kt:96-99`).

| `n` для бизнес-правила, кроме throughput | Рекомендуемая оценка правила | Причина и режим |
| --- | --- | --- |
| `0` | `NO_VERDICT`, как сейчас | `METRIC_NOT_AVAILABLE`; код причины сохраняется для совместимости с F1 (`Policy.kt:112-116`, `verdictReasons.ts:27`). Для полностью пустого окна остаётся также `BUSINESS_OBSERVATIONS_NOT_FOUND`. |
| `1..19` | `NO_VERDICT`, порог не сравнивается | Новая блокирующая причина `INSUFFICIENT_SAMPLES`. |
| `20..min_samples-1` | Порог сравнивается; трактовка вердикта — ниже | Информационная метка `SMALL_SAMPLE`; она сама не превращает правило в `NO_VERDICT`. |
| `min_samples` и выше | Обычный `PASS` либо `FAIL` | Режим `FULL`. |

Рекомендуемые константы ядра: `MIN_SAMPLES_FLOOR = 20`, `MIN_SAMPLES_DEFAULT = 100`. Необязательное целое `min_samples` задаётся в бизнес-правиле в диапазоне `20..1 000 000`; значение ниже пола отвергается при валидации с `MIN_SAMPLES_BELOW_FLOOR`. Явное значение заменяет только умолчание данного правила, но не пол. Для `throughput_rps` с `gte` gate при положительном `n` **не применяется**: малое число запросов за полную длительность окна и есть низкая измеренная пропускная способность, которую правило должно иметь возможность признать `FAIL`. Нуль остаётся `METRIC_NOT_AVAILABLE` по действующему контракту (`Policy.kt:213-219`); изменение этого случая требует отдельного решения. Указание `min_samples` у throughput рекомендуется отвергать как неприменимое поле, чтобы валидный файл не содержал порог без эффекта.

Числа являются допущениями, а не калибровкой стенда. При nearest-rank p95 совпадает с максимумом для `n < 20`; для p99 соответствующий порядок величины — 100. Точная граница для текущего HdrHistogram зависит от его округления и должна быть зафиксирована тестом после ADR 0016. При 100 наблюдениях хвост p95 содержит около пяти наблюдений, а один ошибочный ответ меняет долю ошибок на 1 процентный пункт. Для p99 на практике следует задавать `min_samples` порядка 1 000 в самом правиле. Ни одно из этих соображений не доказывает статистическую достаточность конкретного прогона.

Нынешний `evaluatePolicy` складывает блокирующие и прочие причины в один `reasons`, после чего любая причина побеждает найденный `FAIL` (`Policy.kt:94-106`, `:137-143`). Реализация должна разделить причины, блокирующие вердикт, и информационные причины покрытия. `INSUFFICIENT_SAMPLES` блокирует; `SMALL_SAMPLE` — нет. Аналогичное различие уже существует для ресурсных diagnostic-правил: их причины попадают в coverage, а статусы не попадают в SLA-свёртку (`ResourceStatistics.kt:62-72`).

### Связь режима малой выборки с PASS, FAIL, NO_VERDICT: три варианта

Решение владельца: вердикт на малой выборке не должен выдаваться молча или скрываться, он помечается режимом малой выборки. **Следующая таблица — трактовки этого решения, ожидающие подтверждения владельца**, а не уже выбранная им семантика.

| Последствие при `20 <= n < min_samples` | Вариант 1: буквальное прочтение, рекомендация | Вариант 2 | Вариант 3 |
| --- | --- | --- | --- |
| Правило | Рассчитанный `PASS` или `FAIL` остаётся вердиктом; добавляется `SMALL_SAMPLE`. | Рассчитанный `FAIL` остаётся `FAIL`; рассчитанный `PASS` становится `NO_VERDICT` с `INSUFFICIENT_SAMPLES`. Ориентировочный `PASS` виден с меткой. | Любой рассчитанный исход становится `NO_VERDICT` с `INSUFFICIENT_SAMPLES`. Ориентировочный `PASS`/`FAIL` виден с меткой. |
| `policy_verdict`, если других правил нет | `PASS` либо `FAIL` | `FAIL` либо `NO_VERDICT` | `NO_VERDICT` |
| Код CLI при `VALID` | 0 либо 2, как сейчас; метка только в JSON | 2 для `FAIL`, 3 для бывшего `PASS` | 3 |
| `analysis_coverage` | `INCOMPLETE` из-за `SMALL_SAMPLE` | `INCOMPLETE` | `INCOMPLETE` |
| Statistical baseline | Исключён автоматически | Исключён | Исключён |
| Будущий baseline «только из PASS» в ADR-C | Обязан отдельно требовать `sample_mode = FULL`. | Малого `PASS` нет. | Малого `PASS` нет. |
| Цена | Скрипт, читающий только код возврата, видит обычный `PASS`/`FAIL`. | Асимметрия сложнее для пользователя; малый ориентировочный `PASS` блокирует иной достоверный `FAIL`. | Официальный `FAIL` скрыт за `NO_VERDICT`, хотя находка остаётся видимой. |

Фиксированный пример: R1 проверяет p95 транзакции `checkout` в окне `steady-1`; `n = 30`, `min_samples = 50`, p95 укладывается в порог. Независимое R2 проверяет `error_rate_ratio` для `overall`, имеет большую выборку и достоверный `FAIL`. При действующем приоритете `NO_VERDICT` над `FAIL` (раздел 6) вариант 1 даёт итог `FAIL`, код CLI 2 и метку `SMALL_SAMPLE` у R1. Варианты 2 и 3 дают R1 статус `NO_VERDICT`, поэтому одна редко посещаемая транзакция переводит общий итог в `NO_VERDICT`, код 3. Нарушение R2 остаётся в findings и видно в карточке F1, но вердикт `FAIL` не выдаётся.

Если у той же R1 `n = 12`, она получает `NO_VERDICT` с `INSUFFICIENT_SAMPLES` **при любом варианте**. Пол сам способен закрыть `FAIL` R2. Для редких транзакций владелец может выбрать окна, где наблюдений достаточно, или осознанно снизить `min_samples` до пола; снизить его ниже 20 при предлагаемом контракте нельзя. Открытым остаётся вопрос, нужен ли пол без исключений или он должен блокировать лишь предполагаемый `PASS`.

Рекомендация — вариант 1: он ближе к формулировке владельца «пометить, не скрывать вердикт» и сохраняет достоверную находку R2. Его слабость должна компенсироваться машинной меткой, явным текстом F1 и ограничением baseline. Ориентировочные UI-формулировки: «PASS — режим малой выборки: 30 сэмплов при минимуме 50» и «FAIL — режим малой выборки: 30 сэмплов при минимуме 50». Итоговый копирайт — задача среза UI. `SMALL_SAMPLE` в `verdictReasons.ts` имеет `noVerdict: false`, `INSUFFICIENT_SAMPLES` — `true`; нельзя выдавать информационную метку за причину блокировки.

### Результат и baseline

Без изменения схемы результата к объекту `policy_check` в `evidence[]` аддитивно добавляются `sample_count`, применённое `min_samples` и `sample_mode`. Допустимые значения `sample_mode`: `FULL`, `SMALL_SAMPLE` (`20 <= n < min_samples`) и `INSUFFICIENT` (`0 < n < 20`, блокирующая причина `INSUFFICIENT_SAMPLES`); при `n = 0` поле не ставится, чтобы отсутствие наблюдений не называлось малой выборкой. В `analysis_coverage.reasons` добавляется `SMALL_SAMPLE` либо `INSUFFICIENT_SAMPLES`. Сейчас любая причина делает `analysis_coverage.status = INCOMPLETE` (`AnalysisResult.kt:149-155`). Нового значения `policy_verdict` и нового верхнеуровневого поля результата не требуется: верхний уровень схемы закрыт, а `analysis_coverage` и элементы `evidence` допускают аддитивные поля (`analysis-result.schema.json:37-64`).

`INCOMPLETE` автоматически исключает анализ из кандидатов statistical baseline (`BaselineComparison.kt:101-104`). Ручной выбор baseline эту проверку не выполняет. ADR-C обязан требовать `sample_mode = FULL` для правила «baseline только из `PASS`»; старый результат без метки не следует молча считать `FULL` без повторного анализа или явного решения о миграции.

| Где задан минимум | Identity | Повторное закрепление baseline | Замечание |
| --- | --- | --- | --- |
| Только `min_samples` в правиле; отсутствие поля сохраняет прежнюю оценку, opt-in | Меняется лишь `policy_sha256`, которого нет в ключе сопоставимости. | Нет. | Дефект существующих политик остаётся. |
| Константы ядра default-on, плюс поле правила; условный блок `verdict_gates` вне `SEMANTIC_FIELDS` — рекомендация | Меняется `analysis_id` каждого нового анализа с политикой; старые анализы неизменны. | Нет: ключ сопоставимости не меняется. | Вердикт существующей политики в новом анализе может получить метку или стать `NO_VERDICT`. |
| Константы в `limits` либо повышенная версия `policy-evaluation` | Меняется `limits` или `modules`, входящий в ключ. | Да, для затронутых протоколов. | Отклоняется как лишний переход identity; ADR 0017 требует отдельного повторного закрепления при каждом таком переходе. |

`policy_sha256` входит в identity (`AnalysisResult.kt:43`), но не в `SEMANTIC_FIELDS` (`BaselineComparison.kt:942-943`). Детали рекомендованного блока — раздел 8.

## 2. Область «сервис x плечо» и binding политики

Единица итогового вердикта — анализ **одного плеча**. ADR 0014 уже определил по одному снимку и анализу на плечо, метку `arm` у рядов и условный `resource_arm` в identity; эти срезы ещё требуется реализовать (`0014:484-540`). ADR 0018 зависит от них, но не переопределяет их контракт.

Одна политика протокола рекомендуется для обоих анализов одного прогона: `policy_sha256` одинаков, хэши снимков и `resource_arm` различаются. Поля `arm` в платформенном правиле нет. Опечатка в таком поле могла бы тихо отключить проверку плеча и дать ложный `PASS`. Если наборы сервисов или пороги плеч различаются, нужны две явные политики; подтвердить этот случай должен владелец.

Область платформенного правила имеет форму `{"kind":"service","services":["a","b"]}`. Список непустых точных имён — список **ожидаемых** сервисов, поэтому отсутствие сервиса обнаруживается. Один элемент `platform_rules[]` является шаблоном проверки для каждого сервиса списка, а не 20 скопированными правилами. При 20 сервисах и 6–7 сигналах это 120–140 развёрнутых проверок; копирование правил приблизило бы политику к пределу 256 (`Policy.kt:31`, `ResourceSnapshot.kt:656`). Wildcard и regex не вводятся.

Для пары «правило × сервис» binding ищет в снимке ряд с точными `metric = signal`, `entity = имя сервиса`, `role = system`. Нужен ровно один ряд и совпадающая `unit`. Binding не опирается на случайное совпадение `series_id`.

| Состояние пары | Рекомендуемый исход |
| --- | --- |
| Ровно один ряд с нужной единицей | Развернуть в `ResourceRuleV1` с `seriesId` найденного ряда. |
| Ряда нет, включая отсутствующий ожидаемый сервис | `NO_VERDICT`, `RESOURCE_SERIES_NOT_FOUND`; существующий ресурсный код причины (`ResourceStatistics.kt:260`). |
| Подходит больше одного ряда | `NO_VERDICT`, новый `PLATFORM_SERIES_AMBIGUOUS`; не выбирать первый. |
| Ряд найден, но `unit` отличается | `NO_VERDICT`, новый `PLATFORM_UNIT_MISMATCH`; единицы не конвертируются. |
| Политика содержит `platform_rules`, снимок не передан | `NO_VERDICT`, `RESOURCE_SNAPSHOT_REQUIRED`; заявленная проверка не отбрасывается. |

После binding правило разворачивается в обычное `ResourceRuleV1` с детерминированным id `<rule.id>/<service>`, затем оценивается существующим `evaluateRule` через `evaluateResources` (`ResourceSnapshot.kt:69-77`, `ResourceStatistics.kt:21-74`, `:251-319`). Валидатор проверяет предел id 128 байт UTF-8 и отсутствие коллизий после разворачивания. Сохраняется тип evidence `resource_policy_check`; к нему добавляются `platform_rule_id` и `service`. Новый вычислитель и новый столбец вердикта не нужны.

Число развёрнутых правил вместе с допустимыми diagnostic-правилами снимка должно укладываться в существующий предел 256 ресурсных правил **на оценку**. Предварительный бюджет evidence ADR 0014: `E = W × (S + R)`, `E_max = 20 480` (`0014:1019`). Например, `6 × (290 + 140) = 2 580`; `64 × (290 + 140) = 27 520` превышает предварительный бюджет и при его реализации должно отвергаться как `RESOURCE_LIMIT_EXCEEDED`. Нельзя представлять `E_max` как уже измеренный и реализованный предел.

**Один владелец SLA-порога.** Если политика содержит `platform_rules`, ни снимок, ни профиль источника не могут одновременно поставлять ресурсные правила `effect=sla`: комбинация отвергается до анализа с `PLATFORM_RULES_CONFLICT`, код CLI 4. `effect=diagnostic` в снимке остаётся допустимым, в том числе guard генератора ADR 0009 (`docs/adr/0009-explicit-capacity-stages.md:34-35`). Если `platform_rules` нет, прежний путь SLA-правил снимка и профиля сохраняется. Миграция переносит пороги из снимка/профиля в политику; дальнейшая правка порога меняет `policy_sha256`, а не semantic hash снимка. К последнему уже привязаны планы трендов, capacity и diagnostics (`TrendPlan.kt:100`, `CapacityPlan.kt:117`, `DiagnosticPlan.kt:166`).

Сайдкары учитываются как часть сервиса. Запрос профиля источника сворачивает поды и контейнеры в один ряд на `service × signal`, `entity` равен имени сервиса. Для давления применяется максимум, для событийных счётчиков сумма, для недоступных реплик максимум по обслуживающим сервис workload. Ядро не знает контейнеров внутри ряда. Цена такой свёртки — потеря различимости контейнеров; артефакт по подам относится к ADR-D. Необязательные ряды «худший сайдкар» соответствуют варианту C ADR 0014 (`0014:59-63`). БД проходит тот же binding с `entity` имени БД как сервиса; владелец объявляет её сигналы, по умолчанию diagnostic.

## 3. Правила платформы

Рекомендуемая форма элемента `platform_rules[]`: `id`, `signal` (точное значение `series.metric`), `scope`, `operator`, `threshold`, `unit`, `min_consecutive_cells`, `effect`, необязательное `window_ids`. `operator = gt | lt` означает **условие нарушения**, как в ресурсных правилах (`ResourceStatistics.kt:298-302`). У бизнес-правил `lte | gte` означает условие прохождения (`Policy.kt:117-121`). Редактор и карточка обязаны различать эти смыслы. ADR не фиксирует SLA-пороги: их задаёт владелец в политике. Имена новых `series.metric` ниже рабочие и уточняются с профилем источника в срезе P0; ядро не выводит по имени единицу, знаменатель или эффект.

| Сигнал | Определение, источник, единица | Свёртка в сервис и ряд | Форма правила и эффект по умолчанию | Оговорка |
| --- | --- | --- | --- | --- |
| Близость памяти к лимиту: `openshift_memory_limit_ratio` (рабочее имя) | Для каждого контейнера, включая сайдкары: memory working set / объявленный Kubernetes/OpenShift memory limit; `ratio`. Это отношение величин одного контейнера, а не отношение сумм по сервису. | Максимум отношений по контейнерам и подам; для проверки всплеска — `interval_max`. | `gt` выбранного владельцем порога, `min_consecutive_cells` в ячейках; `sla`. | Если limit не задан или не получен, ряд отсутствует либо имеет пропуски: `NO_VERDICT`, а не ноль. Владелец может понизить сигнал до `diagnostic`. До среза `interval_max` доступен лишь `interval_mean`: среднее сглаживает пики; временный выбор явно записывается в provenance и не выдаётся за максимум. |
| Рост памяти / утечка | `openshift_memory_working_set`, JVM Old Gen, non-heap и headroom; единицы соответствуют рядам. | Описательный `trend-plan.v1`, а не SLA-правило платформы. | `diagnostic`; вывод «наблюдается тренд», не причинный диагноз. | L0 не годится для пилы после рестартов: результат зависит от фазы окна (`docs/adr/0011-trend-plan-l0-materiality.md:123-140`). |
| OOM: `openshift_oom` | Приращение счётчика OOM за время / секунды; `events/s`. | Сумма событий по подам и контейнерам; `interval_rate`. | `gt 0`, `min_consecutive_cells = 1`; `sla`. | Сброс счётчика при пересоздании пода и потеря первого приращения нового ряда **не проверены на стенде**. Запрос профиля применяет `increase`/`rate`; это проверяется на реальных данных. |
| Перезапуски: `openshift_restarts` | Приращение счётчика рестартов подов/контейнеров, включая сайдкары, / секунды; `events/s`. | Сумма по сервису; `interval_rate`. | `gt 0`, `min_consecutive_cells = 1`; `sla`. | Те же не проверенные эффекты сброса счётчика. Плановый rollout исключается областью окон, а не скрытым исправлением ряда. |
| CPU throttling: `openshift_cpu_throttling` | Доля throttled CPU periods от всех CPU periods за интервал; `ratio`; нулевой знаменатель даёт пропуск. | Отношение считается для контейнера, затем максимум по контейнерам сервиса; для пиков — `interval_max`. | `gt` порога владельца; по умолчанию `diagnostic`. | Это симптом; его влияние на задержку отражают бизнес-метрики. Повышение до `sla` — отдельный выбор владельца. |
| Доступность: `openshift_unavailable_replicas` | `desired - available` из состояния workload сервиса; `count`. | Максимум по относящимся к сервису workload, затем максимум в интервале. | `gt 0`, `min_consecutive_cells >= 2`; `sla`. | Единый нулевой порог не требует разного `pod_count` для каждого сервиса. Ряд обязателен в профиле P0: агрегат `max by` по оставшимся подам не показывает пропавший под. Краткий rollout допускается длиной серии. |
| JVM heap/headroom, Old Gen, non-heap, GC, пулы; `openshift_pod_imbalance`, сеть, файловая система, БД | Определение и единица задаются отдельным запросом профиля. | По смыслу конкретного ряда; без неявной агрегации в ядре. | `diagnostic` по умолчанию. | Повышение до `sla` возможно лишь после определения источника, единицы, знаменателя и покрытия. |

Для события `gt 0` важно получать именно **приращение за интервал**, а не накопленный счётчик: иначе один старый OOM давал бы нарушение в каждом следующем окне. Для availability важно сравнивать `desired` и `available`, а не принимать присутствующие поды за полный состав сервиса. До реализации профиля P0 эти значения и гарантия покрытия не проверены.

Только `effect=sla` входит в вердикт. Нарушение diagnostic-правила остаётся в findings, а его пропуски попадают в coverage (`ResourceStatistics.kt:62-64`). `min_consecutive_cells` считает соседние нарушающие **ячейки**, не секунды; пропуск обрывает серию (`ResourceStatistics.kt:269-296`). Длительность равна числу ячеек, умноженному на шаг снимка. При автошаге ADR 0014 она меняется; подписи UI и документация должны показывать шаг, иначе тот же численный минимум воспринимается как прежняя длительность. Эффект `interval_max` — серия интервалов с пиками, не непрерывное превышение внутри каждого интервала (`0014:1092-1125`).

## 4. Окно правила и стадии

Сегодня все бизнес- и ресурсные правила проверяются в каждом окне (`WindowPolicy.kt:25-42`, `ResourceStatistics.kt:33-47`). Окна либо явно перечислены в снимке, либо образуют `run-intersection` (`ResourceSnapshot.kt:143-184`). При неявном окне разгон и завершение входят в оценку. Автоопределение стационарных стадий не вводится: ADR 0009 отверг автоматический детектор и использует явные ступени (`docs/adr/0009-explicit-capacity-stages.md:1-35`).

Рекомендуется считать стадией именованное окно `snapshot.windows`. Необязательный массив уникальных `window_ids` добавляется бизнес- и платформенному правилу; каждый id не длиннее 128 байт UTF-8. Нет поля — правило действует во всех окнах, сохраняя старое поведение. Есть поле — правило участвует только в названных окнах. Уровневого `default_window_ids` в политике нет: несколько повторённых id яснее второго механизма умолчаний.

Если в окне нет применимых бизнес-правил, бизнес-часть получает `NO_POLICY`, а не пустой `PASS`, который сейчас получился бы из ветки `else` после фильтрации всех правил (`Policy.kt:101-142`). Пустое окно без применимых бизнес-правил не должно затем принудительно превращаться в `BUSINESS_OBSERVATIONS_NOT_FOUND`: нынешний оконный gate (`WindowPolicy.kt:28-33`) применяется лишь когда есть правило, которому нужны наблюдения. Ресурсная часть уже даёт `NO_POLICY` при отсутствии SLA-правил (`ResourceStatistics.kt:66-72`).

Неизвестный id окна при binding даёт `NO_VERDICT` с `RULE_WINDOW_NOT_FOUND`, по образцу `TRANSACTION_NOT_FOUND`; это зависит от предъявленного снимка, поэтому одна лишь валидация JSON политики не может решить вопрос. Бизнес-правило с `window_ids` при анализе без снимка получает ту же причину: названных окон нет. Для **развёрнутого платформенного** правила окно с меньшим числом ячеек, чем `min_consecutive_cells`, даёт `NO_VERDICT` с `RULE_WINDOW_TOO_SHORT`. Иначе проверка физически не может найти достаточную серию и ложно даёт `PASS` (`ResourceStatistics.kt:269-270`, `:315-319`). Исправление такого случая для существующих правил снимка и профиля здесь не выполняется.

Для протокола 4–8 часов рекомендуется явно назвать стационарные стадии и привязать SLA-правила к ним. Редкую транзакцию следует проверять в тех стадиях, где она действительно вызывается и достигает своего `min_samples`; объединять её с пустой стадией только ради общего окна нельзя. `throughput_rps` по-прежнему делится на полную длительность соответствующего окна (`docs/adr/0005-resource-window-sla.md:12-19`; `docs/user/slice-1-local-analysis.md:598-603`). Конкретные стадии остаются решением владельца протокола.

## 5. Пропуски данных

Сегодня любой `null` в окне SLA-правила обрывает серию и даёт `NO_VERDICT` с `MISSING_RESOURCE_CELLS`, даже если отдельная серия нарушений уже найдена; findings сохраняются (`ResourceStatistics.kt:290-319`). Отсутствующие данные источника должны оставаться пропусками, а не нулями (`docs/adr/0007-opt-in-online-sources.md:17-19`). Карточка F1 уже показывает найденное нарушение при `NO_VERDICT` (`verdictSummary.ts:295-301`).

Рекомендация D6 — оставить этот fail-closed порядок для платформенных `sla`. Никакого `min_coverage_ratio` и допуска пропусков в данном ADR нет. Diagnostic-пропуск отражается в coverage, но не блокирует SLA-вердикт. Покрытие платформы учитывается по `service × signal × window × arm` **до** свёртки pod→service на границе профиля: профиль обязан представить ожидаемый сервис и его доступность. При этом ядро получает только сервисный ряд и не может самостоятельно доказать, что запрос не потерял один из подов. Ряд `openshift_unavailable_replicas` — обязательная защита от случая, когда `max by` по сохранившимся подам выглядит непрерывным после исчезновения другого пода.

| Наблюдение | Причина | Влияние на SLA-вердикт |
| --- | --- | --- |
| Ожидаемый сервис или его сигнал не дал ряда | `RESOURCE_SERIES_NOT_FOUND` | `NO_VERDICT` |
| Более одного ряда подходят к точной паре | `PLATFORM_SERIES_AMBIGUOUS` | `NO_VERDICT` |
| Единица ряда не совпадает с правилом | `PLATFORM_UNIT_MISMATCH` | `NO_VERDICT` |
| Нет снимка для объявленных `platform_rules` | `RESOURCE_SNAPSHOT_REQUIRED` | `NO_VERDICT` |
| В связанном ряду есть `null` в окне | `MISSING_RESOURCE_CELLS` | `NO_VERDICT`; найденные нарушения остаются в findings |
| То же у `effect=diagnostic` | Причина остаётся в coverage | Само diagnostic-правило не меняет вердикт |
| Сервисный ряд непрерывен, но исчез под до агрегации | Обнаруживается рядом `unavailable_replicas`, если профиль его поставил | SLA-проверка availability; гарантия профиля ещё не проверена |

Допуск пропусков можно рассмотреть после замера их частоты на реальных длительных прогонах; пункт 9 плана замера ADR 0014 ещё не выполнен (`0014:1128-1130`). Решение потребует отдельно определить, побеждает ли уже установленный `FAIL` непроверенную часть данных; см. раздел 6.

## 6. Свёртка business x resource x platform по окнам и плечам

Рекомендуемая свёртка использует существующую структуру результата. В **каждом анализе плеча** для каждого окна:

1. Бизнес-часть сворачивает применимые правила: блокирующий `NO_VERDICT`, затем найденный `FAIL`, затем `PASS`; нет применимых правил — `NO_POLICY`.
1. Ресурсная часть сворачивает `effect=sla` из снимка **либо** развёрнутые платформенные правила. Diagnostic-правила не участвуют. Порядок уже реализован как `NO_VERDICT > FAIL > PASS`, пустой список — `NO_POLICY` (`ResourceStatistics.kt:46-72`).
1. `jointVerdict` соединяет бизнес- и ресурсный вердикты окна: `NO_VERDICT` побеждает, оба `NO_POLICY` дают `NO_POLICY`, затем побеждает `FAIL`, иначе `PASS` (`WindowPolicy.kt:46-55`).
1. `overallVerdict` сворачивает окна: любой `NO_VERDICT`, затем все `NO_POLICY`, затем любой `FAIL`, иначе `PASS` (`WindowPolicy.kt:57-63`).

Платформенные правила являются ресурсными после binding, поэтому отдельного третьего столбца в `window_policy_summary` нет; существующие `business_verdict` и `resource_verdict` сохраняют смысл (`WindowPolicy.kt:65-80`). Между плечами ядро ничего не сворачивает и не сохраняет «вердикт стенда»: UI показывает два независимых вердикта и одну общую бизнес-часть, как требует ADR 0014 (`0014:582-589`). Если понадобится заголовок «оба плеча», предлагается вычислять его только в UI тем же приоритетом и явно помечать производным. Нужность заголовка решает владелец.

Приоритет `NO_VERDICT` над `FAIL` уже принят для политики: ADR 0003 прямо задаёт `NO_VERDICT`, если транзакция не найдена или неоднозначна, даже при провале другого правила (`docs/adr/0003-policy-v1-metrics-evidence.md:133-141`). ADR 0005 сохраняет находки при таком вердикте (`docs/adr/0005-resource-window-sla.md:12-19`). F1 показывает их рядом с причиной, по которой вердикт пока не выдан. Рекомендация K — сохранить этот порядок.

| Случай | K: сохранить `NO_VERDICT > FAIL`, рекомендация | C: установленный `FAIL` побеждает пропуск |
| --- | --- | --- |
| В одном окне R1 нашло SLA-нарушение, R2 имеет пропущенную ячейку | Итог окна `NO_VERDICT`, код CLI 3; finding R1 виден. | Итог мог бы стать `FAIL`, код 2, лишь если нарушение R1 уже окончательно доказано. |
| Плечо A имеет `FAIL`, плечо B — `NO_VERDICT` | Сохраняются два вердикта. Необязательный производный заголовок UI был бы `NO_VERDICT`. | Два вердикта в ядре остаются; производный заголовок при ином приоритете был бы `FAIL`. |
| `TRANSACTION_NOT_FOUND`, `AMBIGUOUS_TRANSACTION`, `RULE_WINDOW_NOT_FOUND`, неоднозначный платформенный ряд либо `INVALID`/`DEGRADED` вход | `NO_VERDICT` | Тоже `NO_VERDICT`: структурная привязка или валидность не восстанавливается найденным нарушением. |

Аргумент в пользу C ограничен: для ресурсного правила уже найденная серия из `min_consecutive_cells` подряд нарушающих наблюдённых ячеек не исчезнет при заполнении других пропусков. Для бизнес-перцентиля, доли ошибок и throughput результат при неполных наблюдениях не обладает той же монотонностью. Поэтому C потребовал бы специального режима только для доказанного ресурсного нарушения и валидного бизнес-прогона. Он меняет ADR 0003 и ADR 0005, результаты существующих входов и golden-тесты; повышение версии `policy-evaluation` меняет `modules` ключа сопоставимости и требует отдельного повторного закрепления baseline по ADR 0017. Копирайт F1 тоже пришлось бы изменить. Рекомендация K оставляет этот переход вне ADR 0018; решение владельца всё ещё открыто.

## 7. Версия схемы политики и совместимость

Рекомендуется вариант A: аддитивно расширить `policy.v1` на месте. Поле `min_samples` и массив `window_ids` необязательны у бизнес-правила; верхнеуровневый `platform_rules` необязателен. Существующий обязательный непустой `rules` остаётся (`Policy.kt:429-447`; `policy.schema.json:4-27`). `schema_version` и `input_versions.policy` остаются `policy.v1` (`AnalysisResult.kt:95-104`). Старый валидный JSON сохраняет прежние canonical bytes и `policy_sha256`, так как валидатор хэширует исходный canonical JSON (`Policy.kt:61-70`); **оценка** старого файла может измениться из-за default-on gate раздела 1. Новый файл старый строгий читатель отвергнет как `UNKNOWN_FIELD` (`Policy.kt:429`, `:444`, `:544`), что безопаснее тихого игнорирования.

| Вариант | Выгода | Цена и решение |
| --- | --- | --- |
| A. Расширить `policy.v1` на месте — рекомендация | Один файл на протокол; свойства бизнес-правила остаются в самом правиле; `input_versions.policy` и ключ сопоставимости не меняются. | Это сознательное ослабление замороженного v1. Старые читатели не читают новые файлы; схема, редактор и документация меняются совместно. |
| B. Ввести `policy.v2` | Читатель явно отказывает по версии; граница контракта чище. | Изменяется `input_versions.policy`, входящий в ключ baseline (`BaselineComparison.kt:942-943`); при миграции протокола нужно повторное закрепление. Существующие редактор и подсказка для ИИ привязаны к v1 (`docs/user/slice-1-local-analysis.md:353-358`, `:475-490`). |
| C. Отдельный `platform-policy.v1` | Не меняет форму `policy.v1` для платформенных правил. | Второй файл и хэш, новый вход multipart job; `min_samples` и `window_ids` бизнес-правил всё равно требуют изменения политики, а прежнее владение SLA в снимке остаётся проблемой. |

ADR 0005 прямо говорил, что `policy.v1` остаётся неизменным (`docs/adr/0005-resource-window-sla.md:12-19`, `:34-37`). ADR 0009 оставил guard в ресурсных diagnostic-правилах (`docs/adr/0009-explicit-capacity-stages.md:34-35`); ADR 0011, как это пересказывает ADR 0014, отверг расширение `resource-snapshot.v1` «новым видом правила» ради необязательной возможности, которую можно вынести в отдельный план (`docs/adr/0014-resource-series-limits-autostep-arm-api.md:167-193`). Здесь `min_samples` и `window_ids` являются свойствами самого правила политики, а платформенное SLA-правило должно разделять с бизнес-правилами владение протоколом. Это обоснование выбора A, а не утверждение, что прежние ADR уже разрешили его. Переход к v2 требуется при смене смысла существующего поля или оператора, новом обязательном поле либо несовместимой свёртке.

Рекомендуемые проверки нового контракта:

| Поле или связь | Проверка |
| --- | --- |
| `min_samples` | Целое `20..1 000 000`; ниже пола — `MIN_SAMPLES_BELOW_FLOOR`; для throughput поле неприменимо. |
| `platform_rules[].scope` | Только `kind=service`, непустой массив уникальных точных имён, каждое до 128 байт UTF-8, не более 64 сервисов на правило; нарушение — `INVALID_SCOPE`. |
| `id` | Уникален совместно в `rules` и `platform_rules`; существующий `DUPLICATE_RULE_ID` расширяется на оба массива. Проверяется и длина развёрнутого `<id>/<service>`. |
| `window_ids` | Непустой массив уникальных id до 128 байт UTF-8, если поле присутствует; неверная форма — `WINDOW_IDS_INVALID`. Существование id проверяется при binding со снимком. |
| Общее число проверок | После разворачивания выполняются предел 256 ресурсных правил и бюджет evidence раздела 2; переполнение — `RESOURCE_LIMIT_EXCEEDED`. |
| Бизнес-метрики | Четыре существующие метрики и сочетания `lte`/`gte` не меняются (`Model.kt:37-51`, `Policy.kt:449-463`). |

Редактор политики в срезе U4 и нормативная подсказка для ИИ должны поддерживать и сохранять `platform_rules`, `min_samples`, `window_ids`. Нынешний редактор описан только для старых полей (`docs/user/slice-1-local-analysis.md:353-358`), а подсказка запрещает стадии и новые поля (`:475-490`); без её обновления правка или повторная генерация может молча потерять новые правила.

## 8. Влияние на identity

Identity строится как canonical JSON с `policy_sha256` и другими верхнеуровневыми ключами (`AnalysisResult.kt:26-58`). Ключ сопоставимости baseline выбирает лишь `source_type`, `engine`, `parsers`, `modules`, `input_versions`, `outputs`, `histogram`, `normalization`, `limits`; `policy_sha256` в этом списке нет (`BaselineComparison.kt:603-610`, `:942-943`).

| Вклад | Рекомендация и следствие |
| --- | --- |
| Байты политики | Новые поля меняют `policy_sha256` только у файлов, которые их содержат. Развёрнутые правила детерминированно выводятся из политики и снимка; отдельный хэш разворачивания не нужен. |
| Константы gate | Только при наличии политики добавить верхнеуровневый `verdict_gates` с `min_samples_floor`, `min_samples_default`, `throughput_exempt`. Блок не входит в `SEMANTIC_FIELDS`. |
| `analysis_id` и кэш | Из-за `verdict_gates` новый анализ с политикой получает иную identity и пересчитывается. Сохранённый старый анализ неизменяем. Анализ без политики (`NO_POLICY`) не меняется. |
| Сопоставимость baseline | Ключ остаётся прежним; автоматического повторного закрепления baseline из-за одного `verdict_gates` нет. Golden-тест обязан показать одинаковый ключ до и после. Риск старого закреплённого baseline с малой выборкой решает ADR-C, см. раздел 1. |
| Версии | `input_versions.policy = policy.v1` остаётся (`AnalysisResult.kt:99`); `modules` не повышаются при рекомендуемой свёртке K. Помещение gate в `limits` изменило бы ключ. |
| Плечо | `resource_arm` и его включение в ключ относятся к отдельному срезу ADR 0014 (`0014:494-540`), не к этому изменению. |
| Результат | Появляются причины и аддитивные поля evidence; golden-фикстуры результата обновляются даже там, где итоговый `PASS`/`FAIL` не изменился. |

Это осознанный компромисс: новое default-on поведение меняет `analysis_id`, но не объявляет метрики другого поколения для baseline. ADR 0017 предписывает не совмещать изменения identity: срез gate выпускается отдельно от `resource_arm` и ADR 0016 (`docs/adr/0017-baseline-candidates-and-confirmation.md:173-180`). Владелец должен подтвердить именно этот компромисс, а не только числа 20 и 100.

## Следствия

После решения владельца рекомендуемый порядок реализации: сначала ADR 0016 с ограничением перцентиля максимумом и необходимые срезы ADR 0014 для плеча и `interval_max`; затем отдельные PR для (1) gate выборки и режима, (2) окон правил, (3) правил платформы. Порядок не превращает предварительный `E_max` в принятый предел. Production dependencies не добавляются. Публичные изменения — схема `policy.v1`, причины и аддитивное evidence результата, поведение CLI/UI и условный блок identity — фиксируются в плане реализации до кода.

| Область | Ожидаемое изменение в PR реализации |
| --- | --- |
| Ядро политики | `Policy.kt`, `Model.kt`: парсер, gate, разделение блокирующих и информационных причин, поля правил. `WindowPolicy.kt`: применимость и пустые окна. |
| Ресурсы | `ResourceStatistics.kt`: применимость по окну и вызов существующего вычислителя. Небольшой код binding/разворачивания платформенных правил; отдельный файл допустим, если уменьшает сложность. |
| Контракты | `docs/contracts/policy/v1/policy.schema.json`, valid/invalid-примеры; только аддитивные поля внутри разрешённых объектов `analysis-result.v1`. |
| Identity и ввод | `AnalysisResult.kt`: условный `verdict_gates`; `LocalApi.kt` и CLI: конфликт владельцев SLA и код 4 для него. |
| UI | `verdictReasons.ts`, `verdictSummary.ts`, карточка F1 и редактор: отличать `SMALL_SAMPLE` от блокирующего `INSUFFICIENT_SAMPLES`, показывать сервис, окно и плечо. |
| Документация | `docs/user/slice-1-local-analysis.md`: поля политики, смысл операторов, причины, коды возврата и подсказка для ИИ; `CHANGELOG.md`: заметное пользователю поведение. |

Приёмочная матрица должна проверять конечные наблюдаемые исходы, а не только функции-помощники:

| Сценарий | Ожидаемое по рекомендациям |
| --- | --- |
| `n = 0, 19, 20, 99, 100`, умолчание 100 | Соответственно `METRIC_NOT_AVAILABLE`; `INSUFFICIENT_SAMPLES` и `NO_VERDICT`; помеченная оценка; помеченная оценка; `FULL`. Проверить и полный прогон, и окно точной транзакции. |
| `throughput_rps` с малым положительным счётом | `gte` может дать настоящий `FAIL`; gate его не прячет. При нуле сохраняется прежняя причина. |
| R1 `checkout`, `steady-1`, `n=30`, минимум 50, расчётный `PASS`; R2 overall с `FAIL` | Вариант 1: итог `FAIL`, код 2, у R1 `SMALL_SAMPLE`, coverage `INCOMPLETE`, finding R2 виден. |
| Неизвестный `window_ids`; окно без применимых бизнес-правил | `RULE_WINDOW_NOT_FOUND` и `NO_VERDICT`; соответственно бизнес-часть `NO_POLICY`, не пустой `PASS`. |
| Из 20 ожидаемых сервисов отсутствует один; два подходящих ряда; неверная `unit` | Соответственно `RESOURCE_SERIES_NOT_FOUND`, `PLATFORM_SERIES_AMBIGUOUS`, `PLATFORM_UNIT_MISMATCH`; ни один случай не даёт молчаливого `PASS`. |
| `platform_rules` без снимка; одновременно SLA-правило снимка | Соответственно `RESOURCE_SNAPSHOT_REQUIRED`/`NO_VERDICT` и отказ `PLATFORM_RULES_CONFLICT` до анализа, CLI 4. Diagnostic guard допускается. |
| Платформенное окно короче `min_consecutive_cells`; пропуск после доказанной серии | `RULE_WINDOW_TOO_SHORT`/`NO_VERDICT`; соответственно `MISSING_RESOURCE_CELLS`/`NO_VERDICT` с сохранённым finding. |
| Два плеча одного прогона | `FAIL` на A и `PASS` на B остаются двумя результатами; бизнес-метрики UI показывает один раз. |
| Identity и baseline | При gate меняется `analysis_id`, но `semanticKey` совпадает; statistical baseline отвергает анализ с `SMALL_SAMPLE` через `INCOMPLETE`. |
| Совместимость | Старый валидный файл сохраняет canonical hash; новый файл старый читатель отвергает, новый читатель сохраняет все новые поля при редактировании. |

Перед выпуском каждого среза требуется проверить относящиеся к нему контракты, golden-результаты, CLI, UI и документацию. Нельзя считать стадийный gate пройденным по синтетическим тестам профиля: доступность подов, сбросы счётчиков и пропуски требуют реального прогона.

## Отклонённые альтернативы

| Альтернатива | Причина отклонения в рекомендуемом проекте |
| --- | --- |
| Сохранённый общий вердикт стенда в ядре | Владелец определил независимые вердикты плеч; смешение лишило бы анализ собственного смысла. Производный заголовок UI остаётся вопросом. |
| Держать платформенные SLA только в снимке или профиле | Сохраняет двух владельцев порога и меняет semantic hash снимка при его правке, заставляя перепривязывать планы, зависящие от снимка. |
| Добавить `arm` в правило | Опечатка способна отключить правило одного плеча; плечо уже задаётся анализом и снимком по ADR 0014. |
| Wildcard или regex для сервисов | Не выражают полный ожидаемый состав и не обнаруживают отсутствующий сервис так надёжно, как явный список. |
| Автоопределять стадии | Стадии протокола должны быть объявлены; ADR 0009 уже отверг детектор плато. |
| Ввести `SMALL_SAMPLE` как новое значение `policy_verdict` или верхнеуровневое поле результата | Закрытый enum и `additionalProperties: false` потребовали бы изменения схемы результата (`analysis-result.schema.json:37-64`); причины и evidence достаточны. |
| Отдельный вычислитель платформенных правил | Дублирует `evaluateRule`, его обработку пропусков, findings и приоритеты. |
| Ввести допуск пропусков до замеров | Нет измеренной частоты пропусков и согласованного порядка между доказанным `FAIL` и непроверенной частью. |
| Поместить пол и умолчание в `limits` | `limits` входит в `SEMANTIC_FIELDS`; возник бы лишний переход baseline. |
| Варианты 2 и 3 малой выборки, вариант C свёртки | Их цена и сохраняющийся вопрос владельцу изложены в разделах 1 и 6. |

## Риски и непроверенное

- Пороги 20 и 100 не калиброваны по прогонам стенда. Граница, на которой текущий HdrHistogram перестаёт давать p95, равный максимуму, не проверена; до ADR 0016 существует риск ложного `FAIL`.
- Сбросы OOM/restart-счётчиков и потеря первого приращения нового ряда после пересоздания пода на стенде не проверены. Смысл и запрос каждого сигнала должен быть зафиксирован профилем P0.
- Ядро не видит исходный состав подов после pod→service. Гарантия покрытия зависит от запроса, поставляющего `openshift_unavailable_replicas`; его отсутствие должно быть обнаружено проверкой ожидаемых рядов.
- `E_max = 20 480` предварителен. `interval_max` и `arm` приняты в ADR 0014, но ещё отсутствуют в `src/main`. Частота пропусков за реальные восьмичасовые прогоны неизвестна.
- Вариант 1 не даёт отдельного кода возврата для малого `PASS`/`FAIL`; скрипт, читающий только exit code, не увидит режим. UI-тексты раздела 1 ориентировочные.
- Старый вручную закреплённый baseline может иметь малую выборку без новой метки. Неизменный ключ сопоставимости не доказывает его пригодность; ADR-C должен определить проверку или повторный анализ.

## Открытые вопросы владельцу

1. Как трактовать малую выборку при `20 <= n < min_samples`: вариант 1, 2 или 3 раздела 1? **Рекомендация: 1**, с явной меткой и ограничением baseline.
1. Подходят ли пол 20, умолчание 100 и исключение throughput; нужен ли пол вообще либо он должен действовать только на предполагаемый `PASS`? **Рекомендация: оставить предложенный пол**, пересмотреть по первым реальным прогонам и тесту HDR.
1. Включать ли gate по умолчанию с `verdict_gates` вне ключа или только при явном поле правила? **Рекомендация: default-on**, иначе нынешний дефект остаётся у всех существующих политик.
1. Выбрать расширение `policy.v1` на месте (A), `policy.v2` (B) либо отдельный платформенный документ (C)? **Рекомендация: A** с признанной односторонней совместимостью читателей.
1. Сохранить `NO_VERDICT > FAIL` (K) или принять ограниченный вариант C для доказанного ресурсного `FAIL`? **Рекомендация: K**, согласно ADR 0003, ADR 0005 и F1.
1. Оставить для малого `PASS`/`FAIL` коды CLI 0/2 или ввести отдельный код, например свободный 7? **Рекомендация: 0/2** с обязательной машинной меткой в JSON и явным UI; риск скриптов, читающих только код, должен быть принят отдельно. Сейчас CLI пишет в stderr только ошибки (`CommandLine.kt:62-90`, `:277-290`).
1. Считать ли CPU throttling diagnostic либо SLA и какие сигналы обязательны для каждого типа сервиса? **Рекомендация: SLA для близости памяти к лимиту, OOM, рестартов и недоступных реплик; throttling — diagnostic**. Численные пороги устанавливает владелец протокола.
1. Одинаковы ли ожидаемые сервисы и пороги двух плеч? **Рекомендация: одна политика**, пока это верно; при различии — два явных файла, без `arm` внутри правила.
1. Нужен ли допуск пропусков после замера на стенде и следует ли отдельно исправить ложный `PASS` существующих правил снимка/профиля на окне короче `min_consecutive_cells`? **Рекомендация: допуск отложить до замера; исправление старого пути оформить отдельным решением**, поскольку оно меняет результаты старых входов.
1. Показывать ли производный заголовок «оба плеча»? **Рекомендация: сначала два независимых вердикта без заголовка**; если он нужен, рассчитывать и подписывать его только в UI.

## Не входит

Jenkins; артефакт с данными по подам (ADR-D); история релизов и правило «baseline только из `PASS`» (ADR-C, которому передаётся требование `sample_mode = FULL`); печать хэша (ADR-E); ограничение советов ИИ (ADR-F); корреляции и их калибровка (ADR-G, фаза C); реализация автошага ADR 0014; новые production dependencies. Свёртка подов адаптером остаётся границей П-1 ADR 0014 (`0014:1173-1179`).

**REPORT-ONLY наблюдение вне объёма:** у существующего ресурсного правила из `snapshot.rules` или профиля окно с числом ячеек меньше `min_consecutive_cells` не может создать finding и сейчас получает `PASS` (`ResourceStatistics.kt:269-270`, `:315-319`). Этот ADR предлагает защиту только для новых развёрнутых платформенных правил; старый путь не исправляется без отдельного решения владельца.

## Documentation impact

Этот PR меняет только `docs/adr/`. Схемы, примеры, пользовательская документация и `CHANGELOG.md` обновляются в соответствующих PR реализации после решения владельца.
