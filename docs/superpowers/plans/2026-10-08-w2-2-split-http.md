## Что выяснено фактами (до реализации)

- `LocalApi.kt` (2718 строк): `installLocalApi` одна функция на ~1100 строк (182-1282) с лямбдами маршрутов (в перечне названо 73; фактически зарегистрировано 53 пары метод+путь и замыкающий `/api/{...}`, подсчёт по дереву маршрутов Ktor); ниже
  ~1400 строк закрытых (`private`) помощников всех ресурсов вперемешку. Единственный потребитель вне файла:
  `LocalServer.startLocalServer` вызывает `installLocalApi(context)`; тесты используют `LocalApiContext`,
  `startLocalServer` и `copyBoundedUpload` (все `internal`, один пакет `io.ltverdict.web`).
- Функции длиннее ~200 строк в `web/`: `installLocalApi` (~1100) и `receiveJob` (320, строки 1912-2230). Длинная лямбда
  маршрута `analytics` (160) укладывается в предел. Критерий «нет функций длиннее ~200» требует разрезать и `receiveJob`
  (Ruling R4).
- Ktor 3.5.2 выбирает маршрут по качеству селектора (константа лучше параметра, `{...}` хуже всего), а не по порядку
  регистрации; двух зарегистрированных маршрутов с одинаковым путём и методом нет, `route("/api/{...}")` (404 для
  неизвестного) остаётся регистрироваться последним. Порядок регистрации поэтому не наблюдаем (Ruling R2); это проверяется
  таблицей маршрутов и обходом всех маршрутов.
- Помощники пересекаются между ресурсами: `baselineString`, `baselineOperation`, `resolveBaselineScope` (baseline <-> release,
  analytics), `releaseTextField`, `releasesOfAnalyses`, `releaseLabel`, `releaseProfile` (release <-> baseline, analytics),
  `receiveBaselineRequest` (jenkins, grafana, baseline, release), `requireAnalysis` (почти все), `RUN_ID`, `MAX_RESOURCE_BYTES`,
  `MAX_POLICY_BYTES`. Они получают видимость `internal` (были `private` только потому, что файл был один).
- Циклы `core` <-> `storage` существуют сейчас (`core/AnalysisService.kt` и `core/AnalysisResult.kt` импортируют
  `storage.*`, `storage/RunBundleStore.kt` импортирует `core.*`). Этот PR их не трогает; это цель третьего PR.

## Ruling

- **R1. Три цели W2.2 три PR; здесь только маршруты.** Почему: поручение оркестратора и условие 3 исключения; доменные
  правила и хранилища это независимые перемещения с отдельными рисками (хэши identity, формат на диске). Цена ошибки: больше PR;
  обратимо.
- **R2. Порядок регистрации маршрутов не сохраняется (группировка по ресурсам).** Почему: Ktor выбирает по качеству
  селектора, дубликатов нет (проверка: таблица маршрутов, 53 записи метод+путь и замыкающий `/api/{...}`, все уникальны; обход шлёт запрос на каждый
  шаблон и сравнивает ответ с замороженным), замыкающий `/api/{...}` регистрируется последним. Цена ошибки: другой
  обработчик на каком-то пути; ловит снимок ответов.
- **R3. Регистраторы это расширения `Route.xxxRoutes(...)`, общие помощники в `ApiSupport.kt`.** Почему: рекомендуемая в
  Ktor структура; не интерфейс и не реестр (MINIMAL-CHANGE, п. 5). Общего состояния (кэш рядов, семафоры, токены) регистраторы
  не создают: они создаются в `installLocalApi`, как раньше, и передаются явными параметрами. Цена: файлы `*Routes.kt` видят
  друг друга через `internal`.
- **R4. `receiveJob` режется в этом PR.** Почему: критерий W2.2 «в web нет функций длиннее ~200 строк», `receiveJob`
  (320) его нарушает, и это функция HTTP-слоя. Делается минимально: переменные-накопители выносятся в приватный holder, цикл
  `forEachPart` остаётся одним блоком (в нём шесть почти одинаковых ветвей остаются дословными: дублирование предпочтительнее
  абстракции), проверки привязок и сборка запроса выходят в две функции. Порядок: чтение частей, проверка `run_id`,
  проверка online-источника, чтение input, привязки по очереди (resources, diagnostics, capacity, trend, pod view, platform),
  контексты OpenSearch, PostgreSQL, сборка. Цена ошибки: изменённый порядок ошибок валидации; ловят 20+ существующих тестов
  заданий и обход (отдельный коммит, чтобы его можно было отклонить).
- **R5. Снимок ответов нормализует только недетерминированное** (UUID заданий, метки времени ISO-8601, идентификаторы
  релизов, порт заглушки, токен CSRF и cookie) и для гоночных ответов (статус задания сразу после отправки) сравнивает только
  статус и набор ключей. Всё остальное, включая тело отчёта HTML, сравнивается по SHA-256. Почему: иначе тест мигает (проверено
  повторными прогонами). Цена: формат метки `updated_at`, которую создаёт сам обработчик `PUT /api/releases/{releaseId}`
  (`Instant.now().truncatedTo(MILLIS)`), в снимке нормализован; поэтому тест отдельно проверяет его форму регулярным
  выражением (замечание Astra принято).
- **R6. Успешные ветви Jenkins и Grafana проверяются локальной заглушкой.** Astra верно указала: существующие тесты
  (`LocalApiTest`, e2e с моками браузера) не защищают успешные `collect` и `render`. Поэтому снимок включает второй сервер с
  настоящими `JenkinsWorkflow` и `SourceHttp` против заглушки на JDK `HttpServer` (как в `JenkinsWorkflowTest`). PostgreSQL
  capture и ИИ-совет остаются на ранних ветвях (профиль не настроен / нет раннера): их успешные пути покрыты существующими
  тестами или требуют JDBC и внешнего ИИ, это вне цели.
- **R8. Совет Codex Astra (read-only) учтён.** Принято: `BaselineScope` internal; `releaseProfile(JsonElement?)` остаётся
  private (пересекается только расширение с nullable-получателем); число маршрутов 53 + замыкающий; инварианты ниже; порядок
  валидации частей multipart сохраняется (проверка идёт при чтении, в порядке прихода, до проверки `run_id`); тест порядка частей,
  неподдерживаемых методов, слэша в конце; успешные Jenkins/Grafana; проверка формы `updated_at`. Не принято как отдельная
  работа: управляемое выполнение заданий (после `awaitComplete` статусы устойчивы, гонки есть только в ответе на отправку,
  он сравнивается по статусу и ключам; повторные прогоны дают тот же снимок).

### Инварианты, которые сохраняет разрезание (из совета Astra)

- Перехватчик безопасности и отображение исключений остаются на уровне приложения (`intercept(ApplicationCallPipeline.Plugins)`
  в `installLocalApi`), не внутри `/api`: иначе SPA потеряет заголовки.
- Состояние установки создаётся в `installLocalApi` один раз и передаётся: один `SnapshotCache` на оба маршрута рядов, один
  `jenkinsPermit` (java.util.concurrent.Semaphore, мгновенный отказ `JENKINS_BUSY`), один `postgresCapturePermit` на оба
  маршрута pre/post (Java Semaphore), один `podViewPermit` (корутинный Semaphore, ожидание), токены сессии и CSRF; `finally`
  с `release()` не двигаются.
- Замыкания `listOf("pre","post").forEach { phase -> ... }` и `mapOf(route to name).forEach` переносятся целиком в свой
  регистратор вместе с захваченными значениями.
- `receiveJob`: цикл `forEachPart` с валидацией по приходу части остаётся одним блоком; `catch` вокруг чтения частей
  (пропускает ApiFailure и Invalid*, остальное превращает в «Multipart body is malformed») охватывает только чтение; привязки
  и сборка вне него.
- **R7. Файлы документов ADR со ссылками на номера строк `LocalApi.kt` не правятся.** Почему: исторические записи, номера
  устарели и до этого PR. Цена: нет.

4. В `src/main/kotlin/io/ltverdict/web` нет функции длиннее 200 строк (скрипт подсчёта из шага проверки).

   прежнему `LocalApi.kt` плюс объявленные добавления (заголовки, импорты, объявления регистраторов, `internal`, holder
   `receiveJob`); отчёт скрипта в отчёт оркестратору.
6. Полный набор «Без CI» на результате слияния с `origin/main`: `Invoke-LtvExclusive { gradlew --no-daemon cleanTest check

   потому что это HTTP-слой; `python tools/verify_slice0.py`; `python tools/changelog_assemble.py --check`; markdownlint для
   изменённых `.md`.
