# Синтетический набор данных «8 часов» для показа UI

Генератор и сборщик каталога данных, после которых `ltv ui --data-dir <dir>`
открывается с заполненными релизами, историей, сравнением, платформой, трендами
и pod-view. Сценарий: «Checkout, релиз 2026.09.3», тест 8 часов по сценарию
макета интерфейса. **Данные придуманы, это не реальный прогон**: числа, имена
сервисов и поды не относятся ни к какому стенду.

Что здесь есть:

- `tools/demo_dataset.py` строит входы (JTL, политики, снимки ресурсов по плечам,
  планы трендов и корреляций, pod-view, контекст OpenSearch, стадии);
- `tools/demo_dataset_build.py` запускает `ltv analyze` по матрице из 14 анализов,
  поднимает `ltv ui` без браузера и через локальный HTTP API сохраняет релизы и
  baseline (в CLI таких команд нет);
- `scenario.json` рядом: стадии, транзакции, сервисы и числа подов, релизы, сюжет,
  наклоны трендов, пороги политики. Сгенерированные файлы в репозиторий не попадают.

Ядро, схемы, API и UI не менялись. Только стандартная библиотека Python.

## Что внутри

Серия `Checkout`, шесть релизов, профиль нагрузки (шесть полей релиза) у всех
одинаков. Ожидаемые вердикты проверены реальными запусками (профиль `demo`):

| Релиз | Начало (UTC) | Плечо A | Плечо B | Особенность |
| --- | --- | --- | --- | --- |
| 2026.09.3 (текущий) | 2026-09-29 10:00 | FAIL (2 правила) | FAIL (3 правила) | сюжет макета: колено на 224-й минуте |
| 2026.09.2 (baseline) | 2026-09-22 10:00 | PASS | PASS | p95 checkout около 820 мс |
| 2026.09.1 | 2026-09-15 10:00 | PASS | PASS | p95 около 860 мс |
| 2026.09.0 | 2026-09-08 10:00 | NO_VERDICT | NO_VERDICT | в JTL нет `POST /checkout` (`TRANSACTION_NOT_FOUND`) |
| 2026.08.3 | 2026-08-25 10:00 | FAIL (1) | FAIL (1) | p95 checkout около 2110 мс |
| 2026.08.2 | 2026-08-18 10:00 | PASS | PASS | третий PASS для статистического baseline |

Анализов 14: по два (A, B) на каждый из шести запусков и один анализ стадий S у
2026.09.3 и 2026.09.2. Baseline (`manual`, 2026.09.2) задан для слотов A, B и для
слота без плеча (анализ S).

Нарушения 2026.09.3: на B это `checkout-p95` (p95 3025 мс при пороге 2000),
`checkout-errors` (885 из 51 161, 1,73 % при пороге 1 %) и `restarts/payments-svc`
(`sla`); на A только первые два. Диагностические правила на B дополнительно
помечают `memory-limit/payments-svc` и `cpu-throttling/checkout-api`.

Сюжет (плечо B, релиз 2026.09.3): под 2 сервиса `payments-svc` упирается в память
(пила с периодом около 84 мин, 3 рестарта на 228-й, 312-й и 396-й минутах, два
из них в окне `soak`); два пода `checkout-api` в троттлинге после 150-й минуты;
один горячий под `catalog-svc` на обоих плечах. Тренды в `soak`: Old Gen, потоки
и пул соединений `checkout-api`, память сайдкара `gateway`, CPU JVM `payments-svc`.
20 сервисов и БД (21 нагрузка), 78 подов на плечо.

## Профили и замеры

Профиль выбирается `--profile`. По умолчанию `demo`.

| Профиль | Нагрузка | Назначение |
| --- | --- | --- |
| `demo` (по умолчанию) | `--rps-scale 0.2`, ось 10:00-18:00 | показ и приёмка UI |
| `full` | истинные 121 зпр/с на плато | необязательно, диск в пять раз больше по JTL |
| `tiny` | 24 мин, 4 нагрузки, `0.02` | тесты, быстрая проверка сборки |

В `demo` остаются верными ось времени, границы и множители стадий, колено, наклоны
трендов, доля ошибок, форма p95, число сервисов, подов и рядов. Абсолютные RPS в
пять раз ниже (меньше RPS, а не короче длительность: окна и тренды `soak` не
меняются).

Измерено на этой машине (Windows 11, JDK 21), реальные числа:

| Что | `demo` | `full` | `tiny` |
| --- | --- | --- | --- |
| Строк JTL, релиз 2026.09.3 | 735 211 | 3 676 036 | 3 686 |
| Размер JTL, 2026.09.3 | 31,2 МБ | 155,9 МБ | 0,16 МБ |
| Время генерации одного JTL | 3,6 с | 16,9 с | менее 1 с |
| Снимок ресурсов плеча (275 рядов, 1 920 ячеек) | 2,8 МБ | 2,8 МБ | 0,04 МБ |
| pod-view плеча (78 подов, 540 строк, 240 колонок) | 0,86 МБ | 0,86 МБ | 0,04 МБ |
| Входы всех шести релизов | 221 МБ, 68 файлов | не собирался | 1,9 МБ, 68 файлов |
| Каталог данных после 14 анализов | 351 МБ | не собирался | не замерялся |
| Генерация входов всех релизов | 37,7 с | не замерялась | не замерялась (менее 5 с) |
| 14 анализов | 227,9 с (около 16 с на анализ) | один анализ JTL 156 МБ без политики: 24 с | около 24 с |
| Сохранение релизов и baseline через API | 1,7 с | не замерялась | 1,6 с |
| Сборка целиком | 4 мин 27 с | не собиралась | около 26 с |

`full` целиком не собирался: измерены только генерация и разбор одного JTL.
Шесть таких запусков и их копии в каталоге данных дадут около 2 ГБ (оценка по
измеренному JTL, не замер). Пиковая память разбора не измерялась. Нужно свободное
место примерно вдвое больше размера входов: каталог данных хранит копию каждого
запуска (скрипт сборки проверяет это перед запуском).

Формат JTL один для всех релизов: шесть колонок
`timeStamp,elapsed,label,responseCode,success,failureMessage`. Парсер принял 4, 6 и 7
колонок (проверено запусками `ltv analyze`); с шестью колонками остаются коды ответа
и сообщения об ошибках, значит работают группы ошибок.

## Сборка

Сначала дистрибутив из корня репозитория:

```text
./gradlew installDist -x test
```

Всё одной командой (Windows, из корня репозитория):

```text
python -m tools.demo_dataset_build --ltv build\install\ltv\bin\ltv.bat --out build\demo-8h\inputs --data-dir build\demo-8h\data --profile demo
```

Linux и macOS:

```text
python -m tools.demo_dataset_build --ltv build/install/ltv/bin/ltv --out build/demo-8h/inputs --data-dir build/demo-8h/data --profile demo
```

Показ:

```text
build\install\ltv\bin\ltv.bat ui --data-dir build\demo-8h\data
```

Скрипт отказывает на непустом каталоге данных (без `--force-new`): анализы
идемпотентны, а повторное сохранение релиза даёт «уже входит в релиз». Каталог
данных открывает один процесс: `ltv ui` стартует только после всех `ltv analyze`.
Только генерация входов без анализов:

```text
python -m tools.demo_dataset generate --out build/demo-8h/inputs --profile demo
```

`ltv ui` скрипт запускает с `JAVA_OPTS=-Djava.awt.headless=true`: так браузер не
открывается, а адрес (`http://127.0.0.1:<порт>`) печатается в stderr отдельной
строкой (проверено). Мутирующим запросам нужны `Host` и `Origin` сервера, cookie
`ltv_session` и заголовок `X-LTV-CSRF` из `GET /api/bootstrap`. Для локальных
вызовов Python используется открыватель без системного прокси; иначе прокси
перехватывает loopback на машинах с общей настройкой прокси.

Тесты: `python -m unittest tools.test_demo_dataset -v` (профиль `tiny`, включая
побайтовый детерминизм и зафиксированные хэши файлов 2026.09.3). С `LTV_BIN`
(путь к `ltv`) дополнительно запускается `ltv policy validate` для обеих политик.
Повторная сборка `demo` в чистый каталог дала те же 14 `analysis_id` и те же
SHA-256 всех входных файлов (проверено). Любое осознанное изменение генератора меняет хэши, `analysis_id` и golden-тест.

## Стадии и платформа в разных анализах

Продукт запрещает `--stages` вместе с `--resources` (`STAGES_RESOURCES_CONFLICT`,
ADR 0030, R3). Поэтому лента стадий видна на анализе S (политика только из
бизнес-правил, потому что платформенное правило `sla` без снимка блокирует вердикт),
а платформа, поды и тренды на A и B. Запрет будет снят отдельным ADR. Для такого
перехода всё изолировано в одном месте: `analysis_matrix(..., combined_stages)`
в `tools/demo_dataset_build.py` и флаг `--combined-stages` (константа
`STAGES_WITH_RESOURCES`). С флагом анализы A и B получают `--stages`, а отдельный
анализ S и его политика в матрице исчезают. Пока запрет действует, флаг не
запускайте: ядро отклонит такой вызов. Переход проверен только на уровне матрицы вызовов
(14 анализов превращаются в 12), реальным запуском не проверялся.

## Чего воспроизвести нельзя

1. Лента стадий и платформа на одном экране (см. раздел выше).
2. Карточки «Требует внимания» с evidence: инциденты v0 не входят в
   `analysis-result` и UI.
3. ИИ-разбор: экран остаётся пустым, записанный совет не создаётся (решение
   владельца 2026-11-19).
4. График колена ёмкости: анализ ёмкости (необязательная Task 9 плана) не
   собирался, `capacity_knee` не откалиброван.
5. Pod-view с шагом 15 с: предел 240 колонок даёт шаг 120 с (в `tiny` 60 с).
   Рестарты в pod-view отсутствуют (в его схеме нет такой метрики): они видны в
   ряду `openshift_restarts` снимка, а у пода 2 `payments-svc` в pod-view видна
   пила памяти.
6. Онлайн-источники Prometheus/OpenSearch/PostgreSQL на экране «Новый анализ»:
   офлайн доступна только ветка загрузки файла.
7. Вердикт «3 из 9» на обоих плечах: нагрузка одна, поэтому бизнес-правила
   нарушены и на A (нарушены 2 правила), на B нарушены 3.
8. Как UI считает «n из 9» (шаблоны правил или развёрнутые проверки): не проверялось.
9. Статистический baseline: нужны три PASS с одним профилем (2026.09.2, 2026.09.1,
   2026.08.2); в набор заложены, режим `statistical` скрипт не вызывает.
10. Время UI: JTL хранит UTC, начало запусков 10:00Z; макет показывал локальное время.

История ограничена шестью релизами (решение владельца 2026-11-19); релизы 2026.08.4
(4 часа, другой профиль), 2026.08.1 и 2026.07.4 из макета не строились.

## Необязательно: слить ошибки OpenSearch в снимок

Контекст OpenSearch подаётся на `analyze` флагом `--source-context`, в снимок он не
сливается: `ltv opensearch prepare` перезаписал бы снимок и сломал привязки хэшей.
Слияние через `ltv opensearch prepare --resources` не проверялось и в сборку не
входит.
