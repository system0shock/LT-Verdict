# Агентное расследование на Qwen Code: отчёт разведки и план пилота

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** ответить на предложение владельца (расширить ИИ-разбор до агентного расследования на native workflow Qwen Code) ограниченным пилотом в харнессе: проверить поддержку workflow в Qwen Code 0.21.1, зафиксировать границы доступа и контур безопасности, измерить качество, стоимость, задержку и воспроизводимость относительно одношагового разбора (prompt v1/v2) и руки C плана ИИ.

**Architecture:** пилот не меняет продукт. Инструменты ядра и чтения репозитория исполняются шлюзом вне контейнера Qwen (MCP по HTTP); шлюз ничего не вычисляет, а отдаёт заранее записанные ответы ядра («пакет ответов») и маскированное содержимое снимка репозитория, и сам не имеет маршрута наружу; relay считает и ограничивает запросы и сверяет модель; журнал источников и действий пишут шлюз и relay. Две руки: нативный `agent` в одной сессии Qwen (D1: `--safe-mode` без `--bare`, точный список исключений инструментов, проверка реестра) и своя оркестрация вокруг одиночных вызовов (D2: `--bare --safe-mode --max-tool-calls=0` как сегодня).

**Tech Stack:** Docker Engine 29.2.1 (Docker Desktop 4.62.0, прежняя проба), Qwen Code 0.21.1, Node.js (шлюз, mock relay), Python (харнесс, `unittest`), PowerShell (топология). Новых production-зависимостей нет.

**Spec:** `docs/adr/0024-agentic-investigation-on-qwen-code.md` (Proposed); связанные: `docs/adr/0010-advisory-ai-boundary.md`, `docs/adr/0021-advisory-ai-prompt-v2-and-schema-retry.md`, `docs/adr/0023-advisory-ai-consent-removal-and-model-config.md`, план `docs/superpowers/plans/2026-10-04-ai-v2-implementation.md`.

Материалы вне git (решение владельца 2026-10-04: материалы эксперимента не коммитятся), ссылки путями в code span: каталог проб `docs/ui-mockup/ai-experiment-2026-09-30/v3/qwen-agent-probe-assets/` (скрипты, mock relay, журналы запусков `runs/`), отчёт пробы `docs/ui-mockup/ai-experiment-2026-09-30/v3/qwen-agent-investigation-probe.md`, прежние `.../v3/qwen-workflow-recon.md` и `.../v3/qwen-container-probe.md`.

- Исходный код клиента (`customer`) к ModelStudio не уходит; расследование с репозиторием `customer` для профиля `external` запрещено (ADR 0024 Д4, п. 2). - Случаи холдаута ADR 0021 в пилоте не используются; метка prompt по умолчанию не меняется.
- Каждый контейнер пилота (Qwen, relay, шлюз) и каждая сеть несут метку `io.ltverdict.advisory-runtime`; чистятся только свои ресурсы по точным именам; контейнеры демо-стенда и других агентов не трогать.

### 1.3 Оценка осуществимости нативного workflow

1. **Технически осуществимо** при конфигурации: `--safe-mode`, без `--bare`, `--mcp-config` (HTTP к контейнеру инструментов), `--allowed-mcp-server-names=ltcore`, `--exclude-tools` по точному перечню (все инструменты, кроме `agent` и `structured_output`), `--allowed-tools=agent`, агенты в `/work/.qwen/agents` (read-only mount), `cwd` не репозиторий, relay с лимитом запросов и сверкой модели. Это **не** текущая изоляция ADR 0010 п. 6, а её замена набором проверок.
2. **Нативный `workflow` (скрипт) не рекомендуется**: модель сама пишет JS, исполняемый в `node:vm`; `maxTurns` агента перекрыт 50 ходами; лимит агентов по умолчанию 1000; токеновый бюджет мягкий (проверяется на входе диспетчера, проба: перерасход 1000 из 700); родитель всё равно решает, вызвать ли `workflow`; ещё 4,4 КБ описания на каждый запрос. Нативный `agent` проще и поддаётся ограничению `maxTurns`.
3. **Порядок и независимость рецензии не принуждаются**: hooks под `--safe-mode` недоступны, `structured_output` доступен с первого хода. Продукт может только проверить журнал после запуска и отказать в публикации.
4. **Цена**: запрос основного агента 27-39 КБ против 5,3 КБ у одношагового разбора (описание `agent` 12 КБ), минимальный конвейер orchestrator + researcher + reviewer 7-11 запросов и 76-212 КБ суммарно (пробы `r15`, `r3s`, `r3`) без реального evidence.
5. **Вывод**: нативный путь достаточен для **эксперимента**; для продукта аргументов в его пользу меньше, чем у своей оркестрации (D2): экономии запросов нет, исключений из ADR 0010 больше, порядок недетерминирован. Решение между D1 и D2 откладывается до дымового прогона и данных.

### 1.4 Бюджет и контроль

| Механизм | Что реально ограничивает (проба) | Достаточность |
| --- | --- | --- |
| `--max-tool-calls=N` | Только вызовы верхнего уровня (`agent` = 1, MCP родителя считаются, `structured_output` нет); вызовы детей не считаются (`r3tc3`: 11 запросов при пределе 3) | Недостаточно |
| `--max-session-turns=N` | Не считает запросы детей (`r6aturns2`: лимит 2, ребёнок сделал 3 запроса) | Недостаточно |
| `maxTurns` агента | Через `agent`: держит (3 запроса при `maxTurns: 3`, `r6e`); через `workflow` перекрыт 50 (50 запросов, `r6d`) | Частично |
| `--max-wall-time` | Для основного агента; влияние на детей не проверено | Не проверено |
| `QWEN_CODE_MAX_TOKENS_PER_WORKFLOW` | Только `workflow`, output tokens, мягкий (`r6c`) | Недостаточно |
| Relay: предел пересланных запросов + сверка модели | Авторитетный счётчик; единственный, кто видит все запросы всех агентов | Достаточно (нужен тест) |
| Шлюз: квоты вызовов и байтов | Ограничивает данные, ушедшие к модели | Достаточно (нужен тест) |

### 1.5 Оценка запросов, токенов и задержки (оценка)

Число запросов для нативной руки: `N = (m + 1) + Σ(k_i + 1)`, где `m` число вызовов `agent`, `k_i` число раундов вызовов инструментов у ребёнка `i` (параллельные вызовы раунда считаются одним). Пример пробы `r15`: `m = 2`, researcher `k = 1`, reviewer `k = 1`, итого `3 + 2 + 2 = 7`. Типичный случай расследования: `m = 2`, `k_1 = 3`, `k_2 = 2` дают 10; ошибка схемы итога добавляет 1 (ADR 0021 Д2); предел relay 16. Для руки D2 (свои одиночные вызовы) число запросов по тому же порядку: шаги расследования `s` плюс рецензия плюс итог (6-12).

Входные токены (оценка, 3,5-4 байта на токен, evidence порядка 6,5 тыс. токенов как в экспериментах ADR 0021): одношаговый разбор около 7 тыс.; нативный запуск `3 × (6,5 + 7,7) тыс.` на основном агенте плюс контексты детей (исследователь около 21 тыс., рецензент около 6 тыс.) то есть порядка 70 тыс., то есть в 8-12 раз больше. Выходные токены: основной итог около 13-16 тыс. (как в наблюдении прежних серий для других моделей) плюс 2-6 тыс. на каждый вспомогательный ход, то есть в 2-3 раза больше. Задержка: последовательные запросы; один запрос DeepSeek 57-131 с (итоговый), короткие ходы короче; ожидание 5-20 минут на расследование против 1-2 минут; для GLM 5.3 ещё в 2-3 раза больше. **Это не измерение**: пилот обязан заменить оценку данными (метрики ниже).

### 2.1 Инструменты ядра

Закрытый набор v1 только чтение (ADR 0024 Д3): `core_facts_list`, `core_result_get`, `core_series_catalog`, `core_series_values`, `core_compare_baseline`, `core_verify_number`; инструменты репозитория `repo_list`, `repo_read`, `repo_search`. Инструмент это **поиск готового ответа ядра**, а не вычисление в шлюзе. Пилот собирает **пакет ответов ядра** (`ltcore-tool-pack.v1`, закрытая структура пилота вне git и вне контрактов продукта) скриптом на хосте, который вызывает существующие GET-маршруты запущенного приложения: серии (`resource-series`, `resource-series/values`, D0a), `comparison`, `result` и проекцию evidence; пакет монтируется в шлюз read-only. Запрос вне пакета даёт `OUT_OF_LIMIT`. Продуктовый код не меняется, шлюз не имеет маршрута наружу (приложение слушает только `127.0.0.1` и проверяет `Host`, так что из контейнера оно недостижимо без нового listener: вопрос 13). `core_verify_number` ищет значение по ссылке или серии и сравнивает с заявленным, арифметики не выполняет; `core_stat` из v1 исключён (считать перцентили в Node это не ядро; p50/p95/p99 уже в `result`). Контракт ответа: `tool_contract`, `call_id`, `analysis_manifest_sha256`, `result`, `result_sha256`, `truncated`, `notes[]`, типизированные ошибки. Воспроизводимость: один вызов при том же `analysis_manifest_sha256` даёт тот же `result_sha256`; повтор журнала даёт побайтно те же ответы. Корреляции только прочитанные из сохранённого результата (заголовки ADR 0022); новых ad hoc корреляций в v1 нет (множественные сравнения).

### Контракт relay пилота (срез AG2)

Текущий relay продукта пилоту не подходит и копируется как есть быть не может: он (после #78) допускает ровно один инструмент `structured_output`, только текстовые сообщения (кроме продолжения повтора схемы) и не более двух запросов, а модель не отклоняет, а перезаписывает на закреплённую до проверки (`tools/advisory_ai_runtime_relay.mjs:82-100`, `:109`, `:118-124`, `:341-358`, `:383-387`). Relay харнесса (копия `relay2.mjs` плана ИИ) обязан:

1. проверять `model` во **входящем** теле до перезаписи, отклонять несовпадение (409) и писать в журнал;
2. для каждого запроса определять роль по SHA-256 системного prompt (оркестратор, исследователь, рецензент; в руке D2 шаги) и требовать, чтобы множество имён инструментов запроса **в точности равнялось** списку роли (`mcp__ltcore__...`); неизвестный prompt или лишнее имя: 409 и счётчик;
3. допускать сообщения ролей `assistant` с `tool_calls` и `tool`, не расширяя набор инструментов;
4. считать и ограничивать пересланные запросы на расследование (16; 11 на время смока) и общий ledger пилота (210) с атомарным резервом до пересылки;
5. ограничивать размеры тела запроса и ответа, писать журнал запроса (роль, размер, исход, `usage`) без текстов.

### Методика сравнения

1. **Руки.** A: prompt v1, один запрос; B: prompt v2, один запрос (ADR 0021); C: черновик, проверка, итог тремя одиночными вызовами через relay (W1 плана ИИ, если к моменту пилота выполнена); D1: расследование нативным `agent` (AG2, рука D1); D2: расследование своей оркестрацией (AG2, рука D2); E: дешёвая база сравнения: одношаговый совет (prompt v2) с заранее отобранными детерминированным правилом фрагментами репозитория (файлы по именам сервисов и ключам конфигурации из evidence), без агента и без рецензента. Модель, провайдер и temperature 0 как в руках A и B.
2. **Случаи.** 8 repo-случаев AG3 и 4 evidence-only случая из K01-K12. Для K01-K12 результаты рук S0 и S1 (prompt v1 и кандидат v2) уже получены экспериментом ADR 0021 на DeepSeek; для сравнения берутся они (оговорка: другие дни и харнесс), новые запросы на них только для руки D. Для repo-случаев нужны новые запросы для A, B и E (3 × 8 = 24) и, если рука C доступна, для C (3 × 8 = 24).
3. **Холдаут не используется.** Выбор случаев и правил фиксируется предрегистрацией до первого запроса.
4. **Разметка.** Слепой пул, перемешивание, два рецензента-модели, человека нет (как в ADR 0021 Д7); итог маркируется «model-reviewed». Для repo-случаев оракул причины и детерминированные Q4, Q5 не зависят от рецензентов. Утверждения о коде рецензент оценивает по цитируемым фрагментам снимка, которые пул предоставляет вместе с ответом.
5. **Сопоставимость.** Рука D получает больше информации (код, ядро), чем A и B; прямое сопоставление качества по repo-случаям нечестно по построению (A и B кода не видят). Поэтому: на repo-случаях сравнение D1 и D2 между собой и с C; на evidence-only случаях D сравнивается с A, B и C как проверка отсутствия ухудшения; стоимость и задержка сравниваются на всех. Рука E отвечает на вопрос, сколько эффекта на repo-случаях даёт сам доступ к коду, а сколько агентность: если E близка к D по попаданию причины, агентность не окупается.
6. **Статистика.** При n = 12 выводы описательные: таблицы, интервалы Уилсона, парный знаковый тест только там, где различий не меньше 5; никаких заявлений об эффекте без правила, зафиксированного заранее.

### Критерии продолжения и остановки (предложение автора, подтверждает владелец до первого запроса)

Остановка немедленная (любое одно): исполненная канарейка, утечка приманки секрета в advice, журнал или UI, выход за корень или запись, изменение хэшей анализа, реестр `init` не равен эталону, превышение предела relay.

Продолжение на AG6 после дымового прогона, если выполнено всё: Q4 100 %, Q5 100 % либо пометка, S1-S3 чисты, медиана запросов не больше 12 и p95 не больше 16, медианная задержка не больше 15 минут, не OK не больше 1 из 6 запусков. Это пороги для решения «стоит ли тратить дальше», а не доказательство качества.

**Решение о дальнейшей работе** (владелец по итогам AG6; это не принятие режима и не утверждение о качестве): продолжать к предрегистрированному холдауту на реальных инцидентах с человеческой оценкой стоит, если выполнено всё: на repo-случаях внесённая причина в топ-3 минимум в 5 из 8 и рука D не хуже руки E по этому показателю более чем на 1 случай в пользу E; на evidence-only случаях подтверждённых `hard_defect` не больше, чем у руки B, плюс 1 из 4; стоимость и задержка приемлемы владельцу. Иначе режим отклоняется, продукт остаётся на prompt v1/v2 и (по W5 плана ИИ) возможной руке C. Пилот не даёт оснований для общего вывода о качестве: восемь случаев с внесёнными дефектами, выбор руки после трёх смоков, руки A и B без доступа к коду и две модели-рецензента без человека.

5. **Источник ссылки на репозиторий и commit.** Рекомендация: ручной ввод и список `repo_id` развёртывания; расширение `local-release.v1` отдельным решением.
6. **Вопрос инженера и иммутабельность.** До 500 символов; до 5 расследований на анализ; базовый совет не заменяется. Рекомендация: да.
7. **Окно времени.** Отдельное окно расследования, не 600 с базового совета; значение по данным смокa. Рекомендация: да.
8. **Журнал.** Хэши и диапазоны без содержимого, срок как у анализа. Рекомендация: да.
9. **База знаний и связи сервисов.** Нужны источник и формат; без них в пилот не входят. Рекомендация: связи из манифестов репозитория, база знаний отложена.
10. **Рецензент той же модели.** Рекомендация: да в пилоте.
11. **`workflow`.** Рекомендация: не использовать.
12. **Критерии продолжения и остановки.** Подтвердить до первого запроса. Рекомендация: принять предложенные.
